# 推理强度选项云端动态化改进计划

## 1. 背景

一期「推理强度」四级下拉按用户拍板的**每接口静态声明**落地：kimi-acp 写死
`low/high/max`、kilocode-acp 写死 `high/max`，其余接口留空。用户随后提出
改进要求：**强度档位应从各后端的云端/CLI 目录动态获取**，以便模型目录
更新（新模型、新档位）时 IDE 零改动自动跟进。

本计划基于对 `参考代码/kilocode-main` 的源码研究（2026-08-06，explore
子代理全链路勘察）与 kimi CLI 既有实测记录（2026-0725-0205 计划），给出
分接口的动态化方案。

## 2. 一期现状（代码实证）

| 位置 | 现状 |
|---|---|
| `llm/registry.py` BackendSpec | `efforts: tuple[str, ...]` 静态声明 + `default_effort`；空 = 不支持 |
| `llm/providers/kimi_common.py` | `list_kimi_models()` 调 `kimi provider list --json` 但**只取别名**，丢弃 `support_efforts` / `default_effort` 字段 |
| `llm/providers/kilocode_acp.py` | `list_kilocode_models()` 调 `kilo models`（纯文本，无强度信息） |
| `gui/panels/chat/model_bar.py` | 第四级菜单**挂接口级**——只在切接口时重建（`_refresh_models` 尾部调 `_refresh_efforts`），切模型不重建 |
| `gui/settings.py` | `model_efforts` 记忆表：接口实现名 → 强度值（接口级粒度） |

关键限制：一期强度是**接口级**的，但真实世界的强度档位是**模型级**的
（kimi k3-256k = low/high/max，而 kimi-for-coding 可能只有 high/max；
kilo 各模型档位差异更大，见 §3）。动态化必须同时把粒度升级为模型级。

## 3. kilocode-main 研究结论（参考实现勘察，2026-08-06）

### 3.1 kilo 的 effort 选项不是常量，是「按模型动态计算」的 variants 表

- ACP `session/new` 的 configOptions 中 `{"id":"effort","category":"thought_level"}`
  的 options = 当前模型 `Provider.Model.variants` 的 key 集合
  （`packages/opencode/src/acp/config-option.ts:52-70,193-197`）；
- variants 由 `ProviderTransform.variants(model)` 生成——约 400 行按
  provider npm 包 × 模型 id 正则的大分支规则函数
  （`packages/opencode/src/provider/transform.ts:688` 起）：
  - Anthropic Claude 5+ = `low/medium/high/xhigh/max`，老式 Claude 仅
    `{high, max}`（budget 档）；Gemini 按 flash/pro 给 `[minimal,low,medium,high]`
    / `[minimal,high]` 等；deepseek/qwen 等直接 `{}`（无推理强度轴）；
  - 先决条件 `model.capabilities.reasoning` 为假则无 variants，ACP 侧
    `effort` configOption **整个缺席**；
  - Kilo Gateway 自有模型的 variants 直接来自 Kilo 目录数据的 `variants`
    字段透传（`kilocode/provider/provider.ts:60-73`），不经规则计算；
- **models.dev 缓存（`~/.cache/kilo/models.json`）不含档位枚举**——只有
  `reasoning: bool`，档位是 kilo 进程内代码算出来的，IDE 侧无法靠读
  缓存文件复刻（除非照抄 400 行规则，违反不臆造红线）。

### 3.2 IDE 侧可用的三条数据通道（研究给出的可行性小结）

| 通道 | 粒度 | 成本 | 评价 |
|---|---|---|---|
| ACP configOptions（session/new 与 set_config_option 响应内嵌） | 会话级、**仅当前模型** | 协议内建零额外成本 | 最正路但需先起会话；一次只看一个模型 |
| `kilo models --verbose` | 全局、模型级全量 | 一次 CLI 子进程 + 自行切分「id 行 + pretty JSON 块」混排输出 | **唯一能离线枚举全部模型 × 全部档位的现成通道**（model JSON 含完整 variants keys）；格式非稳定 API，升级可能变 |
| `~/.cache/kilo/models.json` 缓存文件 | 全局、模型级 | 读文件 | **不可用于 effort**（无档位枚举），排除 |

### 3.3 kimi 侧既有事实（2026-0725-0205 实测）

`kimi provider list --json` 每模型条目携带 `support_efforts`
（如 `["low","high","max"]`）与 `default_effort`（如 `"high"`）字段——
服务端目录下发，CLI 重登录时刷新。**kimi 的动态化只需解析既有子进程
调用的既有 JSON 载荷**，零新增进程、零新增协议。

## 4. 目标与非目标

### 目标

- G1：kimi-acp 强度档位改为解析 `kimi provider list --json` 的
  `support_efforts` / `default_effort`，**模型级**粒度；
- G2：kilocode-acp 强度档位改为解析 `kilo models --verbose` 的 variants
  keys，**模型级**全量；解析失败静默回退一期静态声明（`high/max`）；
- G3：ModelBar 第四级由接口级升级为**模型级联动**（切模型即重建强度
  菜单），数据源与值域变化对用户透明；
- G4：reasonix-acp / opencode-acp 安排 spike 实测各自的强度轴与值域，
  实测后填（维持「不臆造」红线）。

### 非目标

- ❌ 不照抄 kilo `transform.ts` 的 400 行档位规则到 IDE 侧（违反不臆造
  红线，且随 kilo 升级必然漂移）；
- ❌ 不读 `~/.cache/kilo/models.json`（无档位数据，研究已证伪）；
- ❌ 不做 ACP configOptions 实时校准（需先起会话，重；列为后续候选，
  见 §8 R4）；
- ❌ 不动 `set_effort` 协议应用层（configId 各家自持，本期零改动）；
- ❌ 记忆表键结构不变（`model_efforts` 仍接口 → 值，见 D3）。

## 5. 设计决策（待用户拍板）

### D1：数据源分接口定案（推荐方案）

| 接口 | 数据源 | 失败回退 |
|---|---|---|
| kimi-acp | `kimi provider list --json` 的 `support_efforts`/`default_effort`（既有调用同载荷解析，**零新增子进程**） | 模型条目缺字段 → 该模型无强度轴（菜单禁用标注），不做静态兜底 |
| kilocode-acp | `kilo models --verbose` 解析 variants keys（新增一次子进程调用，进程级缓存同 list_models 范式） | 解析失败/超时 → 回退一期静态声明 `high/max`（保可用） |
| reasonix-acp | spike 实测 config.toml / configOptions 后填 | 维持留空 |
| opencode-acp | spike 实测（opencode 原版 configOptions 是否含 effort） | 维持留空 |
| dream-acp | 无强度轴（示例 agent） | 维持留空 |

### D2：粒度升级为模型级

- `BackendSpec` 静态 `efforts`/`default_effort` 字段**保留但改语义**为
  「接口级兜底值」（kilo 解析失败回退用）；
- 新增 `list_efforts: Callable[[], dict[str, tuple[list[str], str | None]]]`
  ——模型别名 → (档位列表, 默认档)；空 dict = 无模型级数据，UI 回退
  接口级兜底（再空 = 不支持）。经 `_cached_list_models` 同款进程级
  缓存包装，`refresh_models()` 同点失效；
- kimi 的 list_models 与 list_efforts **共享同一次 `provider list --json`
  调用**（缓存层合一，防双倍子进程）；kilocode 的 `models`（纯文本）与
  `models --verbose` 两次调用分别缓存（解析逻辑不同源）。

### D3：记忆表键结构不变，应用前校验值域

- `model_efforts` 维持「接口 → 强度值」（不引入接口+模型复合键，防
  键空间膨胀与迁移代码）；
- 应用路径（tabs 解析后、panel 下发前）校验记忆值 ∈ 当前模型档位列表；
  失效（如 kimi 记忆了 `low` 但切到只支持 high/max 的模型）→ 静默落
  该模型默认档，**不写盘**（沿用红线 5 回退不落盘）。

### D4：ModelBar 第四级改挂模型级

- `_refresh_efforts(backend, model)`：数据源 = `list_efforts()` 查模型
  别名，miss/空 → 回退接口级 `spec.efforts`；
- 重建触发点从「切接口」扩为「切接口 + 切模型」——`_refresh_models`
  尾部与 `_on_model_picked` 均联动；
- 切模型后强度勾选解析优先级：记忆值（校验值域）→ 模型默认档
  （list_efforts 的 default）→ 接口级 default_effort → 首项；
- 菜单项保持协议原文（low/high/max/xhigh 等原样透传，不翻译不映射）。

## 6. 任务分解

- **T1（kimi 动态化）**：`kimi_common.py` 新增 `list_kimi_efforts()`
  解析 `support_efforts`/`default_effort`；registry 缓存层合一改造；
  `kimi-acp` 注册项挂 list_efforts。
- **T2（kilocode 动态化）**：`kilocode_acp.py` 新增

  块内 json.loads 取 `variants` keys；`reasoning: false` 或无 variants

- **T3（ModelBar 模型级联动）**：第四级重建改挂模型级（D4）；

  不写盘）。
- **T5（reasonix/opencode spike）**：`.temp/` 脚本实测两家 configOptions
  / config.toml 强度轴与值域，结果回填注册表（实测后填，不臆造）。
- **T6（验证）**：更新 `.temp/smoke_effort.py` 与
  `.temp/smoke_effort_integration.py` 覆盖模型级场景（kimi 切
  k3-256k ↔ kimi-for-coding 档位变化、记忆值跨模型失效回退、
  kilo --verbose 解析失败回退静态表）；实机走查。

## 7. 风险与红线

- R1：`kilo models --verbose` 输出格式**非稳定 API**（id 行 + pretty
  JSON 混排，无 --json 旗标），kilo 升级可能改变格式——解析必须全
  try 兜底且失败可回退静态声明（D1），不得硬依赖格式细节；
- R2：**不臆造档位**——任何模型档位只来自 CLI/协议实测输出，禁止
  IDE 侧按模型名猜档位（kilo 的 400 行规则已证明档位语义极复杂）；
- R3：缓存生命周期与 list_models 对齐（进程级 + `refresh_models()`
  唯一失效口），设置中心「重新检测」路径需同步失效 list_efforts 缓存；
- R4（后续候选，本期不做）：ACP `set_config_option(model)` 响应内嵌
  刷新后的 `effort` options，可做运行时校准（协议真值 > CLI 枚举）；
  需 provider 层把 configOptions 响应透传回 GUI，跨层改动较大，单独立项；
- R5：xhigh/minimal 等新档位出现时 IDE 零改动自动跟进（动态化的核心
  收益），但按钮宽度贴合文本策略下长档位名会小幅顶宽底行——沿用
  一期拍板的宽度策略，不特判。

## 9. 实施记录（2026-08-06 05:30，T1-T6 全落地）

### 9.1 实测修正留痕（与计划文档偏差，以实测为准）

1. **kimi 字段名为 camelCase**：计划 §3.3 所记 `support_efforts`/
   `default_effort`（snake_case）实为 `supportEfforts`/`defaultEffort`
   （2026-08-06 `kimi provider list --json` 实测）；且
   `kimi-code/kimi-for-coding(-highspeed)` 两模型**无** `supportEfforts`
   字段 → 按 D1 该两模型无强度轴（菜单禁用，不静态兜底），仅
   k3/k3-256k 有 low/high/max。
2. **T5 spike 实测结论**（`.temp/spike_effort_axes.py` /
   `spike_reasonix_effort_models.py`）：
   - reasonix：configOptions 存在 effort 轴（category=thought_level，
     configId="effort"），值域 `auto/disabled/high/max`、默认 `auto`，
     两模型值域相同 → 注册表静态回填（无模型级动态数据源，R4 候选）；
   - opencode：configOptions 仅 model + mode 两项，**无 effort 轴**
     （kilo 的 effort 是 fork 自加）→ 维持留空。
3. **kilocode 默认模型无强度轴**：`kilo models` 首项
   `deepseek/deepseek-chat` 为 reasoning:false → 第四级禁用为正确语义
   （非回归）；直连 12 模型中 8 个有 variants（kimi-for-coding/* 与
   glm-5.2* 为 high/max，deepseek-v4-* 与 glm-4.7/5-turbo 为
   low/medium/high[/max]）。
