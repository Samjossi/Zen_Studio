## 1. 背景与动机

依据 `文档/协议指南/版本信息与自动版本号通用指南_v1.0.md`（下称「指南」）改造本项目版本治理与打包链路。当前三个病本项目全中：

1. **版本双处手改**：`config/version.json` 为单一来源（现值 `1.7`），`pyproject.toml` 为人工同步副本——指南药方是反过来：`pyproject.toml` 为唯一来源，一切派生；
2. **无构建号**：同为 `1.7` 的两次构建产物无法区分新旧，拿到截图/产物说不出对应哪次提交；
3. **产物元数据残缺**：AppImage 的 desktop 无 `X-AppImage-Version` 字段，版本信息仅以运行时数据文件（`config/version.json`）形式躺在 bundle 里。

改造后目标态（指南 §二）：基础版本 `1.7.0` 人工拍板于 `pyproject.toml`，构建号取 `git rev-list --count HEAD`（当前 395）自动递增，完整版本四段 `1.7.0.395`，产物/界面/日志/ACP 握手同源显示。

## 3. 方案

### 3.1 版本号模型映射

```
现状  config/version.json "1.7"（两段，人工 +0.1）
  ↓
目标  pyproject.toml version = "1.7.0"（三段基础版本，唯一来源）
      构建号 = git rev-list --count HEAD（当前 395，每提交自动 +1）
      完整版本 = 1.7.0.395（四段，界面/日志/产物/ACP 统一）
```

两段 `1.7` 规范化为三段 `1.7.0`，语义不变、与指南模型对齐。产物文件名维持固定不带版本（指南 §二设计要点）。

### 3.2 新建 `building/version.py`（版本中枢）

拷贝指南 §四实现，两处适配：

- `ROOT` 定位：`building/` 的上一级即项目根，与指南 `packaging/` 布局一致，无需改；
- `bump` 的 `uv lock` 刷新段**保留**——§2.1 已实证 uv.lock 记录本项目版本。

命令行约定：`uv run python building/version.py get` / `bump patch|minor|major`（与构建脚本既有的 `uv run` 习惯一致；`uv run` 先决条件即 lock 同步，bump 内置刷新正好闭环）。

### 3.3 重写 `src/core/version.py`（解析链，消费方零改动）

保留模块路径与 `APP_VERSION` 导出名，内部按指南 §五改为解析链：

```
frozen（IS_FROZEN，复用 core/paths.py 判据，禁止自探 _MEIPASS）
  → 读 PROJECT_ROOT/version.txt（frozen 态 PROJECT_ROOT 即 _MEIPASS，
    datas 落点 (".") 与此一致）
脚本态 → importlib.metadata.version("zen-studio")
  → 直读 pyproject.toml（本项目 virtual source 永不安装成 dist，
    importlib 一级注定 miss，pyproject 一级是实际主路径，两级都保留）
git 仓库内 → 追加提交计数（与冻结态显示一致）
全链失效 → 回退兜底常量并告警（保留现有「不因版本问题启动失败」语义）
```

界面显示随之自动变为四段：关于对话框 `Zen Studio 1.7.0.395`、ACP `clientInfo.version` 同源。消费方代码一行不改。

### 3.4 spec 改造（`building/zen-studio.spec`）

- 顶部加指南 §6.1 的自算段：tomllib 读 `pyproject.toml` + `git rev-list --count HEAD`，写出 `.temp/build/version.txt`（🔴 指南红线：spec 运行环境独立，禁止 import 项目模块含 `version.py`，同规则双实现）；
- datas：删 `config/version.json` 条，改收编 `(.temp/build/version.txt, ".")`；
- docstring 的 datas 五条表述同步更新。

### 3.5 构建脚本改造（`building/build_appimage.sh`）

- [2/5] 阶段：断言改为 `_internal/version.txt` 存在，且内容与 `uv run python building/version.py get` 输出一致（双实现交叉校验，防 spec 自算漂移）；config 白名单两条断言删除（config 不再入包，白名单失去对象）；
- [3/5] 阶段：desktop heredoc 之后追加 `X-AppImage-Version=$VERSION`（`VERSION` 于 [1/5] 前置自查时捕获并公示）；
- [5/5] 冒烟：清单中 `usr/bin/_internal/config/version.json` 换为 `usr/bin/_internal/version.txt` 并比对内容；config 白名单复核删除；desktop 追加字段随解包一并核对。

### 3.6 清理与文档

- 删除 `config/version.json`（git 历史可溯，属可逆删除）；
- 同步 §2.4 四处活文档；
- `pyproject.toml` 的 version 行注释改为「唯一来源」声明；
- 新写注释遵守 `AGENTS.md`：只答 why，不记日期/计划编号。

### 3.7 明确不做（指南 §十 + 项目红线）

- ❌ Windows 版本资源（指南 §6.2）：本项目 Linux x86_64 单平台红线（spec docstring 明令禁止跨平台分支）；
- ❌ 设置页「版本」行：设置中心现无此行，非本次范围；
- ❌ git tag 发版 / Release / changelog / 产物文件名带版本：指南 §十后续增量，按需另立计划。

## 5. 影响面评估

- ✅ 消费方零改动（`APP_VERSION` 导出名与加载语义不变），GUI/ACP/探针五处 + 两处自动继承完整版本；
- ✅ 产物文件名不变（固定名覆盖惯例保持），版本只进产物内部与界面；
- ⚠️ 显示面变化：关于对话框与 ACP clientInfo 由 `1.7` 变 `1.7.0.395`——下游 ACP 服务端若按版本串做精确匹配会失配（现网后端均为本机 CLI，无语义化版本匹配逻辑，风险可忽略）；
- ⚠️ 浅克隆构建号失真（指南 §九）：打包必须全量历史克隆；本项目打包机即本机仓库，无 CI 浅克隆场景；
- ⚠️ 非 git 环境（拷贝源码树）版本退化为三段 `1.7.0`——指南认可的预期行为；
- ⚠️ `uv.lock` 联动：bump 内置刷新已覆盖；手工改 pyproject 版本则需自行 `uv lock`。

## 6. 回退

全部改动收一个提交（新文件 + 机械替换 + 一文件删除），`git revert` 单提交整体回退；`config/version.json` 经 git 历史恢复。无数据迁移、无配置格式变化。
