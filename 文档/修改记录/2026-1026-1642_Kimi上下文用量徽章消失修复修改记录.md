## 变更摘要

修复 Kimi CLI 后端状态行右侧上下文用量徽章空白：

- 轮末改为优先消费 ACP `usage_update`（`source="push"`），response 后在同一 ≤3s 窗口继续收集 ACP 与 wire，避免两路等待串行叠加；ACP 缺失时回退 wire（`source="transcript"`）。
- 上下文窗口改读 `kimi provider list --json` 的 `maxContextSize`（先合并 `overrides`），不再把 `llm.request.maxTokens` 当窗口。目录在 worker 会话准备阶段加载缓存，GUI 轮询只读缓存和 wire 尾部，不起目录子进程。
- wire `used` 改为上游 `tokenUsageTotal()` 同口径：`inputOther + inputCacheRead + inputCacheCreation + output`；四项均校验非负整数，异常记录不用 0 补猜。
- 只有带非空 `turnStep` 的 `llm.request` 参与轮次基线、计数和输出速度配对，隔离 operation/compaction 等非 turn 请求。
- 轮末超时保留本轮已落盘的有效用量子集；速度同样按有效配对子集计算，不再把部分数据整体丢弃。
- ACP 与 wire 同时有效时固定选 ACP；其他迟到 session/update 和 sidecar 尾部继续排干，不吞工具活动帧。
- 双源均失败时保持诚实空态，并做一次无正文、无参数、无完整路径的诊断日志；成功后重置告警状态。

## 现场确认的根因

本机 Kimi Code CLI 2.3.2 的真实会话证明：

- `kimi-for-coding` 与 `k3.1-pro` 的 `llm.request` 均**没有 `maxTokens` 字段**；旧代码要求该字段作为 `size`，因此必然返回 `None` 并隐藏徽章。
- 真实 `llm.request` 带 `turnStep`，可用于区分 turn 请求。
- 新链路下 ACP 与 wire 的 `used/size` 在上述短轮次中完全一致，且均与模型目录窗口一致。
- 官方 ACP `usage_update` 确实在 prompt response 后可被收集；旧实现会在此时立即返回，漏掉该数据源。

因此，本次故障不是 GUI 布局问题，也不是会员额度重置把上下文清零，而是 Zen 对私有 wire 的错误字段假设与轮末时序缺口共同导致。

## 关键实施点

- `src/llm/providers/kimi_common.py` 新增 `context_sizes_from_catalog()`，与模型、档位、显示名共享同一目录载荷并应用 `overrides`；只接受正整数。
- `src/llm/providers/kimi_acp.py` 新增目录缓存、统一 turn 请求识别、四项用量定型、尾部读取、双源轮末收集与降级诊断；`_poll_wire_usage()` 同步修正超时部分结果语义。
- `src/llm/base.py`、`src/llm/context_limits.py` 同步上下文与输出预算的语义，不再沿用旧的 input+cache.read 两项说明。
- `src/llm/providers/acp.py` 与 `src/gui/panels/chat/panel.py` 无需修改；既有 `map_usage_update()`、`_on_chunk()` 与徽章控件直接承接恢复后的数据。
