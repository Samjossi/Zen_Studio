# 对话区 AI 活动信息充分展示初步计划

> ⚠️ **本文档为初步文档**：问题定位与链路分析已实证闭环，但展示范围、
> 渲染形态等关键决策（§3 之 D1–D5）尚未经用户拍板。拍板后本文档修订
> 转正（状态改「草稿」），再进入实施。

## 1. 背景与问题

### 1.1 现象

用户截图实证：AI 执行多步任务时，对话区仅出现零星灰字单行——
「• 调用工具 TodoList」「• 调用工具 Agent」「• 调用工具 Bash」——
todo list 内容、工具参数、执行状态流转、子代理活动**全部不可见**。
信息展示过于简单，用户无法追踪 AI 在做什么、做到哪一步。

### 1.2 根因定位（已实证）

**不是 ACP 协议给的信息不够，而是 IDE 在映射层主动丢弃。**

`llm/providers/kimi_acp.py` 的 `_map_update`（其余三个 provider 逐行
一致，各文件 docstring 自述「与 KimiAcpLLM 逐行一致」）：

```python
# llm/providers/kimi_acp.py
if kind == "tool_call":
    return Chunk("reasoning", f"\n• 调用工具 {update.get('title') or '?'}\n")
return None  # tool_call_update / plan / usage_update / available_commands_update 等
```

丢弃清单：

| sessionUpdate 类型 | 协议载荷 | 现处置 | 对应用户盲区 |
|---|---|---|---|
| `plan` | entries 全量快照：content / status(pending/in_progress/completed) / priority | `return None` | **todo list 不可见** |
| `tool_call` | title / kind / **rawInput（完整参数）** / locations / status | 压成一行灰字，rawInput 丢弃 | 工具参数不可见 |
| `tool_call_update` | status 流转（pending→in_progress→completed/failed）/ content（含 diff、终端输出） | `return None` | 执行进度与结果不可见 |
| `usage_update` | token 用量 / 上下文占比 | `return None` | 用量不可见（可选增强） |
| `available_commands_update` | 斜杠命令清单 | `return None` | 维持丢弃（合理） |

### 1.3 现状链路

```
agent 子进程 ──ndjson──> AcpConnection._dispatch_line（acp.py，全量入队，无丢弃）
    ──> provider._map_update（★ 丢弃点：plan/tool_call_update 等 return None）
    ──> ChatWorker.chunk_received = Signal(object)（worker.py，透传，天然支持结构化载荷）
    ──> ChatPanel._on_chunk（panel.py，仅路由 text/reasoning 两种 kind）
    ──> ChatOutput（output.py，QTextBrowser 追加式渲染，无富块能力）
```

结论：**改造不动 ACP 连接层、不需要 agent 侧配合**，是
「协议映射层放出来 + GUI 层设计渲染形态」的纯 IDE 侧改造。

## 2. 改造总思路

一条纵贯线，自下而上四层：

1. **抽象层**（`llm/base.py`）：`Chunk` 扩展结构化 kind 与载荷；
2. **协议层**（`llm/providers/acp.py` + 四 provider）：映射逻辑上收
   公共实现，`plan` / `tool_call` / `tool_call_update` 全量映射为
   结构化 Chunk；
3. **路由层**（`gui/panels/chat/panel.py`）：`_on_chunk` 按新 kind 分发；
4. **渲染层**（`gui/panels/chat/output.py`）：新增工具块 / plan 块渲染
   方法，配色入主题资源包。

## 4. 初步改造方案（基于 §3 初步倾向，拍板后细化）

### 4.1 T1：`llm/base.py` —— Chunk 结构化扩展（对应 D3-A）

1. `Chunk` kind Literal 扩展：`"text" / "reasoning" / "tool_call" /
   "tool_call_update" / "plan"`。
2. 新增可选载荷字段（frozen dataclass 加默认值字段，存量
   `Chunk("text", ...)` 构造调用零改动）：
   - tool_call：title / kind / 参数摘要（协议层预格式化的单行文本，
     防 GUI 层解析 rawInput 各家差异）/ toolCallId
   - tool_call_update：toolCallId / status / 输出摘要（预截断）
   - plan：entries 列表（content/status/priority）
3. docstring 同步：`LanguageModel.chat` 的 yield 语义补注新 kind
   「仅上屏，不入历史、不回传」（与 reasoning 同约束）。

**约束**：`text` 字段保留为「兜底显示文本」，GUI 对未识别 kind
按 text 渲染——新协议层配旧 GUI 不崩（多标签/多开版本错配防御）。

### 4.2 T2：`llm/providers/acp.py` —— 公共映射 `map_session_update`（对应 D4）

1. 新增模块级函数 `map_session_update(obj: dict) -> Chunk | None`：
   现有四种 kind 映射逻辑原样搬入（行为等价），新增
   `tool_call`（全字段）/ `tool_call_update` / `plan` 三个分支。
2. 参数摘要规则（协议层单点格式化）：
   - bash/execute 类：取 command 首行，超 80 字符截断；
   - read/edit/write 类：取文件路径（locations/rawInput.path 优先）；
   - fetch/search 类：取 url/query；
   - 未识别：仅 title。
3. `usage_update` / `available_commands_update` / `_meta` 厂商扩展维持
   返回 None（R1 纪律：泛化层不臆造协议）。
4. 输出摘要截断规则：头部 20 行 + 尾部 5 行 + 「…共 N 行」（防
   QTextBrowser 大卡，截断阈值写模块常量）。

### 4.3 T3：四 provider —— 切换公共映射

`kimi_acp.py` / `reasonix_acp.py` / `opencode_acp.py` /
`kilocode_acp.py` 各自删除私有 `_map_update`，`_iter_turn_chunks`
改调 `map_session_update`（import 自 `llm.providers.acp`）。
各文件 docstring「逐行一致」自述改为指认公共实现出处。

### 4.4 T4：`gui/panels/chat/output.py` —— 富块渲染

1. `append_tool_call(...)`：工具调用块上屏——kind 图标字符 +
   title + 参数摘要，主题资源包新增 `chat.tool_fg` 配色
   （沿用 reasoning_fg 注入范式，`gui/theme.py` 资源表加键）。
2. `update_tool_status(...)`：状态流转——一级方案**追加状态行**
   （「✔ 完成」/「✖ 失败」），不做就地改写（QTextBrowser 定位成本
   与收益不匹配；就地更新仅留给 plan 块，见 T5）。
3. 渲染纪律：与 reasoning 同——显式 QTextCharFormat 上屏，防格式
   经光标位置继承（既有 append_stream_chunk 注释的坑）。

### 4.5 T5：plan 块就地更新（对应 D2-A，本期技术难点）

1. `ChatOutput` 新增 plan 块锚点簿记：首个 `plan` Chunk 到达时
   插入清单块并记录起始 QTextCursor 位置（document position int）；
   后续快照到达时选中旧块范围替换文本。
2. 清单渲染：`- [ ]` / `- [>]（进行中）` / `- [x]` 前缀 + 条目文本，
   完成项用 reasoning 灰弱化。
3. 轮次收尾（`end_stream` / 中断 / 失败）时锚点作废：下一轮 plan
   作为新块插入（防跨轮锚点串位）。
4. **降级预案**：若锚点替换实测出现格式错乱（QTextBrowser HTML/
   光标混合渲染的已知脆弱性），退回 D2-B 差异行追加——T5 因此
   独立成任务，与 T1–T4 解耦，可单独回退。

### 4.6 T6：`gui/panels/chat/panel.py` —— chunk 路由扩展

`_on_chunk` 新增三分支：`tool_call` → `append_tool_call`；
`tool_call_update` → `update_tool_status`；`plan` → plan 块方法。
三类均**只上屏，不入 `_stream_buffer` / `_history`**（与 reasoning
同约束，历史污染防 DeepSeek 系回传禁令）。

### 4.7 T7：主题与收尾

1. `gui/theme.py` 各主题资源包补 `chat.tool_fg`（及 plan 完成项
   弱化色，如复用 reasoning_fg 则不新增）；
2. `ChatPanel.apply_theme` 同步注入新色（沿用 set_reasoning_color 范式）；
3. 受影响文件 docstring 同步（Chunk 语义、_on_chunk 路由清单）。

## 5. 不做的事

- 不改 `AcpConnection` 连接层任何逻辑（帧收发/反向请求/死讯注入
  与信息展示正交）。
- 不向 agent 声明新能力（fs/terminal 维持 False），不要求 agent 侧
  任何配合。
- 不做子代理内部步骤嵌套展示（D5-A；留待二级范围）。
- 不做 usage_update 上屏（D1 一级不含；映射层继续返回 None 即兼容）。
- 不上屏原始 JSON / 未截断长输出（bash 数千行输出必须过 §4.2 截断）。
- 不动审批链路（`permission_dialog.py` / `permission_queue.py`）——
  审批框是决策点、工具块是流水记录，两系统并存；视觉风格统一
  （图标/配色语言）留二级打磨。
- 不改消息历史与会话持久化（新 kind 一律不入历史）。

## 7. 边界与遗留

- **协议载荷差异**：tool_call 的 rawInput 结构随 agent/工具而异，
  参数摘要是尽力而为（§4.2 规则 2）；摘要失败回退仅显示 title，
  不阻断上屏。
- **锚点脆弱性**：QTextBrowser 就地替换依赖 document position
  簿记，用户在输出区手动选择/复制不影响力矩，但若未来输出区改
  富交互（块删除等）需重审 T5。
- **多标签隔离**：plan 锚点存于各 ChatOutput 实例，天然隔离；
  worker 串行化轮次保证 plan 快照不交叉。
- **转正流程**：D1–D5 拍板 → 本文档修订（§3 决策表落「选定」列、
  §4 任务按选定方案裁剪）→ 状态改「草稿」→ 实施。
