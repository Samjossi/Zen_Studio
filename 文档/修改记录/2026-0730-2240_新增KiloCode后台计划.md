# 新增 Kilo Code 后台计划

## 1. 目标与决策

### 1.1 目标

ModelBar 三级下拉新增第五个后台「Kilo Code」（本机 Kilo CLI，
v7.4.17 已安装实测可用），与 Kimi / Reasonix / OpenCode 并列。

### 1.2 决策（待用户拍板，文中按推荐项展开）

| # | 决策点 | 推荐 | 备选 |
|---|---|---|---|
| D1 | 接口形态 | **ACP**（`kilo acp`，长驻子进程 + ndjson JSON-RPC） | run 形态（`kilo run --format json`，每轮 spawn） |
| D2 | 接口数量 | **先只接 ACP 一个接口**（最小增量） | 同 kimi 双接口（acp + run）一并接入 |
| D3 | 模型枚举 | **`kilo models` 纯文本逐行解析** | session/new 的 configOptions 反查（需先起会话，重） |
| D4 | 默认后台 | **不变**（仍为 kimi-cli） | 切换为 kilocode-acp |
| D5 | mode 处理 | **不触碰**（agent 默认 ask，纯问答模式） | 固定切 code 模式（允许编辑工具） |

**推荐 ACP 的理由**（§2 实测支撑）：Kilo CLI 官方自述为 OpenCode
fork（docs：「The Kilo CLI is a fork of OpenCode」），其 ACP 实现与
现有 `AcpConnection` 泛化层**协议级兼容**——initialize / session/new /
session/set_config_option / session/prompt / 流式 update 全链路实测
通过（§2.3-§2.5），接入代码量与 opencode_acp 同量级（约 300 行，
其中大半是 docstring），token 级流式、思维链、协议级取消、审批
回环全部免费获得。run 形态仅消息粒度上屏，无任何优势项。

**D5 推荐「不触碰」的理由**：kilo 的 mode 默认 `ask`（纯问答，
禁用编辑工具），恰好匹配 IDE 对话场景——比 OpenCode 默认 build
（允许编辑）更贴合、更安全；code/debug/orchestrator/plan 四模式
本期均不暴露 UI（未来如需「编码代理模式」再单列计划）。

## 2. 调研实测记录（2026-07-30，本机 kilo 7.4.17）

全部实测在项目根目录完成；协议探针脚本留档
`.temp/probe_kilo_acp.py`（ndjson 握手 + 会话 + 流式对话全链路）。

### 2.1 二进制探测

- 安装方式：`npm install -g @kilocode/cli`（官方文档安装页首推），
  落在 npm 全局 bin：`~/.local/bin/kilocode` 与 `~/.local/bin/kilo`
  **双名 symlink** 同指 `~/.local/lib/node_modules/@kilocode/cli/bin/kilo`。
- npm 全局 bin 目录（`~/.local/bin`）通常在桌面会话 PATH 中，
  但**不保证**（用户自定义 npm prefix 时路径漂移）→ `_find_bin`
  需 fallback 到 `~/.local/bin`（对齐 kimi `~/.kimi-code/bin`、
  opencode `~/.opencode/bin` 的兜底范式）。
- Kilo CLI 无安装根环境变量（官方环境变量表只有 `KILO_CONFIG` /
  `KILO_PROVIDER` / `KILO_ORG_ID` 等配置与覆盖项），故探测链为
  两级：PATH → `~/.local/bin`。
- **命名取舍**：PATH 探测按 `kilocode` → `kilo` 顺序——`kilocode`
  更长更不易与他物撞名，`kilo` 为官方主推名兜底；两名字实测
  指向同一二进制，行为一致。
- 官方另有 baseline 变体（无 AVX 老 CPU 的 GitHub releases 直装
  二进制），落在用户自选路径，不在探测链内——PATH 命中即可，
  本期不为它加兜底级（YAGNI）。

### 2.2 模型枚举（`kilo models`）

```
kilo/~anthropic/claude-fable-latest
kilo/anthropic/claude-opus-4.8
...
deepseek/deepseek-chat
kimi-for-coding/k3-256k
zai-coding-plan/glm-4.7
```

- 纯文本输出，每行一个 `provider/model` 全名；**无 `--json` 旗标**
  （`--verbose` 只加元数据列，`--refresh` 触网刷新缓存——均不用于
  解析）。
- 本机实测 **294 行**：大头是 `kilo/...`（Kilo Gateway 聚合的
  500+ 模型目录中已可用项），含 `kilo/~anthropic/claude-fable-latest`
  类 `~` 前缀**别名行**（指向最新版的快捷别名，是合法模型 ID，
  实测可直通 set_config_option）；其余为已认证直连 provider
  （本机另有 deepseek / kimi-for-coding / zai-coding-plan 三家）。
- 数据源是已认证 provider（models.dev 缓存），与 ACP session/new
  的 configOptions.model.options **同源**（实测两列表同为 294 项）。
- 解析策略：逐行 strip、跳过空行，含 `/` 的行保留（`~` 别名行
  天然含 `/`，与全名行同等对待，不特判）；失败/空输出 → 空列表
  （provider 用 agent 默认模型，与 kimi/opencode 同一兜底语义）。
- 与 opencode 的差异：opencode 无 `~` 别名行、总量 15 项；
  kilo 目录量级 294 项——ModelBar 三级菜单变长属如实呈现，
  本期不做折叠/搜索（UI 零改动红线）。

### 2.3 ACP 握手（`kilo acp`）

`initialize`（protocolVersion 1）实测响应：

```json
{"protocolVersion":1,
 "agentCapabilities":{"loadSession":true,"mcpCapabilities":{...},
   "promptCapabilities":{"embeddedContext":true,"image":true},
   "sessionCapabilities":{"close":{},"fork":{},"list":{},"resume":{}}},
 "authMethods":[{"id":"kilo-login","name":"Login with Kilo",
   "description":"Run `kilo auth login` in the terminal"}],
 "agentInfo":{"name":"Kilo","version":"7.4.17"}}
```

- 协议同构：与 kimi/reasonix/opencode 同为 ACP v1，帧格式 ndjson
  （字段级逐一对照一致——fork 同源的预期结果）。
- authMethods 为静态能力声明（同 reasonix/opencode 实测结论），
  **不能作未登录信号**；未登录/失效的真实信号在 session/prompt
  错误，归 provider 自行翻译（D5 惯例）。

### 2.4 会话与模型切换

`session/new` 实测响应（关键字段）：

```json
{"sessionId":"ses_...",
 "configOptions":[
  {"id":"model","currentValue":"kimi-for-coding/k3-256k",
   "options":[... 共 294 项]},
  {"id":"effort","currentValue":"high",
   "options":[{"value":"high"},{"value":"max"}]},
  {"id":"mode","currentValue":"ask",
   "options":[{"value":"ask"},{"value":"code"},{"value":"debug"},
              {"value":"orchestrator"},{"value":"plan"}]}]}
```

- `configOptions` 结构与 opencode/reasonix 完全一致，
  `configId="model"` 直通 `session/set_config_option`（实测返回
  更新后 configOptions，currentValue 已变更）→ **set_model 即时
  生效机制零新代码**。
- **与 opencode 的差异**（实测对照）：
  - opencode 默认模型 `opencode/big-pickle`；kilo 默认随用户配置
    （本机实测 currentValue 为 `kimi-for-coding/k3-256k`）。
  - kilo 多出 **`effort`** 选项（high/max，推理力度）：本期不触碰，
    agent 默认 high，不暴露 UI。
  - kilo 的 **`mode`** 默认 `ask`（opencode 默认 build），选项为
    ask/code/debug/orchestrator/plan 五值（D5：不触碰，ask 即
    纯问答，恰好匹配 IDE 对话场景）。

### 2.5 流式对话端到端

`session/prompt`（prompt「只回复两个字：收到」）实测：

- update 类型统计：`agent_thought_chunk` ×47、
  `agent_message_chunk` ×1、`usage_update` ×1——**全部命中现有
  ACP 标准映射**（thought → reasoning 灰字、message → text 正文，
  其余忽略）。注：opencode 实测多出 `available_commands_update`，
  kilo 本轮未出现，两者均为忽略语义，无映射差异。
- 响应：`{"stopReason":"end_turn","usage":{...}}` —— 正常收尾；
  正文聚合为「收到」，正确。
- 进程终止：terminate 后回收正常（退出码 -15，预期）。

### 2.6 run 形态（备选，文档留档）

`kilo run [message] --format json` 与 opencode run 同构（fork 同源）：
stdout 逐行 JSON 事件，`-s <sessionID>` 续接。事件 schema 与 kimi
stream-json 不同构（需新映射层），作为 D1 备选留档，本期不实施。
（沿用 opencode 计划 §2.6 结论，未重复实测。）

### 2.7 权限与凭证

- 凭证：`kilo auth login` / TUI `/connect` 管理，存
  `~/.local/share/kilo/auth.json`（本机已有 Kilo Gateway 等凭证）。
  配置在 `~/.config/kilo/kilo.json[c]`。代码库零密钥惯例不变。
- ACP 审批回环：`session/request_permission` 协议标准方法，
  promptCapabilities 声明支持；**事件载荷形态未实测**，列为实施期
  验证项（§6-T6）。兜底：handler=None 时 AcpConnection 自动允许
  （现状语义）。
- kilo 侧另有细粒度 permission 配置（`kilo.json` 的 `permission`
  段，allow/ask/deny + 通配规则）：agent 内部生效，与 IDE 审批
  回环叠加不冲突，IDE 不干预。

## 3. 改造方案

### 3.1 新增 `llm/providers/kilocode_acp.py`（约 300 行）

与 `OpenCodeAcpLLM` 高度同构，复用 `AcpConnection` 全量基建。
模块 docstring 逐条记录与 kimi/reasonix/opencode 的差异（项目惯例）：

1. **bin 探测**：`_find_bin()` 两级链 PATH（`kilocode` → `kilo`
   双名顺序探测）→ `~/.local/bin/kilocode` 兜底；常量
   `KILOCODE_BIN_NAMES = ("kilocode", "kilo")`。
2. **模型枚举**：`list_kilocode_models()` spawn `kilo models`
   解析纯文本行（§2.2），15s timeout，全 try 兜底空列表；
   `~` 别名行不特判（含 `/` 即保留）。
3. **认证文案映射**（D5 各自翻译）：session/new 与 session/prompt
   的 error 帧宽松匹配 auth/login/credential/unauthorized 关键词 →
   「请先运行 kilo auth login」。
4. **cwd 归一化**：`os.path.abspath`（对齐 reasonix/opencode 稳妥
   做法）。
5. **mode/effort 不触碰**：不使用 `session/set_config_option` 的
   mode（默认 ask 纯问答）与 effort（默认 high）项（§2.4，D5）。
6. 别名私有语义（D6 红线 2）：`provider/model` 全名（含 `~` 别名）
   不透明透传，公共层不解析不拼接。

类骨架（与 OpenCodeAcpLLM 逐方法对应）：

```python
class KiloCodeAcpLLM(LanguageModel):
    __init__(model=None, workspace_root=None)   # + atexit.register(close)
    set_model(alias)        # session/set_config_option(configId="model")
    reset_session()         # 清 sessionId，进程保留
    set_workspace_root(root)  # abspath + reset_session（预留，无调用方）
    set_permission_handler(handler)
    close()                 # _closed 先置位 + atexit 注销 + terminate
    cancel()                # session/cancel，不杀长驻进程
    chat(messages)          # _turn_lock 串行化 + begin_turn/迭代/end_turn
    _ensure_session()       # spawn 前后双检 _closed + initialize + session/new
    _iter_turn_chunks(conn) # next_update 循环 → Chunk
    _map_update(obj)        # ACP 标准映射（thought/message/tool_call）
```

注：`sessionCapabilities` 含 close/fork/list/resume，本期均不使用
（每标签一实例、标签销毁即进程终止的现语义不变）。

## 6. 风险与回归点

- **T6 审批载荷**：kilo `session/request_permission` 的 options
  结构未实测，若与 kimi 不同构需按 D5 在 kilocode_acp 内翻译，
  不动公共层。（fork 同源，预期与 opencode 一致，仍须实测。）
- **`kilo models` 输出漂移**：无 --json 契约，未来版本可能改
  格式；解析层全 try 兜底空列表（最坏退化：模型下拉为空、用
  agent 默认模型，对话功能不受影响）。
- **294 项长菜单**：模型三级菜单长达 294 项，滚动体验依赖现有
  菜单组件；本期如实呈现不做 UI 增强（零改动红线），若体验
  不可接受再单列「模型菜单搜索/折叠」计划。
- **`~` 别名行**：`kilo/~anthropic/claude-fable-latest` 类别名随
  上游发版漂移指向，属 Kilo Gateway 语义，IDE 透明透传不固化
  （D6 红线 2）。
- **mode=ask 语义差异**：kilo 默认 ask 为纯问答（编辑工具禁用），
  与 opencode 默认 build 不同；用户若期望 agent 改文件会困惑——
  实施时在 provider docstring 与计划文档明示（D5），UI 层不提示。
- **npm prefix 漂移**：用户自定义 npm 全局前缀时二进制不在
  `~/.local/bin`，探测链 PATH 未命中即误判未安装——与 kimi/
  opencode 同级风险（自定义安装路径本就依赖 PATH），不新增
  兜底级。
- **stdin EOF**：沿用 opencode 实测结论（管道 stdin 关闭即终止
  acp 进程）——长驻 AcpConnection 持管无此问题，调试脚本需
  保持 stdin 打开（探针 `.temp/probe_kilo_acp.py` 已示范）。
- **models.dev 缓存**：`kilo models` 首次运行触网刷新，list_models
  的 15s timeout 覆盖；`--refresh` 不主动调用。
- **多标签进程数**：每标签一 acp 长驻进程，沿用既有标签数上限
  约束（ChatTabs D1），无新增资源压力。
