## 1. 目标

代码读起来像代码，不像历史书。规则一句话：注释回答 **why**（为什么这么写），不回答 **when/what changed**（那是 git log、CHANGELOG 与 `文档/修改记录/` 的事）。落地方式两步：**规则写入 `AGENTS.md`** 让 AI 与协作者遵守；**不搞一次性大扫除，随改随清**——每次动到某个文件顺手清掉该文件的历史类注释，几个月自然收敛。原则：**先做到比现状好，不追求完美**。

## 2. 现状盘点（2026-09-10 实测）

- 自有代码（`core/`、`gui/`、`llm/`、`main.py`，不含 vendored `markdown_it/`、`mdurl/` 与 `scripts/` 工具脚本）中带历史痕迹的注释约 **343 处**：`core` 2、`gui` 226、`llm` 111、`main.py` 4（grep 模式：日期戳 / 计划编号 / 拍板翻案记录 / 指向归档文档的引用，人工抽样核对误报率低）。
- 典型形态（抽样自 `gui/panels/chat/`）：
  - 计划编号引用：`# 推理强度（2026-0806 计划）：切后台/接口/模型后按（新）接口的…`
  - 拍板/翻案记录：`# 默认开合约定（P2 / 0640-D4-A；2026-0803 拍板翻案：bash 改为运行中开、…`
  - 归档文档路径引用：`# Git 状态去抖刷新，诊断报告 文档/修改记录/2026-0731-1256 方案 A）`
  - 纯日期戳：`#: 列表上限（超出截断最旧；2026-09-02 由 10 扩到 24，菜单全量展示）`
- 关键辨析：这批注释大多**不是纯垃圾**——"由 10 扩到 24"里的"24 上限、超出截断最旧"是 why，"2026-09-02 由 10"是 when。整改动作是**删 when 留 why、把 why 改写成去时间化的自包含陈述**，不是整行删除。
- `AGENTS.md` 现无注释纪律条目（2026-09-10 grep 确认），AI 与协作者无规可依，是存量持续增长的源头。

## 3. 实施步骤

### T1 注释规则写入 AGENTS.md

- 项目根 `AGENTS.md` 增一条注释纪律，措辞对齐方案：

  > 注释只回答 why（设计意图、坑、约束），不记录 when/what changed（日期、计划编号、拍板记录）；历史归属 git log 与 `文档/修改记录/`。改动文件时顺手清理该文件内的历史类注释。

- 顺手核对 `维护手册/`、`work charter/` 内是否有注释规范相关表述需同步一句指向（有则补，无则过）。

实施实录（2026-09-10 05:05）：`AGENTS.md` 在 check.sh 条后增注释纪律条（逐字如上）。核对发现 `维护手册/AI 友好代码协议-v1.2.0.md` §3.3 已有"写为什么不写做什么"但无"不记历史"，补一段指向 `AGENTS.md`；`work charter/` 无相关表述，过。

### T2 试点清理（1~2 个高密度文件）

- 候选：`gui/panels/chat/panel.py`、`gui/panels/chat/tabs.py`（存量最密、近期活跃）。实施时先清 `panel.py`，量可控则连 `tabs.py` 一起。
- 逐条处置规则：
  1. 纯历史注释（只有日期/计划编号/拍板记录，无 why 价值）→ **整行删除**。
  2. why+when 混合 → **删 when 留 why**，改写为去时间化自包含陈述，如"（2026-0806 计划）切后台后按新接口记忆表解析"→"切后台后按新接口的记忆表解析"。
  3. 指向 `文档/修改记录/` 归档文档的引用 → 一律删除；该目录本身即是历史归属地，代码内不留指针。
  4. 拿不准是 why 还是 when 的 → **保留**，留给下次。
- 硬性约束：**只动注释，不改任何代码行**；docstring 中含 API 语义说明的部分不动，仅清其中夹带的历史记录。

实施实录（2026-09-10 05:05）：两文件均清，共 313 插入 / 355 删除（净减 42 行，全部注释/docstring）。panel.py 改写保留 why 约 100 处 + 整行删除 3 处；tabs.py 改写保留 why 28 处、无整行删除。模块 docstring 从历史编年体改为按主题分组的现状陈述。清理后两文件历史模式（日期戳/计划编号/拍板/翻案/走查/诊断报告/修改记录路径）grep 零命中；`git show HEAD:` 与工作区做去 docstring AST 对比，两文件代码 AST 一致——可执行代码行与字符串字面量零改动。

### T3 确立"随改随清"常态约定

- T1 规则入 `AGENTS.md` 后即生效：此后任何代码改动（含本仓库其他整改计划）触及文件时，顺手按 T2 处置规则清该文件的历史类注释。
- 不设完成期限、不排存量清零节点——收敛靠规则约束新增 + 随改随清自然衰减。

## 4. 验证清单

1. `AGENTS.md` 新增注释纪律条目，措辞与方案第 11~13 行一致；`scripts/check.sh` 全绿（ruff + pytest 不回归）。
2. 试点文件（至少 `panel.py`）grep 复测：历史模式（日期戳/计划编号/拍板/修改记录路径）命中清零；why 类注释仍在（抽样人工核对 3 处改写结果语义未失真）。
3. `git diff` 确认试点清理改动面**仅含注释行**，无代码行变更。
4. `git status` 确认本计划总改动面仅限：`AGENTS.md`、试点 1~2 个 `.py` 文件、本计划文档（及可能的 `维护手册/` 一句同步）。

## 5. 风险与代价

- 首批投入约 1~2 小时（T1 分钟级，T2 逐条人审是大头）。
- ⚠️ 唯一可能翻车的点：误把真 why 判成历史删掉，丢失设计意图且无人察觉。规避：处置规则第 4 条"拿不准就保留"；改写后抽样核对语义。
- 历史信息不会因删注释而丢失——git log 与 `文档/修改记录/` 归档才是其归属地，注释里的日期/编号本就只是副本。
- 存量 343 处靠随改随清收敛，短期内存量仍在——这是方案既定取舍，不追求一次清完。

## 6. 明确不做（本计划边界外）

- ❌ 一次性大扫除、全库批量清理 343 处——方案明确否定，改不尽的还会再长，靠规则防新增。
- ❌ vendored `markdown_it/`、`mdurl/` 与 `scripts/`、`dream-acp/` 工具脚本的注释清理。
- ❌ 新增 lint 规则 / check.sh 门禁机械拦截历史类注释——中文注释模式难以可靠机器判定，误报成本高于收益；靠 AGENTS.md 规则约束人与 AI。
- ❌ 改动任何代码逻辑、docstring 的 API 语义部分。
- ❌ 为被删历史注释另建索引/对照表——git log 与归档文档已足。
