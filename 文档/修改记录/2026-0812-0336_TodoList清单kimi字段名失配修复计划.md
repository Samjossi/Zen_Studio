## 1. 背景

0808 计划的 TodoList 清单可视化在真机（kimi 后端）完全失效，诊断报告已定位根因：

> kimi 系 TodoList 载荷条目以 `title` 字段承载条目文本，而 `_extract_todo_entries`（`llm/providers/acp.py`）只收录 `content` 字段（kilocode/opencode 系字段名）为字符串的条目——kimi 条目全体被静默跳过，提取结果恒为空列表，"清单载荷 → TodoListCard 渲染 → 入参 JSON 抑制"全链路从源头断流，按空清单静默降级路径退化为普通 McpCard。

失效无声（三层静默降级叠加）、mock 假绿（场景全部按 kilocode `content` 形态构造）、真机验收遗留未做——三者叠加导致"已落地"假象持续 4 天。诊断报告 §5 已逐项排除运行环境嫌疑（AppImage 含新代码）、帧路径层级嫌疑（入参 JSON 与提取读同一 `rawInput["todos"]`），断点唯一且确定。

## 3. 修复方案

按"协议层 → mock 补盲 → 真机验收"推进，共三个任务。

### T1：`_extract_todo_entries` 增补 `title` 回退（`llm/providers/acp.py`）

**改动点（唯一代码改动）**：条目收录判据从"仅 `content` 字符串"放宽为"`content` 或 `title` 任一字符串即收录，`content` 优先"：

```python
# llm/providers/acp.py
for item in items:
    if not isinstance(item, dict):
        continue
    # kimi 系 TodoList 条目文本键为 title；kilocode/opencode 系
    # todowrite 为 content——两形归一，内部统一 content 存储
    text = item.get("content")
    if not isinstance(text, str):
        text = item.get("title")
    if not isinstance(text, str):
        continue
    entry = TodoEntry(content=text)
    ...
```

要点：

- **两键均缺维持静默跳过**——防御语义不变，空清单静默降级路径不受影响；
- **`content` 优先**——两键同现时以 kilocode 语义为准（`title` 在此情形下的语义无实证，取保守序）；
- **docstring 同步**：注明"kimi 系 `title` / kilocode 系 `content` 两形归一"；函数 docstring 现存"两通道同构（F1）"表述保留（指的是 plan/rawInput 通道，不冲突）；
- **plan 通道零影响**：plan 通道 `entries` 条目为 `{content, status, priority}`（协议文档 §2.2 表格），走同一提取函数，判据放宽对其无行为变化；
- **diff 比对口径不改**：`_apply_todo_diff` 的 same 口径（content+status+priority 全等）作用于归一后的内部形态，天然兼容两系；kimi 无 `priority` 键，条目无该字段即不参与差异（既有容错）。

**协议文档同步**（同纪律前例：0808 计划 R2 ④）：`dream-acp/protocol/dream-acp-v1.md` §2.2 todo 清单载荷段（0808-0627 修订段）补一句——"条目文本键两系归一：kimi 系为 `title`，kilocode/opencode 系为 `content`，客户端协议层统一归一为 `content` 存储"。

**明确不动**：`llm/base.py`（TodoEntry 契约内部形态不变）、`gui/panels/chat/cards.py`、`gui/panels/chat/panel.py`（P2 归一原则的直接推论）。
