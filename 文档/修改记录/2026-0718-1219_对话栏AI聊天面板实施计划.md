## 3. 架构设计

模块化原则：一个功能一个子包，控件按职责拆分为单文件，包内经 `__init__.py` 对外导出。

```
gui/                           # 前端：全部界面代码
├── panels/
│   └── chat/                    # 聊天面板子包（左栏）
│       ├── __init__.py          # 对外导出 ChatPanel
│       ├── panel.py             # ChatPanel：面板装配（垂直 QSplitter + 上下区组合）
│       ├── output.py            # ChatOutput(QTextBrowser)：消息列表、追加、自动滚动
│       ├── input.py             # ChatInput(QTextEdit)：Enter 发送 / Shift+Enter 换行
│       └── worker.py            # ChatWorker(QThread)：后台跑流式 generator，信号上屏
llm/                             # 后端：LLM 调用层子包（与 gui/ 平级）
├── __init__.py                  # 对外导出 registry、get_llm
├── base.py                      # LanguageModel Protocol（流式 chat 接口）
├── registry.py                  # LLMRegistry：名称 → provider 注册表
└── providers/                   # provider 子包（每家厂商一个文件）
    ├── __init__.py
    └── deepseek.py              # DeepSeekLLM：openai SDK 直连 DeepSeek 端点
```

> 说明：`llm/` 为后端逻辑（网络请求、密钥读取），与界面无关，故置于项目根与 `gui/` 平级；前端仅经 `from llm import get_llm` 消费，依赖方向为"前端 → 后端"。

| 组件 | 职责 |
|:---|:---|
| `LanguageModel`（Protocol） | 统一接口：`chat(messages) -> Iterator[str]`（流式产出文本块），与 UI 解耦 |
| `LLMRegistry` | 名称 → provider 实例的注册表，仿 theia-zen 注册表模式 |
| `DeepSeekLLM` | 首个 provider；读 `api_key/deepseek` 文件的密钥，openai SDK 流式调用 |
| `ChatPanel` | 面板装配：上 `ChatOutput` 下 `ChatInput` + 发送按钮，连接 `ChatWorker` |
| `ChatOutput` | 消息逐条追加（用户/AI 前缀区分）、流式块上屏、自动滚动到底部 |
| `ChatInput` | 输入框：Enter 发送 / Shift+Enter 换行，发送中禁用并显示"停止" |
| `ChatWorker`（QThread） | 后台线程跑流式 generator，`pyqtSignal(str)` 逐块推给输出区，避免阻塞 UI |

## 7. 风险与对策

| 风险 | 等级 | 对策 |
|:---|:---:|:---|
| DeepSeek API 网络不通/超时 | 🟡 | provider 层捕获异常并以消息形式上屏，不崩溃；报错信息含超时提示 |
| 流式回调阻塞 Qt 主线程 | 🟡 | 流式 generator 强制放 QThread，UI 只经信号更新 |
| 密钥误提交 | 🔴 | `api_key/` 已在 .gitignore；provider 只接受文件路径读 key，代码中不出现任何密钥字面量 |
| openai SDK 版本 API 差异 | 🟢 | 锁定 `uv add openai` 最新版，按 2.x `client.chat.completions.create(stream=True)` 写法 |
