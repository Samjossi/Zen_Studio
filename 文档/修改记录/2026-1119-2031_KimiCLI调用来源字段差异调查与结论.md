# Kimi CLI 调用来源字段差异调查与结论

> **状态**：已确认
> **范围**：纯调查结论记录，无代码改动；涉及 Kimi Code CLI 内部请求路由行为与 Zen Studio IDE 的接入边界
> **时间**：2026-11-19 20:31（设计）
> **优先级**：低
> **依据**：用户指示（2026-11-19）——调用记录中 K2.8 来源显示 `OpenAI/JS 6.34.0`、K3.1 显示 `kimi-code-cli/2.3.2`，要求查明原因并留档，避免后人重复追问

---

## 1. 背景与目标

用户查阅 Kimi 平台调用记录时发现：同为 Kimi Code CLI（2.3.2）发出的请求，**K3.1 Pro 的来源列为 `kimi-code-cli/2.3.2`，K2.8 Preview（`kimi-for-coding`）的来源列却是 `OpenAI/JS 6.34.0`**。初步怀疑与 IDE 或第三方工具有关。

调查目标：

1. 确认这些请求是否真由 Kimi Code CLI 发出；
2. 查明来源字段差异的根因；
3. 结论留档，后续同类疑问直接引用本文档。

**最终结论（TL;DR）**：差异与 IDE、与第三方工具均无关。Kimi Code CLI 内部按模型分两条 HTTP 通道——K2.8 走内嵌的 openai JS SDK 打 OpenAI 兼容端点（UA 为 SDK 默认的 `OpenAI/JS 6.34.0`），K3.1 走 CLI 原生请求路径（UA 为 `kimi-code-cli/2.3.2`）。平台「来源」列显示的就是实际请求的 User-Agent。属 CLI 正常内部实现，**Zen Studio 零改动**。

## 2. 调查过程摘要

调查分四步，每步结论均为实测/实证，非推测：

1. **IDE 侧排查**：全库检索确认 Zen Studio 自身从不发 HTTP 请求——`src/ide/llm/registry.py` 注册的 7 个后端全部是 ACP 子进程传输层（`kimi acp`、`dsh acp` 等），`src/ide/llm/README.md` 亦声明代码库不存放、不读取任何 API KEY。IDE 无产生 `OpenAI/JS` 来源的能力。
2. **二进制取证**：对 `~/.kimi-code/bin/kimi`（189MB Deno 编译单文件）做字符串提取，找到内嵌 openai JS SDK 的指纹与版本号（见 §4）。
3. **官网文档核对**：Kimi Code 官方模型配置页对 K3.1 明确推荐「native APIs」，第三方/兼容层走 `https://api.kimi.com/coding/v1`（OpenAI 兼容协议）。
4. **本机会话实证**：`~/.kimi-code/sessions/*/wire.jsonl` 中对应时间窗的会话记录，确认请求确由 CLI 发出、且模型与时间窗吻合（见 §4 证据三）。

## 3. 结论

| 模型 | CLI 内部通道 | 端点 | User-Agent（=平台来源列） |
| --- | --- | --- | --- |
| K2.8（`kimi-for-coding`） | 内嵌 **openai JS SDK**（v6.34.0） | `https://api.kimi.com/coding/v1`（OpenAI 兼容协议） | `OpenAI/JS 6.34.0` |
| K3.1 Pro（`k3.1-pro`） | CLI **原生请求路径** | 原生 Responses / 聊天接口 | `kimi-code-cli/2.3.2` |

推论：判断一条 Kimi 平台调用是否走 CLI 原生路径，看来源列是否含 `kimi-code-cli/` 前缀即可；显示 `OpenAI/JS` 不等于「第三方工具盗用」，也可能是 CLI 自己的 K2.x 兼容通道。

## 4. 证据明细

### 证据一：IDE 侧无 HTTP 能力（排除 IDE 嫌疑）

- `src/ide/llm/README.md`：「对话统一经本机 agent CLI 完成，代码库不存放、不读取、不输入任何 API KEY」；DeepSeek API KEY 直连已于 2026-07-18 移除。
- `src/ide/llm/registry.py`：全接口均为 ACP 传输层（注释明言「kimi CLI `-p` 模式已于 2026-07-31 移除」）。
- `src/ide/llm/providers/kimi_acp.py`：Kimi 后端 = 长驻 `kimi acp` 子进程（`AcpConnection(bin_path, ..., "kimi acp")`）。无论选哪个模型，发请求的永远是本机 kimi 二进制。

### 证据二：kimi 二进制内嵌 openai JS SDK 6.34.0

对 `~/.kimi-code/bin/kimi` 执行 `strings` 提取，命中：

- SDK 指纹头：`"X-Stainless-Lang": "js"`、`"X-Stainless-Package-Version": VERSION`（`X-Stainless-*` 为 openai npm SDK 专有请求头）；
- UA 模板：`JS ${VERSION}`（与 `OpenAI/` 前缀拼成 `OpenAI/JS <版本>`）；
- 版本号字面量：`6.34.0`——与调用记录中 `OpenAI/JS 6.34.0` 精确吻合；
- 并存 `anthropic-sdk-typescript/0.95.2` UA 与 `kimi-code-cli/<version>` UA，以及 UA 构造中间件代码：

```text
if (!userAgent.includes(`${shared_cjs_1.PRODUCT_NAME}/`)) config.headers.set("User-Agent", `${userAgent} ${shared_cjs_1.USER_AGENT}`)
```

- 预设端点表：`kimi-for-coding → https://api.kimi.com/coding/v1`、`kimi-for-coding-global → https://api.kimi.ai/coding/v1`（OpenAI 兼容端点）。

（当时亦排查并排除了本机 opencode：`~/.opencode/bin/opencode` 内无 `OpenAI/JS` 字符串；`~/.config/opencode/opencode.jsonc` 未配置 kimi provider。）

### 证据三：官网文档佐证

Kimi Code 官方模型配置页（https://www.kimi.com/code/docs/en/kimi-code/models.html ）：

- 「Use the native APIs: for K3.1 Pro models, we recommend the Kimi Coding Plan's **native** Responses, chat completion, or message APIs for the most stable output. Protocol translation through proxy tools may cause model behavior to vary.」——K3.1 存在原生 API 路径；
- 第三方工具 Base URL：`https://api.kimi.com/coding/v1`（OpenAI Responses / Chat Completions 兼容）、`https://api.kimi.com/coding/`（Anthropic 兼容）——K2.x 通道即此类兼容端点。

### 证据四：本机会话落盘实证（确认确为 CLI 所发）

`~/.kimi-code/sessions/` 下按工作区分目录、`*/agents/main/wire.jsonl` 记录每次 `llm.request`。2026-11-16 时间窗核对：

- `wd_zen_quant_4691d86cd0b8` 会话（wire.jsonl 最后写入 13:59:48）：144 条 `llm.request` 全部 `provider:"openai"`、`model:"kimi-for-coding"`、`modelAlias:"kimi-code/kimi-for-coding"`——与调用记录中 13:58:55–13:59:25 的四条 `OpenAI/JS 6.34.0` + K2.8 记录时间吻合；
- `wd_graphify_8_ffbd46a02ea1` 两个会话（最后写入 14:01:33 等）：`llm.request` 为 `model:"k3.1-pro"`——与 13:53:52、14:01:35、14:01:42 的 `kimi-code-cli/2.3.2` + K3.1 记录吻合。

注：wire.jsonl 中的 `provider:"openai"` 是 CLI 内部的**协议实现标签**（openai 兼容协议），两条模型都挂这个标签；真正的 UA 差异发生在更下层 HTTP 客户端，由证据二的 SDK 内嵌与 UA 构造代码解释。

## 5. 影响与后续注意事项

- **Zen Studio 零改动**：这是 Kimi Code CLI 自身的内部路由实现（老模型走 OpenAI 兼容 SDK 通道、新旗舰走原生通道），IDE 仅启动 `kimi acp` 子进程，不感知、也无法改变该行为。
- CLI 升级后 UA 版本号会随版本变化（记录基线时为 2.3.2 / openai SDK 6.34.0），来源列前缀规律不变。
- 后人再问到「为什么来源列不是 kimi-code-cli」：先看来源列有无 `kimi-code-cli/` 前缀——有即原生路径（K3.x），是 `OpenAI/JS` 即兼容 SDK 路径（K2.x），均属 CLI 正常行为；只有出现其他 UA（如 `python-requests`、`node`、未知 SDK）才需要怀疑第三方工具。

## 6. 风险与注意点

- 本文结论基于 CLI 2.3.2 二进制取证（2026-11-19）。CLI 大版本升级后内部路由可能调整，复验方法：§4 证据二的 `strings` 提取命令对新版二进制重跑一遍即可。
- 取证命令会输出大体积内容，建议在项目 `./.temp/` 下落盘再检索，勿直接全量打印。

## 7. 已确认决策

- 差异根因 = Kimi Code CLI 内部按模型分通道（K2.8 → 内嵌 openai JS SDK → UA `OpenAI/JS`；K3.1 → 原生路径 → UA `kimi-code-cli/`），非 IDE 行为、非第三方调用。
