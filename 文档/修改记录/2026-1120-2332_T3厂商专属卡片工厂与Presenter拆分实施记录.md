## 4. 边界与偏差

- **卡片字段落屏仍在厂商 `cards.py`**：`presenter.py` 承接的是跨帧路由（标题/命令账本、迟到帧闸门、旧轨输出裁剪、todo entries、改盘终态判断）；每张卡的 `apply_update` 仍由本厂商卡片类解释自身 payload 并驱动 `card_base.ToolCard` 的通用生命周期。这样卡片 body 的字段覆盖不需要在 presenter 再暴露一套 mutator，且 payload 解释仍完全在厂商包内。计划 T3.3.1 字面上的「卡片更新分支移入 presenter」按此口径落地。
- **旧轨（classic）保留为通用文本渲染器**：面板不再解析载荷；各厂商 presenter 在交给 `ChatOutput` 前完成标题回填、命令头注入与 20 行裁剪。`output.py` 仍按 `command`/`output`/`summary` 等字段渲染旧轨文本卡，这是冻结回退通道的既有格式，不再是面板级厂商分支。
- **Kimi/DSH/Local 工具名表按行为基线收敛**：Kimi 保留历史 `ask`（reasonix 截图蓝本）与 `todowrite`；Local 保留旧共享表中 Local 可能收到的 `askuserquestion`/`ask`/`agent`/`task`/`readmediafile`/`todolist`/`todowrite`，但不收 DSH 的 `read_image`/`todo_write`；DSH 按计划只承接 `read_image`/`todo_write`/`subagent`。三张表各自持有，不互相 import。
- **图片/输出 HTML helper 共享到 `card_base`**：`MCP_IMAGE_WIDTH`、略缩图宽/大小护栏、JSON pretty、`compose_mcp_output_html`、`media_thumb_html` 属无厂商语义技术件，未复制进三家 cards；todo 条目绘制与问答出参解析仍留在各厂商 cards，因为它们是卡片格式而非纯技术件。
- **`card_base.ToolCard` 只读生命周期元数据**：仅读 `tool_call_id`/`tool_kind`/`title`，`summary` 由厂商子类作为 subtitle 传入；`error_detail`/`error` 的默认错误块也下沉到各厂商 `ToolCard._on_failed`，base 不再读取错误字段。
- **额外收敛看门狗旁路**：T3 计划只要求轮后用量宽限，但 T0 清单把 `_llm_name == "kimi-acp"` 的看门狗旁路也列为待移出项；本项一并改为 `stall_watchdog_enabled()` 可选能力，避免通用面板残留后台 ID 分支。
- **`QuestionBridge` 增加 vendor 参数**：提问卡注册表按厂商隔离后，面板把当前 `_chat_vendor` 传入桥；旧调用方缺省 `local`，不破坏无 GUI 夹具。
- T3 未启动 T4；`permission_policy.py` 的 Kimi 类型依赖、权限分类、DSH 提问回环仍归 T4。

## 5. 后续注意

- T5 架构守卫应把本记录中的边界固化为 AST 断言：通用面板/card_base 不 import 具体厂商包或私有 mapper；三家厂商包不得横向 import；`vendors/registry.py` 是唯一允许同时 import 三家卡片包的位置。
- 若后续新增厂商，需要同时提供 `cards.py`/`factory.py`/`presenter.py` 并只在 `vendors/registry.py` 注册；不要复用其他厂商的工具名表或卡片类。
- 历史工具卡载荷不入存档；将来若改变会话持久化格式，需先补对应厂商 presenter 的旧载荷读取测试，再改存档 schema。
