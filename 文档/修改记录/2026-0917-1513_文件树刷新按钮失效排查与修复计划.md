## 1. 问题现象

用户实机反馈（AppImage 打包新版）：

1. 编程 agent 在外部将一个文件重命名；
2. 文件树仍显示旧文件名；
3. 用户右键「在文件管理器中显示」，确认磁盘上文件名**已正确更改**——即磁盘状态正确、只有树滞留；
4. 用户点击右下角悬浮刷新按钮，**按钮 UI 有按下反馈，但树无任何变化**，旧名字依旧。

结论：前次落地（`2026-0916-1353_文件树右下角悬浮刷新按钮落地计划.md`）的刷新按钮在用户真实场景中**未能完成刷新**。

## 2. 已有事实（2026-09-17 探针验证）

探针脚本 `.temp/probe_refresh_rename.py`（offscreen，本地 .venv PySide6）实测：

- 🟢 **场景 A（watcher 正常）**：外部重命名后树自动更新；`refresh()` 脱根重挂亦正常。`refresh()` 方法本身逻辑有效。
- 🟡 **场景 B（模拟 watcher 漏事件）未模拟成功**：`model.findChildren(QFileSystemWatcher)` 返回 **0 个**，屏蔽落空；重命名后树照常自动更新。即 **"watcher 真失效 + refresh 补救"这条用户真实路径至今未被复现验证**，前次计划 T4 的"功能验证通过"实际只覆盖了 watcher 正常的路径。

由此推出：本次排查的核心未知量是——**当 watcher 真的漏掉事件、模型节点缓存滞留时，`setRootPath("")` + `setRootPath(root_dir)` 的脱根重挂到底清不清缓存**。Qt 不同版本对此行为有差异，不能凭前次计划的假设作答。

## 3. 嫌疑假设（按优先级排序）

| 编号 | 假设 | 依据 |
|:---:|:---|:---|
| H1 | **`refresh()` 根本没被执行**：按钮"UI 动了"只是 pressed 视觉态，`clicked` 未发射（按下后位移/释放偏出），或槽内异常被 Qt 吞到 stderr（AppImage 下不可见） | 用户只确认 UI 反馈，未确认刷新动作发生 |
| H2 | **脱根重挂在 watcher 失效时清不掉节点缓存**：`QFileSystemModel` 内部节点树缓存滞留，`setRootPath` 不强制失效 | 前次计划 §2.2 的"强制全量重读"是假设，未在 watcher 失效场景实测；探针场景 B 未能覆盖 |
| H3 | **AppImage 打包环境差异**：打包的 PySide6/Qt 版本与本地 .venv 不一致，`setRootPath` 或 watcher 行为不同 | 用户用的是 AppImage，探针跑在本地 .venv |
| H4 | **刷新对象错位**：用户期待的"刷新"不止目录结构（如 Git 状态着色），或滞留节点在子目录层级 | 用户描述集中在文件名，优先级最低 |

## 4.5 排查结果（2026-09-17 探针实证）

### P1 点击链路核查 —— 🟢 链路完好，H1 代码层排除

- `config/logs/zen-studio.log` 无 refresh 相关 traceback（仅一条 2026-09-10 无关测试日志）；须注意 AppImage 运行日志不落本目录，用户现场日志不可得。
- 探针 `.temp/probe_p1_click.py`：中心点击 → `refresh()` 精确调用 1 次；直接发射 `clicked` → 连接完好。
- 附带确认机制事实：**pressed 视觉态 ≠ clicked 发射**——按下后移出按钮再释放，按钮有"动了"的视觉反馈但 `refresh()` 调用 0 次。H1 在代码层无缺陷，但用户现场无法完全排除"按下位移导致 clicked 未发射"，列为次要伴随因素。

### P2 版本对比 —— 🟢 H3 排除

- 本地 .venv：PySide6 6.11.1 / Qt 6.11.1。
- AppImage 产物 `building/dist/zen-studio/_internal/`：`libQt6Core.so.6` 版本串 6.11.1，`libpyside6.abi3.so.6.11`、`libshiboken6.abi3.so.6.11`——**与本地完全一致**，打包环境差异排除。

### P3 watcher 真失效复现 —— 🔴 复现成功，H2 实锤

- 命名空间隔离方案不可用：本机 AppArmor 拦截非特权 user namespace（`unshare -Ur` 与 `bwrap` 均被拒）。改用 **LD_PRELOAD 故障注入**：`.temp/no_inotify_shim.c` 拦截 `inotify_add_watch` 恒返回 ENOSPC，Qt 端表现与 inotify 耗尽完全一致（stderr 可见 Qt 自己的 `inotify_add_watch(...) failed: (No space left on device)` 警告），作用域仅探针进程，系统零影响。
- 探针 `.temp/probe_p3_refresh.py`（根目录平铺场景）：watcher 失效 → 外部重命名 → 树滞留旧名 ✅ → 真实点击按钮 → **根层刷新成功**。
- 探针 `.temp/probe_p3b_nested.py`（**子目录 + 文件选中态**，贴合用户现场）：watcher 失效 → 外部重命名 → 树滞留旧名 ✅ → 真实点击按钮 → **🔴 子目录内仍显示旧名**，与用户反馈完全一致。展开态回填"成功"（subdir 重新展开）恰恰是因为陈旧缓存节点还活着——回填端回来的是旧数据。

### P4 缓存层级定位 —— 根因锁定

探针 `.temp/probe_p4_cache_level.py` 诊断：

1. refresh 后 `directoryLoaded` 只触发根目录（`proj`），**子目录从未被重新列举**；
2. 滞留子目录节点 `canFetchMore = False`——populated 标记存活，模型视缓存为权威，`fetchMore` 补救路径不可用。

**根因结论**：`setRootPath("")` + `setRootPath(root_dir)` 只强制重列**根目录一层**；根目录以下已填充的子目录节点树（populated 标记 + 子项缓存）原样存活。watcher 正常时深层更新靠 watcher 事件补齐，故前次计划 T4 验证通过、根层探针也通过；一旦 watcher 真失效，**深层滞留永远救不回来**——这正是"偶尔一直显示旧的"且"点了刷新也没用"的完整机制。

## 5. 修复方案（2026-09-17 已拍板：方案 A + 日志系统完善）

根因是 `QFileSystemModel` 深层节点缓存无公共 API 可失效，候选方案：

- **方案 A（✅ 已拍板）：重建模型实例**。`refresh()` 不再脱根重挂，改为：收集展开/选中状态 → 新建 `QFileSystemModel`（全新节点树，缓存物理消灭）→ proxy `setSourceModel` 换挂 → `directoryLoaded` 接力回填。改动集中在 `explorer.py` 的 `refresh()` 与 `_build_model()`；需把 filter、readOnly 等装配参数抽成可复用段，并验证旧 model 的 `directoryLoaded` 连接切换到新 model。
- **方案 B：根层逐子目录递归强制失效**。无公共 API，只能靠 `removeRows` 等间接手段逐个拔节点，fragile，不推荐。
- **方案 C：升级 Qt 版本**。H3 已排除版本差异，且 Qt 6.11 行为即如此，升级不解问题，排除。

### 5.5 日志系统完善（✅ 已拍板，本次事故的三个观测盲区）

本次排查暴露日志设施的三个洞，逐一补：

1. **Qt 自身警告不进日志**：本次关键线索 `inotify_add_watch(...) failed` 是 Qt 直接写 stderr 的 qWarning，不经 Python logging——打包态 stderr 不可见，彻底丢失。补法：`setup_logging()` 里装 `qInstallMessageHandler`，按 QtMsgType 映射级别桥接进 logging（logger 名 `qt`）。
2. **槽内异常吞 stderr**：PySide6 槽函数异常打印 traceback 后继续运行，打包态不可见。补法：`sys.excepthook` / `threading.excepthook` 桥接进 logging，异常落日志文件。
3. **关键动作无审计痕迹**：本次无法分辨用户"没点到"还是"点了没用"。补法：`FileExplorer.refresh()` 入口与完成各落一条 INFO 日志（含待回填的展开/选中计数），下次同类反馈可直接从日志分辨。

设施现状：`main.py` 的 `setup_logging()` 已实现 INFO 级文件 + stderr 双输出、各模块 `getLogger(__name__)` 纪律（2026-0909-2349 计划 T1），本次在其上增量补三个桥，不重建。

## 7. 影响面评估

- P 阶段只加探针脚本（`.temp/`）与只读排查，零产品代码改动。
- 方案 A 改动集中在 `gui/panels/file_explorer/explorer.py` 的 `refresh()` 与装配段；Git 状态着色、右键动作、拖出均挂在 proxy/tree 上（proxy 不重建，仅换 sourceModel），重挂后需验证信号重连与着色刷新。
- **agent 工作中刷新的安全性（2026-09-17 用户提问，已审查）**：全项目检索确认 `FileExplorer` 仅被 GUI 层引用（`gui/main_window.py`、`gui/controllers.py`、`gui/menus/view_menu.py`），`llm/`、`dream-acp/`、`core/` 零引用——agent 写文件走后端工具层直写磁盘，与文件树零耦合；refresh 对磁盘唯一动作是重读目录项（readdir），不写不锁不发信号，agent 任务无感。时序边角：刷新恰逢写入中间瞬间，树可能短暂显示中间态，但重建出的新模型带健康 watcher，写入完成即自我修正——比现状改善。
- 日志三桥为纯增量：`qInstallMessageHandler` 全局唯一，装好勿重复装；excepthook 桥保留原 hook 链（先落日志再走原行为）。
- ✅ P3 实际采用 LD_PRELOAD 进程内故障注入（`.temp/no_inotify_shim.c`），未触碰系统 inotify 全局资源，无需恢复操作、无需 sudo。
