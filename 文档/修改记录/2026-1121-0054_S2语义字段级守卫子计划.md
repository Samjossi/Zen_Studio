## 1. 背景与目标

现有守卫以固定 token 词表和 import 方向为主：它能阻止跨厂商 import，但抓不住通用 GUI 读取 `command`/`output`/`summary`/`status`/`error`/`is_subagent` 这类字段级违约，也抓不住中文厂商文案、`kimi_wire_sidecar` 设置键与能力鸭子接口。S0/S1 已把这几类现状清零，本子计划把边界固化为可执行的规则。

本子计划目标：

1. 增加 AST 语义扫描：只检查代码中的字符串常量与属性名，排除注释与 docstring。
2. 落地通用 GUI 载荷字段白名单、能力探针禁止清单、厂商设置键归属、厂商新模块 import 归属。
3. 每条规则配受控反例，并保留聚合入口失败用例。

## 2. 启动条件与边界

- S0、S1 已完成并获批准后，本子计划再单独取得用户同意；批准不包含 S3。
- 只改测试与守卫；生产源码原则上零改动。若规则抓到 S0/S1 遗漏的违约，先回报，再做与规则同边界的最小修复。
- 不引入新依赖；保持标准库 `ast`/`tokenize`；不扫描 `tests/`、`scripts/`、历史文档与帧存档。
- 规则必须能失败：每条规则至少一个受控反例；聚合入口也要有失败用例。
- 不把厂商语义改名藏到公共模块来规避规则。

### S2.2 AST 语义扫描 helper

1. 在测试文件内增加源码解析 helper：收集 `ast.Constant` 字符串、`ast.Attribute` 属性名、`ast.Name` 标识符。
2. 跳过模块/类/函数 docstring（`ast.Expr` 且值为字符串常量的节点）；注释天然不在 AST 中，不额外处理。
3. 保留现有原始源码 token 扫描作为补充，但新规则以 AST 结果为准，避免注释与 docstring 误报。
4. helper 必须有自测：同一段文本放进注释、docstring、字符串常量时，结果分别是「不命中 / 不命中 / 命中」。

### S2.3 五类规则

1. **公共层与通用 GUI 厂商词表**：代码字符串常量中不得出现厂商显示名、工具名、私有路径与设置键；日志/用户文案也要按中性文本写。
2. **通用 GUI 载荷字段白名单**：通用聊天模块只允许读取 `tool_call_id`、`parent_tool_call_id`、`tool_kind`、`title` 等路由/生命周期字段；`command`、`output`、`output_total_lines`、`summary`、`status`、`error`、`error_detail`、`diff_hunks`、`is_subagent`、`questions`、`result_summary`、`media_path` 只允许出现在厂商包。
3. **能力探针禁止清单**：通用 GUI 不得以 `getattr(provider, "supports_images_override")` 等形式读取 `supports_images_override`、`post_turn_usage_grace_s`、`stall_watchdog_enabled`、`recovery_pending`、`set_subagent_sidecar`；只能走 `capabilities_of()` 与厂商设置入口。
4. **厂商设置键归属**：`kimi_wire_sidecar`/`KEY_KIMI_*` 只允许出现在 Kimi 包与注册表组合根；通用 GUI 不得出现。
5. **新增厂商模块 import 归属**：`kimi/wire.py`、`kimi/usage.py`、`kimi/subagent.py`、`dsh/session_log.py` 只允许本厂商包导入；公共 ACP 与通用 GUI 不得导入。

### 6.3 经验沉淀

1. **载荷规则必须绑定「载荷表达式」而不是字段名本身**：`command`/`status` 这类词在 ACP 权限参数、设置、日志里都合法；按 `payload` 接收者与赋值别名判定，既抓住 `timeline.py` 的真违约，也避免把 `permission_dialog` 的 `rawInput` 误报。字段名全局禁用会把守卫变成噪声源。
2. **旁路组件是字段级守卫的盲区**：面板把工具帧同时喂 presenter 与时间线，时间线直读载荷多年未被 import/词表守卫发现。审查「通用 GUI 是否解释厂商载荷」时，要单独列旁路消费者（timeline、通知、统计），不能只看卡片与面板主路径。
3. **把解释下沉为「中性投影」比在通用层加例外更稳**：投影是纯函数、每厂商 14 行，通用组件只认 `tip/weight/failed/failure_detail`；视觉公式不变，却把 summary/status/error 的归属彻底移到厂商侧。三家重复是实现隔离的代价，参数化测试防止三份漂移。
4. **白名单要预留中性呈现键**：严格白名单会立刻要求回答「投影键算不算载荷」。先登记 `tip/weight/failed/failure_detail` 与 `entries`，并注明来源，可避免每次新增展示字段都被迫修改规则。
5. **持久化 schema 是设置键规则绕不开的例外**：S0 已预判并写入回写；S2 若机械执行「只允许组合根」，会把不能删的兼容键判成违约。凡「键名归属」规则，都要同时检查「schema 声明层」与「消费层」。
6. **未创建模块也能前置守卫**：按绝对模块名匹配 import 目标，并用 `from 包 import 子模块` 的候选展开覆盖两种写法；反例先于文件存在，S3/S4 落地时守卫自动生效。
