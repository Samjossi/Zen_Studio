# 切模型 / 切后台性能优化计划

## 1. 问题与原因

### 1.1 现象

- OpenCode / KiloCode 后台下**切换模型**卡顿明显；
- **切换后台**（一级菜单）卡顿更严重。

### 1.2 调查结论（2026-07-30 只读调查，精确到行）

所有耗时均为 **GUI 线程上的同步阻塞调用**，且被「广播 × 标签数（≤4）」放大：

| # | 阻塞点 | 位置 | 触发时机 | 最坏耗时 |
|---|--------|------|----------|----------|
| 1 | `subprocess.run(["kilo"/"opencode", "models"], timeout=15)`，**无任何缓存** | `llm/providers/kilocode_acp.py:102`、`opencode_acp.py:98` | 每次 `ModelBar.set_selection()` 都无条件 `_refresh_models()`（`model_bar.py:285`）→ 切模型/切后台/切接口/新建标签全中招 | 15s/次 × 标签数 |
| 2 | 旧 provider 同步 `close()` → `terminate()` → `_proc.wait(timeout=5)` | `gui/panels/chat/panel.py:148-150` → `llm/providers/acp.py:269-274` | 切后台/切接口且旧实例存活 | 5s/次 × 面板数 |
| 3 | 活跃会话上 `session/set_config_option` RPC 同步等待（`timeout=10`） | `kilocode_acp.py:150`、`opencode_acp.py:146` | 切模型且该标签已有会话 | 10s/次 |

**关键事实**（排除非瓶颈）：

- 切模型**不重启** ACP 进程（`session/set_config_option` 同会话热切换）；
- 新后台 provider 懒启动，握手推迟到下一轮对话，不在切换路径上；
- 打开菜单不重建（eager 构建），「打开菜单卡」的体感实为上一次点击的重建还在卡；
- `update_settings` 落盘为毫秒级，非瓶颈。

### 1.3 根因排序

1. **模型列表零缓存 + `set_selection` 无条件重建模型菜单**：纯切模型时模型目录根本没变，仍每面板跑一次完整 CLI 子进程（Node 冷启动 + 可能触网刷新 models.dev）。
2. **切换路径的 `close()` 未异步化**：`ChatPanel.close()` 早已两段式（阻塞 terminate 挪 daemon 线程，`panel.py:165-193`），但 `set_model_selection` 的切换路径（`panel.py:148-150`）是同步 close——同一个类两种策略不一致，切换路径没吃到异步化红利。
3. **set_model RPC 在 GUI 线程同步等 agent 应答**：正常亚秒，但与 #1/#2 叠加放大卡顿。

## 2. 决策

| # | 决策点 | 选定 | 理由 |
|---|--------|------|------|
| D1 | 模型列表缓存位置 | **注册表层 `registry.py` 包装缓存**（进程级 dict：`backend → aliases`），provider 层零改动 | 单一消费入口（`spec.list_models()`），一处加缓存所有消费方（ModelBar ×N 面板、设置中心）同时受益；settings_dialog 已有同款 `_models_cache`（`settings_dialog.py:146`）先例 |
| D2 | 缓存失效策略 | **无 TTL，进程生命周期内一次拉取** + 设置中心 `reload` 时提供 `refresh_models(backend)` 显式刷新口 | 模型目录变化频率以天计；GUI 进程内反复拉取纯属浪费。简单优先，不做 TTL/文件监听 |
| D3 | 无谓重建消除 | `ModelBar.set_selection()` 中 **backend 未变时跳过 `_refresh_models`**（仅重新勾选） | 纯切模型时目录数据不变，重建纯属浪费；缓存到位后此条为锦上添花，一并做 |
| D4 | 旧 provider close 异步化 | `set_model_selection` 切换路径复用 `_cleanup_blocking` daemon 线程模式（对齐 `ChatPanel.close()`） | 同类已有成熟模式，消除 5s/次 的 GUI 干等 |
| D5 | set_model RPC 异步化 | **fire-and-forget daemon 线程**执行 `set_model`；失败降级语义不变（provider 内部已含「下次重建会话」兜底） | RPC 响应不改变 UI 状态（菜单勾选已先行），无需同步等待 |
| D6 | D6 红线 | **不破**：模型目录仍挂接口级（缓存在接口 key 上）；别名仍不透明透传；先清后建/回退首项语义不变 | 缓存只是「同一次调用结果复用」，不改变数据来源层级 |

**不做的事**：不改 ACP 握手时机（不在切换路径上）；不做菜单懒加载（eager 构建配合缓存已毫秒级）；不做跨进程/落盘缓存（YAGNI）；不动 kimi/reasonix 后台行为（同型缓存自动惠及，无需特改）。

## 3. 改造方案

### 3.1 `llm/registry.py`：模型列表缓存（核心）

- 模块级新增 `_models_cache: dict[str, tuple[str, ...]]`（backend → 模型别名元组）。
- `ProviderSpec.list_models()` 消费入口不变；在注册表层包一个缓存访问函数（或给 spec 的 list_models 加薄缓存包装），命中直接返回缓存副本。
- 新增 `refresh_models(backend: str | None = None)`：清指定 backend（或全部）缓存并重新拉取，供设置中心等显式刷新场景调用。
- 模块 docstring 补充缓存语义：进程生命周期内一次拉取、模型目录低频变化、`refresh_models` 为唯一失效口。
- **D6 红线 1 不破**：缓存 key 即接口名（backend），目录仍由接口级 `list_models` 提供。

### 3.2 `gui/panels/chat/model_bar.py`：跳过无谓重建

- `set_selection()`：记录当前 `_model_group` 对应 backend；若 `self.current_backend()` 与传入 backend（回退后有效值）一致且模型组非空，跳过 `_refresh_models()`，只做勾选修正。
- `_refresh_models` 本身不动（先清后建语义保留，供真实切换/回退使用）；缓存到位后即便重建也是毫秒级，此为双保险。

### 3.3 `gui/panels/chat/panel.py`：切换路径异步化

- `set_model_selection` 中旧实例处理（`:148-150`）：`pop` 出来后不同步 `close()`，改为 `threading.Thread(target=_cleanup_blocking, args=([old], None, None), daemon=True).start()`（复用同类 `:192-193` 模式；`_cleanup_blocking` 需支持 worker/panel 为 None 的调用形态，若不支持则加默认值或内联薄封装）。
- `set_model(version)` 调用（`:155-157`）：挪入 daemon 线程 fire-and-forget；provider 内部 RPC 失败的「下次重建会话」降级逻辑已在 provider 层，无需 GUI 层补偿。
- **线程安全说明**：provider 实例的 `close()`/`set_model()` 本就被设计为可从清理线程调用（`ChatPanel.close()` 先例）；切换后旧实例不再被本面板引用，无并发访问。

### 3.4 零改动确认

| 消费方 | 改动 |
|--------|------|
| `llm/providers/*.py` | 无（缓存加在注册表层） |
| `gui/settings_dialog.py` | 可选接线 `refresh_models`（本期不动，其自有 `_models_cache` 维持现状） |
| ACP 连接生命周期 | 无（握手仍在 `_ensure_session`，切模型仍热切换） |
| D6 红线 1/2/4/5 | 无（§2 D6） |

## 5. 验收标准

1. 同一 GUI 进程内，`list_models` 底层子进程每 backend 至多执行一次（第二次起缓存命中）。
2. 4 标签全开下切模型：GUI 无线程级卡顿（无子进程调用、无 RPC 同步等待），主观即时响应。
3. 切后台：无 `terminate/wait` 同步阻塞，主观即时响应；旧进程在后台线程正常回收（无僵尸进程累积）。
4. 两注册表烟测全过（含新缓存断言）；全库 grep 确认缓存仅存在于注册表层（provider 层零改动）。
5. 切换后首轮对话正常（含切模型热切换、切后台新会话握手）。

## 6. 风险与回归点

- **模型目录过期**：用户新装 provider / agent 更新模型目录后，GUI 进程内看不到——需重启 GUI 或后续接线设置中心刷新口；目录变化以天计，可接受（D2 明示取舍）。
- **异步 close 与复用竞态**：切后台 A→B 又快速切回 A，`pop` 后旧 A 实例在后台 close，新 A 实例重新构造——两实例独立子进程，无共享状态；close 仅终止旧进程，安全。
- **fire-and-forget set_model 时序**：切换后立刻发消息，`set_model` 线程与对话线程可能并发触达同一 provider——provider 层 `_ensure_session` 已有锁/状态管理（需实施时核实；若无锁，T4 退化为「set_model 仍在切换路径同步执行、仅 close 异步」，风险可控）。
- **缓存与 D6 红线 4「先清后建」**：缓存只加速数据获取，菜单先清后建/回退首项语义不变，旧后台别名不会残留。
