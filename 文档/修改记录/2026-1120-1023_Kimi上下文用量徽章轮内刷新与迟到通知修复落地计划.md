> **优先级**：高

## 1. 背景与目标

### 1.1 现象

- Kimi 聊天面板右侧上下文用量徽章有时长时间空白，长任务结束后才出现百分比。
- 悬停位置仍能出现 tooltip，但缺少上下文已用量、上限等段，表现为信息不完整。
- 用户还观察到已显示的徽章后来消失；更换 IDE 后仍遇到轮末才显示的情况。

### 1.2 修复目标

1. Kimi 多步任务中，每次模型调用完成并产生真实计量后，徽章应在现有 2 秒轮询节拍内刷新，不应普遍等到整个任务结束。
2. 会话目录或模型目录的一次临时失败，不得让整个会话永久失去轮内用量。
3. 大型工具输出不得把既有有效用量挤出固定 64KB 窗口后造成后续采样失灵。
4. prompt response 后迟到的官方 `usage_update` 不得仅因超过 3 秒或下一轮清理队列而永久丢失。
5. 暂无真实数据时明确显示等待/不可用状态，不伪造 `0%`；已有有效值不得被后续空轮询清掉。
6. tooltip 在没有用量数值时给出明确原因；有数据时保留既有用量、计时和速度明细。

### 1.3 非目标

- 不修改 Kimi CLI 或其他 IDE，不降级或锁定 CLI 版本。
- 不把上下文占用与会员额度、Token 累计消耗混为一谈。
- 不按流式文本长度虚构上下文百分比，不新增静态模型窗口表。
- 不改变 `stopReason`、手动停止、看门狗、排队待发和会话恢复语义。
- 不放宽所有 ACP 后端的通知清理规则；改动优先封闭在 Kimi provider 与徽章计时器内。

## 2. 调查结论与证据边界

### 2.1 用户线索只对了一半：官方 ACP 本来就是轮末单帧

对照此前记录的 2.3.2 实现与本次核对的 2.6.3 实现，关键链路没有改成另一种字段或另一种推送时机：

- `onTurnEnded()` 先结算 prompt，再异步调用 `emitUsageUpdate()`。
- `emitUsageUpdate()` 依次等待模型目录与当前上下文，随后才发出 `usage_update`。
- 帧格式仍为 `sessionUpdate="usage_update"`，携带 `used` 与 `size`。
- 上游端到端测试同样是在 prompt 完成后等待这条通知。

因此，**只消费公开 ACP 的其他 IDE 在长任务结束后才显示，符合 Kimi 当前实现，不足以证明 Zen 的对接字段已经失效。** Zen 的轮内刷新来自自己额外读取 wire 的通道，故障重点应放在这条补充通道及迟到帧接收上。

上游证据：

- [Kimi Code 2.6.3 ACP session 实现](https://github.com/MoonshotAI/kimi-code/blob/b0de2fbd2de04d87689225aafd3912e5d193b62d/packages/acp-server/src/session.ts)
- [Kimi Code 2.6.3 usage_update 帧构造](https://github.com/MoonshotAI/kimi-code/blob/b0de2fbd2de04d87689225aafd3912e5d193b62d/packages/acp-server/src/events-map.ts)
- [Kimi Code ACP 轮次端到端测试](https://github.com/MoonshotAI/kimi-code/blob/b0de2fbd2de04d87689225aafd3912e5d193b62d/packages/acp-server/test/e2e-turn.test.ts)

### 2.2 已复现的本地缺陷

以下结论来自当前源码和本次无网络、无真实会话内容的合成探针，不依赖对上游变化的猜测。

#### F1 会话目录定位失败被永久负缓存

`KimiAcpLLM.poll_usage()` 在第一次按 session ID 查目录时，无论成功还是 `None`，都记录 `_poll_dir_sid`。后续同一 session ID 不再反查。

本次探针让第一次定位返回 `None`、第二次本应成功，实际两次轮询均为 `None`，目录查找次数恒为 1。一次索引尚未就绪、半行 JSON 或临时读取失败，就足以让该会话的轮内 wire 永久失效；轮末官方 ACP 仍可能成功，于是形成「只在任务结束后显示」。

#### F2 模型窗口目录首次为空后不再重试

`_ensure_context_sizes()` 第一次调用后立即置 `_context_sizes_loaded=True`，即使目录载荷为空。后续调用直接返回。

本次探针让第一次目录为空、第二次返回有效 `maxContextSize`，实际目录命令只调用一次，缓存仍为空。没有窗口就无法从 wire 定型 `UsageStats`，但官方 ACP 自带给定 `size`，所以同样表现为轮内长期空白、轮末可能恢复。

#### F3 固定 64KB 尾部窗口会丢掉仍然有效的历史采样

`_read_wire_usage_tail()` 要求在同一尾部窗口内同时找到 turn 请求与有效用量。大型工具结果可以把两类记录都挤出 64KB；函数随后返回 `None`，没有增量游标或最后有效采样可复用。

本次合成文件按 `llm.request → usage.record → 70KB tool.result` 排列，真实有效用量存在，函数仍返回 `None`。现有 GUI 虽会保留旧徽章，但首轮采样或后续新值会被延迟，长工具任务中尤其明显。

#### F4 轮末 3 秒窗口与下一轮 purge 会永久丢弃迟到推送

官方发送用量前需要两次异步读取，Zen 却只在 response 后最多等待 3 秒。超时后 worker 收尾；队列中的迟到通知最终会被下一轮 `purge_updates()` 清空。

`work plans/2026-1120-0946_ACP轮次中断止血与stopReason修复落地计划.md` 当时已明确把「轮末 3 秒窗口的迟到帧归属重做」暂缓。本计划只处理其中的用量通知，不重做全部轮次状态，也不把迟到的正文或工具帧归入下一轮。

### 2.3 wire 中已有更直接的上下文水位记录

Kimi 2.6.3 的 `token_counting.measured` 是 durable 事件，直接携带当前实测上下文 `tokens`。它与每次模型调用后的上下文测量对应，比 Zen 再从 `usage.record` 四项求和更贴近官方水位语义。

轮内读取应按文件顺序接受最新的有效 `token_counting.measured`，并保留 `usage.record` 四项求和作为旧版本/缺失事件兜底。Token 累计消耗与输出速度仍使用 `usage.record`，不得改用水位记录。

上游证据：[Kimi Code 2.6.3 token counting 事件定义](https://github.com/MoonshotAI/kimi-code/blob/b0de2fbd2de04d87689225aafd3912e5d193b62d/packages/agent-core-v2/src/agent/tokenCounting/tokenCountingOps.ts)。

### 2.4 tooltip 与“消失”现象的判断

- tooltip 的用量段以 `_usage is not None` 为前提。没有用量时只显示计时/速度段，所以“tooltip 信息不全”主要是同一数据缺口的表象；但当前没有一句明确的不可用说明，需补上。
- 当前面板没有按时间自动清空 `_usage` 的逻辑。空轮询会保留最后有效值；显式清空发生在切换后端并重置会话时。新建标签、关闭旧标签或重放历史也不会恢复原用量。
- 本次没有真实故障现场证明“同一标签、同一后端、已有有效百分比后被代码自动清空”。实施时须用持久性回归测试排除该路径，并记录真实清零点；不得为了迎合现象而虚构一个定时清除根因。

### 2.5 证据边界

已证实上述四类采集/时序缺陷均可独立造成缺失或延迟，但本次未读取用户真实私有会话，不能把其中某一个断言为所有现场的唯一根因。修复应同时消除这些确定缺陷，并用真实 2.6.3 长任务验收闭环。

现有相关测试基线为 **59 passed**，但它们没有覆盖负缓存重试、目录为空重试、大型工具输出、超过 3 秒的迟到推送和徽章持久性，因此全绿不能排除本故障。

## 4. 设计决策

### D1 保持“双源分工”，不把轮末推送误当轮内信号

- 轮内：wire 的真实计量，2 秒轮询。
- 轮末：官方 ACP `usage_update` 优先，wire 作为缺失兜底。
- 轮末 push 与 transcript 数值允许因官方估算尾部而略有差异，固定以 push 收尾，避免来回覆盖。
- 单次模型调用尚未完成时没有新真值，显示最近一次有效值或等待态，不插值。

### D2 只缓存成功，临时失败必须有界重试

会话目录：

- 成功定位后才缓存 `session ID → sessionDir`。
- `None` 不形成永久负缓存；后续 tick 可重试。
- 为避免失败时每个 2 秒 tick 都全量扫描索引，增加短退避，例如首次 2 秒、随后 5 秒、最长 15 秒；成功或 session 切换立即复位。

模型目录：

- 只有解析到非空窗口映射才置 loaded。
- 空目录在下一轮 worker 的会话准备阶段重试；GUI tick 不启动目录子进程。
- 非空但个别模型缺窗口仍按诚实无数据处理，不用静态值补猜。

### D3 wire 改为增量游标 + 最后有效采样，淘汰反复依赖固定尾部

为每个 session 维护独立的轮询状态：

- 文件偏移、未完成半行缓冲、最近模型别名、最后有效 `UsageStats`。
- 首次只读末尾 64KB 建立状态；后续只读新增字节，不在 GUI 每 2 秒全量读取 MB 级文件。
- 新记录按文件顺序更新状态；`token_counting.measured.tokens` 作为优先水位，旧 `usage.record` 四项求和继续兜底。
- 大型工具输出之后仍返回最后有效采样；新用量到达后再替换。
- 文件截断、缩小或 session 切换时重置偏移、半行和采样，防跨会话串值。
- 线程安全由 provider 内小锁保护；不得在持锁期间执行目录子进程或等待 ACP。

### D4 迟到 ACP 用量与活跃轮次隔离，并增加轮后短宽限

保留现有 response 后最多 3 秒的 worker 收尾窗口，不通过单纯延长 busy 时间掩盖问题。新增两层接收：

1. 轮结束后，Kimi 的用量轮询进入最长 10 秒的短宽限，与上游端到端测试的等待上限同量级；busy 已解除，不阻塞完成播报、停止或排队逻辑。
2. 宽限后仍未收到的用量，在下一次 `purge_updates()` 前再做一次回收，避免已被下一轮清掉。

`KimiAcpLLM.poll_usage()` 只有在非阻塞取得 `_turn_lock`、确认没有活跃 chat 后，才可排空空闲队列并提取最近一次有效 usage；取不到锁时只读 wire，绝不从 worker 嘴边抢正文、工具或响应帧。回收的上一轮 usage 只更新徽章，不进入当前正文、历史、活动卡或 Token 消耗账本。

宽限计时规则：

- 新轮发送时取消旧宽限并正常启动 2 秒轮询。
- 正常完成、失败和取消后可进入宽限；连接关闭、切换后端和标签销毁立即停掉。
- 宽限结束停止计时器，不让所有标签永久每 2 秒读盘。
- 其他后端不启用该宽限。

### D5 保留最后有效值，空态用 `—` 和原因说明而非假百分比

- 后续 `None`、字段残缺或空 usage chunk 不得清空已有百分比，沿用并测试现有簿记原则。
- 新会话尚未发送时维持原空白；发送后仍无任何真实用量时显示 `—`，不是 `0%`。
- tooltip 在有会话计时但无 usage 时增加明确行：轮内为「上下文用量：等待首轮模型计量」，空闲为「上下文用量：暂不可用（未收到有效 agent 数据）」。
- 一旦收到有效值，`—` 与说明被真实用量段替换；estimate 的 `~` 规则不变。

### D6 改动边界

- 公共 `map_usage_update()`、`UsageStats` 字段和其他 provider 的帧映射不改。
- 不用 wire 判定轮次完成/失败，不触碰近期修复的 `stopReason` 与取消分类。
- 不修改 Token 热力图累计口径；迟到上下文 push 不生成 `TurnConsumption`。
- 私有 wire 读取继续 fail-soft；失效时最多显示 `—` 和最后有效值，不能影响聊天主流程。

## 6. 风险与注意点

- **私有格式漂移**：`token_counting.measured` 与 usage.record 都不是 ACP 公共契约，解析失败必须静默降级，不能影响聊天。
- **队列竞争**：空闲回收必须非阻塞取得轮次锁；否则可能偷走新轮正文、工具帧或 response，造成比徽章更严重的回归。
- **跨轮污染**：迟到 usage 没有 turn ID，只能按「上轮收尾后、下轮 prompt 发出前」的队列边界回收，不得把轮中帧另起通道重排。
- **数值语义**：measured 是实测水位，ACP 可包含官方估算尾部；Token 热力图是逐次调用累计消耗，三者不得混算。
- **I/O 成本**：失败重试须有退避，增量游标必须避免每 2 秒全量读取；目录命令只能在 worker 路径执行。
- **UI 误导**：`—` 只表示没有有效数据，不能显示成 `0%`；最后有效值可能较旧，但比清空更符合当前会话语义，且轮末官方值会校正。
- **近期中断修复回归**：不得改变 response 分类、取消、看门狗、排队和恢复行为；相关测试必须纳入定向门禁。
- **现场未决项**：若真实验收仍出现同标签同后端百分比自动消失，应保留脱敏状态转移日志另案定位，不得在缺少证据时继续扩大本次改造。

## 7. 已确认决策

1. 接受官方 ACP 轮末单帧的现实；Zen 的轮内体验由 wire 补充，不要求上游改成流式 usage。
2. 同时修复负缓存、一次性模型目录、固定尾部窗口和迟到帧丢失，不把某个未证实的上游变化当唯一根因。
3. 轮内优先读 `token_counting.measured`，usage.record 保留兜底；轮末仍 ACP push 优先。
4. 保留 worker 的 3 秒收尾窗口，新增不阻塞 busy 的轮后短宽限及下轮 purge 前回收。
5. 无数据用 `—` 和说明，保留最后有效值；不伪造 0%、不按字符数估算 Kimi 水位。
6. 先补可失败回归，再改生产代码；最终必须完成真实多步任务与 AppImage 验收，不以现有 59 个测试全绿代替故障验收。
