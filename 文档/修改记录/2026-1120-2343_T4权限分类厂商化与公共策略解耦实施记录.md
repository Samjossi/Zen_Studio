## 2. 结构映射

| 旧实现 | 新归属 |
|:---|:---|
| `permission_policy._QUESTION_TOOL_NAMES` / `is_question_request` | Kimi `permissions.py`、Local `permissions.py` 各自持有；公共策略不再识别工具名 |
| `QuestionDialog._extract_questions` 的 `rawInput.questions` / `rawInput.question` / content 解析 | 各厂商 `permissions.py::_question_texts`，结果以中性 `questions` 放入 `PermissionRequest` |
| provider `set_permission_handler(params -> optionId)` | provider 对外收 `PermissionRequest -> optionId`；连接层仍收原始 `params -> optionId`，由 provider 适配方法桥接 |
| GUI 队列/对话框/提问桥直接读 `PermissionParams` | 统一读 `PermissionRequest`；原始荷载仍从 `request.params` 无损取得 |
| `permission_policy` → 具体 provider 取型 | `permission_policy` → 稳定 ACP 协议类型 |

## 4. 边界与偏差

- **`PermissionRequest` 增加中性 `questions`**：计划只要求「原始参数 + 中性分类」，但公共 `QuestionDialog` 与 `QuestionBridge` 的文本匹配必须拿到问题文本，又不能继续解析厂商 rawInput。把文本提取放在各厂商 `permissions.py`、以中性 `tuple[str, ...]` 传递，是「分类归厂商、宿主不解析」的最小闭环；卡片布局与答案渲染仍在各厂商卡片包。
- **DSH 恒为 permission 是行为边界而非遗漏**：旧公共策略会按 `rawInput.questions`/`AskUserQuestion` 把任何后端都识别为提问。DSH 没有提问回环实证，本项按要求不激活；若 DSH 未来真的发送提问帧，在补实证前会按普通审批处理（`auto_all` 下可能自动选答）。这是计划明确接受的取舍，待真实帧取证后只改 `dsh/permissions.py`。
- **Kimi provider 删除协议类型 re-export**：`PermissionOption`/`PermissionParams`/`ToolCallInfo` 的旧再导出已无消费方（`permission_policy` 改从稳定 ACP 包取型），顺手移除避免继续把 Kimi 当公共类型出口；不涉及行为。
- **提问框标题保留既有文案**：`PermissionDialog` 标题仍为「Kimi ACP 请求执行工具」，因为 T4 要求用户可见文案不变；该文案对 DSH/Local 并不准确，属已知残留，未在本项扩大为文案专项。
- **未提前做 T5**：`llm/__init__.py` 仍保留既有公共再导出，只在本次补了 `PermissionRequest`；公共出口收敛与 AST 守卫留给 T5。
