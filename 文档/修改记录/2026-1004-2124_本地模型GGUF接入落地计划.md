## 1. 需求背景

用户在本机 `~/models/qwen3.5-gguf/` 放置了两个 GGUF 本地模型：

| 文件 | 体积 |
|:---|:---|
| `Qwen3.5-35B-A3B-MXFP4_MOE.gguf` | 21 GB（MoE，MXFP4 量化） |
| `Qwen3.5-9B-UD-Q4_K_XL.gguf` | 5.6 GB（9B，Q4_K_XL 量化） |

需求：Zen Studio 的「厂商 → 接口 → 模型」选择菜单中新增一项**「本地模型」**，让用户直接选用上述 GGUF 模型对话。

**路线拍板（用户 2026-10-04 决定）**：不动 `参考代码/Dream_Cli/`（用户未来另有用途），**整目录复制为新子项目 `Local_Cli/`** 承载本地模型推理；IDE 侧不改 `dream-acp` 注册项，**新增 `local-acp` 接口**。通信路线沿用 ACP CLI 子进程（§3）。

## 3. 路线选型（已定）

**通信路线：包装成 ACP CLI 子进程**，理由（对比表略，要点）：IDE 侧五家后端全是 ACP 传输层，走 ACP 则工具审批、终端桥、流式、取消、崩溃恢复全部现成，GUI 零改动；直连 HTTP 需新写异构 provider 且放弃整套工具生态。协议面与 Dream 完全同源（dream-acp-v1.md），无需新协议。

**工程路线：复制而非改造 Dream_Cli**（用户拍板）：

1. Dream_Cli 作为独立产品线保持原样，不受本地模型实验拖累；
2. IDE 注册表「追加一项」是既定扩展方式，`dream-acp` 与用户既有配置零影响；
3. 风险隔离——Local_Cli 改坏不影响任何既有功能。

## 4. 方案设计

**D1（新子项目 `Local_Cli/`）**：项目根新建 `Local_Cli/`（与 `dream-acp/` 平级，不放进 `参考代码/`——它是现役组件而非参考材料）。整目录复制 `参考代码/Dream_Cli/` 后机械改名：

- 包 `dream_cli/` → `local_cli/`；`AGENT_NAME` `"dream"` → `"local"`；入口 `local-cli acp` / `local-cli gui` / 新增 `local-cli models`（§D3）。实施期修正：二进制名定 **`local-cli`** 而非 `local`——`local` 是 bash/POSIX shell 内建保留字，终端直敲 `local models` 会被 shell 拦下（只能在函数中使用）。
- 用户态路径：`$DREAM_HOME` → `$LOCAL_HOME`，`~/.dream/` → `~/.local-cli/`。
- 自带协议文档拷贝（dream-acp-v1.md 改名 local 语境留存），保持自包含、搬走即完整的原设计。
- 独立 `.venv`（沿用 uv 工程），与 Zen Studio 的 `.venv` 互不依赖。
- 复制后第一件事：跑 `spike_handshake.py`（25 过）+ `verify_extras.py`（10 过）确认改名无损，作为后续改造的回归基线。

**D2（Local_Cli · 推理层）**：`local_cli/model/` 新增 GGUF 实现（与 Mock 并存、配置切换），`__main__.py` 接线处按配置选模型实现。推理运行时：

- **首选：包装 `llama-server` 子进程**（Local_Cli 作 orchestrator：按选定模型拉起 `llama-server --model <gguf> --port <随机空闲端口>`，走 localhost OpenAI 兼容 API 取 SSE 流式，逐块转协议帧）。理由：llama.cpp 二进制独立升级，MXFP4 等新量化跟随上游；连续批处理与内存管理成熟；Python 侧零重型依赖（HTTP 客户端用标准库即可）。
- 备选：`llama-cpp-python` 库内嵌——wheel 版本常滞后上游，MXFP4 MoE 支持可能缺位，仅首选路线遇硬障碍时启用。

**D3（Local_Cli · `local-cli models` 子命令）**：扫描配置的模型目录输出 `*.gguf` 别名清单（纯文本行，与 `opencode models` / `kilo models` 同构范式）；目录缺失/为空时优雅报错退出码非零（IDE 侧据此兜底空列表）。

**D4（IDE 侧 · 新增 `local-acp` 接口）**：

- 新建 `src/llm/providers/local_acp.py`：照 `dream_acp.py` 逐行同构复制改写——`_find_bin()` 探测链 PATH → `$LOCAL_HOME/bin/local-cli` → `~/.local-cli/bin/local-cli`；`local_available()`；`list_local_models()` 调 `local-cli models`（异常兜底空列表，R2 纪律）；`LocalAcpLLM` 类复用 `AcpConnection` 全链路。类内差异逐条写进 docstring（沿用 dream_acp.py 的可核对惯例）。
- `src/llm/registry.py` REGISTRY **追加**一项（dream-acp 原样保留）：`name="local-acp"`、`label="Local ACP"`、`vendor="local"`、`vendor_label="本地模型"`、`available=local_available`、`list_models=_cached_list_models("local-acp", list_local_models)`、`factory=LocalAcpLLM`、`supports_images=False`（GGUF 文本模型）、`efforts=("auto",)`。注册即全链路生效，ModelBar 一级菜单出现「本地模型」，设置中心同步，GUI 零改动。
- 红线不破：模型别名不透明字符串，禁解析禁跨后台共享；`available`/`list_models`/`factory` 全惰性。

**D5（模型目录配置）**：GGUF 目录属用户数据，配置归 Local_Cli 自管（与各 CLI 凭证自管的零密钥红线同理）：`~/.local-cli/config.toml` 的 `model_dir` 键，默认 `~/models`。`~/models/qwen3.5-gguf` 由用户写入配置（或软链），代码库不出现该绝对路径。

**D6（阶段划分）**：

1. **T0 spike（前置验证，先行）**：安装/编译 llama.cpp → `llama-server` 直接加载两个 GGUF 冒烟。只验证三件事：MXFP4 MoE 能否加载、内存是否够（预估 ≥24 GB 可用）、流式是否正常。**T0 不过则计划暂停，回报硬件/格式结论。**
2. **阶段一**：D1 复制改名 + 回归基线。
3. **阶段二**：D2 + D3（Local_Cli 推理层与枚举命令）。
4. **阶段三**：D4（IDE 侧 provider + 注册）+ 测试。
5. **阶段四**：文档同步 + 门禁全绿。

## 6. 风险与开放项

- ⚠️ **内存**：21 GB MXFP4 MoE 加载后 + KV cache 预估需 ≥24 GB 可用内存；9B 版（约 7 GB）为兜底——T0 实测不足时菜单默认项指向 9B。
- ⚠️ **MXFP4 兼容性**：依赖 llama.cpp 版本；T0 不过则降级为「仅 9B Q4_K_XL」或提示用户换量化。
- ⚠️ **llama.cpp 安装**：编译安装属系统级操作，列为用户配合项（或经用户授权后代为编译，产物不放项目目录）。
- ⚠️ **首载耗时**：21 GB 模型冷启动可能数十秒——Local_Cli 侧需经 `session/update` 或状态帧向 IDE 反馈「模型加载中」，避免误判卡死（协议面若需扩展，按协议「变更纪律」升版本）。
- ⚠️ **双项目维护**：Local_Cli 复制后与 Dream_Cli 分道扬镳，协议内核的后续修复如需互通要人工同步——接受此代价（用户已拍板独立演进）。
- 开放项：GPU offload 参数、上下文窗口大小（`--ctx-size`）是否暴露给设置中心——本期不做，留后续计划。

**T0 实测留痕（2026-10-04 22:00 前后）**：llama.cpp 源码编译（`~/opt/llama.cpp`，v0.5.0-dev，CPU 构建，源码确认含 MXFP4 支持）。9B Q4_K_XL：加载约 3 秒（页缓存热），SSE 流式正常，含独立 `reasoning_content` 思维链通道（对接 ACP `agent_thought_chunk` 用），RSS 7.7 GB。35B-A3B MXFP4 MoE：加载约 10 秒，流式正常，128 token 约 9.9 秒（≈13 tok/s，纯 CPU 8 线程），RSS 30.8 GB（ctx 4096），46 GB 内存机型可用但余量有限——大 ctx 需留意。两模型冒烟均通过，§6 的内存与 MXFP4 兼容性两条风险解除。
