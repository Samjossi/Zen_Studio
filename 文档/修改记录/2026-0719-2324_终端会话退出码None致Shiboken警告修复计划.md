# 终端会话退出码 None 致 Shiboken 警告修复计划

## 1. 现象

关闭一个终端 tab 时，运行 `uv run main.py` 的控制台打印若干条：

```
_pythonToCppCopy: Cannot copy-convert 0xa408a0 (NoneType) to C++.
```

每关闭/终止一个会话产生 1 条（用户观察到 8 条 = 累计 8 次会话终止操作）。属警告而非异常，不导致崩溃，但属不应出现的噪音，且背后伴随一个真实功能缺陷（见 §5）。

## 2. 调查过程与证据

| 步骤 | 方法 | 结论 |
|---|---|---|
| 复现 | offscreen 平台启动 MainWindow，分别测试「关闭一个 tab」与「关闭主窗口」 | 仅**关闭 tab** 触发，警告地址 `0xa408a0` 与用户所见一致；关主窗口不触发 |
| 二分定位 | 手动逐步复刻 `_close_tab`（pop → disconnect → terminate → removeTab → _switch_tab），逐步泵事件循环 | 警告出现在 **`entry.session.terminate()` 期间**，与其余步骤无关 |
| 机制验证 | `Signal(int).emit(None)` 直接发射 | 产生**逐字相同**的警告（地址同为 `0xa408a0`），确认警告 = 向 int 型信号发射了 None |
| 插桩 | 替换 `_read_loop` 为带打印版本 | `finally` 中 `proc.wait()` 实际返回 **`None`**（`code=None type=NoneType`），随后 `emit(None)` 触发警告 |
| 源码证据 | ptyprocess 0.7.0 `PtyProcess.wait()` | 见 §3 |

调试脚本留存于 `.temp/`（复验用）：`repro_warning.py`（复现）、`bisect_warning.py`（二分）、`verify_emit_none.py`（机制+插桩）、`verify_fix.py`（修复验证）。

## 3. 根因

`ptyprocess 0.7.0` 的 `PtyProcess.wait()` 中，子进程**被信号杀死**时退出码显式置为 `None`：

```python
elif os.WIFSIGNALED(status):
    self.exitstatus = None                     # ← None 的来源
    self.signalstatus = os.WTERMSIG(status)
return self.exitstatus
```

完整因果链：

```
_close_tab / _kill_active
  → PtySession.terminate()          # GUI 线程：SIGHUP → SIGKILL 阶梯杀 bash
  → bash 属「被信号杀死」（WIFSIGNALED）
  → reader 线程从 proc.read() 醒来，进入 finally
  → code = proc.wait()              # 返回 None（ptyprocess 上述行为）
  → process_exited.emit(None)       # 信号声明为 Signal(int)
  → Shiboken 无法把 NoneType 转为 C++ int
  → stderr: _pythonToCppCopy: Cannot copy-convert 0xa408a0 (NoneType) to C++.
```

`0xa408a0` 是 Python `None` 单例的地址，故所有警告地址恒相同。

## 4. 触发路径矩阵

| 操作 | 是否触发 | 原因 |
|---|---|---|
| 关闭 tab（`_close_tab`） | **触发** | terminate → 信号杀死 → wait() 返回 None → emit(None) |
| 右键菜单「终止」（`_kill_active`） | **触发** | 同上 |
| 终端内正常 `exit` | 不触发 | `WIFEXITED` 正常退出，wait() 返回 int 退出码 |
| 右键菜单「重开」（`_restart_active`） | 不触发 | `start()` 先递增 `_generation`，旧 reader 的 emit 被代次守卫拦截 |
| 关闭主窗口 | 不触发 | `aboutToQuit` → `_closing=True`，`_may_emit()` 拦截 |

## 5. 附带发现的真实缺陷

`_kill_active`（终止但保留 tab）场景下信号连接未断开，`emit(None)` 转换失败导致 `_on_exited` **收不到退出事件**，`exit_code` 停留在 `None`，状态栏不显示「[进程已退出 code N]」。即该警告不仅是噪音，还意味着**终止会话后状态栏退出状态不更新**。修复后此缺陷一并消除（验证收到退出码 129）。

## 6. 修复方案

### 6.1 主方案（必选）：`_read_loop` finally 中 None 兜底

文件：`gui/panels/terminal/session.py`，`_read_loop` 的 finally 块：

```python
finally:
    code = -1
    try:
        if not proc.isalive():
            code = proc.wait()
    except Exception:  # noqa: BLE001 — 退出码不可得时按 -1
        code = getattr(proc, "exitstatus", -1) or -1
    if code is None:
        # ptyprocess：被信号杀死时 wait() 返回 None（exitstatus=None）；
        # 按 shell 惯例以 128+signo 回报（SIGHUP=129 / SIGINT=130 / SIGKILL=137）
        sig = getattr(proc, "signalstatus", None)
        code = 128 + sig if isinstance(sig, int) else -1
    if generation == self._generation and self._may_emit():
        self.process_exited.emit(code)
```

要点：
- 保证 `emit` 的参数恒为 `int`，根治警告；
- 被信号杀死时按 shell 惯例回报 `128+signo`，状态栏可显示有信息量的退出码（如 `[进程已退出 code 129]`）而非 `-1`；
- 不能用 `proc.wait() or -1` 的写法：正常退出码 `0` 会被误判为 -1。

### 6.2 可选优化（建议一并做）：except 分支的 `or -1` 陷阱

现有 `getattr(proc, "exitstatus", -1) or -1` 在 `exitstatus == 0`（正常退出）时会把 `0` 错报为 `-1`。改为显式 None 判断：

```python
    except Exception:  # noqa: BLE001 — 退出码不可得时按 -1
        rc = getattr(proc, "exitstatus", None)
        code = rc if rc is not None else -1
```

### 6.3 明确不做的

- 不改 ptyprocess（第三方库，且其 `exitstatus=None / signalstatus=信号号` 的语义本身合理）；
- 不把信号改为 `Signal(object)`（会丢失类型约束，掩盖而非解决问题）。
