## 1. 背景与目标

本项把具体卡片格式、工具名分派、迟到帧和更新逻辑按厂商隔离。公共 GUI 只保留无厂商语义的 Qt 技术基础件、卡片生命周期和事件转发；通用面板不得继续认识 `command`、`summary`、`diff_hunks`、`questions` 等厂商载荷字段。

迁移初期允许复制现有具体卡片以保证等价，之后由各厂商独立演化。禁止保留公共 `BashCard`、`DiffCard`、`QuestionCard` 等具体实现，也禁止以统一 `card_kind` 或中性类型表变相恢复公共卡片体系。

## 2. 启动条件与边界

- 主计划 T2 已勾选，且用户明确批准 T3 后才能开始；本项批准不包含 T4。
- 必须使用 T0 的「通用生命周期保留 / 移入厂商 presenter」清单和帧到卡片基线。
- 不改变卡片观感、持久化键、默认后台、模型别名或用户配置。
- 厂商 GUI 包只 import 本厂商 models 的纯数据类型，不得 import provider 运行时、连接对象或其他厂商卡片。
- 权限中性分类属于 T4；本项只保证现有提问卡内容与交互不因卡片迁移改变。

## 3. 实施步骤

### T3.1 建立 UI 基础件与卡片组合根

1. 建立 `src/ide/gui/panels/chat/card_base.py`，等价承接 `ToolCard` 生命周期、折叠/展开、复制、颜色、基础 body、图片显示等稳定技术能力。
2. 建立 `src/ide/gui/panels/chat/vendors/registry.py`，按后台 registry 的 `vendor` 选择本厂商卡片工厂。
3. 后台组合根不 import GUI；通用面板只接触卡片组合根，不 import 具体厂商卡片包。

### T3.2 等价复制三家具体卡片与工厂

1. 为 Kimi、DSH、Local 分别建立 `factory.py`、`cards.py`、`presenter.py`。

## 6. 实施结果回写（2026-11-20 23:32 UTC+8）

T3 全部完成。

### 6.1 与计划的偏差

1. **卡片字段落屏仍在厂商 cards，presenter 承接跨帧路由**：`presenter.py` 持有标题/命令账本、迟到帧闸门、旧轨输出裁剪、todo entries 与改盘终态判断；每张卡的 `apply_update` 仍由本厂商卡片类解释自身 payload 并驱动 `card_base.ToolCard` 的通用生命周期。T3.3.1 字面上的「卡片更新分支移入 presenter」按此口径落地：通用面板不再有更新分支，字段覆盖不再需要 presenter 暴露整套 mutator。
2. **旧轨保留为通用文本渲染器**：面板只转发不透明载荷；各厂商 presenter 在交给 `ChatOutput` 前完成标题回填、命令头与 20 行裁剪。`output.py` 的 `command`/`output`/`summary` 渲染是冻结回退通道的既有格式，不是新的厂商分支。
3. **工具名表按行为基线而非「纯厂商私有」收缩**：Kimi 保留历史 `ask`/`todowrite`；Local 保留旧共享表中 Local 可能收到的通用问题/媒体/清单名，但明确不收 DSH 的 `read_image`/`todo_write`；DSH 只承接计划点名的 `read_image`/`todo_write`/`subagent`。三张表各自持有、不互相 import；Local 的保留是为了不改变旧共享表下可能出现的 Local 提问/清单卡行为。
4. **纯技术件共享到 card_base**：MCP 出参 HTML、图片略缩图、JSON pretty、图片宽/大小护栏收进 `card_base.py`，未复制进三家 cards；todo 条目绘制与问答出参解析仍留在各厂商 cards，因为它们是卡片格式而非 Qt 基础件。
5. **`card_base.ToolCard` 只读生命周期元数据**：仅 `tool_call_id`/`tool_kind`/`title`；`summary` 由厂商子类作为 subtitle 传入，`error_detail`/`error` 默认错误块下沉到厂商 `ToolCard._on_failed`，base 不读错误字段。
6. **额外收敛看门狗旁路**：T3.4 只要求轮后用量宽限，但 T0 清单也列了 `_llm_name == "kimi-acp"` 的看门狗旁路；本项一并改为 `stall_watchdog_enabled()` 可选能力，面板不再保留后台 ID 分支。
7. **QuestionBridge 增加 vendor 参数**：提问卡注册表按厂商隔离后，面板把当前 `_chat_vendor` 传入桥；旧调用方缺省 `local`，不破坏无 GUI 夹具。
8. **会话持久化审计**：`session_store.py` 只保存 user/assistant 正文与图片附件引用，工具卡/todo/思维链/用量不入存档，`replay_session` 只重放文字；因此无需厂商旧工具载荷兼容分支，也未恢复公共兼容工厂。

### 6.3 经验沉淀

1. **先拆「无厂商语义外壳」再复制具体卡**：`card_base.ToolCard` 只保留生命周期，厂商 cards 解释自己的 payload；这样三家卡片可以有意重复而不把公共层变成厂商字段汇集点。
2. **presenter 的账本必须跟面板/轮次同寿命**：标题/命令/节流账本从 panel 实例字段迁到 presenter 实例，并在 `_send_turn` 调 `reset()`；实例化本身不等于隔离，切后台时必须换新 presenter。
3. **旧/新卡快照对比比只看测试更可靠**：用同一批 mock 帧分别跑旧公共卡与新厂商卡，比较用户可见文本、状态、body 计数与嵌套子卡，32+3 个场景 0 差异，能抓住测试未覆盖的空白/顺序回归。
4. **工具名表迁移要先保行为再谈纯洁**：Local 若直接清空旧共享表会丢掉旧行为；保留 Local 可能收到的通用名、同时明确拒绝 DSH 私有名，是行为等价与厂商隔离的折中。
5. **提问卡是「按厂商注册表 + 组合根分发」而非全局单例**：`QuestionBridge` 必须知道请求所属 vendor，否则同名 toolCallId 或跨后台切换会定位错卡；vendor 参数是比全局查表更稳的契约。
6. **纯技术件下沉能显著减少重复**：图片 HTML/略缩图/JSON pretty 下沉后，三家 cards 只保留格式与字段解释；todo 条目与问答解析则因属卡片格式而有意保留在厂商侧。
