## 1. 背景与目标

本项是厂商隔离重构的前置基线，不是目录迁移。目标是在任何生产代码移动前，用现有存档、内存假 ACP 连接和卡片测试固定三家当前行为，并列清后续迁移必须修改的消费方，避免把移动错误、语义变化和既有失败混在一起。

完成后应能回答：迁移前每家有哪些可观察行为、旧公共入口被谁引用、`src/ide/gui/panels/chat/panel.py` 中哪些职责应保留、哪些必须进入厂商 presenter。

## 2. 启动条件与边界

- 只有用户明确批准 T0 后才能开始；本子计划的批准不包含 T1。
- 若 `bash scripts/check.sh` 基线失败，先区分既有失败与本项新增失败并如实记录，不通过重构或删除测试制造绿色基线。
- 测试套件不启动真实 CLI，不读取或改写 CLI 凭据；临时产物只放 `.temp/`。
- 不顺手修复与基线无关的既有缺陷，不实施 DSH edit 合成 diff、提问回环激活等新能力。

## 3. 现状锚点

- 公共映射入口集中在 `src/ide/llm/providers/acp.py`，模块级账本被多家共享。
- 公共工具载荷位于 `src/ide/llm/base.py`，具体卡片与工具名分派位于 `src/ide/gui/panels/chat/cards.py`。
- `src/ide/gui/panels/chat/panel.py` 同时承担通用卡片生命周期和若干厂商载荷、后台 ID 判断。
- 迁移影响生产模块、测试以及 `scripts/capture_tool_frames.py`、`scripts/spike_dsh_acp.py`、`scripts/shot_tool_cards.py`、`scripts/probe_subagent_frames.py`、`scripts/capture_askuser_2q_frames.py` 等脚本。

## 8. 实施结果回写（2026-11-20 22:54 UTC+8）

T0 全部完成。

**与计划的偏差**：

1. 主计划写「至少覆盖 14 个测试文件」，实际全库只有 2 个测试文件消费旧入口（旧架构测试已在 `ef6cf28` 清理）；以实际搜索为准，未虚构迁移项。
2. 基线测试新增 15 个用例，而不是只补少量断言：为了让 Kimi/DSH/Local 三家都具备「帧 → 载荷 → 卡片」贯通覆盖，按厂商拆成独立用例，避免一个巨型用例失败时无法定位是哪个厂商。
3. Kimi 轮内收到 `usage_update` 后，轮末仍会再产出一个同值 usage Chunk（既有行为）。基线只断言“正文一次、所有 usage 值一致”，不锁定重复次数，防止后续 mapper 实例化时把无用户可见差异的重复收尾误判为回归。
4. `tests/test_vendor_behavior_baseline.py` 直接调用 `kimi_acp._synthesize_wire_call` / `_synthesize_wire_result` 固化 wire 旁路格式；这是当前唯一能贯通验证「sidecar → 父指针 → 子卡嵌套」的入口，T3 拆分后应改为通过厂商 presenter 的公开测试入口，届时同步迁移该用例。

**验证结果**：

- 迁移前基线：`UV_CACHE_DIR=$PWD/.temp/uv-cache bash scripts/check.sh` → **24 passed**，隐私扫描、ruff、可选中 QLabel 裸用守卫全绿（日志 `.temp/t0_baseline_check.log`）。
- 环境说明：直接运行 `bash scripts/check.sh` 时 uv 试图写 `~/.cache/uv`，在沙箱下报 `Could not acquire lock / Read-only file system`；这是运行环境失败而非测试失败，改用项目内 `UV_CACHE_DIR=$PWD/.temp/uv-cache` 后通过，未放宽沙箱或修改门禁脚本。
- T0 新增后：同命令 → **39 passed**（24 + 15），全绿（日志 `.temp/t0_after_baseline_check.log`）。
- 定向：`QT_QPA_PLATFORM=offscreen .venv/bin/python -m pytest tests/test_vendor_behavior_baseline.py -q` → **15 passed**。
- 未启动真实 CLI；未读写 CLI 凭据；临时日志只落在 `.temp/`。

**经验沉淀**：

1. 基线要锁「用户可见语义 + 稳定载荷键」，不要锁私有辅助函数与重复帧次数；否则后续拆分会被迫保留无意义 shim 或改测试掩盖差异。
2. 三家的差异不在「有没有卡片」，而在「首帧空壳、迟到字段、kind 兜底、入参命名」；基线必须覆盖首帧 + 迟到 update 两段，只测首帧会漏掉 Kimi/DSH 的主要真实形态。
3. `map_session_update` 的模块级账本会跨用例串联；基线用独立 `toolCallId` 隔离，不 import 私有账本手工清理，避免 T2 改为实例状态后测试结构失效。
4. 面板职责清单按「读取点 → 归属」记录，比按文件罗列更能直接指导 T3 presenter 拆分；T1 只做路径迁移，不提前改这些读取点。
