# 多实例多标签架构改造计划

## 1. 背景与目标

### 1.1 起因：AI 读错目录的 bug

诊断结论（2026-07-22）：切换工作区后 AI 仍读旧目录。根因是两个后端的工作目录被硬编码为 `PROJECT_ROOT`，且 `_switch_workspace` 只联动文件树/聊天@路径/终端/Git 四处，**未联动 LLM 层**：

- `llm/providers/kimi_cli.py` `_spawn`：`subprocess.Popen(..., cwd=PROJECT_ROOT)`
- `llm/providers/kimi_acp.py` `_AcpConnection.__init__`：`cwd=PROJECT_ROOT`；`_ensure_session`：`session/new` 传 `{"cwd": str(PROJECT_ROOT)}`

### 1.2 目标（用户拍板方向）

1. **多标签 AI**：同一项目文件夹内可同时开多个 AI 标签页，并行修改/查看文件。**标签数上限 = 4**（用户决策 D1）。
2. **工作区切换改多开**：不再在同一窗口内切文件夹，而是**多开进程**——一进程绑定一工作区。**不设单例程序锁**（用户决策 D3）。多 agent 改同一文件的冲突**由用户人工协调**（用户决策 D2：一改一查，不冲突）。

### 1.3 架构总览（两层模型）

```
进程（窗口）= 一个工作区根          ← 命令行参数绑定，根治 cwd bug、删切换联动
  └─ 标签页 = 一个 AI 会话（独立后端实例） ← 上限 4，并行 agent
```

进程边界天然隔离工作区状态（文件树/Git/终端/agent cwd），标签边界天然隔离会话上下文。这与 VS Code「多窗口 + 多终端/会话」模型一致。

### 4.4 D5 定稿：标签页模型选择 = 全局共享

- **决策**：所有标签共用一个模型选择（用户拍板，2026-07-22）。
- **实现含义**：
  - `ModelBar` 上移到 `ChatTabs` 容器顶部，为**全局控件**，不再属于单个 `ChatPanel`。
  - 切换模型时 `ChatTabs` 将选择**广播到全部标签**的 provider 实例（`set_model`）。
  - 设置菜单「AI 模型」联动对象从单一 `ChatPanel` 改为 `ChatTabs`（写活动标签 provider + 广播全部标签）。
  - 任务 11（ChatTabs）负责托管 ModelBar；任务 12（ChatPanel）移除自身 ModelBar。
  - 与 §4.3 任务 15 配合：全局模型下，任一标签响应中即整体禁用 ModelBar，防止切换中途打断正在响应的标签。

### 4.5 D6 定稿：ACP 多标签连接模型 = 每标签独立连接（方案 A）

- **决策**：每标签独立连接（用户拍板，2026-07-22）。

**背景**：`KimiAcpLLM` 现状为"一实例 = 一条长驻 `_AcpConnection`（`kimi acp` 子进程）= 一个 sessionId"。`_AcpConnection` 的消息路由建立在"同一时刻仅一个活跃轮次"的假设上（见 `llm/providers/kimi_acp.py` 类 docstring）：`_turn_id` 单值配对 prompt 响应、`_updates` 单队列消费轮次内通知、`_turn_lock` 串行化轮次。`session/update` 通知虽带 `sessionId`，但当前实现**不做区分**，全部进同一队列。

| 维度 | A. 每标签独立连接（✅ 已采纳） | B. 单连接多 session（❌ 已否决） |
|:---|:---|:---|
| 结构 | 每标签一个 `KimiAcpLLM` 实例 → 各自 `kimi acp` 子进程 → 各自 session | 一条 `_AcpConnection` 上多次 `session/new`，每标签一个 sessionId |
| 并行性 | 天然并行（各实例 `_turn_lock` 互不干扰） | 受单连接路由限制；agent 侧并发 prompt 行为未实测 |
| 故障域 | 单连接崩溃仅影响一个标签 | 进程崩溃则全部标签阵亡 |
| 进程/内存 | 4 标签 = 最多 4 个 `kimi acp` 进程 | 恒定 1 个进程 |
| 改动量 | **零协议层改动**：P1 已让实例接收 workspace_root，P3 任务 12 直接每标签自建实例 | **协议层重写**：`_updates` 需按 sessionId 分队列、`_turn_id`/`begin_turn`/`end_turn` 改 per-session、`session/update` 按 params.sessionId 路由到对应标签 |
| 审批路由 | 无歧义（一条连接只服务一个标签，请求天然归属该标签） | 需按 `session/request_permission` 的 params.sessionId 反查归属标签 |
| 模型设置（配合 D5 全局共享） | `ChatTabs` 广播 `set_model` 到各实例 | 需对每个 sessionId 逐个 `session/set_config_option` |

- **采纳 A 的理由**：P3 任务 12（ChatPanel 自持 provider 实例）已按 A 设计，零返工；`_AcpConnection` 的单轮次假设深埋在分发逻辑里（`_dispatch_line` 的 `_turn_id` 匹配、`session/update` 全进同一队列），改 B 等于重写协议层路由，且并行正确性依赖 kimi acp 未实测的行为，风险/收益不划算。省下的 3 个进程内存（每进程数十 MB 级）不构成动机。
- **未来重评 B 的触发条件**：若实测 4 进程内存/启动开销不可接受，或需要跨标签共享 agent 侧上下文，再单独立项重写路由层。
