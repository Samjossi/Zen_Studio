# CLI 后台抽象层与 Reasonix 接入计划

## 1. 目标

1. **注册表层**：把"后端发现 / 可用性探测 / 模型枚举 / 实例工厂"从散落的硬编码
   （`llm/__init__.py` 常量 + `ChatPanel._build_providers`）收敛为单一注册表，
   后续新增 CLI 后台只动 `llm/providers/` 一处。
2. **UI 三级选择**：ModelBar 在现有下拉前新增「后台」，三级链定为
   `后台（CLI 产品）→ 接口（接入实现）→ 模型（模型别名）`；
   现有「模型」按钮改名「接口」，现有「版本」按钮改名「模型」。
3. **接入 Reasonix**：新增 `reasonix-acp` 后端（ACP v1 长驻子进程），与现有
   `kimi-cli` / `kimi-acp` 并存，用户可在底行下拉自由切换。
4. **零回归**：默认选择不变（`kimi-cli` 系），存量 settings 无感知；kimi 两后端
   行为逐行等价。

## 3. Reasonix 调研结论（已核实官方文档 main-v2/docs）

| 调研项 | 结论 |
|:---|:---|
| 二进制 | `reasonix`（npm i -g reasonix / 预编译包）；1.0 起 Go 单二进制重写 |
| **ACP 支持** | ✅ `reasonix acp`：stdio 上 NDJSON JSON-RPC 2.0，ACP v1（`protocolVersion: 1`）——**与 `KimiAcpLLM` 现有协议层同构** |
| 会话生命周期 | `initialize` → `session/new(cwd, mcpServers)` → `session/prompt` / `session/cancel`（通知）→ `session/close`；另支持 `session/load`/`resume`/`list`（二期可用） |
| 流式更新 | `session/update` 通知：`agent_message_chunk` / `agent_thought_chunk` / `tool_call` 等（ACP 标准，现有 `_map_update` 可直接消费） |
| 模型切换 | `session/set_config_option`，`configId="model"`；另有 `effort` / `work_mode` / `tool_approval` 控制轴（二期可暴露） |
| 审批 | `session/request_permission` 反向请求（同 kimi-acp，现有审批回环可复用） |
| 模型列表来源 | 全局配置 `~/.reasonix/config.toml`（`REASONIX_HOME` 可覆盖）：`default_model` + `[[providers]]` 段 `name`/`models`/`default`；**无 CLI 枚举命令**，需自行解析 TOML |
| 未配置态 | 未 setup 时 `initialize` 响应声明 terminal 型 auth method → 检测后提示用户先跑 `reasonix setup` |
| 一次性模式 | `reasonix -p "..." --output-format stream-json`（eventwire 格式，与 kimi 不同构）——**本期不做**，备案二期 |
| 厂商扩展 | `_reasonix.io/session/steer`（回合中引导）等 `_meta` 扩展——忽略即可兼容，不消费 |

## 4. 方案选型与关键决策

### D1：三级下拉语义（**已定稿**：后台 → 接口 → 模型）

| 层级 | 按钮文案 | 语义 | 取值示例 |
|:--|:--|:---|:---|
| 一级 | 后台 | CLI 产品（厂商） | Kimi / Reasonix |
| 二级 | 接口 | 该后台下的接入实现 | Kimi CLI（一次性 spawn）/ Kimi ACP（长驻）/ Reasonix ACP |
| 三级 | 模型 | 模型别名 | kimi-code/k3-256k / deepseek/deepseek-v4-flash … |

> 按钮改名：原「模型」→「接口」（承载接入实现层），原「版本」→「模型」
> （承载模型别名层）。按钮恒显标签、当前值归 tooltip 的范式不变。

### D2：持久化不新增键、不改名

`model_backend` 仍存**接口实现名**（`kimi-cli` / `kimi-acp` / `reasonix-acp`），后台
由注册表 `BackendSpec.vendor` 推导；`model_version` 仍存**模型别名**。两键键名与
语义不变（仅 UI 层级文案重命名），存量 settings 值天然有效；跨后台切换时
`model_version` 按现有"无效项静默回退首项"语义处理。

### D3：注册表形态

```python
# llm/registry.py（新增）
@dataclass(frozen=True)
class BackendSpec:
    name: str                    # 接口实现名（持久化值）："kimi-cli"
    label: str                   # 显示名："Kimi CLI"
    vendor: str                  # 后台名："kimi"
    vendor_label: str            # 后台显示名："Kimi"
    available: Callable[[], bool]
    list_models: Callable[[], list[str]]
    factory: Callable[..., LanguageModel]   # (model, workspace_root) → 实例
```

- `REGISTRY: dict[str, BackendSpec]` 模块级单点；`BACKEND_LABELS` 等旧常量改为
  由 REGISTRY 派生并在 `llm/__init__.py` re-export（外部 import 不破）。
- import 无副作用（AFCP 2.3）：`available()`/`list_models()`/`factory()` 均为
  惰性可调用，探测不发生在模块级。

### D4：provider 懒实例化

`_build_providers` 不再预建全部实例，改为 `dict[name, factory]`，首轮 `chat`
前按当前选中接口实现名实例化；切换接口时旧实例 `close()`（acp 系）后丢弃。
**动机**：4 标签 × N 个 ACP 长驻进程的资源膨胀；同时顺带精简 panel 的
`isinstance(provider, (KimiCliLLM, KimiAcpLLM))` 硬编码判断。

### D5：ACP 连接层泛化边界

抽 `llm/providers/acp.py`：`_AcpConnection` → `AcpConnection`，参数化
`agent_name`（错误文案）与 `client_info`（initialize 载荷）；kimi 专有的
`-32000 authRequired → "请 kimi login"` 文案映射**不搬**，改由各 provider 的
`_ensure_session` 钩子自行翻译。kimi_acp.py 行为逐行等价（回归冒烟兜底）。

### D6：模型范围按接口级隔离（**硬性约束，防漏读**）

不同 CLI 支持的模型范围**天然不同**——这是产品级约束而非配置巧合
（例：Reasonix 是 DeepSeek-native，直连 `api.deepseek.com`，只支持 DeepSeek
系模型；Kimi CLI 只支持 Kimi 账号下配置的模型）。以下 5 条为实现红线，
代码评审逐条核对：

| # | 红线 | 反例（禁止出现） |
|:--|:---|:---|
| 1 | **模型目录挂在接口级**：每个 `BackendSpec.list_models()` 各调各的（kimi → `kimi provider list --json`；reasonix → 解析自身 `config.toml`），**全库禁止出现跨后台共享的模型表/模型常量** | 全局 `MODEL_LIST`、在 UI 层写死 `["deepseek-v4-flash", ...]` 给所有后台用 |
| 2 | **模型别名格式是各后台私有语义**：kimi 长 `kimi-code/k3-256k`，reasonix 长 `deepseek/deepseek-v4-flash`（`provider/model` 全名）。注册表与 UI 只把别名当**不透明字符串**透传，不解析、不拼接、不校验格式 | 在公共代码里按 `/` 切分别名推断 provider；对别名做统一的合法性校验 |
| 3 | **`set_model` 生效机制各实现自持**：kimi-cli 是 `-m` 参数、kimi-acp/reasonix-acp 是 `session/set_config_option`（configId=`model`）。抽象层不统一生效路径，只承诺"字符串原样交给对应 CLI" | 在 registry 或 panel 层替 provider 拼 `set_config_option` 载荷 |
| 4 | **切后台/接口时模型菜单必须先清后建**：旧后台的别名立即失效，静默回退新列表首项；**不得在新后台下保留/复用旧别名** | 切换后模型菜单仍残留上一个后台的勾选项；把旧 `model_version` 直接塞进新 provider |
| 5 | **持久化的 `model_version` 只在本后台内有意义**：跨后台切换后若别名失效，回退即弃，**不得把失效别名写回 settings** | 切到 Reasonix 后把 `kimi-code/k3-256k` 写盘，下次启动 Reasonix 拿着它去 `set_config_option` |

> 结构保障：红线 1 由 D3 的接口级 `list_models` 保证；红线 4/5 由 T5 的
> "先清后建 + 回退首项"联动链与 T7 的状态层写盘路径保证（写盘只发生在
> 用户主动切换或菜单/设置中心驱动时，回退不写盘——沿用现状语义）。

## 7. 风险与备案

| # | 风险 | 对策 |
|:--|:---|:---|
| R1 | Reasonix ACP 与 kimi 实现存在细节差异（`_meta` 扩展、错误码语义） | 泛化层不臆造协议：未识别 update 类型返回 None（现状语义）；差异在 T11 实测中逐个对齐 |
