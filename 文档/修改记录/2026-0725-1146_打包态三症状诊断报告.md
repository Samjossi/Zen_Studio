## 3. 逐症状结论

### S1 标题变 `_internal` —— 🔴 真 bug（frozen 默认工作区语义错误）

- **机理**：文件树标题 = 工作区根目录名（`gui/panels/file_explorer/explorer.py` `Path(self.root_dir).name`）。无启动参数时 `main.py` `resolve_workspace_root` 静默回退 `PROJECT_ROOT`；frozen 态 `PROJECT_ROOT = sys._MEIPASS`（`core/paths.py`），AppImage 下即 `/tmp/.mount_*/usr/bin/_internal`。
- **结果**：默认工作区落在**解包目录**——标题显示 `_internal`，文件树展示的是运行时库文件而非用户项目。开发态回退项目目录合理，打包态该回退**无意义**（解包目录不是任何人的工作区）。
- **连带**：终端面板 cwd 同样落 `_internal`（AppImage 只读挂载，截图提示符可见 `/tmp/.mount_Zen_StEDEDGb/usr/bin/_internal$`），用户在该目录下的一切写操作必然失败。

### S2 齿轮图标 —— 🟢 非 bug（误判，图标系统完好）

- **探针数据（决定性）**：frozen 探针与开发态输出**逐项一致**——主题 `Yaru-prussiangreen` 正常检出，`fromTheme` 对 `text-x-python` / `application-x-sharedlib` / `folder` / `application-zip` / `text-plain` 全部解析成功，`QFileIconProvider` 对 `.py` / `.so` / 目录 / `.lock` 全部返回有效图标。**打包未丢失任何图标能力**（产物内 `iconengines/libqsvgicon.so`、`imageformats/`、`platformthemes/libqgtk3.so` 均收编齐全）。
- **实图核验（决定性）**：Yaru 主题的 `application-x-sharedlib`（共享库 `.so` 的 mimetype 图标）**本色就是齿轮**——已读取 `/usr/share/icons/Yaru/48x48/mimetypes/application-x-sharedlib.png` 实图，与截图中的齿轮完全一致。
- **真相**：用户因 S1 被带进 `_internal`（满目录 `.so` 系统库），看到的全是「共享库」的合法齿轮图标；Python 文件的蛇标（`text-x-python`）在该目录下根本没有出现机会。修复 S1 后此症状自然消解，无需任何动作。

### S3 无法切换工作区 —— 🔴 真 bug（spawn 命令行为开发态专用）

- **机理**：`gui/main_window.py` `_spawn_window` 起新窗命令写死为开发形态：
  `subprocess.Popen([sys.executable, str(PROJECT_ROOT / "main.py"), folder])`
  frozen 态下：① `sys.executable` = AppImage 内 `zen-studio` 二进制自身；② `PROJECT_ROOT / "main.py"` = `_internal/main.py`——**源码收在 PYZ 归档内，解包目录无此文件**（已实证 `ls _internal/main.py` 不存在）。
- **推演**：子进程 `sys.argv` = `[zen-studio, "<_internal>/main.py", folder]` → `parse_args` 收到两个位置参数 → argparse 报 unrecognized arguments，`SystemExit(2)` → 2s 探活（`_close_after_spawn`）发现进程已死 → 状态栏「新窗口启动失败（退出码 2），本窗口已保留」。
- **结果**：用户点击「打开文件夹」后新窗秒死、旧窗保留，感知即「无法切换」。**同链路全灭**：「新建窗口」「在新窗口打开文件夹」「最近打开的项目」均经 `_spawn_window`，打包态全部不可用。
- 防护设计（探活失败保留旧窗）按预期工作，未造成次生损失——这是该链路中唯一行为正确的部分。
