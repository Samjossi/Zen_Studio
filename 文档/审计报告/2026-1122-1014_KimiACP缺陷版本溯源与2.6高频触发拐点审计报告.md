# Kimi ACP 缺陷版本溯源与 2.6 高频触发拐点审计报告

> **⚠️ 归档状态**：本文档撰写于 2026-1122-1014，记录当时的实施状态。
> 文档中提及的"已知问题"和"待办项"可能已在后续修复，请勿以本文档推断当前代码。

> **状态**：待验证（历史症状、版本包含关系与 ACP/TUI 改动边界已确认；触发率拐点待隔离 A/B 实测）
> **范围**：Kimi Code CLI 0.22.3–2.7.2 的 ACP 通知轮、忙态 prompt、取消语义；2.5.0–2.7.2 上游行为变更；Zen Studio 历史验收与客户端防护对症状可见性的影响
> **时间**：2026-11-22 10:14（审计）(UTC+8)
> **优先级**：高（涉及退版判断、客户端防线去留与后续上游修复验收）

## 1. 结论摘要

1. **本缺陷不是 2.6 才诞生。** 通知轮不可见至少在 0.29.0 已有公开报告；“通知轮不可见 + 忙态 prompt 立即空 `end_turn`”的完整同签名现象至少在 0.41.0 已出现，2.0.2、2.1.1 也有明确报告。首次引入版本仍未完成二分，不能精确指认。
2. **“缺陷早存在”不能推出“各版本触发率相同”，也不能推出“退版没有价值”。** 用户关于“以前一直正常、2.6 某次修改后频繁、2.7 后稳定触发”的体感，与早期缺陷潜伏并不矛盾。
3. **当前最可疑的触发率拐点是 2.6.0 包含的上游 PR #4630。** 该 PR 将 agent 执行统一切换到 Core Loop，重构 normal/notify/remind 队列、后台 detached task 通知和 prompt 结算边界。版本比较证实 2.5.0 不含该提交，2.6.0、2.6.3、2.7.1 均包含。
4. **2.7.1 的“通知轮期间保持排队 prompt”不是 ACP 修复。** 对应 PR #5166 是 `fix(tui)`，23 个改动文件中没有 ACP 文件；它新增 `loop.drained`/`loop.idle`，但 ACP 未接入这些边界。
5. **2.5.0 是值得优先做隔离 A/B 的临时规避候选，但不是已证实的安全版本。** 在完成同版本对照探针前，不把 #4630 写成已证明的唯一根因，也不承诺退到 2.5.0 就能根治。
6. **现有客户端防线不能因本次版本溯源而撤除。** 它解决的是上游违约后的假完成、危险接续和停止失效；版本触发率变化不改变这层保护价值。

## 2. 问题边界与触发条件

本报告跟踪的主缺陷由三类症状组成：

1. 后台任务完成、停止、cron 等事件启动的内部通知轮不向 ACP 客户端发送对应 `session/update`；
2. 通知轮活跃期间到达的 `session/prompt` 被提前回复空 `end_turn`，文本未进入执行，或延迟到通知轮后才执行；
3. `session/cancel` 覆盖不到没有 ACP prompt driver 的通知轮，需要会话级 `session/close` 才能可靠清理。

该故障不是每条普通消息都会触发。已复现场景的关键条件是：

- 存在后台任务完成或停止通知；
- 通知 steering 与用户轮次的工具链、下一轮 prompt 或排队发送发生交错；
- ACP 仍按 prompt driver 过滤事件和结算请求，无法正确表达内部通知轮。

因此，“特定后台通知探针百分百触发”不等于“所有普通对话百分百失败”。普通对话长期正常，不能证明该路径不存在缺陷。

这张表同时证明两件事：**缺陷的历史起点很早；2.6 附近仍可能存在显著的触发率变化。** 两者不可互相替代。

## 4. 2.6.0 高度可疑拐点：PR #4630

### 4.1 版本包含关系已确认

上游 PR [#4630](https://github.com/MoonshotAI/kimi-code/pull/4630) 标题为 `refactor(agent-core-v2): port agent loop runtime core`，于 2026-11-11 合入主干，核心提交为 `b263e80ff3ca93998336b1f89e7bc85946f8f76f`。

以该提交为比较基准，GitHub compare 返回：

| 目标版本 | compare 状态 | merge base | 判定 |
|:---|:---|:---|:---|
| 2.5.0 | `diverged` | `244819a526026f8b26177b9780a64889c18fa18c` | 不含 `b263e80` |
| 2.6.0 | `ahead` | `b263e80ff3ca93998336b1f89e7bc85946f8f76f` | 包含 `b263e80` |
| 2.6.3 | `ahead` | 同上 | 包含 `b263e80` |
| 2.7.1 | `ahead` | 同上 | 包含 `b263e80` |

这正好把该改动定位在 **2.5.0 与 2.6.0 之间**，与用户体感的时间边界一致。

### 4.2 改动不是普通重构

PR 正文明确列出以下行为变化：

- Core Loop 成为唯一执行状态机，旧 machine 执行路径一次性移除；
- 统一 normal、notify、remind 三类队列和消息历史；
- 排队消息按 ID 移动，新输入进入 notify，并由实际消费它的新 Turn 结算；
- 用户取消、内部通知和排队用户消息的续跑语义被重新收敛；
- 后台任务完成结果改经 Core detached tool 投递；
- TUI、desktop/web、ACP、SDK 的 Prompt/Turn 调用都位于受影响消费面。

虽然 PR 名义为 refactor，但它更换了通知产生、排队和结算的实际执行核心。**它可能没有改变 ACP 缺陷本身，却改变了缺陷被触发的频率和表现。**

### 4.3 ACP 旧缺陷没有被这次切换修掉

对 `b263e80` 中 `packages/acp-server/src/session.ts` 的改动核对显示，直接变化主要是 `tool.progress` → `tool.updated` 的事件适配与工具状态去重；没有看到针对 prompt driver、自主通知轮事件转发或 ACP 结算边界的修复。

因此当前最合理、但仍待 A/B 验证的工作模型是：

1. 2.6.0 的 Core Loop 切换使 notify 轮次及其排队/结算边界更加明确或更容易进入交错路径；
2. ACP 继续沿用旧的 prompt driver 过滤与请求结算方式；
3. 底层通知轮越稳定地产生，旧的 ACP 缺陷就越稳定地表现为隐藏轮、提前 `end_turn` 和取消落空。

这属于**有代码与版本包含关系支持的高置信假设**，不是已经完成因果闭环的实测结论。

### 4.4 为什么更新日志里看不到它

#4630 未出现在 2.6.0 release notes 中；PR 明确记录“不加 changeset”。因此仅检索发布说明会漏掉这次大切换。本次是继续检查路径提交历史与 PR 正文后才发现。

## 5. 2.6.3 与 2.7 邻近改动的实际边界

### 5.1 2.6.3 的通知相关修复不能直接解释正常路径高频触发

- PR [#4989](https://github.com/MoonshotAI/kimi-code/pull/4989)：将恢复/分支时的任务通知改为 prompt-only 记录，避免恢复或 fork 时额外发起模型请求。它主要减少 restored task 通知，不是正常后台任务完成通知的通用修复。
- PR [#4992](https://github.com/MoonshotAI/kimi-code/pull/4992)：让 Tower 只响应真实用户 prompt，避免后台通知误唤醒或停止 Tower 任务。改动范围是 Tower 与 prompt origin，不是 ACP 轮次结算。
- PR #4836、#4848 等 2.6.0 邻近改动主要处理恢复/undo 的通知去重与会话互斥；#4831 的 detached scheduler lease 修复可能扩大后台并发能力，但目前没有证据证明它单独造成本故障。

这些条目说明官方在 2.6 附近集中调整过后台通知和生命周期，但都不能替代 #4630 的 A/B 验证，也不能被误写成 ACP 主缺陷修复。

### 5.2 2.7.1 的排队改动只修 TUI

PR [#5166](https://github.com/MoonshotAI/kimi-code/pull/5166) 标题为 `fix(tui): defer queued prompts until the loop drains`。其实际边界为：

- 旧 TUI 把单个 `turn.ended` 错当全局空闲，导致排队消息过早出队；
- 新增 `loop.drained` 表示 normal/notify/remind 等待处理输入已清空；
- 新增 `loop.idle` 表示连 detached 后台任务在内的全局空闲；
- 23 个改动文件中没有 ACP 文件，ACP 没有消费这些新事件。

该 PR 反而从官方设计侧印证：**`turn.ended` 不是全局空闲。** 但它修的是 TUI，不应被引用为“2.7.1 已修复 ACP 排队语义”的证据。

2.7.2 的发布条目仅涉及 Web 思考强度草稿继承，与本缺陷无关。

## 6. 为什么过去可以一直正常使用

目前有三类并存解释，均不应省略：

1. **触发面未覆盖**：早期本地验收以普通对话、工具调用、用量和断管恢复为主，没有覆盖“后台通知 + 工具链 + 后续 prompt”的组合。历史通过不能证明这条路径正常。
2. **上游行为拐点**：#4630 在 2.6.0 更换通知与排队执行核心，可能把旧 ACP 缺陷从低概率、难观察变为稳定复现。这是本次最重要的待验证假设。
3. **客户端防护改变症状可见性**：11-20 曾加入一致性核对、drain 与看门狗，随后在 `85cf8aa` 中移除；11-21 又恢复终态确认、drain 和 `session/close` 分流。防护的增删会改变用户看到的是“同步中”“假完成”“停止失效”还是“受控恢复”，但它不是上游缺陷的诞生点。

所以，用户过去的真实良好体验可以被尊重，同时也必须保留 0.41.0 等版本已有同签名报告的事实。前者说明触发率与可见性，后者说明缺陷历史，两者并不冲突。

## 7. 对退版结论的纠偏

此前“退到 2.6 之前也解决不了”的说法过于绝对，现修正为：

- **退到 0.41.0、2.0.2、2.1.1 不能避开完整同签名缺陷**，这些版本已有公开复现；
- **2.5.0 不含 #4630，具有明确的实验价值**，可能恢复过去的低触发率；
- 2.5.0 仍可能保留早期 ACP 缺陷，故只能称为“临时规避/A/B 候选”，不能称为“已知无缺陷版本”；
- 即使退版后症状消失，也只能证明该版本组合下触发条件不再成立，不能反推早期缺陷从未存在。

## 8. 最小验证方案

在不变更当前生产 CLI 的前提下，用隔离安装或隔离可执行副本对 2.5.0、2.6.0 做同探针对照。每组使用新会话、相同模型、相同工作区与相同时序，至少重复 3 轮：

1. 后台 Bash 自然完成，同时原用户轮仍在工具链中；
2. 后台任务停止产生通知；
3. 通知轮活跃时发送后续 prompt；
4. 连续两个通知与一次追问交错；
5. 通知轮活跃时分别测试 `session/cancel` 与 `session/close`；
6. 回归普通多轮、手动停止后续问、`session/resume`。

每轮只记录脱敏元数据：CLI 版本、ACP request ID、`stopReason`、ACP 帧序、wire 的 `turn.prompt`/`prompt.steered`/`turn.ended`/`prompt.completed`、origin/trigger、最后 finishReason 和进程回收结果。

判定原则：

- 若 2.5.0 多轮正常而 2.6.0 同场景稳定失败，#4630 的触发率拐点假设得到强支持；
- 若两版同样失败，说明 #4630 不是必要条件，应继续向前二分；
- 若 2.5.0 只是不再出现症状，但仍存在通知轮不可见或 prompt 无响应，不得判为通过；
- 任何版本只有在通知可见、prompt 恰好执行一次、终态时机正确、停止有效同时满足时，才算本缺陷场景通过。

## 9. 当前行动建议

1. 保留现有客户端终态确认、drain、禁止危险自动接续与 `session/close` 停止分流。
2. 将 2.5.0 作为第一优先级的隔离 A/B 候选；未经对照，不直接替换生产 CLI，不宣称退版根治。
3. 上游跟踪增加 #4630 与 #5166 两个版本行为锚点：前者用于解释 2.6 触发率变化，后者用于防止把 TUI 修复误判为 ACP 修复。
4. 官方后续修复验收必须覆盖 ACP，不因 TUI 的 `loop.drained`/`loop.idle` 已落地而推定 ACP 通过。
5. 本报告结论在 A/B 完成后更新为新的审计报告，不回写或篡改历史证据。
