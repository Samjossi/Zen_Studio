## 1. 结论摘要

1. **2.5.0 退版后的「问题依然在」不能作为上游缺陷的证据。** 该时段有 4 条 `轮次响应`、**0 条 `终态确认`、0 条 `轮末汇总`**；四轮全部卡在客户端终态确认里，没有任何一轮走到上游判定。
2. **直接原因是私有 wire 的一处必填字段。** 2.5.0 的 `turn.prompt` 没有 `trigger` 字段，`_consume_prompt()` 把「`trigger` 不是字符串」判为 `broken` 并丢弃该轮，`snapshot()` 因此落到 `unknown`。
3. **`unknown` 在 `_confirm_turn_end` 里没有出口。** 该循环只认 `normal`、`desynchronized` 且 agent 空闲、连接死亡、用户停止；`unknown` 会一直保持 busy 并每隔约 1 秒轮询，直到用户放弃或关会话。
4. **2.5.0 的其余终态证据是完整的。** `turn.ended.reason=completed`、`prompt.completed.reason=completed`、`step.end.finishReason=end_turn` 全部存在。用同一份真实 wire 做判定器重放：原版跟踪器 → `unknown`；仅把 `trigger` 放宽为可选 → `normal`；2.7.2 原版 → `normal`。三者只差这一个字段。
5. **这是设计缺陷，不是 2.5 专属兼容问题。** fail-closed 无时间上界 + 把私有 schema 当硬契约，意味着任何未来 CLI 的字段改名/缺失都会 100% 挂起，把上游的低频故障放大成客户端的高频死锁。
6. **现有逃生路径代价高且会掩盖证据。** 停止 → `session/cancel` 不生效 → `session/close` → agent 被 SIGTERM（`exitCode=-15`）→ 连接代次重建。用户看到的是「会话报废、换一个」，而不是可归因的失败。

## 3. 根因：一处必填字段把整轮判成「不可信」

### 3.1 版本字段差异（真实记录，非推断）

对两个版本真实 `turn.prompt` 记录的键集合比对：

| 版本 | `turn.prompt` 记录键 | `origin` 键 |
|:---|:---|:---|
| 2.5.0 | `agentId, input, origin, promptId, time, turnId, type` | `kind` |
| 2.7.2 | `agentId, input, origin, promptId, time, **trigger**, turnId, type` | `kind` |

两个版本只有 `trigger` 有无之分；`origin.kind`、`turnId`、`promptId` 形态一致。

### 3.2 代码路径

`src/ide/llm/providers/kimi/turn_state.py:217-237` 的 `_consume_prompt()`：

```python
trigger = record.get("trigger")
if (not isinstance(prompt_id, str) or not prompt_id or turn_id is None
        or not isinstance(origin, dict) or not isinstance(trigger, str)):
    self.broken = True
    return
```

`trigger` 缺失 → `broken=True` 且**该轮不入 `_turns` / `_by_prompt` / `_by_turn`**。

`src/ide/llm/providers/kimi/turn_state.py:321-333` 的 `snapshot()`：

```python
if not self.available and not self._turns and not self._notifications:
    return result("normal", "wire 不可用且无风险证据")
if self.broken or self.missing:
    if (user is not None and ...):
        return result("normal", "wire 受损但用户轮证据完整")
    return result("unknown", "wire 元数据不可用或格式损坏")
```

此时 `available=True`、`broken=True`、`user is None`（该轮被丢弃），因此返回 `unknown`。

`src/ide/llm/providers/kimi/provider.py:558-609` 的 `_confirm_turn_end()` 循环：`normal` 返回、`desynchronized 且 !agent_active` 返回、`dead` 抛错、其余状态一律 `self._turn_pending = True` 后继续 `next_update(timeout=_CONFIRM_POLL_S)`。`unknown` 不在任何出口里。

### 3.3 为什么落到 `unknown` 而不是 `desynchronized`

`broken` 分支在 `user is None` 分支之前短路。若只是「用户轮未登记」而没有 `broken`，`snapshot()` 会在宽容窗口后返回 `desynchronized`（至少还有一个出口）；`broken` 把它升级成了 `unknown`——一个**没有任何出口**的状态。这一点直接决定了「可诊断失败」变成了「静默挂死」。

### 3.4 判定器离线重放（同一份真实 wire，只改一处）

用真实 wire 直接驱动 `TurnStateTracker`，不启动 IDE、不调用上游：

| 输入 | 跟踪器 | 判定 | 说明 |
|:---|:---|:---|:---|
| 2.5.0 真实 wire | 原版 | `state=unknown, broken=True` | 复现线上现象 |
| 2.5.0 真实 wire | 仅 `trigger` 改为可选 | `state=normal, finish=end_turn, broken=False` | 只差这一处 |
| 2.7.2 真实 wire | 原版 | `state=normal, finish=end_turn, broken=False` | 对照 |

结论：2.5.0 不是「终态证据不足」，而是「一处非必要字段缺失被当成整体不可信」。

## 4. 两个放大因素

### 4.1 fail-closed 没有时间上界

`unknown` 在 `_confirm_turn_end` 中每 1 秒轮询一次 wire，但没有任何 deadline，也没有「判不出来就降级」的分支。用户能做的只有两件事：按停止，或关会话。这不是「保守」，而是把不可判定的情况转成了**无限期 busy**。

同一状态还会置 `_turn_pending=True`，使 `src/ide/gui/panels/chat/panel.py:1133-1142` 的待发闸门拒绝自动补发，把待发内容留在输入框并提示「后台轮次尚未落定」。它不制造挂死，但会让恢复路径多一层阻塞，且提示语指向「后台」而非「我们的解析失败」，误导归因。

### 4.2 逃生出路是杀会话

`src/ide/llm/providers/kimi/provider.py:273-283`：

```python
if session_id and conn.cancel_turn(session_id):
    conn.abort_turn()
    return
if session_id and conn.is_alive and self._turn_pending:
    if self._close_supported:
        conn.close_session(session_id)
    ...
conn.abort_turn()
```

终态确认挂住时，`_turn_id` 已在 response 后清理，`cancel_turn()` 返回 False；于是走 `session/close`，agent 进程收到 SIGTERM（日志 `exitCode=-15`），下一次发送再靠 `session/resume` 重建。若 resume 不被支持或失败，就是 fail-closed 的「原会话恢复失败」，会话上下文直接报废。

这条路径在 2.7.2 的假完成场景里是有效的止血手段；但在 2.5.0 这里，它被用来收拾一个**客户端自己制造的**挂起，代价是每轮都杀一次 agent。

## 5. 影响评估

1. **2.5.0 当前 100% 失能**：4/4 轮无终态确认；每轮以停止、关会话或新建会话收场。
2. **不是 2.5 专属**：任何未来 CLI 只要改名/缺失 `trigger`（或其它被当成必填的私有字段），同样 100% 挂起。2.5.0 只是第一个撞上的版本。
3. **本次退版 A/B 无效**：不能据此判断「2.5 是否仍有上游缺陷」，也不能据此判断「2.6 拐点假设成立/不成立」。
4. **症状遮蔽**：每轮必挂的新症状盖住了原始的「长任务后无响应」，用户与后续排查都无法区分两者。
5. **会话资产损失**：每轮以 `session/close` + 进程重建收场，上下文依赖 `session/resume`；resume 失败即会话报废，且用户会误以为「Kimi 2.5 更差」。

## 6. 结论边界（本文未证明）

- 未证明上游通知轮/提前 `end_turn` 缺陷在 2.5.0 上存在或不存在；
- 未证明 2.5.0 是安全版本，也未证明它不是；
- 未证明原始「长任务后无响应」症状是否仍会复现；
- 「放宽 `trigger`」只做了离线判定器重放，**未**在真实链路验证完整行为（含 GUI 收尾、待发、停止）；

## 7. 建议

| 编号 | 优先级 | 建议 | 理由 |
|:---|:---|:---|:---|
| P0-1 | 高 | `trigger` 改为条件必填：仅 `origin.kind != "user"` 时要求；缺失按非 notify 处理 | 用户轮不需要 `trigger` 也能判定；把可选字段当硬契约是本次直接原因 |
| P0-2 | 高 | `unknown` 加时间上界（建议 30–60s）：到期记 WARNING 并退回原生单轮次收尾，不得无限保持 busy | 私有 schema 不可控；不可判定必须有降级出口 |
| P0-3 | 高 | `session/close` 只用于关标签/切后端/退出；「停止」优先 `cancel` + 本地 abort，需关闭会话语义时显式提示 | 现在停止会静默杀掉 agent，用户以为只是「停这一轮」 |
| P1-1 | 中 | 观测与行为分离：日志、`generation`、`failure_reason`、`exitCode` 保留；行为防线做成可独立开关 | 回退实验与日常排障都需要「行为关了、证据还在」 |
| P1-2 | 中 | 版本能力探测：`initialize` 已返回 `agentInfo.version`，按版本选择 wire schema，而不是硬编码新字段 | 避免下一次 CLI 升级再撞同类问题 |
| P2 | — | 按用户已拍板的全裸基线做原始症状复现实验 | 见 `work plans/2026-1122-1144_KimiACP连接层全裸回退与原始症状复现验证计划.md` |
