## 1. 诊断结论

本次事故不是此前修复所针对的“ACP 断管后无法恢复原会话”，也不是 `session/resume` 已调用但恢复失败。直接故障是：

**IDE 在 Kimi CLI 的内部后台通知轮次及用户排队请求尚未真正完成时，已将界面轮次按正常完成收尾；随后旧 agent 仍继续执行工具和修改文件，形成“界面假完成、后台继续运行”的状态分裂。**

既有恢复机制只覆盖连接死亡、写帧失败和持续无帧停滞。本次 IDE 收到了其所认为的正常 ACP `response`，没有进入上述任何故障分支，因此没有设置恢复标记，也没有执行 `session/resume`。

旧上下文没有从磁盘删除。事故会话的 `state.json`、主 agent `wire.jsonl` 和诊断日志均仍存在，旧 ACP 进程在证据截取时仍存活。用户所感受到的“上下文被抛弃”，实际是新建标签与原 Kimi 会话之间没有关联，加上现有存档不保存 provider 会话身份，导致界面缺少重新挂接入口。

高置信的触发背景是：**后台 Git 任务终止通知生成 CLI 内部轮次，与 IDE 下一轮用户 prompt 的排队/发送发生时序交错。** 但现有日志没有保留正常 ACP 响应帧的请求 ID、`stopReason` 与协议时序，尚不能最终判定是 Kimi CLI 提前响应、ACP 通知语义变化，还是 IDE 对帧的解释不完整。

## 4. 直接故障链

### 4.1 CLI 内部通知轮次与 IDE 轮次模型不一致

wire 明确显示：原用户轮次完成后，CLI 立即启动一个 `origin.kind=task`、`trigger=notify` 的内部轮次。该轮次不是 IDE 面板独立创建的用户轮次，却真实占用 agent 执行能力并运行工具。

IDE 当前主要以单个 ACP `session/prompt` 的响应划分轮次，没有表达“agent 正在处理内部通知轮次”或“用户 prompt 已接收但仍在 CLI 队列中”的状态。

### 4.2 IDE 将 ACP response 等同于用户任务真实完成

`src/ide/llm/providers/kimi_acp.py` 的主消费循环收到 `kind == "response"` 后，进行用量收尾并直接返回。`src/ide/gui/panels/chat/worker.py` 随后发出正常完成信号，面板解除 busy、记录历史并触发完成通知。

该链路只验证“某个 ACP 请求已有响应”，没有额外验证：

- 对应用户 prompt 是否已真正进入 wire 执行；
- 对应用户 `promptId` 是否已记录 `prompt.completed`；
- agent 是否已经进入另一个内部通知轮次；
- ACP response 是否只是排队、取消或状态迁移的早期回执。

因此，协议响应与真实任务完成之间一旦出现语义间隙，界面就会提前播报成功。

### 4.3 用户请求后来在旧会话继续执行

用户“继续”最终于 09:18:51 进入旧会话，并在此后继续修改工作区。这证明假完成不是单纯的提示音误报，而是实际执行生命周期已经脱离面板控制。

其风险包括：

- 用户看到完成后新建会话，旧任务却仍修改同一工作区；
- 新会话与旧会话并发修改同一文件；
- 用户重复发送指令，造成重复写文件、重复命令或重复提交；
- 面板无法可靠表示停止、完成、工具副作用和上下文归属。

## 5. 既有恢复机制为何没有生效

既有恢复设计为以下三类触发：

| 触发类别 | 本次是否发生 | 结果 |
|:---|:---|:---|
| reader EOF、进程退出、写帧失败 | 否；旧进程持续存活，wire 持续增长 | 不进入连接死亡恢复 |
| 看门狗持续无帧停滞 | 否；没有停滞标记日志，且 provider 已按 response 收尾 | 不调用 `mark_stalled()` |
| 用户在看门狗/断管后的下一次手动发送 | 前提未成立 | 不执行 `session/resume` |

09:16 的 generation=2 没有“恢复开始”，不是 `_resume_session()` 失效，而是新标签创建了新 provider，其 `_session_id` 初始为空，按设计走 `session/new`。

因此，本次不能通过增加 `resume` 重试次数解决。首先必须让 IDE 识别“正常响应但真实轮次未完成”的第四种故障：**轮次状态失配。**

## 6. 上下文与恢复入口诊断

### 6.1 旧上下文仍然存在

事故会话目录、`state.json` 和 `wire.jsonl` 均保留，且 wire 在事故后继续增长。没有证据表明 Kimi 删除了旧上下文。

需要区分两件事：

- **数据层上下文仍存在**：已由会话文件证实；
- **当前 UI 能否安全接回**：现有产品没有完整入口，且旧 agent 活跃时不应盲目启动第二个客户端恢复同一会话。

### 6.2 新标签不会继承旧 provider 会话

`src/ide/gui/panels/chat/tabs.py` 的新建标签路径创建独立面板和独立 provider。新建标签只注入后端与模型选择，不携带旧 Kimi `sessionId`。

因此，点击加号后继续对话会创建新空会话，不会自动迁移旧上下文。

### 6.3 重启存档只恢复文字，不恢复模型上下文

`src/ide/gui/panels/chat/session_store.py` 的 `SessionRecord` 仅包含 `backend`、`version` 和 `history`，没有 Kimi 会话 ID、工作区创建参数或恢复状态。

`src/ide/gui/panels/chat/panel.py` 的重放逻辑也明确说明：重放内容只用于界面展示，不回传 provider；ACP provider 重启后会形成全新会话。

这意味着既有断管恢复仅覆盖“原标签仍存活、provider 仍持有内存会话 ID”的场景，尚未覆盖关闭标签、应用重启或误新建标签后的显式重挂接。

对恢复提交 `2ccca93` 与其父提交的差异核对显示，该提交主要修改：

### 7.3 已确认是既有修复覆盖不全

此前真实与冻结态验收覆盖的是“定点结束 ACP 进程，再由下一次手动发送恢复”。该场景能证明断管恢复有效，但不能覆盖：

- 后台任务通知生成内部轮次；
- 用户待发与内部通知轮次交错；
- ACP response 早于 wire 用户轮次执行；
- IDE 完成后 agent 继续执行；
- 新标签或应用重启后的原会话重挂接。

所以准确结论是：**断管修复本身有实证通过，但故障矩阵不完整，本次暴露了另一类轮次一致性问题。**

## 8. 根因分层

### 8.1 已确认的直接原因

1. IDE 将 ACP response 直接解释为用户任务正常完成。
2. CLI 在事故时段存在独立内部通知轮次，且用户“继续”晚于 IDE 完成提示才真正执行。
3. IDE 缺少 ACP response、wire 用户轮次和 agent 活跃状态之间的一致性检查。
4. 状态失配不属于既有恢复触发条件，导致恢复状态机未启动。
5. 会话存档没有 provider 会话身份，新标签与重启后缺少原上下文重挂接能力。

### 8.2 高置信诱因假设

后台 Git 任务终止通知在 09:14:08 立即生成 CLI 内部轮次，与下一轮用户 prompt 的排队/发送交错，是最明显的触发背景。前一次事故的审计也记录过后台 Git 通知与故障相邻，因此该条件应提升为优先复现项。

但“相邻”仍不等于已经证明因果。只有取得正常 ACP 响应元数据并完成真实复现，才能把它升级为上游根因。

### 8.3 尚未锁定的责任边界

保留以下可能，不提前单选：

1. Kimi CLI 在内部通知轮次期间对后续 ACP prompt 先返回响应、后排队执行；
2. ACP 对 `session/prompt` 响应的完成语义与 IDE 当前假设不同；
3. IDE 在后台通知、待发接续和轮次 ID 簿记上存在尚未复现的竞态；
4. 多种因素共同造成响应与实际用户轮次错位。

## 9. 建议解决方案

### 9.1 P0：先阻止假完成和危险接续

不能简单把 ACP response 丢弃并永久等待 wire，否则正常后端或私有格式变化会造成新的 busy 卡死。建议增加有界“轮次一致性核对”状态：

1. 正常 response 收尾时记录请求 ID、`stopReason`、会话 ID、连接代次和当前 wire 用户 `promptId/turnId` 元数据，不记录正文。
2. 若 response 对应的用户 prompt 尚未出现或尚未完成，不得播报任务成功，不得自动发送排队内容。
3. 面板显示“agent 轮次状态尚未同步，请勿重复发送”，保留原会话和工具卡片。
4. 有界等待真实轮次落定；若 wire 显示 agent 仍在执行，不得直接 kill 或恢复会话。
5. 确认 agent 空闲后，再重建 ACP 并以原 `sessionId` 执行 `session/resume`，随后只允许用户手动发送新指令。
6. 核对超时或无法判定时 fail closed：不自动重放、不自动新建空会话、不伪报成功。

这里的核心是“先确认 agent 是否仍有副作用，再决定重连”，而不是看到失配就立即杀进程。

### 9.2 P0：消除内部通知轮次与自动待发的危险竞态

在真实协议能力允许的范围内，发送下一轮前应确认 agent 已从内部通知轮次回到空闲。至少应做到：

- 前一轮刚完成时不盲目立即接续待发，增加可验证的轮次边界；
- 检测到内部通知轮次活跃时暂停自动待发，并明确提示；
- 正常完成、状态失配、用户停止和连接死亡使用不同收尾状态；
- 任何失配分支均禁止自动重放原 prompt。

不能仅依赖固定 sleep 作为最终方案，因为通知延迟不可预测；固定延迟最多是探针或临时缓解，不是协议修复。

### 9.3 P1：持久化会话身份并提供显式重挂接

扩展会话存档，保存必要的 provider 恢复身份：

- 后端类型；
- Kimi `sessionId`；
- 会话 cwd 与 MCP 创建参数；
- 模型与 thinking 选择；
- 存档时的轮次/恢复状态。

用户入口应明确区分：

- **仅查看历史文字**；
- **恢复原模型上下文**；
- **明确新建空会话**。

恢复前必须检查旧 agent 是否仍活跃，避免两个客户端同时控制同一会话。恢复失败继续遵守不发送 prompt、不静默新建空会话。

### 9.4 P1：补全正常帧诊断与真实复现

在现有异常诊断之外，增加正常轮次收尾的有界结构化元数据：

- ACP 请求 ID 与响应 ID；
- `stopReason`；
- sessionId 与连接代次；
- 当前用户 prompt 的本地轮次序号；
- wire 中对应 `promptId/turnId` 的出现与完成状态；
- 内部通知轮次的起止元数据。

不得记录完整 prompt、工具输出或凭证。

真实复现矩阵至少包含：

1. 长任务中启动后台 Bash；
2. 后台任务结束或被停止并生成通知；
3. 通知轮次开始时用户已有待发；
4. ACP response 早于用户 wire prompt；
5. 旧 agent 继续执行时禁止自动重发；
6. agent 空闲后恢复原会话；
7. 新标签、关闭标签和应用重启后的显式重挂接；
8. 开发态与最终 AppImage 均验证。

### 9.5 P2：依据真实帧修复或上报上游

- 若真实帧证明 Kimi CLI 提前返回了误导性的完成响应，应携带脱敏时序、请求 ID、`stopReason` 和内部通知轮次证据另案上报或修复 CLI。
- 若 IDE 忽略了既有协议字段或错误处理通知边界，应在 IDE 协议层修复，并加入真实帧夹具。
- 在上游责任未锁定前，IDE 仍需保留状态一致性防护，不能把安全完全寄托于上游永不错位。

## 10. 验收标准

修复验收不得只检查“最终又能聊天”，必须同时满足：

- ACP response 与真实用户轮次不一致时，成功通知次数为零；
- 状态失配时自动待发次数为零；
- 原 prompt 自动重放次数为零；
- agent 活跃时强制 kill 或盲目 resume 次数为零；
- agent 空闲后恢复前后 `sessionId` 相同；
- 恢复后仅发送用户新的手动指令；
- 旧工具写操作不重复执行；
- 新标签和重启后的恢复入口能区分文字重放与模型上下文恢复；
- 正常对话、正常停止、普通断管恢复和排队发送不回归；
- 正常响应日志有足够元数据定位责任边界，且不泄露正文和凭证；
- 真实后台通知竞态及最终冻结版 AppImage 验证通过。

## 11. 最终结论

本次事故的核心不是原会话被 Kimi 删除，也不是 `session/resume` 失效，而是：

**后台任务通知引入 CLI 内部轮次后，IDE 的 ACP 请求生命周期与 CLI 的真实执行生命周期发生分离；IDE 过早完成并允许用户转向新会话，旧 agent 却继续运行。既有恢复机制因只看到“正常 response”而没有触发。**

正确解决顺序是：

**识别轮次失配 → 停止假完成与自动待发 → 确认真实 agent 是否仍执行 → 安全恢复原会话 → 持久化会话身份并提供显式重挂接 → 以真实 ACP 帧完成上游归因。**

不能只靠增加自动重试、延长看门狗或反复调用 `resume` 处理；这些做法会分别引入重复副作用、继续误报和活跃任务被中断的风险。
