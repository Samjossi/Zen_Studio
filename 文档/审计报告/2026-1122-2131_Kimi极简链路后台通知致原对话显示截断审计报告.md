## 2. 极简链路特别说明：不要与旧报告中的机制混淆

### 2.1 事故时的客户端基线

事故运行实例为 Zen Studio 1.8.0.581，Kimi 已采用**极简链路**：

- `session/prompt` response 即本轮终态；`end_turn` 正常收尾；
- 不使用私有 wire 判断轮次是否真实结束；
- 不做 `_confirm_turn_end`、轮末 drain、`turn_state` 四态判定或 `TurnDesynchronized`；
- 不产出后台轮次同步提示，不保留 `_turn_pending` 待发闸门；
- 停止只走 `session/cancel` 与本地 abort，不回落 `session/close` 分流；
- `post_turn_usage_grace_s=0.0`，不进行 response 后的用量宽限或空闲 ACP 队列回收。

因此，旧审计报告里出现的“终态确认继续 drain”“失配后恢复”“轮后 3 秒收集”“面板最长 10 秒宽限”等机制，**都不是本事故运行实例的现有行为，也不能用来解释本次显示截断**。

### 2.2 审计时工作树的新增量

本次事故排查前，工作树刚完成只读轮内上下文用量恢复：

- `src/ide/llm/providers/kimi/usage_poll.py` 只读 `session_index.jsonl` 与 `wire.jsonl`，为徽章提供轮内水位；
- `poll_usage()` 不接收 ACP 连接、不获取 `_turn_lock`，不读取、排空、清理或重排 ACP 帧；
- 官方 `usage_update` 仍只在正常帧循环中处理，response 即终态的契约未变；
- 该功能不改变正文、工具卡、通知轮次归属或对话持久化。

**本报告审计的是轮次结算与对话呈现，不是用量徽章。** 不得把“只读 wire 获取用量”误写成“读取 wire 判断终态”，也不得为修复本事故而让徽章轮询触碰 ACP 队列。

### 2.3 与历史审计的关系

`2026-1122-1250_KimiACP全裸基线通知轮交错提前end_turn复现审计报告.md` 已证明同类上游缺陷可在无客户端补偿的基线上复现。本次的新信息是：

- 触发源是 agent 工具产生的真实后台任务完成通知，而非专门的带外交错探针；
- 后续工作没有丢失，而是跨多个通知轮次继续执行，导致用户误以为对话读取中断。

## 5. 根因分层

### 5.1 上游直接原因：通知 steering 后提前结算原用户轮

以下三点构成直接证据：

1. `prompt.steered` 出现时原用户轮仍在执行；
2. 原轮次最后一步明确为 `finishReason=tool_use`，不是自然 `end_turn`；
3. wire 与 IDE 在同一毫秒级窗口分别记录 `turn.ended` 和 ACP `end_turn`，后续工作却进入新通知轮。

因此，可确认的直接原因是 **Kimi CLI 在后台任务通知 steering 后，提前把仍有工作的原用户轮次结算为完成**。这与既有全裸基线审计中的上游结算缺陷同类。

本报告未审计 Kimi CLI 上游源码，不能进一步指定其内部函数或代码行。

### 5.2 客户端呈现机制：response 即终态，通知轮不续接原轮

极简 provider 收到合法 response 后按设计结束 `_iter_turn_chunks()`，GUI worker 随后收尾。后续通知轮没有原 `session/prompt` 的请求 ID，也没有作为该 worker 的后续 chunk 继续上屏。

这解释了用户看到的全部现象：

- 原对话停留在中间 Bash 卡片；
- 完成提示提前出现；
- 后续工具调用和最终答复没有立即续接到原视图；
- 下一次手动发送后，用户才重新看到会话活动。

**response 即终态不是本次上游提前 response 的制造者，但它决定了提前 response 一旦出现，界面就会立即截断。** 两者必须分层归因。

| 网络断连或 ACP 子进程崩溃 | 无 EOF、BrokenPipe、`connection_dead` 或连接换代；后续仍用 generation 3 | 排除 |
| 后台 Bash 没有继续执行 | 各任务产物完整，时间戳与通知轮一一对应 | 排除 |
| 实施结果未保存 | 新模块、测试、文档与 20:23 实施回写均存在于磁盘 | 排除 |

| 旧版 drain 失效 | 当前极简链路本就没有 drain | 不适用 |

## 6. 影响与未证明事项

### 6.1 已确认影响

- 原轮次被提前播报为完成，用户无法从原视图判断 agent 仍在工作；
- 后续执行与最终答复在短期内不可见，形成“IDE 没继续读取”的实际体验；
- 工作成果并未丢失，但用户可能误以为任务中断而重复操作；
- 多次后台通知会把一个逻辑任务拆成多个通知轮，增加人工核对难度。

### 6.2 本次未证明

1. 未证明所有后台任务完成通知都会触发该问题；本次是确定的一次真实命中，不是触发率统计。
2. 未抓取完整 ACP stdout，因此不判断通知轮是否向客户端发送过其它未被记录的协议帧。
3. 未审计 Zen Studio 会话历史的持久化文件，结论限于“项目成果未丢失”和“通知轮存在于 wire”，不扩展为所有 GUI 历史均已正确保存。
4. 未验证不同 CLI 版本、 cron、提醒或子代理通知是否复用同一结算路径。
5. 未在本报告中提出或实施客户端修复；任何方案需独立选型与验证。

## 8. 最终判断

本次事件可以概括为：

**后台任务完成通知 steering → 上游把 `tool_use` 中的原用户轮提前结算 → 极简 IDE 按 response 正常收尾 → 后续工作转入 task/notify 轮次并继续执行 → 原对话视图没有续接显示。**

所以，用户关于“执行后台任务后 IDE 没有继续接着读”的判断与证据一致；但技术口径应写成**轮次被提前结算并切换显示通道**，而不是网络断连、后台任务失败或代码没有保存。
