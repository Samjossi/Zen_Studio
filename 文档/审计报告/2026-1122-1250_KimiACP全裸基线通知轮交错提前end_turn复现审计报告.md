## 1. 结论摘要

1. **原始「长任务后无响应」（S1）在全裸基线上未复现。** 前台长任务场景 B 两版各跑 3 次：2.5.0 在 489.8–494.4s、2.7.2 在 489.5–493.2s 均正常收到 `session/prompt` response；3/3 的 response 之后都没有 `tool.call`，标记文件在 response 之前落盘。
2. **但 S2（假完成）稳定复现，且触发条件与 CLI 版本无关。** 触发动作是「后台任务通知轮仍在执行时，客户端发来 `session/prompt`」。
3. **机制已由帧与 wire 双边钉死。** prompt 到达后 **9–10ms** 就收到 `stopReason=end_turn`（正文 0 字、本轮 0 个工具帧）；随后 agent 把该 prompt 排队，在通知轮结束后的**不可见轮次**里执行（Read/Write，实测 4.3–9.6s），全程不再发 `session/update`。若出现迟到的可见帧，只有隐藏轮的工具权限请求——实测出现在 end_turn 之后 187ms（2.5.0 C2）与 6.2s（2.7.2 E2）；2.7.2 的 C2 那一轮则连该帧也没有。
4. **2.5.0 不免疫。** C2 交错探针在 2.5.0 上 **3/3** 复现；2.7.2 为 **2/3**。唯一未复现的一轮，追问在通知轮结束后 **352ms** 才到，落在窗口外。
5. **「2.6.0 的 #4630 是触发率拐点」未获本实验支持。** 两版通知轮时长同量级（2.5.0 3.5–7.9s；2.7.2 2.3–4.0s），进入交错窗口后同样中招；本实验没有观察到 2.7.2 更高的触发率。
6. **「停止失效」的真实机制也拿到了。** 提前结算后 B0 的 `_turn_id` 已清空；用户在隐藏轮执行中按停止，客户端**连 `session/cancel` 都不会发**（帧计数 0），agent 继续跑满 53.6s 并落盘。不是 agent 忽略取消，而是客户端误以为轮次已结束。
7. **B0 没有任何客户端防线仍然复现，排除「客户端自己制造」。** 反过来也说明：现有客户端防线（终态确认、待发闸门等）不能消除这个签名，只能承接或提示；它们不是缺陷的起源。

## 3. 核心证据：通知轮交错 → 提前空 end_turn → 隐藏执行

### 3.1 C2 探针设计

1. 第 1 轮：让 agent 用 Bash 后台模式启动 `sleep 30; echo bg-done > c2_bg_result.txt`，立即回复；
2. `sleep 30` 到点后，CLI 自发启动一个 **origin=task / trigger=notify** 的内部通知轮；
3. 第 2 轮在首轮结束后 **31s** 发出：「读取 `c2_bg_result.txt`，把内容写进 `c2_marker.txt`，回复 C2-OK」。

追问到达时，通知轮是否仍在执行，由 wire 的 `turn.prompt`/`turn.ended` 时间戳直接判定；标记文件是「追问是否真的被执行」的客观证据。

### 3.2 C2 矩阵（两版各 3 次）

| run | CLI | 追问落在通知轮内 | ACP 响应 | ACP 正文 | wire 中该用户轮实跑 | wire 工具数 | marker |
|:---|:---|:--:|--:|--:|--:|--:|:--|
| `122039-250-c2` | 2.5.0 | 是（通知轮结束 −1ms） | **0.01s** | 0 | **4503ms** | 2 | `bg-done` |
| `122137-250-c2` | 2.5.0 | 是（−1ms） | **0.01s** | 0 | **6585ms** | 2 | `bg-done` |
| `122237-250-c2` | 2.5.0 | 是（−1ms） | **0.01s** | 0 | **9572ms** | 2 | `bg-done` |
| `122346-272-c2` | 2.7.2 | 是（+1ms） | **0.01s** | 0 | **4344ms** | 2 | `bg-done` |
| `122445-272-c2` | 2.7.2 | 否（+352ms） | 5.04s | 5 | 5032ms | 3 | `bg-done` |
| `122545-272-c2` | 2.7.2 | 是（+1ms） | **0.01s** | 0 | **4457ms** | 2 | `bg-done` |

相关性是干净的：**凡追问与通知轮收尾相差 ±1ms 的 5 轮，全部提前空收尾；唯一相差 +352ms 的一轮正常。** 2.5.0 3/3、2.7.2 2/3，差异来自时序而非版本。

> 场景 C（`sleep 75`，追问延后 80s）也复现了同样规律：2.5.0 那轮追问在通知轮结束后 3.4s 才到 → 正常 5.5s；2.7.2 那轮在通知轮结束后 1ms 到达 → 0.01s 空收尾、wire 里实跑 4990ms。

### 3.3 单轮帧序列（2.5.0，`122039-250-c2`）

```
seq 101  c2s  session/prompt  id=6                      12:21:15.667
seq 102  s2c  (response)      id=6  stopReason=end_turn 12:21:15.676   ← 9ms 后空收尾
seq 103  s2c  session/request_permission id=1           12:21:15.863   ← end_turn 后 187ms
seq 104  c2s  (permission reply) id=1                   12:21:15.863
（此后到 run 结束，没有任何 session/update）
```

即：客户端在 9ms 内被明确告知「这一轮结束了」，但 187ms 后仍有隐藏轮在请求工具权限；正文、工具调用、工具结果三类 `session/update` **一条都没有**。

### 3.4 wire 证明执行发生在 end_turn 之后

同一 run 的 wire（已脱敏，只保留元数据）：

| wire 轮 | origin/trigger | 起止（相对） | 时长 | 工具调用 |
|:--|:--|:--|--:|--:|
| turn 0 | user / — | — | 3800ms | 1（启动后台任务） |
| turn 1 | **task / notify** | — | 4195ms | 1 |
| turn 2 | user / — | 通知轮结束同毫秒启动 | **4503ms** | 2（Read + Write） |

`turn 2` 的 2 次工具调用正是「读取 `c2_bg_result.txt`、写出 `c2_marker.txt`」，marker 内容 `bg-done` 落盘。而 ACP 侧在 turn 2 开始前 1ms 就已经把 prompt 结算为 `end_turn`。**工作不是没做，是做在了客户端已经认为结束后。**

### 3.5 为什么这是「上游结算边界」而不是客户端阻塞

- B0 在该轮没有任何终态确认、闸门、看门狗或 abort 逻辑（B0 不含这些代码）；
- 客户端只是在 `next_update()` 上等 response；response 真的到了，且是协议合法的 `end_turn`；
- 隐藏轮的执行由 CLI 自己继续，客户端既收不到帧，也没有任何 API 能感知；
- 唯一的迟到信号 `session/request_permission` 是反向请求，不属于轮次流。

因此这条链路上客户端无可归因的阻塞点；问题在 CLI 把「通知轮活跃期收到的 prompt」提前结算，并在结算后继续执行。

### 3.6 停止失效的真实机制（E2）

E2 探针：后台 `sleep 30` → 通知轮活跃期发追问「执行 `sleep 45` 后写 marker」→ 客户端 10ms 收到空 end_turn → **3 秒后调用停止**。

2.7.2 实测（`131143-272-e2`）：

| 时刻 | 事件 |
|:--|:--|
| prompt 发出 | `13:12:21.418` |
| ACP response `end_turn` | `13:12:21.428`（10ms，正文 0） |
| 隐藏轮请求 Bash 权限 | `13:12:27.628`（end_turn 后 6.2s） |
| 客户端按停止 | 约 `13:12:24.5`，**帧日志中 `session/cancel` 计数 = 0** |
| wire 中该用户轮结束 | `13:12:35.898`，`durationMs=53564` |
| marker | 存在，内容 `done` |

原因：B0 的 `cancel_turn()` 只在 `_turn_id is not None` 时发帧；而 `_iter_turn_chunks` 在收到 early `end_turn` 时已经返回并执行了 `end_turn()`，`_turn_id` 被清空。**用户按下的停止因此变成 no-op，agent 继续跑满 53.6s 并落盘。**

注意口径：此时客户端已不显示 busy，因此**不满足 S3 的「按停止后 60s 无收尾」字面签名**；但它正是 S3 的上游成因——用户以为停了、实际没停，且客户端没有可用的 cancel 通道。

这修正了计划对 S3 的归因：不是「B0 没有本地 abort，所以 agent 沉默时停止必然无效」，而是「提前结算让客户端误以为轮次已结束，连 `session/cancel` 都不会发」。

2.5.0 的 E2 那一轮，追问比通知轮结束晚 **2ms**，落在窗口外，因此正常执行 50.2s；这也再次说明交错边界只有毫秒级。

## 5. 对计划三个问题的回答

- **Q1：全裸基线 + 2.5.0，原始「长任务后无响应」是否复现？**
  **否。** B 场景两次 240s 前台长任务后正常收尾（490s）。原始 S1 未复现。
- **Q2：若复现，帧证据是否证明上游没有回 `session/prompt` response？**
  本次复现的是 S2 而非 S1。帧证据证明上游**回了** response，但回的是**提前的空 `end_turn`**（9–10ms、0 正文、0 工具帧），真实执行发生在其后的不可见轮次。因此不能把原始症状归因于「上游不回包」；可归因的是「上游在通知轮边界提前结算」。
- **Q3：若不复现，是场景未触发，还是 2.5.0 改变了触发条件？**
  B 场景本身不产生交错窗口，未触发不等于上游已修。C2 在 2.5.0 上 3/3 复现，说明 **2.5.0 没有改变触发条件**；触发条件是「通知轮活跃期收到 prompt」，与版本无关。

## 6. 对既有判断的修正

### 6.1 「退到 2.5.0 可规避」不成立（至少对本签名）

2.5.0 与 2.7.2 在同样的交错窗口内表现一致：提前空 end_turn、隐藏执行、客户端零帧。2.5.0 只是通知轮更短或更长地改变了窗口出现的概率，不是消除了缺陷。

**可以保留的说法**：2.5.0 不含 #4630，触发率可能不同；**不能再说的说法**：2.5.0 是更安全的规避版本。

### 6.2 「2.6 #4630 是触发率拐点」未获支持

本实验两版通知轮时长同量级，交错窗口内同样 100% 中招。样本量小（每版 3 次），不足以证明「完全没有拐点」，但足以否定「2.5.0 不触发、2.6 才触发」这一强形式。

### 6.3 与原始症状的关系

原始症状是「长任务后会话无响应」。本次没有复现 S1，但复现了同一族缺陷的另一种表现：**用户看到「完成」（且回复为空），实际工作还在后台跑**。两者共享同一个结算边界；若隐藏轮与下一次 prompt 再次交错，理论上可以演化为「新 prompt 被吞/永远等不到自己的 response」，但本实验未构造出该组合（见 §8）。

3. 未做 2.6.0/2.6.3 的同口径对照，不能给出完整触发率曲线；
4. 每版 C2 仅 3 次，统计置信度有限；结论依赖机制一致性（±1ms 相关性）而非大样本；
5. 未验证 GUI 权限模式为「询问」时，end_turn 后的权限请求会以什么形态呈现（本次 auto-allow）；
6. 未审查上游是否在其它边界（cron、reminder、子代理）复用同一结算路径。

## 9. 建议

| 编号 | 优先级 | 建议 | 理由 |
|:---|:---|:---|:---|
| P0-1 | 高 | 停止把「通知轮活跃期收到的 prompt」立即结算；无 prompt driver 时应挂起结算，等真实轮次开始/结束再回 response | 本次根因；客户端无法补救 |
| P0-2 | 高 | 保留并强化客户端「response 后仍有权限请求/工具活动」的观测：记 WARNING、标轮次可疑，不要静默自动允许；该信号同时可作为隐藏轮 pending 的判定依据 | 当前 auto-allow 会把隐藏执行变成「成功」，掩盖证据；E2 的权限帧是唯一迟到信号 |
| P0-3 | 高 | 保留现有终态确认/待发闸门，但修正 `trigger` 条件必填与 `unknown` 无出口（既有审计 P0-1/P0-2） | 与本缺陷叠加时，客户端会把可诊断失败放大成静默挂死 |
| P1-1 | 中 | 停止路径需感知「提前结算后的隐藏轮」：response 后若仍收到同会话的 permission/工具帧，应重新置 pending 并允许 cancel；否则按 `session/close` 显式兜底 | E2 已证明此时客户端连 cancel 都不发 |
| P1-2 | 中 | 上游修复验收必须覆盖「通知轮活跃期发 prompt」，不能只看普通多轮与前台停止 | 本实验证明触发条件隐蔽且与版本无关 |
| P2 | — | 不再以「2.5.0 是否复现」作为退版依据；版本选择回到稳定性/功能维度 | 2.5.0 同样中招 |
