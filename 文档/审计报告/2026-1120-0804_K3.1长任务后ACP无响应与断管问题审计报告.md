## 1. 审计结论

本次事故可以概括为两条相继发生的故障：

1. **K3.1 的最后一次模型请求没有留下响应或错误记录，轮次失去正常推进能力。**
2. **随后 ACP 通道断开，用户输入的“继续”未进入 Kimi 事件流，IDE 最终记录到断管。**

这不是“上下文使用到 15% 后触发上限”。事故时上下文约为 161,077 / 1,048,576 tokens，即 15.36%；日志没有上下文溢出、自动压缩失败、鉴权失败、限流或 HTTP 状态错误。15% 只是事故发生时徽章所显示的占用量。

IDE 主进程没有崩溃，冻结版进程在事故后仍存在并继续写日志。因此，准确故障边界是**该标签的模型请求与 ACP 会话通道**，不能笼统描述为整个 IDE 进程退出。

现阶段能够确认 IDE 侧存在三项重要缺陷：

- 子进程 stderr 被直接丢弃，首次失败缺少关键诊断面；
- 连接死亡时会话 ID 被清空，后续只能新建会话，缺少原上下文恢复路径；
- 看门狗虽然能中止停滞轮次，但中止后的下一次发送没有保证使用健康连接。

首次模型请求为何没有返回，仍不能仅凭现有日志归因于模型服务端、网络或 Kimi CLI。任何更具体的单一根因说法都属于推测。

## 4. 逐项审计发现

### F1 高：ACP stderr 被丢弃，首次失败无法完整取证

`src/ide/llm/providers/acp.py` 启动 agent 时使用 `stderr=subprocess.DEVNULL`。Kimi 官方 ACP 文档明确说明：stdin/stdout 用于 JSON-RPC，日志写 stderr 及诊断日志。

因此当前实现恰好丢弃了协议外的重要诊断通道。其直接后果是：

- 无法判断 Kimi CLI 是否打印过网络、流式响应、内部异常或取消错误；
- IDE 日志只能看到后续写断管，看不到最初为何停滞；
- 开发态与冻结态出现同类事故时，排查只能依赖不完整的会话日志。

**整改要求**：stderr 改为持续排空的 reader，并使用有界缓冲；异常时输出脱敏、截断的必要尾部。不能只改成 `stderr=PIPE` 而无人读取，否则可能因管道写满引入新的停滞。

### F2 高：连接死亡时丢弃会话 ID，缺少原上下文恢复路径

`src/ide/llm/providers/kimi_acp.py` 在轮次内收到 `dead` 时清空 `_session_id`。后续 `_ensure_session()` 虽然可以重建进程，但只能进入 `session/new`。

这会造成两个用户可见后果：

- 新进程不等于原会话恢复，模型上下文可能被迫放弃；
- 用户为了继续任务只能新建会话，与本次事故描述一致。

Kimi 当前官方能力目录声明支持 `session/resume`，可在不重放历史的情况下重连既有会话。项目尚未使用该能力。

**整改要求**：连接死亡与清除会话身份解耦；保留原会话 ID 和必要创建参数，在下一次手动发送时使用 `session/resume`。不得静默退回新空会话。

### F3 高：看门狗解决“能停止”，尚未解决“停止后能健康继续”

既有 `2026-1118-1115_IDE长任务后会话无响应修复落地计划.md` 已实现：

- `abort_turn()` 本地解封；
- 无帧看门狗自动停止；
- 停止后 busy 解除、待发取消。

这些能力仍然必要，但它们只保证当前等待能够结束。若 agent 进程或会话状态已经卡死，下一次发送仍可能复用同一可疑连接，或者进入新空会话。

**整改要求**：看门狗停滞与普通手动停止分流。看门狗停滞后，下一次手动发送必须重建连接并恢复原会话；普通手动停止不强制重建。

### F4 高：写失败处理分散，断管未必及时转化为统一连接失效

`request()`、`begin_turn()`、`cancel_turn()` 和反向 RPC 应答各自处理写入异常。`terminal/wait_for_exit` 完成应答路径可以只记录 `BrokenPipeError`，没有统一的连接健康状态收口。

这会降低后续状态判断的一致性：某些路径认为连接已死，其他路径仍可能保留旧状态并尝试写入。

**整改要求**：所有写路径共享幂等失效处理，唤醒 pending、轮次 consumer 和 terminal wait；记录失败方法、请求 ID、连接代次及退出码。失效函数不得形成 `_write_lock` 重入死锁。

### F5 中：缺少“恢复失败不得发送”的显式保护

如果未来仅简单加入自动重连，可能出现更隐蔽的问题：恢复失败却退化为新会话，随后把用户 prompt 发给没有原上下文的 agent；或者自动重发中断 prompt，重复执行工具。

**整改要求**：`resume` 不支持、超时或失败时，本轮 prompt 发送次数必须为零，新建空会话次数也必须为零。保留草稿并让用户明确选择下一步。

### F6 中：事故提示没有把“原请求是否已执行”与“如何继续”讲清楚

中断前模型可能已经执行部分工具。若界面只显示“可重新发送”，用户无法判断重发是否安全，也不知道原上下文能否恢复。

**整改要求**：故障卡片明确说明：

- 中断请求不会自动重发；
- 已显示的工具结果需要用户核对；
- 下一次手动发送将尝试恢复原会话；
- 恢复失败不会静默创建新会话。

## 5. 既有防护评估

| 既有机制 | 当前作用 | 本次缺口 |
|---|---|---|
| `session/cancel` | 请求 agent 优雅取消 | agent 卡死时不能单独保证解封 |
| `abort_turn()` | 本地解除轮次等待 | 不负责重建死亡连接 |
| 无帧看门狗 | 长时间沉默后自动停止 | 停止后未标记下轮需要恢复 |
| 失败取消排队待发 | 防止连续失败烧 token、减少重复执行 | 必须保留，不得被自动恢复绕过 |
| 进程死亡后重新 spawn | 能创建新 agent 进程 | 当前只走新会话，未恢复原 ID |
| Kimi wire 日志 | 提供会话事件和用量证据 | 不能替代被丢弃的 stderr，也不能证明未记录的请求已送达 |

结论是：既有修复方向正确，不需要推倒重来；本轮应在其下方补全**连接健康状态机和原会话恢复**。

## 6. 根因分层与责任边界

### 6.1 已确认的直接故障

- 最后一次模型请求未完成；
- 后续用户 prompt 未进入 Kimi 事件流；
- ACP 最终断管；
- IDE 缺少原会话恢复与完整诊断。

### 6.2 已排除的常见解释

- **不是 15% 上下文硬上限**：占用远低于模型窗口，且无对应错误。
- **不是整个 IDE 主进程崩溃**：事故后进程仍存在并继续记录日志。
- **不是“继续”已被模型收到但模型不答**：事件流没有对应 `turn.prompt`。
- **不是已有证据证明的鉴权或限流**：日志没有相关错误码或错误文本。

### 6.3 仍未锁定的上游根因

以下假设均保留，但当前没有足够证据排序：

1. 模型服务端或网络请求停滞；
2. Kimi CLI 在特定长任务、后台任务通知或取消竞态中停滞；
3. ACP 子进程提前退出或内部状态损坏；
4. IDE 与 agent 在反向 terminal RPC、后台任务通知之间存在特定时序问题。

新增 stderr 和生命周期日志后，应按真实请求 ID、退出码和时序重新归类，不能提前选择其中一个作为结论。

## 7. 影响与风险评估

### 7.1 可用性

长任务中断后无法在原会话继续，用户可能误以为模型或账户失效。反复发送、停止或重启 IDE 都缺乏明确状态指引。

### 7.2 上下文连续性

当前重建进程只走新会话，可能迫使长任务丢失模型上下文。对本类长任务而言，这是主要损失之一。

### 7.3 工具副作用

如果简单以自动重试解决，中断前已经执行的写文件、终端命令、提交或其他操作可能重复发生。恢复方案必须把“恢复原会话”与“重放原请求”严格分开。

### 7.4 诊断与隐私

完全不记录 stderr 会阻碍排障；无界记录完整 stderr 又可能引入隐私和磁盘风险。正确方向是持续排空、有界缓冲、异常触发、脱敏输出。

## 8. 建议的恢复与防范方案

按 `2026-1120-0804_ACP会话断管恢复与诊断加固落地计划.md` 实施，优先级如下：

1. **P0：原会话恢复**——保留会话 ID，使用 `session/resume`，下一次手动发送时恢复。
2. **P0：禁止自动重放**——原中断 prompt 不自动重试，恢复失败不发送、不新建空会话。
3. **P0：统一连接失效**——所有写路径、EOF 和进程退出进入同一幂等状态收口。
4. **P0：诊断补盲**——stderr 持续排空、有界缓冲、异常落日志，记录连接代次和请求 ID。
5. **P1：看门狗分流**——普通停止不重建；看门狗停滞后下轮恢复。
6. **P1：真实与冻结态验收**——真实 CLI 验证同 ID 恢复，AppImage 验证断管恢复和日志完整性。
7. **P2：上游追查**——待新证据出现后，再针对 Kimi CLI、网络或服务端另案处理。

## 9. 验收审计清单

实施后审计不得只检查“能重新回复”，还必须同时满足：

- 恢复前后 `sessionId` 相同；
- 原中断 prompt 自动重放次数为零；
- 新手动 prompt 只发送一次；
- `resume` 失败时 prompt 与新空会话均为零；
- 普通手动停止不重建连接；
- 看门狗停滞后下一次手动发送会恢复；
- 旧连接迟到事件不影响新连接；
- 工具审批、终端 wait、子代理、用量和排队语义不回归；
- stderr 大数据量不阻塞、不无限占内存、不泄露凭证或完整 prompt；
- 自动化全量门禁通过；
- 真实 Kimi 与冻结版 AppImage 均完成端到端验证，未做项如实保留。

## 10. 最终结论

本次事故的核心不是模型上下文占用达到某个阈值，而是**请求停滞后，ACP 连接健康状态、原会话恢复和诊断取证未能形成闭环**。

短期正确做法是停止盲目重发并恢复连接；长期正确做法不是简单增加自动重试，而是建立以下完整链路：

**发现异常 → 安全中止 → 保留原会话身份 → 用户确认后的手动恢复 → `session/resume` → 仅发送新指令 → 全程有界可诊断。**

首次无响应的上游根因保持未决，直至新的 stderr、请求 ID、退出码和协议时序证据能够支持进一步归因。
