## 4. 上游缺陷：2.7.2 复现确认与新增表现

12:25 审计报告在 2.7.1 上定位了四类上游缺陷（U1–U4）。本次在 2.7.2 上的实测结论：

### 4.1 已复现（与 2.7.1 相同）

| 缺陷 | 2.7.1 证据（12:25 报告） | 2.7.2 证据（本次） |
|:---|:---|:---|
| steering 使 `tool_use` 中的用户轮提前 `end_turn` | 12:03:53 steering → 12:03:57.485 `step.end finishReason=tool_use` → .486 `turn.ended` → .489 ACP `end_turn` | 13:54:33.579 steering → 13:54:40.368 `turn.ended completed`（模型后续 74 秒工作落入通知轮）→ .374 ACP `end_turn` |
| 排队 prompt 先回 `end_turn`、后执行或永远不执行 | 追问 8ms 空 `end_turn`，16 分钟后才执行 | 草稿 `"s"` 50 秒后空 `end_turn`，wire 无任何 `turn.prompt`（比 2.7.1 更糟：彻底不执行） |
| 通知轮无 ACP 轮次级句柄、无自己的响应 | turn1 无请求 ID，客户端不可见 | 两轮通知轮均无 ACP 响应（第一轮 IDE 至今无 requestId=6，第二轮通知轮结束前后无对应响应） |

### 4.2 新增表现一：执行中轮次收到提前 `end_turn`（无第二 prompt）

13:59:31.090 IDE 收到 `requestId=7` 的 `end_turn`，而 turn2 当时正在流式输出（step 2.8，13:58:59.257–13:59:44.083），wire 无 `turn.ended`。两种候选解释均构成契约违反：

- **解释 A**：该响应属于 turn2 的请求，CLI 在轮次执行中途发出终态——"响应不得早于执行完成"被违反，且没有任何触发条件（无 steering、无新 prompt 进入）。
- **解释 B**：CLI 在 13:59:31 收到了新的输入（`state.json` 同 instant 写入），未执行即以 7ms 返回 `end_turn`——与 `"s"` 同型的 prompt 吞没，且连 `lastPrompt` 都未更新。

两种解释下，客户端都收到一个无法与任何真实终态对应的 `end_turn`，并据此播报完成、解除 busy。该现象 1/1 命中，需裸 ACP 探针补测确认触发条件。

### 4.3 新增表现二：wire 格式漂移，`step.end` 消失

2.7.1 的 wire 含 `step.begin`/`step.end`（含 `finishReason`）/`content.part`；2.7.2 的 wire 全部不再出现这些记录（两轮事故会话 260+ 行记录中类型全集经枚举确认）。`finishReason=tool_use` 这一客户端可用的关键判据不复存在：

- 无法区分"模型自然收尾"与"CLI 截断"（卡死轮用户轮 6 秒关闭即因此无法定责到行）；
- 任何依赖 `step.end` 的客户端检测逻辑（包括已移除的 KimiTurnTracker 的 2.7.1 版本口径）在 2.7.2 上必然失明；
- 12:25 报告 §9.4 建议抓取的证据清单需要随版本更新。

这是对客户端可见格式的破坏性变更，上游应在 changelog 中声明，并提供替代判据（如 `turn.ended` 携带最后一步 `finishReason`）。

## 5. 客户端侧缺陷与放大链

### 5.1 假完成播报复发（已证）

今天 13:54:40.789、13:55:34.443、13:59:34.097 三次"任务完成"播报，后两次对应幽灵/提前响应，第一次对应仍有 74 秒余量工作的用户轮。`_classify_stop_reason` 对 `end_turn` 直接返回正常终态（`src/ide/llm/providers/kimi/provider.py`），无任何旁证核对。

### 5.2 假完成 → 自动待发 → prompt 被吞（已证）

假完成 #1 解除 busy 后面板自动发送了输入框待发草稿 `"s"`。该 prompt 被 CLI 吞没（未执行、返回空 `end_turn`），用户侧表现为：草稿消失、无回答、历史里多一条空轮。这正是 `2026-1120-1528_ACP后台通知轮次失配与编辑卡片假完成修复落地计划.md` §D6 明确禁止的"自动待发进入仍处于内部通知轮次的 agent"，在防护移除后原样复发。

### 5.3 卡死（假设，待复现定案）

已证事实：

- 卡死发生在通知轮结束（13:44:02）之后、无任何日志/异常/看门狗记录；
- 通知轮全程无 ACP 响应，其工具活动帧以 `session/update` 形态到达客户端时，IDE 侧已没有活跃轮次（worker 已于 13:41:53 收尾）；
- `85cf8aa` 已停用挂起看门狗（30s tick + 自动中断），无任何超时兜底能打破卡死。

工作假设（按可能性排序，均待 `.temp/` 复现 + 栈转储验证）：

1. **孤儿帧处理死锁**：通知轮的 update/response 帧到达无活跃轮次的连接层或面板，路由/渲染路径（如按请求 ID 匹配、向当前轮追加卡片）在无主状态下互斥等待，形成线程间死锁。
2. **无主响应 parked**：通知轮的响应（若 CLI 有发送）因无匹配请求被暂存，后续 `begin_turn` 或连接层清理与该暂存交互时阻塞。
3. **GUI 线程阻塞**：面板在 idle 状态下收到迟到工具帧，渲染路径等待一个永远不来的轮次上下文。

排除项：非断管（无 `connection_dead`/EOF/写失败记录）、非 CLI 崩溃（CLI 日志 13:44 后正常 idle）、非看门狗误杀（看门狗已停用）。
