## 1. 审计结论

**换根后的第二个 IDE 继承了第一个 IDE 所在的启动终端。**

更具体地说，`src/ide/gui/main_window.py` 的 `_spawn_window()` 原先直接调用 `subprocess.Popen(cmd)`，没有重定向 stdin、stdout、stderr，也没有创建独立会话。因此，打开工作区时创建的第二个 IDE 会继续使用第一个 IDE 从 Shell 继承的终端文件描述符和终端会话。

第一个 IDE 在新窗口探活成功后退出，启动 Shell 此时已经恢复并显示提示符；第二个 IDE 却仍在运行，并继续向这个终端写入 DSH、提示音、桌面通知和退出日志。最终形成以下用户可见现象：

1. Shell 提示符已经返回；
2. 第二个 IDE 的异步日志写在提示符之后，把提示符顶离当前光标行；
3. 第二个 IDE 退出时，Shell 不需要也不会因为该事件重新打印提示符；
4. 屏幕上只剩空白光标，看起来像是“关闭 IDE 后终端没有返回提示符”；
5. 实测此时 Shell 已能执行下一条命令，不是 ACP Agent 或 IDE 主进程仍在阻塞 Shell。

该问题属于原计划中的 **C 分支：IDE 与已知子进程均消失，终端仍无提示符，应检查终端启动/等待方式和外层进程关系**。本例进一步明确了具体机制：不是 Shell 还在等待，而是换根后第二个 IDE 的迟到输出破坏了已有提示符的显示。

## 2. 术语与进程边界

本文使用以下称呼，避免把两个 IDE 混为一个进程：

- **第一个 IDE / 父窗口 / 父 IDE**：用户在终端执行 `uv run main.py` 后首先启动的进程；无参启动时是空白窗口。
- **第二个 IDE / 子窗口 / 子 IDE**：用户在第一个窗口中选择“打开文件夹”后，由第一个 IDE 通过 `_spawn_window()` 创建的新进程；它绑定目标工作区并接替第一个窗口。
- **换根**：本项目中不是原进程内更换目录，而是“创建绑定新工作区根的新进程 → 探活 → 关闭旧进程”。
- **启动终端**：执行最初 `uv run main.py` 的交互 Shell 所在的终端或 PTY。
- **提示符已返回**：Shell 已打印提示符并恢复读取下一条命令；不能仅凭屏幕当前是否能看到提示符判断。

“第二个 IDE 继承启动终端”不表示第二个 IDE 是 Shell 的子进程。进程父子关系与文件描述符继承是不同概念。第二个 IDE 的创建者是第一个 IDE；它继承的是第一个 IDE 已持有的终端输入输出通道。

## 3. 正常换根链路

实际链路如下：

1. 用户执行 `uv run main.py`，启动第一个 IDE。
2. 无参启动按项目设计进入空白窗口。
3. 用户选择打开工作区，调用 `src/ide/gui/main_window.py` 的 `open_folder_here()`。
4. `open_folder_here()` 保存布局，并通过 `_spawn_window(folder)` 创建第二个 IDE。
5. 第一个 IDE 使用 `QTimer` 在探活窗口期后调用 `_close_after_spawn()`。
6. 第二个 IDE 存活时，第一个 IDE 关闭。
7. 启动 `uv run` 对应的等待链结束，Shell 打印提示符并恢复输入。
8. 第二个 IDE 继续存在，完成工作区加载和后续 AI 对话。
9. 用户关闭第二个 IDE；该进程退出，但这不是启动 Shell 正在等待的那个进程。

因此，“第一个 IDE 退出后返回提示符”和“第二个 IDE 退出后没有再次打印提示符”在进程模型上都是正常的。异常在于第二个 IDE 仍然能够向启动终端写日志。

## 6. 根因代码

换根、新建空白窗口、在新窗口打开文件夹和最近项目回放共用 `_spawn_window()`。原实现的关键代码为：

```python
# src/ide/gui/main_window.py
proc = subprocess.Popen(cmd)
```

没有显式配置时，子进程继承父进程的 stdin、stdout、stderr。由于第一个 IDE 本身从启动 Shell 继承了终端，第二个 IDE 也获得同一终端的通道。

同时，原实现没有使用 `start_new_session=True`。第二个 IDE 与第一个 IDE 因而仍处于同一终端会话及相应的进程组关系中，直到修复前都没有形成适合独立 GUI 生命周期的终端边界。

问题不是 `Popen` 本身错误，而是这里创建的是一个**有意比父进程活得更久的独立 GUI**，不能直接沿用短生命周期命令行子进程的终端继承策略。

## 7. 会造成什么后果

### 7.1 已实测确认的后果

#### 1. Shell 提示符被第二个 IDE 的日志覆盖或顶走

第一个 IDE 退出后，Shell 已打印提示符。第二个 IDE 后续写出的每一行日志都可能出现在提示符后或提示符所在行附近，使用户无法从屏幕上判断 Shell 是否已恢复。

这会造成明确的可用性故障：用户认为终端仍被 IDE 占用，可能反复等待或按 `Ctrl+C` 才获得一个重新绘制的提示符。

#### 2. 第二个 IDE 关闭后没有新的提示符，形成“退出悬挂”的假象

Shell 并未把第二个 IDE 作为自己当前等待的前台任务，因此第二个 IDE 退出不会触发 Shell 再打印一次提示符。日志输出结束后，光标可能停在空白行，看起来像进程尚未退出。

实测证明此时输入命令仍可执行，所以该现象不能作为 Agent 泄漏或主进程未退出的证据。

#### 3. 不同进程、不同时间阶段的日志混在同一终端

第一个 IDE 的退出日志、Shell 提示符、第二个 IDE 的 Agent 与通知日志会交错出现。这会破坏日志的时间边界，使排障人员容易把第二个 IDE 的活动误归到第一个 IDE 的启动命令等待阶段。

本次初期诊断就曾因日志集中在同一终端而把注意力放在 ACP 退出上；完整时间线和双 PID 才揭示真实进程关系。

#### 4. 多个长寿命 GUI 窗口可能交叉写同一终端

`_spawn_window()` 同时服务新建窗口和最近项目等入口。只要这些窗口由同一终端启动链派生，它们就可能共享输出通道。日志可能按调度时序交错，降低可读性并增加归因难度。

这是由共用实现直接决定的影响面；本次没有构造多窗口混写样本，不把它列为已观测事故。

### 7.2 条件性风险与机制推论

以下后果由终端继承机制产生，但本次没有逐项触发，应与已实测后果区分。

#### 1. 子 GUI 或其组件可能读取、消费 Shell 输入

stdin 被继承意味着第二个 IDE 及其派生组件在主动读取标准输入时，可能与启动 Shell 竞争输入。当前 IDE 主流程没有控制台读取行为，本次也未观察到输入被吃掉，因此这是需要隔离的潜在风险，不是已发生事实。

#### 2. 终端信号可能影响多个 IDE 进程

没有独立会话时，父子 IDE 保持相同终端会话及相应进程组关系。在第一个 IDE 仍是前台任务的阶段，终端生成的 `SIGINT`、`SIGHUP` 等可能同时影响两个进程。

第一个 IDE 退出、Shell 重新取得前台状态后，第二个 IDE 是否收到特定信号取决于当时的进程组和终端前台设置，不能笼统宣称每次 `Ctrl+C` 都会终止第二个 IDE。修复使用独立会话，消除了这类不必要的终端生命周期耦合。

#### 3. 启动终端关闭或断开会传导到第二个 IDE

第二个 IDE 若继续向已失效的终端写 stdout/stderr，可能遇到断管或写入错误。GUI 的正常日志已有文件通道，终端继承只会增加额外的故障面。

本次没有执行“先关闭启动终端、再操作第二个 IDE”的试验，因此不宣称已发生具体崩溃。

#### 4. 外层日志收集器或包装程序可能延迟看到 EOF

当 stdout/stderr 不是终端，而是被构建工具、测试工具或其他包装程序用管道捕获时，父 IDE 退出并不意味着管道写端全部关闭。第二个 IDE 继续持有写端时，读取方可能一直等不到 EOF，直到第二个 IDE 也退出。

这与交互 Shell 的提示符机制不同，但同源于文件描述符继承，会造成自动化工具误判进程未结束或日志流未结束。

#### 5. 诱发错误的修复方向

如果只看“最后一条是 atexit 日志”，容易继续调整 Agent、Worker 或 Python 析构，而忽略新窗口进程与终端的关系。本次实证表明，真正需要修复的是进程启动边界；ACP 最终回收等加固有价值，但不是该截图现象的直接根因。

## 8. 为什么此前的退出测试没有发现

前期测试覆盖了未对话、真实 DSH、PTY、`uv run`、生成中关闭、初始化中关闭和多标签，但仍然漏掉了本问题，原因有四点：

1. **直接使用工作区根启动**：测试进程一开始就绑定项目根，没有经历“空白窗口 → 打开文件夹 → 第二个进程”的换根链路。
2. **只观察最终进程是否存在**：主 PID 与 Agent PID 消失只能证明资源退出，不能证明终端显示正确。
3. **只检查最终提示符，没有在换根中途探针**：第一个 IDE 退出时提示符已经返回，第二个 IDE 的日志随后才覆盖它；只看最后画面无法还原该时序。
4. **把“没有可见提示符”等同于“Shell 不能输入”**：实际探针证明 Shell 早已恢复，二者必须分开验证。

因此，退出类测试必须同时覆盖进程状态、终端输出归属和真实命令可执行性。

## 9. 修复内容

`src/ide/gui/main_window.py` 的 `_spawn_window()` 现在统一使用：

```python
# src/ide/gui/main_window.py
proc = subprocess.Popen(
    cmd,
    stdin=subprocess.DEVNULL,
    stdout=subprocess.DEVNULL,
    stderr=subprocess.DEVNULL,
    start_new_session=True,
)
```

各参数的职责：

- `stdin=DEVNULL`：新 GUI 不再与启动 Shell 共享标准输入，避免输入竞争。
- `stdout=DEVNULL`、`stderr=DEVNULL`：新 GUI 不再向启动终端写迟到日志；正常日志仍由 `main.py` 的统一日志配置写入 `config/logs/zen-studio.log`。
- `start_new_session=True`：新 GUI 建立独立会话，切断不必要的终端信号与前台进程组耦合。

修复没有模拟 `Ctrl+C`、伪造提示符、强制 `os._exit()` 或按进程名杀进程，也没有改变一窗一根、换根探活和长驻 Agent 复用机制。

## 12. 后续验证原则

为防止同类问题再次出现，后续修改新窗口启动或退出逻辑时，应保留以下回归条件：

1. 从无参空白启动开始，真实经过换根双进程链路，而非只直接启动目标工作区。
2. 在第一个 IDE 退出后立即执行 Shell 探针，确认提示符对应的输入能力已经恢复。
3. 在第二个 IDE 活跃期间检查其日志是否出现在启动 PTY 中；预期为不出现。
4. 在第二个 IDE 退出后再次执行 Shell 探针，确认不依赖 `Ctrl+C`。
5. 分别核对两个 IDE PID 和本实例 Agent PID，不能只看最后一行日志。
6. 确认第二个 IDE 的日志仍存在于统一日志文件，避免把“终端干净”实现成“日志丢失”。
7. 若进程由管道捕获输出，还应检查父进程退出后的 EOF 与第二个 IDE 生命周期是否符合设计。

## 13. 最终结论

本次“AI 对话后关闭 IDE，终端不返回提示符”的直接原因已经确定为：**换根后的第二个 IDE 继承了启动终端，并在 Shell 已返回提示符后继续输出日志，造成提示符消失和退出悬挂的假象。**

Shell 实际并未等待第二个 IDE，ACP Agent 也已完成回收。正确修复边界是新窗口进程与启动终端的分离，而不是继续扩大 ACP 退出重构。该修复已经通过同链路修前/修后交互对照和全量自动化门禁。
