# 裸 API / CLI / ACP 三模式对比及多后端接入分析

> **日期**：2026-07-21
> **范围**：LLM 对接三种姿态（裸 API 直连 / CLI 单发 / ACP 长驻协议）的统一对比；评估模式分类对后续接入 open code / kilo code 等第三方 agent 的适用性
> **依据源码**：`llm/base.py`、`llm/__init__.py`、`llm/providers/kimi_cli.py`、`llm/providers/kimi_acp.py`
> **依据文档**：`llm/README.md`、`文档/修改记录/2026-0718-1445_KimiCLI后端接入实施计划.md`、`文档/修改记录/2026-0718-1455_移除APIKEY直连统一CLI后端实施计划.md`、`文档/修改记录/2026-0718-1555_KimiACP后端升级实施计划.md`
> **沿革**：本文前身 `2026-07-21-06_CLI模式与ACP模式区别及多后端接入分析.md`（CLI/ACP 二分对比）；本轮应需求方要求加入"裸 API"第三选项并更名，三模式统一对比为本文核心

---

## 1. 结论摘要

1. 三模式的本质分界在**上下文谁保管、怎么灌**与**agent 能力谁提供**：
   - **裸 API**：客户端持全量历史、每轮全量重发；无 agent 能力（纯文本对话）；
   - **CLI 模式**：CLI 侧磁盘持会话、每轮只发新消息 + `session_id`；agent 能力开箱即用；
   - **ACP 模式**：长驻进程会话对象持历史、协议内增量交互；agent 能力开箱即用且可审批。
2. **模型层三者完全等价**：LLM 推理天然无状态，历史永远全量重放进上下文窗口——区别只在**谁负责重放、经什么通道重放**。
3. 裸 API 已于 2026-07-18 被本项目移除（1455 计划），原因不是架构不支持，而是**零密钥安全策略**（代码库不存不读不输入任何 API KEY）；其历史教训仍是理解三模式权衡的必要参照。
4. 接入第三方 agent 时：**"单发 vs 长驻协议"的分类维度依然适用**，但"CLI/ACP"是 kimi 专有子命令名，不可硬套。承重墙是 `LanguageModel` Protocol + 注册表——三种模式均可实现该协议并存于注册表。

## 2. 三模式核心差异总表（重点）

| 维度 | 裸 API（直连 LLM 服务） | CLI 模式（`kimi-cli`，路线 A） | ACP 模式（`kimi-acp`，路线 C） |
|:---|:---|:---|:---|
| 对接姿态 | HTTPS 请求 → 远端推理服务 | 每轮 spawn `kimi -p` 短进程 | 长驻 `kimi acp` 进程 + ndjson JSON-RPC |
| 进程/连接模型 | 无本地进程；每轮一次 HTTP（SSE 流式响应） | 每轮冷启动短进程，答完即退 | 长驻单进程，会话即协议对象 |
| **历史谁保管** | **客户端**（调用方内存中的 messages 数组） | **CLI 侧磁盘**（会话存储，`session_id` 索引） | **长驻进程会话对象**（磁盘持久化 + `session/list` 可枚举） |
| **每轮发送内容** | **全量历史重发**（每次 POST 带完整 messages） | **仅新消息** + `-S session_id` | **仅新消息**（`session/prompt`，协议内寻址会话） |
| 凭证管理 | **调用方管 API KEY**（违反本项目零密钥原则） | CLI 自管（OAuth，存 `~/.kimi-code/`） | CLI 自管（同左） |
| agent 工具能力 | ❌ 无（纯文本对话；要工具需自建 tool-use loop） | ✅ 开箱即用（CLI 内建读写文件/执行命令） | ✅ 开箱即用（同左） |
| 工具审批 | 无概念（没有工具执行面） | ❌ 无（`-p` 固定 auto，静态 deny 兜底） | ✅ `session/request_permission` 反向请求 → UI 弹窗 |
| 流式粒度 | token 级（SSE） | 消息粒度（整段上屏） | **token 级**（`agent_message_chunk`） |
| 思维链可见性 | 取决于 API 是否暴露 reasoning 字段 | ❌ stream-json 不含 | ✅ `agent_thought_chunk` → reasoning 通道 |
| 文件读写语义 | 无 | agent 直写磁盘 | `fs/read_text_file` / `fs/write_text_file` 反向 RPC 可路由到编辑器缓冲区（备案 C4） |
| 会话浏览/恢复 | 客户端自行持久化 | `session_id` 续接（无枚举 UI） | `session/list` / `session/load` 原生语义（备案 C5） |
| 模型切换 | 请求参数指定 | 下次请求 `-m` 生效 | `session/set_config_option` 会话内即时生效 |
| 中断能力 | 断开 HTTP 连接 | 杀进程（`terminate`） | `session/cancel` 协议级中断 |
| 冷启动开销 | 无本地进程，仅网络往返 | **每轮进程冷启动** + 磁盘读会话 | 仅首轮启动，后续零冷启动 |
| 实现成本 | 低（HTTP 客户端） | 低（约百行，JSONL 解析） | 高（JSON-RPC 帧层 + 审批回环 + 进程生命周期） |
| 网络依赖 | **必须联网**到远端 API | 推理仍需网络，但调度在本机 | 同左 |

## 3. 上下文装载机制：传输层 vs 模型层（重点）

"每轮是否重读前文"须拆两层回答，三层统一结论如下：

### 3.1 模型层：三者完全等价

LLM 推理天然无状态。无论哪种模式，**每一轮推理都是把整段对话历史重新灌进上下文窗口重新计算**。所谓"长驻进程有记忆"是幻觉——ACP 的 session 对象同样只是替你把历史保管起来，推理时照样全量重放。三种模式在模型层**没有任何区别**。

### 3.2 传输/保管层：三者的真正分界

| | 裸 API | CLI 模式 | ACP 模式 |
|:---|:---|:---|:---|
| 历史存放位置 | 调用方内存（messages 数组） | CLI 磁盘会话存储 | 长驻进程内会话对象（落盘持久化） |
| 每轮线上流量 | 全量历史（O(n) 累积增长） | 新消息 + session_id（O(1)） | 新消息（O(1)，协议内寻址） |
| 谁负责"灌"进模型 | 你的代码（全量随请求发） | kimi 新进程从磁盘读出来灌 | 长驻进程会话对象灌 |
| 客户端重启后 | 内存历史丢失即失忆 | 会话仍在磁盘，`-S` 可续 | 会话仍在磁盘，`session/list` 可枚举恢复 |

判别窍门：**看进程跑完退不退出**（CLI 退 / ACP 不退），**看历史在哪边**（裸 API 在客户端 / 两种 CLI 模式在 agent 侧）。

## 4. 三模式优缺点对比（重点）

### 4.1 裸 API（直连 LLM 服务）

**优点**
- 实现最简单：一个 HTTP/SSE 客户端即可，无本地二进制依赖、无进程管理；
- token 级流式现成（SSE）；
- 不依赖任何本机 agent 安装，部署面最窄。

**缺点**
- **凭证入代码库**：API KEY 需存放/读取，违反本项目零密钥安全模型（1455 计划移除的直接原因）；
- **无 agent 能力**：模型只会说话不会动手——读写文件、执行命令须自建 tool-use loop + 权限审批体系，等于重造一个 agent CLI；
- **历史全量重发**：客户端必须完整保管 messages，长会话线上流量 O(n) 累积，且进程重启即失忆（除非自行持久化）；
- 能力上限受制于 API 暴露面（思维链、工具定义各厂商不一）。

### 4.2 CLI 模式（单发短进程）

**优点**
- **零密钥**：凭证 CLI 自管（OAuth），代码库不出现密钥；
- **agent 能力开箱即用**：工具执行、权限策略、会话持久化全由 CLI 负责；
- **客户端免管历史**：每轮只发新消息 + session_id，线上流量 O(1)；
- 实现成本低（约百行），与 worker/generator 架构同构。

**缺点**
- **每轮冷启动**：重新加载二进制 + 磁盘读会话，响应体感为"等待后整段出现"；
- 消息粒度流式（非 token 级），无思维链；
- **无审批回环**：`-p` 固定 auto 权限，agent 动作不可逐次确认（一刀切信任）；
- 无协议级中断（只能杀进程）、无会话枚举 UI。

### 4.3 ACP 模式（长驻协议服务）

**优点**
- 零密钥、agent 能力开箱即用（同 CLI 模式）；
- **token 级流式 + 思维链可见**（`agent_message_chunk` / `agent_thought_chunk`）；
- **审批回环**：`session/request_permission` 反向请求 → UI 弹窗逐次确认，权限从"一刀切 auto"细化到单工具单参数；
- **IDE 语义对齐潜力**：`fs/*` 反向 RPC 可路由到编辑器缓冲区与撤销栈（备案 C4）；
- 会话内即时切模型、协议级中断、崩溃自动重启、`session/list` 历史浏览；
- 长驻无冷启动，Zed/JetBrains 同款集成方式（开放标准协议）。

**缺点**
- **实现成本最高**：ndjson JSON-RPC 帧层、请求 id 配对、反向请求即时应答（不当则 agent 永久阻塞）、审批回环 UI、长驻进程生命周期管理（僵死/句柄泄漏/退出残留）；
- 长驻进程本身即运维面：需 atexit 纪律、崩溃检测与重启逻辑；
- 推理仍依赖网络（与 CLI 模式同为远端模型，本机只是调度壳）。

### 4.4 选型一句话

> 要"能说话"选裸 API（但交出密钥与动手能力）；要"能动手且省心"选 CLI（接受冷启动与一刀切权限）；要"能动手且可控、体验对齐 IDE"选 ACP（付出帧层与回环的实现成本）。本项目现状：裸 API 因零密钥原则移除，CLI 保底、ACP 主力。

## 5. 接入第三方 agent CLI（open code / kilo code）的适配性评估

### 5.1 分类维度仍然成立

"单发 vs 长驻协议"（及其上游的"裸 API 直连"）是与厂商无关的对接姿态分类。任何 agent 对外提供的对接方式几乎必落三类之一：

| 情况 | 该 agent 的对接方式 | 归类与实现蓝本 |
|:---|:---|:---|
| ① REST/SSE API | 远端 HTTP 推理服务 | 归裸 API 型；HTTP 客户端 provider（历史形态：`deepseek_api.py`，已移除） |
| ② 支持 ACP | 有 `acp` 子命令，说 agentclientprotocol | 归 ACP 型；复用 `KimiAcpLLM` 的 `_AcpConnection` 帧层（可抽象为 command 可配的 ACP 基类） |
| ③ 仅单发 | 只能 `xxx -p "..."` 一次性执行 | 归单发型；仿 `KimiCliLLM` 写 provider |
| ④ 自有协议 | MCP-style / 自定义 JSONL 长连接等 | **第四类**，需新增协议族；但 `LanguageModel` 接口层不变 |

### 5.2 "CLI/ACP"命名不可照搬

`kimi-cli` / `kimi-acp` 是 kimi 一家的两个子命令名。换一家 agent，子命令名与协议均可能不同。若按厂商×模式做笛卡尔积命名（`opencode-cli` / `opencode-acp` / `kilocode-cli` …），分类将爆炸且语义漂移。

### 5.3 架构承重墙：`LanguageModel` Protocol 与注册表

`llm/base.py` 已把协议差异抽象干净：

```python
class LanguageModel(Protocol):
    def chat(self, messages: list[Message]) -> Iterator[Chunk]: ...
    def cancel(self) -> None: ...
```

- 前端仅经 `get_llm("<名称>")` 消费，不感知后端是裸 API、单发还是长驻、说什么协议。
- **三种模式均曾/可实现该协议**：裸 API（DeepSeek，1455 计划前存在）、CLI（`kimi-cli`）、ACP（`kimi-acp`）——注册表天然支持三模式并存，移除裸 API 是安全策略决策而非架构限制。
- 新增 agent = 在 `llm/providers/` 下新建 `<名称>.py` 实现协议 + 在 `build_default_registry()` 中探测注册，**接口层零改动**。
- 1455 计划备案已预留此路径："Kilo Code CLI 接入：优先考察 ACP 兼容面"。

### 5.4 演进建议（命名层面，非必须）

接入第三家 agent 时，建议将分类从"按厂商"提升为"按协议姿态"：

- **方案甲**：注册键带协议族前缀，如 `"kimi:acp"`、`"opencode:one-shot"`、`"deepseek:api"`；
- **方案乙**：后端名仍按厂商，内部以"协议族/能力矩阵"字段标注（是否 token 流式、是否审批、是否 fs 反向 RPC、是否需密钥），UI 按能力而非按名字决定展示。

两方案均不触碰 `LanguageModel` Protocol——协议抽象层是承重墙，模式分类只是墙皮。

## 6. 风险与遗留项

| 项 | 说明 |
|:---|:---|
| 第三方 agent 的 ACP 兼容性未经实测 | 需以协议摸底脚本直连验证（参照 1555 计划 C1 的 `.temp/acp_probe.py` 方法） |
| 情况④（自有协议）出现时 | 需新增协议族，但帧层与 `Chunk` 映射模式可复用 |
| `AcpConnection` 当前与 kimi 命令耦合 | 若复用为通用 ACP 基类，需将 command/args 参数化（重构项，非本期） |
| 裸 API 复出可能 | 若未来引入远端模型兜底，须先解决密钥托管方案（不破零密钥原则，如系统密钥环），并重估 agent 能力缺口 |
