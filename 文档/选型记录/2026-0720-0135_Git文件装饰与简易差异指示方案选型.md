# Git 文件装饰与简易差异指示 方案选型

## 一、背景与约束

### 1.1 需求范围（已与需求方确认）

**做**：

1. **Git 文件装饰（File Decorations）**：文件树 / 标签页按 Git 状态变色——
   - `M` 已修改（Modified）→ 黄/橙色
   - `U` 未跟踪（Untracked）→ 绿色
   - `D` 已删除（Deleted）→ 红/灰色
   - 被 `.gitignore` 忽略的文件 → 变灰
2. **文件级差异统计（最简版 Diff Indicators）**：只显示文件相对 HEAD 的统计数字（如 `+12 -3`），展示位置为状态栏 / 标签页 tooltip，**编辑器内不画 gutter 色条，不做任何内嵌 diff 对比视图**。

**不做**：

- ❌ Git 提交树（DAG 泳道图）——已确认放弃，复杂度高、投入产出比低
- ❌ 行粒度 gutter 指示（哪些行被改过的编辑器内色条）——本期不做，保留为后续迭代方向
- ❌ 内嵌 diff 对比视图

### 1.2 约束

- 技术栈：Python 3.12 + PySide6（QWidget 体系），强制使用项目 `.venv`
- 现有依赖仅 4 个（ptyprocess / pygments / pyside6 / pyte），风格偏轻量
- 功能对标：VS Code 的 `git.decorations.enabled`（文件装饰）与文件级 `+/-` 统计

### 1.3 功能原理（各方案共用）

- 文件状态数据来源：`git status --porcelain=v1`（含 ignored 需加 `--ignored`）
- 差异统计数据来源：`git diff --numstat HEAD`（直接输出 `增加数 删除数 文件路径`，无需逐行解析）
- 两条命令即可支撑全部需求，不需要 lane 算法、不需要 diff 内容解析

## 二、候选方案

本选型包含两个决策维度：**维度一：Git 数据获取层**（方案 A / B / C）；**维度二：状态刷新机制**（方案 甲 / 乙 / 丙）。两个维度正交，最终实施为各维度选一个方案组合。

### 维度一：Git 数据获取层

#### 方案 A：直接调用系统 git CLI（subprocess）

用 Python 标准库 `subprocess` 调用系统 `git`，解析文本输出：

```bash
git status --porcelain=v1 --ignored    # 文件状态（M/U/D/ignored）
git diff --numstat HEAD                # 每文件 +增/-删 行数
```

**优点**：

- **零新增依赖**，纯 stdlib，与项目现有轻依赖风格完全一致
- 输出格式稳定（porcelain 是 git 官方承诺的机器可读接口，跨版本兼容）
- 语义与用户命令行行为完全一致（含 `.gitignore`、`.gitattributes` 处理），无行为偏差
- 参考代码可直接借鉴：Multi_Cli_Studio 的 Rust 端就是用同样方式（spawn + 解析），其 format 串与解析思路可翻译成 Python
- 未来扩展（分支名显示、stash 数量等）只是多加一条命令

**缺点**：

- 需手写输出解析（porcelain 的 rename 条目、带引号路径等边角情况需处理）
- 依赖系统安装 git，需做缺失检测与降级（无 git 时功能整体隐藏/禁用）
- 每次刷新产生进程开销（实测百文件级仓库单条命令 < 50ms，可忽略）

#### 方案 B：引入 GitPython 库

`pip install GitPython`，用其对象 API（`repo.index.diff`、`repo.untracked_files` 等）获取状态。

**优点**：

- Pythonic API，无需手写文本解析，代码量少
- 内部仍调用系统 git CLI，行为与方案 A 一致
- 后续若做提交历史列表等扩展功能，API 现成

**缺点**：

- **新增第三方依赖**（GitPython + 其依赖 gitdb/smmap），违背项目轻依赖风格
- 对本需求而言是杀鸡用牛刀：两个功能只需两条命令的输出，API 便利性体现不出来
- 同样依赖系统装有 git，未解决环境依赖问题

#### 方案 C：引入 pygit2（libgit2 绑定）

`pip install pygit2`，基于 libgit2 的 C 库直接读仓库，不调用 git 命令行。

**优点**：

- 不依赖系统安装 git（libgit2 内嵌），环境适应性最好
- 性能最好（无进程开销，直接读 .git 内部结构）

**缺点**：

- **带二进制扩展**，跨平台打包/分发复杂度高（Windows/macOS/Linux 各需对应 wheel），与项目纯 Python 风格冲突最大
- libgit2 与 git CLI 在部分边缘行为上存在差异（如某些 ignore 规则、attribute 处理）
- numstat 统计需自己对比 diff 计算，反而比方案 A 的直接输出更麻烦
- 对本需求严重过度设计

### 维度二：状态刷新机制

#### 方案 甲：事件驱动刷新（保存 + 焦点 + 手动）

触发时机：文件保存后、应用窗口重获焦点时、用户手动刷新。

**优点**：

- 实现最简单，与现有代码编辑器/主窗口事件体系直接挂钩
- 无后台开销，无轮询线程
- 刷新时机符合直觉（用户动作后状态才变）

**缺点**：

- **覆盖不了"外部变更"**：用户在终端里 `git checkout` / 其他进程改文件时，界面不会自动更新，需靠窗口焦点事件兜底（IDEA/VS Code 也是这个策略，体验可接受）
- 若项目内已有文件保存事件总线则成本极低，否则需补埋点

#### 方案 乙：定时轮询

后台 QTimer 每隔 N 秒（如 5s）执行一次 status 刷新。

**优点**：

- 实现极简，一个 QTimer 搞定
- 能覆盖外部变更

**缺点**：

- 无论有无变化都周期性 spawn 进程，空转浪费（虽小但不优雅）
- 轮询间隔是体验折衷：太短浪费、太长延迟感明显
- 与方案甲的事件触发并不互斥，但单独使用体验不如甲

#### 方案 丙：文件系统监听（watchdog 等）

监听工作区与 `.git` 目录变化（尤其 `.git/index`、`.git/HEAD`），变化即刷新。

**优点**：

- 最及时、最精确，外部 git 操作也能秒级感知
- VS Code 实际采用的就是此策略（监听 `.git` 目录）

**缺点**：

- 需新增 `watchdog` 依赖（或用 Qt 的 `QFileSystemWatcher`，但大目录树监听有平台数量限制与性能坑）
- `.git` 目录变更频繁（每次 status 本身也会触碰），需做去抖与过滤，实现复杂度在三者中最高
- 对本"最简版"需求而言过度设计

## 三、综合对比表

### 维度一：Git 数据获取层

| 维度 | 方案 A：系统 git CLI | 方案 B：GitPython | 方案 C：pygit2 |
|---|---|---|---|
| 新增依赖 | **无** | GitPython + gitdb/smmap | pygit2（含二进制） |
| 解析工作量 | 中（手写 porcelain/numstat 解析） | 低（API 现成） | 中高（numstat 需自算） |
| 依赖系统 git | 是 | 是 | **否** |
| 行为与 git CLI 一致性 | **完全一致** | 一致 | 有边缘差异 |
| 打包/分发复杂度 | 无变化 | 略增 | **显著增加** |
| 匹配本需求程度 | **刚好够用** | 过剩 | 严重过剩 |
| 综合推荐度 | ★★★★★ | ★★★ | ★ |

### 维度二：状态刷新机制

| 维度 | 方案 甲：事件驱动 | 方案 乙：定时轮询 | 方案 丙：文件监听 |
|---|---|---|---|
| 实现成本 | **低** | 低 | 高 |
| 外部变更感知 | 弱（靠焦点兜底） | 中（有轮询延迟） | **强** |
| 运行时开销 | **无** | 周期空转 | 监听开销+去抖 |

| 综合推荐度 | ★★★★★ | ★★★ | ★★ |

## 四、推荐结论与后续实施要点

### 推荐组合：**方案 A（系统 git CLI）+ 方案 甲（事件驱动刷新）**

理由：

1. 本需求只需两条 git 命令的输出，方案 A 刚好够用且零依赖；B/C 的 API 便利性和独立性优势在本需求中体现不出来，却要付出依赖与打包成本；
2. 事件驱动（保存 + 焦点 + 手动刷新）是 VS Code / IDEA 验证过的成熟策略，成本最低；外部变更的场景由"窗口重获焦点"事件兜底，体验可接受；
3. 该组合为后续迭代留有余地：数据层封装成独立模块后，未来若增加提交历史、行粒度 gutter 等功能，可平滑扩展或替换为 GitPython。

### 实施要点

1. **数据层**（建议位置 `core/git/` 或类似目录）：
   - `status()`：执行 `git status --porcelain=v1 --ignored`，返回 `{文件路径: 状态}` 映射
   - `numstat()`：执行 `git diff --numstat HEAD`，返回 `{文件路径: (新增行数, 删除行数)}` 映射
   - 解析注意：porcelain 的 rename 条目（`R  old -> new`）、带空格/引号路径、未跟踪目录折叠（`?? dir/`）
   - 环境检测：启动时检测 `git --version` 与当前目录是否仓库（`git rev-parse --is-inside-work-tree`），不满足则功能静默禁用
2. **UI 层**：
   - 文件树：在现有树控件的 `QStyledItemDelegate`（或 model 的 `ForegroundRole`）中按状态映射上色；忽略文件变灰建议同时降低不透明度
   - 标签页：tab 文本着色与 tooltip 显示 `+12 -3` 统计
   - 状态栏：显示当前文件统计数字
   - 颜色值应进主题配置（参考现有 `gui/theme.py`），不做硬编码
3. **刷新层**：主窗口 `focusInEvent`/窗口激活信号 + 编辑器保存信号 → 触发数据层刷新（建议加 300ms 去抖，避免连续保存时频繁 spawn）；刷新失败（如变基中途的仓库锁定）静默降级，不弹错误
4. **性能**：单线程同步执行两条命令即可（百文件级 < 50ms）；若实测卡顿再考虑 QThread/QThreadPool 异步化，预留接口不预留实现

### 后续迭代预留（本期不做）

- 行粒度 gutter 色条：数据层增加 `git diff -U0` hunk 头解析即可扩展
- 提交历史列表：数据层增加 `git log` 解析（参考 Multi_Cli_Studio 的 format 串）
- 外部变更秒级感知：刷新层升级为方案丙（监听 `.git/index`、`HEAD`）
