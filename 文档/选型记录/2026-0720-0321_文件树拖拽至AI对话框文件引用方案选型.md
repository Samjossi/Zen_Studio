# 文件树拖拽至 AI 对话框文件引用 方案选型

## 一、背景与约束

### 1.1 需求（需求方原话确认）

在文件树中拖拽某个文件（如 `readme.md`）到 AI 聊天输入框，输入框中出现 `@` + 该文件的**工作区相对路径**（如 `@docs/readme.md`），使 AI 明确知道用户引用的文件并纳入上下文。

### 1.2 本项目现状（已核实代码）

- 技术栈：Python 3.12 + PySide6（QWidget 体系），强制使用项目 `.venv`；现有依赖仅 4 个（ptyprocess / pygments / pyside6 / pyte），风格轻量
- 文件树：[`gui/panels/file_explorer/explorer.py`](gui/panels/file_explorer/explorer.py) — `QTreeView` + `QFileSystemModel` + 噪音过滤代理模型，支持多选（ExtendedSelection），目前**未启用任何拖拽**（Qt 默认拖拽未开启）
- 聊天输入框：[`gui/panels/chat/input.py`](gui/panels/chat/input.py) — `ChatInput(QTextEdit)`，纯文本（`setAcceptRichText(False)`），Enter 发送
- 发送链路：[`gui/panels/chat/panel.py`](gui/panels/chat/panel.py) — 输入文本原样进 `_history`，经 `ChatWorker` 发给 LLM 后端；**前端目前不做任何文件内容读取**
- LLM 后端：[`llm/providers/kimi_cli.py`](llm/providers/kimi_cli.py) 与 [`llm/providers/kimi_acp.py`](llm/providers/kimi_acp.py)，均走本机 agent CLI；消息为纯文本
- 主窗口装配：[`gui/main_window.py`](gui/main_window.py) — 左栏 ChatPanel、右栏 FileExplorer，二者目前唯一交互是 `file_opened` → 查看器

### 1.3 约束

- 零/少新增依赖，保持纯 Python 风格
- 文件树与聊天面板解耦（现状经由 MainWindow 信号连接，不互相 import）
- 若文件树后续支持"树内拖拽移动文件"（`QFileSystemModel` 读写场景常见需求），本功能的拖拽实现须与之共存不冲突

### 1.4 参考项目调研结论摘要

| 参考项目 | 技术栈 | 与本需求相关的实现 |
|---|---|---|
| `参考代码/Multi_Cli_Studio` | Tauri + React | **无拖拽**；文件树行内 "+" 按钮向输入框插入纯文本 `@相对路径`（目录带尾 `/`），发送时**原样透传给终端 CLI，由 CLI 自行解析 `@` 引用**，前端不读文件内容。另有键入 `@` 触发补全（正则 `/(?:^|\s)@([^\s@]*)$/` 定位 token） |
| `参考代码/theia-zen` | Theia（TS） | **有拖拽**：文件树 dragStart 设自定义 MIME `theia-editor-dnd`（换行分隔 URI），聊天框（Monaco）drop 端插入 `#file:相对路径` 短引用文本，同时把文件加入**独立 chip 上下文列表**；发送时 parser 扫描触发符 → resolver 读文件内容 → 以工具形式供 LLM 按需取用 |
| `参考代码/VS_Code_Python`（实为 PyGPT 源码） | **PySide6**，与本项目同栈 | **有拖拽**：`QTreeView` 子类 dragStart 把选中路径转 `QUrl` 同时设 `setUrls()` + `text/uri-list`；投放端用 **eventFilter 挂在控件及其 viewport()** 拦截 DragEnter/Drop（QAbstractScrollArea 必须过滤 viewport 的关键细节）；本地文件 URL 走附件管线而非插入文本。另有右键菜单"复制相对路径并插入输入框"，即本需求的非拖拽原型。**无 `@` 补全** |

三个项目恰好对应三种架构取舍：Multi_Cli_Studio = 纯文本透传；theia-zen = 短引用 + 结构化上下文 + 发送时解析；PyGPT = 同技术栈的 Qt 拖拽工程细节范本。

## 二、候选方案

本选型包含两个决策维度：**维度一：引用的呈现与消费架构**（方案 A / B / C，决定"拖进去之后是什么、发送时怎么处理"）；**维度二：Qt 拖拽工程实现**（方案 甲 / 乙，决定拖拽事件怎么写）。两个维度正交，最终实施为各维度选一个组合。

### 维度一：引用呈现与消费架构

#### 方案 A：纯文本 `@相对路径` 插入 + 原样透传（Multi_Cli_Studio 路线）

拖拽落点直接在 `ChatInput` 光标处插入纯文本 `@相对路径`（统一 `/` 分隔，目录带尾 `/`），发送时文本原样进历史、原样发给后端 CLI，**前端不读文件内容**，由 agent CLI 自行解析 `@` 引用（Multi_Cli_Studio 对 Claude Code 等 CLI 即如此）。

**优点**：

- **实现量最小**：只动文件树（启用拖出）与 ChatInput（落点插入）两个文件，发送链路零改动
- 输入框内所见即所发，无隐藏状态，用户可直接编辑/删除引用文本，心智成本最低
- 与现有纯文本历史机制（`ChatPanel._history`）完全兼容，多轮回话中引用自然延续
- 为后续"键入 `@` 触发补全"铺路：文本格式一致，补全只是另一个插入入口

**缺点**：

- ⚠️ **依赖后端 CLI 支持 `@` 引用解析**——kimi-cli 是否解析 `@路径` 需实测验证；若不支持，AI 看到的只是一段路径文字，引用失效（此时须降级到方案 B 的前端注入）
- ACP 后端无 `@` 约定，同样存在失效风险
- 无结构化记录，无法做"引用文件失效标红""chip 删除"等增强体验
- 大文件/多文件的 token 消耗完全交给 CLI 控制，前端无法干预

#### 方案 B：纯文本 `@相对路径` 插入 + 发送时前端解析注入

插入形式同方案 A（纯文本 `@路径`），但发送前前端用正则扫描文本中的 `@路径`，**读取文件内容拼接进发给 LLM 的消息**（屏幕上仍只显示 `@路径` 或附摘要）。

**优点**：

- 不依赖后端 CLI 的任何约定，两个后端（kimi-cli / kimi-acp）行为一致、确定可用
- 前端可控：可限制文件大小、跳过二进制、对超大文件截断，token 消耗可预期
- 插入/展示层与方案 A 完全相同，后续加 `@` 补全同样受益
- 发送时解析（而非拖拽时快照），引用的总是文件最新内容

**缺点**：

- 需在发送链路加一步解析-注入（改动 `ChatPanel._on_send`），且注入内容进不进 `_history` 需仔细设计（进则历史膨胀、多轮重复注入；不进则 AI 下轮"失忆"，需每轮重新解析注入——theia 的做法是每轮重新 resolve）
- 正则解析有边角情况：路径含空格需引号规则、用户手打的 `@` 非引用文本（如邮箱）会误匹配（可用"路径必须真实存在于工作区"过滤兜底）
- 与 CLI 自身的 `@` 解析可能重复（若 kimi-cli 也解析，则同一份内容注入两遍）——需按后端能力差异化处理

#### 方案 C：短引用文本 + 结构化 chip 上下文列表（theia-zen 路线）

拖拽后输入框插入短引用文本（如 `@相对路径`），同时在输入框上方渲染一个**chip 列表**（图标 + 文件名 + 删除按钮）作为结构化上下文；发送时以 chip 列表为准解析文件内容注入，文本中的短引用主要起展示作用。

**优点**：

- 体验最好：引用可视化管理、可单独删除、可校验失效（文件被删后 chip 标红，theia 的 `ContextFileValidationService` 即此）
- 文本与数据分离，解析不依赖正则猜文本，边角情况最少
- 图片等非文本文件可纳入同一框架（chip 存路径，发送时单独处理），扩展天花板最高

**缺点**：

- **实现量最大**：需新增 chip 容器控件（流式布局 + 自定义 QFrame）、引用注册表、文本-引用同步逻辑（用户手动删掉文本里的 `@路径` 时 chip 要不要联动？theia 的做法是不联动，但这本身是需要向用户解释的行为）
- 输入框区域布局改动大（chip 区挤占空间），与现有极简输入区风格冲突
- 对本需求"让 AI 知道所选文件"而言明显过度设计，且仍须回答问题 A/B 的"内容如何进 prompt"，只是把它做得更完备

### 维度二：Qt 拖拽工程实现

#### 方案 甲：QTreeView 启用原生拖出 + ChatInput 重写 dropEvent

文件树侧：`tree.setDragEnabled(True)` + 重写 `mimeData()`/`startDrag()`，把选中路径转 `QUrl.fromLocalFile` 设入 `QMimeData`（PyGPT 的做法：同时 `setUrls()` 与 `text/uri-list`，多选 `\r\n` 分隔，兼容性最好）。输入框侧：`ChatInput` 设 `setAcceptDrops(True)`，重写 `dragEnterEvent`（含本地文件 URL 才 accept）与 `dropEvent`（`os.path.relpath` 转相对路径 → 拼 `@` → 光标处 `insertPlainText`）。

**优点**：

- Qt 标准做法，代码直接、可读性好，全部改动集中在两个控件类内
- `text/uri-list` 是通用格式，天然兼容"从系统文件管理器拖文件进输入框"的附加场景
- 多选拖拽一次插入多个 `@路径` 零额外成本

**缺点**：

- 开启 `setDragEnabled` 后需处理与"树内拖拽移动"的关系：`QFileSystemModel` 配 `setReadOnly(False)` 时默认可拖入树内目录移动文件，本期若不做移动功能需显式屏蔽（`tree.setDropIndicatorShown(False)` + 树自身不接受 drop），避免用户误拖移动文件
- `QTextEdit` 是 `QAbstractScrollArea`，拖放事件落在其 `viewport()` 上——重写虚函数时 Qt 已处理好转发，通常无碍，但个别样式/代理组合下需实测验证

#### 方案 乙：独立 eventFilter 投放处理器（PyGPT 路线）

不重写控件虚函数，写一个独立 `QObject` 事件过滤器，同时安装在 `ChatInput` 及其 `viewport()` 上，拦截 `DragEnter/DragMove/Drop`：本地文件吞掉并插入 `@路径`，其余放行默认行为。

**优点**：

- 处理器与控件解耦，同一过滤器可复用到多个投放目标（未来终端、查看器也想收拖拽时直接复用）
- 不继承/修改现有控件类，对 `ChatInput` 零侵入（PyGPT 验证过的模式，含防重入一次性标志处理"eventFilter 吞掉后默认 insertFromMimeData 仍触发"的重复插入问题）

**缺点**：

- 间接一层，调试与阅读成本高于方案甲（事件流向不直观）
- 需引入 PyGPT 的防重入标志等防御性细节，实现比甲多约一倍代码
- 本项目只有一个投放目标，复用价值当前体现不出来

## 四、推荐结论与后续实施要点

### 推荐组合：**方案 B（纯文本插入 + 前端解析注入）+ 方案 甲（原生拖出 + 重写 drop）**

理由：

1. 本项目后端是 kimi-cli / kimi-acp 而非 Claude Code，其 `@` 解析能力未经证实；方案 A 把核心功能押在外部 CLI 的未验证行为上，风险不可控。方案 B 前端读文件注入，行为确定、两后端一致，成本仅比 A 多一个发送前解析步骤；
2. 方案 C 的 chip 体系对本需求过剩，可作为后续体验迭代方向（架构上 B 的解析管道可直接升级为 C 的 resolver，不浪费）；
3. 维度二当前只有一个投放目标，方案甲的直接改写比 eventFilter 的间接复用更划算；PyGPT 的工程细节（`text/uri-list` 兼容、viewport 注意点）在甲中同样适用，直接吸收即可。

**若实测确认 kimi-cli 完整支持 `@` 引用解析**，可降级为方案 A（跳过前端注入），进一步减负——建议实施第一步先做此验证（在终端手测 `kimi` CLI 对含 `@路径` 提示词的反应），再定 A/B。

### 实施要点

1. **拖拽源**（[`gui/panels/file_explorer/explorer.py`](gui/panels/file_explorer/explorer.py)）：
   - `tree.setDragEnabled(True)`，重写 `startDrag`/`mimeData`：选中路径 → `QUrl.fromLocalFile`，同时 `setUrls()` + 手写 `text/uri-list`（`\r\n` 分隔、末尾换行）
   - 屏蔽树内 drop（防误拖移动文件）：树自身不接受拖放
2. **投放端**（[`gui/panels/chat/input.py`](gui/panels/chat/input.py)）：
   - `dragEnterEvent`：仅当 `mimeData().hasUrls()` 且为本地文件时 `acceptProposedAction`
   - `dropEvent`：逐 URL → `os.path.relpath(path, 工作区根)` → 统一 `/` 分隔 → 目录加尾 `/` → 光标处 `insertPlainText("@路径 ")`（参考 Multi_Cli_Studio 的归一化规则：去首尾多余斜杠、`\`→`/`）
   - 工作区根路径来源：目前 FileExplorer 的 `root_dir` 即项目根，需经 MainWindow 注入 ChatPanel（保持面板间解耦，走构造参数或 setter）
3. **发送解析**（[`gui/panels/chat/panel.py`](gui/panels/chat/panel.py)，方案 B）：
   - 发送前正则扫描 `@路径` token（规则与 Multi_Cli_Studio 一致：行首或空白后的 `@` 起，到空白止；目录尾 `/` 展开为文件列表或提示不支持）
   - **存在性过滤**：仅当路径在工作区内真实存在才视为引用并读内容，否则原样保留文本（防邮箱等误匹配）
   - 注入策略建议：屏幕消息与 `_history` 只存用户原文（含 `@路径`）；发给 LLM 的 messages 中，用户消息改写为 `原文 + 附件段`（如 `---\n@docs/readme.md 的内容：\n<文件内容>`）；每轮发送时对当轮及历史中的 `@路径` 重新读取（保证内容最新），或仅解析当轮、历史轮靠历史消息中已有的注入文本（二选一，建议前者更一致，实现时定）
   - 防御：单文件大小上限（如 100KB 截断并标注）、二进制后缀跳过（png/pyc/zip 等）、编码错误 `errors="replace"`
4. **验证前置**：实施第 0 步先实测 kimi-cli 的 `@` 行为，决定 A/B 落点
5. **测试**：`测试文档_001.md` 等现有测试文件可作为拖拽对象手测；多选拖入、目录拖入、从系统文件管理器拖入三个场景需覆盖

### 后续迭代预留（本期不做）

- 键入 `@` 触发文件补全弹窗（`QCompleter` + 自定义模型；token 定位正则与插入格式均已就绪）
- chip 化上下文管理（方案 C，含失效校验、图片引用）
- 文件树内拖拽移动文件（与本功能拖拽源共存时区分 drop 目标：`event.source()` 判断内部/外部，PyGPT 有此模式）
- 右键菜单"复制 `@路径` 到输入框"（非拖拽入口，PyGPT 与 Multi_Cli_Studio 均有此等价物）
