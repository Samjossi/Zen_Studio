# AI 聊天图片粘贴与缩略图预览选型

## 1. 背景与目标

用户实测：当前 AI 对话框**无法粘贴图片**，Ctrl+V 粘贴截图无任何反应。需要的完整功能：

1. 在聊天输入框中**粘贴图片**（截图、复制的图片文件）；
2. 已附加的图片以**缩略图**形式列出；
3. **点击缩略图可看大图**；
4. 发送时图片随文字一起**发给 AI**（多模态）。

本文只做方案比对，不涉及具体实现。

## 2. 现状与约束（技术事实）

### 2.1 本程序现状（调研结论）

- **输入框**：`gui/panels/chat/input.py:17` `ChatInput(QTextEdit)`，`setAcceptRichText(False)`，**未重写 `insertFromMimeData`**——粘贴的图片数据被 Qt 默认行为直接丢弃，这就是「粘贴无反应」的病根。
- **拖放已有先例**：`input.py:89-129` 已重写 dragEnter/drop，但只识别本地文件 URL → 插入 `@工作区相对路径 ` 纯文本引用（后端 agent CLI 自行解析 @路径），不处理图片。
- **发送链路**：`ChatInput.send_requested(str)` → `ChatPanel._on_send`（`panel.py:498`）→ `ChatWorker`（QThread）→ `provider.chat()` → ACP `session/prompt`。
- **消息类型锁死纯文本**：`llm/base.py:6-10` `Message.content: str`；四个 ACP 后端（kimi / kilocode / opencode / reasonix）的 `session/prompt` 均只构造 `{"type": "text", "text": ...}` 单块。
- **协议层已就位**：ACP `session/prompt` 的 `prompt` 字段本就是 ContentBlock **数组**，协议支持 `{"type": "image", "data": base64, "mimeType": ...}`、`resource`、`resource_link` 等块类型——扩展无需改协议，只需三层数据模型（输入框 → Message → provider prompt 数组）逐层放开。
- **输出区**：`ChatOutput(QTextBrowser)`，用户消息是纯文本气泡卡（HTML 转义），Qt 富文本子集支持 `<img>`，已发送消息中的图片缩略图可以直接渲染。
- **Qt 绑定**：PySide6（≥6.11.1），Python ≥3.12。
- **大图预览已有先例**：中栏查看器有 `media_viewer.py`（图片文件预览），项目另有 `gui/popups.py` 弹窗体系。
- **临时文件约束**：AGENTS.md 规定临时文件必须放项目根目录内（`./.temp/`、`./tmp/`、`./cache/`），`.tmp/` 已有截图先例。
- **项目规范**：强制使用 `.venv` 的 Python。

### 2.2 关键未知（风险）

- **各 ACP agent 是否真的接受 image ContentBlock**：协议结构支持 ≠ 各家 agent CLI 实现支持。kilocode 后端即 opencode，其 `FilePart{type:"file", mediaType, url:data:...}` 明确支持图片；kimi / opencode / reasonix 的 ACP 模式对 image 块的支持程度需要实测验证（参考项目 Multi_Cli_Studio 的教训：它按 CLI 能力过滤，仅 codex / claude / gemini 放行图片附件）。**实施前需做一次四家后端的图片块实测（spike）。**
- 剪贴板图片在不同来源下形态不同：截图工具给 `QImage`（mime `image/*`）、文件管理器复制图片文件给 `text/uri-list`、浏览器复制图片可能给 `text/html` + URL——入口处理需覆盖多种形态。

### 2.3 参考项目实现摘要（调研结论）

| 项目 | 技术栈 | 图片入口 | 缩略图形态 | 大图预览 | 数据载体 | 发送结构 |
|---|---|---|---|---|---|---|
| **Multi_Cli_Studio** | Tauri+React | 粘贴 + 文件选择器（原生对话框） | 输入框上方 chip 行（缩略图+文件名+删除×） | `createPortal` 全屏 Lightbox（Esc/点遮罩关闭） | 粘贴=立即 data URL；选文件=路径推迟读盘 | 按后端分：OpenAI `image_url` / Anthropic `image.source.base64` / Gemini `{type:"image",mimeType,data}`；限 5 张 / 10MB / 按 CLI 能力过滤 |
| **kilocode-main** | VS Code 扩展 webview | 粘贴 + 拖放（含资源管理器 URI） | 输入框上方缩略图行 | 点击→写临时文件→调宿主 VS Code 图片预览编辑器 | 粘贴即转 data URL 常驻内存 | opencode `FilePart{type:"file", mediaType, url(data:...)}`，provider 差异交给 SDK |
| **theia-zen** | Theia（Monaco 输入框） | 粘贴（双路径+键绑定补丁）+ 拖放 + `#` 变量选择器 | 输入框上方上下文 chip（内嵌小图） | 无 lightbox；仅路径型图片可在编辑器打开原文件 | 粘贴=base64 存注册表，文本内插 `#imageContext:img_1` 短引用；拖入=路径引用发送时才读盘 | 自有 `ImageMessage{type:"image", image:{base64data, mimeType}}`，每 provider 手写映射 |
| **PyGPT**（参考代码里的 VS_Code_Python） | **PySide6/Qt** | 粘贴（`QImage`→先落盘成 PNG）+ 拖放 + 添加按钮 | 输入区旁**独立附件列表面板**（无内嵌缩略图） | 双击→系统打开文件 | **剪贴板图立即落盘**（`clipboard-时间戳.png`），之后一律按路径处理 | 发送时整文件 base64 → OpenAI `image_url` data URL |

**可借鉴要点**：
1. 粘贴入口的最小公共实现 = 过滤 mime `image/*` → 立即转 base64；文件选择器/拖入文件可推迟到发送时读盘。
2. 数据结构推荐 Multi_Cli_Studio 形态：`{kind, source(data URL/路径/URL), previewSource, mediaType, fileName}`——`source` 三态、发送时统一归一化。
3. 四个参考项目**都没有做尺寸压缩**，仅 Multi_Cli_Studio 做了数量/大小拒绝（5 张 / 10MB）。
4. PyGPT 的「剪贴板图先落盘」路线对 Qt 桌面应用最省事（QImage.save 一步到位，内存不囤 base64），但预览体验最弱。
5. 大图预览两条路线：自绘弹窗（Multi_Cli_Studio lightbox → 对应 Qt 的 QDialog）或复用宿主查看器（kilocode → 对应本项目中栏 `media_viewer`）。

## 3. 决策维度分解

本功能由 5 个相对正交的决策点组成，先分维度列选项，第 4 节再组合成端到端方案。

### 维度 1：图片入口方式（可多选）

- **1a 剪贴板粘贴**（必需）：重写 `ChatInput.insertFromMimeData`，拦截 `mimeData().hasImage()`（截图/QImage）与 `urls()` 中的图片文件。
- **1b 文件拖入**：扩展现有拖放分支——图片文件走附件，非图片文件维持 `@路径` 现状。
- **1c 文件选择器按钮**：输入区加「添加图片」按钮，原生 QFileDialog 多选。
- **1d 截图按钮**：调系统截图工具直接入附件（PyGPT 有先例；可后续迭代，非本期必需）。

### 维度 2：缩略图摆放形态

- **2a 输入框上方缩略图行**（Multi_Cli_Studio / kilocode 式）：输入区与输出区之间插入一条附件行，每个附件一个 chip：缩略图 + 文件名 + 删除×。有附件时才出现，无附件时隐藏（注意显隐不得引起布局跳动——可在粘贴时才插入、发送后移除）。
- **2b 输入框内嵌**（ QTextEdit 内 `QTextImageFormat`）：图片直接作为文档内嵌对象显示在光标处。观感最像「贴在输入框里」，但与纯文本 `@路径` 混排、删除/计数/发送拆分的逻辑复杂，QTextEdit 内嵌图片还会污染 `toPlainText()` 提取，不推荐。
- **2c 独立附件面板**（PyGPT 式）：输入区旁常驻 QListWidget 列表。左栏宽度有限，常驻面板挤压输入区，且与「随消息发送」的即时语义距离远，不推荐。

### 维度 3：大图预览方式

- **3a 自绘 QDialog 大图弹窗**（Multi_Cli_Studio lightbox 式）：模态/非模态对话框，QPixmap 等比缩放适配窗口，Esc/点击关闭，可缩放可拖动。体验最完整，不依赖中栏状态。
- **3b 复用中栏 `media_viewer`**（kilocode 式）：点击图片→在中栏查看器打开。复用现有组件、零新窗口；但中栏可能被用户用于看代码/文档，预览会顶掉当前查看内容，且粘贴型图片（无磁盘文件）需先落盘才能进 viewer。
- **3c 系统打开**（PyGPT 式）：调 OS 默认看图程序。跳出应用窗口，体验最割裂，仅作兜底。

### 维度 4：图片数据载体（内存 vs 落盘）

- **4a 全内存 base64**：粘贴即 `QImage→QByteArray→base64` 常驻内存，发送时直接入 ACP image 块。实现最简、无文件清理问题；大图（如 4K 截图）内存占用高，且历史消息回显也需持有一份。
- **4b 落盘 `./.tmp/`（或 `./.temp/`）+ 路径引用**：粘贴的 QImage 立即 `save()` 成 PNG（PyGPT 式），附件对象只存路径；发送时读盘编码 base64。内存友好、预览/调试可直接看文件、历史消息回显重读文件即可；需管理临时文件生命周期（发送后删/定期清理/保留最近 N 个），且要遵守 AGENTS.md 的项目内临时目录约束。
- **4c 混合**：粘贴型落盘（来源无路径）、文件选择/拖入型保留原路径（发送时才读盘）——即 Multi_Cli_Studio 的 `source` 三态。语义最正，实现复杂度略高。

### 维度 5：发送给后端的结构

- **5a ACP image ContentBlock**：`prompt` 数组追加 `{"type": "image", "data": base64, "mimeType": ...}`。协议原生、语义最正；**前提是 agent 端支持（见 2.2 风险）**。
- **5b ACP resource_link / @路径 文本透传**：图片落盘后把 `./.tmp/xxx.png` 以 `@路径` 引用（复用现有拖放链路）或 ACP `resource_link` 块发给 agent，由 agent 自己读图。IDE 侧零编码成本、无 base64 流量；但依赖 agent 的文件读取与视觉理解能力，且「图片进上下文」的时机由 agent 自行决定，不如 image 块直接。
- **5c 双轨**：默认 5a，按后端能力探测/配置回退 5b。最稳但实现面最大。

## 4. 端到端候选方案

### 方案 A：全内存 + 缩略图行 + QDialog 弹窗 + ACP image 块（kilocode 式）

组合：1a+1b → 2a → 3a → 4a → 5a（不支持 image 块的后端本期先禁用图片附件并提示）。

- **优点**：链路最短——粘贴即 base64，发送即入块，全程无文件 IO、无清理逻辑；缩略图行与 QDialog 弹窗是两个自包含新组件，不触碰中栏；体验与 kilocode / Multi_Cli_Studio 对齐，用户心智零迁移。
- **缺点**：大图全量常驻内存（粘贴多张 4K 截图时明显）；历史消息中的图片要么持 base64 要么丢失；不支持 image 块的后端只能整体禁用（除非加 5c 双轨）；无磁盘文件可排查「到底发了什么图」。

### 方案 B：落盘 + 缩略图行 + QDialog 弹窗 + ACP image 块（PyGPT 数据层 + Multi_Cli_Studio 表现层）

组合：1a+1b+1c → 2a → 3a → 4b/4c → 5a（不支持则提示，或后续迭代加 5c）。

- **优点**：数据层最健壮——粘贴即落盘 `./.tmp/`，内存只持缩略图 QPixmap 与路径；发送时读盘编码，天然支持「原图不变形」；调试时可肉眼检查 `./.tmp/` 里的实际图片；临时文件按「保留最近 N 个」策略清理（kilocode 预览目录先例）；历史消息回显重读文件，不占内存。
- **缺点**：比 A 多一层文件生命周期管理（清理策略、异常残留）；发送时同步读盘大文件有轻微延迟（可在 worker 线程内做）；同样受后端 image 块支持度制约。

### 方案 C：附件面板 + 系统打开（PyGPT 原样照搬）

组合：1a+1b+1c → 2c → 3c → 4b → 5a。

- **优点**：Qt 组件全现成（QListWidget + QDesktopServices），工作量最小。
- **缺点**：体验全面落后——无内嵌缩略图（列表项只有小图标/文件名）、看大图跳出应用；左栏宽度有限，常驻面板挤压输入区；与用户明确提出的「缩略图 + 点击看大图」诉求不匹配。**仅作完整性列出，不推荐。**

### 方案 D：最小可用版——落盘 + @路径透传（不改消息结构）

组合：1a → 粘贴的图片落盘 `./.tmp/` → 输入框插入 `@./.tmp/xxx.png` 文本（完全复用现有拖放链路）→ 5b。

- **优点**：改动面最小——只加 `insertFromMimeData` 里一个图片分支 + 落盘，输入框/Message/provider 三层数据结构**零改动**，四家后端立即全部「可用」（只要 agent 会读图）；可先解「能发图」的燃眉之急。
- **缺点**：**没有缩略图、没有点击看大图**——不满足用户核心诉求的一半；`@./.tmp/` 路径噪音污染输入文本与对话历史；图片是否真被 AI 看到不可控（取决于 agent 是否主动读）。**适合作为先行过渡版，不适合作为终态。**

## 6. 倾向性意见（待定夺）

**推荐方案 B 作为终态、方案 D 作为可选先行版**，理由：

1. **B 的数据层（4c 混合落盘）是唯一对所有后续演进都友好的选择**：历史消息回显、调试可查、内存安全、临时文件管理有 kilocode 与项目 `.tmp/` 双重先例；表现层（缩略图行 + QDialog 弹窗）与 A 相同，用户体验不打折。
2. **D 可在一个小迭代内先解「能发图」**（只动 `input.py` 一个文件），且其落盘与入口代码在升级 B 时全部复用，不存在返工。若用户希望尽快见到效果，可 D→B 两步走；若接受一次到位，直接 B。
3. **维度 3 大图预览推荐 3a QDialog 弹窗而非 3b 中栏 viewer**：预览是「确认我要发的图对不对」的瞬态动作，不应顶掉中栏正在查看的内容；QDialog 自包含、Esc 即关，与 `gui/popups.py` 现有弹窗体系一致。
4. **限制策略**建议对齐 Multi_Cli_Studio：单张 ≤10MB、单次 ≤5 张、超限时在附件行内给出拒绝提示；尺寸压缩四参考项目都没做，本期亦不做（后续如出现体积问题再议）。
5. **后端兼容是最大风险，建议实施前先做 spike**：用四家 ACP 后端各发一条「text + image 块」的 prompt，确认哪些后端真正能看图；不支持的后端在附件行/发送按钮处给出禁用提示（Multi_Cli_Studio 的能力过滤先例）。

A 适合「想最省事、接受内存代价」的取舍；C 不推荐；D 单独作为终态不满足诉求。
