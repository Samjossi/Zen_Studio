## 1. 背景与问题

### 1.1 现状与痛点

Zen Studio 双后端的权限现状：

| 后端 | 权限行为 | 问题 |
|:---|:---|:---|
| `kimi-cli`（`-p` 单发） | 固定 auto 权限，无审批面 | 一刀切放手，无中间态 |
| `kimi-acp`（长驻 JSON-RPC） | `session/request_permission` → `PermissionDialog` 三按钮（允许一次/始终允许/拒绝），180s 超时按拒绝兜底 | **"始终允许"不生效**：客户端按协议把 agent 给的 `approve_always` optionId 原样回传（1555 计划 C1 纪要：optionId 为 agent 原值，回应必须原样回传），但 **kimi agent 侧不做持久记忆**，下一次 Bash 调用照弹——审批弹窗沦为每轮必点的形式主义 |

痛点本质：**"始终允许"的语义决定权在 agent 侧，agent 不记忆，客户端就只能重复弹窗**。三家参考项目对此的共识解法是——**把"始终允许"的记忆与自动应答收到客户端侧**。

### 1.2 协议可见面约束（方案设计的硬边界）

依据 1555 计划 C1 纪要与 `PermissionParams` TypedDict，审批时刻客户端能拿到的匹配依据：

| 字段 | 审批时刻可见性 | 可用作匹配键 |
|:---|:---|:---|
| `toolCall.title`（工具名，如 Bash/Write） | ✅ 稳定 | ✅ **工具级匹配主键** |
| `toolCall.kind`（execute/edit/other） | ✅ 稳定 | ✅ 辅助键 |
| `toolCall.content`（可读描述，如 "Requesting approval to Running: ls \*.md"） | ✅ 渐进流式 | 🟡 命令级匹配只能解析此自然语言串，**脆弱** |
| `toolCall.rawInput`（结构化参数） | ❌ **批准后才出现**（`tool_call_update`） | ❌ 审批时刻不可用 |
| `options[].kind`（allow_once/allow_always/reject_once/reject_always） | ✅ | 应答时按 kind 选 optionId |

**推论**：白名单/黑名单的粒度在现有协议下**工具级（title+kind）是稳定解，命令级是脆弱解**（除非 kimi 后续版本在审批请求中携带 rawInput）。

### 1.3 约束

- 审批请求在 `_AcpConnection._reader` 线程到达，**自动应答路径必须零 GUI、零阻塞**（agent 等不到应答会永久挂起）；
- 持久化遵循项目双文件分工：偏好入 `config/settings.json`（`AppSettings` TypedDict 扩展），会话级覆盖留内存；
- `kimi-cli` 后端无审批回环，客户端规则引擎管不到它（它永远放手）；如需约束只能换启动参数（kimi CLI 权限模式参数未验证，列摸底项）；
- kimi ACP 官方能力矩阵含 `session/set_mode`（stable，1555 C1 纪要），模式值清单未知，列摸底项。

## 2. 参考项目实现调研

### 2.1 Multi_Cli_Studio（Tauri/Rust + React，统一对接 codex/claude/gemini 三套 CLI）

权限管理为**四层机制**，代码位于 `src-tauri/src/main.rs` / `automation.rs` / `acp.rs` 与 `src/lib/store.ts`：

**① 会话级权限模式（per CLI，运行时可切）**

每家 CLI 映射到其原生权限/沙箱模式，用户经 `/permissions` slash 命令切换，按 CLI 存于会话（sqlite transport session 持久化）：

| CLI | 可选模式 |
|:---|:---|
| claude | `default` / `acceptEdits`（自动批准编辑）/ `bypassPermissions`（全部放行）/ `plan`（只读规划） |
| gemini | `default` / `auto_edit`（自动批准编辑）/ `yolo`（全部放行）/ `plan` |
| codex | `read-only` / `workspace-write`（可写根=项目目录）/ `danger-full-access` |

codex 侧直接翻译为沙箱策略 JSON（`readOnly` / `workspaceWrite{writableRoots:[项目根]}` / `dangerFullAccess`）——**模式即 agent 原生能力，客户端只做映射**。

**② 审批"始终允许"→ tab 级自动批准（客户端记忆）**

`respondAssistantApproval`：`decision === "allowAlways"` 时，除回应当次请求外，**把该 tab 的 `toolApprovalMode` 置为 `"auto"`**——后续该 tab 的审批请求客户端直接自动应答，不再弹窗；若 bridge 应用失败则**回滚 `manual`** 并追加系统消息提示。审批状态四值（`pending/approved/approvedAlways/denied`）持久化进聊天消息块。

**③ 本地模式驱动自动应答（不弹窗路径）**

`gemini_permission_result`：收到 `session/request_permission` 时按本地模式**直接选定 optionId 回应**，零 UI：

```text
plan          → reject_once ∨ reject_always（只读模式拒绝一切写操作）
yolo/auto_edit → allow_always ∨ allow_once
default       → allow_once ∨ allow_always（保守优先 allow_once）
```

**④ 自动化工作流权限档案（headless 场景）**

三档档案 `standard` / `full-access` / `read-only`，job 级 + workflow 节点级（节点可 `inherit` 继承 job 默认），经 `automation_permission_mode_for_cli` 映射表翻译到各家原生模式（如 `(claude, full-access)→bypassPermissions`、`(gemini, read-only)→plan`）。无人值守场景下权限是**声明式配置**而非交互。

### 2.2 theia-zen（Theia AI，ai-chat 包）

`ToolConfirmationManager`（`chat-tool-preference-bindings.ts`）+ 偏好 schema（`chat-tool-preferences.ts`），是四家中**最完整的客户端规则引擎**：

**① 三态确认模式**

`ToolConfirmationMode`：`always_allow`（免确认执行）/ `confirm`（弹窗确认）/ `disabled`（禁用该工具）。

**② 分层解析优先级**（`getConfirmationMode`）

```text
会话级覆盖（内存，per chatId，不持久）
  → 工具级持久偏好（ai-features.chat.toolConfirmation: {toolId: mode}）
    → 全局默认（ai-features.chat.defaultToolConfirmation，默认 confirm）
```

**③ 危险工具保护（confirmAlwaysAllow）**

工具可声明 `confirmAlwaysAllow` 标记：此类工具**不继承全局 `always_allow`**，默认回落 `confirm`——防止"全局放手"误放危险操作；但用户**显式设置的工具级偏好仍然生效**（知情同意原则：用户明确点过的不拦）。

**④ 工作区信任门**

默认值经 trust-aware reader 读取：**不受信工作区不能把默认改得更宽松**。

**⑤ 超时自动拒绝**

`toolConfirmationTimeout`（秒）：正数时确认对话框超时按拒绝；0 禁用。

**⑥ 偏好写入最小化**

设置值与有效默认相同即删除条目（不产生冗余配置）；批量更新合并为单次 preference 写。

### 2.3 VS_Code_Python（pygpt_net）

权限思路为**预防式过滤**，与运行时审批正交：

**① MCP 插件白/黑名单**（`plugin/mcp/config.py`）

每个 MCP server 配置 `allowed_commands`（白名单，逗号分隔）/ `disabled_commands`（黑名单）。过滤发生在**工具发现阶段**——被禁工具根本不暴露给模型，模型无感知、无运行时审批开销、无弹窗。

**② 远端 MCP 审批直通**（`provider/api/openai/responses.py`）

OpenAI Responses API 的 `mcp_approval_request` 直接回 `"approve": True` 自动批准，无 UI 回环（放手姿态）。

（注：`CMD_CONFIRM` 事件属无障碍语音控制的"确认上一动作"，与 AI 工具审批无关，不计入。）

### 2.4 三家机制定位图

| 机制 | Multi_Cli_Studio | theia-zen | pygpt |
|:---|:---:|:---:|:---:|
| 全局模式切换（放手/逐次/只读） | ✅（per CLI 原生模式） | ✅（全局默认三态） | ❌ |
| 工具级三态持久配置 | ❌ | ✅ | ✅（仅 MCP 工具，白/黑名单二态） |
| "始终允许"客户端记忆自动应答 | ✅（tab 级 auto） | ✅（会话覆盖+工具级持久双档） | ❌ |
| 危险工具不继承全局放行 | ❌ | ✅（confirmAlwaysAllow） | ❌ |
| 预防式过滤（模型不可见） | ❌ | ❌ | ✅ |
| 超时自动拒绝 | ❌ | ✅ | ❌ |
| 无人值守声明式档案 | ✅（automation 三档） | ❌ | ❌ |

## 3. 候选方案

### 方案 A：客户端记忆自动应答（Multi_Cli_Studio ②③ 路线）

审批对话框点"始终允许"→ 客户端把该工具（`title`+`kind`）记入**放行集**；后续 `PermissionHandler` 先查放行集，命中即按 options 自动选 `allow_always ∨ allow_once` 的 optionId 直接回应，**不再弹窗**。拒绝侧对称：可加"始终拒绝"记入拒答集。

- **优点**：直接消除痛点；改动集中在 `PermissionHandler` 注入处与 panel，协议层零改动；无 GUI 线程依赖（handler 内纯查表），不阻塞 reader 线程；与 kimi 行为解耦（不依赖 agent 修复记忆）
- **缺点**：只解决"不再弹"，没有提供"全局放手/只读"模式与禁用工具能力；记忆粒度受 §1.2 限制（工具级稳定，命令级脆弱）
- **成本**：低（handler 前加一层查表 + 对话框写入记忆，约百行）

### 方案 B：全局权限模式三态切换（Multi_Cli_Studio ① 路线）

设置项/菜单提供全局三态：**放手（自动全放行）/ 逐次确认（现状）/ 只读（自动全拒）**。handler 按全局态自动应答，弹窗仅在"逐次确认"态出现。

- **优点**：心智模型最简单（一个开关）；无人值守/演示场景直接切放手；实现极简（handler 三个分支）
- **缺点**：粒度最粗——放手时连危险命令也不问，只读时连无害读取也拒；无中间态（"编辑自动放行但 Bash 必问"做不到）；与方案 A 记忆机制叠加后才有实用价值
- **成本**：低

### 方案 C：工具级三态持久配置（theia-zen ①② + pygpt ① 路线）

`settings.json` 增 `permission_rules: {工具名: always_allow|confirm|disabled}`，handler 解析：命中 `always_allow` 自动放行、命中 `disabled` 自动拒答（agent 收到否定会调整策略）、否则弹窗。配套审批对话框按钮从三态扩为五态（允许一次/本会话允许/永久允许/拒绝/永久禁用）。

- **优点**：粒度细（Bash 逐次确认、Write 永久放行等任意组合）；持久化跨重启；`disabled` 档等价 pygpt 黑名单（虽不能阻止模型看见工具，但拒答后 agent 会收到否定并改道）
- **缺点**：配置项管理 UI（规则列表的增删改）成本上升；命令级细化受协议限制做不了（§1.2）
- **成本**：中

### 方案 D：agent 原生模式切换（Multi_Cli_Studio ① 映射表路线）

实测 kimi ACP `session/set_mode` 的可用模式值。若存在 bypass/yolo 类模式，全局切换直接下发 agent 原生模式（审批请求从源头不再产生），客户端只保留映射表。

- **优点**：若可用则最根治——权限决策回归 agent 原生实现，客户端零规则引擎；与 Multi_Cli_Studio 的 claude/gemini/codex 做法完全同构
- **缺点**：模式值清单未知，**需摸底脚本实测**（可能根本没有放手模式，kimi 走用户配置文件的权限策略）；各家值域不一，接入第二家 agent 时需各自维护映射表；即便可用也只能提供模式级粒度，工具级仍需方案 C 补齐
- **成本**：摸底小，接入小～中

> **摸底结论（2026-07-22 实测，kimi acp 0.27.0，脚本 `.temp/probe_acp_modes.py`）**：
> `session/new` 响应**无 `modes` 字段**（`session/set_mode` 模式面不存在），
> 但 `configOptions` 携带审批模式选择项（id=`mode`，经 `session/set_config_option`
> 下发）：`default`（逐次审批）/ `plan`（只读规划不执行工具）/ `auto`
> （自动批准安全操作）/ `yolo`（全批准）。**无目录沙箱模式**——硬围栏不可用，
> 目录约束维持 cwd 软约束（等 C4 fs 桥接路径校验）；`auto` 档为 agent 侧
> 审批放行的可用路径（与 F 客户端侧放手等价，可作备选实现，但决策权让渡
> agent、黑名单兜底失效，故维持 F 客户端侧决策为本案）。

### 方案 E：分层权限规则引擎（组合新方案，推荐）

取各家所长组合为单一规则引擎，handler 入口一次解析：

```text
session/request_permission 到达
  → ① 会话级覆盖（内存，"本会话允许/拒绝"写入）          ← 方案 A
  → ② 工具级持久规则（settings.json，always_allow/confirm/disabled） ← 方案 C
  → ③ 全局默认模式（放手/逐次确认/只读）                  ← 方案 B
  → ④ 危险工具保护：标记工具不继承③的放手，回落逐次确认     ← theia ③
命中 always_allow → 自动选 allow optionId 回应（零弹窗）
命中 disabled/只读 → 自动选 reject optionId 回应（零弹窗）
否则 → 弹窗（按钮五态：允许一次/本会话允许/永久允许/拒绝/永久禁用）
```

- **优点**：一次到位——痛点消除（①②）、模式切换（③）、危险兜底（④）齐备；解析优先级与 theia 同构，语义经得起推敲；危险工具保护防"全局放手误放 rm -rf"；各层独立可分期交付
- **缺点**：四方案中成本最高；规则引擎需明确"有效默认相同即删条目"等写入纪律（theia ⑥）避免配置膨胀
- **成本**：中（分期后每期小～中）

### 方案 F：默认放手 + 双护栏（组合裁剪新方案，AI-first 定位推荐）

**定位前提**：本 IDE 以 AI 为主——人不做细粒度控制，只防两类大灾：**危险命令**与**目录越界**。据此对 E 做极简裁剪：砍掉会话层、工具级持久配置、五态按钮（全是细粒度控制），只留"默认信任 + 黑名单兜底 + 目录围栏"：

```text
session/request_permission 到达
  → 默认：自动放行（零弹窗）——AI 优先，人不打扰
  → 护栏二命中（危险命令黑名单，仅 Bash 类）：弹窗（仅此一种情况弹）
  → 护栏一（目录围栏）：agent cwd 限定项目根（已内建，软约束）
                       + set_mode 沙箱/fs 桥接路径校验（硬围栏，摸底项）
                       ※ 2026-07-22 摸底结论：set_mode 模式面不存在，无沙箱模式，
                         硬围栏转备案（等 C4 fs 桥接路径前缀校验，见方案 D 行实测注记）
```

组成 = 方案 B 的"放手态" + theia ③ 的危险保护思想 + pygpt 的黑名单思想。

- **优点**：与产品定位精确对齐——人只在危险黑名单命中时被打扰；默认全放行后"始终允许"需求自然消失（方案 A 失去存在必要）；成本最低档（P0 仅 handler 一个分支）；黑名单失败方向安全——漏匹配最多不弹（接受的残余风险），误匹配顶多弹一次窗
- **缺点**：黑名单是"已知危险"枚举，**防不住未知危险**（放手的固有风险，选型即接受）；命令提取自 `content` 自然语言串（§1.2 脆弱面，但黑名单只需粗匹配，不构成障碍）；硬围栏落地前 agent 的 Bash 有能力 `cd` 出项目目录（软约束期残余风险）
- **成本**：低（P0 极小 / P1 小 / P2 摸底小）

| AI-first 定位契合 | 🟡 | 🟡 | ❌（细粒度控制） | 🟡 | ❌（细粒度控制） | ✅ |

---

## 5. 推荐结论

**推荐方案 F（默认放手 + 双护栏）**——依据产品定位裁决（2026-07-22 需求方明确）：本 IDE 以 AI 为主，人**不做细粒度控制**，只防危险命令与目录越界两类大灾。方案 E 的会话层/工具级配置/五态按钮恰是被排除的细粒度控制，降级为未来定位变化时的演进备案（见 §6）。

| 期 | 内容 | 价值 |
|:---:|:---|:---|
| P0 | handler 默认自动放行（按 options 选 allow optionId 直接回应，零弹窗）；弹窗退役为黑名单专用 | **立即消除痛点**，成本极小 |
| P1 | 危险命令黑名单（Bash 类工具从 `content` 粗匹配毁机/越界/不可逆模式，命中才弹窗并显示原因） | 危险兜底 |
| P2 | 目录硬围栏：摸底 `session/set_mode` 有无沙箱模式（codex `workspace-write` 同款），有则下发；无则等 C4 fs 桥接后校验路径前缀 | 越界兜底（现状 cwd 软约束已内建） |

**残余风险（选型即接受）**：① 黑名单防不住未知危险（放手的固有代价）；② 硬围栏落地前 agent 的 Bash 可 `cd` 出项目目录（软约束期暴露面，P2 尽快摸底收敛）。

**不选其余方案的理由**：A 在默认全放行后需求消失；B 粒度太粗且无危险兜底（其"放手态"已被 F 吸收）；C/E 的细粒度控制违背 AI-first 定位；D 依赖未验证的 agent 能力，降格为 F 护栏一的实现候选（P2 摸底）。

### 实施要点

1. **匹配键纪律**：危险判断只对 Bash 类工具（kind=execute）做 `content` 粗匹配；不做工具级/命令级白名单（细粒度控制，定位外）
2. **自动应答路径纪律**：默认放行在 handler 内同步完成，零 GUI、零阻塞（reader 线程纪律，1555 计划风险表同一条）
3. **黑名单失败方向**：漏匹配→不弹（接受）；误匹配→弹一次窗（安全方向失败，可接受）
4. **黑名单可维护**：模式清单常量化集中定义（AFCP 3.4），每条注明"为什么危险"
5. **`kimi-cli` 后端说明**：本就固定 auto 无审批面，与 F 的默认放手语义天然一致，零改动
6. **审批超时**：黑名单命中弹窗保留 180s 超时按拒绝兜底（危险场景超时拒=安全方向）

## 6. 备案

1. **方案 E 分层规则引擎**：若未来定位转向需要细粒度控制（会话级/工具级/五态按钮），按 E 的 A→C→B 分期演进；F 的默认放手态即 E ③ 的特例，平滑衔接
2. kimi 审批请求携带 `rawInput` 后：黑名单匹配从 `content` 解析升级为结构化参数匹配（更准）
3. `session/set_mode` 摸底结论回填本文档方案 D 行与 F 护栏一
4. 审批日志面板（黑名单命中与自动放行可审计——自动放行时代的透明性补偿）
5. kimi CLI 启动参数权限档摸底（`kimi-cli` 后端如需约束的唯一路径，不阻塞）
