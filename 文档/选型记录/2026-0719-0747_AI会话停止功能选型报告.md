## 1. 背景与需求

左栏 AI 会话（`gui/panels/chat/`）现状：消息发出后 `ChatWorker(QThread)` 后台消费 `llm.chat()` generator 逐块上屏，期间输入框与模型栏禁用（`_set_busy(True)`），**没有任何中途强制停止的入口**。AI 思考过久、输出跑偏、agent 长循环时用户只能干等。

需求：

1. **可中断**：响应进行中出现停止入口，点击后尽快停住流式输出
2. **资源释放**：停止后底层资源必须真正回收——kimi-cli 子进程不能残留后台、kimi-acp 会话要收到取消
3. **状态复原**：输入区恢复可用；已输出内容保留上屏（不主动擦除，用户可复制）；历史记录整体回滚（中断轮视同未发生，用户消息与半截回复均不入历史）
4. **不误伤**：停止是协作式的，不能用 `QThread.terminate()` 强杀（会泄露子进程、破坏流状态）

技术约束：Python/PySide6 单进程；`llm.chat()` 是 generator（`Iterator[Chunk]`）——这决定了我们的中断天然钩子是**"停止消费 + `generator.close()`"**：close 会让 generator 在 yield 点抛 `GeneratorExit`，provider 的 `finally` 块即成为资源清理的统一挂点。

**关键启示**：

- 三家 UI 层结论一致收敛：**发送/停止同一位置互斥切换**（streaming 时发送键变停止块图标），无需额外布局——直接照搬。
- 中断时效性分三档：**轮询（PyGPT）< 令牌（theia）≈ 协议中断（Multi_Cli）**。轮询只能等下一 chunk；令牌/协议中断能立刻打断阻塞。
- **竞态处理是隐藏考点**：Multi_Cli 的"Pending 挂起补发"与 theia 的"令牌已取消则发起前即拒"（`openai-language-model.ts` L149）都在解决同一问题——停止请求可能早于流建立。
- generator 语义是我们的底牌：`for` break + `gen.close()` → `GeneratorExit` → provider `finally` 清理，这一条链能把 Multi_Cli 的后端分发与 theia 的资源回收合并进 Python 惯用法。

## 3. 候选方案对比（四个维度）

### 3.1 维度一：中断信号机制（核心分歧点）

| | A. 标志位轮询（PyGPT 路线） | B. 按后端分发的协议中断（Multi_Cli 路线） | C. 取消令牌传导（theia 路线） |
|:---|:---|:---|:---|
| 做法 | worker 持 `_stop_requested`；`for chunk` 循环每轮检查即 break | 停止时直接对当前后端执行取消原语：kimi-acp 发 `session/cancel`；kimi-cli 对子进程 `terminate()` | 每请求生成一个令牌对象，沿 `panel → worker → llm.chat()` 显式传参；provider 在内部等待点上挂 `on_cancelled` 回调 |
| ✅ 优点 | 实现最简（worker 加 5 行）；无跨层接口变更；对"流式逐块到达"场景够用 | **能打断阻塞**（协议取消/杀进程立即生效，不等下一 chunk）；后端差异收敛在 provider 内，上层无感；与我们双后端形态精确对应 | 契约最严谨——令牌是显式参数，新增 provider 不可能忘记处理取消；取消回调在阻塞等待点上立刻触发 |
| ❌ 缺点 | **停不住阻塞**：kimi-cli 子进程无输出等待期、kimi-acp 等 agent 回包期，轮询点永远等不到下一 chunk——恰是用户最想停的场景；工具长循环需另找埋点 | 两后端各写一份取消原语；停止请求早于流建立的竞态要处理（Multi_Cli 用 Pending 补发，我们要等价物） | Python 无 CancellationToken 基础设施，需自造（`threading.Event` + 回调注册 ≈ 30 行）；改动面最大（`llm/base.py` 协议签名 + 两个 provider + worker + panel 全要过手） |

### 3.2 维度二：底层资源清理

| | A. generator `close()` + provider `finally` | B. 停止时直接持有句柄清理 |
|:---|:---|:---|
| 做法 | worker break 后调 `gen.close()` → `GeneratorExit` 在 yield 点抛出 → kimi_cli `finally` 杀子进程、kimi_acp `finally` 发 cancel/断连 | panel/worker 直接持有 llm 实例或子进程句柄，停止时调 `llm.cancel()` 或 `proc.terminate()` |
| ✅ 优点 | 清理逻辑收在 provider 自己的上下文管理里，**正常结束/异常/停止三条路径共用同一 finally**，不会漏；Python 惯用法 | 停止路径直给，不绕 generator 语义 |
| ❌ 缺点 | 阻塞中的 generator 在**下一次 yield 之前**收不到 close（与 3.1-A 同源的时效问题） | 清理逻辑与 provider 内部状态脱节（子进程句柄在 generator 栈帧里），容易清理一半；异常路径（非停止的报错）覆盖不到 |

### 3.3 维度三：UI 交互模式（三家已收敛，仅一处分歧）

| | A. 发送/停止按钮互斥切换（三家同款） | B. 独立停止按钮（PyGPT 全局 stop 款） |
|:---|:---|:---|
| 做法 | streaming 时发送键变停止块图标（Square），点击即停；title 提示"停止生成" | 输入区旁或状态栏常驻一个停止按钮，仅 streaming 时可见 |
| ✅ 优点 | 零新增布局；肌肉记忆友好（VS Code/Theia/Multi_Cli 用户零学习成本）；输入框可保持可编辑（用户可边等边打下一条） | 停止目标更醒目；可同时保留发送禁用态 |
| ❌ 缺点 | 无 | 多占布局；与我们窄侧栏空间不匹配 |

附加快捷入口（可选增强，三家均有）：Esc 停止（theia L1535、PyGPT access/control.py L148）、"stop"命令词（PyGPT input.py L73-78）。

### 3.4 维度四：停止后的状态收尾

| | A. 部分内容入历史 + 中断标注（Multi_Cli 路线） | B. 整体丢弃回滚（现 `_on_finished` 失败路径同款） |
|:---|:---|:---|
| 做法 | 已输出部分保留上屏并入历史，末尾/下方追加系统标注（Multi_Cli 文案："Response interrupted before completion. You can retry this prompt."） | 连用户消息一起 `_history.pop()`，视同未发生 |
| ✅ 优点 | 现场不丢——用户常因"答案已够好但 AI 还在啰嗦"而停，部分内容正是他要的；下轮对话上下文连续 | 历史最干净 |
| ❌ 缺点 | 历史中存在截断回复，需在 content 里可识别 | 用户要的半截答案没了；重问要重述上下文 |

**决策记录**（2026-07-19 08:12 用户确认）：**选 B**。理由：① 用户的打断动机为"AI 卡住"与"方向跑偏"两类，几乎不因"输出过长"打断——卡住时无内容可留、跑偏时内容是负资产，A 的核心卖点不触发；② B 复用现有失败路径的 `_history.pop()`，改动约 3~5 行，A 需新增截断标注机制并处理续写歧义；③ 截断回复回传后端属未验证领域（kimi-cli/acp 对半截 tool_call 的容忍度未知），B 使整个问题域消失；④ 屏幕上的半截内容不擦除，真想要可选中复制，零成本兜底。

## 4. 综合对比与推荐结论

🟢 **推荐组合：B + A + A + B**（2026-07-19 08:12 用户审阅确认）——**按后端分发的协议中断（Multi_Cli 蓝本）+ generator close/finally 资源清理 + 发送/停止互斥按钮 + 整体丢弃回滚**：

| 维度 | 决策 | 理由 |
|:---|:---|:---|
| 中断机制 | **B. 按后端分发的协议中断** | 唯二能打断阻塞的方案之一，且与我们双后端形态（kimi-cli 子进程 / kimi-acp 协议）精确同构，Multi_Cli 的 `session/cancel` 与 SIGINT 兜底两条原语可直接翻写为 Python；C（令牌）契约更优美但改动面与自造成本高一个量级，列为演进方向 |
| 资源清理 | **A. generator close + provider finally** | 正常/异常/停止三路径共用一个 finally；Python 惯用法零新设施；与 B 互补——协议原语负责"立刻停"，finally 负责"兜底清" |
| UI 交互 | **A. 发送/停止互斥切换** | 三家收敛结论；窄侧栏零布局成本；输入框顺势保持可编辑 |
| 状态收尾 | **B. 整体丢弃回滚** | 用户打断动机为卡住/跑偏（3.4 决策记录），半截内容无保留价值；复用现有失败路径 `_history.pop()` 改动最小；规避截断回复回传后端的未验证风险；屏幕内容不擦除，可复制兜底 |

**折中与否决记录**：

- **PyGPT 标志位轮询（3.1-A）**：实现最省，但恰恰在用户最想停的"AI 卡住"场景（阻塞无 chunk）失效，否决为核心机制；其"agent 工具循环每轮查标志"作为 B 的补充保留（循环间检查点仍必要）。
- **theia 令牌传导（3.1-C）**：契约最严谨，列为二期演进——若后续 provider 增多或取消点增多（工具确认、子任务委派），再升级为显式令牌（届时 `llm/base.py` 加 `CancellationToken` 协议类）。本期 B 方案的"provider 内收敛"已覆盖双后端。
- **部分内容入历史（3.4-A）**：与用户打断动机（卡住/跑偏）不匹配，且引入截断标注与回传风险，否决（2026-07-19 用户决策）；若未来出现"保住半截答案"的高频诉求，再以 Multi_Cli 文案思路回补。
- **直接杀 QThread**：`QThread.terminate()` 泄露子进程、破坏流，三条参考链一致规避，否决。

**双保险设计**（B 与 PyGPT 的交集，推荐一并实施）：

1. **立即层**（B）：停止点击 → 按当前后端分发取消原语（kimi-acp：`session/cancel`；kimi-cli：子进程 `terminate()`）
2. **检查点层**（PyGPT）：worker `_stop_requested` 标志，`for chunk` 每轮检查 break——接住协议取消之后的残余流、覆盖未来 agent 多轮循环的轮间停止
3. **竞态层**（Multi_Cli Pending 思路）：停止请求到达时 worker 尚未 start（排队中）→ 直接置标志，worker 启动后第一轮即 break

## 5. 实施要点（供后续计划引用）

1. **`llm/base.py`**：`LanguageModel` 协议补 `cancel()` 方法约定（默认空实现）——kimi-acp 实现为发 `session/cancel`，kimi-cli 实现为子进程 `terminate()`；两 provider 的 `chat()` generator 补 `finally` 清理（进程存活则杀、连接复位），使 break + close 路径也能兜底。
2. **`gui/panels/chat/worker.py`**：`ChatWorker` 加 `_stop_requested` + `request_stop()`（置标志 + 调 `llm.cancel()`）；`run()` 循环每轮查标志，break 后 `gen.close()`；停止导致的结束通过 `finished_with_error` 正常信号收尾（新增或复用中断语义，不视为错误）。
3. **`gui/panels/chat/panel.py`**：
   - busy 时发送区变停止按钮（`input.py` 加 `stop_requested` 信号，或 panel 内按钮互斥，参照 `ChatPromptBar.tsx` L4240-4254 的单按钮双态写法）
   - 停止点击 → `_worker.request_stop()`；`_set_busy` 期间输入框不再禁用（仅模型栏禁用），占位提示"响应中…可点击 ■ 停止"
   - `_on_finished` 区分三态：正常完成 / 用户中断（`_history.pop()` 回滚用户消息，半截回复不入历史；屏幕已输出内容不擦除，追加系统标注"⏹ 已手动停止，本轮不计入对话"）/ 失败（现有 pop 回滚 + 错误上屏）
4. **竞态处理**：`request_stop()` 在 worker 未 running 时仍置标志；`_on_send` 启动前查一次标志防复用脏 worker。
5. **可选增强（备案）**：Esc 停止（input 的 `keyPressEvent` 已有定制点）；"stop"命令词；agent 工具循环轮间检查（待 kimi-acp 长循环场景实测后定）。
6. **验证要点**：流式中途停止（chunk 密集到达时）；阻塞中停止（kimi-acp 等回包期间点击，应秒停）；停止后子进程无残留（`ps` 验证）；停止后立即可发下一条；中断轮历史回滚验证（用户消息与半截回复均不入 `_history`，屏幕内容保留 + 标注）；连点停止幂等（不崩不重复清理）。
