# 变更对比 Diff 视图功能 方案选型

## 一、背景与约束

### 1.1 需求范围（已与需求方确认）

为 IDE 增加"变更后对比"功能：同一窗口内展示文件改动，**红色 = 删除，绿色 = 新增**。核心要求是**实现尽量简单**，不做复杂对比。

**做**：

1. Unified Diff 行级对比视图：单窗口，删除行标红、新增行标绿，带 `-`/`+` 前缀
2. 典型触发场景：查看某文件相对上游分支（`@{upstream}`，即"已推送状态"）的改动；仓库未配置上游时回退到 HEAD 对比

**不做**：

- ❌ Inline Diff（词/字符级行内高亮）——超出"尽量简单"的要求
- ❌ Side-by-Side 并排对比——需滚动同步与对齐连线，UI 工作量大
- ❌ 三方合并（merge）视图

### 1.2 约束

- 技术栈：Python 3.12 + PySide6（QWidget 体系），强制使用项目 `.venv`
- 项目风格偏轻依赖（现状仅 ptyprocess / pygments / pyside6 / pyte 等少数依赖），能零依赖就不新增
- 主题色必须走 `src/gui/theme.py` 资源包体系，不硬编码（已有 `chat` 包 `diff_add_fg`/`diff_del_fg` 红绿键可复用）

## 二、名词说明

| 术语 | 含义 |
|:---|:---|
| **Diff 视图** | 差异对比视图的统称，源自 Unix `diff` 工具 |
| **Unified Diff** | 统一差异视图：新旧内容混合在单窗口，删除行标红（`-`），新增行标绿（`+`）——**即本次选定的模式** |
| **Inline Diff** | 行内差异：在 Unified 基础上细化到词/字符级高亮 |
| **Side-by-Side** | 并排对比：左右双面板，带滚动同步与对齐连线 |

## 三、展示模式选型（维度一）

| 模式 | 常用叫法 | 实现难度 | 说明 |
|:---|:---|:---|:---|
| **Unified Diff** | 统一差异视图 / 行对比 | ⭐ 最简单 | 单窗口，删除行标红、新增行标绿，带 `-`/`+` 前缀 |
| Inline Diff | 行内差异 | ⭐⭐ 中等 | 在 Unified 基础上，同一行内改动的词/字符用红绿底色高亮 |
| Side-by-Side | 并排对比 / Split View | ⭐⭐ 中等 | 左右双面板，需处理滚动同步、对齐连线，UI 工作量明显更大 |

**结论：Unified Diff。** 满足"红色删除、绿色新增"的最低需求，实现最简单，已与服务端确认。

## 四、实现方案选型（维度二）

### 方案 A：difflib（Python 标准库）

`difflib.unified_diff()` 生成行级差异，Qt 侧只读控件按行渲染红绿。

**优点**：

- **零新增依赖**，纯 stdlib，与项目轻依赖风格完全一致
- 能力刚好覆盖 Unified Diff 行级需求，不多不少
- 纯 Python 函数，可脱离 Qt 直接单测

**缺点**：

- 仅行级，不支持词/字符级行内高亮（本需求用不上）
- 纯 Python 实现，万行以上大文件较慢（需加行数上限兜底）

### 方案 B：diff-match-patch（Google）

**优点**：支持词/字符级行内高亮；跨语言实现成熟。

**缺点**：**新增第三方依赖**；其行内高亮优势在本需求（行级 Unified）中完全体现不出来，属过剩能力。

### 方案 C：jsdiff

JS/TS 技术栈的 npm 包，与本项目 Python/Qt 技术栈不匹配，直接排除。

### 方案 D：Monaco Diff Editor

Web/Electron 编辑器内核，体量大、面向 Web IDE（VS Code 插件、Electron 应用），无法嵌入 Qt QWidget 体系，直接排除。

### 综合对比表

| 维度 | 方案 A：difflib | 方案 B：diff-match-patch | 方案 C：jsdiff | 方案 D：Monaco |
|:---|:---|:---|:---|:---|
| 技术栈匹配 | **Python 原生** | Python 可用 | ❌ JS/TS | ❌ Web/Electron |
| 新增依赖 | **无** | 单文件库 | npm 包 | 编辑器内核（体量大） |
| 行内高亮 | ❌ 仅行级 | ✅ 词/字符级 | ✅ 词/字符级 | ✅ 完整 |
| 大文件性能 | 一般（纯 Python） | 较好 | 较好 | 好（虚拟滚动） |
| 匹配本需求程度 | **刚好够用** | 过剩 | 不适用 | 不适用 |
| 综合推荐度 | ★★★★★ | ★★★ | ★ | ★ |

## 五、关键选型因素（除难度外）

1. **IDE 技术栈**——决定性因素：本项目为 Python/Qt，difflib 或 diff-match-patch 二选一；jsdiff/Monaco 天然出局
2. **行内高亮需求**——只到"行"级 difflib 就够；要到"词/字符"级才必须 diff-match-patch，本期明确不做
3. **文件规模**——变更对比场景通常是单文件改动（几百至几千行），difflib 性能足够；万行以上加大文件上限提示兜底
4. **后续扩展**——若未来要加 Inline/Side-by-Side/merge，可再评估升级 diff-match-patch 或 Monaco；本期以"简单可交付"为先，接受将来可能的返工成本

---

## 六、推荐结论

**展示模式：Unified Diff（行级）；实现方案：difflib + Qt 原生渲染。**

理由：

1. difflib 是标准库零依赖，`unified_diff()` 的输出形态与 Unified Diff 视图一一对应，刚好够用；
2. Qt 侧用只读 `QTextBrowser`/`QPlainTextEdit` 按行设红绿着色即可，项目已有 `DiffCard`（`src/gui/panels/chat/cards.py`）的 hunk 三色渲染先例与 `chat` 主题包 `diff_add_fg`/`diff_del_fg` 现成色键，渲染成本极低；
3. diff-match-patch 的行内高亮优势本期用不上，不值得为它打破零新增依赖；
4. 大文件短板以行数上限提示兜底，不预设复杂分块方案。
