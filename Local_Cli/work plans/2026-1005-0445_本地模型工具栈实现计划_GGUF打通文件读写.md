## 1. 背景与目标

本地链路（IDE → `local-cli acp` → llama-server → GGUF 模型）目前是纯文本对话：
模型没有被暴露任何工具，也没有 system prompt。实测中用户让本地模型「在根目录
写一个 .md 文件」，模型只能回复「我作为 AI 语言模型，无法直接访问或操作你电脑的
文件系统」——这是准确陈述事实，不是协议故障。

缺口定位（已排查确认）：

- GGUF 后端发给 llama-server 的请求体只有一条裸 user 消息，无 `tools` 字段、
  无 system 消息（`local_cli/model/gguf.py`）。
- 轮次层对真实模型恒走纯文本路径，唯一的工具演示通路只对 Mock 后端开放
  （`local_cli/acp/turn.py`）。
- 按协议职责划分，文件读写的执行责任在 **agent 侧**（即本服务端），客户端 fs
  反向能力恒 false（`../dream-acp/protocol/dream-acp-v1.md` §1.3）。

本期目标：

- ✅ 为 GGUF 链路补齐工具栈：工具定义注入（system prompt）→ 模型输出 tool_call
  解析 → 服务端沙盒内执行文件读写 → 审批回环 → 结果回灌模型的**有界工具循环**。
- ✅ 工具集：`write_file` / `read_file` / `list_dir`，全部约束在会话 cwd 沙盒内；
  写操作必须经 `session/request_permission` 审批。
- ✅ 无工具调用的轮次帧序列与现状完全一致（思维链 → 正文 → usage → end_turn），
  spike 既有断言零回归。
- ❌ 不做终端/命令执行工具；不做跨轮次会话记忆；不做 llama-server 原生
  function calling；不动 IDE 侧任何代码。

验收主线：**在 Zen Studio 里对本地模型说「在项目根目录写一首诗的 poem.md」，
IDE 弹出审批窗 → 允许 → 文件真实落盘到会话 cwd，且全链路可被 spike/smoke
断言回归。**

## 3. 总体设计

### 3.1 工具调用机制选型：提示词协议（prompt-based）

候选两案：

| 方案 | 原理 | 优势 | 短板 |
|:---|:---|:---|:---|
| **A. 提示词协议（本期采用）** | system prompt 注入工具定义与输出格式，模型用围栏代码块输出 tool_call JSON，服务端解析执行 | 任意 GGUF 模型可用，不依赖 chat template；解析逻辑自主可控 | 依赖模型指令遵循能力；格式不合规时需容错回灌 |
| B. llama-server 原生 tools | 请求体带 OpenAI 式 `tools` 字段，依赖模型模板支持（`--jinja`） | 输出结构化、最干净 | 并非所有 GGUF 模板的 chat template 支持工具；换模型即可能失效 |

选 A 的理由：本地模型的型号由用户自选、不可预知，方案 B 的能力随模板有无而
漂移；方案 A 对任意能听懂中文指令的模型都可用，且容错回灌（解析失败把错误
原因喂回模型重试）能消化大部分格式抖动。方案 B 留作后续选型（§7）。

### 3.2 工具调用线格式（模型 ↔ 服务端约定）

模型需要调用工具时，回复中输出**恰好一个**围栏块：

````text
```tool_call
{"tool": "write_file", "args": {"path": "poem.md", "content": "……"}}
```
````

约定要点：

- `path` 一律为相对会话 cwd 的相对路径；绝对路径与 `..` 逃逸一律拒绝。
- 每条回复至多一个工具调用；需要连续操作时等待工具结果后再发下一个调用。
- 围栏语言标记 `tool_call` 使 IDE 端以普通代码块渲染，即使裸露也可读（v1
  接受其出现在对话流里，不做隐藏，见 §6 风险表）。
- 工具结果以 user 角色消息回灌：`【工具结果】…` 或 `【工具错误】…`。

### 3.3 工具集与审批策略

| 工具 | 参数 | 副作用 | 审批 |
|:---|:---|:---|:---|
| `write_file` | `path`, `content` | 写盘（自动建父目录） | 🔴 必须审批 |
| `read_file` | `path` | 只读 | 免审批 |
| `list_dir` | `path` | 只读 | 免审批 |

三个工具均发 tool_call / tool_call_update 通知（IDE 可见过程），区别仅在是否
阻塞等审批。审批复用既有三态 options；`allow_always` 本期落地为会话级记忆
（同会话后续同工具不再重复询问）。

### 3.4 模块划分

```text
# 目录结构（新增部分；类名体现 OOP 单一职责，继承链仅一层）
local_cli/
├── model/
│   ├── base.py           # 扩展：ChatMessage dataclass + stream_chat() 默认实现
│   │                     #   （默认摊平成 prompt_text 走 stream_reply，Mock 零改动）
│   └── gguf.py           # 覆写 stream_chat()：system + messages 载荷进 llama-server
├── toolkit/              # 新增包：工具内核，不 import acp/ 与 model/（纯函数+沙盒执行）
│   ├── __init__.py
│   ├── definitions.py    # 工具 schema 表 + system prompt 文案（单一出处）
│   ├── parser.py         # ToolCallParser：围栏块提取、JSON 校验、工具名/参数校验
│   └── executor.py       # ToolExecutor：cwd 沙盒（Path.resolve 防逃逸）、三工具执行
└── acp/
    ├── turn.py           # TurnRunner：无 demo 意图且 tools_enabled 时委托 ToolLoopRunner
    └── tool_loop.py      # 新增：有界工具循环（流式 → 解析 → 审批/执行 → 回灌，≤ N 轮）
```

设计约束：

- **行为不变量**：`tools_enabled=false` 或无工具调用的轮次，出站帧序列与现状
  逐字节一致；spike 既有 25 项断言不许翻红。
- **轮次内消息列表**：工具循环的消息上下文（system + 当前 user + assistant/
  工具结果交替）仅在单轮次内存活，不写回会话——跨轮次记忆不在本期（§7）。
- **取消语义**：每次迭代开始前、审批返回后均检查 cancel_event，语义与既有
  `_is_cancelled()` 一致（§1.6 停后同会话可续）。
- **usage 聚合**：多轮迭代的 token 统计累加后单帧回报（used/size 同帧，§2.3）。
- **零新依赖**：全部 stdlib 实现，不新增 Python 包。

### 3.5 新增配置项

`~/.local-cli/config.toml` 增两键（缺省即生效，老配置文件无感升级）：

| 键 | 默认 | 语义 |
|:---|:---|:---|
| `tools_enabled` | `true` | 工具循环总开关（仅 GGUF 后端生效；Mock 走既有演示路径） |
| `tool_max_iterations` | `5` | 单轮次内工具循环上限，超限以说明性文本收尾 end_turn |

## 6. 风险与对策

| 风险 | 等级 | 对策 |
|:---|:---|:---|
| 模型不遵循 tool_call 围栏格式（小模型指令遵循弱） | 🟡 | 解析失败时把错误原因作为【工具错误】回灌，给模型 ≤ `tool_max_iterations` 次自我修正机会；超限以说明文本收尾，不静默吞错（A.3） |
| 模型把工具 JSON 散写在正文里，用户看到原始围栏块 | 🟢 | v1 接受裸露（围栏在 IDE markdown 下渲染为代码块，可读）；后续可做渲染期隐藏，属 IDE 侧优化，不在本期 |
| 工具循环上下文膨胀撑爆 ctx | 🟡 | 迭代上限 + `read_file`/`list_dir` 结果截断（命名常量阈值）+ usage 聚合上报，用户可见 token 消耗 |
| `allow_always` 记忆放大误授权面 | 🟡 | 记忆粒度=单会话×单工具，进程退出即失效；写操作首次必弹审批 |
| 沙盒逃逸（符号链接/编码诡计） | 🟡 | 一律 `Path.resolve` 后做 cwd 前缀判定；executor 用例覆盖 `..`、绝对路径、软链三种逃逸 |
| 提示词协议占用 system 位，改变既有对话风格 | 🟢 | `tools_enabled=false` 一键回退纯文本旧行为；帧不变量有 spike 兜底 |

## 8. 后续展望（ roadmap ）

本期落地文件读写后，本地链路的演进路线与 kimi/reasonix 的已知先例一致，
按依赖顺序排列（每一期届时各自单独立项，本节只做方向锚定）：

### 8.1 下一期：命令执行工具（Bash）

- **形态**：在 `toolkit/` 增 `run_command` 工具，agent 侧进程内执行（协议 §1.3
  职责划分：工具必须 agent 自行执行；kilocode/opencode 即此模式——bash 调用
  全程零 terminal/* 帧，命令内部执行，见
  `文档/审计报告/2026-0817-1522_ACP终端反向能力五agent实测报告_ZenStudio.md`）。
- **依赖本期**：工具循环、审批回环、`allow_always` 记忆全部复用，新增面仅
  执行器本身。
- **风险面大于文件写**：任意命令执行需独立设计——超时上限、输出截断回流、
  工作目录锁会话 cwd、是否引入命令白名单/黑名单，届时以选型文档定夺
  （落 `work options/`）。审批策略底线：每次执行必审批，且 `allow_always`
  记忆不适用于本工具。

### 8.2 增强期：terminal 投屏（ACP terminal/* 反向能力）

- **形态**：服务端在「模型已决定执行命令」后，改发 `terminal/create` →
  `terminal/output` → `terminal/wait_for_exit` → `terminal/release` 反向请求，
  把命令挪到 IDE 终端面板的用户可见 AI tab 里以真 PTY 执行；provider 侧把
  `src/llm/providers/local_acp.py` 的 terminal 能力声明拨为 true。
- **IDE 零改动**：`AgentTerminalBridge`（`src/gui/panels/terminal/agent_bridge.py`）
  已实现全部五个方法，且注入接线对 local provider 本就会执行，只是声明
  false 从未被调用；kimi/reasonix 已实测走通全程。
- **收益**：命令在用户眼前滚动、可 Ctrl+C 接管，契合本地链路看重的
  「进度可见」纪律。
- **硬依赖**：必须先有 8.1 的 agent 侧命令执行层——terminal/* 只是执行落地
  点，不是触发源，单独拨 true 无意义。

### 8.3 更远的 backlog（暂无排期）

- 跨轮次会话记忆（§7 已声明不做，届时另立计划）。
- llama-server 原生 function calling（`tools` 字段 / `--jinja`），随模型生态
  成熟再评估，选型文档落 `work options/`。
- 工具围栏块的 IDE 渲染期隐藏（观感优化，属 Zen Studio 侧改动）。
- 多工具并行调用与 `tool_call_update` 流式增量。
