# 时间线色块条与用量徽章布局位置选型

## 1. 背景与目标

左栏聊天区现有两个信息型组件，均位于**每个会话标签的内部底部**：

- **会话活动时间线色块条**：横排色块展示 AI 活动（读/写/工具调用），当前置于聊天卡片内、**输入对话框之下**常驻（splitter 之外，细条定高）。
- **上下文用量徽章**：纯文本百分比（如 `~42%`）+ tooltip 明细，当前置于输入区底行、模型下拉与发送按钮之间。

痛点：两者都埋在标签内部底部，用户在阅读输出区内容（视线上方）时无法感知 AI 活动节奏与上下文余量；尤其是用量徽章——上下文将满是最需要提前警示的信息，却放在视线最不可能停留的底行角落。

**目标**：重新选择这两个组件的摆放位置，提升可见性与信息层级合理性。本文只做方案比对，不涉及具体实现。

## 2. 约束与前提

- **每会话语义**：两个组件的数据都绑定单个会话标签——时间线随会话清空、用量按后端会话各自独立簿记。任何「标签外」的位置都意味着改为**容器级单例、跟随当前激活标签切换显示**，这是所有上移方案共同的语义代价。
- **横向空间**：时间线色块条是横向延展型组件，越长越有信息量；用量徽章是定宽小文本（约 `~100%` 宽度），对横向空间无要求。
- **垂直空间**：左栏宽度有限（三栏式布局），新增一行会压缩输出区高度。
- **显隐稳定性**：已有教训（左栏宽度病根治理）——组件显隐不得引起相邻控件尺寸跳动。
- **多标签并行**：多个标签可同时响应中，单例位置只能显示当前标签的活动，其余标签的活动不可见（现状每标签一条则无此问题，但用户一次也只盯一个标签，此代价可接受性需评估）。

## 3. 候选方案

### 方案 A：标签栏上方新增独立一行（用户提议）

在**左栏范围内**、会话标签栏正上方新增一行（菜单栏下方），时间线色块条与用量徽章同行摆放（如左条右徽，或徽章嵌入条尾）。

> 子选项 A1：新增行仅左栏宽（标签栏正上方，推荐理解）。
> 子选项 A2：新增行横跨整个主窗口（菜单栏正下方全宽行）——会割裂三栏布局的整体感，时间线条横贯终端/查看器上方语义不通，一般不推荐，列出仅供完整性。

### 方案 B：嵌入标签栏行（不新增行高）

将两个组件塞入标签栏这一行的空余处：标签不多时标签栏右侧有大片空白（「+」按钮左侧），时间线条可伸缩填充该空白，徽章置于条尾或「+」旁。

### 方案 C：保持现状（基线）

时间线条留卡片内底部、徽章留输入区底行，仅做视觉强化（如用量高热态变色已有，可再提升对比度）。

### 方案 D：迁入主窗口状态栏

主窗口底部状态栏常驻且全宽可见，将时间线条 + 徽章作为状态栏左侧/中部区段。

### 方案 E：标签内顶部（卡片内、输出区上方）

仍在每个标签内部（保留每标签实例语义），但从底部搬到卡片顶部一行，输出区之上。视线先经过信息条再进入内容。

### 方案 F：输入区上方同行摆放（用户补充提议）

仍在每个标签内部（保留每标签实例语义），将两个组件从输入对话框之下/输入区底行**上移到输入区上方**——即输出区与输入区之间的分界位置，时间线色块条与用量徽章**同行摆放**（如左条右徽，或徽章嵌入条尾）。

> 位置语义：这一行成为「对话流末端的状态槽」——输出区最新内容在上方滚过，状态条横亘在输出与输入之间，用户打完字抬眼即见；也是发送前最后一眼能看到上下文余量的位置。

## 4. 各方案优缺点

### 方案 A：标签栏上方独立一行

**优点**
- 位置语义清晰：「会话级信息条」悬于所有会话标签之上，层级上成为左栏的门面行。
- 横向空间完整（左栏全宽），时间线条有充分延展余地；徽章同行右侧天然对齐。
- 不影响标签内布局，卡片内部回归纯粹的「输出 + 输入」。
- 新增一行不依赖标签存在（零标签占位页时也可常驻，或随之隐藏——可再定）。

**缺点**
- 占用一行垂直空间（约 20~28px），压缩输出区。
- 每会话 → 容器级单例的语义切换：切标签时整条内容瞬换，用户需建立「这行属于当前标签」的心智；后台标签的活动完全不可见。
- 与菜单栏的距离关系需处理——菜单栏是窗口级、新增行是左栏级，视觉上是「左栏内部顶行」，并非真的贴着菜单栏（中间还隔着面板边距），用户对「菜单栏下方」的预期可能是横跨整窗的一行（即 A2，不推荐）。

### 方案 B：嵌入标签栏行

**优点**
- 零新增垂直空间，纯利用现有空白，是空间效率最高的上移方案。
- 与标签同行，「属于当前标签」的语义最直观——标签和数据在同一视线路径上。

**缺点**
- 标签栏宽度随标签数变化：4 个标签占满时剩余空白有限，时间线条被压缩失去信息量；标签标题变长也会挤压。
- 时间线条高度受标签栏行高限制（标签栏行高远大于细条理想高度，或反之撑高标签栏）。
- 标签栏行交互密集（点击切换、关闭按钮、「+」按钮），色块条嵌入需避让热区，视觉噪音集中在一行。
- 同样有容器级单例的语义切换代价。

### 方案 C：保持现状

**优点**
- 零改动、零语义迁移成本；每标签独立实例，后台标签数据不丢失。
- 时间线条贴输入区，与「AI 正在为我工作」的手感位置一致（活动发生在对话流末端）。

**缺点**
- 可见性差（本次选型要解决的痛点依旧）：用量警示错过风险最高。
- 底行本就拥挤（双下拉 + 徽章 + 按钮），信息层级不清晰。

### 方案 D：主窗口状态栏

**优点**
- 状态栏常驻、全宽、永远不滚出视野；符合 IDE「状态信息在状态栏」的传统习惯（如 VS Code 的行列号、语言模式）。
- 不占左栏任何空间，三栏共享的存量空间再利用。

**缺点**
- 状态栏在窗口**底部**，比现状的视觉优先级提升有限——用量徽章从「左栏底行」挪到「窗口底栏」，视线距离几乎没变。
- 状态栏是窗口级全局语义，放「当前会话」的私有数据，语义错位感最强。
- 时间线条塞入状态栏会撑高状态栏或压缩色块，破坏状态栏 26px 定高的一体化设计。

### 方案 E：标签内顶部

**优点**
- 保留每标签独立实例——无容器级语义迁移，后台标签各自保留自己的时间线与用量，切回即见。
- 位置移到输出区上方，进入视线首屏，可见性达标。
- 卡片内部自上而下的信息流「状态 → 输出 → 输入」层级通顺。

**缺点**
- 每个标签都有一条，标签栏 + 卡片顶行 + 输出区三行叠加，头部行数偏多，左栏显得重。
- 横向宽度受卡片内边距限制，比方案 A 的左栏全宽略窄（差异很小）。
- 占用一行垂直空间（与 A 相同量级）。

### 方案 F：输入区上方同行摆放

**优点**
- 保留每标签独立实例——与 E 一样无容器级语义迁移，后台标签数据原位保留，切回即见。
- 位置是输出区与输入区的天然分界，属于用户交互视线的高频区（打字、看最新回复都经过这里）；发送前最后一眼可见上下文余量，用量警示的触达时机最合理。
- 同行摆放（左条右徽）把两个底部组件合并为一行：徽章从拥挤的输入区底行（双下拉 + 徽章 + 按钮）解放出来，底行回归纯粹的「模型选择 + 发送」操作行，信息/操作分区更清晰。
- 徽章与「~100%」恒宽占位语义不变，同行右侧对齐天然满足；时间线条横向仍有卡片全宽可用。
- 垂直空间代价约一行（时间线条本身定高），但因徽章从底行挪走、底行不再受徽章约束，净增高度可能小于一行。

**缺点**
- 仍占用约一行垂直空间（压缩输出区，与 A/E 同量级）。
- 位置在输入区**上方**而非对话区上方，阅读长输出时滚动到上方后状态条同样滚出/远离视野——可见性弱于 A（栏顶常驻）与 E（卡片顶行），属于「底部高频交互区可见」而非「全程可见」。
- 输出区与输入区之间的分界行会打断「内容直接流入输入框」的连续感，视觉上加了一道隔断（也可视为优点：分区更明确）。
- 若徽章嵌入条尾（而非独立右侧），时间线条可用宽度略减。

## 6.1 倾向性意见（定夺前记录）

综合可见性、空间代价与语义自然度，**方案 A（左栏级，子选项 A1）、E、F 同属第一梯队**：

- 若接受「时间线/用量 = 当前激活会话的快照」这一心智（与 VS Code 状态栏跟随当前编辑器同理），选 **A**：门面感最强、横向空间最足，是用户提议的合理化版本。
- 若坚持每会话数据物理跟随标签（多标签并行时切回不丢现场），选 **E** 或 **F**：
  - **E（卡片顶行）**：状态信息悬于内容之上，自上而下「状态 → 输出 → 输入」，读输出全程可见，但头部行数偏多。
  - **F（输入区上方同行）**：状态槽落在输出/输入分界，发送前最后一眼可见用量，且顺带把徽章从拥挤的输入区底行解放出来、信息/操作分区更干净；代价是读上方历史输出时状态条同样远离视野。

方案 B 作为空间敏感的备选；方案 D 语义错位明显不建议；方案 C 不解决痛点仅作基线。

另有一个可单独决策的拆分点：两个组件**不必绑定搬迁**——例如时间线条走 A/E 上移、用量徽章留底行（或反之），如认为两者可见性诉求不同可分开定夺。
