## 2. 候选方案对比

| 维度 | A. PyGPT（VS_Code_Python） | B. Multi_Cli_Studio | C. theia-zen（Theia AI） |
|:---|:---|:---|:---|
| 实现语言 | **Python / PySide6**（同栈） | TS/React + Rust | TypeScript + InversifyJS |
| 面板结构 | 垂直 QSplitter：上输出下输入（布局仅 ~530 行） | React 组件群（输入框 4345 行） | ai-chat + ai-chat-ui 约 140 文件 |
| LLM 调用 | openai SDK 直连流式 + **注册表模式**（含 `deepseek_api.py`） | 三套 CLI 子进程协议（JSON-RPC/JSONL/ACP） | `LanguageModel` 统一接口 + 注册表 |
| 消息渲染 | ① QTextBrowser 纯文本（242 行，易剥离）② QWebEngine + Markdown/highlight.js | react-markdown | React 渲染管线 + mermaid |
| 高级机制 | 流式输出、附件 | 中断句柄、审批回环、watchdog | change-set 确认流、`@agent`/`#变量`、工具调用 |
| 代码可直接移植度 | 🟢 高（同栈，剥离 window 引用即可） | 🔴 无（仅协议规格可参考） | 🔴 无（仅接口设计可翻译） |

## 3. 优缺点分析

### 方案 A：PyGPT 对话栏

- ✅ 与项目同栈（PySide6），`ChatOutput(QTextBrowser)` 仅 242 行、依赖少，可直接剥离复用
- ✅ LLM 注册表 + 流式 generator 模式清晰，已有 DeepSeek provider 参考（匹配本地 `api_key/deepseek`）
- ✅ 上下分栏结构与现有 QSplitter 布局体系一致
- ❌ 控件强依赖 `window` 上帝对象，需写适配层（与文件树移植同款工作）
- ❌ `ChatInput` 1734 行体量偏大，需裁剪（大粘贴保护、附件等非必需）
- ❌ change-set、工具调用等 IDE 级 AI 机制缺失，需后续自建

### 方案 B：Multi_Cli_Studio 对话层

- ✅ 三套 AI CLI 协议接入规格独一无二（若未来要嵌 Claude Code 等 CLI 必选）
- ✅ 中断/审批/watchdog 机制设计成熟
- ❌ React + Rust 零代码可移植，运行验证需 Node + Rust 工具链（违反项目约束）
- ❌ 其模型是"编排外部 CLI"，而我们要的是"面板内直连 LLM API"，形态不匹配

### 方案 C：theia-zen AI 子系统

- ✅ 架构最完整：`LanguageModel` 统一接口、注册表、提示词模板、`@`/`#` 上下文变量、change-set 确认流
- ✅ 接口设计与语言无关，可 1:1 翻译为 Python Protocol
- ❌ 50 万行 TS 体系，只能读设计不能搬代码，落地成本最高
- ❌ 运行验证需整套 Node/Electron 环境（违反项目约束）

## 4. 选型结论

🟢 **选定方案 A（PyGPT 对话栏）为主体，吸收方案 C 的接口设计**：

| 层 | 决策 |
|:---|:---|
| 面板 UI | 移植 PyGPT 的上下分栏结构（QTextBrowser 输出 + QTextEdit 输入），与文件树移植同款的"剥离 window 引用"工艺 |
| LLM 调用层 | 借鉴方案 C 的 `LanguageModel` Protocol + 注册表模式，用 Python 自研薄层；首个 provider 为 **DeepSeek**（使用 `api_key/deepseek`，参考 PyGPT `provider/api/openai` 的流式写法与其 `deepseek_api.py` 的端点配置） |
| 消息渲染 | 第一阶段用 QTextBrowser 纯文本渲染（242 行方案）；Markdown/代码高亮渲染留作第二阶段 |
| 方案 B | 本期不采用；若未来接入 AI CLI（Claude Code 等）再回读其协议规格 |

## 5. 裁剪范围（第一阶段）
