## 二、问题定性

1. **防御层替上游缺陷兜底，且成本记在客户端。** 核心缺陷只有一个：Kimi CLI 的 ACP 适配层在内部轮次仍在执行时提前回 `end_turn`。为识别它，客户端被迫读 Kimi 私有 `wire.jsonl`、建四态状态机、加 drain 与同步提示。私有格式一旦变更（或 2.x→3.x 重构），这套代码静默失效或误判。
2. **防御层与主链路互相污染。** 停止按钮的语义被拆成 `session/cancel` 与 `session/close` 两条分流，`_turn_pending`、`_needs_recovery` 同时影响待发闸门、标题状态、下一轮 resume——任何一个布尔量错了，故障表现都是「界面卡住」或「消息发不出去」，而不是「一个明确报错」。
3. **回归面远大于功能面。** 2925 行里真正「把协议翻译成界面」的部分是 `updates.py` 与其周边；其余约一半代码是为了让界面不被假完成骗到。新增任何一个小功能都要先理解这套生命周期，认知成本与出错概率同步放大。
4. **它没有换来根治。** 上游 issue（#5095 / #4944 / #4109 / #4027）至今 open；同步提示只是把错误可见化，不是修复。

用户诉求据此成立：**不要继续在旧实现上做减法，而是新写一条干净链路，能跑通就删旧扶正。**

## 三、候选方案

三个方案的区别只在一点：**客户端要不要继续替上游判断「这一轮到底结束了没有」。**

### 方案 A：完全按官方 ACP 语义，不判断

`session/prompt` 的响应 `stopReason` 即本轮终态：`end_turn` 正常收尾，`cancelled`/`max_tokens`/`refusal` 走失败通道。不读 `wire.jsonl`，不建第二状态机，不做 drain，不推同步提示。收到 `session/update` 就上屏，收到响应就结束。

- 优点：链路与官方文档一一对应，代码量可回到数百行；任何人读代码不需要先读事故报告；上游修好后客户端不需要跟着删补丁。
- 缺点：上游提前回执时，界面会**再次**表现为假完成——提前显示完成、完成音、排队文本注入忙态、停止按钮对隐藏通知轮 no-op。
- 适用前提：接受「这是上游缺陷，客户端如实反映协议」的立场。

### 方案 B：官方语义 + 一条最小旁证

同上，只加一处：响应到达后若同一会话仍持续收到 `session/update`，在输入区提示「轮次已结束但仍有活动」，不读私有文件、不建四态。

- 优点：几百行内挡住最刺眼的假完成，不需要理解 Kimi 私有格式；误报只会多一行提示。
- 缺点：**判不准**——合法的迟到帧、下一轮的首帧都可能触发；提示只影响观感，**不能让停止生效**，停止失效问题照旧。
- 定位：介于 A 与 C 之间的折中，不是根治，只是缓冲。

### 方案 C：保留 wire 终态确认（即现状）

- 优点：目前唯一能真正识别「ACP 说完了但 agent 还在跑」的手段。
- 缺点：私有格式强耦合、维护成本与认知成本最高；本质是把上游缺陷内部化。选 C 等于承认这次重写只剩模块整理，与用户「回到最简单」的目标冲突。

### 对比

| 维度 | A 完全不管 | B 最小旁证 | C wire 终态确认 |
|:---|:---:|:---:|:---:|
| 预计代码规模（不含 `updates.py`） | 最小（约 600 行） | 小（约 700 行） | 现状（约 2300 行） |
| 能识别提前 `end_turn` | ❌ | 🟡 部分 | ✅ |
| 能让停止按钮对通知轮生效 | ❌ | ❌ | 🟡 依赖 `session/close` |
| 依赖 Kimi 私有文件格式 | ❌ | ❌ | 🔴 强依赖 |
| 上游修复后需删代码 | 不需要 | 需删一条提示 | 需删半个包 |
| 误报风险 | 无（不判断） | 中（迟到帧） | 低 |
| 理解成本 | 低 | 低 | 高 |

## 四、结论

**采用方案 A。** 用户明确选择「按官方 ACP 语义收尾，不替上游做判断」，以换取链路的可读与可维护，并接受假完成症状可能重现。

不选 B 的理由：B 的提示既不改变协议行为，也不恢复停止能力，只是把同一个上游缺陷换成另一种观感；一旦加上，后续很难抵抗「再加一点就准了」的引力，容易长回 C。不选 C 的理由见上：它等于放弃本次重写的目的。

**这是有意识的取舍，不是认为旧代码写错了。** 旧代码解决了当时必须解决的问题；现在的前提变了——上游缺陷已定位并上报，客户端可以选择如实反映协议并把问题留在上游。

## 五、接受的代价与配套约定

### 5.1 明确接受的代价

1. 后台任务完成的通知轮、通知轮与用户轮交错的场景，界面可能提前显示完成、排队文本可能被自动注入忙态、完成音可能提前播放。
2. 停止按钮在「ACP 已回执但 agent 仍在跑」的窗口内可能无效（`session/cancel` 覆盖不到隐藏通知轮）。
3. 用户需要自己核对「界面说完成但文件还在变」的情况。

上述症状一律按**上游缺陷**记录并附证据，不得在实施记录里写成「IDE 已修复」。上游跟踪见 `Kimi上游ACP缺陷跟踪任务.md`。

### 5.2 风险控制

- 重写在新分支进行，旧实现完整保留在分支起点与 git 历史中；验收不通过可零成本回退。
- 新旧实现并行注册一段时间，可同机切换对比，避免「删了才知道不行」。
- 若方案 A 落地后假完成在实际使用中不可接受，回退路径是「恢复旧实现」或「重新评估方案 B」，**不得在新实现上临时加私有判定**——那会重新长成 C。

### 5.3 边界

- 只动 Kimi 的 provider 包与注册点；不改 DSH、Local 的协议语义，不改公共 `src/ide/llm/providers/acp/` 连接层。
- 不修改本机 Kimi CLI 与 `~/.kimi-code` 配置。
- 产品能力（子代理卡片、私有用量、图片）第一版先不搬，验收通过后按需逐项加回，避免一开始就长回去。
- 交付方式：分支上留工作树，汇报后等确认再提交；不自动 commit/push。
