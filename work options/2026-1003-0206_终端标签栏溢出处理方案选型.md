# 终端标签栏溢出处理 方案选型

## 一、背景与约束

### 1.1 问题现象

中栏底部终端面板开太多终端标签后，标签栏把中栏布局向左右两边顶宽，左栏（会话面板）被压窄。行业通用叫法为 **标签栏溢出（tab overflow）**，浏览器、VS Code 均通过"标签压缩 / 标签滚动 / 溢出下拉"三类策略处理。

### 1.2 根因（已调研确认）

终端标签栏是裸 `QTabBar`（`src/gui/panels/terminal/panel.py`）：

- 已显式关闭原生滚动箭头 `setUsesScrollButtons(False)`（用户曾反馈原生箭头方向感反转）；
- **从未调用 `setElideMode`**，Qt 默认 `ElideNone`——每个标签的最小宽度都包含完整标题文字 + 关闭按钮；
- 因此 `QTabBar.minimumSizeHint` 随标签数**线性增长**，沿"标签栏 → 终端面板 → 中栏 QSplitter"逐级向上顶，把中栏最小宽度越顶越大；左栏、右栏被压到各自最小宽度下限后，整个窗口的最小宽度也被顶大——形成"标签越多左栏越窄"的死结；
- 加剧因素：AI 会话标签标题为 `🤖 <命令名>`（`src/gui/panels/terminal/agent_bridge.py`），长度不可控。

### 1.3 约束与现有家底

- 技术栈：Python 3.12 + PySide6（QWidget 体系），强制使用项目 `.venv`
- `◀ ▶` 按钮**已存在**（`src/gui/panels/terminal/panel.py` 的 `_step_tab`），语义为"选中左/右邻居标签（循环切换）"，标签 ≥2 时启用——无需新建切换交互
- 项目内无可复用的溢出处理模式：左栏会话标签（`src/gui/panels/chat/tabs.py`）靠 `MAX_TABS = 4` 硬上限回避问题
- `tests/` 中暂无覆盖标签栏溢出/导航的用例
- 主题样式集中在 `assets/themes/base.qss` 的 `#TerminalTabs` 段，当前无任何宽度约束

## 二、名词说明

| 术语 | 含义 |
|:---|:---|
| **Tab overflow（标签栏溢出）** | 标签数量超过标签栏可用宽度时的挤压现象，即本文档要解决的问题 |
| **Elide（省略）** | Qt 文本省略机制，空间不足时以 `…` 截断文本；`ElideNone`=不省略、`ElideRight`=右省略 |
| **minimumSizeHint** | Qt 控件向布局上报的"最小建议宽度"；本问题中正是它随标签数膨胀导致顶宽 |
| **Size Policy Ignored** | Qt 尺寸策略之一，控件的 sizeHint/minimumSizeHint 不再约束布局，布局可自由压缩它 |

## 三、候选方案

### 方案 A：省略号压缩（elide + 解除最小宽度上报）

给标签栏调 `setElideMode(ElideRight)`，并把标签栏水平 Size Policy 设为 `Ignored`（或其最小宽度不再向布局传播）。标签全部保留在栏内，空间不足时 Qt 自动把每个标签压窄、标题以 `…` 省略。

**优点**：

- 改动最小（`src/gui/panels/terminal/panel.py` 数行配置），零新增控件、零新增依赖
- 直接斩断"最小宽度随标签数线性增长"的死结，左栏从此不再被顶窄
- 标签**全部可见可点**，鼠标直点任意标签的交互不丢失；`◀ ▶` 按钮继续可用
- Qt 原生行为，绘制、悬停 tooltip（可补全完整标题）均有成熟支撑
- 与 VS Code 的"tab sizing: shrink"策略同款，用户心智成本低

**缺点**：

- 标签极多时每个标签被压得只剩图标/省略号，辨识度下降，需要靠 tooltip 或 `◀ ▶` 辅助定位
- 压到很窄时关闭按钮可能挤占标题空间，观感变糙（可用 QSS 微调缓解）

### 方案 B：阈值折叠占位（超过 N 个折成"… +k"，靠 ◀ ▶ 切换）

标签数 ≤ N 时正常铺开；超过 N 后只显示当前标签附近的少数几个，其余折叠为"… +k"占位符（或下拉列表），用户用已有 `◀ ▶` 按钮循环切换。

**优点**：

- 最贴合"开多了不铺开、用左右按钮切换"的原始设想
- 可见标签始终保完整标题宽度，辨识度最好
- 标签栏占用宽度有硬上限，布局绝对稳定

**缺点**：

- 裸 `QTabBar` 不支持"部分隐藏 + 占位"，需自绘或换成自定义标签栏控件，**改动量最大**
- 被折叠的标签不可直接点击，必须先 `◀ ▶` 翻到才能操作（关闭非当前标签更绕）
- 需自行维护"当前标签始终在可视窗内"的窗口滑动逻辑，边界情况（关标签、插标签、AI 会话标题更新）多，测试成本高
- 与现有 `_step_tab` 循环语义要重新对齐，交互规则变复杂

### 方案 C：数量上限（仿 ChatTabs 的 MAX_TABS）

设终端标签数量上限（如 8/10），到顶禁用 `+` 按钮并 tooltip 提示，参照 `src/gui/panels/chat/tabs.py` 的 `_refresh_add_button` 模式。

**优点**：

- 实现最简单，项目内已有完全同款先例（ChatTabs），交互一致性最好
- 上限内标签永远完整显示，零视觉退化

**缺点**：

- 治标不治本：上限取值稍大（如 10）时，10 个完整标签宽度叠加**仍可能顶宽中栏**，需同时配合方案 A 才真正解死结
- 硬性限制用户开终端的自由，重度多终端场景会被卡住

### 方案 D：恢复 Qt 原生滚动箭头

重新 `setUsesScrollButtons(True)`，超出宽度的标签隐藏，用原生左右箭头把标签带滚进视野。

**优点**：

- 一行配置，Qt 全托管

**缺点**：

- 历史上已被否：2026-0818-1111 计划（方案 B）正是因为用户反馈原生箭头"标签带反向移动、方向感反转"才关掉它并改为 `◀ ▶` 选中切换，回退等于推翻已定版决策
- 滚动箭头仍会以 sizeHint 参与布局，需配合 Size Policy 调整才彻底解死结

### 方案 E：A + C 组合（省略号压缩 + 宽松数量上限）

方案 A 解死结为主，再叠一个宽松上限（如 16）防止无限开终端导致的辨识灾难与资源膨胀。

**优点**：

- 根治布局问题，同时给极端场景兜底
- 上限宽松，正常用户几乎感知不到限制

**缺点**：

- 两处改动、两条交互规则，复杂度略高于单 A
- 上限数值是拍脑袋参数，将来可能要调

## 五、关键选型因素

1. **死结根因是 minimumSizeHint 线性增长**——任何方案必须包含"标签栏不再向布局上报随标签数增长的最小宽度"这一动作，否则只是缓解不是根治。A/E 天然满足；C/D 单独用不满足。
2. **历史已定版决策**——原生滚动箭头（D）因方向感问题被用户否定过，回退成本高。
3. **用户原始设想**——"开多了用省略号/占位 + 左右按钮切换"，A 的省略号 + 现有 `◀ ▶` 已覆盖其体验目标的大部分；B 是设想的完全体但性价比低。
4. **项目轻改动偏好**——终端面板代码集中、无测试覆盖，小步改动风险最低。

## 六、推荐结论

**已拍板：方案 A（省略号压缩）+ 方案 C（数量上限，暂定 40）组合**（2026-10-03 需求方确认）。

落地要点：

1. 方案 A 为主：`setElideMode(ElideRight)` + 标签栏最小宽度不再向布局传播，斩断死结；
2. 方案 C 兜底：`MAX_TABS = 40`（用户会话与 AI 会话同口径，按标签总数计），到顶禁用 `+` 并 tooltip 提示；40 远超正常使用量，属防呆而非约束；
3. 不采用 B（阈值折叠占位）——改动量大、收益相对 A 增量有限；若 A+C 实测体验仍不足再回评。
