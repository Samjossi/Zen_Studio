# Git 提交拓扑图现成实现复用方案选型

## 一、背景与纠偏

当前内嵌 Git 页使用 `git log --graph` 的字符前缀，再由 `GraphColumnDelegate` 把 `*`、`|`、`/`、`\`、`-`、`_`、`.` 等字符转换为 QPainter 图元。虽然已经改成 graph-only，但本质仍是“Git 字符画的图形化翻译器”：

- 布局被 Git 的文本格和额外连接行牵着走，节点、曲线与行之间的关系不够直接。
- 需要持续盘点字符形态，复杂合并的视觉效果和断线风险由本项目自行承担。
- 本轮继续调整字符图元只能做局部修补，不能回应“不要继续造轮子”的核心诉求。

本次重新盘点 `参考代码/`，目标是寻找已有提交 DAG 产品实现，优先复用其算法、视觉几何、交互语义和测试，不再围绕 ASCII 字符继续设计一套新图。

## 二、结论先行

**推荐移植 Theia SCM History Graph：以其 parents → lanes 算法为数据核心，以其 VS Code 风格 SVG 几何为视觉基线，再用项目现有 PySide6 控件体系承接。**

需要明确：

- 参考区**没有可直接 import 或 pip 安装的 PySide6 Git 提交图控件**。
- Theia 实现是 React + TypeScript，不能原样在 QWidget 中运行；但其核心算法是无框架纯函数，渲染部分也主要是确定的 SVG 路径，可完整移植，不需要重新设计 DAG 或猜测字符含义。
- 因此推荐的是**复用现成产品实现的设计、算法与测试**，不是引入 WebEngine，也不是继续修补当前字符画转换器。
- 如果要求“零移植、直接运行”，本地参考代码没有满足条件的候选，不应把 Mermaid 或通用流程图库误称为现成 Git 历史视图。

## 三、调研结果

### 3.1 Theia SCM History Graph：唯一完整命中的产品实现

核心文件：

| 文件 | 已有能力 | 可复用价值 |
|:---|:---|:---|
| `参考代码/theia-zen/packages/scm/src/browser/scm-history-graph-lanes.ts` | 从有序 commit id + parentIds 计算每条提交的泳道、颜色和边 | 核心纯函数，无 React/Theia 依赖，可作为移植主体 |
| `参考代码/theia-zen/packages/scm/src/browser/scm-history-graph-widget.tsx` | 每行 SVG 图元、节点、分叉/合并曲线、HEAD、选中、悬停和 refs | 提供完整视觉几何与交互语义 |
| `参考代码/theia-zen/packages/scm/src/browser/scm-history-graph-lanes.spec.ts` | 线性、分支合并、独立并行、八爪鱼合并、泳道释放复用、兄弟分支、颜色循环等测试 | 可直接翻译成参数化回归，避免重新摸索边界 |
| `参考代码/theia-zen/packages/scm/src/browser/scm-history-graph-model.ts` | parents 数据进入图模型、加载后统一重算 | 数据职责参考，不移植其分页和依赖注入 |
| `参考代码/theia-zen/packages/scm/src/browser/scm-history-graph-tooltip.ts` | 作者、双时间、提交正文、refs、hash 的悬停信息组织 | graph-only 的按需解释参考 |
| `参考代码/theia-zen/packages/scm/src/browser/style/scm-history-graph.css` | 行高、hover、选中、文本与 refs 布局 | 状态样式参考，颜色仍映射本项目主题 |

其图模型只有三类边：

| 类型 | 含义 | 视觉表达 |
|:---|:---|:---|
| `pass-through` | 其他活跃泳道穿过当前提交行 | 从行顶到行底的竖线 |
| `branch-out` | 当前提交连接到下方另一父提交泳道 | 从当前节点中心向行底目标泳道的三次贝塞尔曲线 |
| `merge-in` | 上方已有泳道汇入当前提交 | 从行顶来源泳道向当前节点中心的三次贝塞尔曲线 |

这套表达直接消费真实 parents，不再存在“纯连接行”“未知图线字符”或字符格端点偏移问题。每个提交固定占一行，活跃边与提交节点在同一模型中描述。

其默认视觉几何也已明确：

- 泳道宽度 22px，节点位于泳道中心。
- 提交行高 22px，节点圆心位于行中。
- 普通节点半径 5px；HEAD 外圆半径 7px，并带主题背景色内点。
- 节点线只在确有上/下连接时绘制，曲线从节点中心起始或终止，不穿过节点。
- 节点最后绘制，覆盖曲线端点，保证连接外观干净。

### 3.2 Mermaid：有 GitGraph 图，但不是提交历史控件

本地依赖中存在 Mermaid GitGraph 实现：

- `参考代码/deepseek-harness/node_modules/.pnpm/mermaid@11.17.2/node_modules/mermaid/`
- `参考代码/theia-zen/node_modules/mermaid/`

**定位：文档绘图引擎，不是本次现成 SCM 图控件。**

### 3.3 Multi_Cli_Studio React Flow：只有通用流程图，不是 Git 拓扑

`参考代码/Multi_Cli_Studio/package.json` 声明了 `@xyflow/react`，实际用于自动化工作流编辑和运行画布；其 `GitPanel.tsx` 是工作区变更、提交与 diff 面板，没有提交 DAG 渲染。

React Flow 能提供节点拖拽和通用边，但泳道分配、提交排序、合并语义仍需自行实现，且会把只读 Git 图带入不需要的画布交互。

**定位：通用节点编辑器，不选作 Git 图底座。**

## 四、候选方案

### 方案 A：移植 Theia 泳道算法与 SVG 视觉，PySide6 原生承接（推荐）

保留现有 `GitGraphPanel`、`GitGraphContent`、完整弹窗和加载边界，只替换结构化取数与图模型/绘制内核：

1. 结构化 Git 输出提供完整 commit id 和有序 parent ids，并使用 `--topo-order` 保证输入满足参考算法前提。
2. 将 `computeGraphRows()` 翻译为无 Qt 依赖的 Python 函数，输出与参考一致的 lane/color/edges/hasTopLine/hasContinuation。
3. 按参考 SVG 路径和节点尺寸绘制三类边；不再消费 `git log --graph` 字符前缀，不再生成连接行。
4. 内嵌页继续 graph-only；完整弹窗可共享同一图列，同时保留文本四列。
5. 翻译参考算法测试，并用真实复杂仓库比较提交顺序、节点泳道和边集合。

**优点**

- 有完整产品算法和测试作为真值来源，不需要自研 DAG。
- 视觉直接对齐 VS Code/Theia 的成熟形态，不再围绕字符画反复调外观。
- 保留 Qt 原生主题、键盘、tooltip、滚动、打包与无头测试体系。
- 数据模型更直接，复杂合并不需要新增字符补丁。

**缺点**

- 仍需做一次 TypeScript → Python、SVG → Qt 绘制语义的移植，不是零代码依赖接入。
- 当前 `CommitRow` 缺少完整 id 和 parents，需要调整结构化取数。
- 需要逐项验证移植等价性，不能只凭几张截图认定算法正确。
- 实质移植需保留来源版权与许可证信息。

### 方案 B：用 WebEngine 直接运行 Theia React/SVG 组件

**优点**

- 看似能保留最多 JSX、SVG 和 CSS。
- 浏览器可直接运行 SVG 与前端虚拟列表。

**缺点**

- 当前组件依赖 Theia 的 model、provider、依赖注入、hover、菜单和 URI 服务，不能直接抽出一个可运行控件。
- 引入 WebEngine、前后端桥接、打包体积和进程复杂度。
- 仍需重做 Git 数据、主题、选中状态和桌面交互，并非真正零改造。
- 与项目 QWidget/QSS 技术栈割裂。

**结论：否决。**

### 方案 C：Mermaid GitGraph 生成静态 SVG

**优点**

- 已有成熟的文档级 Git 分支示意渲染。
- SVG 输出外观可快速得到。

**缺点**

- 仍需把真实 Git DAG 转成另一套 DSL，且布局目标不是 SCM 提交列表。
- 逐提交交互、长列表、刷新恢复和主题接入均需另写。
- 需要 Web/JavaScript 运行环境或额外预渲染链路。

**结论：不适合本次，否决。**

### 方案 D：继续维护当前 Git 字符前缀 + QPainter 转换

**优点**

- 取数改动最少，无需 parents 字段。
- 可继续复用 Git 自身的文本布局。

**缺点**

- 仍需本项目维护字符覆盖、连接行和视觉修补。
- 文本布局与图主视觉存在结构性冲突。
- 正是本次希望退出的路线。

**结论：停止作为长期主形态；仅保留现有彩色富文本作为失败降级。**

## 六、推荐实施边界

### 6.1 应移植

- `computeGraphRows()` 的完整状态机，包括第一父继承、额外父分支、已有父汇入、重复泳道收敛、根节点和泳道释放复用。
- 三类边的起点、终点和控制点，以及普通/HEAD 节点的层次关系。
- 参考测试中的拓扑样例和边断言。
- 整行 hover/选中与完整提交信息 tooltip 的语义。

### 6.2 应保留本项目现有实现

- `GitStatusService` 的仓库可用性结论，不新增第二套仓库探测。
- 进入页面和手动按钮两类加载入口，隐藏时不查询。
- `--all` 引用视野、500 条上限、空仓库/非仓库/失败占位和彩色富文本降级。
- graph-only 内嵌页、完整四列弹窗、下方 `ChangesPanel` 及 M/U/D 双击行为。
- 当前主题 `TERMINAL_PACK`、选中与横纵滚动恢复，不把 Theia CSS 变量直接搬进项目。

### 6.3 明确不移植

- React、Virtuoso、Theia 依赖注入和 provider 框架。
- 提交展开、变更文件懒加载、右键写操作和分页加载。
- “第一行即 HEAD”的推断；HEAD 继续由真实 refs 判定。
- Theia 的横向隐藏策略；本项目超宽泳道仍允许横向滚动。

### 6.4 取数改造前提

当前结构化命令只取短 hash，未提供 parents。采用方案 A 时必须：

- 同时取得完整 commit id 与完整 parent ids，不能只用短 hash 做图节点身份。
- 使用 `--topo-order`，不能假设普通日期排序必然满足算法前提。
- 保留短 hash 作为显示字段，refs 和提交元数据解析沿用现有逻辑。
- 结构化主取数可以移除 `--graph`；`fetch_commit_graph()` 的彩色文本降级继续独立保留。
- 500 条截断时，未加载父节点只能作为图边界处理，不伪造提交记录。

## 七、验证与视觉验收建议

1. **算法等价**：先翻译参考纯函数和测试，确保线性、交叉合并、三父以上合并、兄弟分支、独立根、泳道复用全部通过。
2. **真实仓库对照**：在项目 `.temp/` 构造连续分叉、长并行、八爪鱼合并和共享祖先 fixture，断言每条预期 parent 边恰好出现一次。
3. **像素连续性**：验证行顶/行底端点、曲线到节点中心、节点覆盖线端、HEAD 内环和超宽滚动。
4. **前后视觉对照**：使用同一复杂仓库和同一生产 QSS 截帧；重点比较当前字符转换与 Theia 几何，不再以“有像素”作为美观验收标准。
5. **回归边界**：加载次数、隐藏不查询、500 条、降级、完整弹窗、下方变更列表和 M/U/D 行为继续通过。
6. **最终门禁**：执行聚焦测试、视觉闭环与 `bash scripts/check.sh`。
