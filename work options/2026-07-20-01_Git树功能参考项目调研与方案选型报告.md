# Git 树功能参考项目调研与方案选型报告

## 一、背景与约束

Zen_Studio（Python 3.12 + PySide6 桌面 IDE）计划新增 **Git 树功能**，即以图形化方式展示仓库提交历史（commit graph / DAG：分支泳道、分叉与合并线条、ref 徽标、提交详情与 diff 联动等）。

本报告对三个参考项目进行调研，确认各自是否存在该功能、实现方式如何，并从**可移植性、优缺点、技术栈匹配度**等维度对比，给出移植/自研建议。

**本项目硬约束**：

- 技术栈为 **Python + PySide6（QWidget 体系）**，非 Web 技术栈，前端 React/TypeScript 代码无法直接移植，只能移植**算法与思路**。
- 目前项目依赖中**无任何 Git 访问库**（无 GitPython / pygit2），Git 数据层需从零引入。
- 强制使用项目 `.venv` 的 Python。

## 二、各参考项目调研结论

### 2.1 theia-zen（Eclipse Theia fork，TypeScript/React/Node.js）

**结论：存在完整的 Git 树功能，且质量最高，是三个项目中唯一的"真·提交图"实现。**

- 该 fork **删除了上游 `@theia/git` 包**，Git 能力完全由 VS Code 内置 git 插件（`plugins/vscode.git` v1.108.2，内部 spawn 系统 `git` CLI）通过插件主机提供。
- 在 `packages/scm` 中自研了仿 VS Code "Source Control Graph" 的提交历史图组件：

| 关键文件 | 作用 |
|---|---|
| `packages/scm/src/browser/scm-history-graph-widget.tsx`（711 行） | 图组件主 Widget（React + react-virtuoso 虚拟列表 + 行内 SVG） |
| `packages/scm/src/browser/scm-history-graph-model.ts` | 数据模型：分页加载（每页 50 条）、去重、触发 lane 计算 |
| `packages/scm/src/browser/scm-history-graph-lanes.ts` | **DAG 泳道（lane）计算算法核心**：为每个提交计算 lane 列、颜色（0–7）、边类型（pass-through / branch-out / merge-in） |
| `packages/scm/src/browser/scm-history-graph-helpers.ts` / `-tooltip.ts` | ref 徽标（分支/tag/远程）、Markdown 悬浮提示 |
| `packages/scm/src/browser/scm-main.ts`（plugin-ext 内） | RPC 桥接：前端 → 插件侧 `SourceControlHistoryProvider` |
| `*.spec.ts`（约 800 行测试） | 图算法单元测试（测试覆盖充分） |

- **渲染方式**：每行左侧一个内联 SVG，直线（pass-through）+ 三次贝塞尔曲线（branch-out 分叉 / merge-in 合并），8 色循环，结构"完全对齐 VS Code"。
- **数据链路**：widget → model → `ScmHistoryProvider.provideHistoryItems` → plugin-ext RPC → vscode.git 插件 → 系统 `git log`。前端根据提交的 `parentIds` 计算 DAG 布局。
- **交互**：ref 徽标、HEAD 标记、右键菜单（checkout/cherry-pick/revert 等，对接 VS Code `scm/historyItem/context` 贡献点）、展开文件变更、打开 diff、分页加载。

**依赖**：系统 `git` CLI（无 dugite/isomorphic-git）、React + react-virtuoso、自研 lane 算法（零第三方 graph 库）。

### 2.2 Multi_Cli_Studio（Tauri 2 + React 19 + Rust）

**结论：有完整的 Git 面板（提交历史三栏视图），但不存在真正的提交图（DAG）；其"图形"仅是装饰性单竖线 + 圆点。**

- **数据层（值得参考）**：Rust 端 `src-tauri/src/main.rs` 直接调用系统 `git` CLI，使用
  `git log --decorate=short --date-order --pretty=format:%H%x1f%h%x1f%s%x1f%B%x1f%an%x1f%ae%x1f%ct%x1f%P%x1f%D%x1e`
  解析输出，**已解析 `parents`（父提交列表）和 `refs`（分支/tag 装饰）字段** —— 即画 DAG 所需原料齐全，但前端未利用。SSH 远程工作区通过内嵌 Python 脚本远程执行 git。
- **UI 层**：`src/components/settings/DesktopGitSection.tsx`（4650 行）三栏布局（分支树 | 提交列表 | 提交详情+diff）；提交栏每行一个圆点 + 一根贯通竖线（纯 CSS，`.git-history-graph*` 类），**无泳道、无分叉/合并曲线**。分支栏按分支名 `/` 前缀构建文件夹式树（如 `feature/xxx` 折叠），是"名字树"而非拓扑树。
- 仓库已有 `@xyflow/react`（React Flow）和 echarts，但**均未用于 git**，仅用于工作流画布与仪表盘。

**对本项目的价值**：`git log` 的 format 串与解析方案可直接借鉴（`%x1f`/`%x1e` 分隔符技巧、parents/refs 提取）；图形化部分无代码可复用。

### 2.3 VS_Code_Python（实为 PyGPT，PySide6 桌面应用）

**结论：不存在任何 Git 相关功能**（目录名有误导性，实为 PySide6 写的 AI 聊天助手）。无 GitPython/pygit2/dulwich 依赖。

但存在两类与 Git 树实现**技术栈完全匹配（PySide6）的可复用 UI 基础设施**：

| 路径 | 可借鉴点 |
|---|---|
| `src/pygpt_net/ui/widget/filesystem/explorer.py` | `MultiDragTreeView(QTreeView)` + `QFileSystemModel`：model/view 模式、多选拖拽、右键菜单、滚动定位 —— 可直接套用到提交列表/变更文件树 |
| `src/pygpt_net/ui/widget/lists/base.py` | `BaseList(QTreeView)`：列表面板基类（选择锁定、滚动恢复），提交列表的最简起点 |
| `src/pygpt_net/ui/widget/node_editor/` + `src/pygpt_net/core/node_editor/graph.py` | **基于 QGraphicsScene/QGraphicsView 的节点-连线编辑器**：NodeGraph 模型、节点/边增删、撤销/重做命令栈 —— 是项目中唯一"带图形化连线"的实现，其 Edge 绘制机制在原理上可改造为分支/合并曲线绘制 |

**对本项目的价值**：不提供任何 Git 逻辑，但提供了 PySide6 下实现图形连线的现成范式（QGraphicsView 路线）。

## 四、可移植性分析

三个项目**没有任何一个的 Git 树代码可以直接复制进 Zen_Studio**（两个是 Web 栈、一个无 Git 功能），但三者恰好互补，拼出了完整的实现蓝图：

```
Git 数据层        ← 借鉴 Multi_Cli_Studio 的 git log format 串（Rust→Python 易翻译）
DAG 泳道算法      ← 移植 theia-zen 的 scm-history-graph-lanes.ts（纯算法，TS→Python 可行）
图形渲染层        ← 借鉴 VS_Code_Python 的 QGraphicsScene/QGraphicsView 范式（或 QTreeView + 自绘委托）
```

1. **算法移植（theia-zen → Python）**：`scm-history-graph-lanes.ts` 是纯数据结构与算法（输入 commit 列表 + parentIds，输出每行的 lane/颜色/边类型），不依赖 React/DOM，翻译为 Python 的工作量可控（估计 300–500 行），且其 800 行单测可作为移植正确性的对照基准。**这是最有价值的移植标的**。
2. **数据层（参考 Multi_Cli_Studio）**：用 `subprocess` 调系统 `git log --pretty=format:...%P...%D...` 并解析，无需引入 pygit2 等重型依赖，与项目现有轻依赖风格一致；也可选 GitPython 换取 API 便利性（见方案对比）。
3. **渲染层（参考 VS_Code_Python）**：PySide6 下两条路线——
   - **路线 A（推荐）**：`QListView/QTreeView + 自定义 QStyledItemDelegate`，在行左侧自绘泳道线条（对齐 theia-zen/VS Code 的"列表行内嵌图"形态，虚拟滚动性能好，交互简单）；
   - **路线 B**：`QGraphicsScene/QGraphicsView` 自由画布（对齐 GitLens 风格，可缩放平移，但行选择、列表联动、性能都要自己处理，复杂度高）。

## 五、候选方案与优缺点

### 方案 A：数据层调系统 git CLI + 移植 theia-zen lane 算法 + QTreeView 委托自绘（推荐）

- **优点**：
  - 零新增重型依赖（保持项目轻依赖风格，仅需 stdlib `subprocess`）；
  - 拿到的是经过验证、有单测对照的核心算法，视觉效果对齐 VS Code Source Control Graph；
  - QTreeView 委托路线与项目现有面板体系（QWidget）集成成本最低，天然支持虚拟化大仓库；
  - SSH/远程场景未来可参考 Multi_Cli_Studio 的远程执行思路扩展。
- **缺点**：
  - 算法翻译（TS→Python）与委托自绘均需手工完成，存在一定的理解成本；
  - 依赖系统装有 git（需做缺失检测与降级提示）；
  - 自绘委托要实现贝塞尔曲线（branch-out/merge-in），需要细致的坐标计算工作。

### 方案 B：引入 GitPython/pygit2 + 自研简化图（仅单泳道竖线+圆点，类似 Multi_Cli_Studio 现状）

- **优点**：实现最快（1–2 天量级）；GitPython API 友好，提交遍历、diff、分支操作开箱即用；先交付可用的提交历史面板，图后续迭代。
- **缺点**：
  - 无分叉/合并可视化，"树"的卖点缺失，与 Multi_Cli_Studio 一样只是装饰线；
  - 新增第三方依赖（pygit2 还带 libgit2 二进制依赖，打包复杂）；
  - 后续升级为真 DAG 时，数据层抽象可能需要返工。

### 方案 C：QGraphicsView 自由画布全景图（参考 VS_Code_Python node_editor 范式）

- **优点**：视觉上限最高，可做缩放、平移、节点拖拽（未来交互式 rebase 等高级功能的载体）。
- **缺点**：开发量最大；大仓库（上万提交）性能需自行做视口裁剪；与"提交列表+详情"的常规 IDE 交互模式偏离，需要额外做大量联动；本项目阶段而言投入产出不合理。

### 方案对比小结

| 维度 | 方案 A（推荐） | 方案 B | 方案 C |
|---|---|---|---|
| 真·DAG 可视化 | ✅ | ❌ | ✅ |
| 开发成本 | 中（约 3–5 天） | 低（1–2 天） | 高（1–2 周） |
| 新增依赖 | 无 | GitPython/pygit2 | 无 |
| 大仓库性能 | 好（列表虚拟化） | 好 | 需自行优化 |
| 视觉对齐 VS Code | ✅ | ❌ | 可超越 |
| 后续扩展性 | 高（菜单/diff 联动易加） | 中（需返工） | 最高（但过度设计） |

## 六、推荐结论与后续实施要点

**推荐方案 A**，可分两步走以控制风险：

1. **第一步（MVP）**：实现数据层（`subprocess` + git log format 串，参考 Multi_Cli_Studio 的字段选择）+ QTreeView 提交列表（参考 VS_Code_Python 的 `BaseList`/`explorer.py` 模式）+ 分支/tag 徽标 + diff 联动 —— 先交付可用的历史面板。
2. **第二步（图形化）**：移植 theia-zen `scm-history-graph-lanes.ts` 算法为 Python 模块（同时翻译其单测作为验收基准），在列表委托中自绘泳道 SVG 等价的 QPainter 贝塞尔曲线。

**实施要点**：

- 数据层封装为独立模块（如 `core/git/`),接口对齐 `HistoryProvider` 思路（输入 ref/分页参数，输出带 `parents`/`refs` 的提交列表），便于未来换 GitPython 或支持远程仓库；
- 算法模块与 UI 解耦，纯函数输入输出，先跑通 theia-zen 单测的对应用例再接 UI;
- 注意 `git log` 的 `--date-order`/`--topo-order` 选择对泳道稳定性的影响（theia-zen 依赖插件侧排序，本项目需自行确定）;
- 系统无 git 时的降级策略需在设计中明确。
