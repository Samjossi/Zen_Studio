## 1. 目的与勾选方式

目标是把「一家厂商的变化只影响该厂商」落实到完整垂直切片，而不只停留在文件搬家或卡片拆分。本文列出当前可识别、具有实际拆分价值的候选项，并保留公共稳定机制的边界。

使用方法：

- 将希望纳入目标架构的条目由 `- [ ]` 改为 `- [x]`；可直接修改条目描述或添加附注。
- 未勾选项不进入后续实施计划；勾选表示「纳入目标范围」，不表示一次性全部实施。
- V01 的「卡片严格分开」已在讨论中原则确认，仍保留复选框供最终范围确认。
- 已依据 `2026-1120-1818_Kimi与DSH后台厂商隔离及公共层收口落地计划.md` 自动勾选 **V01–V11、V17、V19**，以及有限口径的 **V18**。V18 仅指真实旧数据确需兼容时由对应厂商承接，不包含预设多版本适配层；其余项未纳入当前计划。上述勾选项的**实际落地状态以 §3.1 为准**：T0–T7 只完成了物理隔离与主要语义归属，不等于每一项都已完成模块级拆分。
- **2026-11-21 修订**：新增收尾项 **V20–V24**，并纳入 **V12**；**V13 并入 V21**，不单独立项。V14–V16 保持未选，V18 保留条件口径并下调评分。classic 旧文本轨下线已由用户确认（见 V20）。
- 本轮推荐范围与顺序见 §5.5，实施计划见 `2026-1121-0049_后台厂商垂直切片收尾与能力契约落地计划.md`；本文仍不授权实施。
- 推荐度是架构建议，不代表已替用户拍板；最终以用户调整后的勾选结果为准。

## 2. 评分口径

| 维度 | 取值与含义 |
|:---|:---|
| 复杂度 | **小**：单文件或少量纯函数可收口；**中**：少量模块与测试可收口；**大**：多个生产模块、状态流或存档需联动；**很大**：跨后台、GUI、持久化或多条状态链，必须分阶段 |
| 收益 | **高**：显著减少跨厂商波及或消除现有方向错误；**中高**：明显改善边界，但主要集中于局部；**中**：有维护价值，短期缺陷风险较低；**中低**：局部维护价值，当前不足以单独立项 |
| 推荐度 5/5 | 核心边界，建议纳入首轮目标架构 |
| 推荐度 4/5 | 推荐拆分，在核心边界稳定后跟进 |
| 推荐度 3/5 | 可选；建议触及对应功能时顺手拆，不必单独大改 |
| 推荐度 2/5 | 暂缓；当前收益不足以证明成本 |
| 推荐度 1/5 | 不建议拆，应保留公共实现 |

### 3.1 实施现状与判断依据

T0–T7 已完成主计划列出的物理隔离、mapper 拆分、卡片拆分、权限分类、守卫与回归；以下只列与「是否真正完成」相关的判断依据。

**已落地**：V01、V02、V03、V08、V10、V17；V04 基本落地（注册表静态元数据待 V12）。后台与卡片已按厂商分目录，`acp/updates.py` 与公共 `cards.py` 已删除，权限分类与中性 `PermissionRequest` 已落地，卡片的工厂/presenter 与依赖守卫已有回归。

**部分落地或仅完成归属**：

- **V05**：能力值已分散到各 provider，但 GUI 仍以鸭子类型读取 `supports_images_override`、`post_turn_usage_grace_s`、`stall_watchdog_enabled`、`recovery_pending`；`base.py` 只声明了后两者，缺少统一快照。
- **V06**：错误、认证与 stopReason 已由各 provider 自持；但共享审批框标题仍写「Kimi ACP 请求执行工具」，对 DSH/Local 是错误文案。
- **V07/V09/V11**：归属正确，模块未拆。Kimi 的 session_index/wire/字节游标/轮内轮询/轮后宽限/sidecar 与 DSH 的会话日志差量仍堆在各自 `provider.py`；上一轮主计划 §5.1 列出的 `kimi/wire.py` 从未创建。
- **V19**：守卫以固定 token 词表为主，抓 import 方向有效；抓不住通用 GUI 读取 `command/output/summary/status/error/is_subagent` 这类字段级违约，也抓不住中文厂商文案、`kimi_wire_sidecar` 设置键与能力鸭子接口。

**未做**：V12、V14、V15、V16、V18。其中 V18 的原始收益评估偏高：会话存档只保存 user/assistant 正文与图片引用，思维链、工具卡、todo、用量均不入存档，因此「历史旧载荷兼容」目前没有真实消费者，只剩 DSH developer preview 的版本漂移需要按证据处理。

**评分修订**（按实施后的代码证据，不改变原始拆分内容）：

| 项 | 原评 | 现评 | 依据 |
|:---|:---:|:---:|:---|
| V13 | 3/5 | 2/5 | 实际只剩 `kimi_wire_sidecar` 一个无 UI 的设置键，并入 V21 的厂商选项机制即可 |
| V14 | 4/5 | 3/5 | 已知厂商差异主要是空 text 占位；图片降级文案问题归 V21，不需要独立拆 Prompt 策略 |
| V15 | 3/5 | 2/5 | Kimi 私有轮次同步与失配提示已随原生 ACP 链路移除，剩余通知量很小 |
| V16 | 3/5 | 2/5 | 日志上下文已天然分厂商；脱敏与 stderr ring 应继续共享，单独拆收益低 |
| V18 | 4/5 | 3/5 | 存档不含工具卡，历史载荷兼容无真实消费者；仅在 DSH 版本漂移取证后启用 |

**不打算再拆的地方**：三家 `cards.py` 目前是约 905 行的受控复制，彼此只有注释差异；继续按卡片拆文件只会扩大改动面，不增加隔离收益。`mapper` 内部词表与公共 `permission_policy` 同理不再细分。

## 4. 可勾选拆分项

### A. 协议、数据与界面核心

- [x] **V01 厂商数据载荷、具体卡片、卡片工厂与 presenter**
  - **拆分内容**：各厂商独立 `models.py`、具体卡片、工具名分派、迟到字段覆盖、卡片更新与嵌套展示；取消统一 `card_kind`、公共具体卡片和公共 `make_tool_card()`。
  - **优点**：卡片格式与后端真实能力一致；一家改布局、字段或交互不碰另一家；消除 GUI 同时认识多家工具名的问题。
  - **缺点**：后台、载荷、Qt 卡片和测试需同步迁移，工作量最大；通用 UI 修复需逐家回归。
  - **保留共享**：`ToolCard` 生命周期、折叠、复制、颜色、图片显示、文本截断等纯技术基础件。
  - **评判**：复杂度 **很大**｜收益 **高**｜推荐度 **5/5，核心必拆，且必须连同 presenter 一起拆**。

- [x] **V02 ACP `session/update` 映射与工具字段解析**
  - **拆分内容**：Kimi 显式 kind、camelCase、迟到 rawInput；DSH kind=other 兜底、snake_case、工具字段、todo、图片与 content 解释分别归入本厂商 mapper。
  - **优点**：直接拆除当前 `acp.py` 最大的厂商语义汇集点；新增字段不再修改公共键表；帧问题可定位到单一厂商。
  - **缺点**：两家会保留部分相似的 content/diff 处理代码；需要大量逐帧等价测试防止静默丢信息。
  - **保留共享**：标准 text/reasoning/usage、标准 ACP content 块、ANSI 清理、通用截断和标准 oldText/newText diff 纯函数。
  - **评判**：复杂度 **大**｜收益 **高**｜推荐度 **5/5，是其他垂直拆分的前置基础**。

- [x] **V03 会话生命周期、取消、恢复与轮次收尾**
  - **拆分内容**：initialize、session/new、模型应用、cancel、close、断管、session/resume、轮次锁、响应等待和收尾顺序由各厂商自行组合。
  - **优点**：Kimi 的恢复与轮次一致性不再向 DSH/Local 泄漏；DSH 可独立调整会话重建和失败策略；避免共同基类隐藏流程差异。
  - **缺点**：连接关闭、竞态和取消逻辑重复后，每家都需单独验证孤儿进程与线程解封；重构期间回归风险高。
  - **保留共享**：JSON-RPC 请求原语、连接代次、进程失效通知、写锁和本地中断机制。
  - **评判**：复杂度 **大**｜收益 **高**｜推荐度 **5/5，核心必拆，禁止以共同会话基类再次合并**。

- [x] **V04 模型目录、显示名、推理强度与配置切换**
  - **拆分内容**：Kimi 动态 `provider list --json`、目录派生和 `thinking`；DSH 自有模型值、显示名和 `reasoning_effort`；Local 自有 GGUF 枚举分别归位。
  - **优点**：模型目录变化只影响对应厂商；配置键、默认值和失败降级不再互相牵制；注册表只看不透明数据。
  - **缺点**：目录缓存、刷新和 UI 回退需逐家测试；部分注册装配代码会重复。
  - **保留共享**：通用缓存机制、后台/接口/模型菜单、无效选择回退策略和不透明字符串契约。
  - **评判**：复杂度 **中**｜收益 **高**｜推荐度 **5/5，边界清楚，适合较早完成**。

- [x] **V05 能力探测与功能开关**
  - **拆分内容**：图片、terminal、强度、session/resume、子代理、附件等能力的静态兜底、initialize 实测和运行时刷新由各厂商维护。
  - **优点**：避免以一家能力推断另一家；GUI 只消费能力，不再按厂商名写分支；上游新增能力时修改面明确。
  - **缺点**：能力来源增多后需要统一的最小读取约定；运行时能力变化仍要处理 UI 刷新时机。
  - **保留共享**：能力查询的通用接口、无能力时的 UI 隐藏/禁用机制，不包含具体能力默认值。
  - **评判**：复杂度 **中**｜收益 **高**｜推荐度 **5/5，是消除 GUI 厂商特判的必要项**。

- [x] **V06 异常、认证、stopReason 与用户诊断**
  - **拆分内容**：认证关键词、凭据提示、错误码、stopReason、恢复失败、进程退出解释及用户动作建议分别归各厂商。
  - **优点**：避免公共关键词误匹配；错误文案能准确指向本厂商修复动作；一家新增终态不会改变另一家成败判断。
  - **缺点**：错误矩阵和测试数量增加；部分底层连接错误文本会重复。
  - **保留共享**：异常传输机制、连接死亡的通用技术事实、日志脱敏；不共享厂商错误解释。
  - **评判**：复杂度 **中**｜收益 **高**｜推荐度 **5/5，改动集中且隔离收益直接**。

### B. 用量、权限与状态流

- [x] **V07 上下文用量、Token 消耗、输出速度与轮后收尾**
  - **拆分内容**：Kimi ACP+wire 双源、轮内轮询、轮后宽限、请求配对；DSH 会话日志差量、usage 推送和事件基线分别实现。
  - **优点**：避免统一收尾窗口改变另一家时机；用量口径、去重和缺失处理独立；消除面板对 Kimi 轮后宽限的特判。
  - **缺点**：涉及时序、线程和真实 token 数据，验证成本高；两家都要维护相似的缺失值与迟到数据处理。
  - **保留共享**：`UsageStats`、`TurnConsumption` 等 Zen 稳定统计载荷，以及 GUI 数字展示；不共享采集流程。
  - **评判**：复杂度 **大**｜收益 **高**｜推荐度 **5/5，核心必拆，依赖 V11 的私有日志边界**。

- [x] **V08 权限分类、提问识别与交互回环**
  - **拆分内容**：各厂商识别自己的提问工具、问题结构和答案选项，再交给 Zen 权限策略；提问卡如何展示和回传由本厂商实现。
  - **优点**：公共策略不再认识 Kimi 工具名；DSH 提问能力可按实测独立演进；避免 auto_all 误自动回答。
  - **缺点**：属于安全与交互交叉面，回归要求严格；权限队列、QuestionBridge 和卡片需同步改造。
  - **保留共享**：权限四态、危险命令黑名单、optionId 原样回传、队列串行和超时兜底。
  - **评判**：复杂度 **中**｜收益 **高**｜推荐度 **4/5，推荐拆，但不能借拆分启用未实证提问能力**。

- [x] **V09 子代理、层级事件与迟到帧账本**
  - **拆分内容**：Kimi wire sidecar、父子合成和轮次观察；DSH 工具 ID、kind 回填和状态推进；各厂商 input/todo/derived-kind 账本实例化。
  - **优点**：消除模块级跨后台状态；子代理展示不再依赖另一家 ID 形态；迟到信息的生命周期清晰。
  - **缺点**：与 V02、V03、V01 都有接合点，拆分顺序敏感；需要多实例、多会话和连续轮次测试。
  - **保留共享**：最小调用 ID/父 ID 路由信封；不共享合成规则、账本和清理策略。
  - **评判**：复杂度 **大**｜收益 **高**｜推荐度 **4/5，推荐与 V02、V01 同批实施**。

### C. 接入、注册与私有存储

- [x] **V10 CLI 探测、启动参数、环境变量与工作目录**
  - **拆分内容**：二进制查找、PATH 回退、argv、环境变量、cwd 规范化、启动超时和安装提示分别归厂商。
  - **优点**：安装位置和启动方式变化不波及公共连接；桌面环境下的厂商路径问题更易定位。
  - **缺点**：启动冒烟和未安装态测试需逐家维护；公共连接构造签名要先调整。
  - **保留共享**：Popen、stdin/stdout/stderr 管道、线程读取、terminate/kill 和进程失效收口。

## 6. 明确保留共享的部分

以下内容不是厂商垂直语义，不建议为了「彻底」而复制：

- `LanguageModel`、`Message`、稳定流式事件信封和最小调用路由元数据。
