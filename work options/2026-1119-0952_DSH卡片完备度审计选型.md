# DSH 卡片完备度审计选型

## 一、背景与目标

用户诉求：DSH 后台的对话卡片应与 Kimi 后台一样完善。前置事实：读图卡缺陷已单独立项（`2026-1119-0938_DSH图片卡片对齐Kimi落地计划.md`，含用户侧图片能力动态翻案），本文覆盖**读图卡之外的完备度审计**与**完善路径选型**。

审计基准：DSH acp profile 实际挂载的工具集以 base bundle 为准（`参考代码/deepseek-harness/packages/bundle/base/cordis.patch.yml`），工具参数形态以官方工具目录为准（`参考代码/deepseek-harness/docs/tool-catalog.md`），帧投影形态以 ACP 适配源码为准（`参考代码/deepseek-harness/packages/acp/acp/src/updates.ts`、`参考代码/deepseek-harness/packages/acp/acp/src/content.ts`）。

## 二、结论先行

**推荐方案 B（归一化别名层收口）+ 三个专项按各自性质处理**：工具名分派走「归一化剥下划线别名」一条规则，入参键读取走「snake_case/camelCase 别名并联」一条规则，从根上消掉 DSH 与 kimi 系的命名口径差；edit 的 diff 缺口走「rawInput 合成 diff」专项（复用 write 合成路径先例）；`ask_user_question` 走「工具名收录 + 实测回环」专项。

不推荐的路线：为 DSH 单写一套投影适配器（方案 C）——隔离了差异但制造第二真相源，后续每接一个新后端都要双写一遍；也不推荐继续逐项硬编码打补丁（方案 A 裸用）——已发生的遗漏（read_image、ask_user_question 两个专用卡均未生效）正是补丁式维护漏检的直接证据。

## 五、候选方案

### 方案 A：逐项精确补录（不推荐单独使用）

按审计表逐工具补：分派表加 `read_image`/`ask_user_question`/`subagent_fork` 条目，键表加 snake_case 键，_tool_call_summary 补 file_path。

- 优点：改动直白、风险最小、每步可独立验证。
- 缺点：补丁式维护，无规则兜底——DSH 后续新增/改名工具、再接入第三个后端时，同样性质的遗漏会重演（read_image、ask_user_question 漏检即前车之鉴）。

### 方案 B：归一化别名层收口（推荐）

在既有归一化单点上加两条通用规则，替代逐名硬编码：

1. **工具名**：`_normalize_tool_name` 产出一个主键的同时，分派查找接受「剥 `_`/`-` 后的紧凑别名」——`ask_user_question` 与 `askuserquestion`、`read_image` 与 `readimage` 同表命中；`_extract_media_path` 无扩展名兜底的工具名判定同步走同一归一化。
2. **入参键**：已知键与路径/摘要提取改为「键别名并联」读取（file_path∥filePath∥path、old_string∥oldString、queries∥query），一处实现全表受益。
- 优点：一条规则覆盖所有后端同类差异，新后端接入零补丁；与既有「归一化剥 mcp__ 前缀」同构，不引入新抽象层级。
- 缺点：归一化规则写宽了有误匹配理论风险（如某后端真存在仅下划线不同名的两个不同工具）——以「别名仅作分派查找的补充键、不改变载荷透传」约束，风险可忽略。

### 方案 C：DSH 专属投影适配器（否决）

在 `dsh_acp.py` 侧把 DSH 帧重映射为 kimi 口径（改工具名/键名）再进公共管线。

- 优点：公共层零改动、差异完全隔离。
- 缺点：制造第二真相源；每个新后端各写一份适配器，公共层的通用性名存实亡；键重映射后 GUI 显示的入参键名与后端真实键名不符，调试时多一层误导。

## 六、专项决策（三处真实差距）

### 6.1 read_image 读图卡

已由 `2026-1119-0938_DSH图片卡片对齐Kimi落地计划.md` 覆盖（分派表收录 + file_path 键 + 用户侧能力动态翻案），本文不重复决策。

### 6.2 edit 无 diff 可视化

DSH edit 出参无结构化 diff 是协议投影边界（automation-only），客户端改不出真 diff 项；但 rawInput 的 old_string/new_string 是真实所给，合成 oldText/newText 与 write 合成路径同纪律（0803 计划先例：数据为后端真实所给，合成仅是 diff 化重表达）。

- 决策：扩展 `_extract_write_diff` 的合成口径——kind=edit 且 rawInput 含 old_string/new_string（或其 camelCase 双形态）时合成 unified diff（replace_all 为真时按全文逐处匹配求 diff，单处替换直用两段文本）。
- 取舍：合成 diff 展示的是「请求替换」而非「落盘结果」（与 write 合成口径已知取舍一致，记录不另立新规）。

### 6.3 ask_user_question 提问卡

分派修复（收录 `ask_user_question`）是前置条件；但 QuestionCard 的卡片内交互依赖权限回环把 question 请求路由到 QUESTION_BRIDGE。

- 决策：先实测本机 dsh——提问是否以 session/request_permission 帧到达（参考 reasonix 提问实测先例 `文档/帧存档/ask_reasonix_*.json` 的同款判别）；回环到达则分派修复后交互即通，未到达则提问卡先按「只读问答对渲染」落地，交互激活另立小项。
