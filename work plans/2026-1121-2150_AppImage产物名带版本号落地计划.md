### 1.2 固定文件名带来的实际问题

1. **同目录多次构建互相覆盖**：`building/dist/` 下永远只有一个 AppImage，上一版被静默替换，无法并存回滚。
2. **分发件无法自证版本**：文件发给用户后，只能启动后进「关于」才能知道版本；文件名、下载页、聊天记录里都看不出。
3. **归档/对比容易张冠李戴**：把不同时期的包收进 `~/AppImages/` 或测试目录后，多个同名文件只能靠人工改名区分。

## 2. 目标与非目标

### 2.1 目标

- **G1**：每次构建产出的真实 AppImage 文件名携带完整版本号，例如 `Zen_Studio-1.8.0.574-x86_64.AppImage`。
- **G2**：版本号只来自现有唯一来源 `building/version.py get`，不新增第二套版本逻辑、不引入时间戳。
- **G3**：构建脚本自身断言「文件名含版本、版本与 `version.py get` 一致」，版本逻辑退化时构建直接失败，而不是产出错名文件。
- **G4**：保留一个稳定入口，使现有文档、桌面快捷方式、用户习惯路径不因改名立刻失效（方案见 §3.2，待确认）。

### 2.2 非目标

- ❌ 不改 AppImage 内部元数据（`version.txt`、`X-AppImage-Version` 已正确，保持不动）。
- ❌ 不做自动更新、签名、zsync、发布服务器。
- ❌ 不改 onedir 中间产物目录名 `building/dist/zen-studio/`。
- ❌ 不自动清理旧版本产物（避免误删可用于回滚的包；磁盘策略另议）。
- ❌ 不改写历史文档中的旧文件名。
- ❌ 不改变「同一 git 提交重复构建得到同一版本号」的语义。

## 3. 命名方案

### 3.1 命名规则（D1 已确认）

```text
Zen_Studio-<完整版本>-x86_64.AppImage
```

即：在现有 `Zen_Studio` 与 `-x86_64` 之间插入 `-<版本>`，扩展名不变。

| 场景 | 版本值 | 产物文件名 |
|:---|:---|:---|
| 正常 git 仓库（四段） | `1.8.0.574` | `Zen_Studio-1.8.0.574-x86_64.AppImage` |
| 非 git 环境/浅克隆（三段） | `1.8.0` | `Zen_Studio-1.8.0-x86_64.AppImage` |

理由：

- 采用 AppImage 社区惯用的 `名称-版本-架构` 次序，文件管理器/`ls` 按名称排序即按版本排序，便于归档与回滚。
- 版本段固定在架构之前，文件名语义稳定；架构仍只保留 `x86_64` 单平台。
- 与现有版本中枢零耦合：版本段直接复用 `building/version.py get` 的输出。

**格式守卫**：版本值会进入文件名，构建脚本在拼接前断言匹配 `^[0-9]+\.[0-9]+\.[0-9]+(\.[0-9]+)?$`。版本来源虽可信，但一旦 `pyproject.toml` 被误写成含 `/`、空格或通配符的值，不能让脚本把产物写到意外路径。

### 3.2 稳定别名（D2 已确认保留）

改名后，所有现存引用（README 示例、用户桌面快捷方式、习惯命令）都会指向一个不存在的路径。在 `building/dist/` 内额外维护一个**相对目标**的符号链接：

```text
building/dist/Zen_Studio-x86_64.AppImage -> Zen_Studio-1.8.0.574-x86_64.AppImage
```

规则：

1. 别名指向**当前最新且已通过冒烟**的版本化产物；使用相对目标，整个 `dist/` 目录可整体搬移不断链。
2. **先冒烟、后切别名**：别名更新放在 `[5/5]` 冒烟全部通过之后，保证稳定入口永远不指向未验证产物。
3. 别名创建为**尽力而为**：文件系统不支持符号链接（FAT/exFAT、部分网络盘）时只告警、不阻断构建——核心交付是版本化文件名，别名只是兼容层。告警需明确提示「文档/desktop 请改用实际版本文件名」。
4. 首次升级构建时，`dist/` 下旧的无版本真实文件会被同名符号链接替换；该文件就是上一次构建产物，其他历史版本仍以版本化文件保留，不构成回滚能力损失。构建日志需明示这一替换。
5. **分发时拷贝版本化真实文件，不要分发别名**：符号链接离开 `dist/` 可能断链，且接收方不应依赖开发机的目录布局。

### 3.3 已确认决策

| 编号 | 决策 | 确认结果 | 影响 |
|:---:|:---|:---|:---|
| **D1** | 版本号放在架构前还是后 | **前置**：`Zen_Studio-<版本>-x86_64.AppImage`（AppImage 惯例，按名排序即按版本排序） | `build_appimage.sh` 一处模板字符串 + 文档示例 |
| **D2** | 是否保留稳定别名 `Zen_Studio-x86_64.AppImage` | **保留**，指向最新已验证版本，兼容现有文档/快捷方式 | 脚本多约 10 行；文档同时描述别名与真实产物 |
| **D3** | 旧版本产物如何处理 | **保留不自动删**，构建结束打印当前版本化产物数量与总占用 | 磁盘占用（单包约 149M）；不误删回滚件 |

## 4. 脚本改造设计（`building/build_appimage.sh`）

### 4.1 关键顺序问题

当前 `APPIMAGE` 在脚本第 18 行定义，而 `VERSION` 到第 106 行才捕获。必须把产物路径的派生**移到版本捕获之后**，否则拿不到版本号。`APPIMAGE` 的所有使用点（174、179、185、224、225）都在第 106 行之后，移动不影响执行顺序。

### 4.2 改动点

| 位置 | 现状 | 改为 |
|:---|:---|:---|
| L18 | `APPIMAGE="$DIST_DIR/Zen_Studio-x86_64.AppImage"` | 删除；L107 之后新增派生逻辑 |
| L106-107 | `VERSION="$(uv run python building/version.py get)"` + 打印 | 捕获后立即校验版本格式；计算 `APPIMAGE_NAME` / `APPIMAGE` / `LATEST_LINK`，并打印「产物名」 |
| L160 | 注释「版本元数据注入产物内部（文件名保持固定不带版本）」 | 改为「版本元数据注入产物内部；文件名由 §3.1 规则派生」 |
| L174-178 | appimagetool 输出到 `$APPIMAGE` | 不变（变量已指向版本化路径）；参数仍为 ASCII 相对路径，规避其 locale 缺陷 |
| L179 | `chmod +x "$APPIMAGE"` | 不变 |
| L181-221 | 冒烟解包核对 | 冒烟对象改为版本化文件；新增「文件名含版本且与 `$VERSION` 一致」断言 |
| L220 之后 | 冒烟结束直接统计体积 | 新增别名更新与校验（D2 已确认保留），失败仅告警 |
| L223-226 | 打印 `$APPIMAGE`、体积 | 打印版本化路径、别名指向、版本化产物累计数量/占用（D3 已确认保留） |

示意（非最终代码）：

```bash
VERSION="$(uv run python building/version.py get)"
[[ "$VERSION" =~ ^[0-9]+\.[0-9]+\.[0-9]+(\.[0-9]+)?$ ]] \
    || { echo "❌ 版本格式非法，不能用于文件名：$VERSION"; exit 1; }

APPIMAGE_NAME="Zen_Studio-${VERSION}-x86_64.AppImage"
APPIMAGE="$DIST_DIR/$APPIMAGE_NAME"
LATEST_LINK="$DIST_DIR/Zen_Studio-x86_64.AppImage"
echo "    完整版本：$VERSION"
echo "    产物名：$APPIMAGE_NAME"
```

别名更新（冒烟通过后）：

```bash
if ln -sfn "$APPIMAGE_NAME" "$LATEST_LINK" \
   && [[ -L "$LATEST_LINK" && "$(readlink "$LATEST_LINK")" == "$APPIMAGE_NAME" ]]; then
    echo "    稳定别名：$LATEST_LINK -> $APPIMAGE_NAME"
else
    echo "    ⚠️ 稳定别名创建失败（文件系统不支持符号链接？）"
    echo "       文档/desktop 请直接使用版本化文件名：$APPIMAGE_NAME"
fi
```

### 4.3 边界与语义

| 情形 | 行为 |
|:---|:---|
| 同一 git 提交重复构建 | 版本号相同，同名文件被覆盖（沿用现有语义，不引入时间戳） |
| 工作区有未提交改动 | 版本号不变；文件名不体现 dirty，与 `version.txt` 口径一致 |
| 非 git 环境 | 三段版本，文件名仍成立；格式守卫已允许三段 |
| 构建中途失败 | 不更新别名，稳定入口仍指向上一次成功构建 |
| 旧无版本文件存在 | 被同名符号链接替换；日志明示，不静默 |
| 磁盘积累多个版本 | 不自动删除；结束提示数量与总占用，由用户决定清理 |
