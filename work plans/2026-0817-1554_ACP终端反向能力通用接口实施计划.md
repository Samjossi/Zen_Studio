## 1. 背景与目标

现状：五 provider 的 `initialize` 全部声明 `"terminal": False`（`kimi_acp.py:537`、`reasonix_acp.py:306`、`dream_acp.py:215`、`kilocode_acp.py:312`、`opencode_acp.py:221`），agent 的 Bash 命令全部在其内部进程执行，用户无法实时看输出、无法在长任务时感知进度。

目标：以**一份通用实现**接通 ACP `terminal/*` 反向能力——agent 的 Bash 命令落到 IDE 终端面板的用户可见 tab 中执行（真 PTY，所有权在用户侧，AI 远程"驾驶"），用户实时看输出、可 Ctrl+C 干预。

核心判据：不同 agent 机制不同，但 `terminal/*` 是 ACP 标准反向请求——通用接口做在协议连接层（`llm/providers/acp.py`，一份实现，五 provider 共享），各 provider 只差一个能力开关。**不支持的 agent 保持 `terminal: false`，行为与现状逐字节等价**（实测证实这两家在该声明下无行为变化）。

## 2. 架构（单向依赖，零环）

```
agent 进程 ──stdio──▶ AcpConnection._handle_reverse     (llm/providers/acp.py，改)
                         │ set_terminal_handler 鸭子类型注入（同 set_permission_handler 先例）
                         ▼
                  AgentTerminalBridge                    (gui/panels/terminal/agent_bridge.py，新增)
                         │ 仅经公开方法操作面板；reader 线程 → GUI 线程封送
                         ▼
                  TerminalPanel（AI tab）                 (gui/panels/terminal/panel.py，小改)
                         │ _spawn 抽参数化入口
                         ▼
                  PtySession × N（每 terminalId 一套）    (session.py，不改)
```

线程模型（关键约束）：

- 反向请求到达于连接层 **reader 线程**（`acp.py:1084`）。
- `create`/`output`/`kill`/`release`：bridge 封送到 GUI 线程同步执行后回包——复用 `_ask_permission` → `PERMISSION_QUEUE.ask`（`gui/panels/chat/panel.py:774`）已验证的阻塞封送模式；`create` 是快操作，阻塞可接受。
- `wait_for_exit`：**长阻塞语义，严禁占 reader 线程**（会卡死同 session 的 `session/update` 流）——改异步应答：连接层持有 response id 挂起，bridge 挂 `process_exited` 一次性信号，进程退出时回调连接层 `_send` 补发响应包。实施时先核实 `_send` 的锁保护覆盖跨线程调用。

## 3. 任务分解

### T1 连接层通用分发（`llm/providers/acp.py`）

1. 定义 `TerminalHandler` 抽象（签名注释定型，同 `PermissionHandler` 先例，`acp.py:106`）：
   - `create(command: str, args: list[str], cwd: str | None, env: dict | None) -> str` → terminalId
   - `output(terminal_id: str) -> dict` → `{output, truncated, exitStatus?}`（尾部 64KB 截断策略）
   - `wait_for_exit(terminal_id: str, callback: Callable[[dict], None]) -> None` —— **回调式**，进程退出时 bridge 回调 `{exitCode, signal}`
   - `kill(terminal_id: str) -> None`、`release(terminal_id: str) -> None`
2. `AcpConnection` 增 `set_terminal_handler(handler)`；`_handle_reverse`（`acp.py:1133`）增 `terminal/create|output|wait_for_exit|kill|release` 五个方法分发；**无 handler 时维持 `-32601` 现状**（兜底语义不变，kilocode/opencode/dream 路径零影响）。
3. `wait_for_exit` 异步应答：`_handle_reverse` 内登记 `(response_id → 待回包)`，回调到达时 `_send` 补发；连接关闭/terminate 时对挂起项兜底回 error（防 agent 永久阻塞）。
4. 新增 `build_client_capabilities(terminal: bool) -> dict`，收口 fs/terminal 声明构造。

### T2 provider 能力开关（五 provider 各约两行）

- 支持矩阵常量落定（初值按实测报告）：kimi=True、reasonix=True、kilocode/opencode/dream=False。常量放各 provider 模块级（如 `_TERMINAL_CAPABILITY = True`），registry spec 不加字段（避免配置面膨胀）。
- 各 provider `initialize` 载荷改调 `build_client_capabilities(terminal=self._terminal_enabled)`；`_terminal_enabled = 矩阵常量 and 已注入 handler`（无 GUI 环境的 headless 场景自动退化 false）。
- `set_terminal_handler` 由各 provider 透传到 `AcpConnection`（provider 持有 `_conn` 懒建——注入时若连接未建则暂存，`_ensure_session` 建成时注入；参考 `set_permission_handler` 既有处理）。

### T3 GUI 桥（`gui/panels/terminal/agent_bridge.py`，新增）

`AgentTerminalBridge(terminal_panel)` 实现 T1 五个方法：

- `create`：封送 GUI 线程建会话——tab 标题 `AI·<命令首词>`（如 `AI·python`）；cwd 用 agent 请求值（空则面板工作区根）；每 terminalId 独立 `_Session` 走 panel 会话栈。**create 载荷两形态兼容**（实测报告 §3-2）：args 非空直起 argv；args 为空则 `$SHELL -c <command整串>`。
- 输出缓冲：bridge 侧每 terminalId 维护尾部缓冲（`data_received` 信号分一路进缓冲，GUI 线程内完成，屏幕渲染路径不动），配 `threading.Lock` 供 reader 线程的 `output` 读取；尾部 64KB 截断 + `truncated` 标志。
- `wait_for_exit`：挂 `process_exited` 一次性回调（`acp.py` 侧异步应答，见 T1-3）；进程已退出则立即回调。
- `kill`：`terminate()`（幂等）；`release`：解除协议侧跟踪，**tab 保留**供用户查看，标题后缀「已结束」。
- agent 进程异常退出（死讯注入路径）时，bridge 清理该 agent 全部挂起 wait 回调（兜底 exitCode=-1 回包）。

### T4 终端面板小改（`gui/panels/terminal/panel.py`）

- `_spawn`（`panel.py:182`）抽出参数化入口 `spawn_agent_session(argv, cwd, title) -> 会话句柄`：复用现有 `_Session`/tab 栈/信号接线，用户手开会话路径不变。
- AI tab 视觉区分仅靠标题前缀，不动 qss。
- 用户手动关闭 AI tab：等价 `kill` + `release`（bridge 监听 tab 关闭，回调清理）。

### T5 注入接线（`gui/main_window.py` + `gui/panels/chat/panel.py`）

- `main_window.py:176` TerminalPanel 单例建成后构造 `AgentTerminalBridge`，注入 ChatTabs/各 ChatPanel（沿用 main_window 现有的面板间引用传递方式，实施时对齐现场）。
- `chat/panel.py:266` `_get_provider` 增鸭子类型注入：provider 有 `set_terminal_handler` 即注入 bridge（与 `set_permission_handler` 同排同风格）。

### T6 验收

1. spike 回归：五 agent 复跑 `scripts/spike_terminal_capability.py`，结论与实测报告一致（kimi/reasonix 6 过，其余结论不变）。
2. 真机手动验收：kimi 标签跑长任务（`for i in $(seq 1 30); do echo $i; sleep 1; done` 类）——终端面板出现 `AI·bash` tab 实时滚动；退出码回传、聊天区 Bash 卡片正常 completed；用户手开 tab 与 AI tab 互不干扰；用户可 Ctrl+C 干预 AI tab。
3. 不支持方回归：kilocode/opencode 标签跑命令——无 AI tab 出现，行为与现状一致。
4. 异常路径：任务中途 kill agent 进程——无悬挂 reader 线程、无僵尸 PTY。
5. 文档同步：`llm/README.md`、`gui/README.md`（terminal 子包条目）；本计划归档转 `文档/修改记录/`。

## 4. 风险与对策

| 风险 | 对策 |
|:---|:---|
| `wait_for_exit` 同步等待卡死 reader 线程（session/update 流中断） | T1-3 异步应答为硬性设计约束，验收 T6-4 覆盖 |
| AI tab 的 PTY 尺寸与面板网格耦合（后台 tab 尺寸语义） | 复用 `_switch_tab` 既有 resize 补同步；create 时按当前网格 spawn，与 `_spawn` 同口径 |
| reasonix 整行 shell 串形态 | T3 create 两形态兼容（spike 已实证处理） |
| 多 chat 标签 × 多 provider 并发 create | bridge 内 terminalId 全局唯一（`ai-term-N` 递增），会话栈本身线程安全由 GUI 封送保证 |
| 用户在 AI tab 手动键入干扰 agent 命令 | 设计内行为（所有权在用户侧，与 Zed 语义一致）；不锁键盘 |

## 5. 明确不做

- 不给不支持 terminal/* 的 agent（kilocode/opencode/dream）做"输出投屏"模拟 hack。
- 不改 `PtySession`/`TerminalScreen`/`TerminalWidget` 内部实现（只经公开 API 复用）。
- 不做聊天区后台任务状态条（独立立项）。
- 不动 `fs.readTextFile/writeTextFile` 声明（保持 false）。
