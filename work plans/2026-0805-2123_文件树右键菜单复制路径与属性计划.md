# 文件树右键菜单新增「复制相对路径 / 复制绝对路径 / 属性」计划

## 1. 背景

用户原话：

> 当用户在文件树系统里右键的时候，它的右键菜单我希望能增加三项东西。「复制相对路径」「复制绝对路径」「属性」这三项。按照正常的逻辑来说，属性要放在最底下，其他的按你的想法来排放。

决策已明确：

- 三项全部加入文件树右键菜单；
- 「属性」恒置于菜单最底部（其前加分隔线）；
- 两个复制项的相对顺序由实现方决定——本计划定为「复制相对路径」在上、「复制绝对路径」在下（相对路径是本 IDE 内更常用的形态，与 2048 计划「标题行路径相对化」的产品取向一致）。

### 2.2 结构性事实

- 技术栈为 **PySide6 单进程桌面应用**，无前后端分离：剪贴板 = `QApplication.clipboard()`，文件元信息 = `QFileSystemModel.fileInfo(index)` / `Path.stat()`，均就地取数，无需新 API。
- 项目内**无**剪贴板工具模块，惯例是就地 `QApplication.clipboard().setText(...)`（先例：`gui/panels/chat/cards.py:364`、`gui/panels/terminal/widget.py:186`）。
- 项目内**无**属性对话框先例；对话框成熟范式为 `gui/git_graph_dialog.py`（QDialog 子类 + 主题/字号挂链 + 中文按钮）与 `gui/settings_dialog.py`（弃用 `QDialogButtonBox`，因其本地化依赖未装载的 QTranslator）。
- 文件树当前隐藏了大小/类型/修改时间列（`explorer.py:157-159`），数据在 `QFileSystemModel` 中现成可取，属性对话框零额外 IO 成本。
- 相对路径换算先例：`ViewerPanel._display_path()`（2048 计划产物，`gui/panels/viewer/panel.py`）的 resolve → `relative_to` 逻辑。
- `ExplorerActions.__init__` 已注入 `file_path_of`、`selected_paths`、`host`，新增三项动作**无需改动构造函数**。

## 3. 设计决策

### D1：菜单项排放顺序

最终菜单结构（─ 为分隔线）：

```
打开
使用 Typora 打开            （条件项，维持原样）
在文件管理器中显示
─────────────────────
新建文件
新建目录
─────────────────────
重命名
删除
─────────────────────
复制相对路径
复制绝对路径
─────────────────────
属性
```

- 「复制相对路径」先于「复制绝对路径」：相对路径在 IDE 场景（引用、文档、chat 附件）使用频率更高，且与 2048 计划的产品取向一致。
- 复制项独立成组，置于「重命名/删除」之后：复制是读取类操作，与破坏性的删除拉开视觉距离；同时也与「在文件管理器中显示」这类"定位"语义区分。
- 「属性」前单独加分隔线并沉底：符合 Windows/macOS 文件管理器的普遍惯例，也满足用户"属性放最底下"的明确要求。

### D2：置灰规则

三项均按 `has_selection`（`index.isValid()`）置灰：

- 空白处右键时复制路径无意义（相对/绝对都需要具体目标），属性亦然。
- 与现有 open/reveal/rename/delete 的置灰惯例完全一致，探针断言写法可直接沿用。

### D3：相对路径的换算口径

- 以**工作区根目录**（`FileExplorer` 构造时传入的 `workspace_root`）为基准，复用 2048 计划确立的 resolve → `Path.relative_to` 口径；换算失败（理论上不会发生，树内节点必在根下）时回退为绝对路径，不弹错误框。
- 复制到剪贴板的是**纯文本路径**，不带引号、不带 `file://` 协议头，与终端/chat 复制惯例一致。

### D4：「属性」对话框形态

新文件 `gui/panels/file_explorer/properties_dialog.py`，对齐 `GitGraphDialog` 范式：

- **模态对话框**（`dialog.exec()`）而非 `GitGraphDialog` 的非模态单例——属性查看是瞬时动作，无驻留价值，模态实现更简单，也避免与主题/字号挂链的额外成本。
- 内容（只读表单）：名称、类型（文件/目录 + 后缀或 MIME 简述）、大小（人类可读，如 `12.3 KB`）、位置（父目录绝对路径）、创建时间、修改时间、权限（如 `rw-r--r--`）。
- 目录的大小显示为「—」（递归统计成本不可控，本期不做，见 R2）。
- 取数方式：优先 `QFileSystemModel.fileInfo(index)`（树内零 IO），创建时间/权限等 `QFileInfo` 未覆盖的字段用 `Path.stat()` 补齐。
- 按钮仅一个中文「关闭」`QPushButton`，弃用 `QDialogButtonBox`（settings_dialog 先例：本地化依赖未装载的 QTranslator）。

### D5：不新增工具模块

剪贴板与路径换算逻辑体量极小（各 ≤5 行），就地写在 `actions.py` 的 `_action_*` 方法内，符合项目既有惯例；若未来第三处需要复制路径再提炼。

## 5. 风险与取舍

- **R1：菜单变长的可读性**——现有菜单 7~8 项，新增后 10~11 项，仍在常规文件管理器菜单体量内（VSCode/Nautilus 均在此量级），以分隔线分组维持可读性。不做二级子菜单（过度设计）。
- **R2：目录大小不统计**——递归 `stat` 在大目录上不可控，本期目录大小显示「—」。若后续用户要求，单独立项做异步统计。
- **R3：多选语义**——现有菜单动作（重命名/删除除外）均基于右键命中的单个 `index`，复制与属性照此口径，不处理多选批量复制（与 reveal/open 现状一致）。
- **R4：相对路径基准固定为工作区根**——不提供"相对于其他目录"的选项，避免 UI 复杂度膨胀；该口径与 2048 计划一致，用户已有心智模型。

### 超出计划范围的发现与计划微调（均已落地，记录备查）

1. **`ExplorerActions` 构造函数新增 `workspace_root: str` 注入**（计划原称
   无需改动构造函数）：相对路径换算基准在类型系统显式化，延续该文件
   「依赖全部构造注入」的架构原则（头注 AFCP 整改）；`explorer.py` 装配处
   同步传 `self.root_dir`。全项目唯一实例化点，无遗漏。
2. **属性取数方式收敛为 `Path.stat()` 单次调用**（计划 D4 原说优先
   `QFileSystemModel.fileInfo`）：瞬时对话框一次性展示，无缓存复用价值；
   `stat()` 一次拿全 size/mtime/mode，字段反而比 QFileInfo 更全。
3. **合规整改：if/elif 分发链 → `_dispatch_table` 分发表**。新增 3 个 elif
   后 `open_context_menu` 嵌套达 10 层（存量 elif 链模式的加重），触发
   嵌套 ≤3 红线；重构为 QAction→回调 dict 并抽出 `_dispatch_table` 方法，
   嵌套归零，且延续「构建与弹出分离」惯例使分发链路可探针断言。
4. **offscreen 平台两条实证**（探针方法论收获，供后续引用）：
   - shiboken 类型的**类方法 monkeypatch 不生效**：`QMenu.exec` 赋值后实例
     调用仍走 C++ 实现并阻塞；
   - offscreen 下 `QMenu.exec` 对编程式 `trigger()` **不返回被选 action**
     （trigger 后 exec 不退出；trigger+hide 退出但返回 None）。
   结论：菜单分发链路的探针验证须走「分发表抽离 + 直接调用 handler」
   路线，不可仿真 exec 交互。
5. **创建时间字段**：Linux 多数文件系统无 `st_birthtime`，回退 `st_ctime`
   （元数据变更时间），已在代码注释标明，语义偏差为平台所限，可接受。
