## 1. 问题现象

用户反馈：模型选择下拉框里没有「K2.8」选项，怀疑前端未跟上后台能力。

**2026-09-20 实测核查结论**：后台 CLI 正常，前端链路也正常——K2.8 一直在列表里，只是显示的是别名而非显示名：

- 本机 kimi CLI 0.43.1 执行 `kimi provider list --json`，目录载荷中 `kimi-code/kimi-for-coding` 条目的 `displayName` 为 **"K2.8 Preview"**（K2.8 全量上线后 Model ID 不变，见 `2026-0917-0646_后端模型列表更新与KiloCode封存落地计划.md` §4 补记）。
- 前端模型菜单的数据源 `models_from_catalog`（`src/llm/providers/kimi_common.py`）只取 `models` 表的 key（别名），`displayName` 字段在解析层被丢弃；菜单项与按钮文本因此显示 `kimi-for-coding`，用户无法与「K2.8」对上号。

## 2. 现状诊断

### 2.1 数据链路：displayName 已送达，唯独没人读

- 目录载荷每条模型条目带 `displayName`（服务端下发或 `config.toml` overrides 固定），`efforts_from_catalog` 已在读同一份载荷（0455 计划 T1：`_kimi_catalog` 原始载荷缓存一次、多路派生，防双倍子进程）——显示名派生是**同缓存的第三路消费，零新增子进程**。
- overrides 语义：本机 `kimi-for-coding` 的 `displayName: "K2.8 Preview"` 正是写在 overrides 子表里，解析须按 CLI effective 语义先并入 overrides 再读（`efforts_from_catalog` 同款处理，直接对齐）。

### 2.2 前端两个消费点均直显别名

| 消费点 | 现状 |
|:---|:---|
| ModelBar 模型菜单（`src/gui/panels/chat/model_bar.py` `_refresh_models`） | 菜单项 text=别名、data=别名 |
| ModelBar 按钮短文本（同文件 `_refresh_button_texts`） | `short_model_alias` 取 '/' 末段 |
| 设置中心模型下拉（`src/gui/settings_dialog.py` `_fill_models`） | 逐别名灌入 QComboBox |

### 2.3 红线边界确认

D6 红线 2「别名对注册表是不透明字符串」约束的是**协议透传与持久化**（别名不解析、不拼接、不校验）；显示名映射是**纯 UI 呈现层**的事，与既有 `short_model_alias`（同样只做 UI 短文本）同性质，不破红线。持久化 `model_versions`、ACP 协议载荷继续携带别名原值，零改动。

### 2.4 各后端显示名数据源盘点

| 后端 | 数据源 | 结论 |
|:---|:---|:---|
| kimi-acp | `provider list --json` 条目 `displayName`（含 overrides） | ✅ 有，本次接入 |
| reasonix-acp | 解析 `~/.reasonix/config.toml`，模型条目无显示名字段 | ❌ 无，走兜底 |
| opencode-acp | `opencode models` 纯文本行 | ❌ 无，走兜底 |
| kilocode-acp | 已封存，不动 | ❌ 不接入 |
| dream-acp | 单别名示例 agent | ❌ 无，走兜底 |

## 3. 方案

**D1：注册表新增显示名数据源字段，仿 `list_efforts` 既有范式。**
`BackendSpec` 新增 `list_display_names: Callable[[], dict[str, str]] | None = None`——别名 → 显示名；`None` 或返回空 dict = 该接口无显示名数据源，UI 一律回退别名原文。语义与 `list_efforts` 的「空 dict 回退接口级兜底」同构，注册表使用方零学习成本。

**D2：kimi 显示名从共享目录载荷派生。**
`kimi_common.py` 新增 `display_names_from_catalog(data)`：遍历 `models` 表，条目先并入 `overrides`（effective 语义，与 `efforts_from_catalog` 一致）再读 `displayName`；缺字段/非字符串的条目不产生映射（该模型回退别名）。注册段挂 `list_display_names=lambda: display_names_from_catalog(_kimi_catalog())`——与 list_models/list_efforts 同源同缓存，`_kimi_catalog` 失效口（`refresh_models`）天然覆盖，不加新缓存层。

**D3：ModelBar 菜单与按钮显示名呈现。**
- 菜单项：text = 显示名（有则）否则别名；data 恒为别名（勾选定位 `_find_action` 按 data 匹配，不受影响）；菜单项 tooltip 写完整别名，保留溯源能力。
- 按钮短文本：有显示名用显示名（实测 "K2.8 Preview"/"K3" 均为短文本，宽度贴合逻辑不变），无显示名维持 `short_model_alias`。
- 四按钮 tooltip 的「模型」行：显示名与完整别名并列（如 `模型：K2.8 Preview（kimi-code/kimi-for-coding）`），无显示名时维持原样。

**D4：设置中心模型下拉同款呈现。**
`_fill_models` 灌入 QComboBox 时 item 显示文本用显示名、userData 存别名；持久化读写、当前值定位均走 userData，行为不变。

**D5：其余后端挂 `None`。**
reasonix/opencode/dream 无数据源，kilo 封存不动；上游日后提供显示名字段时再挂对应派生函数，UI 层零改动。

**改动清单**：

1. `src/llm/registry.py`：`BackendSpec` 加 `list_display_names` 字段；kimi 注册项挂派生 lambda；其余四项显式 `None`（依赖默认值，不逐一出参）。
2. `src/llm/providers/kimi_common.py`：新增 `display_names_from_catalog`。
3. `src/gui/panels/chat/model_bar.py`：`_refresh_models` 菜单项 text/tooltip、`_refresh_button_texts` 模型按钮文本、`_refresh_tooltips` 模型行。
4. `src/gui/settings_dialog.py`：`_fill_models` 下拉项呈现（userData 别名）。
5. `tests/` 新增显示名解析与回退测试（见 T5）。
6. **不动**：持久化 `model_versions`、ACP 协议载荷、枚举/缓存/失效口逻辑、`short_model_alias` 本体（无显示名时仍是兜底）。

## 5. 影响面评估

- ✅ 持久化与协议零改动：菜单/下拉的 data 层恒为别名，`model_versions` 记忆、ACP 会话模型切换不受影响。
- ✅ 缓存零新增：显示名与模型/档位同源同载荷，`_kimi_catalog` 单缓存三消费，`refresh_models` 失效口自动覆盖。
- ✅ 无显示名后端行为不变：`None`/空 dict 回退别名原文，reasonix/opencode/dream/kilocode 菜单逐字节不变。
- ✅ 启动恢复安全：恢复逻辑按别名匹配 data，显示名不参与匹配。
- ⚠️ 显示名长度不可控（服务端下发）：按钮宽度随文本贴合的既有逻辑会自适应，极端长名由 tooltip 兜底全名；不引入截断逻辑，实测后再议。
- ⚠️ 已知遗留（不在本次范围）：`refresh_models` 无 GUI 触发入口，模型目录更新需重启进程生效；如需「重新检测」按钮另立计划。
