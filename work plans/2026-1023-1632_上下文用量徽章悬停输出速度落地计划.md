# 上下文用量徽章悬停输出速度落地计划

> **状态**：已实施（修改记录：`文档/修改记录/2026-1023-1650_上下文用量徽章悬停输出速度修改记录.md`）
> **范围**：AI 聊天面板状态行（`src/gui/panels/chat/panel.py`）、kimi ACP 后端（`src/llm/providers/kimi_acp.py`）、协议定型（`src/llm/base.py`）
> **时间**：2026-10-23 16:32（设计，UTC+8）/ 2026-10-23 16:50（实施）
> **优先级**：中

## 需求

上下文用量徽章（`chatUsageLabel`，状态行右侧百分比）悬停 tooltip 已有用量两行 + 计时段三行（见 `2026-1022-1519_上下文用量徽章悬停会话计时落地计划.md`，已实施）。用户希望再增一条信息：**本轮对话的平均输出速度（tokens/秒）**。

口径要求（用户明确）：按规矩只算**输出 token**，且分母只计**模型生成时间**——读取文件、工具执行、审批等待等轮次内非生成时间不得算入，否则失真。

## 关键探查结论（已实测核实）

实测样本：本机 kimi 真实会话 wire.jsonl（2026-10-23，一轮 16 次 API 调用，224KB）。

- **output 有真值**：`usage.record`（`usageScope=="turn"`）的 `usage` 含 `inputOther/output/inputCacheRead/inputCacheCreation` 四字段（`2026-0731-1454_上下文用量徽章四家后端通用化移植计划.md` E2 已登记，现用量徽章只用了前两个）。
- **`usage.output` 是单次调用值，不是累计值**：实测序列 277→201→326→90→192……非单调，直接取用，**禁止差分**（inputOther+inputCacheRead 才是单调爬升的累计口径，现状不变）。
- **每条 wire 记录都带 `time`（epoch 毫秒）**，且单次 API 调用在文件中的事件序为：
  `step.begin → llm.request（turnStep "0.N"）→ usage.record → content.part → tool.call/tool.result → step.end`。
- **生成耗时可精确隔离**：单次调用生成时间 = 配对 `usage.record.time − llm.request.time`。工具执行与审批等待发生在上一次 `step.end` 与下一次 `llm.request` 之间，天然落在窗外——正好满足「不算读取时间」的口径。实测单调用 tok/s 9.7~31.8（k3-256k），量级合理。
- **配对规则**：文件序上每条 `usage.record` 与其之前最近的 `llm.request` 配对（turnStep 递增一一对应，实测 16 对 16 无错位）。
- **轮内多条、末条晚到**：一轮 N 次调用产生 N 条 `usage.record`，前 N-1 条轮内实时落盘，**末条在 response 后约 1~3s 异步写盘**（既有 `_WIRE_USAGE_WAIT_S=3s` 轮询兜底）。现有 `_poll_wire_usage` 等待条件是「条数 > 基线」，多步轮次会被前 N-1 条提前满足，等不到末条——速度计算须改等待条件（见实施步骤 2）。
- **非 kimi 后端无数据**：kilocode/opencode 的 `usage_update` 推送帧只有 used/size/cost（input+cache.read 口径，无 output）；reasonix 为 chars/4 估算。→ 速度行**仅 kimi 后端显示**，其余后端该行缺省不显示（与 tooltip「有数据才有」的既有分段纪律一致）。
- **私密通道风险**：wire.jsonl 是 kimi-code 私有落盘格式，无协议契约（`维护手册/后端CLI工具维护说明手册.md` §6 同款定性）。读取失败/字段漂移一律静默降级为「该行不显示」，不抛出、不臆造。

## 默认行为决策

- **指标定义**：一轮的平均输出速度 = Σ 本轮各次调用的 `usage.output` ÷ Σ 本轮各次调用的生成耗时（配对 `usage.record.time − llm.request.time`）。多步轮次自动加权，等价于「全轮输出 token 全轮生成时间」，不取各次速度的算术平均（短调用会虚高权重）。
- **只算正常收尾轮**：速度在 `_iter_turn_chunks` 的 response 收尾分支计算（此处本就有基线与 ≤3s 等待）。失败轮（`_raise_on_turn_error` 抛错在前）与手动中断轮不计算、不更新——上轮速度值保持最后一次正常轮的记录，与「有数据才显示」纪律一致。
- **簿记内存态**：`_turn_speed` 与 `_usage`、计时簿记同寿命（切后端/重启归零），不持久化、不考古存档会话。
- **tooltip 行位置**：紧跟「上轮任务」行之后，文案：
  `上轮输出速度：X.X tok/s（输出 N tokens / 生成 S 秒）`（速度一位小数，tokens 千分位，生成时长复用 `_format_duration`）。
- **busy 期间不做本轮实时速度**（D2）：轮内前 N-1 条记录虽已落盘，但尾部 64KB 窗口内配对 request 可能已被截出窗外，改造复杂度与失真风险不值；busy 期间悬停仍显示「上轮输出速度」（与「上轮任务」行同语义）。若日后需要实时速度再单独立项。
- **协议字段命名**：新增定型 `TurnSpeed`（frozen dataclass：`output_tokens: int`、`gen_seconds: float`），挂在 `Chunk.speed: TurnSpeed | None = None`——与 `Chunk.usage` 同模式，旧 GUI 配新协议层不崩（dataclass 带默认值）。

## 实施步骤

### 1. 协议定型（`src/llm/base.py`）

- 新增 frozen dataclass `TurnSpeed`：`output_tokens: int` + `gen_seconds: float`（注释写明口径：仅模型生成时间，不含工具/审批间隙；分子为 wire `usage.output` 单次调用值求和，非累计差分）。
- `Chunk` 增加字段 `speed: TurnSpeed | None = None`（放末位带默认值，不破坏既有构造点）。

### 2. kimi 后端计算（`src/llm/providers/kimi_acp.py`）

- 新模块级函数 `_read_wire_turn_speed(session_dir, baseline_count) -> TurnSpeed | None`：
  全量读 wire.jsonl（收尾路径，与 `_read_wire_usage` 同款一次读法，非 2s 轮询，无红线问题）；取基线之后的记录段，按文件序配对 `llm.request → usage.record`，累计 `usage.output` 与 `rec.time − req.time`；任一条缺 `time`/`output`/配对失败则跳过该条；有效配对为 0 或总耗时 ≤ 0 → None。
- `_iter_turn_chunks` 基线双记：轮次开始除 `usage.record` 条数外，同记 `llm.request` 条数基线（`_read_wire_usage` 扩展返回值或并行小函数，保持原签名兼容则新增独立计数）。
- 收尾等待条件修订：`_poll_wire_usage` 现等「usage 条数 > 基线」；为等到末次调用的记录，改为等「新增 usage.record 数 ≥ 本轮新增 llm.request 数」，上限仍 `_WIRE_USAGE_WAIT_S=3s`；超时按已落盘子集计算（均速语义仍成立，只是缺末次调用）。注意保持原有用量徽章语义不退化：stats 取自末条 usage.record 的逻辑不变。
- response 收尾分支：`speed = _read_wire_turn_speed(...)`，非 None 时随用量同帧 `yield Chunk("usage", "", usage=stats, speed=speed)`。

### 3. GUI 簿记与文案（`src/gui/panels/chat/panel.py`）

- 新增字段 `_turn_speed: TurnSpeed | None = None`；`_on_chunk` 的 `kind == "usage"` 分支：`chunk.speed is not None` 时顺手存入。
- 切后端清理段（`_usage = None` 同段）一并 `_turn_speed = None`。
- `_compose_usage_tooltip` 增加 `speed: TurnSpeed | None` 参数（放 `turn_started_at` 后、`now` 前），`last_turn` 行之后追加速度行；`_refresh_usage_tooltip` 调用点同步传参。

### 4. 测试

- 扩展 `tests/test_usage_badge_timing.py`：`_compose_usage_tooltip` 新参用例——speed 非 None 时末行文案形态、None 时无该行（回归既有用例需补 None 实参）。
- 新增 `tests/test_turn_speed.py`（纯函数，合成 wire.jsonl 于 tmp_path）：
  - 单调用配对：output 直取、耗时 = rec.time − req.time；
  - 多调用求和：Σoutput / Σgen（含 output 非单调序列，验证不差分）；
  - 缺 time/缺 output/孤儿 usage.record（无前置 request）→ 跳过；
  - 全部残缺 → None；
  - 基线截断：基线前的记录不参与。
- 探针式 GUI 验证（offscreen，`.temp/`）：mock 一轮带 speed 的 usage chunk，读徽章 tooltip 确认末行。

### 5. 门禁与收尾

- 跑 `bash scripts/check.sh`，全绿。
- 真实环境人工验证：kimi 后端发一轮（含工具调用），收尾后悬停见速度行，数值与手算 wire.jsonl 配对结果一致；kilocode/reasonix 后端悬停无该行。
