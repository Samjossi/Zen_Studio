# ACP 会话 rawOutput 字符串帧诊断与修复计划

> 打包版 Zen Studio 聊天面板出现 `[请求失败] 'str' object has no attribute 'get'`。
> 经 wire.jsonl 落盘证据 + 开发态探针复现双重实证：kimi-code 在工具被中止
> （aborted）时发出的 `tool_call_update` 帧中 `rawOutput` 是**字符串**而非对象，
> 公共帧映射层对其做了 dict 假设，抛出 AttributeError。与打包无关，开发态同病。

## 1. 故障现象

用户于打包版（AppImage/onedir，2026-07-31 23:31 构建）聊天面板提问，
后端 Kimi（ACP）/ 模型 k3-256k。输出区依次上屏：思维链 → 正文一段 →
Grep、Bash 两张工具卡 → 随后流中断，末尾出现：

```
[请求失败] 'str' object has no attribute 'get'
```

发送按钮回到空闲态，本轮用户消息按失败纪律不入历史
（`gui/panels/chat/panel.py` `_on_finished`）。

### 2.2 开发态探针复现（实证，与打包无关的关键证据）

探针 `.temp/repro_acp_str_get.py`（项目 `.venv` 直驱 `KimiAcpLLM`，
monkeypatch `AcpConnection._dispatch_line` 记录全部原始帧 + 完整 traceback），
发同一 prompt 后**稳定复现同一异常**。肇事协议帧原文：

```

`rawOutput` 为裸字符串 `"Grep aborted"`，非 ACP 常规的对象形态。
该帧之后 agent 回 `{"result": {"stopReason": "cancelled"}}` 收尾。

```

### 2.3 打包产物排查

`building/dist/zen-studio/_internal/` 为 PyInstaller PYZ 归档，协议代码与

此前开发测试未踩到该路径，"打包后才出现"系巧合。

## 3. 根因

`llm/providers/acp.py` 公共帧映射层对 `tool_call_update.rawOutput` 做了
**单一形态假设（必为 dict）**：

- `_extract_tool_output`：`rawOutput.output` 取值前无类型分流，
  str 形态直接 `.get` 抛 AttributeError（本次肇事点）。
- `_map_tool_call_update` 的 failed 分支：`rawOutput.error` 取值同病
  （本次被上一处先行拦截，未暴露）。

kimi-code（0.29.1）在**工具被中止**场景把 `rawOutput` 降级为纯文本
（如 `"Grep aborted"`），属于 agent 侧合法的宽松序列化；客户端 R1 纪律
「泛化层不臆造协议」的反向含义同样成立——**不臆造对端必为对象**。

异常经 `ChatWorker.run` 兜底捕获后仅 `str(e)` 上屏
（`gui/panels/chat/worker.py`），traceback 全丢，导致协议层 bug 的
一线症状只剩一句无上下文的 `'str' object has no attribute 'get'`。

### 3.1 事件链全貌

```
step2 LLM 请求 → 轮次被取消（turn.cancel）
  → agent 中止进行中 Grep，发 status=failed + rawOutput="Grep aborted"（str）
  → _extract_tool_output 对 str 调 .get → AttributeError
  → worker 捕获 → finished_with_error → [请求失败] 上屏
  → 真实语义（轮次取消/工具中止）被二次异常完全吞掉
```

## 5. 修复计划

### T1 — `_extract_tool_output` rawOutput 类型分流（`llm/providers/acp.py`）

取值改为三态分流，str 直接作为输出文本进入既有净化/截尾管线
（`_clean_terminal_text` → 单行截断 → 截尾末 N 行），语义与 content
兜底拼接天然同构：

```python
# llm/providers/acp.py（_extract_tool_output 取值段示意）
raw = update.get("rawOutput")
if isinstance(raw, dict):
    output = raw.get("output")
elif isinstance(raw, str):
    output = raw          # 中止/失败场景的纯文本降级形态
else:
    output = None
```

后续 `isinstance(output, str)` 判定与 content 兜底逻辑零改动。

### T2 — failed 分支 error 提取同范式分流（`llm/providers/acp.py`）

`_map_tool_call_update` 的 failed 分支：dict 走 `rawOutput.error`
（保 dict→message 二次提取）；str 直接当作错误文本交 `_truncate_line`
取首行——`"Grep aborted"` 得 `payload["error"]="Grep aborted"`，
上屏 `✖ ▸ Grep（Grep aborted）`，与 `_tool_update_fallback` 渲染零改动衔接。

### T3 — worker 异常留 traceback 诊断通道（`gui/panels/chat/worker.py`）

`ChatWorker.run` 兜底分支在 `finished_with_error.emit(str(e))` 前补
`traceback.print_exc()`（stderr）。上屏文案不变（用户界面纪律不动），
仅保证下次协议层异常可一眼定位，杜绝"只剩一句 str(e) 全靠猜"。

### T4 — 回归验证

1. **单元级**：构造 `rawOutput` 为 str 的 `tool_call_update` 帧（直接复刻
   §2.2 肇事帧）过 `map_session_update`，断言返回合法
   `Chunk("tool_call_update", ...)` 且 `payload["error"]` 取到中止文本。
2. **集成级**：重跑探针 `.temp/repro_acp_str_get.py`，全程无 exception、
   `stopReason=cancelled` 轮次按既有语义收尾（不再伪装成"请求失败"）。
3. **冒烟级**：`.temp/` 现有 smoke 脚本（`smoke_chat_activity.py` 等）
   回归，确认 tool_call_update 渲染无漂移。

### 验收标准

- ✅ str/dict/缺省三形态 `rawOutput` 均不抛异常，语义各自正确上屏。
- ✅ 中止场景上屏为 `✖ ▸ 工具名（中止文本）`，不再出现 `[请求失败] 'str' object ...`。
- ✅ worker stderr 可见完整 traceback（仅异常路径）。
- ✅ 既有 smoke 脚本全绿。
