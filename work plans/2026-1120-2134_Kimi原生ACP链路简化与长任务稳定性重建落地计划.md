## 1. 先回答两个问题

### 1.1 这些错误能不能修复

**IDE 自己制造的“同步不止、十分钟误杀、停止后旧同步泄漏到下一轮”可以修，而且应靠删除复杂机制来修。**

但另一类问题不能直接靠 IDE 宣称根治：既有真实证据显示，Kimi 曾在用户轮次仍需继续工作时，对 ACP `session/prompt` 提前返回 `end_turn`。这是上游违反轮次契约的问题。IDE 若完全遵守官方协议，就无法凭空知道上游是否还将在私有通知轮次里继续工作。

因此，本计划把责任拆清：

- IDE 只实现官方 ACP 的一条可预测链路，不再自建第二套轮次生命周期；
- 上游通知轮次问题用最小真实场景独立验收、独立留存证据和上报；
- 上游未通过时不得再写成“全部修复”，也不得重新堆一套私有门禁把问题藏起来。

### 1.2 场景矩阵测试能不能解决

**场景矩阵是必要的验收工具，不是修复本身。**

它能稳定复现“后台通知交叉、停止与恢复竞争、长时间静默、真实断管”等条件，防止同一缺陷换种文案回来；但若生产代码仍保留互相矛盾的状态机，增加再多假后端测试也只会把组合继续放大。本次顺序必须是：

1. 先删掉第二套生命周期；
2. 再用小规模场景矩阵守住唯一链路；
3. 最后用真实 Kimi 和最终 AppImage 验收用户原始长任务。

当前工作树只有 `tests/test_gate.py` 这一实质性测试文件；前序计划提到的 `tests/test_acp_recovery.py`、`tests/test_turn_abort.py`、`tests/test_kimi_turn_consistency.py` 当前均不存在。因此不得沿用历史“578 项通过”等数字充当本次基线，也不恢复一整套已经失联的测试堆；本次只新增与简化后行为一一对应的聚焦测试。

## 2. 本次事故证据与根因分层

### 2.1 官方连接方式已经足够

Kimi 官方文档明确给出的 IDE 接入方式是：IDE 启动 `kimi acp` 子进程，通过 stdin/stdout 运行 JSON-RPC。官方能力已经覆盖：

- `initialize`：协商能力；
- `session/new`：创建会话；
- `session/resume`：重挂接既有会话且不回放历史；
- `session/prompt`：发送提示并接收流式更新，响应中的 `stopReason` 表示本轮终态；
- `session/update`：转发正文、工具、计划等事件；
- `session/cancel`：取消当前轮次；
- `session/close`：关闭活动会话。

官方文档没有要求 IDE 读取私有 `wire.jsonl` 判断完成、排空内部通知、设置十分钟无响应判死，或在正常 `end_turn` 后再建立恢复标记。

官方入口：

- ACP 参考：<https://www.kimi.com/code/docs/en/kimi-code-cli/reference/kimi-acp.html>
- IDE 接入：<https://www.kimi.com/code/docs/en/kimi-code-cli/guides/ides.html>
- 会话机制：<https://www.kimi.com/code/docs/en/kimi-code-cli/guides/sessions.html>
- 更新日志：<https://www.kimi.com/code/docs/en/kimi-code-cli/release-notes/changelog.html>

### 2.2 20:28 这次不是已证实的“先断线”

运行日志中的顺序是：

1. 20:27:45，Kimi CLI 2.7.1 初始化成功；
2. 20:28:48，IDE 已收到 `stopReason=end_turn`，随后私有跟踪器进入 `draining`；
3. 20:28:48 至 20:39:15，没有对应的 `connection_dead`，也没有 `drain_end`；
4. 20:39:15，看门狗主动执行 `mark_stalled`、`session/cancel` 和本地中断；
5. 20:41:59，用户下一次手动发送时重建连接，`session/resume` 成功。

所以这次符合用户体感的机制是：**ACP 已答复，但私有门禁仍称后台活跃；看门狗又把这种活跃误判成无响应并取消。**20:41:59 的 EOF/退出码 `-15` 晚于看门狗，属于后续受控重建，不是最初故障证据。

### 2.3 21:26 这次还暴露了旧同步泄漏

21:26:33 收到 `end_turn` 后进入 drain；21:27:27 用户手动停止；21:27:44 下一次发送尚未建立新 prompt，就以 `requestId=None` 再次进入“内部通知轮次仍活跃”的旧 drain。

这说明私有通知状态跨手动停止残留，下一轮先处理旧轮次，而不是简单发送用户的新指令。继续给这个状态机补停止分支，只会增加下一组竞态。

### 2.4 上游与本地两层问题不能混写

- **上游层**：后台通知 steering 后，ACP 可能提前 `end_turn`，或用户追问未形成真实执行轮。Kimi 2.7.1 更新日志虽包含“后台通知轮次结束前保持排队 prompt”，当前 2.7.1 的真实事故说明仍需按本机场景复验，不能把 changelog 当作已经解决。
- **本地层**：为补偿上游缺陷而加入的 `KimiTurnTracker`、四态判定、轮前/轮后 drain、失配恢复和看门狗形成了第二套生命周期。它没有可靠地修复上游，反而新增了无限同步、自动取消和跨轮残留。

本计划只承诺彻底移除本地第二层问题；上游第一层必须单独通过真实验收。

## 3. 目标与非目标

### 3.1 目标

- Kimi 每轮只有一条生命周期：发送 prompt → 转发 update → 收到 prompt response → 按 `stopReason` 收尾。
- 私有 wire 永远不再决定 busy、成功、失败、取消、恢复或待发。
- Kimi 不再因“十分钟无新帧”自动取消，更不在已经收到 response 后自动杀掉任务。
- 手动停止只执行 `session/cancel` 与本地解封；停止后的下一轮不携带旧 drain、旧 requestId 或旧恢复标记。
- 只有真实 stdout EOF、进程退出或写帧失败才使连接失效；下一次手动发送可 `session/resume` 原会话，原 prompt 自动重放次数为 0。
- 用量和子代理展示即使保留，也只是附加信息，缺失、迟到或格式异常不得改变轮次结果。
- 生产代码以净删除和路径缩短为目标，不新增状态枚举、恢复模式、定时器、重试器或并行消费通道。

### 3.2 非目标

- 不保证用 IDE 本地逻辑根治 Kimi 上游通知调度缺陷；
- 不重写公共 ACP 连接层，不统一改造其他 provider；
- 不引入新的通用 `TurnOutcome`、会话状态机或恢复状态机；
- 不自动重放中断 prompt，不自动新建空会话冒充恢复；
- 不通过禁用所有后台任务、隐藏工具卡或关闭提示音制造“已稳定”的假象；
- 不恢复前序计划中当前已不存在的大批测试文件，不追求测试数量指标。

## 4. 简化后的唯一设计

### 4.1 正常轮次

`chat()` 在同一会话串行执行：

1. 确保进程和会话可用；新会话使用 `session/new`，已有活会话直接复用；
2. 发送恰好一次 `session/prompt`；
3. 将 `session/update` 映射为正文、工具、计划等 Chunk；
4. 收到该 requestId 的 response 后，只按协议处理：
   - `end_turn`：正常完成；
   - `cancelled`：非成功取消收尾；
   - `max_tokens`、`max_turn_requests`、`refusal`：明确失败；
   - 协议 error：明确失败；
   - 未知值：保留现有兼容策略并记录原始值。
5. 用量只做有界、尽力而为的收集；无论是否有用量，都不再重新审查或推翻已经收到的 ACP 终态。

删除 response 后的 `snapshot → drain → settled → desynchronized` 链路，也删除下一轮 prompt 前的旧通知 drain。

### 4.2 手动停止与长时间等待

- 用户停止是唯一主动的轮次超时替代品：调用 `session/cancel`，并用本地 abort 解除等待；
- 手动停止不终止活进程、不标记恢复、不清空 sessionId；
- 下一轮直接复用同一活会话，不先排空旧通知；
- Kimi 不启动现有 stall watchdog，也不再显示“十分钟无响应，已自动中断”；
- 其他后端的看门狗设置暂不改语义，避免扩大范围；Kimi 侧只做明确旁路，不新增能力接口。

这是对“简单可预测”的明确取舍：真正永久沉默时由用户决定何时停止，而不是 IDE 猜测 agent 已死亡。

### 4.3 真实连接失效与恢复

仅以下证据进入连接恢复：

- ACP stdout EOF；
- agent 进程意外退出；
- `session/prompt`、`session/cancel` 或反向 RPC 应答发生真实写帧失败。

处理保持现有已验证的安全边界：当前轮次非成功收尾，保留原 sessionId，不自动重放；下一次用户手动发送才重建进程、`initialize`、`session/resume`，再发送这次新指令。恢复失败不发送 prompt、不静默 `session/new`。

普通协议错误、用量缺失、私有 wire 异常、手动停止和“等待时间长”均不得标记连接死亡。删除 Kimi `mark_stalled()` 及其与面板恢复文案的耦合。

### 4.4 私有 wire 与展示信息的边界

- 删除 `src/ide/llm/providers/kimi_turn_consistency.py` 及所有引用；
- 删除 `TurnDesynchronized`、轮次一致性日志、`turn_sync` Chunk 和“正在同步/核对”临时提示；
- 同步清理临时提示面板的设置、预览、转发和说明，避免留下无生产入口的 UI 功能；
- 既有 wire 用量、Token 消耗和子代理 sidecar 可在本期保留，但只能提供展示数据；不得再向轮次控制流回传活跃、完成或恢复判断；
- 若实施中发现任一展示功能仍要求 drain 才能工作，应先解耦或暂时关闭该增强展示，不得为保展示而恢复第二套生命周期。

## 5. 场景矩阵：只测一条链路，区分 IDE 与上游责任

### 5.1 IDE 必须通过的自动化场景

| 编号 | 场景 | 必须观察到的结果 |
|:---|:---|:---|
| I1 | 普通 `end_turn` | 成功一次；无 drain、无失配、无恢复 |
| I2 | 非成功 `stopReason` 与协议 error | 分类正确；不播报成功；不自动待发 |
| I3 | response 后 wire 缺失、损坏或仍有通知记录 | 轮次结果不变；不阻塞、不重建 |
| I4 | 用量缺失或延迟 | 只影响用量展示，不影响终态 |
| I5 | 流式输出中手动停止 | `cancel` 一次；本地解封；不杀活进程 |
| I6 | 手动停止后立即发送下一条 | 新 prompt 一次；无 `requestId=None` 的旧 drain |
| I7 | 超过旧十分钟阈值但仍有活动帧 | 自动取消 0 次；任务继续 |
| I8 | 超过旧十分钟阈值且完全静默 | 自动取消 0 次；用户可手动停止 |
| I9 | response 前 stdout EOF | 当前轮失败；保留下轮恢复身份；不自动重放 |
| I10 | 写帧失败 | 与 EOF 同一恢复边界；无假发送 |
| I11 | 下一次手动发送时 resume 成功 | sessionId 不变；只发送新 prompt |
| I12 | resume 不支持、超时或失败 | 新 prompt 0 次；隐式新会话 0 次 |
| I13 | 正常完成后的待发 | 仅正常成功可自动接续；失败/停止不接续 |
| I14 | 等待 response 时关闭标签 | 不重建进程；不恢复；无迟到死讯污染 |

I3 是本次删除私有门禁的关键测试：它不再要求 IDE 从 wire 证明成功，而是证明 wire 无法干扰官方终态。

### 5.2 真实 Kimi 上游契约场景

| 编号 | 真实场景 | 通过标准与失败归属 |
|:---|:---|:---|
| U1 | 后台 Bash 自然完成，同时用户轮次仍在工具链中 | agent 不得提前结束仍需工作的用户 prompt；若提前 `end_turn` 后继续执行，记为上游失败 |

### 10.3 经验沉淀

- 删除本地补偿后，上游提前 `end_turn` 会直接可见；这比继续堆 drain 更诚实，也更容易把责任分层。验收必须同时记录“工具已执行”和“正文是否到达”，不能把工具副作用当作成功。
- 空 `end_turn` 可能发生在 3 秒内且没有任何 update 帧；仅靠 provider 的 chunk 序列无法区分“模型没说话”和“上游提前收尾”，需要裸 ACP 帧序或 CLI 内部日志作为第二证据。
- AppImage GUI 验收可用 `Xvfb + xdotool + 隔离 XDG_CONFIG_HOME` 完成；ASCII 输入前必须禁用 fcitx（`QT_IM_MODULE=qt`、`XMODIFIERS=@im=none`），否则会被拼音输入法组合成中文。隔离配置目录路径要短，Unix domain socket 路径超过约 108 字节会让 `QLocalServer.listen` 失败并静默退出。
- 真实 Kimi CLI 在 workspace-write 沙箱下会因无法写 `~/.kimi-code` 报 `session/new -32603 storage write failed`；这是沙箱权限问题，不是 ACP 故障，验收时应与协议失败分开记录。
- “长任务自然完成”与“后台通知轮次契约”是两条独立验收线：前者已通过，不能据此宣布后者也通过；后者仍应以上游修复或明确规避为准。
