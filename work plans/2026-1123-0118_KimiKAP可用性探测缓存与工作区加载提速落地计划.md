## 1. 背景与目标

Kimi 切换为唯一 KAP 接口后，选择工作区时的首个 `ChatPanel` 加载出现性能回退。空白窗口不创建 `ChatTabs`，因此没有该问题；选择工作区会启动新进程并创建 `ChatTabs → ChatPanel → ModelBar`，触发 Kimi 可用性与模型目录探测。

当前生产探针实测（2026-11-23，本机，offscreen 生产控件）：

| 指标 | 当前结果 |
|:---|---:|
| 首个 `ChatPanel` 总耗时 | 1426.8 ms |
| Kimi CLI 调用合计 | 1402.6 ms |
| `kimi --version` | 4 次，分别 281.1 / 275.0 / 277.0 / 273.8 ms |
| `kimi provider list --json` | 1 次，295.7 ms |
| KAP 服务是否启动 | 否 |

根因已经确认：`ModelBar` 在厂商、接口、模型、强度四条刷新路径分别调用 `spec.available()`；Kimi 唯一接口的 `available=kimi_kap_available` 每次都同步启动 `kimi --version`。旧 ACP 可用性只查二进制，且原双接口排序会让厂商级 `any()` 短路，因此没有这四倍放大。模型目录已有进程缓存，可用性结果却没有缓存。

目标：

1. 同一进程内，Kimi KAP 可用性只探测一次；首个 `ChatPanel` 的 Kimi CLI 调用从 5 次降为 2 次（版本 1 次 + 目录 1 次）。
2. 多标签恢复、重复创建 `ModelBar`、打开设置中心不再按控件数量重复执行版本探测。
3. 保留 CLI ≥ 2.7.0 门槛、版本解析失败 fail-open、CLI 缺失 fail-closed 等现有语义。
4. 可用性与模型目录按接口名隔离，并经 `registry.refresh_models()` 同点失效；显式刷新后能重新探测新版本。
5. 用生产控件调用计数和同一探针耗时对比验收，不以“感觉变快”代替证据。

非目标：

- 不删除或弱化 KAP 版本门槛，不把可用性退化为仅检查二进制。
- 不引入后台探测线程、跨进程磁盘缓存、TTL 或文件监听。
- 不改 `ModelBar` 四级选择结构，不改设置中心布局。
- 不改 KAP 建连、会话、通知轮、停止与恢复链路，不改 DSH/Local provider。
- 不承诺新进程零探测：每个工作区新进程仍保留一次版本检查和一次目录拉取。

## 3. 现状锚点

- `src/ide/llm/cache.py` 已实现 `_models_cache`、`_efforts_cache`、`_raw_cache`，键恒为接口实现名；`_cache_lock` 覆盖“查 + 拉 + 写”，`clear(name=None)` 是唯一失效实现。
- `src/ide/llm/providers/kimi/spec.py` 已用 `cached_raw("kimi-kap", load_kimi_provider_catalog)` 保证目录一路拉取、三路派生，但 `available` 直接引用原始 `kimi_kap_available`。
- `src/ide/llm/providers/kimi/catalog.py` 的 `kimi_kap_available()` 每次执行 `kimi --version`，单次超时上限 5 秒；`load_kimi_provider_catalog()` 每次实际 miss 执行 `kimi provider list --json`，超时上限 15 秒。
- `ModelBar` 构造路径的厂商检查、接口刷新、模型刷新、强度刷新各调用一次 `available()`，与实测四次版本调用一一对应。
- `ChatPanel._get_provider()` 在首轮对话前的懒实例化也可能调用 `available()`；进程缓存应让该调用命中，不再增加版本子进程。
- `registry.refresh_models(name=None)` 已委托 `cache.clear(name)`，公共签名无需变化；当前模型目录采用进程级无 TTL 语义，可用性缓存应保持一致。
- `tests/test_llm_spec_cache.py` 的 `clean_cache` fixture 每个用例前后调用 `cache.clear()`，新增缓存纳入同一清理口即可避免测试串态。

## 4. 设计决策

1. **复用现有缓存范式，不在 GUI 加 Kimi 特判**：性能问题归接口声明与缓存层，`ModelBar` 继续只消费 `spec.available()`。
2. **进程级无 TTL**：与模型目录一致，不做定时刷新；CLI 安装/升级后的显式重检经 `refresh_models()`，普通应用重启自然重新探测。
3. **False 必须可缓存**：CLI 缺失或低版本同样只探测一次；实现不得用会混淆“未缓存”与“已缓存 False”的简易 `dict.get()` 判空。
4. **同锁去重**：首个调用在锁内完成探测，后续 GUI/设置中心/其他线程等待同一结果；并发 miss 不得重复拉起 CLI。
5. **异常不固化**：缓存包装只有在 `fn()` 正常返回后才写入；若原始函数自身抛出异常，下次调用允许重试。原始函数现有的错误转 bool 语义不变。
6. **定向失效**：`clear("kimi-kap")` 同时清 Kimi 可用性、模型、强度、原始载荷；`clear("dsh-acp")` 不得清 Kimi 结果；`clear()` 清全部。
7. **不改原始函数出口**：`kimi_kap_available()` 仍可供传输测试直接验证版本门槛；缓存包装只放在 `spec.py`，避免把缓存藏进传输/目录实现。
8. **调用次数是主闸门，耗时是同机佐证**：单元/回归测试不拿绝对毫秒做脆弱断言；真实探针记录前后耗时，调用次数必须严格达标。

## 6. 风险与注意点

- ⚠️ **可用性结果会随进程缓存**：用户在应用运行中安装/升级 CLI 后，不会在每个控件刷新时立即重检；必须经 `refresh_models()` 或重启，文档需明确。
- ⚠️ **False 缓存最容易写错**：若用 `cached = dict.get(name); if cached is None` 虽能区分 False 与缺失，但若改用真值判断会重复探测；必须有低版本/缺失回归。
- ⚠️ **锁内慢调用会等待**：首个版本/目录探测仍阻塞当前调用线程，这是控制重复子进程的既定缓存语义；本计划不把它改成后台任务。
- ⚠️ **新进程仍有固定成本**：选择工作区会新建进程，无法复用旧进程缓存；验收目标是从五次降到两次，不是宣称完全无探测。
- 🔴 **不得放松版本门槛**：不能为提速把 `available` 改回只查二进制，也不能缓存“任何版本均可用”的假结果。
- 🔴 **不得扩大协议改动**：KAP 传输、DSH/Local 和公共 ACP 不属于本次性能修复范围。

## 7. 已确认决策

- 用户拍板（2026-11-23）：针对选择工作区后加载明显变长的问题先写修复计划。
- 已确认根因：Kimi 唯一 KAP 接口的 `available()` 在首个 `ModelBar` 中同步执行 4 次 `kimi --version`，另有 1 次模型目录调用；空白窗口不建 `ChatTabs`，所以不经过该路径。
- 本计划采用进程级、按接口隔离的可用性缓存，复用 `llm.cache` 同锁与同失效口；保留每个新进程一次真实版本检查。

**经验沉淀**：

1. 可用性缓存必须以“键是否存在”判断命中，不能用真值判断；`False` 与首次 miss 的生命周期不同。只有原始探测正常返回后才写入，异常自然保留重试机会。

4. 进程级无 TTL 缓存不能跨工作区新进程复用；每个新进程保留一次版本探测和一次目录拉取是既定边界，运行中升级 CLI 必须显式刷新或重启。
