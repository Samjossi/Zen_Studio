# 插话（排队消息）功能与停止按钮修复计划

## 1. 背景

两件事同一轮交互链路（发送/停止双态按钮 + 轮次状态机），合并立项：

1. **停止按钮失效（缺陷）**：用户反馈 busy 期间点击「■ 停止」无法中断
   AI 输出。2026-08-06 06:2x 已诊断定位（见 §2.1），本计划含修复。
2. **插话功能（新功能）**：用户拍板立项——AI 执行任务（轮次进行中）时，
   用户仍可继续输入一句话；这句话**等当前处理完成后插入对话**（自动
   作为下一轮发出）。参考 `参考代码/kilocode-main` 的排队消息实现
   （调研摘要见 §2.3）。

用户明确要求：停止功能与插话功能**并存**，busy 期间两者都可用。

## 2. 现状诊断与调研

### 2.1 停止按钮失效根因（2026-08-06 诊断，探针实证复现）

`_on_send`（panel.py）执行顺序缺陷：

```
671  input.clear()        → textChanged → _refresh_send_button（worker=None，置禁用）
672  _set_busy(True)      → 文本「■ 停止」+ setEnabled(True)   ← 按钮已正确激活
...
682  attachments.clear()  → _sync_visibility() 无条件发 changed
                          → _on_attachments_changed → _refresh_send_button()
                          → 此时 self._worker 仍为 None（693 行才创建）
                          → busy 守卫（worker is not None and isRunning）失效
                          → setEnabled(空文本 and 0附件 = False)  ← 按钮被重新禁用
693  ChatWorker 创建并 start
```

offscreen 探针（`.temp/probe_stop_button.py`）实证：busy 态按钮文本
「■ 停止」但 `isEnabled()=False`，点击不触发任何动作。引入点为
1ed6a7c（0340 图片附件功能）——此前无 `changed` 发射源落在该窗口。

协议层与 agent 无罪：直连 `kimi acp`（0.29.1）两次 spike
（`.temp/spike_cancel_kimi.py` / `spike_cancel_tool.py`）——纯文本流式中
与工具执行中发 `session/cancel`，均 0.01s 收到 `stopReason=cancelled`
收尾帧。Esc 路径完好（直调 `request_stop`，不依赖按钮使能，
`.temp/probe_stop_esc.py` 验证通过）。

### 2.2 协议约束：并发 prompt 不可行，插话须 IDE 侧排队

`dream-acp/protocol/dream-acp-v1.md` §1 明确：**同一时刻仅一个活跃
对话轮次**。本项目 ACP 形态为「agent 侧管理会话历史、IDE 每轮只发
末条 user 消息」——轮次进行中直接发第二个 `session/prompt` 的行为
各后端未定义（kimi/kilocode/opencode/reasonix 需 T0 spike 实测取证，
见 §4）。因此插话的通用实现路径是 **IDE 侧 FIFO 队列**：busy 期间的
输入在 IDE 本地排队上屏，轮次收尾后自动出队发送——零协议改动、
四后端天然同构。

### 2.3 kilocode 排队消息机制调研摘要（`参考代码/kilocode-main`）

两代实现，要点如下（详细调研记录见本会话，引注行号为仓库内路径）：

- **V1 现役**（`packages/opencode/src/kilocode/session/prompt-queue.ts`）：
  每会话一个内存态 FIFO Promise 链；**消息先入历史存储、队列只存
  MessageID**；当前 turn 每 step 前 `scope()` 把排队消息从发给 LLM 的
  messages 中隐藏；step 边界 `hasFollowup()` 则以 `superseded`（非
  `interrupted`）软交棒；abort（停止按钮）= version 戳整队作废 +
  中断当前流。
- **V2 下一代**（`packages/core/src/session/input.ts`）：SQLite 事件溯源，
  显式双模式 `Delivery = "steer" | "queue"`——steer 在 turn 内 step
  边界注入当前对话，queue 等 turn 完全结束后开新 turn。
- **UI**：输入框 busy 不锁定；排队消息以完整用户消息上屏 + 「Queued」
  徽标 + 删除×（**可删不可编辑**）；徽标可纯客户端推导；turn 关闭
  原因区分 `completed | error | interrupted | superseded`，被排队
  顶掉的轮次不弹中断警告。

对本项目的映射结论：

| kilocode 概念 | 本项目映射 |
|---|---|
| 消息先入存储、队列只存 ID | 入队即上屏排队气泡 + 队列簿记（文本+附件快照），`_history` 仍在实际发送时才入 |
| `queue` 模式（turn 结束后接管） | 用户拍板的语义即此：**等当前处理完成后插入对话** |
| abort = 队列作废 | 停止语义对齐（D5），排队文本退回输入框不丢（比 kilocode 宽容） |
| `superseded` 非中断 | 自动接续的轮次不加「⏹ 已手动停止」类标注 |
| steer 模式（turn 内注入） | **非目标**（§7）：需 agent 侧支持，协议未定义，远期候选 |

## 3. 设计决策

### D1 停止按钮修复：busy 簿记守卫（治本）+ 信号精确化

- **panel.py 新增 `_busy: bool` 簿记**（初值 False，`_set_busy` 单点
  置位）；`_refresh_send_button` 的守卫由「worker 存在性代理」改为
  `if self._busy: return`——消除「busy UI 已立、worker 未建/已销毁」
  的竞态窗口，任何信号源（textChanged/attachments.changed/未来新增）
  落入该窗口均安全。
- **attachments.py 信号精确化**：`clear()` 无 chip 时不发 `changed`
  （`_sync_visibility` 仅在可见性实际变化时发射）——语义精确 + 去除
  空转，与 D1 第一刀叠加双保险。
- 备选（不采纳）：仅把 `attachments.clear()` 挪到 `_set_busy(True)`
  之前——最小但治标，窗口仍在，未来新增信号源可再踩。

### D2 插话架构：IDE 侧每标签 FIFO 队列（零协议改动）

- 队列归 **ChatPanel 实例自持**（与 provider/worker 同生命周期，多
  标签天然隔离，对齐 0112 计划各标签独立粒度）；
- 队列项 = `(文本, 附件快照)`（附件与正常发送同一收集路径，入队时
  快照、出队时随消息发送；`_history` 仅在实际发送时写入，现语义
  不变）；
- 内存态、不持久化（会话本身不跨重启持久化，与 kilocode V1 一致）；
- 容量上限 **10 条**，满队再发送 → 输出区系统提示「排队消息最多
  10 条」（防误触连发刷屏，对齐附件上限的提示惯例）；
- 入队触发点：`_on_send` 现有的 `worker.isRunning()` 早退分支改造为
  入队路由（Enter 与按钮同走 `_on_send`，天然双入口）。

### D3 底行布局：双常驻恒宽按钮（停止/插话并存，守 2305 宽度纪律）

busy 期间两个动作都要可达（用户明确要求），且**任何状态下
sizeHint 不变**（左栏宽度病根纪律，2026-0724-2305）：

- 底行右端改为**两个常驻按钮**：「发送/插话」双态钮 +「■ 停止」钮；
- 「发送/插话」：空闲=「发送」（空文本禁用），busy=「插话」（文本
  非空即可点，恒宽按两态文本较大者一次写死，现状手法平移）；
- 「■ 停止」：常驻恒宽、**仅 busy 可用**（空闲禁用，修复后 busy
  恒可用——D1 保障）；文本恒定故宽度恒定；
- Esc 语义不变（busy=停止）；busy 期间 Enter=插话入队；
- **左栏最小宽上调至 400（用户拍板，2026-08-06 06:45）**：底行新增
  一钮抬高静态下限（现 315/320 实证链），`ChatTabs.MIN_WIDTH`
  320 → 400 一处改（0401 计划 D4 单一来源常量），main_window 双闸
  接线不变；T5 按 0401 计划 T6 同法重测静态下限实证链，实测值与
  400 的对账留痕实施记录（实测若 >400 以实测为准回填并留痕）。

### D4 排队消息上屏：用户气泡 + 「排队中」徽标 + 删除×

- 入队即在输出区末尾追加**排队气泡**：复用用户气泡渲染，叠加
  「排队中」灰徽标与右上角 ×（语义对齐 kilocode 的 Queued 徽标 +
  删除钮，可删不可编辑）；
- 出队发送时**徽标摘除转正式气泡**（同一控件改写，不重复 append）；
- 删除× → 队列项剔除 + 气泡移除；
- 双轨同构：新轨 `ChatTranscriptView` 与旧轨 `ChatOutput` 各加一个
  三方法最小接口 `append_queued_user_message(text, images) → handle` /
  `promote_queued(handle)` / `discard_queued(handle)`（对齐图片附件
  双轨实现先例；旧轨属新功能上屏，非冻结违约）；
- 排队气泡**不参与** `_history`/`_stream_buffer`，轮次收尾的
  `reset_activity_anchors`/`end_stream` 不受影响（簿记独立）。

### D5 出队时机与停止/失败语义

| 轮次收尾 | 队列行为 |
|---|---|
| 正常完成（`_on_finished` 无错误） | **自动出队发送**下一条（FIFO，接续轮不加中断标注——kilocode `superseded` 同义） |
| 失败（有错误） | **不自动接续**：队列保留，输出区系统提示「上轮失败，排队消息已保留（N 条），可手动发送或删除」——防连环失败烧 token |
| 用户停止（`_on_stopped`） | **队列清空**：对齐 kilocode abort 语义（停=全停）；排队文本**合并退回输入框**草稿（多条以换行相接）不丢——比 kilocode 整队删除宽容 |
| 标签关闭 | 队列随 panel 销毁（现有 close 两段式不变） |

失败态的「手动发送」入口：输入框已有草稿或用户重新点击发送时，
优先消耗队列首条？——**否**，简化为：失败保留的队列在用户下次
正常发送成功后恢复自动接续（发送动作本身即解锁）。队列清空（停止）
后退回的文本可由用户自由编辑再发。

### D6 占位符与状态行文案

busy 期间输入框占位符由现状
「{后端} 响应中…点击下方 ■ 停止或按 Esc 可中断」改为
「{后端} 响应中…Enter 插话排队 / ■ 停止或 Esc 中断」；
有排队消息时追加「（已排队 N 条）」——状态行空间不动（占位符不
参与布局宽度）。

### D7 多标签与设置中心零改动

队列每标签自持（D2），切标签互不感知；`busy_changed`/`turn_finished`
语义不变（自动接续仍是一轮正常对话，Git 刷新联动照旧）；设置中心
模型页禁用逻辑不变。

## 6. 风险与取舍

- ⚠️ **底行宽度增加**：双常驻钮抬高左栏静态下限（D3），左栏最小宽
  320 → 400（用户拍板，2026-08-06 06:45）——窄屏用户左侧可用宽度
  变小，为停止/插话双钮并存的明确取舍。
- ⚠️ **停止清空队列的误触成本**：用户连点停止会丢掉排队消息——以
  「文本退回输入框」兜底（D5），实际损失为零（仅丢失排队动作本身）。
- ⚠️ **agent 侧历史与 IDE 队列的可见性差异**：排队期间 agent 不知道
  有后续消息，当前轮次的回答不会顾及排队内容（kilocode `queue`
  模式同此语义，与用户拍板的「完成当前处理后插入」一致）。
- **附件快照的落盘依赖**：排队消息携带的粘贴型附件在出队发送前
  被外部删除时，按既有读盘失败跳过惯例尽力而为（0340 计划 D 系
  语义平移）。
- **多标签并行**：各标签队列独立，无跨标签调度（D7），无新增并发
  面。

## 7. 非目标

- **steer（turn 内注入当前对话）**：需 agent 侧支持（kilocode V2 的
  `Delivery="steer"` 需 agent 实现），ACP 协议未定义、四后端行为
  未知——T0 spike 取证后留档为远期候选，本期不做；
- 排队消息的**编辑**（kilocode 亦仅有删除）；
- 队列**跨重启持久化**（kilocode V2 的 SQLite 事件溯源，会话本身
  不持久化的前提下无意义）；
- 全局（跨标签）排队调度；
- dream-acp 协议文档修订（本期零协议改动）。

## 偏差 1：`_refresh_send_button` 的 _busy 守卫未落地（D1 细化）

D1 原设计守卫 `if self._busy: return` 针对「单双态钮」时代的停止使能
保护；D3 双常驻钮落地后，停止钮使能只由 `_set_busy` 管理（`_refresh_`
零触碰），而发送/插话钮在 busy 期间**必须**随文本重算使能（插话语义：
文本非空即可点）——守卫反而阻断 D3。治本目标（停止恒可用）由「停止钮
使能单一来源 = _set_busy」达成，`_busy` 簿记保留为 busy 路由/守卫的
单一真值。竞态窗口根因（worker 存在性代理）已随双钮分离彻底消除。

## 偏差 2：旧轨排队句柄 = 不透明令牌 + 操作期现算定位（T3 实证翻案）

旧轨（QTextBrowser）先后尝试 int position 三元组与 QTextCursor 三元组
