# 变更面板 Git 状态刷新实时化落地计划

> **状态**：已实施（真机验证用户已确认）
> **范围**：Git 状态刷新链路（`src/gui/controllers.py` `GitStatusController`）、聊天面板工具活动路由（`src/gui/panels/chat/panel.py`、``tabs.py``）、主窗口接线（`src/gui/main_window.py`）
> **时间**：2026-10-22 16:27（设计，UTC+8）/ 2026-10-22 16:40（实施）
> **优先级**：高

## 需求

1. AI 改一个文件，变更面板（连同文件树着色 / 查看器徽标 / 状态栏统计）应在该次改动落盘后**即时**反映，不再等到整轮任务结束才一次性涌出。
2. 主 agent 直接编辑与子 agent（task 工具）内部编辑一视同仁——用户实测两条路径都只在轮次结束时更新。
3. 刷新链路保持廉价：连续多次落盘合并刷新，不得因高频触发演变成 `git status` 子进程风暴。

## 根因探查结论（已核实）

刷新汇流点在 `src/gui/controllers.py` `GitStatusController`：全部事件源经 300ms 去抖（`REFRESH_DEBOUNCE_MS`）汇成一次 `refresh()`，扇出四面（文件树着色 / 查看器徽标 / 变更面板 / 状态栏统计）。现有事件源五处：

| # | 事件源 | 覆盖什么 | 漏什么 |
|---|---|---|---|
| 1 | 窗口激活（`schedule_refresh`） | 外部编辑器、终端 checkout 等离开后回窗 | 窗口前台期间的任何改动 |
| 2 | 查看器外部重载（去抖） | 当前打开文件被外部改写 | 未打开的文件 |
| 3 | 视图菜单手动刷新 | 用户显式触发 | — |
| 4 | **AI 轮次结束**（`turn_finished` → `schedule_refresh`，`main_window.py:370`） | 一切 AI 改动（兜底） | **轮次进行期间完全无刷新——本次症状的的直接原因** |
| 5 | 文件树模型结构信号（`rowsInserted`/`rowsRemoved`/`fileRenamed`/`directoryLoaded` → 去抖，`controllers.py:92-98`） | 已加载目录下的新建 / 删除 / 重命名 | **既有文件内容覆写（edit/write 的绝对主流形态）不产生任何结构信号**；未展开目录不在监视范围，其下新建同样漏报 |

关键机制事实：`QFileSystemModel` 经 `QFileSystemWatcher` 只监视**目录项增减**，文件内容修改不触发 `directoryChanged`（内容级 `fileChanged` 仅对单独 addPath 的文件生效，模型只对目录 addPath）。因此 AI 覆写既有文件时事件源 5 静默，只剩事件源 4 在轮次结束时兜底——与用户观察到的「任务结束才一次性显示全部变更」完全吻合；子 agent 同理（其落盘路径相同，且文件树往往未展开到目标目录，连新建都可能漏）。

## 已具备的精确数据源（本次修复的抓手）

所有 `tool_call` / `tool_call_update` 帧——**含子 agent 嵌套帧**（带 `parent_tool_call_id`，簿记键为 `父/子` 全串）——都汇流 `ChatPanel._on_activity_chunk`（`src/gui/panels/chat/panel.py:1079`）。载荷已带归一化 `tool_kind`：协议层（`src/llm/providers/acp.py`）将 write/edit/patch 归为 `"edit"`，且对 kind 缺失/敷衍上报 `"other"` 的后端有按工具名的兜底推导账本（`_derived_tool_kinds`，update 帧回填）。即 GUI 侧无需猜测，读 `payload["tool_kind"]` 即可精确识别「这次工具调用改了文件」。

## 方案决策

**新增第六事件源：AI 编辑活动提示**。在工具活动路由处识别改盘类工具调用的终态帧，发信号 → 走既有 300ms 去抖 → `refresh()`。

- **为什么不用递归 `QFileSystemWatcher` 全量监视工作区**（备选方案 B，否决）：Linux inotify 每进程监视数有上限（默认 8 万级实例上限、单 watch 亦有成本），`node_modules`/`.venv`/`.git` 等大目录需豁免逻辑（与噪音过滤偏好耦合）；`.git` 自身 churn 会制造大量无效触发；新增一套与文件树模型并行的监视体系，重量且易踩坑。现有事件源 1/2/5 已兜底外部改动，本计划只补「AI 前台改盘」这一精确缺口。
- **终态帧触发而非首帧触发**：`tool_call` 首帧到达时写盘尚未发生，刷新只会读到旧状态；`tool_call_update` 的 `completed`/`failed` 终态帧到达时改动已落盘（failed 亦可能部分落盘，如 multi-edit 中断，刷一次无妨）。`in_progress` 帧不触发。
- **`tool_kind` 取 `edit` 与 `execute` 两类**：edit 覆盖写/改文件；execute 覆盖 `sed -i`、重定向、代码生成器、`git checkout` 等命令行改盘（误报成本 = 300ms 去抖后一次 `git status`，可接受；漏报则回到本症状）。read/search/fetch/think/todo 不触发。
- **去抖沿用既有 `QTimer` 不新设**：连续 N 次落盘天然合并为一次刷新；信号语义是「可能改了」，汇流点判重。
- **保留轮次结束兜底**（事件源 4 不动）：终端面板内用户手敲命令改文件等无工具帧路径仍有最后一道网。

### 不做项（已知取舍，留档）

- 终端面板内用户手动执行命令造成的**内容级**改动，前台期间仍不实时（窗口激活兜底）；如需覆盖须另立计划评估 shell 集成（OSC 133 命令边界探测），本计划不碰。
- 递归文件系统监视（上述方案 B）不实施。

  def _is_fs_mutation_terminal(payload: dict) -> bool:
      """tool_call_update 终态帧且 kind 为改盘类（edit/execute）→ 应提示刷新 Git。"""
