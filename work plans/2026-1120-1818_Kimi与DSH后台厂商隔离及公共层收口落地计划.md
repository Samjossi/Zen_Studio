## 1. 背景与问题定性

当前三个 ACP 后台都复用 `src/ide/llm/providers/acp.py`。该文件最初只抽象连接层，后来逐步收进工具卡字段提取、工具名推导、状态归一、提问识别、图片识别、回执过滤和跨帧账本，已经从「稳定 ACP 传输设施」变成「多厂商语义汇集层」。

这带来两类实际问题：

1. **共享的是当前相似性，不是变化轴稳定性**：Kimi 的 camelCase、显式 kind、wire 旁路，与 DSH 的 snake_case、`kind="other"`、会话日志和配置错误语义都进入同一实现。修一家时需要逐项证明另一家不受影响。
2. **依赖方向存在破口**：公共权限策略从 Kimi 具体 provider 借类型，GUI 直接判断 `kimi-acp`，GUI 卡片工厂同时认识 Kimi 与 DSH 的私有工具名。即使把文件物理搬走，这些方向不改，波及面仍不可预期。

本次不是追求「代码只出现一次」，而是追求「一种厂商变化只修改该厂商的后台与卡片目录」。后台数据载荷、具体卡片格式、卡片分派和卡片更新逻辑均按厂商隔离，允许受控重复；禁止为了消重再次抽出厂商流程基类、统一卡片类型体系或大而全的钩子层。

## 2. 既有决策的关系

### 2.1 保留的有效决策

`2026-0730-0150_CLI后台抽象层与Reasonix接入计划.md` 中以下判断继续有效：

- `LanguageModel` 是稳定业务接口，不新建厂商流程基类。
- 注册表是装配单点，模型目录和模型别名按接口隔离。
- ACP 帧收发、请求 ID 配对、反向请求分发、进程失效收口可以共享。
- 认证错误、模型切换、会话建立等语义由各 provider 自持。

### 2.2 本次替代的演进口径

`2026-1119-0952_DSH卡片完备度审计选型.md` 推荐把 snake_case/camelCase 和工具名别名继续收进公共归一化层，并否决 DSH 专属适配器。该建议针对当时「快速补齐卡片」有效，但继续执行会扩大本次要拆除的共享易变层。

本计划批准后：

- **替代**该文档第二阶段「公共别名层继续扩张」的演进口径；尚未实施的部分不再按原路线落地。
- **不回退**已实施的 DSH 图片卡、snake_case 入参提取等修复；它们随行为基线迁入 DSH 目录。
- 不再把 DSH 帧伪装成 Kimi 帧。两家只共用稳定的流式事件信封和 Qt 基础组件，各自拥有数据载荷、具体卡片、卡片工厂与更新逻辑；DSH 不必为了进入 Kimi 卡片而合成同形数据。
- 「卡片观感暂时相同」不构成继续共用具体卡片实现的理由。迁移时可为零回归先复制现状，之后各家独立演化，原始后端帧才是各自数据的唯一真相源。
- 原选型文档作为历史决策保留，不篡改；在实施记录和 `src/ide/llm/README.md` 中说明现行边界。

## 4. 目标、非目标与验收总纲

### 4.1 目标

1. Kimi、DSH 的协议差异、处理流程、异常语义、工具字段、落盘格式和卡片数据分别位于自己的后台目录。
2. Kimi、DSH 的具体卡片格式、卡片类、工厂、工具名分派与更新逻辑分别位于自己的 GUI 厂商目录。
3. 公共 ACP 层不含厂商名、厂商工具名、私有配置键、私有日志路径或厂商错误关键词。
4. 通用 GUI 不导入具体 provider，不识别厂商工具名，不以接口 ID 特判厂商流程；厂商工具名只能出现在该厂商自己的后台或卡片目录。
5. 厂商后台与厂商卡片包均不得跨厂商导入，provider 不得反向导入 registry 或 GUI；后台与卡片各只有一个组合根负责装配具体实现。
6. 迁移前后已有 Kimi、DSH、Local 行为等价；存档帧载荷、卡片类型、卡片内容、异常类型和用户可见错误保持一致。
7. 每一阶段均可独立运行、测试和回退，不做不可定位的大爆炸重写。

### 4.2 非目标

- 不修改 `参考代码/`、DSH 上游、Kimi CLI 或 Local CLI。
- 不顺手实现尚未落地的 DSH edit 合成 diff、`ask_user_question` 交互激活等新功能。
- 不统一 Kimi 与 DSH 的会话恢复、轮次收尾、错误文案、模型目录、用量采集流程或具体卡片格式。
- 不借拆分重新设计卡片外观；迁移初期可以复制现有具体卡片以保证等价，但复制后归各厂商独立维护。
- 不复制折叠、复制按钮、颜色、图片显示、文本截断等无厂商语义的 Qt 技术基础件。
- 不更换持久化键、默认后台、模型别名或用户配置。
- 不引入新的架构检查依赖；依赖守卫使用现有 pytest 与 Python 标准库 AST。

### 5.3 允许与禁止的依赖

允许：

- 通用 GUI → `ide.llm` 稳定契约 / 后台 registry / 卡片组合根。
- 后台 registry → 各厂商后台包 → 稳定 ACP 包 / `llm.base`。
- 卡片组合根 → 各厂商 GUI 卡片包。
- 厂商 GUI 卡片包 → 本厂商 `models.py` 中的纯数据类型；不得导入 provider 运行时或连接对象。
- 厂商后台包内部、厂商 GUI 包内部分别自由依赖本厂商模块。
- 厂商 mapper → 无厂商语义的 ACP 纯函数；厂商卡片 → 无厂商语义的 UI 基础件。

禁止：

- `llm.permission_policy` → 任一具体 provider。
- 公共 ACP 包 → Kimi / DSH / Local。
- Kimi ↔ DSH ↔ Local 的后台或 GUI 任意横向导入。
- provider / 公共 ACP 包 → registry 或 GUI。
- 通用面板、公共 UI 基础件 → 具体 provider、私有 update mapper、具体厂商卡片或工具名表。
- 以「类型安全」为由让通用面板 import 厂商 models；只有对应的厂商 GUI 包可以这样做。
- 新建 `BaseKimiDshProvider`、`CommonVendorSession`、以某张具体卡片供多家继承的基类，或包含大量厂商 hook 的会话/卡片基类；无格式语义的 `ToolCard` 生命周期接口不在此禁例。

后台组合根是 `src/ide/llm/registry.py`，卡片组合根是 `src/ide/gui/panels/chat/vendors/registry.py`；二者分别装配，不让 LLM registry 反向 import GUI。

### 5.4 厂商专属载荷与最小路由契约

`Chunk` 只保留稳定流式事件信封。工具活动路由最多识别事件类型、调用 ID、父调用 ID等生命周期元数据；其余 `payload` 对通用面板是不透明数据。

- 现 `llm.base.ToolCallPayload`、`ToolUpdatePayload`、`TodoEntry`、`TodoPayload` 中的卡片字段不再作为公共契约，迁入各厂商 `models.py`。
- 每家 mapper 生成自己的首帧和更新帧载荷；每家卡片工厂直接理解自己的工具名、字段和格式。
- 每家 presenter 决定迟到帧如何补卡、哪些字段覆盖、何时清理账本，以及子代理如何嵌套。
- 通用面板只按调用 ID 找到卡片并转交事件；不得继续读取 `command`、`summary`、`diff_hunks`、`questions` 等具体字段做厂商判断。
- 不设置统一 `card_kind`，不保留公共 `make_tool_card()`，不通过中性类型表把各家重新压回同一套卡片。
- 原始 `title`、原始参数和各厂商真实结果仍如实保留；卡片如何表达这些事实由各厂商包决定。

### 5.5 权限与轮后能力契约

权限入口改为「原始参数 + 中性分类」的 `PermissionRequest`：

- ACP 连接仍只负责及时收发，不认识提问工具名。
- 各厂商把自己的原始 `PermissionParams` 分类为 `permission` 或 `question`，再交给统一权限策略和 GUI。
- 权限四态、危险命令黑名单和 optionId 原样回传继续共享；它们是产品安全策略，不是厂商卡片格式。
- GUI 权限队列只提供稳定宿主服务；提问卡的内容、布局和交互由对应厂商卡片包实现，原始参数不丢失。

轮后用量宽限改为 provider 可选能力，例如 `post_turn_usage_grace_s()`：Kimi 根据恢复状态返回现行宽限值，DSH / Local 默认返回 0。`ChatPanel` 不再判断 `kimi-acp`，也不直接读取 Kimi 恢复字段。

### 5.6 共享内容的最终判据

只有满足以下任一条件的代码才能留在公共层：

- 由 ACP / JSON-RPC 标准定义，且不包含某家私有扩展；
- 是 Zen Studio 自己稳定的技术契约，如流式事件信封、权限四态、`ToolCard` 生命周期接口；
- 是无厂商词表、卡片格式和流程假设的纯技术设施，如截断、ANSI 清理、标准 diff 计算、折叠与复制组件。

「两家现在都有同名字段」「卡片现在长得一样」「复制后行数较多」「未来可能统一」都不是共享理由。

## 6. 实施步骤

### T0 行为基线与迁移清单

1. 在任何移动前运行 `bash scripts/check.sh`，记录真实基线与既有警告；若基线红，先区分本次前已有失败，不以重构掩盖。
2. 用现有存档和内存假 ACP 连接固化 Kimi、DSH、Local 的迁移前行为：
   - Kimi：正文、思维链、显式 kind、edit/write diff、ReadMediaFile、TodoList、AskUserQuestion、Agent sidecar、usage、stopReason、恢复。
   - DSH：正文、usage、bash/read/write、`read_image`、snake_case 入参、todo_write、subagent、配置错误和 stopReason。
   - Local：可控假 agent 的正文、usage、模型/配置错误、取消和关闭。

6. Local 依据自身可控假 agent 和协议资料形成独立 mapper 与 models；即使当前输出与 Kimi 相似，也不得 import Kimi mapper 或载荷类型。

**检查点**：同一存档逐帧对比通过；新增「两家同 toolCallId、同 sessionId 也无串扰」测试；两家显式修改各自 mapper 的测试不会触及对方文件。

### T3 厂商专属卡片、工厂与 presenter 拆分

1. 建立 `card_base.py` 和 `vendors/registry.py`，抽出且不改变折叠、复制、颜色、图片显示和 `ToolCard` 生命周期等稳定技术能力。
2. 为 Kimi、DSH、Local 分别建立 `factory.py`、`cards.py`、`presenter.py`。将现有具体卡片按当前后台实际使用路径等价复制到各厂商包；本步不重新设计外观。
3. Kimi 工厂承接 `AskUserQuestion`、`Agent/Task`、`ReadMediaFile`、`TodoList` 等 Kimi 工具名分派；DSH 工厂承接 `read_image`、`todo_write`、`subagent` 等 DSH 工具名分派。未知工具分别落入本厂商通用卡，不设公共兜底格式。
4. 将 `_TOOL_NAME_CARDS`、`_normalize_tool_name` 和公共 `make_tool_card()` 随迁移删除，不引入统一 `card_kind` 替代它们。
5. 按 T0 清单把 `panel.py` 中的标题/命令账本、迟到字段判断、diff/summary/questions 等载荷读取和卡片更新分支移入各厂商 presenter。通用面板只保留调用 ID 定位、卡片插入/结束、展开状态和信号封送。
6. 后台切换时经后台 registry 的 `vendor` 选择对应卡片工厂；LLM registry 不 import GUI，通用面板不 import 任何具体厂商卡片包。
7. 审计会话持久化或历史回放是否直接保存旧工具载荷。需要兼容时，由各厂商 presenter 读取自己的旧载荷；禁止恢复一个同时认识所有厂商工具名的公共兼容工厂。
8. 用 `post_turn_usage_grace_s()` 替代 `_llm_name == "kimi-acp"`，保留现行 Kimi 恢复中和正常态行为，DSH / Local 不新增宽限。

**检查点**：Kimi Agent/AskUserQuestion/ReadMediaFile/TodoList 与 DSH read_image/todo_write/subagent 均保持原卡片内容和观感；通用面板与 `card_base.py` 无厂商工具名、载荷格式或后台 ID 流程分支。
