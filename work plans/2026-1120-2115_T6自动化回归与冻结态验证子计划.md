## 1. 背景与目标

## 6. 实施结果回写（2026-11-21 00:07 UTC+8）

T6 全部完成，修改记录见 `文档/修改记录/2026-1121-0007_T6自动化回归与冻结态验证实施记录.md`。以下为实施过程中相对原计划的偏差与经验。

**与计划的偏差**：

1. **新增启动注册表日志**：为让冻结态冒烟能直接确认三家后台，`main.py` 启动首行后打印 `已注册后台：kimi-acp（kimi）、dsh-acp（dsh）、local-acp（local）`。只读 `ide.llm.REGISTRY`，无流程分支、无实例化时机变化。
2. **新增 3 个生命周期参数化用例**：计划只说「使用现有内存假 agent」跑三家全链路；既有用例分别覆盖正文/用量/取消，但没有把工具帧串到 provider 轮次。补在 `tests/test_vendor_provider_lifecycle.py`，覆盖会话建立、工具帧、正文、自然停止、close 幂等与第二个实例的账本隔离。
3. **修正 `scripts/shot_tool_cards.py` 的旧 `QuestionDialog` 契约**：T4 后对话框接收 `PermissionRequest`，脚本仍传裸 dict，重跑时在最后一屏抛 `AttributeError`。改为走 Kimi `build_permission_request`，这是本次发现的真实旧入口残留。
4. **新增 `scripts/shot_vendor_cards.py`**：原脚本只覆盖 Kimi，无法证明 DSH/Local 独立工厂；新脚本显式装配三家 mapper/presenter/工厂，出 11 张代表卡并逐张断言卡片类来自目标厂商包。`scripts/README.md` 同步补两条脚本说明。
5. **未修 40/41 的历史 reasonix 副标题差异**：这两个 `task` 帧是已移除 reasonix 后台的历史形态，`kind="other"`；Kimi T2 已定为显式 kind 信任、不按工具名兜底，因此不再派生 `think`，父卡副标题/`is_subagent` 缺失。当前 Kimi Agent 走 `kind="think"`，由 T0 基线与新脚本覆盖；不为旧后台恢复厂商工具名兜底。
6. **真基线用重构前代码重出，而不是 8 月旧截图**：8 月截图早于多个场景定型（如 23 号卡片），直接比对会误报。用 `git archive 7ea4d3c^` 抽到 `.temp/t6/pre_refactor/` 后在同环境重跑同一截图脚本，作为 T0 前基线；截图保留在 `.temp/t6/pre_refactor_card_shots/`，36 张同名场景中 30 张完全一致。
7. **AppImage 未走 FUSE 直跑**：本机无 `fusermount`，直接挂载不可用；用 `--appimage-extract` 解到 `.temp/` 后跑 `AppRun`，验证同一份 squashfs 内容，同时避免向系统临时目录写挂载点。
8. **清理截图脚本的文档归档副本**：`shot_tool_cards.py` 既有行为会在 `文档/帧存档/` 生成 6 张带时间戳副本；按 T6「截图只放 `.temp/`」清理本次生成件，未改脚本归档逻辑。

**经验沉淀**：

1. **视觉脚本也是契约消费方**：厂商 API 改了而截图脚本没改，会在最后一次运行才炸；T6 把 `QuestionDialog` 的旧 dict 调用抓出来，说明「脚本能跑」要纳入每轮厂商拆分门禁，不能只看 pytest。
2. **基线必须同环境、同场景版本重出**：历史 PNG 的时间戳不等于语义版本，8 月截图会混入场景未定型的差异；用重构前 commit 在同机重跑，才能把「重构导致的差异」和「夹具路径/场景演化」分开。
3. **冻结态要可观测，不靠推断**：启动日志直接打印注册表清单，比「启动成功所以三后台肯定注册了」更硬；再用 `pyi-archive_viewer` 证明模块确实入包，两层证据互补。
4. **同一 toolCallId 的跨实例账本要单独造第二个实例**：只测单实例 close 清理，无法证明账本没有跨实例串联；第二个实例重新产出 `input_detail` 才是隔离的反证。
5. **历史厂商帧会误导视觉结论**：reasonix `task` 帧与 Kimi `Agent` 帧共享卡片类但 kind 语义不同；保留历史场景时应标注「历史帧，不承诺当前厂商语义」，避免把 T2 的有意去兜底当成回归修复。
