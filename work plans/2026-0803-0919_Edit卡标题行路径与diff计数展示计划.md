# Edit 卡标题行路径与 diff 计数展示计划

## 1. 背景

用户实机对照两张截图：

- **本程序现状**：Edit 卡标题行只有「chevron + 📝 + Edit + ✔」，
  文件路径、目录、增删计数全缺——用户「根本不知道它编辑了什么」；
- **对标样式**（kilocode 系）：`📝 编辑 · cards.py · gui/panels/chat/ +11 −1`，
  即「图标 + 工具名 + 文件名 + 目录（灰）+ 增删计数（红绿）」五段。

用户需求明确：**不需要看到具体编辑内容，只要标题行带大概信息**
（哪个文件、在哪个目录、增删多少行），不展开也能知道动了什么。

本计划与 0741 计划同方法论：**offscreen 截图 + MOCK 真实帧序列 +
多模态视觉核验 + 冒烟像素/断言回归，形成闭环**，不靠读代码臆断。

## 2. 现状链路（代码实证，2026-08-03 09:19 核对行号）

Edit 卡（`tool_kind == "edit"` → `DiffCard`）标题行信息的三条数据通路：

### 2.1 路径摘要通路（现有，疑似断在上游）

- 协议层 `llm/providers/acp.py` `_tool_call_summary`（415-441 行）：
  edit/read 分支取 `locations[0].path` → 兜底 `rawInput.path / rawInput.filePath`，
  截断单行后填入 `ToolCallPayload.summary`；
- 渲染层 `gui/panels/chat/cards.py` `ToolCard.__init__`（385-398 行）：
  `payload.get("summary") or ""` 直接进标题行副标题（`_subtitle_label`）；
- **现状为空**说明：实机后端（kimi acp）的 `tool_call` 帧里
  `locations` 与 `rawInput.path/filePath` 均未提供路径——
  或路径藏在别处（title 尾部、rawInput 其他键、update 帧），
  **具体位置须 T1 帧取证确认，不臆断**。

### 2.2 diff 计数通路（首帧已有，update 帧缺失）

- 协议层 `_map_tool_call`（469-475 行）：edit 时
  `_extract_diff(update.get("content"))` → `diff_stat`（`+N −M`）、
  `diff_hunks`、`diff_truncated` 三键入 `ToolCallPayload`；
- `_extract_diff`（247-305 行）：content diff 项（`oldText`/`newText`）
  经 difflib unified_diff（n=3）生成 hunk，软上限 1000 行保头截断，
  **无 diff 项返回 None（非必填不臆造，0645 D4 纪律）**；
- **断点**：`_map_tool_call_update`（484-553 行）**全程不碰 diff**——
  completed 帧的 `content` 只走 `_extract_tool_output` 进 `output` 键；
  `ToolUpdatePayload`（`llm/base.py` 95-113 行）**没有
  diff_stat/diff_hunks/diff_truncated 三字段**。后端若在 completed
  update 帧才发 diff content（ACP 协议允许），现有链路直接丢弃。
- 渲染层 `DiffCard._build_body`（529-566 行）：徽标（红绿 `+N −M`）
  与 hunk 三色 body **只在构造时挂一次**；`DiffCard` 未覆写
  `_on_completed`——即使 update 帧带了 diff 也无处安放。

### 2.3 update 帧副标题刷新通路（不存在）

- `ToolCard.apply_update`（430-444 行）：只刷 `title` 与状态图标
  （◐→✔/✖），**不刷 `summary`**；
- `ToolUpdatePayload` 亦无 `summary` 字段。路径若在 update 帧
  才到达（locations 可挂在 update 帧），当前链路同样丢弃。

### 2.4 兜底文本通路（顺带不齐）

- `_tool_call_fallback`（361-369 行）已附 `diff_stat` 计数随行；
- `_tool_update_fallback`（372-381 行）无计数——旧轨降级显示时
  completed 行也不带 `+N −M`。

## 3. 根因小结

标题行空白 = 三条通路各断一节，具体哪节断在后端真实帧里，
须 T1 取证定位。已确认的**协议层固有缺口**（与后端无关）：

1. update 帧不提取 diff content（§2.2）；
2. update 帧不携带/不刷新 summary（§2.3）。

即使后端在首帧就给了全部信息，这两条缺口也会在「diff/路径
迟到」场景下复现空白，故无论 T1 结论如何都要补。

## 4. 任务分解

### T1 帧取证探针（先诊断，不改产品代码）

写 `.temp/probe_edit_frames.py`（范式沿用 `.temp/probe_kilo_acp.py`、
`.temp/probe_thinking_empty.py`）：直连实机后端 ACP 子进程，
发起一次必然触发 edit 的会话，**原样 dump** 全部
`session/update` 帧的 `update` dict（tool_call 与 tool_call_update
全帧 JSON），回答三个问题：

1. 路径在哪：`locations[0].path` / `rawInput.path` / `rawInput.filePath`
   / title 内嵌 / update 帧才到 / 完全没有？
2. diff content 在哪帧：tool_call 首帧 / completed update 帧 / 两帧都有？
3. update 帧带不带 `kind`（影响 §2.2 补提取时的分支条件）？

产出：取证结论与关键帧样例**回填本计划 §6**（替换为实证小节），
T2 的具体补源顺序按结论定稿。若结论为「后端完全不给路径」，
则本计划降级为只做 diff 计数 + title 内嵌信息提取，并在计划里
记为后端能力边界（同 0117 计划 F 系封存款范式），不臆造路径。

### T2 协议层补数据通路（`llm/base.py` + `llm/providers/acp.py`）

1. **`ToolUpdatePayload` 增三键**（`llm/base.py` 95-113 行后追加，
   注释与 `ToolCallPayload` 83-89 行同源口径）：
   `diff_stat: str`、`diff_hunks: list[dict]`、`diff_truncated: bool`；
   同时增 `summary: str` 键（路径迟到场景的副标题迟到刷新，§2.3）。
2. **`_map_tool_call_update` 补 diff 提取**（484-553 行）：
   completed/failed 帧按 T1 结论的 kind 判定（`kind == "edit"` 优先；
   kind 缺省但 content 含 diff 项时同样尝试——`_extract_diff` 本身
   对非 diff 项返回 None，天然安全），命中即填
   `diff_stat/diff_hunks/diff_truncated`。
3. **`_map_tool_call_update` 补 summary 迟到提取**：update 帧
   `locations`/`rawInput` 可解析出路径时复用 `_tool_call_summary`
   填 `payload["summary"]`。
4. **`_tool_call_summary` edit 分支补源**（429-434 行）：按 T1 结论
   在现有两级（locations → rawInput.path/filePath）后追加第三级兜底
   （候选：title 内嵌路径 token 提取——仅当 title 含 `/` 或已知扩展名
   时保守提取，提取失败返回 None，不阻断上屏）。
5. **`_tool_update_fallback` 附计数**（372-381 行）：completed 行尾
   附 `diff_stat`（对齐 `_tool_call_fallback` 367-368 行既有格式）。

纪律：协议层单点格式化不变，GUI 不碰 rawInput；diff 非必填不臆造；
软上限 1000 行保头沿用 `_extract_diff` 既有实现，零新增截断逻辑。

### T3 渲染层两段式路径 + 徽标后补（`gui/panels/chat/cards.py`）

1. **副标题两段式**（DiffCard 专属，不动其他卡）：构造与刷新时把
   `summary` 路径拆为「文件名（正常色）· 目录（弱化灰）」两段富文本
   渲染，对齐对标样式 `cards.py · gui/panels/chat/`。
   拆分用 `os.path`/`PurePath`，仅取 basename 与 dirname 展示，
   **不改 summary 载荷本身**（协议层仍给完整路径单行，拆分纯属视觉，
   放渲染层；复制/簿记语义不受影响）。
2. **`ToolCard.apply_update` 补副标题刷新**（430-444 行）：
   `if summary := payload.get("summary"): self.set_subtitle(...)`——
   对全部卡种无害（其余卡 update 帧本无 summary 键）。
   两段式拆分逻辑收敛在 DiffCard 覆写 `set_subtitle` 或私有
   `_format_subtitle`，基类保持纯文本行为不变。
3. **`DiffCard` 覆写 `_on_completed`**：payload 带
   `diff_stat/diff_hunks` 时补挂徽标与 hunk body。实现上把现
   `_build_body`（529-566 行）的徽标+hunks 段抽为 `_render_diff(payload)`，
   `_build_body` 与 `_on_completed` 共用；补挂前去重（已挂过徽标
   则跳过，防双帧各发一次 diff 时重复挂两块 body）。
4. 徽标插入位置沿用既有约定（标题行状态图标前，
   `_header_layout.indexOf(self._status_label)`）。

### T4 验证闭环（沿用 0741 方法论）

1. **MOCK 帧序列复现**：`.temp/` 脚本构造三帧——

2. **冒烟补断言**（`.temp/smoke_chat_cards.py`）：edit 卡副标题

3. **协议层断言补/复跑**：`.temp/test_map_session_update.py` 与

## 5. 风险与取舍

- **R1 后端能力边界**：若 T1 证实后端完全不给路径，文件名段只能
  缺省——计划内记为封存款，不做正则瞎猜（R1 纪律：泛化层不臆造
  协议）。diff 计数同理。
- **R2 title 解析脆弱性**：T2-4 的 title 内嵌路径提取是兜底中的
  兜底，仅保守模式（含路径分隔符/已知扩展名），宁缺毋滥。
- **R3 双帧重复 diff**：首帧与 completed 帧都发 diff 时 T3-3 的
  去重保证只挂一份；计数徽标以先到者为准（后帧同值刷新无害）。
- **R4 其他卡种零影响**：`apply_update` 的副标题刷新对无 summary
  键的卡是 no-op；两段式拆分收敛在 DiffCard 内，Bash/TextOutput/
  Subagent/Mcp 卡行为不变。

## 6. 验收标准

- 实机 edit 调用后，**不展开卡片**即可见：文件名、所在目录、
  `+N −M` 红绿计数（后端实际提供对应数据的前提下）；
- 修前/修后 offscreen 截图成对存档 `.temp/`，多模态核验通过；
- 冒烟 + 协议层断言新增用例全过，既有断言零回归；
- 后端不给数据的降级形态：退回现状（图标 + Edit + 状态），
  不显示任何臆造信息。
