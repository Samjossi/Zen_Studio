## 1. 背景与目标

本项只改变后台文件位置、ACP 连接启动参数装配位置和 import 路径，让目标目录先可运行。厂商 update 仍暂时共用旧实现，以把「路径与进程启动回归」和「厂商语义拆分回归」分开定位。

目标结构以主计划 §5.1 为准：公共 `acp/` 包承接连接、协议、prompt 等稳定设施，`kimi/`、`dsh/`、`local/` 承接各自 provider 与私有会话流程。

## 2. 启动条件与边界

- 主计划 T0 已勾选，且用户明确批准 T1 后才能开始；本项批准不包含 T2。
- 使用 T0 的行为基线和 import 清单，不另起一套迁移口径。
- 本项暂留 `acp/updates.py` 公共实现，provider 继续走旧映射；不得提前进行 T2 的厂商 mapper 与 models 分离。
- Kimi wire 若单步拆分扩大风险，可暂留 `kimi/provider.py`，在本文档记录偏差，后续独立小步迁移。
- 不修改 CLI 上游，不改变会话恢复、错误、模型目录、用量或用户配置语义。

## 3. 实施步骤

### T1.1 拆出稳定 ACP 包并保持旧映射可运行

1. 将 `src/ide/llm/providers/acp.py` 拆为 `src/ide/llm/providers/acp/` 包，按主计划划分 connection、protocol、prompt 等模块。
2. 保持连接、协议、prompt 和现有 update 行为可运行；本项允许 `acp/updates.py` 暂存旧公共映射。
3. 将连接构造参数改为接收完整 argv 或启动命令，具体 `[binary, "acp"]` 由各厂商 provider 组装。
4. 保持 NDJSON/JSON-RPC、initialize/session/new 参数、反向请求和子进程生命周期与基线一致。

### T1.2 机械迁移厂商后台与消费方

1. 按主计划 §5.1 移动 Kimi、DSH、Local 文件，建立各厂商 `__init__.py`，只导出本厂商公开入口。
2. 依据 T0 清单更新生产、测试和脚本 import，不保留会掩盖错误 import 的长期双入口 shim。
3. 保留 `src/ide/llm/registry.py` 作为后台组合根；不得让 provider 或公共 ACP 包反向导入 registry/GUI。
4. 删除已无人使用的旧平铺模块，并通过全库搜索确认现行代码没有旧路径残留。

### T1.3 同步现行说明并验证等价

1. 更新模块 docstring 和 `src/ide/llm/README.md` 的现行路径，清除「每家厂商一个文件」等旧描述。
2. 对照 T0 基线验证连接 argv、会话参数、正文/工具帧、异常和生命周期。
3. 运行定向测试与 `bash scripts/check.sh`；若出现失败，先判断是移动/import 问题还是既有基线问题，不顺手进入 T2 修语义。

## 5. 风险与注意点

- 包与旧模块同名时容易出现导入遮蔽，删除旧入口后必须实际运行消费方，而非只做静态编译。

- 若 wire 延后拆分，必须作为明确偏差记录，不得把目标路径写成已完成。
