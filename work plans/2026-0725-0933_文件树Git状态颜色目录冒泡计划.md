# 文件树 Git 状态颜色目录冒泡计划

> **需求一句话**：文件树中，新增文件（绿）/ 修改文件（蓝）的 Git 状态色目前只落在文件本身；若变更文件藏在（任意深度的）文件夹里，其各级祖先文件夹也要着色，让状态「冒泡」到可见层级。

## 1. 背景与目标

当前文件树的 Git 着色是**单文件粒度**：目录节点被代码主动跳过，深嵌套的变更文件折叠后完全不可见——用户必须逐层展开才能发现「这里面有东西变了」。VS Code 等 IDE 的通行做法是状态色沿目录向上聚合：目录取其子树内**优先级最高**的状态色。

目标：

1. 目录节点按子树内文件状态聚合着色（任意深度，含多层嵌套）。
2. 状态优先级归并：**冲突 > 修改 > 新增 > 删除 > 忽略**，目录显示归并后最高优先级对应的颜色。
3. 文件节点的现有行为**零变化**（颜色、刷新时机均不动）。
4. 查询开销稳定：目录着色查询为 O(1) 字典查找，不做逐次前缀扫描。

### 2.1 参考实现调研对比（修订一新增）

对三个参考项目做了只读调研，统一对比「目录冒泡」维度的实现取舍：

| 维度 | theia-zen（Eclipse Theia fork） | Multi_Cli_Studio（Tauri + React） | VS_Code_Python（实为 py-gpt，PySide6） |
|:---|:---|:---|:---|
| 目录冒泡 | ✅ 已实现（主链路） | ❌ 未实现（仅单文件精确匹配） | ❌ 无 Git 着色功能（仅有 LLM 索引状态文本列） |
| 数据获取 | 内置 VS Code git 扩展 spawn `git status` | Rust 侧 `Command` 调 `git status --porcelain` | 无 |
| 冒泡算法 | 预聚合平铺表 `parentDecorations`：对每个变更文件沿 `uri.parent` 上溯写表，**遇同级/更高权重已占位即 `break` 剪枝**；渲染时每节点两次 O(1) Map 查找 | 无（目录 key 不存在于状态 Map，恒无色） | 无 |
| 冒泡开关 | `propagate` 由数据源声明：**deleted 不冒泡**（文件已删，冒泡会误导「目录里有东西要处理」） | — | — |
| 状态归并 | 权重比较（weight 大者优先），同权重先到先得 | 隐式：staged+unstaged 串联进 Map，**unstaged 覆盖 staged** | — |
| 颜色定义 | colorId → CSS 变量（数据与主题解耦） | CSS 修饰类：added `#89d185` 绿 / modified `#6bb3f0` 蓝 / **deleted `#ff6b6b` 红 + 删除线** / renamed `#c9a3f5` 紫 | 无（状态走 DisplayRole 文本列） |
| 刷新 | Emitter 事件链 + 150ms 渲染 debounce + RPC 批量合并 | 事件触发全量重跑 `git status`（聊天流结束 / git 操作后），`useMemo` 缓存 Map | `_status_cache` + 信号驱动失效；`setRootPath("")` 暴力重置技巧 |
| 出处 | `packages/filesystem/src/browser/file-tree/file-tree-decorator-adapter.ts:34-150` | `src/components/chat/WorkspaceRightPanel.tsx:544-565,1788-1830`；`src-tauri/src/main.rs:17289-17326`；`src/styles/workspace-right-panel.css:1350-1372` | `src/pygpt_net/ui/widget/filesystem/explorer.py:1623-1764` |

**可借鉴点（采纳进本计划）**：

1. **theia-zen：deleted 不冒泡** → 采纳，修订 §3.2 优先级表（对齐 VS Code 语义：删除的文件树上可能已不可见，冒泡到目录反而误导）。
2. **theia-zen：上溯剪枝** → 采纳，修订 §3.3 T1（目录已有同级/更高优先级状态时 `break`，同目录兄弟文件只冒一次，一行成本换取 O(N×深度) 收敛）。
3. **theia-zen：冒泡态视觉区分**（目录尾部 `circle` 圆点 + tooltip「包含强调项」）→ 本期不采纳（我们无徽标系统），记入 §7 非目标备注。
4. **Multi_Cli_Studio：deleted 删除线样式**（红色 + line-through，删除语义一眼可辨）→ 记为候选增强，QSS/角色内实现成本待评估，列入 §7 非目标备注，有需求再立项。
5. **Multi_Cli_Studio：unstaged 覆盖 staged 的隐式归并** → 反面教材：归并规则必须显式定义优先级，不接受覆盖顺序决定结果。
6. **VS_Code_Python：model 内查询缓存 + 信号驱动失效** → 与我们方案 B 的 `_dir_status` 预聚合缓存同构，互为印证，无新增改动。

**结论**：本计划方案 B 与 theia-zen 主实现架构同构（预聚合平铺表 + O(1) 查询 + 父链上溯 + 根不入表），方向验证正确；另外两个项目均未实现目录冒泡，无可抄算法，仅提供配色与模式佐证。

## 3. 方案设计

### 3.1 总体思路：刷新期预聚合，查询 O(1)（方案 B）

在 `GitStatusService.refresh()` 刷新 `_status` 之后，**一次性构建目录聚合缓存**：

```
_dir_status: dict[str, str]   # {目录相对路径（无尾斜杠）: 归并后状态}
```

构建算法：对每个文件状态键 `a/b/c.py`，沿父链 `a/b`、`a` 逐级向上 merge，按优先级取高者。刷新频率低（去抖后事件触发），预计算成本可忽略；目录着色查询退化为一次字典 get。

**否决方案 A（着色层即时前缀扫描）**：目录节点每次 `data()` 调用都 `startswith` 扫描全量键，深树展开时开销随节点数 × 状态数放大，且把聚合逻辑散在视图层，不干净。

### 3.2 优先级与冒泡开关（修订一：对齐 theia-zen / VS Code 语义）

```
conflict > modified > untracked > ignored
```

- **deleted 不冒泡**：删除的文件在树上可能已不可见，冒泡到目录会误导「目录里有东西要处理」却点开找不到——对齐 VS Code git 扩展的 `propagate = type !== DELETED` 语义（见 §2.1）。deleted 状态**不进父链归并**，但 ignored 折叠目录键照常入缓存。
- 归并函数 `merge(a, b) -> 优先级高者`，在 `core/git/service.py` 内实现（或作为模块级小函数）；**归并规则显式定义优先级，禁止依赖遍历/覆盖顺序**（§2.1 反面教材第 5 条）。
- 依据：冲突必须最先被看见；修改代表已跟踪内容变更，重要性高于新增；忽略垫底（实际上 ignored 目录大多已被噪音过滤折叠，兜底用）。

### 3.3 改动点明细

| # | 文件 | 改动 |
|:--|:---|:---|
| 1 | `core/git/service.py` | ① 新增模块级 `_STATUS_PRIORITY: dict[str, int]` 与 `_merge_status(a, b)`；② `refresh()` 末尾构建 `_dir_status`（对每个**可冒泡**状态键沿 `PurePosixPath.parents` 父链向上 merge，**deleted 键跳过不上溯**、**目录已有同级/更高优先级状态即 `break` 剪枝**——对齐 theia-zen `propagateDecorationsByUri`；ignored 折叠键 `dir/` 直接入缓存不再向上二次推导其孙级；仓库根不入缓存）；③ 新增 `status_of_dir(abs_path) -> str \| None`：绝对路径 → 相对仓库根 → 查 `_dir_status` |
| 2 | `gui/panels/file_explorer/model.py` | `_git_status_color_of()`：目录分支由 `return None` 改为 `status = self._git_service.status_of_dir(...)`，命中后走与文件相同的 `git_status_color()` 查色返回；文件分支逻辑不动；模块 docstring 同步更新（移除「预留开关，本期不启用」表述） |

### 3.4 边界与一致性约定

- **仓库根本身不着色**：父链上推到仓库根为止，根目录节点保持原色（它是常驻锚点，着色反而是噪音）。
- **deleted 不冒泡**：仅含 deleted 变更的目录不着色；deleted 与可冒泡状态共存于同一子树时，目录取可冒泡状态的最高优先级（deleted 参与单文件着色，不参与目录归并）。
- **ignored 折叠键处理**：`git status --ignored` 把被忽略目录报成 `dir/` 单键。该键直接以 `ignored` 状态入 `_dir_status`（键去尾斜杠），其祖先照常沿父链 merge；不为其虚构子文件。
- **空目录 / 无变更目录**：`_dir_status` 无键 → `status_of_dir` 返回 None → 不着色，与现状一致。
- **折叠状态可见性**：目录着色后，其 ForegroundRole 在折叠/展开两态都生效（Qt 对目录节点的文字角色绘制无差别），满足「藏在文件夹里也能看见」的原始诉求。
- **主题兼容**：颜色仍走 `git_status_color(theme, status)`，四主题共享 `GIT_STATUS_PACK`，无需新增色值；未来若觉目录全色过重，再评估「目录降低饱和度变体」，本期不做。

## 6. 风险与注意事项

| 符号 | 项 | 说明 |
|:--:|:---|:---|
| ⚠️ | ignored 折叠键语义 | `dir/` 键是「目录整体被忽略」，必须去尾斜杠后再入缓存，否则前缀 / 键值对不上导致 ignored 目录不着色 |
| ⚠️ | 路径分隔符 | `_status` 键来自 git 输出（POSIX 风格 `/`），`_rel()` 转换后需保持同一风格再查缓存，Linux 单平台下风险低，仍须用例兜底 |
| 🟡 | 整树重绘成本 | `refresh_colors()` 已用 `layoutChanged` 全量重绘，目录着色使受影响节点变多，但 QTreeView 仅绘制可见区，实测无感；若后续出现卡顿再考虑窄化失效范围 |
| 🟡 | 色彩语义边界 | 目录着色 = 「子树内有该级别变更」，不代表目录本身被 git 跟踪变更；文档与注释中保持此语义，避免误读 |
