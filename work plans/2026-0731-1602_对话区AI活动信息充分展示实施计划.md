# 对话区 AI 活动信息充分展示实施计划

> 本文档由 `2026-0731-1405_对话区AI活动信息充分展示初步计划.md` 转正：

> 同时吸收 `2026-0731-1425_对话区活动展示KiloCode借鉴设计计划.md`（已封存）
> 的**协议事实 F1–F5**——封存文档自述「未来任何活动信息展示改造以此为准」，

## 1. 背景与问题

### 1.1 现象

用户截图实证：AI 执行多步任务时，对话区仅出现零星灰字单行——
「• 调用工具 TodoList」「• 调用工具 Agent」「• 调用工具 Bash」——
todo list 内容、工具参数、执行状态流转、子代理活动**全部不可见**。
信息展示过于简单，用户无法追踪 AI 在做什么、做到哪一步。

### 1.2 根因定位（已实证）

**不是 ACP 协议给的信息不够，而是 IDE 在映射层主动丢弃。**

四个 provider 各自持有一份逐行一致的私有 `_map_update`
（kimi_acp.py:292、kilocode_acp.py:315、opencode_acp.py:311、
reasonix_acp.py:388，后三份 docstring 自述「与 KimiAcpLLM 逐行一致」）：

```python
# llm/providers/kimi_acp.py:302-303（其余三家同形）
if kind == "tool_call":
    return Chunk("reasoning", f"\n• 调用工具 {update.get('title') or '?'}\n")
return None  # tool_call_update / plan / available_commands_update 等
```

丢弃清单：

| sessionUpdate 类型 | 协议载荷 | 现处置 | 对应用户盲区 |
|---|---|---|---|
| `plan` | entries 全量快照：content / status(pending/in_progress/completed) / priority | `return None` | **todo list 不可见**（kimi 等发 plan 的后端） |
| `tool_call` | title / kind / **rawInput（完整参数）** / locations / status | 压成一行灰字，rawInput 丢弃 | 工具参数不可见 |
| `tool_call_update` | status 流转（pending→in_progress→completed/failed）/ content / rawOutput | `return None` | 执行进度与成败不可见 |
| `usage_update` | token 用量 / 上下文占比 | 已映射（1454 计划落地，走徽章） | 已闭合，本计划不涉及 |
| `available_commands_update` | 斜杠命令清单 | `return None` | 维持丢弃（合理） |

### 1.3 现状链路（代码实证）

```
agent 子进程 ──ndjson──> AcpConnection._dispatch_line（acp.py:157，全量入队，无丢弃）
    ──> provider._map_update（★ 丢弃点：plan/tool_call_update 等 return None）
    ──> ChatWorker.chunk_received = Signal(object)（worker.py:20，透传，天然支持结构化载荷）
    ──> ChatPanel._on_chunk（panel.py:444，仅路由 usage/reasoning/text 三种 kind）
    ──> ChatOutput（output.py，QTextBrowser 追加式渲染，无富块能力）
```

结论：**改造不动 ACP 连接层、不需要 agent 侧配合**，是
「协议映射层放出来 + GUI 层设计渲染形态」的纯 IDE 侧改造。

### 1.4 协议事实修正（引自 1425 封存款 §2，已实证）

- **F1**：kilocode/opencode 系后端**不发 `plan`**——todo 走 todowrite
  普通工具调用（kind=`other`），载荷在 `tool_call.rawInput.todos`
  （[{content, status, priority}]，status 含 cancelled，title 为 `"N todos"`）。
  → todo 上屏必须**双通道**：①标准 `plan`（kimi 等）；②todowrite
  rawInput 解析（kilocode/opencode 唯一通道）。两通道产出同构 entries。
- **F2**：子代理（task 工具，kind=`think`）内部步骤协议层**不可得**
  （子 session 事件被 agent 静默丢弃）→ D5 被协议事实强制为
  「仅开始/完成行」，非开放选项。
- **F3**：tool_call 全字段：toolCallId（状态锚点键）/ kind（execute、
  edit、read、search、fetch、think、other）/ status 状态机 / title
  （shell 工具 title 即命令本身）/ locations[{path}] / rawInput /
  rawOutput（failed 时含 error）。tool_call_update 除 toolCallId 外
  字段均可缺省，按部分更新合并。
- **F5**：无 `_meta` 私有扩展通道，「未知类型返回 None」纪律完全适用。

## 2. 改造总思路

一条纵贯线，自下而上四层：

1. **抽象层**（`llm/base.py`）：`Chunk` 扩展三个结构化 kind 与通用载荷字段；
2. **协议层**（`llm/providers/acp.py`）：新增模块级公共映射
   `map_session_update`，现有四分支原样搬入 + 新增 tool_call（全字段，
   含 todowrite 特判）/ tool_call_update / plan 三分支；四 provider
   删除私有 `_map_update` 改调公共实现；
3. **路由层**（`gui/panels/chat/panel.py`）：`_on_chunk` 按新 kind 分发，
   三类均只上屏不入历史；
4. **渲染层**（`gui/panels/chat/output.py` + `gui/theme.py`）：工具调用行、
   状态行、todo 锚点块三种渲染方法，配色入聊天资源包。

## 4. 实施任务分解（T1–T7）

### T1：`llm/base.py` —— Chunk 结构化扩展（D3-A）

**现状**（base.py:35-45）：`Chunk` 为 frozen dataclass，kind
Literal["text", "reasoning", "usage"]，字段 text + usage（UsageStats
已带默认值字段 source，证明 frozen dataclass 加默认值字段对存量构造
调用零影响，base.py:32 先例）。

**改动**：

1. kind Literal 扩为 `"text" / "reasoning" / "usage" / "tool_call" /
   "tool_call_update" / "todo"`。
   - 命名说明：不用协议名 `plan` 而用 `todo`——双通道归一后该 kind
     同时承载 plan 快照与 todowrite rawInput 解析结果，语义是
     「任务清单块」而非协议原文（F1）。
2. 新增字段 `payload: dict | None = None`（放 usage 之后，存量
   `Chunk("text", ...)` / `Chunk("usage", "", usage=...)` 构造零改动）。
3. 同文件新增三个 TypedDict 定型 payload schema（入口定型纪律与
   acp.py 协议定型类型同范式）：

```python
class ToolCallPayload(TypedDict, total=False):
    """kind="tool_call" 的载荷（协议层 map_session_update 产出）。"""
    tool_call_id: str   # 状态更新的锚点键（F3）
    title: str          # 工具标题（shell 工具即命令本身）
    tool_kind: str      # execute/edit/read/search/fetch/think/other
    summary: str        # 参数摘要（协议层预格式化单行，GUI 不解析 rawInput）
    is_subagent: bool   # tool_kind="think"（task 子代理）时 True（D5 标记）

class ToolUpdatePayload(TypedDict, total=False):
    """kind="tool_call_update" 的载荷。"""
    tool_call_id: str
    status: str         # in_progress / completed / failed
    error: str          # failed 时的错误首行（预截断；尽力而为，可缺省）

class TodoEntry(TypedDict, total=False):
    content: str
    status: str         # pending / in_progress / completed / cancelled
    priority: str       # high / medium / low（渲染层本期不消费，载荷留存）

class TodoPayload(TypedDict):
    """kind="todo" 的载荷：entries 为全量快照（两通道同构，F1）。"""
    entries: list[TodoEntry]
```

4. docstring 同步：`LanguageModel.chat` 的 yield 语义补注——新三 kind
   与 reasoning 同约束「**仅上屏，不入历史、不回传**」；`text` 字段
   对新 kind 保留为「兜底显示文本」，GUI 对未识别 kind 按 text 渲染
   （多标签/多开版本错配防御）。

**约束**：新 kind 的 `text` 必须由协议层填好可读的兜底单行（如
`"◐ ▸ Edit — gui/panels/chat/panel.py"`），保证新协议层配旧 GUI 不崩。

### T2：`llm/providers/acp.py` —— 公共映射 `map_session_update`（D4 + F1 双通道）

**现状**：模块级函数 `map_usage_update`（acp.py:60-78）已是先例；
`__all__`（acp.py:302-309）需补新导出名。

**改动**：新增模块级函数：

```python
def map_session_update(obj: dict) -> Chunk | None:
    """session/update 通知帧 → Chunk；未消费类型返回 None。

    四 provider 私有 _map_update 的上收公共实现（D4）：原有
    agent_message_chunk / agent_thought_chunk / usage_update 三分支
    行为等价原样搬入；tool_call 分支由「压一行灰字」扩展为结构化
    Chunk；新增 tool_call_update / plan 两分支（1602 计划 T2）。
    """
```

各分支规格：

1. **agent_message_chunk / agent_thought_chunk / usage_update**：
   原样搬入（usage_update 继续调 `map_usage_update`，行为等价——
   kimi 收不到此推送无影响，kilocode/opencode 推送路径不变）。
2. **tool_call → `Chunk("tool_call", 兜底行, payload=ToolCallPayload)`**：
   - **todowrite 特判（F1 第二通道，先于一般分支判断）**：
     `rawInput.todos` 为 list 且元素含 content/status 时，改产出
     `Chunk("todo", ...)`（entries 原样提取 content/status/priority），
     不再产出 tool_call 块——todo 块与工具块分流（1425 封存款
     HIDDEN_TOOLS 同范式印证）。
   - 一般工具：提取 toolCallId / title / kind；
     `kind == "think"` 时 payload 置 `is_subagent=True`（D5 标记）。
   - **参数摘要规则**（协议层单点格式化，GUI 不碰 rawInput 各家差异）：
     - execute（bash/shell）：取 `rawInput.command` 首行，超 80 字符截断
       （title 即命令本身时摘要省略，防重复）；
     - edit/read/write：`locations[0].path` 优先，否则
       `rawInput.path` / `rawInput.filePath`；
     - search（grep/glob）：`rawInput.pattern` / `rawInput.query`；
     - fetch：`rawInput.url`；
     - think（task 子代理）：`rawInput.description` 或 prompt 首行截断；
     - 未识别/取值失败：仅 title（摘要缺省，不阻断上屏）。
3. **tool_call_update → `Chunk("tool_call_update", 兜底行,
   payload=ToolUpdatePayload)`**：
   - 提取 toolCallId / status；status 缺省（纯 content 快照帧）返回
     None（一级不上屏输出内容，无状态可报）；
   - `status == "failed"` 时尽力提取错误首行：rawOutput.error 或
     content 文本首行，截断 80 字符入 payload.error；取不到则缺省。
   - **一级不上屏输出正文**（D1）：content/rawOutput 的长输出不消费，
     无 ANSI/截断/落盘需求（1425 之 K6 属二级范围，本期明确不做）。
4. **plan → `Chunk("todo", ..., payload=TodoPayload)`**：entries 全量
   快照提取 content/status/priority（F1 第一通道，kimi 等后端）。
5. **available_commands_update / 未知类型 / `_meta` 扩展**：维持返回
   None（F5；R1 纪律：泛化层不臆造协议）。
6. 兜底行文本规格（payload 的 text 字段，与渲染层共用同一格式串，
   协议层生成、渲染层重组时保持一致）：
   - tool_call：`"◐ ▸ {title}"`（+ `" — {summary}"`，摘要缺省则省略）；
   - tool_call_update：completed=`"✔ ▸ {title 或 toolCallId}"`、
     failed=`"✖ ▸ {...}（{error}）"`、in_progress 一级不上屏（见 T4）；
   - todo：`- [ ]/- [>]/- [x]` 前缀清单文本。
