## 1. 背景与目标

2026-11-20 07:53，K3.1 长任务在上下文占用约 15% 时出现请求无响应。随后用户输入“继续”未进入 Kimi 事件流，IDE 又记录到 ACP `BrokenPipeError`。现场没有上下文溢出、鉴权失败、限流或 HTTP 错误证据；15% 是事故时的占用读数，不是触发阈值。

既有 `2026-1118-1115_IDE长任务后会话无响应修复落地计划.md` 已提供两项底层能力：

1. `abort_turn()` 使等待中的轮次可以被停止按钮解封；
2. 面板看门狗在长时间无任何消息帧后自动中断。

本次事故暴露的是下一层缺口：**轮次虽然能够被中断，但连接已死亡或 agent 已卡住时，下一次发送缺少可靠恢复路径；原会话 ID 被丢弃，stderr 又被直接抛弃，导致“不能继续”与“无法定位首次失败”并存。**

本计划目标是：

- 连接断开、写帧失败或看门狗判定停滞后，用户能通过下一次**手动发送**重建 ACP 并恢复原 Kimi 会话；
- 恢复使用 `session/resume`，保留模型上下文且不重放历史卡片；
- 中断请求绝不自动重放，防止重复写文件、重复执行命令、重复提交等副作用；
- 恢复失败时明确报错并保留草稿，不得静默新建空会话冒充恢复成功；
- 补足 stderr、退出码、请求 ID 与生命周期日志，使下一次事故能区分 IDE、Kimi CLI、网络和服务端问题；
- 保持正常对话、正常停止、长任务、工具审批、终端反向 RPC 与关闭清理行为不回归。

## 4. 设计决策

### D1 恢复必须保留原会话，不得用新空会话冒充

为 provider 保存“当前/最后可用会话 ID”及其创建参数。连接死亡只销毁连接，不得同时丢弃恢复所需的会话身份。

仅以下显式操作可以清除恢复身份并走 `session/new`：

- 用户新建/清空会话；
- 用户切换工作区或明确切换为不共享上下文的新后端会话；
- 用户在恢复失败后明确选择“新建空会话”。

普通异常、写断管、reader EOF、看门狗停滞均不得隐式清除原会话 ID。

### D2 使用 `session/resume`，不使用默认历史回放

重建 ACP 子进程并完成 `initialize` 后，以原会话 ID 调用 `session/resume`，再恢复模型、推理强度及会话创建所需参数。

选择 `session/resume` 而非默认 `session/load` 的原因：

- `resume` 不重复回放历史，不会把旧正文、旧工具卡片再次插入当前面板；
- 面板已有自身历史展示，不需要借恢复过程重建 UI；
- 避免把恢复通知误算成新一轮 AI 输出。

旧 CLI 未声明 `sessionCapabilities.resume` 时，本轮不静默退回 `session/load`。应提示升级 CLI 或由用户明确选择新会话；若未来确需兼容 `load`，必须另做回放帧抑制与去重设计。

### D3 只在下一次手动发送时恢复，绝不自动重放中断请求

恢复触发语义统一为：

1. 当前轮次因断管或停滞收尾；
2. 面板明确显示连接状态、原请求未自动重发、下一次手动发送会尝试恢复原会话；
3. 用户检查已经发生的工具副作用后，再手动发送新指令；
4. provider 在同一会话发送锁内完成重建与 `session/resume`，随后只发送这次新指令。

禁止：

- 后台自动重试原 `session/prompt`；
- 恢复成功后自动补发看门狗中断的请求；
- 因迟到通知自动启动新轮次；
- 恢复过程中自动触发排队待发。

这样不能保证“原任务自动继续”，但能防止不确定是否已执行的写操作被重复执行。

### D4 区分正常停止、看门狗停滞和真实连接故障

- **正常手动停止**：维持现有 `session/cancel + abort_turn`，不强制重建进程。
- **看门狗停滞**：除自动停止外，将 Kimi provider 标记为“下轮发送前需要恢复”；下一次手动发送先重建并 `resume`。
- **reader EOF、写断管、进程退出**：立即标记连接不可用并保留原会话 ID；下一次手动发送执行同样恢复路径。
- **标签/应用正常关闭**：只清理，不报错、不安排恢复；关闭后迟到的死讯不得重新创建进程。

### D5 所有写路径共享同一连接失效收口

`request()`、`begin_turn()`、`cancel_turn()`、`session/request_permission` 应答与 `terminal/*` 应答的写失败，必须进入统一的连接失效处理，不得只在某一支路打印 `BrokenPipeError` 后继续使用“看似存活”的连接。

失效处理需要：

- 幂等标记连接死亡并唤醒 `_pending`、`_updates` 和挂起的 `wait_for_exit`；
- 保存退出码、最后请求 ID、失败方法及失效类别；
- 避免在持有 `_write_lock` 时调用会再次获取同一把锁的函数；
- 防止旧连接的迟到死讯清理新连接状态。

### D6 stderr 必须持续排空，但不能无界记录或泄露内容

将 agent stderr 改为管道并增加独立 daemon reader，确保持续排空，避免仅改成 `PIPE` 后因无人读取造成二次死锁。

采用“**持续读取 + 有界内存环形缓冲 + 异常时有界落日志**”：

- 正常运行不逐行转发完整 stderr；
- 缓冲总行数与总字节数均设上限，超出丢弃最旧片段并记录截断标记；
- 仅在异常退出、写失败、初始化失败或受控诊断命令中输出必要尾部；
- 单条日志限制长度，禁止记录凭证、完整 prompt、完整工具输出和 ACP stdout 原文；
- 对疑似 token、Authorization、Cookie 等内容沿用项目隐私脱敏与扫描纪律，不把脱敏规则写成“只替换一种固定前缀”。

同时补充结构化生命周期日志：进程 PID、agent 名称/版本、恢复能力、会话 ID、连接代次、轮次请求 ID、取消、abort、EOF、退出码、写失败方法、恢复开始与恢复结果。日志不得记录消息正文。

### D7 恢复失败必须 fail closed

以下情况均视为恢复失败：

- `initialize` 失败；
- CLI 不支持 `session/resume`；
- `session/resume` 超时、返回错误或原会话已不可恢复；
- 模型/推理强度恢复失败且无法保证后续请求使用用户当前选择。

恢复失败时：

- 不发送本轮 prompt；
- 不自动降级为 `session/new`；
- 不删除原会话数据；
- 解除 busy、取消排队待发、保留用户输入草稿；
- 显示可操作错误：“原会话恢复失败，未发送消息；可重试恢复，或明确新建空会话”。

### D8 既有停止与排队语义不回归

- 正常完成仍可按现有规则发送排队内容；
- 用户停止、看门狗停止、写失败和恢复失败均不得自动发送排队内容；
- 不引入“界面显示已完成但 agent 仍在执行”的新状态；
- 原中断轮已显示的工具卡片保留供用户核对，历史状态不得伪造成成功完成。

### T2 加固 ACP 连接生命周期与诊断

修改 `src/ide/llm/providers/acp.py`：

1. 增加有界 stderr reader/ring buffer 与异常尾部日志。
2. 增加连接代次、失效原因、最后请求 ID 和预期/非预期关闭区分。
3. 将各写路径的失败收口到同一幂等失效函数，注意锁顺序和文件关闭顺序。
4. 保证所有 pending、turn consumer 与 terminal wait 都能被唤醒。
5. 对预期 `terminate()` 不再产生误导性的“进程意外退出”错误。
6. 保持 stdout ACP 帧边界不变，诊断信息只能走 stderr reader 或 logging，不能污染协议。

**检查点**：大量 stderr 不阻塞 agent；写断管后连接状态一致；关闭操作无新增死锁。

### T3 实现 Kimi 原会话恢复

修改 `src/ide/llm/providers/kimi_acp.py`：

1. 保存原会话 ID、工作区、MCP 创建参数及连接代次，连接死亡不再直接丢弃恢复身份。
2. 在 `_turn_lock` 内实现连接重建与 `session/resume`，避免同标签并发双恢复。
3. 仅在当前 CLI 声明支持时调用 `resume`；恢复模型与 thinking 配置。
4. 实现“看门狗停滞后下轮需要恢复”和“连接死亡后下轮需要恢复”两类标记。
5. 恢复完成后刷新会话目录/用量缓存，但不得把缓存失效误当成会话清空。
6. `reset_session()`、`set_workspace_root()`、`close()` 的清除语义与异常恢复严格分开。
7. `resume` 不支持或失败时按 D7 fail closed，不进入 `session/new`。

**检查点**：同一原会话 ID 被恢复；旧连接的迟到事件不能污染新连接；任何失败分支均未发送本轮 prompt。

### T4 接通面板恢复提示与手动发送语义

1. 看门狗触发时除 `request_stop()` 外，标记本次为“停滞恢复”，与普通手动停止区分。

3. 连接故障时给出明确错误卡片，提示先核对已发生的工具副作用。
4. 只有用户新的手动发送才进入恢复；恢复期间禁用重复发送与模型切换，避免竞态。
5. 恢复失败按现有失败收尾取消待发并保留草稿，不自动开启空会话。
6. 保持 `_on_finished`、`_on_stopped`、busy、通知和 `turn_completed` 语义一致，不把失败恢复播报为任务成功。

**检查点**：用户不需要放弃原上下文，也不需要反复重启整个 IDE；界面始终知道下一次发送会做什么。

### T5 自动化回归

新增或扩充测试，至少覆盖：

1. 沉默轮次经看门狗停止后，下一次手动发送创建新连接并 `resume` 原会话。

## 6. 验收条件

### 6.1 功能验收

- agent 永久沉默时，既有停止/看门狗仍能解除 busy；下一次手动发送可恢复原会话。
- EOF、写断管后，界面明确失败，不再出现“用户继续发送但请求未进入 agent”的假发送状态。
- 恢复前后 Kimi `sessionId` 相同，模型与 thinking 选择一致。
- 原中断请求自动重放次数为 **0**；恢复后新请求发送次数为 **1**。
- `resume` 失败时新建空会话次数为 **0**，prompt 发送次数为 **0**。
- 正常手动停止不触发进程重建；正常对话和排队发送不回归。

### 6.2 诊断验收

- 每起异常都能从 IDE 日志看到连接代次、会话 ID、请求 ID、失败方法、退出码/EOF 和恢复结果。
- stderr reader 持续排空，缓冲有硬上限；异常日志有足够尾部且不含凭证与完整对话。
- 能明确区分用户停止、看门狗停止、主动关闭、意外 EOF 和写断管。

### 6.3 工程验收

- 新增故障矩阵全部通过，既有 `tests/test_turn_abort.py` 继续通过。
- `bash scripts/check.sh` 全绿，包括隐私扫描、lint 与全量测试。
- 真实 Kimi `session/resume` 通过，冻结版 AppImage 的断管恢复通过；未执行的项目必须在实施回写中明确标注，不得宣称完成。

## 7. 风险与注意点

- **副作用风险**：自动重试可能重复执行不可逆工具，因此本计划明确禁止自动重放，而不是追求表面上的无缝续跑。
- **协议兼容风险**：`session/resume` 是能力协商项，不得假定所有已安装 CLI 都支持；旧版本必须显式降级提示。
- **恢复竞态**：旧 reader、旧 terminal wait 与新连接可能交错，必须使用连接代次和幂等失效处理。
- **管道死锁风险**：stderr 改 PIPE 后必须持续排空；测试和清理均须遵守写端/读端关闭顺序。
- **隐私风险**：stderr 可能包含路径、命令和上游敏感内容，只允许有界、异常触发、脱敏后的诊断尾部。
- **体验风险**：看门狗停滞后强制下轮重建会增加一次初始化延迟，但这是用可预期的短时成本换取不再沿用可疑连接。
- **范围风险**：不得为迎合本次事故增加 15% 上下文特判、自动 compact 或 K3.1 专用分支。

## 8. 已确认决策

1. 本问题按高优先级处理，先保证可恢复与不重复执行，再追求自动续跑。
2. 采用 `session/resume` 恢复原会话；不默认使用带历史回放的 `session/load`。
3. 恢复由下一次手动发送触发，原中断 prompt 永不自动重试。
4. 看门狗停滞与真实断管都进入下轮恢复；普通手动停止保持现状。
5. 恢复失败不得静默创建新会话，必须保留草稿并明确提示。
6. stderr 必须改为持续排空、有界缓冲、异常落日志，不能简单改成无人读取的 PIPE。
7. 首轮上游无响应的根因仍未锁定，新增观测后凭证据另案处理，不在本计划中编造服务端结论。
