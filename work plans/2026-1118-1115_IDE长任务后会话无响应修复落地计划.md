# IDE 长任务后会话无响应修复落地计划

> **状态**：已实施（2026-11-18 11:52 回写）
> **范围**：ACP 连接层轮次中断、全部 ACP 后端 cancel 路径、会话面板挂起看门狗
> **时间**：2026-11-18 11:25（UTC+8）
> **优先级**：高
> **前身**：用户反馈《IDE 长耗时任务后会话无响应问题反馈》（长桥 OAuth 授权现场，日志在用户侧不可获取，转为本地复现驱动）

## 一、问题摘要

同一 IDE 中执行长耗时 Bash 任务（长桥 OAuth 授权等待）后，原会话失去响应：AI 不再回复、无可见错误，用户只能放弃会话上下文新建会话。新会话正常，说明 IDE 整体与网络无全局故障。

## 二、复现结论（2026-11-18 本地复现成立）

复现探针：`.temp/repro_stuck_session/`（`mock_kimi.py` 假 ACP 后端 + `repro.py` 驱动）。

假后端行为等价于「agent 侧丢失后台任务完成事件」：收到 `session/prompt` 后发一帧 execute tool_call（长任务已启动），随后**永久沉默**——不回 prompt 响应、不回 cancel 应答。

驱动以真实 `ChatWorker` + 真实 `KimiAcpLLM` 走 ACP 全链路（`_find_bin` 指向假后端、真实子进程、真实 ndjson 收发），实测结果：

1. tool_call 帧正常到达（链路本身通畅）；
2. 用户按「■ 停止」（`request_stop()`：置停止标志 + 发 `session/cancel`）后 8 秒：**无任何收尾信号，worker 线程仍存活**；
3. 假后端日志确认已收到 prompt 与 cancel——IDE 该做的都做了，是等待 agent 回包等到永远；
4. 仅 `provider.close()`（关标签级 terminate 注入死讯）才能唤醒 worker。

即完整复现现场症状：busy 永不解除、排队待发永不触发、停止按钮失效、只能放弃会话。

## 三、根因链（代码级，逐环已核实）

1. **轮次消费永久阻塞**：`acp.py:1454` `next_update(timeout=None)` 无超时阻塞；`kimi_acp.py:785` 无 sidecar 时以 `timeout=None` 调用。agent 不回 prompt 响应则永不返回。
2. **停止检查点够不到**：`worker.py:52-55` 的 `_is_stop_requested` 检查只在**收到 chunk 时**执行；worker 线程阻塞在 generator 内时标志永远轮询不到。
3. **cancel 依赖 agent 配合**：`kimi_acp.py:673-681` `cancel()` 仅发 `session/cancel` 通知，唤醒仍指望 agent 回包；agent 侧状态卡死则无包可回。
4. **无挂起看门狗**：busy 收尾只由 `_on_finished`/`_on_stopped` 驱动（`panel.py:1295/1339`），二者不触发则排队待发 `_fire_pending_send`（`panel.py:1332`）永不执行，界面无限期静默。
5. **同病者共 7 家**：dream/dsh/kilocode/local/opencode/reasonix 的 chat 循环同样裸调 `conn.next_update()`（无超时），连接层一处修复即可全覆盖。

sidecar 开启（kimi 默认）不改变结论：0.3s 轮询只让 generator 内部空转，worker 的停止检查点依旧只在 chunk 到达时执行。

## 四、修复方案

### D1 轮次中断可逃逸（核心，治「停止按钮失效」）

- `acp.py` `AcpConnection` 新增 `_turn_abort: threading.Event`：
  - `begin_turn()` 清除、`end_turn()` 保持清除；
  - 新增 `abort_turn()` 置位（可从任意线程调用，幂等）。
- `next_update()` 拆拍：内部以 ≤1s 的 `queue.get(timeout=1)` 循环逼近调用方语义，每拍检查 abort 事件，置位则抛 `TurnAborted`（新异常，继承 `Exception`）。`timeout` 参数语义不变（None=无限等帧，除非 abort）。
- 7 家 provider 的 `cancel()` 统一补 `conn.abort_turn()`（cancel 先协议通知、后本地 abort；本地 abort 保证秒级醒来，协议通知给 agent 优雅收场的机会）。
- `worker.py` 零改动：`except Exception` 已兜住 `TurnAborted`，且 `request_stop()` 先置标志再 cancel——abort 抛出时标志已置位，按既有「用户中断」路径收尾（`stopped_by_user` → `_on_stopped` 解除 busy）。
- 效果：即使 agent 永久沉默，「■ 停止」按下后 ≤1s 收尾，原会话 busy 解除、可继续发送，agent 进程保留（长驻连接不被毁）。

### D2 轮次挂起看门狗（治「无限期静默」，对应反馈验收条件）

- `panel.py` 新增看门狗 `QTimer`（30s tick，仿既有 `_usage_timer` 范式，轮次内运行）：`_on_chunk` 更新 `_last_chunk_at`，tick 检查 worker 在跑且距末帧超阈值 → 自动 `request_stop()`（走 D1 秒级收尾）+ 系统消息「本轮已 N 分钟无响应，已自动中断，可重新发送；反复出现请新建会话」。
- 阈值进设置：`KEY_TURN_STALL_TIMEOUT_MIN`，默认 10（分钟），0=关闭。默认 10 分钟的依据：execute 运行中 agent 有 in_progress 帧流动（面板 200ms 尾滚节流的消费侧即此帧）；静默等待型任务（如浏览器 OAuth 无输出）可能长时间无帧，阈值须显著大于正常等待。
- 设置中心「高级」页加该项（数字/下拉档位，即时持久化）。

### D3 会话重建逃生通道（可选增强，本轮不做）

连续挂起自动中断 ≥2 次 → 提示「后端会话疑似卡死」，引导切换后端再切回（既有 `set_model_selection` 路径会销毁重建 provider 实例）或新建会话。看 D2 上线后的实际表现再定。

## 五、实施步骤

1. **连接层**（`src/ide/llm/providers/acp.py`）：`_turn_abort` 事件、`abort_turn()`、`TurnAborted`、`next_update` 拆拍（含 docstring 记录节拍语义）。
2. **7 家 provider cancel 补刀**：kimi/dream/dsh/kilocode/local/opencode/reasonix 的 `cancel()` 末尾加 `conn.abort_turn()`（各文件同位注释，说明 why：agent 沉默时协议 cancel 无回包，本地 abort 是唯一解封路径）。
3. **看门狗**：`panel.py`（`_last_chunk_at` 簿记 + `QTimer` + tick 判定 + 系统提示）、`settings.py`（设置项 + 默认值）、设置中心「高级」页登记。
4. **测试** `tests/test_turn_abort.py`（新文件）：
   - 复现探针固化：假后端收 prompt 后沉默，断言 `request_stop()` 后 worker 在 3s 内发 `stopped_by_user`（修复前此用例挂——红进绿出）；
   - 正常轮次不受拆拍影响（假后端正常回 response）；
   - 看门狗：阈值调小后自动中断 + 系统消息落账。
5. **回归**：`./.venv/bin/python3 -m pytest tests/ -q` 全绿；复现探针 `.temp/repro_stuck_session/repro.py` 修复后重跑验证输出反转（停止后秒级收尾）。

## 六、验收条件

- agent 轮次挂起（不回包）时，「■ 停止」按下后 ≤1s 收尾，busy 解除，原会话可继续发送消息。
- 轮次超过阈值无任何帧 → 自动中断 + 界面明确系统提示（可诊断，不静默）。
- 正常对话、正常停止、失败收尾、关标签清理路径行为不变；7 家 ACP 后端共享受益。
- 完成事件重复/迟到等异常输入不引入新的卡死路径（连接层事件幂等纪律不破）。

## 七、边界与免责

- agent 侧（kimi CLI）丢失后台任务完成事件的根因不在本仓修复范围；本方案保证 IDE 侧任何情况下可中断、可恢复、不静默。agent 侧修复另案跟进。
- D1 的 `session/cancel` 仍照常发送：agent 健康时优雅结束（行为同今），agent 卡死时本地 abort 兜底。
- 本文未包含任何凭证、令牌、本机绝对路径（复现探针路径为项目内相对口径）。

## 实施结果回写（2026-11-18 11:52 UTC+8）

D1/D2 全部完成，修改记录见 `文档/修改记录/2026-1118-1152_会话无响应看门狗与轮次中断实施记录.md`。以下为实施过程中相对原计划的偏差与经验。

**与计划的偏差**：
- 红进绿出的呈现方式改为「探针红 + 测试绿 + 探针反转」三段证据链：测试在修复后代码上编写通过，挂起类故障若以「测试先写」方式红会让门禁在修复提交前持续红；探针修复前的「复现成立」运行记录承担红。
- 计划未预见的隐藏改动点：测试假后端首版踩中「主线程关闭被 reader 线程迭代的管道读端 → close 等读锁 × reader 等 EOF 双向死锁」，改为先关写端、对方收 EOF 退出后再关读端的顺序纪律；`ChatPanel.close()` 清理线程要求 worker 桩具备 `disconnect()/setParent()/wait()` 三接口。
- worker.py 确如计划零改动；D3（会话重建逃生通道）按计划未做，留后续。

**验证结果**：聚焦测试 8 passed；全量门禁 `bash scripts/check.sh` 全绿（482 passed = 原有 474 + 新增 8）；复现探针修复后重跑输出反转（request_stop 秒级收尾 stopped）。未做真机端到端复验（依赖用户现场）；agent 侧根因另案。

**经验沉淀**：阻塞点的停止检查必须让阻塞原语本身可中断（拆拍 + 事件），不能只靠上层轮询；协议 cancel 与本地中断互补，先通知后中断；管道文件对象关闭顺序纪律（先写后端读端）；看门狗判定口径取「无任何消息帧」而非「无正文」，避免误杀正常长等待任务。
