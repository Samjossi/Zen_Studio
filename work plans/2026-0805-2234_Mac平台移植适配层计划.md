# Mac 平台移植：POSIX 红利下的轻量适配计划

## 1. 背景

在 Windows 移植计划（`2026-0805-2226_Windows平台移植适配层计划.md`）敲定 PAL 架构（单 Protocol + 惰性工厂 + 独立平台包）后，macOS 适配成为该架构的第二个受益者。本文档不复述架构原理，只回答一个问题：**macOS 与 Linux 同为 POSIX，移植差异还剩什么，如何以最小代价接入 PAL。**

### 1.1 核心判断：macOS 是「轻量移植」

| 维度 | 结论 |
|---|---|
| 依赖 | `ptyprocess` / `fcntl` 在 macOS **原生可用**，POSIX 两大硬阻塞点不存在 |
| shell | zsh 为默认登录 shell（`/bin/zsh`），`os.environ.get("SHELL", ...)` 探测逻辑原样正确 |
| Agent CLI | kimi/kilocode/opencode 等均提供 macOS 安装路径，`~/.local/bin`、`npm global` 等 Unix 惯例**直接成立** |
| GUI | PySide6 全兼容；Qt 自动处理 Cmd 键映射与 HiDPI（Retina）基础支持 |

因此 macOS 移植**不需要**像 Windows 那样重写 PTY/文件锁后端，差异收敛为「配置目录、自重启、打包签名、桌面习惯」四项，外加若干 GUI 细节核对。预估改动量约为 Windows 移植的 1/3。

### 1.2 与 Windows 计划的关系

- **依赖**：PAL 缝合点（`core/platform_api.py`）与 PosixBackend 必须先于本计划落地（即 Windows 计划 T1+T2 里程碑）。
- **架构验证价值**：macOS 作为第三个后端接入，恰好检验「行为差异进平台包、数据差异留原地」的黄金分割点是否经得起第二个平台的考验——若接入时发现 Protocol 缺方法或抽象过度，应回头修正 PAL 设计而非绕过。

## 2. 现状清单（代码实证）

### 2.1 差异点全量盘点

| 位置 | 现状 | macOS 差异 | 处置 |
|---|---|---|---|
| `core/paths.py` → PosixBackend `user_config_dir` | XDG：`${XDG_CONFIG_HOME:-~/.config}/zen-studio/` | macOS 惯例为 `~/Library/Application Support/zen-studio/`；XDG 亦被部分 Mac 用户接受 | 🟡 决策点 D2 |
| `gui/main_window.py` → PosixBackend `relaunch` | AppImage/FUSE 自重启 | .app bundle 重启（`open -n` 或 execv 到 bundle 内可执行文件） | 🟡 MacBackend 覆写 |
| `gui/panels/terminal/session.py` → `default_shell_argv` | `$SHELL` 兜底 `/bin/bash` | macOS 自带 bash 为 3.2 古董版，兜底应为 `/bin/zsh` | 🟡 MacBackend 覆写 |
| `core/external_apps.py` | 已含 macOS 分支设计（`platform` 注入，Typora 探测回退） | 需核对 `open -a` 调用与「在文件管理器中显示」的 `open -R` | ✅ 已有设计，核对补全 |
| 全局快捷键 | Qt `Ctrl` 修饰符在 macOS 自动映射为 Cmd（`QKeySequence.StandardKey` 体系内） | 手写的字符串快捷键（如 `"Ctrl+W"`）不会自动转换 | 🟡 审计项 |
| 菜单栏 | 应用为无边框自绘标题栏，主菜单在窗口内 | macOS 全局菜单栏（屏幕顶部）是平台惯例；Qt 默认把 QMenuBar 提升为全局菜单 | 🟡 决策点 D4 |
| 窗口 | 自绘无边框 + `startSystemMove/Resize` | macOS 均支持；但红绿灯按钮区、全屏机制（native fullscreen）交互需实机核对 | 🟡 实机项 |
| `building/` | AppImage 链（Linux 专属） | 需 .app bundle + .dmg + **签名/公证**（Gatekeeper 硬门槛） | 🔴 全新链路，工作量大头 |
| `pyproject.toml` dev 组 `python-xlib` | XTEST 视觉验证，Linux X11 专用 | macOS 无 XTEST；视觉验证闭环在 Mac 上不可用 | 🟢 dev-only，文档注明即可 |

### 2.2 不需要动的（POSIX 红利确认）

- PTY 后端：ptyprocess 直接可用，PosixBackend `spawn_pty` **零改动复用**；
- 文件锁：`fcntl.flock` macOS 原生支持，零改动复用；
- provider `_find_bin()` 三级链：PATH → `$X_HOME/bin` → `~/.x/bin` 全部成立，仅 `.exe` 后缀工具恒返回原名（Windows 计划的 `bin_probe` 机制下 Mac 分支返回空，与 Linux 一致）；
- 终端渲染栈（pyte + 自绘）：无平台假设。

## 3. 设计

### 3.1 D1：接入方式——PosixBackend 子类化，而非平行新写

```
core/
├── platform_api.py       ← 工厂增加 darwin 分支（全库仍仅此一处平台判断）
├── platform_posix.py     ← PosixBackend 保持不动，作为基类
platform_mac/
├── __init__.py           ← 导出 MacBackend(PosixBackend)
├── config_dir.py         ← 覆写：~/Library/Application Support
├── relaunch.py           ← 覆写：.app bundle 重启
└── shell.py              ← 覆写：默认 /bin/zsh
```

```python
# core/platform_api.py（工厂分支扩展示意）
if sys.platform == "win32":
    from platform_win import WindowsBackend
    _backend = WindowsBackend()
elif sys.platform == "darwin":
    from platform_mac import MacBackend      # Linux 永不执行
    _backend = MacBackend()
else:
    from core.platform_posix import PosixBackend
    _backend = PosixBackend()
```

**设计理由**：macOS 差异是「POSIX 基座上的三个覆写点」，若平行新写整个后端会造成与 PosixBackend 的大面积重复（PTY、flock 两份相同实现），违背 DRY 且制造双份维护负担。继承体系精确表达「macOS 是 POSIX 超集的子集差异」这一事实。`platform_mac/` 仍为独立包，Linux 构建不收编。

### 3.2 D2：配置目录——跟随平台惯例

`~/Library/Application Support/zen-studio/`（macOS 标准），不沿用 XDG。理由：

- 打包态 .app 用户的预期是平台惯例路径；开发态维持项目内 `config/` 不变（现有规约不动）；
- 旧版若曾以 XDG 路径在 Mac 上运行过，提供一次性迁移：检测到 `~/.config/zen-studio/` 存在且 Library 路径不存在时复制迁移（约 20 行，置于 `config_dir.py`）。

### 3.3 D3：relaunch 与 shell 覆写

| 覆写 | 实现 |
|---|---|
| `relaunch` | 打包态：`subprocess.Popen(["open", "-n", bundle_path])` + `sys.exit(0)`；开发态：与 POSIX 相同的 `os.execv` |
| `default_shell_argv` | `os.environ.get("SHELL")` 优先不变，兜底 `/bin/zsh`（macOS 10.15+ 默认登录 shell；自带 bash 3.2 过于陈旧） |

### 3.4 D4：菜单栏——保留窗口内菜单，全局菜单栏列为可选后置

首版**不**接 macOS 全局菜单栏：应用为无边框自绘标题栏，菜单在窗口内是自洽设计；强行提升为全局菜单反而割裂。Qt 默认会在全局菜单栏放一个基本空的 App 菜单，属可接受状态。列为可选后置项（若做，需将菜单体系迁到 `QMenuBar` + role-based QAction，工作量独立评估）。

### 3.5 D5：快捷键审计（不改架构，一次性排查）

全库 grep 手写快捷键字符串（形如 `"Ctrl+..."`）：Qt 仅在 `QKeySequence.StandardKey` 体系内自动做 Ctrl→Cmd 映射，手写字符串在 macOS 上会按字面要求按 Ctrl——与 Mac 用户习惯相悖。排查后统一替换为 `QKeySequence` 标准键或按平台常量表分发。预估涉及处数量有限（菜单/动作注册点），单次审计可穷尽。

### 3.6 D6：构建链——真正的硬门槛在签名公证

新增 `building/build_mac.sh`（与 AppImage 链平行）：

```
PyInstaller（.app bundle，spec 复用 + macOS 专属 excludes）
    → codesign --deep --sign "Developer ID Application"（需 Apple 开发者证书）
    → 公证：xcrun notarytool submit + staple
    → 打 .dmg（create-dmg 或 hdiutil）
```

⚠️ **Gatekeeper 是硬门槛**：未公证的 .app 在默认安全设置下无法打开（用户需右键绕过，体验不可接受）。这要求：

- Apple Developer Program 账号（$99/年）——**本计划的实际前置条件**，需在 T1 前落实；
- 签名公证步骤必须进构建脚本，不能是手工流程。

### 3.7 依赖标记

`ptyprocess` 环境标记放宽为 `sys_platform != 'win32'`（Windows 计划已如此定义，macOS 自然落入）；无需新增 macOS 专属生产依赖。dev 组 `python-xlib` 注明 Linux-only。

## 5. 测试策略

沿用 Windows 计划确立的四层体系，按 macOS 特点裁剪：

| 层 | 内容 | macOS 特异性 |
|---|---|---|
| 契约测试 | 同一套件跑 MacBackend（mock 覆写点） | MacBackend 大量继承 POSIX，契约测试大部分自动继承通过；新增仅三覆写点的断言 |
| Linux 回归 | 机械检查：全库 `sys.platform` 仍仅在 `platform_api.py` | 工厂分支增加后此检查防止分支逻辑外泄 |
| 构建审计 | .app 内无 pywinpty、含 ptyprocess；公证状态 `spctl --assess` 通过 | 公证验证可脚本化（`stapler validate`），进构建脚本 |
| 实机清单 | 终端（zsh 会话、中文输入）、配置目录落位、重启、CLI 可用性矩阵、快捷键 Cmd 系、Retina 渲染、红绿灯区与自绘标题栏交互 | **输入法**是重点：macOS 输入法框架与 Qt 的交互和 Linux fcitx 完全不同（该项目为 fcitx5 专门构建过插件，Mac 侧需重新实测） |

无 macOS CI runner 时，实机清单为唯一保障；GitHub Actions `macos-latest` 可承担契约测试 + 构建 + 公证验证的自动化。

## 6. 风险

| 风险 | 等级 | 缓解 |
|---|---|---|
| 签名/公证流程失败阻塞发布 | ⚠️ 中 | T0 前置落实账号；构建脚本内 `notarytool` 失败即fail-fast，不产未签名包 |
| Apple Silicon / Intel 双架构 | ⚠️ 中 | PyInstaller 按构建机架构出包；首版仅 arm64（M 系为绝对主流），universal2 列可选 |
| 继承 PosixBackend 引入隐式耦合（父类改动意外影响 Mac） | 🟢 低 | 契约测试双后端约束；覆写点仅三个，review 时显式核对 |
| 输入法/Retina/全屏等 GUI 细节实机才暴露 | 🟢 低 | 实机清单全覆盖；不回污染主库（差异若需代码，进 `platform_mac/`） |
| PAL 抽象被第二平台证伪 | 🟢 低 | §1.2 已将其定位为本计划的验证目标，证伪即修正 PAL，属预期收益而非事故 |
