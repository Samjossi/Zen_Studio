# 上下文 Token 用量百分比显示移植计划

> ⚠️ **本文档为初步文档**：参考实现与现状链路已实证闭环，但显示位置、
> 显示形态等关键决策（§4 之 D1–D4）尚未经用户拍板。拍板后本文档修订
> 转正（状态改「草稿」），再进入实施。

## 1. 背景与动机

Kilo Code（参考代码 `参考代码/kilocode-main`）在对话界面实时显示
「本轮会话已用上下文窗口的百分比」（如 `17%`），让用户对「还剩多少
上下文可用、何时该压缩/新开会话」一目了然。该体验对本项目同样
有价值：多标签长驻 ACP 会话，用户目前对 token 消耗完全无感知
（`tabs.py` 注释自述标签数上限的动机即「约束 token 消耗」）。

**关键利好：数据早已到达 IDE 门口，只是被丢弃。** Kilo Code 官方
后端（及其余三家 agent）均按 ACP 协议在每轮结束后推送
`usage_update` 通知，Zen Studio 的 `AcpConnection._dispatch_line`
全量入队无丢弃，但四个 provider 的 `_map_update` 统一
`return None` 将其丢弃。移植是「映射层放出来 + GUI 层展示」的
纯 IDE 侧改造，**不需要 agent 侧任何配合**。

## 2. 参考实现分析（kilocode-main）

该功能在参考代码中有三处实现，核心算法一致：

### 2.1 TUI 侧栏 Context 组件

`packages/tui/src/feature-plugins/sidebar/context.tsx`（89 行，完整可读）：

```ts
// 取最后一条 output > 0 的 assistant 消息
const last = msg().findLast((item) => item.role === "assistant" && item.tokens.output > 0)
// 五类 token 求和
const tokens = last.tokens.input + last.tokens.output + last.tokens.reasoning
             + last.tokens.cache.read + last.tokens.cache.write
// 查模型的上下文上限，求百分比；无上限数据则为 null（降级只显示 token 数）
const model = providers.find(...)?.models[last.modelID]
percent = model?.limit.context ? Math.round((tokens / model.limit.context) * 100) : null
```

显示三行：`N tokens` / `X% used` / `$cost spent`（可折叠面板）。

### 2.2 VSCode 扩展 webview（功能最完整，重点参考）

四处文件协作：

| 文件 | 职责 |
|---|---|
| `webview-ui/src/context/session-utils.ts` | `calcContextUsage(tokens, contextLimit)` 纯函数：五类 token 求和，`contextLimit` 缺失时 percentage 返回 `null`（第 163–176 行） |
| `webview-ui/src/context/session.tsx` | `contextUsage` memo（第 2898–2911 行）：从最后一条带 tokens 的 assistant 消息取数，经 `provider.findModel` 查 `limit.context` 兜底 `contextLength` |
| `webview-ui/src/components/chat/TaskHeader.tsx` | 头部徽章：显示 `17%`，tooltip 显示 `34,300 tokens (17% of context)`（第 68–74、229–238 行） |
| `webview-ui/src/components/chat/ContextProgress.tsx` | 三段式进度条：已用（≥50% 变红警示）/ 为输出预留 / 可用，左右标注 `34.3k / 200k` 紧凑格式，tooltip 分行明细（76 行，完整可读） |

### 2.3 ACP 产出端（对本项目最重要）

`packages/opencode/src/acp/usage.ts`（第 201–213 行）——agent 侧向
ACP 客户端（即 Zen Studio）推送的通知结构：

```json
{
  "method": "session/update",
  "params": {
    "sessionId": "...",
    "update": {
      "sessionUpdate": "usage_update",
      "used": 34300,            // = tokens.input + tokens.cache.read
      "size": 200000,           // 模型上下文窗口上限
      "cost": { "amount": 0.042, "currency": "USD" }  // 会话累计成本
    }
  }
}
```

要点：

- **`used` 与 `size` 同帧送达**：百分比 = `used / size × 100`，IDE 侧
  无需自维护模型上下文上限表（参考实现的 TUI/webview 需要自己查
  模型目录，我们走 ACP 路径反而更简——agent 已经查好放进 `size`）。
- `size` 可能缺失（agent 查不到模型上限时干脆不发该通知，见
  usage.ts 第 199 行 `if (!size) return`）→ UI 须容忍「收不到
  usage_update」的后端，保持隐藏而非显示 0%。
- 推送时机：每轮 assistant 消息完成后（`service.ts` 第 651 行同款
  载荷），非流式期间高频推送，一轮一次，UI 更新压力极小。

### 2.4 可借鉴的呈现细节

- 百分比整数化（`Math.round`），无小数千分位噪音。
- token 数用千分位（`toLocaleString`）或紧凑格式（`34.3k`）。
- 热态警示：用量 ≥50% 进度条变红（`context-progress-used--hot`）。
- tooltip 承载明细：主显示极简（一个百分比数字），悬停展开
  「已用 / 上限 / 可用 / 成本」。
- 降级链：无 `size` → 只显示 token 数；无数据 → 整体隐藏。

## 5. 改造方案（按倾向稿展开，拍板后修订）

自下而上四层：

### 5.1 抽象层（`llm/base.py`）

新增定型 dataclass + Chunk kind 扩展：

```python
@dataclass(frozen=True)
class UsageStats:
    """ACP usage_update 载荷（协议键 used/size/cost 入口定型）。"""
    used: int            # 已用 token（input + cache.read，agent 口径）
    size: int            # 上下文窗口上限
    cost: float | None   # 会话累计成本（USD；agent 未给则 None）

# Chunk.kind 扩 Literal["text", "reasoning", "usage"]，
# usage 时 text 为空串、载荷经新字段 usage: UsageStats | None 携带
```

### 5.2 协议映射层（`llm/providers/acp.py` + 四 provider）

- `acp.py` 新增公共函数 `map_usage_update(update: dict) -> UsageStats | None`
  （解析 `used`/`size`/`cost.amount`；`size` 缺失或为 0 返回 None——
  无上限数据的通知无意义，不上屏），供四 provider 复用（对齐 1405
  D4 上收方向，本期先上收这一个分支，不动其余映射）。
- 四 provider `_map_update` 各加一分支（逐行一致的两行）：

```python
if kind == "usage_update":
    stats = map_usage_update(update)
    return Chunk("usage", "", usage=stats) if stats else None
```

### 5.3 路由层（`gui/panels/chat/panel.py`）

- `_on_chunk` 增 `usage` 分支：更新本标签的用量显示（不进输出区
  文本流、不入 `_history`）。
- 显示值簿记：`self._usage: UsageStats | None`，收到新通知即覆盖
  （每轮一条，天然「最后一条 assistant 消息」语义，与参考实现的
  `findLast` 等效）。
- 清零时机：切换后端（`set_model_selection` 内，`reset_session`
  语义点）清零并隐藏——旧会话用量不得残留到新后端。

### 5.4 渲染层（依 D1-A / D2-A 倾向稿）

- 底行装配（`_build_input_box`）：`ModelBar` 与 `addStretch` 之间
  插入 `QLabel`（objectName `chatUsageLabel`），初始隐藏。
- 文案：`{used/size 百分比}%`，tooltip：
  `已用 34,300 / 上限 200,000 tokens（17%）`（千分位）。
- 热态：`percentage >= 50` 时置 qss 动态属性 `hot="true"` 变警示色
  （仿 `chatSendButton[stop]` 的 unpolish/polish 先例），主题资源包
  新增 `chat.usage_hot_fg` 配色键（四主题）。
- 宽度策略：恒显时按 `100%` 三字符宽度 `setFixedWidth` 一次写死，
  显隐不改变 sizeHint——吸取 ModelBar busy 显隐撑宽左栏的教训
  （2026-0724-2305 计划病根），显隐只改文本与透明度/可见性前须
  实测 sizeHint 稳定性，必要时改为常驻占位。

### 5.5 线程与生命周期核对（无明显风险，列出备查）

- usage_update 在 worker 线程的 `_iter_turn_chunks` 循环内产生，
  经 `Signal(object)` 跨线程到 GUI，Qt 队列连接天然安全（与现有
  text/reasoning 同路径）。
- 每轮仅一条（或零条），无高频刷新压力。
- 标签关闭：worker 信号已 disconnect（panel.py close 两段式），
  迟到 usage 信号不触达已销毁 UI，无新增生命周期负担。
- 多标签：各 ChatPanel 自持 provider 实例，usage 数据标签间天然
  隔离，无需 ChatTabs 汇总。

## 7. 风险与边界

| 风险 | 评估 | 对策 |
|---|---|---|
| 某家 agent 不发 usage_update 或不填 size | 中（协议允许省略） | UI 降级隐藏，不显示 0% 误导；T5 实测确认 |
| 底行新增控件触发左栏宽度跳变 | 低（已有两次宽度病根治理经验） | 恒宽写死 / 常驻占位，显隐不改 sizeHint（§5.4） |
| 与 1405 计划同改 `_map_update` 冲突 | 低（改动为同一位置加分支） | 先落地者按 1405 D4 方向写（公共函数入 acp.py），后落地者 rebase 无概念冲突 |
| 百分比口径与用户预期不符（used 不含 output） | 低（偏保守，数值偏小） | tooltip 文案写「已用 tokens（输入+缓存）」如实标注口径（一期可简化为 tokens 数，不细分） |

**不做的事**：不自建模型上下文上限表（agent 已在 `size` 里给好，
重复维护即漂移源）；不做自动压缩/compact 触发（Kilo 有
autoCompactThreshold 机制，属另一功能域，用户未要求）；不改
ACP 连接层（数据本就在那里）。
