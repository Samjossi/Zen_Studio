## 1. 背景与症状

0807-0148 计划已修复 kimi 后端 `AskUserQuestion` 的自动选答缺陷（决策特判 +
QuestionDialog/QuestionCard 卡片内交互，验证全绿）。2026-08-12 实测 **reasonix
后端**的提问工具同型复发：

| # | 症状 | 证据 |
|:---:|:---|:---|
| S1 | **用户从未看到选择界面**，提问一闪而过即"完成" | 截图：`ask` 卡片直接带 ✅ 完成，全程无弹窗无按钮 |
| S2 | **被自动选中的恒为第一个选项**（"火锅"） | 截图：两次提问均自动走第一个选项 |
| S3 | **卡片是通用卡（🧩 ask），不是 QuestionCard** | 截图：无问答对渲染、无选项按钮组，标题为小写 `ask` |

本质与 0807-0148 相同：提问交互请求被当成普通工具审批，走"自动放行"通道秒回
第一个选项。差别仅在**工具名**——识别白名单没有覆盖 reasonix 的 `ask`。

## 2. 协议层背景：为什么工具名各家不一样（问题的总根源）

用户追问"没有一个通用标准吗？ACP 协议不统一吗？"——查证结论（蓝本：
`dream-acp/protocol/dream-acp-v1.md` 与各家实证帧）：

**ACP 统一的是"管道"，不是"词汇表"。** ACP（Agent Client Protocol）规定了
客户端与 agent 之间的通信方式：JSON-RPC 帧格式、`session/update` 流式更新、
`tool_call` 帧、`session/request_permission` 反向请求等**传输层与帧结构**。
各家 CLI（kimi/reasonix/kilocode/opencode）实现 ACP，因此 Zen Studio 能用同一
套连接层（`llm/providers/acp.py`）对接所有后端。

**但工具名不归 ACP 管。** `tool_call` 帧只有两个相关字段：

- `kind`：粗粒度分类枚举，仅 `read` / `edit` / `execute` / `search` / `fetch` /
  `think` / `other` 等几种（协议文档 `:163`）；
- `title`：**自由文本**，agent 自行命名——kimi 叫 `AskUserQuestion`，reasonix
  叫 `ask`，协议不做任何约束。

**更关键：ACP v1 没有"向用户提问"这个语义。** `kind` 枚举无 question 类（提问
工具只能挂 `other`）；协议也没有专门的提问交互帧。各家要实现"问用户一个问题
给几个选项"，只能**借用 `request_permission`**——该帧本是工具审批语义，选项
kind 是 `allow_once` / `allow_always` / `reject_once` 这套审批词汇（协议文档
`:253-255`）。于是答案选项（"火锅""牛肉面"）被编码成 `allow_once` kind 传输，
审批通道与问答通道在协议层混用——客户端不做特判，`select_option_id` 按 kind
优先序一挑必然秒选第一个答案（0807-0148 §2 R2 已实证）。

**对本计划的指导意义**：在协议补全"提问-作答"语义之前，**逐后端记工具名是永远
追不上的防线**（新后端、工具更名都会复发本缺陷）。识别提问请求的最稳依据是
**载荷结构**——rawInput 携带 `questions` 字段是"agent 在提问"的事实签名，与
工具叫什么名字无关。这就是 T1 确立"结构通道为主、白名单为辅"双通道识别的立论
依据。

## 3. 根因分析

### 3.1 数据链

```
reasonix agent 调用 ask（提问工具）
  → session/request_permission 反向请求（options = 答案选项，借审批帧传输，见 §2）
  → panel.py _ask_permission
  → decide_permission 前置决策
  → is_question_request(title="ask") → False（白名单只有 "askuserquestion"）
  → 落入普通工具审批分支：kind="other" ≠ "execute" → 四态自动放行
  → select_option_id 按 kind 优先序秒选第一个 allow 类选项回传
  → agent 收到"用户已选第一个选项"，completed 帧下传
  → make_tool_card：_TOOL_NAME_CARDS 无 "ask" 键 → 通用卡渲染（S3）
```

### 3.2 根因定位

| # | 根因 | 位置 | 对应症状 |
|:---:|:---|:---|:---:|
| R1 | **识别条件是封闭白名单，只覆盖 kimi 工具名**：`_QUESTION_TOOL_NAMES = frozenset({"askuserquestion"})`，reasonix 提问工具名为 `ask`，未命中即掉入普通审批链自动放行。深层成因见 §2：协议无提问语义标识，工具名各自为政 | `llm/permission_policy.py:60` | S1 S2 |
| R2 | **卡片分派同病**：`_TOOL_NAME_CARDS` 只注册 `"askuserquestion"`，`"ask"` 回退通用卡——即使交互链路修好，渲染面也不会出问答对与选项按钮组 | `gui/panels/chat/cards.py:1277-1284` | S3 |
| R3 | **载荷结构未实证**：`ask` 的 `rawInput.questions` 结构（options 字段名、multiSelect 字段名、optionId 形态）是否与 kimi 同构未知——`_extract_question_options` 的蓝本是 kimi 帧（`.temp/frame_archive/askuser_*.json`），直接套有漂移风险 | `llm/providers/acp.py:614` | 潜在 |

**判定依据**：截图中卡片标题为小写 `ask` 且呈 🧩 通用卡形态，与 `_normalize_tool_name`
归一化后未命中两张白名单表的预测完全吻合；0807-0148 已验证的决策链/交互链路
（QUESTION_BRIDGE、QuestionDialog、QuestionCard）本身无缺陷，缺陷在**入口识别**。

## 4. 修复方案

总原则：**按实证把 reasonix `ask` 接入既有 question 交互闭环**（决策特判 →
QUESTION_BRIDGE → 卡片按钮/弹窗兜底），不新造链路；同时把入口识别从"记名字"
升级为"**看结构为主、记名字为辅**"双通道（立论见 §2），防下一个后端/下一次
更名重蹈覆辙。

### T0：抓帧实证（先行，一切改造的蓝本）

- 复用既有抓帧手法（`scripts/capture_tool_frames.py` / 0807 的 `spike_askuser_other.py`
  范式），用 reasonix 后端触发一次真实 `ask` 调用，存档全序列帧：
  tool_call 首帧（title/kind/rawInput）→ request_permission 反向请求
  （options 的 kind 编码与 optionId 形态）→ completed 帧（answers 结构）。
- 存档 `.temp/frame_archive/ask_reasonix_*.json`。
- **必须证实的项**：① title 确切值（是否恒为小写 `ask`，有无命名空间前缀变体）；
  ② options 的 kind 是否 `allow_once` 系；③ rawInput.questions 结构是否与 kimi
  同构（options/multiSelect 字段名）；④ 是否支持多选及其编码形态。

### T1：识别条件双通道化（修 R1）—— `llm/permission_policy.py`

1. **结构通道（主防线）**：`toolCall.rawInput` 含 `questions` 列表即判为
   question——提问请求的语义由载荷结构决定，与工具名无关（§2 立论）。
   - 覆盖一切已知/未知后端、现有/未来工具名，新后端零接入成本。
   - 误伤评估：普通工具 rawInput 不带 `questions` 键（0806 计划 T5 起该键即为
     AskUserQuestion 专属提取源），风险低；单测必须含"Bash/Read 不命中"回归。
   - 纪律修订：`is_question_request` 原注释"不碰载荷深层结构"更新为"只看
     rawInput.questions 存在性，不解析内容"。
2. **白名单通道（辅助）**：按 T0 实证补入 `"ask"`。
   - 保留价值：兜底"借审批帧提问但 rawInput 不带 questions"的异构实现（若 T0
     发现此类形态）；已有实证名的后端即使载荷结构漂移也不脱保。
   - 注释同步更新：白名单服务于结构通道覆盖不到的形态，两通道任一命中即
     question，集中维护。

### T2：载荷提取兼容（修 R3）—— `llm/providers/acp.py`

- 按 T0 实证核对 `_extract_questions` / `_extract_question_options` 对 reasonix
  rawInput 的适配：同构则零改动（仅注释补实证出处）；字段名漂移则做兼容提取
  （双字段名兜底，不臆造第三种形态）。
- `questions` / `question_options` 两载荷字段契约不变（`llm/base.py` 不动）。

### T3：卡片分派注册（修 R2）—— `gui/panels/chat/cards.py`

- `_TOOL_NAME_CARDS` 增补 `"ask": QuestionCard`（以 T0 证实的归一化名为键）。
- QuestionCard 的 pending 态按钮组激活、QUESTION_BRIDGE 按 tool_call_id 定位、
  超时/缺卡降级 QuestionDialog 等机制**零改动复用**（0807-0148 已建成）。
- 注：卡片分派只能按名注册（渲染层拿不到决策层结论，且分派需确定性映射），
  不受 T1 结构通道惠及——这正是分派表仍需逐名实证补入的原因；但**交互正确性
  已由 T1 结构通道保证**，此处缺失的最坏后果只是渲染为通用卡（展示降级），
  不会再发生静默自动选答。

### T4：其余后端排查备案

- kilocode / opencode / dream 三后端排查是否有同类提问工具：有则同法抓帧实证
  补入白名单与分派表；无则在 0807-0148 风险表 🟡7 处回填"已排查，无同类工具"。
- 结构识别通道（T1）兜底后，此项为完善项（渲染面补全）而非阻断项。

### T5：验证

1. **单测**（`scripts/test_question_permission.py` 扩展）：
   - `is_question_request`：title `"ask"` 命中；rawInput 带 questions 的非白名单
     title（如未来新名）命中；普通工具（`Bash`/`Read`/无 rawInput）不命中。
   - `decide_permission`：四态 × 上述形态一律 `DECISION_ASK`；非 question 回归不变。
2. **mock 截图**：`scripts/shot_tool_cards.py` 以 T0 存档帧为蓝本补 `ask_pending_
   选项按钮` / `ask_问答对` 场景，确认 `ask` 走 QuestionCard 渲染与按钮组形态。
3. **真机冒烟**（reasonix 后端，验收口径同 0807-0148 §5.3）：
   - A1：触发 `ask` → 弹出选择界面（卡片按钮或弹窗），不操作不自动选答；
   - A2：选非第一个选项 → 回传答案为所选项；
   - A3：关闭不答 → 拒绝兜底，agent 不崩溃；
   - A4：四态权限模式各跑一轮（含 auto_all）均不自动选答；
   - A5：超时按拒绝兜底，agent 不挂死；
   - A6：普通工具审批回归（Bash 黑名单弹窗、非危险自动放行）不变；
   - A7：kimi 后端 AskUserQuestion 回归（既有闭环不被结构通道扰动）。

## 7. 与 0807-0148 计划的关系

0807-0148 建成了完整的 question 交互闭环（决策特判 → QUESTION_BRIDGE →
QuestionDialog/QuestionCard），但其入口识别是**单点白名单**，只覆盖了当时实证的
kimi `AskUserQuestion`——在 ACP 未统一提问语义的现实下（§2），这个缺口迟早被
下一个后端击穿，reasonix `ask` 正是如此。本计划不重建任何链路，只做两件事：
把 reasonix `ask` 按实证接入既有闭环，并把入口识别从"记名字"加固为
"**结构为主、名字为辅**"双通道——闭环建成一次，所有后端受益；识别升级一次，
未来后端免修。
