## 2. 协议层背景：为什么工具名各家不一样（问题的总根源）

用户追问"没有一个通用标准吗？ACP 协议不统一吗？"——查证结论（蓝本：
`dream-acp/protocol/dream-acp-v1.md` 与各家实证帧）：

**ACP 统一的是"管道"，不是"词汇表"。** ACP（Agent Client Protocol）规定了
客户端与 agent 之间的通信方式：JSON-RPC 帧格式、`session/update` 流式更新、
`tool_call` 帧、`session/request_permission` 反向请求等**传输层与帧结构**。
各家 CLI（kimi/reasonix/kilocode/opencode）实现 ACP，因此 Zen Studio 能用同一
套连接层（`llm/providers/acp.py`）对接所有后端。

**但工具名不归 ACP 管。** `tool_call` 帧只有两个相关字段：

- `kind`：粗粒度分类枚举，仅 `read` / `edit` / `execute` / `search` / `fetch` /
  `think` / `other` 等几种（协议文档 `:163`）；
- `title`：**自由文本**，agent 自行命名——kimi 叫 `AskUserQuestion`，reasonix
  叫 `ask`，协议不做任何约束。

**更关键：ACP v1 没有"向用户提问"这个语义。** `kind` 枚举无 question 类（提问
工具只能挂 `other`）；协议也没有专门的提问交互帧。各家要实现"问用户一个问题
给几个选项"，只能**借用 `request_permission`**——该帧本是工具审批语义，选项
kind 是 `allow_once` / `allow_always` / `reject_once` 这套审批词汇（协议文档
`:253-255`）。于是答案选项（"火锅""牛肉面"）被编码成 `allow_once` kind 传输，
审批通道与问答通道在协议层混用——客户端不做特判，`select_option_id` 按 kind
优先序一挑必然秒选第一个答案（0807-0148 §2 R2 已实证）。

**对本计划的指导意义**：在协议补全"提问-作答"语义之前，**逐后端记工具名是永远
追不上的防线**（新后端、工具更名都会复发本缺陷）。识别提问请求的最稳依据是
**载荷结构**——rawInput 携带提问载荷是"agent 在提问"的事实签名，与工具叫什么
名字无关。这就是 T1 确立"结构通道为主、白名单为辅"双通道识别的立论依据；
T0 实证（见 §4 T0）进一步证明白名单对 reasonix 决策路径**完全无效**——它的
request_permission 帧 title 是问题原文。

## 3. 根因分析

### 3.1 数据链

```
reasonix agent 调用 ask（提问工具）
  → session/request_permission 反向请求（options = 答案选项，借审批帧传输，见 §2）
  → panel.py _ask_permission
  → decide_permission 前置决策
  → is_question_request → False（白名单只有 "askuserquestion"，
    而该帧 title 是问题原文——T0 实证，白名单注定命中不了）
  → 落入普通工具审批分支：kind="other" ≠ "execute" → 四态自动放行
  → select_option_id 按 kind 优先序秒选第一个 allow 类选项回传
  → agent 收到"用户已选第一个选项"，completed 帧下传
  → make_tool_card：_TOOL_NAME_CARDS 无 "ask" 键 → 通用卡渲染（S3）
```

## 7. 与 0807-0148 计划的关系

0807-0148 建成了完整的 question 交互闭环（决策特判 → QUESTION_BRIDGE →
QuestionDialog/QuestionCard），但其入口识别是**单点白名单**，只覆盖了当时实证的
kimi `AskUserQuestion`——在 ACP 未统一提问语义的现实下（§2），这个缺口迟早被
下一个后端击穿，reasonix `ask` 正是如此。本计划不重建任何链路，只做两件事：
把 reasonix `ask` 按实证接入既有闭环，并把入口识别从"记名字"加固为
"**结构为主、名字为辅**"双通道——闭环建成一次，所有后端受益；识别升级一次，
未来后端免修。E6（toolCallId 双轨不一致）经真机反馈驱动提前闭环：文本匹配
激活让 reasonix 与 kimi 同享卡片内交互终态，QuestionDialog 回归其本位——
卡片缺失/已终态的兜底载体。
