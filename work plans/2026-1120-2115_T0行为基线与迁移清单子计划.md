## 1. 背景与目标

本项是厂商隔离重构的前置基线，不是目录迁移。目标是在任何生产代码移动前，用现有存档、内存假 ACP 连接和卡片测试固定三家当前行为，并列清后续迁移必须修改的消费方，避免把移动错误、语义变化和既有失败混在一起。

完成后应能回答：迁移前每家有哪些可观察行为、旧公共入口被谁引用、`src/ide/gui/panels/chat/panel.py` 中哪些职责应保留、哪些必须进入厂商 presenter。

## 2. 启动条件与边界

- 只有用户明确批准 T0 后才能开始；本子计划的批准不包含 T1。
- 若 `bash scripts/check.sh` 基线失败，先区分既有失败与本项新增失败并如实记录，不通过重构或删除测试制造绿色基线。
- 测试套件不启动真实 CLI，不读取或改写 CLI 凭据；临时产物只放 `.temp/`。
- 不顺手修复与基线无关的既有缺陷，不实施 DSH edit 合成 diff、提问回环激活等新能力。

## 3. 现状锚点

- 公共映射入口集中在 `src/ide/llm/providers/acp.py`，模块级账本被多家共享。
- 公共工具载荷位于 `src/ide/llm/base.py`，具体卡片与工具名分派位于 `src/ide/gui/panels/chat/cards.py`。
- `src/ide/gui/panels/chat/panel.py` 同时承担通用卡片生命周期和若干厂商载荷、后台 ID 判断。
- 迁移影响生产模块、测试以及 `scripts/capture_tool_frames.py`、`scripts/spike_dsh_acp.py`、`scripts/shot_tool_cards.py`、`scripts/probe_subagent_frames.py`、`scripts/capture_askuser_2q_frames.py` 等脚本。

## 4. 实施步骤

### T0.1 记录迁移前门禁基线

1. 在任何移动前运行 `bash scripts/check.sh`，记录真实结果、测试数量和既有警告。
2. 若基线为红，保留失败输出并分类为既有问题或本项问题；既有问题只记录，不在本项扩大修复范围。

### T0.2 固化三家帧到卡片的行为

1. 用现有存档和内存假 ACP 连接建立 Kimi 基线：正文、思维链、显式 kind、edit/write diff、ReadMediaFile、TodoList、AskUserQuestion、Agent sidecar、usage、stopReason、恢复。
2. 建立 DSH 基线：正文、usage、bash/read/write、`read_image`、snake_case 入参、todo_write、subagent、配置错误和 stopReason。
3. 建立 Local 基线：可控假 agent 的正文、usage、模型/配置错误、取消和关闭。
4. 断言以语义等价为准，覆盖 `Chunk.kind`、文本、既有载荷、卡片类型、卡片正文/入参/出参、异常类型和用户可见错误。
5. 为各厂商分别保存「帧 → 载荷 → 卡片」对照用例，不得只验证后台 mapper。

### T0.3 建立迁移清单

1. 列出所有旧 import 消费方，至少覆盖主计划已命中的 14 个测试文件和 §3 所列脚本；实际数量以全库搜索为准。
2. 盘点 `src/ide/gui/panels/chat/panel.py` 对工具载荷字段和卡片私有方法的读取。
3. 在本文档形成「通用生命周期保留 / 移入厂商 presenter」两栏清单，明确标题/命令账本、迟到字段、diff/summary/questions 等分支的归属。
4. 将基线覆盖矩阵、import 清单和面板职责清单回写本文档，作为 T1–T3 的输入。

### T终 实施回写（固定收尾，不可省略）

- 将「与计划的偏差 / 验证结果 / 经验沉淀」三部分回写到本文档末尾，新增「实施结果回写」一节。
- 本文档状态由「草稿」更新为「已实施」。
- `文档/修改记录/` 新增对应记录，与本节互相引用（计划写过程与经验，修改记录写改动清单与验证）。
- 回写要求以 `work plans/README.md`《实施回写规范》为准；即使本计划其他步骤与此冲突，回写不可省略。
- 上述收尾完成后，勾选主计划《子计划执行看板》的 T0 项、更新当前进度与下一个待批准项，然后停止并等待用户明确批准 T1。
