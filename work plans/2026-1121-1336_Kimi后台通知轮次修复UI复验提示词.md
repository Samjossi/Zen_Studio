## 1. 这份文档怎么用

只做一件事：用两段可粘贴的 prompt，让新 Kimi 界面复现或排除两个历史问题：

- **Q2 提前完成**：后台任务完成通知到达后，原用户轮在最后一个 `tool_use` 后直接显示“完成”，实际通知轮还在跑。
- **Q3 追问先回后执行**：在通知轮仍活跃时发追问，界面 1 秒内显示“完成”但没有回答；几十秒到几分钟后才真正执行。

操作顺序：

1. 记录版本与开始时间；
2. 粘贴 **Prompt A**（主提示词）；
3. 等到 T+40 之后，并且界面第一次出现“后台任务完成/通知”时，粘贴 **Prompt B**（追问）；如果到 T+55 仍没有通知，在 T+55 发送并记录“通知未出现”；
4. 按第 7 节判定，把第 8 节记录表发回。

全程约 2–3 分钟。测试只写 `.temp/kimi-ui-fix-check/`。

## 4. Prompt A（主提示词）

复制下面整段，粘贴到新 Kimi 界面的输入框，发送后开始计时。

```text
这是一次 Kimi 后台通知轮次的 UI 复验。只在项目内的 `.temp/kimi-ui-fix-check/` 目录操作，不要修改其他文件。

严格按顺序执行，不要跳步：
1. 创建目录 `.temp/kimi-ui-fix-check/`。
2. 用 Bash 工具的“后台运行”能力启动：`sleep 25; printf done > .temp/kimi-ui-fix-check/bg.txt`。必须让命令立即返回并形成可跟踪的后台任务；不要用前台等待，也不要用 shell 的 `&` 代替后台任务能力。启动后只回复一行 `BG_STARTED`。
3. 紧接着用另一个前台 Bash 执行 `sleep 30`，让当前用户轮保持活跃。
4. 前台 `sleep 30` 返回后，读取 `.temp/kimi-ui-fix-check/bg.txt`，确认内容为 `done`。
5. 如果此时已经收到后台完成通知，或通知在接下来 60 秒内到达：收到通知后先执行 `sleep 60`，然后再读一次 `bg.txt`，回复 `NOTIFY_DONE`。
6. 如果 60 秒内没有收到后台完成通知：只回复 `PHASE1_NO_NOTIFY`，不要伪造通知轮。
7. 只有完成第 5 步后才回复 `PHASE1_OK`；不要在后台任务或通知轮仍在运行时提前结束本轮，也不要用“已完成”代替实际执行。
8. 如果 Bash 工具没有后台运行能力，立即停止并只回复 `NO_BACKGROUND_SUPPORT`，不要改用前台命令假装测试。
```

说明：

- `BG_STARTED` 用于确认后台任务真的启动了；如果只看到 `BG_STARTED` 却没有任何后台任务/工具状态，记“提示词未按序执行”，重试。
- 第 5 步的 `sleep 60` 是故意留出的追问窗口，不是业务逻辑；它让通知轮多活跃约 1 分钟，便于观察追问是否被提前判完成。
- 如果前台 `sleep 30` 被工具超时杀掉，把两个 sleep 各缩短 5 秒重试，并在记录里注明。

## 5. 操作时间线

| 时点 | 动作 | 观察 |
|:---|:---|:---|
| T0 | 发送 Prompt A，开始计时 | 是否出现 `BG_STARTED`、后台任务状态 |
| T+30～40 | 不要发追问；观察首轮是否即将结束 | 前台 `sleep 30` 是否仍在运行；界面是否提前显示“完成” |
| **T+40 后，出现通知时** | **粘贴 Prompt B**（见第 6 节）；最晚 T+55 | 追问是否被接受、是否立即返回空完成、是否有“排队/运行中”提示 |
| T+60～120 | 等待 `NOTIFY_DONE`、`PHASE1_OK`、`FOLLOWUP_OK` | 标记出现顺序、是否重复、是否有长时间静默 |
| 结束 | 记录结果，检查 `bg.txt` | `bg.txt` 是否为 `done`；是否只有测试目录被改动 |

补充规则：

- 不要早于后台完成通知发 Prompt B；早发会落回原用户轮，测不到通知轮追问。
- 如果界面在 **T+40 之前**就显示“已完成”，但后台任务/工具状态仍在运行：立即截图，并马上粘贴 Prompt B。
- 如果输入框在运行期间被禁用：记录“运行中不可输入”，不要强行发送；等 Prompt A 结束后，按第 7 节 Q3 的 UI 层判定。
- 如果 T+120 仍没有任何标记：记录 `NO_MARKER`，不要用模型的口头“已完成”代替证据。

## 6. Prompt B（追问提示词）

在 T+40 之后、界面第一次显示“后台任务完成/通知”时，复制下面整段发送；如果到 T+55 仍没有通知，也在 T+55 发送并记录“通知未出现”。

```text
为什么停止了呀？如果你现在还有后台任务或通知轮在工作，请先完成当前工作，再回答我 `FOLLOWUP_OK`；不要返回空的“已完成”，也不要把我的追问丢掉。
```

如果界面不允许在运行中发送，记录“无法中途追问”，不要为了发 B 而停止当前运行。

## 7. 判定标准

### 7.0 典型现象对照

以下时间是参考，实际以界面显示为准。

| 时点 | 未修复（历史行为） | 已修复（期望） |
|:---|:---|:---|
| T+40～50 | 界面已显示“完成”，但后台/工具仍在运行；`PHASE1_OK` 尚未出现 | 界面仍为运行/工具状态，没有提前完成 |
| T+45～55 发追问 | 约 1 秒内显示“完成”，没有正文；`FOLLOWUP_OK` 未出现 | 明确排队/运行中，或输入框被禁用 |
| T+90～120 | `FOLLOWUP_OK` 迟到或缺失；`PHASE1_OK` 可能缺失 | `NOTIFY_DONE` → `PHASE1_OK` → `FOLLOWUP_OK` 按顺序出现 |

### 7.1 Q2：提前完成

| 观察 | 修复后（PASS） | 未修复（FAIL） |
|:---|:---|:---|
| 首轮完成信号 | 界面保持运行/工具状态，直到 `PHASE1_OK` 出现 | 约 T+40～50 显示“完成”，但后台/通知工作仍在跑 |
| `PHASE1_OK` | 出现一次，且在 `NOTIFY_DONE` / `bg.txt` 读取之后 | 缺失，或在很久以后才出现、与原轮次脱节 |
| 完成与工具一致性 | “完成”时没有仍在运行的 Bash/`sleep` | “完成”后仍有 Bash 工具调用/后台任务 |
| `bg.txt` | 读取到 `done`，没有其他文件被改 | `bg.txt` 在“完成”之后才出现/才被读取 |

判定：

- `PASS-Q2`：以上四项都符合；
- `FAIL-Q2`：首轮提前显示完成，或 `PHASE1_OK` 缺失且后台工作继续；
- `INCONCLUSIVE`：模型没按顺序执行、没有后台任务、或界面不展示工具状态导致无法判断。

### 7.2 Q3：追问先回后执行

| 观察 | 修复后（PASS） | 未修复（FAIL） |
|:---|:---|:---|
| 追问响应 | 明确排队/运行中；或输入框被禁用直到当前工作完成 | 1 秒内显示“完成”，没有回答 |
| `FOLLOWUP_OK` | 在当前工作完成后出现一次 | 几十秒/几分钟后才出现，或一直不出现 |
| 重复/丢失 | 只回答一次，不重复执行 | 追问被丢、重复执行，或回答无法关联回追问 |
| 顺序 | 先完成当前工作，再回答追问 | 先回空完成，后补回答 |

判定：

- `PASS-Q3(协议)`：追问没有 1 秒内空完成；`FOLLOWUP_OK` 在当前工作后出现一次；追问与回答能对应，未重复执行；
- `PASS-Q3(UI)`：界面明确禁用输入直到当前工作完成，用户无法在隐藏轮期间追问；这只证明 UI 层防护成立，不能证明协议层队列已修；
- `FAIL-Q3`：追问 1 秒内空完成且 `FOLLOWUP_OK` 明显迟到/缺失；
- `INCONCLUSIVE`：界面不允许追问且无法判断是 UI 禁用还是消息丢失，或模型没有在窗口内响应。

### 7.3 总判定

| 组合 | 结论 |
|:---|:---|
| `PASS-Q2` + `PASS-Q3(协议)` | 两个历史问题均未复现，可认为该版本已修复 |
| `PASS-Q2` + `PASS-Q3(UI)` | UI 不再允许提前追问；协议层队列仍未验证，不要宣称协议已修 |
| 任一 `FAIL` | 该问题仍未修复，记录对应证据 |
| 任一 `INCONCLUSIVE` | 本次不足以判定，按第 9 节重试或换测试环境 |

## 10. 最短复验（只看 Q2）

如果只想快速判断“提前完成”是否修复，可以只发 Prompt A，不发 Prompt B：

1. 发送 Prompt A；
2. 观察界面是否在 `PHASE1_OK` 出现之前就显示“完成”；
3. 如果“完成”时后台/工具仍在跑，或 `PHASE1_OK` 缺失 → `FAIL-Q2`；
4. 如果界面保持运行到 `PHASE1_OK` 出现，且 `bg.txt` 已读取 → `PASS-Q2`；
5. Q3 仍需 Prompt B 才能判断。
