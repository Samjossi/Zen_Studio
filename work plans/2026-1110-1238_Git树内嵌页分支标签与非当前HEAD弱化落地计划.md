# Git 树内嵌页分支标签与非当前 HEAD 提交弱化落地计划

> **状态**：已确认
> **范围**：Git 树内嵌 summary 页的 refs 标签、非 HEAD 可达提交弱化、HEAD 可达性取数、tooltip 补充说明、测试与视觉验收
> **时间**：2026-11-10 12:38（设计，UTC+8）
> **优先级**：中

## 1. 背景与目标

用户反馈：当前项目切到 `main` 后，Gitea 内嵌页的提交图仍把 `test/新分支` 的 5 个空提交画在 `main` 那条线上，而且没有任何视觉区分，看起来像 `main` 也吃进了这些提交。

实际数据核对：

- `main` 最新提交仍是 `577e9b4`；
- `test/新分支` 是 `577e9b4` 的单亲线性后代，`git merge-base main test/新分支` 就是 `577e9b4` 本身；
- `git rev-list --count test/新分支..main` 为 0，`main..test/新分支` 为 5；
- 全仓 merge commit 数为 0。

因此这不是泳道算法把两条线合并了：这个 DAG 本来就只有一条泳道，`git log --all --graph` 自己也是一条线。真正的问题有两层：

1. **内嵌 summary 页不画 refs**：数据里 `test/新分支` 和 `main` 都在，但页面上没有任何分支名，用户看不出 `main` 在哪一行结束；
2. **没有区分“该提交是否在当前 HEAD 的历史上”**：次分支的 5 个提交和 main 的提交都用同一个正文色，视觉上完全等价。

另一个项目 `basalt_competition_baseline_submissions` 之所以能看到多条彩色泳道，是因为它有 5 个本地分支、9 个 merge commit，`master` 与 `x11_testing` 各有独立提交（merge-base 为 `a65ca81`，两边分别多出 11 和 2 个提交）。泳道由分叉/合并产生，不由“分支数量”产生；单亲线性分支不会额外分出一条 lane。

主流 Git 提交图的做法是：

- **分支一创建就作为 ref 标签显示在它指向的 commit 上**；
- **只有出现并行提交才多画一条泳道**；
- **空提交只延长当前线，不产生分叉**；
- **fast-forward 合并不产生新泳道，`--no-ff` 合并才产生汇合曲线**。

本计划的目标：

1. 在内嵌 summary 页的提交主题前显示紧凑的 refs 标签，让 `test/新分支`、`main` 这类分支名直接可见；
2. 把**明确不属于当前 HEAD 可达集合**的提交主题改成弱化色；
3. 当前 HEAD 可达的提交保持正文色，HEAD 行继续加粗；可达性未知时不弱化、不谎报范围；
4. 不改变泳道几何、三类边、完整弹窗、500 条截断和降级路径；
5. 让用户在 `main` 页面上看到 `test/新分支` 引用的位置，并识别其 5 个空提交不在当前 HEAD 历史中。

refs 只标记引用指向的 commit，不表达每个提交的唯一分支归属；一个提交可同时从多个分支可达。本计划不承诺为每个提交计算或展示完整分支归属。

## 2. 当前代码与根因

- `src/ide/core/git/log.py` 的 `fetch_commit_rows()` 用 `git log --topo-order --all` 取全部分支，构造 `CommitRow`，但没有“该 commit 是否从 HEAD 可达”的字段。
- `src/ide/gui/git_graph_view.py` 的 `CommitColumnDelegate.paint()` 在 summary 分支只画 `row.subject`，统一使用 `_text_color`；只有 `row.is_head` 时加粗。它在绘制 refs 徽标之前就 `return`，所以 `CommitRow.refs` 里的分支/标签信息被丢弃。
- 同一文件的完整模式已有 hash + refs 徽标 + 主题的绘制逻辑，配色来自 `_badge_colors`（`palette["git_graph"]`），可以直接抽取复用；完整模式保持现状。
- `CommitGraphModel.data()` 的 tooltip 只列出提交元数据和 refs，没有 HEAD 可达性与可达性未知的范围提示。
- `src/ide/core/git/graph.py` 的 lane 按 commit 身份和父子关系分配；单亲链在 `parent_index == 0` 时直接复用当前 lane。这个行为是 Theia 算法的既有语义，也是 `git log --graph` 的语义，不应修改。

根因可以归纳为：**数据层知道 refs，但不计算 HEAD 可达性；展示层只画主题，不画 refs，也没有任何“不在 HEAD 历史中”的视觉降级。** 所以线性次分支的 5 个提交和 main 的提交在视觉上完全等价。

## 3. 需求

1. `fetch_commit_rows()` 为每条已加载的 `CommitRow` 标记三态 `on_head`：`True` 表示 HEAD 可达，`False` 表示明确不在 HEAD 历史中，`None` 表示可达性未知。
2. summary 模式在提交主题前绘制紧凑 refs 标签：
   - 本地分支（`branch`）和标签（`tag`）显示；
   - 远程分支（`remote`）只在同一行没有本地分支/标签时显示，避免 `main` 旁边再挂一个 `origin/main`；
   - `HEAD` 不单独画徽标，继续由现有双圆节点和加粗主题承担；
   - 远端符号引用 `*/HEAD` 不画；
   - 徽标按 kind 优先级和名称稳定排序，空间不足时显示 `+N`。
3. summary 模式中，仅 `on_head=False` 的提交主题使用主题已有的 `muted_text`；`on_head=True` 或 `None` 使用 `text`；HEAD 行继续加粗。
4. 鼠标悬停或选中不在 HEAD 历史中的行时，主题恢复正文色，避免弱化色影响阅读；移出后恢复弱化。
5. 徽标不能挤掉主题：单个徽标超长时中间省略，徽标区最多占提交列的一部分宽度，主题至少保留可读的省略空间。
6. 整行 tooltip 按三态增加“范围：HEAD 可达”“范围：不在 HEAD 历史中”或“范围：未知（HEAD 可达性获取失败）”，并保留现有 refs 明细。
7. 取数失败（unborn HEAD、`rev-list` 错误或超时）时，所有行按 `on_head=None` 处理：保持正文色并显示范围未知，不抛异常、不增加弹窗，绝不把未知误报为 HEAD 可达。
8. 主题切换、字号变化、resize、悬停重绘都不得新增 Git 查询。
9. 不改变 graph lane 几何、节点/边颜色、完整弹窗四列、500 条截断和富文本降级。

## 4. 方案决策

### D1 数据层：一次 `git rev-list HEAD` 计算三态可达集合

在 `CommitRow` 增加字段：

```python
on_head: bool | None = None
```

`fetch_commit_rows()` 在解析完所有行、计算 graph rows 之后，执行一次：

```python
reachable = runner.run_git(repo_root, "rev-list", "HEAD")
head_ids = set(reachable.split()) if reachable is not None else None
```

然后：

```python
on_head = None if head_ids is None else commit_id in head_ids
```

理由与约束：

- 只需要一次子进程，避免逐行 `merge-base --is-ancestor` 的 500 次调用；
- `rev-list HEAD` 输出的是完整 commit id，和 `CommitRow.commit_id` 可直接做集合判断；
- 失败返回 `None` 时所有行保持未知，视觉不变且 tooltip 不谎报；
- detached HEAD 下 `rev-list HEAD` 仍然有效；空仓库会在既有空输出分支返回，但仓库已有其他 refs、当前 HEAD unborn 时仍可能取得 `--all` 行，必须走未知 fallback；
- `rev-list HEAD` 遍历并输出**完整 HEAD 历史**，开销不受页面 500 行上限约束，且当前调用位于同步加载链路，不能仅以“只展示 500 行”推断性能安全。

本期默认保留直观的 `rev-list HEAD`，但实施时必须用项目内构造的大历史仓库（建议至少 1 万提交）记录新增取数耗时，并验证超时只影响弱化、不影响提交图加载。若接近或达到 `runner.TIMEOUT_S` 的 2 秒上限，或出现可感知阻塞，不得把静默 fallback 当作性能验收通过；应先重新评审有界取数、反向集合或后台加载方案。

`git rev-list --all --not HEAD` 与当前集合判断语义等价，在当前仅有 5 个旁支提交的场景下输出更小，但非 HEAD 历史很大时反而更差，不能未经测量直接替换。

500 条截断只影响已加载行；未加载的父提交不生成行、不参与展示判断，保持现有图边界语义，但仍可能包含在完整 `rev-list` 遍历中。

### D2 展示层：summary 页补画紧凑 refs 标签

`CommitRow.refs` 已经包含 `RefBadge(kind, label)`，数据层无需新增取数。展示层新增一个可复用的徽标绘制方法：

```python
def _paint_ref_badges(
    self, painter, rect, fm, badges, *, compact: bool
) -> int:
    """返回实际占用的宽度；compact 用于 summary，full 用于完整弹窗。"""
```

完整模式继续使用现有 `hash + refs + 主题` 顺序；summary 模式使用 `refs + 主题` 顺序，复用同一套 `_badge_colors`、圆角、底色/边框 alpha 和文字基线，避免两套配色漂移。

#### D2-a 显示哪些 refs

summary 的过滤规则：

1. 丢弃 `head`：HEAD 行已有双圆 + 加粗主题，再画 `HEAD` 徽标是重复信息；
2. 保留全部 `branch`、`tag`；
3. `remote` 仅在该行没有任何 `branch`/`tag` 时保留；这样 `main` 不会再显示 `origin/main`，但只有远程分支的提交仍能看到归属；
4. 丢弃远端符号引用 `*/HEAD`（如 `origin/HEAD`），它是默认分支别名，不是独立分支；
5. 过滤后按 `kind` 优先级（branch → tag → remote）+ `label` 排序，保证同一 commit 多标签时顺序稳定。

完整弹窗继续显示全部 refs，包括 `origin/main` 和 `origin/HEAD`；summary 的过滤不污染完整模式。

#### D2-b 徽标布局

以下紧凑布局只作用于 summary：

- 徽标高度取 `max(14, fm.height() - 2)`，不超过行高；
- summary 使用更紧凑的 `hpad=4`、`gap=4`；完整模式保持现有 `_BADGE_HPAD=7`、`_BADGE_GAP=5`；
- 单个徽标宽度上限取提交列宽的一定比例（实现时按字体度量定，建议 45%），文字用 `ElideMiddle` 中间省略，保留分支名前缀和后缀；
- 徽标区最多占提交列宽减去主题最小可读宽度；放不下的徽标不再硬塞，改画一个 `+N` 徽标（使用 `muted_text` 配色）；
- 主题从徽标区右侧开始，按剩余宽度 `ElideRight`，不换行、不增加行高；极窄列不得产生负宽度，必要时不画徽标而优先保留主题省略文本。

完整模式继续按原 refs 顺序、原尺寸和现有空间不足停止逻辑绘制，不新增过滤、排序、省略或 `+N`，避免共享 helper 的抽取改变完整弹窗行为。

#### D2-c 与 HEAD、弱化、悬停的关系

- HEAD 行：主题加粗、节点双圆；如果有本地分支徽标，正常显示该分支名；
- `on_head=False` 行：主题弱化，但 refs 徽标保持全色，引用位置仍然醒目；`on_head=None` 行不弱化；
- 悬停/选中行：主题恢复正文色；徽标不变；
- 没有 refs 的行：主题从原位置开始，和当前布局一致。

**为什么不把 refs 画到图形列：** 图形列是固定宽的拓扑通道，徽标会破坏 lane 几何和横向滚动；分支名属于文本列，应该和主题一起排版。

**为什么 summary 过滤远程重复项：** 窄面板里 `main` 和 `origin/main` 并排会迅速吃掉主题宽度，而两者在当前分支场景下是同一提交的两种引用；完整弹窗仍保留全部明细。

### D3 展示层：只弱化 summary 主题文本

`CommitColumnDelegate` 已有 `_muted_color`（来自 `palette["muted_text"]`），直接复用，不新增主题令牌。

summary 分支的取色规则必须显式判断 `False`，不能对 `None` 使用真值取反：

```python
dimmed = row.on_head is False and not hovered and not selected
painter.setPen(self._muted_color if dimmed else self._text_color)
```

- HEAD 行 `is_head=True` 时仍然加粗；可达性成功时 HEAD 行必为 `on_head=True`，失败时为 `None` 也不弱化。
- 长主题省略、左右内边距、行高不变。
- 悬停/选中时用正文色，保证用户查看具体提交时可读。

**为什么不弱化图形列：** `GraphRow.edges` 里的 `pass-through` 边可能属于当前 HEAD 的 lane；如果按行统一降低透明度，会把属于 HEAD 的过路线也一起压暗，反而破坏拓扑信息。本次只弱化提交主题文本，lane 颜色和几何保持原样。

**为什么不弱化 refs 徽标：** 徽标是引用位置的主要线索，尤其对非 HEAD 分支 tip；压暗徽标会抵消本次修复的意义。徽标不声称所在行具有唯一分支归属。

**为什么不改完整弹窗：** 完整弹窗已经绘制 hash、refs、作者、时间，可直接查看引用位置；本次只修复内嵌 summary 页的误读。完整弹窗共享 tooltip 的三态范围说明，但不弱化提交主题；若后续确认也需要弱化，再单独立项。

### D4 tooltip 补充三态“范围”

`CommitGraphModel.data()` 的 `ToolTipRole` 末尾按 `row.on_head` 追加以下三种文案之一：

```text
范围：HEAD 可达
范围：不在 HEAD 历史中
范围：未知（HEAD 可达性获取失败）
```

`True`、`False`、`None` 与三行文案一一对应。这样既避免 detached HEAD 下“当前分支”措辞失真，也不把 tag-only、stash 等引用到达的提交武断归为“其他分支”。同时保留现有 refs 明细，summary 过滤掉的远程重复项仍在 tooltip 中可见。

### D5 视觉与主题

- 弱化色直接使用各主题已有的 `muted_text`，四套主题（cloud / wheat / sky / mint）分别验收对比度；
- refs 徽标沿用 `git_graph` 资源包的 branch/tag/remote 颜色，不新增令牌；
- 不新增 QSS，不改变现有选中/悬停背景；
- 选中行、悬停行的正文色优先于弱化色，避免交互态发灰；
- 徽标底色/边框在 summary 可略低于完整模式（如 0.10/0.35），但保持同一色相。

## 5. 实施步骤

### T1 数据层标记三态 on_head

1. `CommitRow` 增加 `on_head: bool | None = None`，放在 `is_head` 附近，保持关键字构造兼容；默认未知可避免手工构造行被误报为 HEAD 可达。
2. `fetch_commit_rows()` 增加一次 `rev-list HEAD` 取数，构造行时写入三态 `on_head`。
3. 失败时 `head_ids=None`，所有行保持 `None`；不抛异常、不增加弹窗，提交图仍正常展示。
4. 确认 `replace(row, graph_row=...)` 不会丢掉 `on_head`。
5. 按 D1 记录大历史仓库的新增取数耗时；若触发性能门槛，先调整方案再进入视觉验收。

### T2 summary 页补画 refs 标签

1. 从完整模式抽取出 `_paint_ref_badges()`，保留现有完整模式行为；full 用 `compact=False`，summary 用 `compact=True`。
2. 增加 summary 的 refs 过滤/排序函数，按 D2-a 规则处理 `head`、`branch`、`tag`、`remote`、`*/HEAD`。
3. summary 分支先画徽标，再画主题；徽标区宽度受限，超出显示 `+N`，主题使用剩余宽度省略。
4. 徽标配色复用 `_badge_colors`；`+N` 使用 `muted_text`；不新增主题键。
5. 确认无 refs 行、长主题、超长分支名、多个标签、只有远程分支和极窄列等边界不越界、不换行、不改变行高。
6. 过滤、排序、省略和 `+N` 不得泄漏到 full；完整弹窗的 refs 顺序、尺寸与溢出行为保持原样。

## 6. 验证命令与通过标准

```bash
.venv/bin/python -m pytest tests/test_git_graph_lanes.py tests/test_git_graph_view.py tests/test_git_graph_panel.py -q
bash scripts/check.sh
```

必须同时满足：

1. `main` 与 `test/新分支` 的线性场景中，tip 行显示全色 `test/新分支` 徽标，`577e9b4` 行显示 `main` 徽标；`test/新分支` 的 5 个空提交主题全部为 `muted_text`，`577e9b4`（HEAD/main）为主题正文色并加粗；
2. 同一 commit 的 `origin/main` 不在 summary 重复出现，但完整弹窗仍显示；只有远程分支的提交在 summary 仍能看到远程名；真实符号引用 `origin/HEAD` 不在 summary 显示；
3. 真分叉/合并场景中，HEAD 可达提交不弱化，未合并分支提交弱化，泳道几何和颜色不变；
4. 悬停/选中非 HEAD 行时主题恢复正文色，移出后恢复弱化；徽标始终全色；
5. 超长分支名/多标签时显示 `+N`、中间省略，主题不被挤没，行高不变化；极窄列无负宽度或越界绘制；
6. `rev-list HEAD` 失败或 HEAD unborn 时所有行保持正文色，tooltip 明确显示范围未知，无异常、无额外弹窗，且不触发提交图降级；
7. 大历史性能测量未达到 2 秒超时或可感知阻塞门槛；若达到门槛，已先完成替代方案评审，而不是以 fallback 掩盖性能问题；
8. 主题/字号/resize/悬停不触发新的 Git 查询；
9. 完整弹窗、500 条截断、富文本降级、空仓库/非仓库占位无回归；
10. 聚焦测试与 `bash scripts/check.sh` 全绿。

## 8. 非目标

- 不按分支拆泳道，不为每个 ref 强开一条 lane；
- 不计算或展示每个提交的完整、唯一分支归属；
- 不在 summary 页恢复 hash、作者、时间或完整四列；
- 不新增分支列表、分支过滤器、checkout 或其它 Git 写操作；
- 不改变完整弹窗的四列布局、refs 顺序、尺寸、溢出行为和配色，不弱化完整弹窗主题；
- 不改变 Theia 泳道算法、三类边几何、500 条上限、刷新边界和富文本降级；
- 不为标签/弱化新增主题令牌或 QSS 模板改动；
- 不对未加载的父提交做额外可达性查询或补行。
