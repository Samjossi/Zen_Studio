## 1. 背景与症状

kimi 系后端的待办清单工具名为 `TodoList`（kilocode/opencode 系为 `todowrite`）。截图实证：该工具当前渲染为普通 McpCard——入参区一段 `todos: [{...}]` JSON 原文，出参区一段 `[done]/[in_progress]/[pending]` 纯文本，**人类无法一眼看清进度**（哪项在做、哪项已完成、整体 x/y）。

| # | 痛点 | 场景证据 |
|:---|:---|:---|
| S1 | **清单以 JSON 原文呈现**：状态枚举嵌在引号与花括号里，人类需逐行解码 | 截图：TodoList 卡入参 `todos: [{"status": "done", ...}]` |
| S2 | **无进度总览**：完成度（2/6）需人类自行点数；出参 `[done] ...` 文本与入参 JSON 信息重复但都不直观 | 截图：出参 "Current todo list" 文本块 |
| S3 | **增量更新无感知**：agent 每次调用 TodoList 推进状态，前后快照差异（哪项刚完成、哪项新开始）淹没在整段 JSON 里 | TodoList 工具的典型调用模式（一轮多次调用） |

根因（代码实证）：kimi 系**首帧空壳**——`_map_tool_call`（`acp.py:730`）首帧 `rawInput` 为空，不命中 `raw.todos` 特判，落成普通工具卡；`todos` 随 in_progress update 帧迟到，经 0806 计划 T1 迟到入参回填机制落入入参区（`"other"` kind 白名单含 `"todos"` 键，`acp.py:496`），**永远以 JSON 文本形态上屏，到不了任何可视化通路**。

诉求：**TodoList/todowrite 工具的每次调用渲染为一张独立的清单卡**（状态图标 + 删除线 + 进度计数 + 相对上次调用的变更高亮）——最新快照永远在对话流底部（人的视线路径），历史快照逐卡留痕可回溯。仅供人类查看（不回传 AI、不改协议语义）。

## 3. 参考调研：kilocode 的 todo 渲染链

kilocode（opencode fork）的 todo 可视化由四层组成，逐层拆解并标注对本计划的借鉴价值：

### 3.1 服务端增量视图计算 —— `packages/opencode/src/kilocode/todo-view.ts`

工具 execute 内对**前后快照做 diff**，随 metadata 下发 `view`：

- `TodoView.calculate(before, after)`：逐项比对（`same()` 口径 = content + status + priority 全等），产出 `changed` 标记数组；`before` 取**会话当前 todo 状态**（跨调用 diff，非调用内帧间 diff）；
- **compact 模式**：非结构性变更（长度不变、各项 content 未改）且非全完成时，只下发"变更项 ± 1 上下文"窗口，`hiddenBefore`/`hiddenAfter` 记录折叠数；结构性变更/首帧/全完成 → 回退 full 全量。

**借鉴**：`same()` 比对口径、changed 标记语义、**跨调用 diff 的 before 口径**（本计划协议层复刻，见 T1）。**compact 折叠**：R1 裁决翻转后本计划同样是"每次一卡"的多卡场景，compact 成为对口的降噪手段——但本期不做（先保证每张卡全量 + 高亮可用；若实测一轮多次调用刷屏，再按 `calculate()` 的窗口算法追加，列为 §7 远期）。

### 3.2 Webview 渲染 —— `packages/kilo-ui/src/components/message-part.tsx:2929-2993`

- 数据源回退链：`metadata.view.todos` → `metadata.todos` → `input.todos`；
- 标题副标题 `x/y`（completed/total）；
- 条目：只读 Checkbox + content；`data-completed` 删除线弱化、`data-changed` 高亮（变更项醒目）；
- compact 时前后各一行 "N earlier/later to-dos hidden"。

**借鉴**：副标题 x/y（TodoCard 已有 N/M）、**data-changed 变更高亮**（本计划核心增量点）。

### 3.3 TUI 渲染 —— `packages/tui/src/component/todo-item.tsx` + `routes/session/index.tsx:2823-2847`

- 条目标记：`[✓]` completed / `[•]` in_progress（警告色）/ `[ ]` pending——与 Zen_Studio ☑/▶/☐ 同构；
- 数据源同样 metadata 优先、input 兜底。

**借鉴**：状态色语义（in_progress 用醒目色，TodoCard 当前 in_progress 不着色，可补）。

### 3.4 会话级聚合 —— `TaskHeader.tsx` + `context/todo-revert.ts`

- `todo-revert.state()`：取**最后一次** todowrite 的快照作会话当前 todo 状态（支持 revert 截断）；
- TaskHeader 常驻显示 `{{done}}/{{total}} 个待办已完成`，展开为全列表。

**借鉴**：会话级常驻进度指示的形态。**不照搬**：Zen_Studio 无对应面板位；"最近一次调用即当前状态"的语义由多卡路线天然承担（底部最新卡 = 当前状态）。列为远期可选（§7 展望）。

### 3.5 状态通道 —— `todo.updated` 事件 + `/session/:id/todo` REST

todo 状态与消息流解耦，服务端持有、客户端订阅。**不借鉴**：ACP 协议无此通道，Zen_Studio 数据源只能是工具调用载荷本身。

## 4. 方案对比与裁决（R1 翻转）

| 维度 | kilocode | Zen_Studio 现状 | 本计划裁决 |
|:---|:---|:---|:---|
| 卡片生命周期 | 每次 todowrite 一张新卡（历史留痕） | 单卡就地整刷（位置不变性，弃锚点） | **每次调用一张新卡**（R1 翻转，理由见下） |
| 增量数据源 | 服务端 diff（execute 内 TodoView.calculate）随 metadata 下发 | 无 diff，快照整刷 | **协议层 diff**（对齐 kilocode 架构位 + 「协议层单点处理，GUI 不碰差异」纪律）：检出 todos 时与上次快照比对，changed 标记随载荷下发（比对口径抄 `same()`：content+status+priority） |
| changed 呈现 | data-changed 属性高亮 | 无 | **新增**：变更项醒目色（tool_fg 或主题 accent），in_progress 项恒醒目（对齐 TUI 警告色语义） |
| 进度计数 | 副标题 x/y | 已有 N/M 副标题 | 复用 |
| 首帧空壳迟到 | 无此问题（工具载荷首帧齐备） | todos 漏网进入参 JSON | **update 帧检出 + 载荷回填**（0158 media_path 同范式） |
| 通道归一 | 单通道（todowrite 工具卡即清单卡） | 双通道（kind="todo" 会话卡 + 工具卡 JSON） | **归一**：撤销首帧特判，todowrite/TodoList 一律走 TodoListCard；kind="todo" 只剩 plan 通道 |

### 裁决 D1：卡片生命周期——每次调用一张新卡（R1 翻转定案）

**翻转理由（审阅意见采纳）**：
1. **视线路径**：人的阅读位置恒在对话流底部。单卡整刷的看板会被后续工具卡/正文推向上方，最新进度不在视线内；每次一卡让**最新快照永远在底部**；
2. **历史留痕**：第 1 次调用与第 3 次调用的清单各自定格，可回溯审计进度推进轨迹；单卡整刷只剩最终态；
3. **协议天然支持**：每次 TodoList/todowrite 调用在 ACP 帧流里本就是独立 `toolCallId` 的独立调用——走此路线不是"拆帧"，而是**停止合并**（撤销我们自加的首帧特判即可），ACP 无任何阻碍。

**改道范围**：`_map_tool_call` 的 `raw.todos` 特判仅捕获 todowrite/TodoList 工具调用；`sessionUpdate: "plan"` 通道（`acp.py:912-915`）**不动**——plan 是无 toolCallId 的会话级快照流，天然只能单卡就地更新，TodoCard/旧轨锚点块/timeline todo 色块保留给该通道。

**被否案（原案 A，存档备查）**：保留特判 + 仅补 update 帧检出 + 工具卡内嵌清单。被否原因：看板位置随对话流上移，违背人的视线路径；且双写两条渲染通路。

## 5. 修复方案

按"协议层 → 渲染层 → 验证"推进，共三个任务。

### T1：协议层 `todos` 载荷 + 跨调用 diff（`llm/providers/acp.py` + `llm/base.py`）

**改动点 1 — 首帧特判撤销**：`_map_tool_call` 删除 `raw.todos` 改产 kind="todo" 的分支（`acp.py:730-733`），todowrite/TodoList 回归普通工具卡流程；首帧即带 `rawInput.todos` 时（kilocode 系形态）提取装入 `ToolCallPayload["todos"]`，走改动点 3 的 diff 管线。

**改动点 2 — update 帧检出**：`_map_tool_call_update` 中（迟到入参回填段同位，`acp.py:802` 附近），`rawInput.todos` 为 list 时经既有 `_extract_todo_entries` 提取装入 `ToolUpdatePayload["todos"]`，走同一 diff 管线。**每帧都提、不设去重账本**：todo 语义是快照推进（与 input_detail/media_path "首帧优先" 语义不同）。

**改动点 3 — 跨调用 diff（kilocode TodoView.calculate 复刻）**：

```
_last_todo_snapshots: dict[str, list[TodoEntry]]  # 键 = sessionId（map_session_update 可从 params 取），防跨会话/跨标签快照串联误标

def _apply_todo_diff(session_id, entries) -> list[TodoEntry]:
    before = _last_todo_snapshots.get(session_id) or []
    逐项比对（same 口径 = content+status+priority 全等，kilocode todo-view.ts:60-63）：
    不一致项 entry["changed"] = True
    _last_todo_snapshots[session_id] = entries
    return entries
```

- before 口径 = **会话当前 todo 状态**（跨调用 diff，非调用内帧间）——同次调用的多帧快照幂等（内容相同则 changed 全 False，自然消退）；
- changed 只是高亮标记，错标无害（降级方向安全）；簿记随会话惰性增长，条目极少（会话级单值），暂无清理钩子（同 `_input_detail_seen` 终态清理先例，可在终态帧顺带保留——快照跨轮连续，不按帧清理）；
- 契约同步（`llm/base.py`）：`ToolCallPayload`/`ToolUpdatePayload` 各增补 `todos: list[TodoEntry]` 可选字段；`TodoEntry` 增补 `changed: bool` 可选字段，docstring 注明"相对上次快照的变更标记（协议层 diff 产物，渲染层高亮数据源，仅供人类查看，不回传）"。

**改动点 4 — 回执过滤扩展**：`_RECEIPT_RES`（`acp.py:199-200`）增补 kimi 模板 `Current todo list` 块（多行块：该行及其后 `[status] ...` 连续行整体剔除）——清单区渲染后出参回执与清单信息完全重复。误伤正常输出的风险见 §7。

**改动点 5 — 新轨放行**：`panel.py:_allow_progress_frame` 增补 `payload.get("todos")` 放行条件（与 input_detail/images 同位，0158 先例 `panel.py:957`）——否则 in_progress 帧载荷到不了卡片。旧轨冻结不消费该字段（旧轨纪律；旧轨随之改道的行为退化见 §7）。

### T2：渲染层 `TodoListCard` 专用卡（`gui/panels/chat/cards.py`）

0806/0158 的"工具名二级分派 + 专用卡"范式第四次套用；**每次调用一张新卡由工具卡机制天然承担**（`append_tool_call` 每 `toolCallId` 建一卡），无需任何拆分逻辑：

| 设计点 | 决策 |
|:---|:---|
| 分派 | `_TOOL_NAME_CARDS` 增补 `"todolist": TodoListCard`、`"todowrite": TodoListCard`（归一化机制既有） |
| 继承 | 继承 `McpCard`（入参/出参两节保留——出参经 T1 改动点 4 过滤后仅剩非回执内容，缺省不挂） |
| 清单区位置 | 入参区与出参区之间（阅读顺序：调用 → 清单 → 回执） |
| 条目渲染 | 提取 TodoCard 条目绘制为共享函数（☑/▶/☐ + 完成项灰化删除线 + `_ElidedLabel` 长文本省略 + N/M 计数），TodoListCard 与 TodoCard（plan 通道）共用，无双写 |
| changed 高亮 | **消费载荷 `changed` 标记**（协议层 diff 产物，渲染层不自行比对）：变更项以 tool_fg 醒目色 + 非变更项常规色区分；in_progress 项恒醒目（对齐 TUI 警告色语义） |
| 入参区 todos 抑制 | 清单区已渲染时，入参区 `todos:` JSON 行**抑制显示**（信息重复；其余入参键照常）——抑制点在 ToolCard `_set_input_detail` 层做键过滤还是载荷层分流，实施时按最小侵入定 |
| 副标题 | 卡标题行副标题 `— x/y 项完成`（与 TodoCard 同款表述），随快照整刷更新 |
| 回填钩子 | 覆写 `apply_update`：载荷带 `todos` 即整刷清单区（幂等；首帧空壳场景清单随迟到帧出现） |
| 空清单防御 | `todos: []` 提取为空列表 → 清单区不建（静默降级，入参 JSON 亦不再抑制——无可视化则保留原文兜底） |

**timeline 说明**：todowrite/TodoList 改道后按普通工具调用上条（每次调用一个色块，天然留痕，与 kilocode 每 part 一条一致）；`_feed_todo` 保留给 plan 通道，不改代码。
