> **范围**：kimi-acp 后台模型目录（`src/llm/providers/kimi_common.py`、`src/llm/registry.py`）、ModelBar（`src/gui/panels/chat/model_bar.py`）、强度记忆（`src/gui/panels/chat/tabs.py`）、维护手册与测试

## 需求

用户反馈 Kimi CLI 上线新模型。经官方文档与本机 CLI 双重核实**属实**：

- 官方模型配置页（https://www.kimi.com/code/docs/en/kimi-code/models.html ）已上线 K3.1 Pro 系列，全站模型 ID 由 4 个扩为 6 个；
- 本机 kimi CLI 2.0.0 的 `/model` 列表已含 K3.1 Pro / K3.1 Pro Highspeed（用户截图佐证，2026-10-24）。

| 模型 ID | 版本 | 要点 |
|---|---|---|
| `k3.1-pro` | K3.1 Pro（新） | 3T 级旗舰，1M 上下文（高档位会员），**仅 thinking 模式**（关闭直接 HTTP 400），effort `low`/`high`/`max` 默认 `max`，图像+视频输入；新计划 Plus 及以上 |
| `k3.1-pro-highspeed` | K3.1 Pro Highspeed（新） | 同能力高速版，约 2~3× 速度、约 2× 额度消耗；新计划 Pro 及以上 |
| `k3` / `k3-256k` | K3 | 现状不变 |
| `kimi-for-coding` / `kimi-for-coding-highspeed` | K2.8 Preview / K2.7 Code Highspeed | 现状不变 |

官方使用建议与本项目相关的三条：K3.1 Pro 仅 thinking；切换新模型建议开新会话（切模型/切档位会使上下文缓存失效）；第三方调用须用模型 ID，误填会静默回退 K2.8 Preview 无思考。

## 关键探查结论（步骤 1 实测，2026-10-24）

实测环境：本机 CLI 位于 `~/.kimi-code/bin/kimi`（不在 PATH，项目 `_find_bin` 的 fallback 链 `~/.kimi-code/bin` 可正常探测，IDE 可用性判定不受影响），版本 **2.0.0**。原始载荷存档 `.temp/kimi_provider_list_20261024.json`（`kimi provider list --json` 直出）。

- **两个新模型目录字段齐全**，无需 overrides 过渡（当年 `kimi-for-coding` 靠 config.toml `[models.…overrides]` 固定元数据是 managed 刷新前的过渡手段，本次服务端目录本即为新，条目无 `overrides` 子表）：

| 别名 | maxContextSize | displayName | supportEfforts | defaultEffort | capabilities |
|---|---|---|---|---|---|
| `kimi-code/k3.1-pro` | 1048576 | K3.1 Pro | low/high/max | **max** | thinking, **always_thinking**, image_in, **video_in**, tool_use, dynamically_loaded_tools |
| `kimi-code/k3.1-pro-highspeed` | 1048576 | K3.1 Pro Highspeed | low/high/max | **max** | 同上 |

  `always_thinking` 即官方「仅 thinking」的目录级佐证；`video_in` 意味着 k3.1-pro 补上了 k3-256k 缺位的视频输入能力。

- **IDE 三路派生实测全通过**（项目 `.venv` 直跑解析函数对真实载荷）：
  - `models_from_catalog` → 6 个别名，菜单序（sorted）：`k3 → k3-256k → k3.1-pro → k3.1-pro-highspeed → kimi-for-coding → kimi-for-coding-highspeed`；
  - `efforts_from_catalog` → `k3.1-pro` / `k3.1-pro-highspeed` 均为 `(['low','high','max'], 'max')`，模型级档位自动正确；
  - `display_names_from_catalog` → `K3.1 Pro` / `K3.1 Pro Highspeed` 显示名到位。
- **结论：情况 A 成立，IDE 生产代码零改动**。CLI 2.0.0 目录下发后，ModelBar 三级菜单自动出现新模型，四级档位自动取目录默认 `max`。
- **强度记忆行为细节（如实记录，不改）**：`model_efforts` 记忆表键为接口 → 值，无接口+模型复合键（`src/gui/panels/chat/tabs.py`）。本机 `config/settings.json` 现存 `"kimi-acp": "high"`，切到 k3.1-pro 后该记忆值在新模型值域内 → **实际生效 `high` 而非目录默认 `max`**；用户想要 max 需在四级菜单显式选一次（写盘覆盖）。这属既有「用户显式选择优先」语义，不视为缺陷。
- **「仅 thinking」约束无冲突**：IDE 强度轴只暴露 `low/high/max`，无 `off` 入口，不会触发官方所述「关闭思考被 HTTP 400 拒绝」的路径。
- **ModelBar 短文本通用**：模型别名取 `/` 末段（`kimi-code/k3.1-pro` → `k3.1-pro`），显示名走 `list_display_names` 菜单全文，无需改码。
- **上下文上限无静态表**：kimi 不经 `src/llm/context_limits.py`，用量徽章上限读 wire.jsonl `llm.request.maxTokens` 随会话直给；目录 `maxContextSize` 已达 1048576，徽章是否显示 1M 取决于账号档位（高档位会员才开放 1M），需实测。
- **kilocode-acp 已封存**（`src/llm/registry.py` `archived=True`，`维护手册/后端CLI工具维护说明手册.md` §3），不在本次验证范围；opencode-acp 的 kimi 模型来自 models.dev 缓存，K3.1 Pro 透出与否仅记录结论不改码。
- **维护手册过期**：`维护手册/模型Token单价对比手册.md` 的 kimi-acp 模型清单与定价表均未含 K3.1 Pro 系列；`维护手册/后端CLI工具维护说明手册.md` §1 模型备注停留在 2026-09-17（K2.8 Preview）。

## 默认行为决策

- **默认模型不变**：`config/settings.json` 持久化默认仍为 `kimi-code/k3-256k`；新模型由用户经 ModelBar 显式切换，既有「切换下次请求生效」语义不动（缓存失效属服务端行为，IDE 不额外干预；官方「开新会话」建议转达为用户侧使用建议，不在 IDE 强制）。
- **不做静态兜底**（D1 纪律沿用）：目录字段已实测齐全，无需兜底讨论；若日后 CLI 升级致字段漂移，按「无强度轴」呈现并留痕，不手写档位。
- **强度记忆不改键结构**：不为 K3.1 Pro 引入接口+模型复合键；记忆值 `high` 在新模型上继续生效属既有语义，文档如实告知即可。
