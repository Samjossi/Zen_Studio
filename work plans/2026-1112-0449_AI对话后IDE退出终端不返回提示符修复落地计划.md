# AI 对话后 IDE 退出终端不返回提示符修复落地计划

> **状态**：草稿
> **范围**：主程序退出、聊天面板与 ACP Provider 清理、Agent 子进程回收、对话后提示音与桌面通知子进程、退出验证
> **时间**：2026-11-12 04:49（设计，UTC+8）
> **优先级**：高

## 需求

1. 无论是否发生过 AI 对话，用户关闭 IDE 后，启动 IDE 的终端都应自动返回 Shell 提示符，可直接继续输入，不依赖 `Ctrl+C`。
2. IDE 退出必须同时完成其所拥有的 ACP Agent、通信资源、聊天 Worker 及相关子进程的清理，不能只关闭窗口或只打印“退出完成”日志。
3. 正常退出应有界、幂等且保持 GUI 可响应；Agent 无响应时允许按既定超时强制结束，但不得无限等待。
4. 不改变对话中的长驻 Agent 复用机制，不用模拟 `Ctrl+C`、伪造提示符或无差别杀进程掩盖问题。

## 已知事实与待证假设

### 已核实现状

- 用户对照现象明确：未进行 AI 对话时可以直接退出并返回提示符；完成 AI 对话后，日志出现“Zen Studio 退出”和“Zen Studio 进程收尾完成”，终端仍不返回提示符。复现日志包含 `dsh_acp` Agent、任务完成提示音和桌面通知。
- `main.py` 在 `app.exec()` 返回后记录退出码，启用 10 秒线程栈看门狗，再经 `sys.exit()` 进入 Python 收尾；“进程收尾完成”来自 `atexit` 钩，只代表已执行的收尾钩运行到该位置，不能替代 Shell 对进程退出的确认。
- `src/ide/gui/panels/chat/panel.py` 的标签清理由 daemon 线程执行：先关闭 Provider，再有界等待 Worker；该路径没有向主程序提供整体完成确认。
- `src/ide/llm/providers/dsh_acp.py` 已注册 `atexit` 并调用公共 `AcpConnection.terminate()`；`src/ide/llm/providers/acp.py` 已实现 `terminate()`、5 秒等待和超时 `kill()`，因此不能把“完全没有 Agent 关闭代码”当作根因。
- `AcpConnection.terminate()` 的强制 `kill()` 后没有再次 `wait()`，也未集中关闭 stdin/stdout；这些是需要验证和补齐的资源边界，但仅凭源码尚不能认定它们就是本次终端不返回的直接原因。
- `src/ide/gui/main_window.py` 的 `closeEvent()` 当前只保存布局和会话，没有显式协调 AI 清理完成；最终退出还依赖 Qt 对象销毁和 `atexit` 兜底。
- 对话完成后还会启动 `aplay` 和 `notify-send` 短生命周期子进程；二者均由模块列表持有并轮询回收，但尚无证据排除其对特定退出时序的影响。

### 根因假设，不得跳过验证

| 分支 | 关闭后观察结果 | 优先排查方向 |
|---|---|---|
| A | IDE 主 PID 仍存活 | `atexit` 之后的 Python/Qt 析构、Worker 或清理线程、Provider 关闭阻塞、第三方库收尾 |
| B | IDE 主 PID 已消失，Agent 或其他子进程仍存活 | 子进程所有权、终止信号、强制结束后的回收、进程树与管道继承 |
| C | IDE 与已知子进程均消失，终端仍无提示符 | 终端启动/等待方式、Shell 前台进程组、外层包装进程；不得继续只改 Provider |
| D | 仅在特定 Provider、对话状态或通知开启时复现 | 按最小触发条件定位对应资源，不把 DSH 现象直接推广到所有后端 |

## 设计决策

- **先证实进程层级，再改代码**：以“主进程是否仍在、哪个子进程仍在、卡在哪个线程/等待点”为分流依据；一轮复现只能证明该轮状态，至少重复对照未对话与已对话两组。
- **显式退出为主，`atexit` 为兜底**：在现有窗口/聊天标签销毁路径上形成明确的应用退出清理阶段，记录开始、各阶段完成与失败；`atexit` 保留给异常路径，不作为正常退出的唯一协调者。
- **只管理 IDE 自己创建的资源**：使用已有 Provider、Worker、`Popen`/PTY 对象及其实际 PID 收口，禁止按进程名模糊匹配，禁止无差别终止用户进程组。
- **关闭顺序保持可唤醒**：停止接收新任务，取消活跃轮次，关闭 Provider/Agent 以解封 Worker，再有界等待 Worker；保持现有“先 Provider、后 Worker”的顺序，不倒置成先等 Worker。
- **正常路径不依赖 daemon 线程恰好跑完**：应用最终退出前须获得清理完成状态；等待必须有界，超时走明确降级并记录，不得永久卡住 GUI 或主进程。
- **公共问题公共修**：若根因位于 `AcpConnection`，修复应对所有 ACP Provider 生效；若仅 DSH 可复现，则保留公共行为，只在 DSH 的特有生命周期处修正。
- **日志区分阶段与事实**：窗口关闭、事件循环退出、清理钩完成、操作系统进程消失分别表述；不再用单条“收尾完成”暗示 Shell 已可回收终端。

## 实施步骤

### 1. 建立可重复的诊断样本

- 使用项目 `.venv` 从外部终端启动 IDE，记录启动 PID、所用后端、对话状态和通知/提示音设置。
- 至少覆盖两组最小对照：启动后不对话直接关闭；启动后完成一轮 DSH 对话再关闭。关闭后先等待现有 10 秒看门狗输出，不要立即按 `Ctrl+C`。
- 从第二终端用 `ps` 查看主 PID、父子关系、进程组与状态；保存看门狗线程栈和退出日志，诊断产物放入 `./.temp/`。
- 若主 PID 仍存活，补充各清理阶段的进入/退出日志，定位最后一个已完成阶段与首个未返回阶段；若主 PID 已消失，转查残留子进程和终端等待链。
- 用“关闭声音/通知后是否仍复现”“仅创建 Agent 未完成对话是否复现”“其他 ACP 后端是否复现”缩小变量；这些对照用于定位，不作为最终规避方案。

**检查点**：能用进程状态和线程栈从 A/B/C/D 中确定实际分支，并指出具体卡点；在此之前不提交推测性退出重构。

### 2. 收口应用级退出协调

- 在 `src/ide/gui/main_window.py`、聊天标签容器与 `src/ide/gui/panels/chat/panel.py` 的现有销毁挂点之间明确应用关闭路径：保存状态后触发所有已建聊天面板/Provider 清理，而不是只保存布局后等待隐式析构。
- 复用 `_close_providers()`、`_cleanup_blocking()` 等现有能力，不另建第二套 Provider 注册表；补充可供应用退出等待的完成信号、事件或有界等待结果。
- 保证清理入口幂等：标签单独关闭后再退出应用、多个聊天标签、切换过后端、未实例化 Provider 等场景不得重复终止、重复销毁或死锁。
- 清理期间禁止新建会话和迟到连接，继续利用 Provider 的 `_closed` 双检；清理线程不得在窗口销毁后访问失效 Qt 对象。
- 若诊断证明卡点不在应用协调层，本步只做证实缺失所必需的最小调整，不借本计划重写聊天架构。

### 3. 补齐 ACP 进程与通信资源退出边界

- 依据诊断检查 `src/ide/llm/providers/acp.py`：正常 `terminate()`、5 秒超时、`kill()` 后必须最终 `wait()` 回收，并保证重复调用安全。
- 明确关闭 Agent stdin/stdout 的时机，使 reader 能收到 EOF；如需等待 reader，只使用有界 `join()`，且不得与持有 `_write_lock` 的帧发送路径互等。
- 终止前若有活跃轮次，沿用 `session/cancel` 的协议语义，但退出不能被取消请求无限阻塞；Agent 已死、管道已断和初始化中途失败均应可走完整清理。
- 检查 Agent 是否再创建持有通信管道或终端的子进程；只在确认归属与继承关系后处理对应子进程，禁止把用户独立终端任务一并杀死。
- 若实测仅需 DSH 私有调整，在 `src/ide/llm/providers/dsh_acp.py` 处理；其余 Provider 维持现状并跑公共回归。

### 4. 处理对话后其他子进程与最终化卡点

- 若分支 A/B 的证据指向提示音或通知，分别在 `src/ide/gui/sound_player.py`、`src/ide/gui/desktop_notifier.py` 增加应用退出时的有界回收/清理；保留异步播放和通知行为，不让短音效拖住正常退出。
- 若证据指向 Qt/Python 最终化，依据线程栈调整对象销毁、计时器停止或第三方资源释放顺序；不得通过绕过 `sys.exit()` 或强制 `os._exit()` 隐藏未清理资源。
- 修正 `main.py` 中“收尾完成即进程真的死透”等超出现有事实的注释和日志语义；成功退出时取消/停止看门狗，异常时保留可用于定位的栈输出。

### 5. 自动化测试

新增用例归入现有测试体系，可设 `tests/test_acp_shutdown.py` 与聊天退出相关测试文件；全部使用 monkeypatch/假进程/假 Worker，不起真实 CLI、Agent、播放器或通知进程。

- **进程回收**：正常终止、terminate 超时后 kill、已退出、重复关闭四条路径均最终回收；验证最终 `wait()` 和管道关闭顺序。
- **解封顺序**：先关闭 Provider，再等待 Worker；等待超时只执行既定兜底，不无限等待。
- **应用级幂等**：无对话、单标签、多标签、标签已关闭、切换过后端、活跃轮次、Provider 尚未创建等关闭路径无异常且不重复销毁。
- **竞态**：关闭与初始化/新建连接并发时，迟到连接立即终止；reader EOF 与主动 terminate 同时发生时不重复注入导致异常。
- **条件性回归**：若修改声音或通知，验证退出回收与模块既有轮询不冲突，且测试真实不出声、不发桌面通知。
- **既有行为**：ACP 帧映射、会话复用、主动停止当前轮次、标签单独关闭及终端 PTY 生命周期测试保持通过。

### 6. 真实端到端验收

- 从外部终端真实启动 IDE，未对话直接关闭：自动返回提示符，可立即输入下一条命令。
- 完成一轮 DSH 对话，待任务完成声音与通知出现后关闭：无需 `Ctrl+C` 自动返回提示符；主 PID 与本实例 Agent PID 均不再存活。
- 在 AI 仍在生成时关闭：取消与终止有界完成，GUI 不永久卡死，终端最终自动返回。
- 覆盖初始化中关闭、多标签/多 Provider 后关闭、Agent 人为无响应的超时降级；确认没有按名称误杀其他实例或用户进程。
- 正常完成路径不应触发 10 秒看门狗；异常降级必须有明确日志，且不能以仍残留进程作为“成功”。
- 在 IDE 内嵌终端执行普通程序的启动/退出回归，确认修复没有通过伪造提示符或干预 `Ctrl+C` 行为实现。

### 7. 门禁与文档收尾

- 运行 `bash scripts/check.sh`，隐私扫描、ruff 与 pytest 全量必须通过。
- 实施后更新本计划状态，并按惯例在 `文档/修改记录/` 补修改记录，写明实测根因、修改点、验证矩阵与仍存在的环境限制。
- 若最终改动触及模块说明或项目约定，同步更新对应文档；不保留描述旧退出行为的注释。

## 验收标准

1. “未对话”和“已对话”两条核心路径均无需 `Ctrl+C`，关闭 IDE 后终端自动返回可输入的 Shell 提示符。
2. 退出后无本实例遗留的 IDE 主进程、ACP Agent、聊天 Worker 或应由 IDE 回收的通知/播放器子进程。
3. 正常关闭有界完成；Agent 无响应时能按超时降级并最终退出，不依赖强制结束终端。
4. 连续执行至少三轮“启动—对话—关闭”，无残留进程累积，下一轮启动与对话正常。
5. 自动化测试与 `bash scripts/check.sh` 全绿，真实 DSH 端到端场景通过；未实际验证的后端不得宣称已验证。

## 风险与边界

| 项 | 说明 |
|---|---|
| ⚠️ 过早锁定 ACP | 日志同时出现提示音与通知，且卡点可能在 `atexit` 之后；必须先做进程/线程分流 |
| ⚠️ 多实例误杀 | 只能使用本实例持有的进程对象/PID，不能按 `dsh`、`aplay` 等名称全局清理 |
| ⚠️ 后台清理被误认为完成 | daemon 线程启动不等于清理完成；正常退出需要明确的完成状态和有界协调 |
| ⚠️ 关闭顺序死锁 | Provider、reader、Worker 与 GUI 间存在锁和等待关系；调整顺序须由竞态测试覆盖 |
| ⚠️ 强制退出掩盖泄漏 | 禁止以 `os._exit()`、无条件 SIGKILL 或模拟 `Ctrl+C` 作为正常关闭方案 |
| 🟢 长驻机制保留 | 本计划只修退出与资源所有权，不改变对话期间复用 Agent 的现有设计 |
