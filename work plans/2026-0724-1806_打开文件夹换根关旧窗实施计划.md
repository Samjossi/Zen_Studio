## 目标布局（需求方已确认语义）

```
文件(&F)
├─ 打开文件(&O)…            （现有，保留）
├─ 新建窗口(&N)             （现有，保留：同根起进程）
├─ 在新窗口打开文件夹(&W)…  （现有，保留：换根起进程、留旧窗）
├─ 打开文件夹(&D)…          （新增：换根起进程、探活后关旧窗）
├─ 打开配置目录(&C)         （现有，保留）
├─ 最近打开的项目(&R) ▸     （现有，保留）
├─ ────────────
└─ 退出(&Q)                 （现有，保留）
```

命名理由：与「在新窗口打开文件夹(&W)…」形成对照——&W 文案强调"在新窗口"
（留旧），新项不强调即默认本窗口被替换；助记符 &D（Directory）与既有
&O/&N/&W/&C/&R/&Q 无冲突。行为提示经状态栏消息承载（见 §2 P2.6）。

## 1. 现状与差距

多开改造（2026-0722-0756）后换根只有「在新窗口打开文件夹(&W)…」一条入
口，起新进程后**旧窗留存**；用户想"换个项目继续干活"必须再手动关旧窗，
两步操作且旧窗在任务栏/切换器里短暂残留。缺一条「换根 + 关旧」的合成
入口。

### 1.1 关键既有事实（方案约束来源）

| 事实 | 位置 | 对本计划的约束 |
|:--|:--|:--|
| `_spawn_window(folder)` 起新进程但不返回 `Popen` 句柄，spawn 后仅发状态栏消息 | `main_window.py:364-368` | 微调返回 `subprocess.Popen` 句柄供启动探活；既有 3 处调用方忽略返回值，零影响 |

| `closeEvent` 保存段为「隐藏面板先恢复可见 + `_state_store.save()`」两步，save 内双写 default（后写胜） | `main_window.py:274-286`、`controllers.py:169-187` | 抽出为 `_save_layout_state()` 供 closeEvent 与预写共用；预写另需 `collect_layout_patch()` 采集段抽出（写目标根哈希走 patch 直写，不经 save——save 只写自身根文件） |

| 新窗口启动时经自身记录链自动写入「最近打开的项目」并置顶 | `main_window.py:370-376` docstring | 本功能 spawn 即被记录，无需额外接线 |
| `QTimer.singleShot` 无 receiver 重载在窗口 C++ 对象已删后回调会 `RuntimeError` | PySide6 行为（1901 实施期 shiboken 教训同类） | 探活定时器用 `QTimer.singleShot(ms, self, callback)` 带 receiver 重载：探活窗口期内用户手动关窗则定时器自动取消 |
| `load_layout_state` 回退链：哈希文件存在即**全量采用**（不做键级合并），缺失才回退 default.json | `window_state.py:158-167` | default 继承仅覆盖"目标根首开"——开过的目标根读自身旧布局，当前窗口布局轮不上；故预写必须**写目标根哈希文件**（复制语义），仅写 default 不够（需求方 18:45 拍板，见 P2.4） |

| 冒烟脚本 `.temp/smoke_file_menu.py` 断言菜单 7 项结构 | work plans/2026-0722-1901 §7 | 新增第 8 项为**既有验证产物连带更新**，计入任务分解 |

### 1.2 业界对照论证（为什么不做窗口内就地换根）

调研了 VS Code 与 Eclipse Theia（`参考代码/theia-zen`）两个同类 IDE 的
「打开文件夹」实现，结论：**两家都同时支持"窗口内换根"与"新窗口换根"两
种语义，但窗口内换根的实现全部是"全量重载"而非逐子系统拆解重建**——
它们依赖 web/Electron 架构的 reload 原语，成本为零；本项目的 Qt 单进程
架构没有该原语，模仿即付全链 teardown 代价（1901 否决理由，第三次独立
验证）。

| | VS Code | Theia（参考代码/theia-zen） |
|:--|:--|:--|
| 两种语义的呈现 | 单一入口 + 全局设置 `window.openFoldersInNewWindow`（off/default = 当前窗口替换；on = 新窗口）；命令行 `-r`/`-n` 强制覆盖 | 单一入口 + 偏好 `workspace.preserveWindow`（默认 `false` = **新窗口**；`true` = 当前窗口替换），见 `packages/workspace/src/common/workspace-preferences.ts:22` |
| 「替换当前工作区」语义 | `on` 时行为 = **关旧窗、开新窗**（issue #46985 原文："The current window closes and a new window is created"）——与本计划用户可见行为**完全一致** | `preserveWindow: true` → reload 后旧上下文全灭 |
| 窗口内换根的实现 | workbench **全量 reload**（renderer 重载、扩展宿主整体重启，issue #108575），非精细 teardown | `reloadWindow()` 仅两行：新根写入 URL hash + `windowService.reload()` **整页重载**（`workspace-service.ts:649-654`），非精细 teardown |
| 敢做窗口内换根的架构前提 | Electron：renderer reload 近免费且彻底；重活在独立进程（扩展宿主/语言服务）；终端有 persistent session 重连 | web：前端是无状态壳，后端服务独立进程；reload 即全部重来 |
| 换根失败兜底 | — | `openNewWindow` 被浏览器拦截时回退 reload 当前窗口（`workspace-service.ts:640-645`） ↔ 本计划 2 s 探活失败保留旧窗 |
| 空窗口首开 | — | 首开强制 `preserveWindow=true`（无旧可留，`workspace-service.ts:501`） ↔ 本计划无效回退项目根（V2 语义，不涉及换窗） |

**对本计划的三点结论**：

1. **"关旧开新"是桌面原生架构下对"全量重载"的等价实现**——进程退出即
   全量释放，新进程即全量初始化；比 web 系多付的只是一个 OS 窗口壳的重
   建，换来零 teardown 代码。
2. **窗口内就地换根是架构奢侈品**——web 系能做是因为 reload 原语天成；
   本项目面板/provider（4 个 kimi acp 长驻进程）/终端 pty/worker 线程/
   状态存储同进程纠缠，无免费全量重启手段，不做。
3. 若未来要更贴近 VS Code 的呈现方式，可将行为做成设置项（"打开文件
   夹时：替换当前窗口 / 新开窗口"）替代独立菜单项——属后续打磨，不影
   响本计划。

## 2. 方案

### P1 closeEvent 保存段抽取（`main_window.py` + `controllers.py`）

- 新增私方法 `_save_layout_state()`：恢复四面板可见 + `self._state_store.save()`
  （逻辑逐行搬自 `closeEvent`，含注释）
- `closeEvent` 改调之，行为不变
- `WindowStateStore` 布局 patch 采集段（geometry + 三 splitter encode +
  `splitter_chat` None 跳过逻辑，`controllers.py:179-185`）抽出为
  `collect_layout_patch()` 公开方法，`save()` 改调之——供 P2.4 预写复用，
  避免两份采集逻辑漂移

### P2 核心槽 `open_folder_here()`（`main_window.py`）

1. `QFileDialog.getExistingDirectory(self, "打开文件夹", self.file_explorer.root_dir)`；
   取消无副作用（与 &W 一致）
2. `Path(path).resolve()` + `is_dir()` 探活 → 无效：状态栏
   「文件夹不存在，未做任何更改」，**不 spawn 不关窗**（防 §1.1 静默回退灾难；
   对话框仅保证选中时刻存在，TOCTOU 窗口由此兜底）
3. 同根选择 → **接受，不开特例**（语义 = 重启当前窗口；新窗口读同一哈希
   状态文件恢复布局。对齐 `open_recent_project` "恰为当前根时等价新建窗口，
   接受"的既有风格）
4. 预写布局（**复制语义**，需求方 18:45 拍板）：
   - 数据源：**活窗口实时采集**——`self._state_store.collect_layout_patch()`
     （P1 抽出），**不读源根磁盘文件**（会话期布局调整未落盘，读文件只能
     拿到旧布局）
   - 写入：`update_window_state(window_state_file_for(新根), patch)`（原子
     链）→ 新窗口无论目标根是否开过，启动都读到当前窗口布局（哈希文件
     存在即全量采用，回退链第一级命中）；同根重启即写自身哈希文件
   - default 双写照旧（`update_default_layout(patch)`，1015 首开继承机制
     不动，供其他路径新开窗口继承）
5. `proc = self._spawn_window(str(resolved))`（本 P 微调后的返回值）
6. 状态栏消息覆盖为「正在打开：<目录>（新窗口就绪后本窗口将关闭）」——
   `_spawn_window` 内消息随后发出即被本条覆盖，无需改动其消息逻辑
7. 启动探活：`QTimer.singleShot(SPAWN_PROBE_MS, self, probe)`；probe 内
   `proc.poll()`：
   - `None`（存活）→ `self.close()`（closeEvent 正常走：二次 save 幂等、
     释放 settings flock、终端会话收尾）
   - 非 `None`（启动即败）→ **不关窗**，状态栏
     「新窗口启动失败（退出码 N），本窗口已保留」
8. 模块级常量 `SPAWN_PROBE_MS = 2000`，注释依据：PySide6 冷启动 import
   约 1–2 s，启动失败（解释器错误/import 崩溃）绝大多数在此窗口内退出

`_spawn_window` 微调（属本 P）：签名加返回值 `-> subprocess.Popen`，
`return subprocess.Popen(...)`，docstring 补一句；消息逻辑不动。

### P3 菜单接线（`file_menu.py`）

- 第 4 位（&W 之后）插入「打开文件夹(&D)…」→ `ctx.open_folder_here`，
  登记 `file.open_folder_here`
- 文件头 docstring 清单与计划引用同步；`main_window.py` 文件菜单槽小节
  docstring 同步

1. **新增冒烟**（`.temp/smoke_open_folder_here.py`，offscreen，打桩

## 5. 风险与回滚

| 风险 | 评估与对策 |
|:--|:--|
| 新进程在 poll 探活通过后、窗口 show 前崩溃（import 后期失败）→ 两窗皆无 | 概率极低：启动失败绝大多数发生在 2 s 探活窗口内；残存风险接受（用户重新手动启动即可，无数据损坏——旧根状态文件 closeEvent 已正常保存）。跨进程就绪握手（IPC）方案经评估**裁剪**：协议成本远高于残余风险收益 |
| 预写时隐藏面板被恢复可见，视觉闪现 | 恢复可见是 closeEvent 既有行为；换根场景窗口 2 s 内即关闭，闪现可忽略 |
| 探活窗口期（2 s）内用户继续操作旧窗口 | 用户已明确表达换文件夹意图，close 照常执行；与「在新窗口打开文件夹」后手动关窗的语义等价 |
| 目录在 is_dir 校验后、新进程读取前被删（残余 TOCTOU） | 校验已把窗口收窄到毫秒级；万一命中，新进程回退项目根——用户手动关新窗即可，旧窗已关但状态无损 |
| 同根重启时 settings flock 交接 | 0756 串行化机制已覆盖「旧释放 → 新获取」；close 发生在探活通过后，新进程已在运行，锁竞争由既有读-合并-写原子链收敛 |
| 换根覆盖目标根自身布局（开过的项目原布局被当前窗口洗一次） | 需求方 18:45 拍板接受：换根为主动操作，"窗口样子跟着窗口走"语义自洽；覆盖仅发生换根一刻，之后该项目布局照常保存、独立演化；default 首开继承与其他打开路径不受影响 |
| 目标根正被另一窗口开着（同根多开），其关闭时回写覆盖本次预写 | 既有读-合并-写原子链收敛（后写胜），与多开既有语义一致；两窗各自演化，可接受 |
| 回滚 | 纯新增一槽一菜单项 + 两处抽取 + 一处返回值微调，`git revert` 即还原；无烟无 schema 变更，状态文件格式不动 |
