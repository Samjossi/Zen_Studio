## 1. 背景与目标

公共权限策略目前从 Kimi 具体 provider 借类型，连接与提问识别也夹杂厂商语义。本项将「原始 ACP 参数如何分类」交给各厂商，将权限四态、危险命令黑名单和 optionId 原样回传留在稳定公共策略中。

目标是 `permission_policy.py` 不再依赖任何具体 provider，ACP 连接只负责及时收发，GUI 权限队列只提供中性宿主服务，同时保持用户可见文案、审批结果和提问卡行为不变。

## 2. 启动条件与边界

- 主计划 T3 已勾选，且用户明确批准 T4 后才能开始；本项批准不包含 T5。
- Kimi 现有 AskUserQuestion 与历史兼容输入按基线迁移，不删历史行为。
- DSH 只使用已实证结构，未实测的 ask_user_question 回环留后续专项；不得借重构激活。
- 权限四态、危险命令和 optionId 回传是产品安全策略，可继续共享；厂商工具名和原始参数分类不得留在公共层。
- 具体提问内容如何映射进卡片由对应厂商 presenter/卡片包负责，不恢复公共提问格式。

3. ACP 连接层不新增厂商工具名，仍只负责请求收发与反向请求分发。

### T4.2 收敛公共策略与 GUI 宿主

2. `permission_queue.py`、`permission_dialog.py`、`question_bridge.py` 只保留中性请求传输、选项回传和宿主服务。

## 6. 实施结果回写（2026-11-20 23:43 UTC+8）

T4 全部完成，修改记录见 `文档/修改记录/2026-1120-2343_T4权限分类厂商化与公共策略解耦实施记录.md`。以下为实施过程中相对原计划的偏差与经验。

**与计划的偏差**：

1. **`PermissionRequest` 增加中性 `questions` 字段**：计划只要求「原始参数 + 中性分类」，但公共 `QuestionDialog` 和 `QuestionBridge` 的文本匹配必须拿到问题文本，又不能继续解析厂商 rawInput。实际做法是各厂商 `permissions.py` 提取 `tuple[str, ...]` 问题文本随请求传递，卡片布局与答案渲染仍在厂商卡片包。这比只传 `kind` 多一个中性字段，但避免了 GUI 反向解析厂商载荷。
2. **DSH 分类器恒返回 `permission`**：计划要求不激活未实证提问能力，实际以恒返回明确表达该边界；旧的公共识别会把 DSH 的 `rawInput.questions` 也当提问，本项后 DSH 若真发送提问帧会按普通审批处理（`auto_all` 下可能自动选答）。这是计划明确接受的取舍，已在修改记录标为已知缺口。
3. **顺带移除 Kimi provider 的协议类型 re-export**：`PermissionOption`/`PermissionParams`/`ToolCallInfo` 已无消费方（公共策略改从稳定 ACP 包取型），删除避免继续把 Kimi 当公共类型出口；不改变运行时行为。
4. **提问框标题未改**：`PermissionDialog` 仍显示既有「Kimi ACP 请求执行工具」。T4 要求用户可见文案不变，故未把该文案改成中性；它对 DSH/Local 不准确，属已知残留，未扩大为文案专项。
5. **未提前做 T5**：`src/ide/llm/__init__.py` 仍保留既有公共再导出，只补了中性 `PermissionRequest`；公共出口收敛与 AST 守卫留在 T5。

**验证结果**：

- 权限定向：`QT_QPA_PLATFORM=offscreen .venv/bin/python -m pytest tests/test_permission_boundaries.py -q` → **14 passed**（`.temp/t4_targeted_tests.log`）。
- 全量门禁：`UV_CACHE_DIR=$PWD/.temp/uv-cache bash scripts/check.sh` → 隐私扫描通过、可选中 QLabel 裸用守卫通过、ruff 通过、**79 passed**（`.temp/t4_after_check.log`）。
- 依赖方向：`permission_policy.py` 只 import `ide.llm.providers.acp`；三家 `permissions.py` 只 import 稳定 ACP 包且互不横向 import，AST 断言见 `tests/test_permission_boundaries.py`，搜索证据 `.temp/t4_boundary_grep.log`。
- 行为：四态矩阵、危险命令、`auto_all` 下 question 仍 `ask`、`allow_always` 优先与原样 optionId、连接层「handler 返回 None → reject_once / 无 handler → allow_once」均有用例锁定；Kimi/Local 三类提问形态、DSH 同载荷仍 permission 均通过。
- 未做真实 CLI 端到端；未读写凭据；真实后台验收留 T7。验证日志只落 `.temp/`。

**经验沉淀**：

1. **中性请求要中性到「宿主无需再解析」**：只传 `kind` 会把问题文本解析重新推回公共对话框，等于换个位置保留厂商语义。把问题文本作为中性数据随请求传递，才真正切断 GUI 对厂商 rawInput 的依赖。
2. **适配层放在 provider，而不是连接层**：连接层继续只认原始 params，provider 负责「本厂商分类 → 中性 handler」；这样 ACP 稳定包不必知道 kind 如何判定，脚本/无 GUI 夹具也可继续直接使用连接层。
3. **未实证能力用显式恒等返回表达**：DSH 分类器不写「看起来像提问就提问」的推断，而是恒返回 permission 并在 docstring 记录缺口；这比留空的启发式更容易在后续取证时定位修改点。
4. **受控重复优于共享基类**：Kimi 与 Local 的 `permissions.py` 规则当前相同，但各自持有文件、注释和工具名表；任一家演化不会以「抽公共基类」的方式重新耦合。
5. **安全边界要同时测策略与连接兜底**：只测 `decide_permission` 会漏掉「handler 异常/取消 → reject_once」和「无 handler → allow_once」；本次把连接层兜底也纳入用例，避免重构适配层时悄悄改变拒绝语义。
