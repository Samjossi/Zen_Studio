# T4 权限分类厂商化与公共策略解耦子计划

## 1. 背景与目标

公共权限策略目前从 Kimi 具体 provider 借类型，连接与提问识别也夹杂厂商语义。本项将「原始 ACP 参数如何分类」交给各厂商，将权限四态、危险命令黑名单和 optionId 原样回传留在稳定公共策略中。

目标是 `permission_policy.py` 不再依赖任何具体 provider，ACP 连接只负责及时收发，GUI 权限队列只提供中性宿主服务，同时保持用户可见文案、审批结果和提问卡行为不变。

## 2. 启动条件与边界

- 主计划 T3 已勾选，且用户明确批准 T4 后才能开始；本项批准不包含 T5。
- Kimi 现有 AskUserQuestion 与历史兼容输入按基线迁移，不删历史行为。
- DSH 只使用已实证结构，未实测的 ask_user_question 回环留后续专项；不得借重构激活。
- 权限四态、危险命令和 optionId 回传是产品安全策略，可继续共享；厂商工具名和原始参数分类不得留在公共层。
- 具体提问内容如何映射进卡片由对应厂商 presenter/卡片包负责，不恢复公共提问格式。

## 3. 实施步骤

### T4.1 建立中性请求与厂商分类入口

1. 在稳定 ACP 协议模块定义中性 `PermissionRequest`，保留原始 `PermissionParams`，不得丢参或改写成另一家口径。
2. 在 Kimi、DSH、Local 各自权限模块完成 question/permission 分类，再调用统一 handler。
3. ACP 连接层不新增厂商工具名，仍只负责请求收发与反向请求分发。

### T4.2 收敛公共策略与 GUI 宿主

1. `src/ide/llm/permission_policy.py` 改依赖稳定协议类型，只处理中性分类、权限四态、危险命令和选项选择。
2. `permission_queue.py`、`permission_dialog.py`、`question_bridge.py` 只保留中性请求传输、选项回传和宿主服务。
3. 厂商 presenter/卡片包负责具体提问内容、布局和交互，原始参数不丢失，用户可见文案和 optionId 回传值不变。
4. 保持 auto_all 下 question 仍必须询问，普通 Bash 审批、拒绝兜底与危险命令策略不变。

### T4.3 验证权限矩阵与隔离

1. Kimi AskUserQuestion、历史兼容输入、普通权限与拒绝路径分别跑基线回归。
2. DSH 已实证权限结构跑回归，未实证提问能力明确保持未激活。
3. 验证 Local 分类不通过 import Kimi 继承相似行为。
4. 运行权限四态矩阵、提问卡、危险命令和 `bash scripts/check.sh`，并搜索公共策略是否仍 import provider。
