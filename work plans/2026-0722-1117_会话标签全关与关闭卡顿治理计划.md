# 会话标签全关与关闭卡顿治理计划

## 1. 背景与问题

多标签上线后暴露两个体验缺陷：

### 1.1 标签关不完、序号只增不减

- 现状 [`tabs.py`](../gui/panels/chat/tabs.py) `_close_tab`：`if self._tabs.count() <= 1: return`——**最后一个标签关不掉**。
- 现状 `_tab_seq` 单调递增、关闭不复用（原设计意图：防「会话 2」指代漂移）。
  用户感知却是"会话 1、2、3……不停增加"，关开几轮后序号虚高。
- **用户诉求**：
  1. 所有会话都可以关掉（包括最后一个）；
  2. 全部关掉后计数重置，再新建从「会话 1」开始。

### 1.2 关闭一个会话很慢很卡

关闭路径全程在 **GUI 线程同步执行**，最坏情况冻结 **8 秒**。诊断见 §2。

---

## 2. 诊断：关闭卡顿根因分析

### 2.1 关闭调用链现状（全部阻塞 GUI 线程）

```
tabs._close_tab (GUI 线程)
 └─ panel.close()
     ├─ request_stop()                     # 快：置标志 + llm.cancel()
     │    └─ ACP: conn.cancel_turn()       #   仅发 session/cancel 通知
     ├─ worker.wait(3000)                  # ← 阻塞点①：最长 3s
     └─ KimiAcpLLM.close()
          └─ _conn.terminate()
               ├─ proc.terminate()         # SIGTERM
               └─ proc.wait(timeout=5)     # ← 阻塞点②：最长 5s，超时再 SIGKILL
```

`deleteLater()` 排在最后，因此**阻塞点①+②全部落在 `tabCloseRequested` 槽里**，
UI 在 0.5s ~ 8s 间冻结（典型：agent 退出延迟数百毫秒到数秒，即用户感知的"很卡"）。

### 2.2 三个结构性根因

**C1（主因）— 清理动作同步压在 GUI 线程。**
`worker.wait(3000)` 与 `proc.wait(timeout=5)` 都是"等别人退出"的纯等待，
却让事件循环干等。等待本身不产出任何 UI 结果，全部应移出 GUI 线程。

**C2 — 取消信号覆盖不到 worker 的全部阻塞点，`wait(3000)` 经常等满。**
`request_stop()` 依赖 `llm.cancel()` 生效，但 ACP 后端有两个取消盲区：

| worker 所在位置 | cancel 是否有效 | 后果 |
|:---|:---|:---|
| `_iter_turn_chunks` → `next_update()`（`queue.get()` **无超时**） | 仅当 agent 及时处理 `session/cancel` 并回 prompt 响应；agent 卡在工具执行时迟迟不回 | 等满 3s |
| `_ensure_session()` → `initialize`（30s 超时）/ `session/new`（60s 超时） | **完全无效**：`KimiAcpLLM.cancel()` 要求 `_session_id` 与 `_turn_id` 均已存在，建会话期间两者皆无 | 等满 3s |
| kimi_cli 后端任意点 | 有效（terminate → stdout EOF） | 快 |

**C3 — 关闭顺序倒置：能立刻解救 worker 的动作被排在 `wait` 之后。**
`terminate()` 杀掉 `kimi acp` 后，stdout EOF 会让 reader 线程向 `_updates`
注入 `("dead", …)`、向 `_pending` 注入错误——**worker 的所有阻塞点都会立刻醒来**
（`_iter_turn_chunks` 收到 dead 抛错收尾；`_ensure_session` 的 `request()` 收到错误抛错）。
但现状是 `worker.wait(3000)` 先跑、`provider.close()` 后跑：先干等 3 秒，
才去做那件本来 10 毫秒就能让 worker 解脱的事。

附带风险：3s 等满后 `deleteLater()` 照旧销毁仍在运行的 `ChatWorker(QThread)`
（"QThread: Destroyed while thread is still running"，未定义行为）——
评审修复轮的 `wait(3000)` 只是把窗口收窄到 3s，并未消除。

| 编号 | 议题 | 结论 | 依据 |
|:---:|:---|:---|:---|
| E1 | 全部关闭后的空态呈现 | **占位页（方案 A）**（✅ 已采纳实施） | `QStackedWidget`：有标签时显示 `QTabWidget`，零标签时显示占位页（提示文案 + 居中「+ 新建会话」按钮，点击即 `add_tab`）；比裸空 `QTabWidget`（只剩角落一个 + 号）可发现性好 |

## 4. 实现方案

### 4.1 P1：标签全关 + 计数重置

| # | 文件 | 改动 |
|:---:|:---|:---|
| 1 | [`gui/panels/chat/tabs.py`](../gui/panels/chat/tabs.py) | `_close_tab` **删除 `count <= 1` 保底**，允许关到 0；`removeTab` 后若 `count == 0`：`_tab_seq = 0`（计数重置，下次 `add_tab` 即「会话 1」）并切到占位页 |
| 2 | [`gui/panels/chat/tabs.py`](../gui/panels/chat/tabs.py) | 布局改 `QStackedWidget`：页 0 = 占位页（`QLabel` 提示「暂无会话」+ `QPushButton`「新建会话」→ `add_tab`），页 1 = `QTabWidget`；`add_tab`/`_close_tab` 维护页面切换（0↔1） |
| 3 | [`gui/panels/chat/tabs.py`](../gui/panels/chat/tabs.py) | 零标签健壮性核查（现有代码已基本兼容，逐条确认）：`_panels()` 空列表 → `apply_theme`/`restore_state`/`reset_layout`/`_on_selection_changed` 自然 no-op；`save_state()` 占位页非 `ChatPanel` 返回 `""`；`_route_stop` 空 `_busy_panels` no-op；`_refresh_add_button` 0 < 4 按钮可用。ModelBar 保持常驻（全局控件，不随标签消失） |

> 序号语义变更：原"单调递增防指代漂移"让位于用户决策——**全部关闭即重置**；
> 非全关时仍不复用已关闭序号（例如关「会话 2」留「会话 1/3」，新建仍是「会话 4」），
> 指代漂移防护在非全关场景继续有效。

### 4.2 P2：关闭路径异步化（E2 方案 A）

**核心思路**：`_close_tab` 立即摘标签、立即返回；`panel.close()` 在 GUI 线程只做
毫秒级动作（`request_stop` + 信号断开 + 启动清理线程）；`terminate`/`wait` 全部
移入 daemon 清理线程，结束后经 `QTimer.singleShot` 回 GUI 线程 `deleteLater`。

| # | 文件 | 改动 |
|:---:|:---|:---|
| 4 | [`llm/providers/kimi_acp.py`](../llm/providers/kimi_acp.py) | `_AcpConnection.terminate()` 兜底注入：终止/杀死进程后，主动向 `_updates` 放 `("dead", exitcode)`、向残余 `_pending` 放错误帧（与 reader 线程 EOF 注入**幂等**，加 `_terminated` 标志防重复）——consumer 不必等 reader 反应过来，`next_update()`/`request()` 立即醒来（治 C2） |
| 5 | [`gui/panels/chat/panel.py`](../gui/panels/chat/panel.py) | `close()` 重构为两段：**GUI 段**（毫秒级）——`request_stop()`、断开 worker 信号（防迟到的 `_on_finished`/`_on_stopped` 触碰已摘标签的 UI）、启动 daemon 线程 `_cleanup_blocking`；**线程段**——先 `KimiAcpLLM.close()`（terminate → 依 #4 立即解封 worker，治 C3 顺序），再 `worker.wait(3000)`，最后 `QTimer.singleShot(0, panel, panel.deleteLater)` 回 GUI 线程销毁（`QTimer.singleShot(0, receiver, slot)` 跨线程投递，与 `permission_queue.ask` 既有用法同构） |
| 6 | [`gui/panels/chat/tabs.py`](../gui/panels/chat/tabs.py) | `_close_tab`：`removeTab` 与 busy 清算（`_busy_panels.discard` + `_recompute_busy`）保持在 GUI 线程同步完成（本就毫秒级），`panel.close()` 调用点不变但不再阻塞；`deleteLater` 从 `_close_tab` 移除（移交清理线程） |

**关键不变量**（评审修复轮已确立，本方案保持）：
- worker 退出前不销毁 `QThread` 对象——`deleteLater` 在 `wait` 之后投递；
- busy 清算不提前——worker 收尾信号到达前 `_busy_panels` 已按 panel 维度 discard
  （标签摘除即不再参与汇总，迟到的 `busy_changed` 信号因 panel 已不在集合中，
  `_on_tab_busy` 的 discard/recompute 幂等无害；若求更稳可在 close() GUI 段
  同步 `disconnect` 该信号）；
- 清理线程 daemon 化：应用退出时不阻塞；`KimiAcpLLM` 的 `atexit` 钩兜底杀进程。

**方案 B（备选，不推荐）**：保持同步但重排为 `request_stop → provider.close()
（terminate 解封 worker）→ worker.wait(1000)`，并把 `proc.wait` 超时 5s→2s。
改动更小，但最坏仍冻结 ~3s，仅作 E2 被推翻时的退路。

## 7. 风险与边界

- 🟢 **零标签期 provider 空窗**：全关后无任何 provider 实例存活，kimi acp 进程数归 0；
  新建标签按需重建（`ChatPanel` 构造懒连接，首次发送才 spawn），无额外成本。
- 🟢 **清理线程与退出竞态**：清理线程 daemon 化 + provider atexit 钩双保险；
  线程内只做 terminate/wait，不触碰 Qt 对象（`deleteLater` 经 singleShot 回 GUI 线程），
  无线程亲和性违规。
- 🟡 **占位页样式**：沿用侧栏主题令牌（`check_theme_tokens.py` 双向一致约束），
  不引入新硬编码色值；如需新令牌先入主题资源包。
- 🟢 **序号重置语义**：仅"全关"触发重置，部分关闭不复用序号——指代漂移防护
  （原 `_tab_seq` 单调设计意图）在非全关场景保留。
- 🟢 **kimi_cli 后端**：本就取消有效（terminate → EOF），本计划不改其路径，
  仅共享异步化收益。
