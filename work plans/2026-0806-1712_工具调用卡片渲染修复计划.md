# 工具调用卡片渲染修复计划

> **状态**：草稿
> **范围**：`llm/providers/acp.py`（协议层）、`llm/base.py`（载荷契约）、`gui/panels/chat/cards.py`（渲染层）、`gui/panels/chat/panel.py`（路由层）、`gui/panels/chat/transcript.py`（容器层）、`scripts/`（可视化验证脚本）
> **时间**：2026-08-06 17:12（设计，UTC+8）/ 2026-08-06 17:51（修订）
> **优先级**：高

---

## 1. 背景与症状

当前聊天面板的工具调用卡片（ReadMediaFile、AskUserQuestion、Agent、TodoList 等）存在四类渲染缺陷：

| # | 症状 | 截图证据 |
|:---:|:---|:---|
| S1 | **入参一律显示"（无）"**，即使工具明明携带参数（ReadMediaFile 的 path、AskUserQuestion 的 questions、Agent 的 prompt） | ReadMediaFile / AskUserQuestion / Agent 三张卡 |
| S2 | **出参是原始 JSON 字符串原文展示**，`\r\n`、`\"` 转义裸露，未做任何解析与格式化 | ReadMediaFile 出参整段 `[{"type":"text",...}]` 原文 |
| S3 | **MCP content 数组未按 type 分发**：`image`/`image_url` 块被静默丢弃，base64 图片无法渲染为图像 | ReadMediaFile 出参中 `image_url` 数据以文本形态裸露 |
| S4 | **系统回执类文本原样上屏**：TodoList 出参把 "Ensure that you continue to use the todo list..." 这类系统指令性文本逐字展示 | TodoList 卡 |

另有结构性缺陷 S5：**无按工具名的专用渲染器分派**——`gui/panels/chat/cards.py` 的 `make_tool_card` 仅按 ACP `tool_kind`（execute/edit/read/search/fetch/think 六个枚举）分派，`other` 一律落入通用 `McpCard`（纯文本入参+出参两节），AskUserQuestion/Agent/TodoList 等无任何定制渲染。

## 2. 根因分析

经全链路排查（数据链：ACP 帧 → `llm/providers/acp.py` 帧映射 → `gui/panels/chat/panel.py` 路由 → `gui/panels/chat/transcript.py` 建卡 → `gui/panels/chat/cards.py` 渲染），根因分布于三层：

### 2.1 协议层 `llm/providers/acp.py`

| # | 根因 | 对应症状 |
|:---:|:---|:---:|
| R1 | **入参只在首帧提取，update 帧永不回填**：`_format_input_detail` 仅在 `_map_tool_call`（首帧）调用；`_map_tool_call_update` 完全没有 rawInput 提取逻辑。kimi 系后端首帧为空壳、rawInput 在 in_progress 帧才补发（代码内已有自述注释），迟到参数永远到不了卡片 | S1 |
| R2 | **`_INPUT_DETAIL_KEYS` 无 "other" kind**：ReadMediaFile/AskUserQuestion/Agent/TodoList 的 ACP kind 为 `"other"`，已知键白名单必然落空；首帧 rawInput 又为空，于是走 `or "（无）"` 兜底 | S1 |
| R3 | **出参全链路无 JSON 解析**：`_extract_raw_output` 对字符串形态的 `rawOutput.output` 原样取用，仅做 ANSI/`\r` 净化。全项目 grep 确认出参路径上没有任何 `json.loads`。且 `_OUTPUT_LINE_MAX=300` 会把 minified JSON 单行截断到 300 字符加"…" | S2 |
| R4 | **content 兜底循环只认 text 块**：`_extract_raw_output` 的 content 循环仅取 `item["content"]["text"]` 一种形态，`image`/`image_url`/`resource` 块被静默丢弃 | S3 |
| R5 | **text 项 `"\n".join(parts)` 全量拼接，无任何过滤**，系统指令性文本被当作工具输出逐字透传 | S4 |

### 2.2 路由层 `gui/panels/chat/panel.py`

| # | 根因 | 对应症状 |
|:---:|:---|:---:|
| R6 | `_allow_progress_frame` 会丢弃无 `diff_hunks`/`summary` 的 in_progress 帧——即使协议层未来在 update 帧回填入参，该路由也会把它挡掉 | S1 |

### 2.3 渲染层 `gui/panels/chat/cards.py`

| # | 根因 | 对应症状 |
|:---:|:---|:---:|
| R7 | `McpCard._build_body` 只在构造时读一次 `input_detail`；`ToolCard.apply_update` 不触碰入参区，**无回填通道** | S1 |
| R8 | 出参载体是 `BodyText`（QPlainTextEdit 只读纯文本块），**结构性不可能渲染 `<img>`/富文本**，即使图片数据到达也渲不出 | S3 |
| R9 | `make_tool_card` 无工具名（title）级分派表 | S5 |

**修复面利好**：五个 provider（kimi_acp / kilocode_acp / opencode_acp / reasonix_acp / dream_acp）均直接调公共 `map_session_update`，无私有映射——只需改 `llm/providers/acp.py` 一处协议层 + `gui/panels/chat/cards.py` 一处渲染层即可全后端受益。

## 3. 参考架构：kilocode 的做法

参考 `参考代码/kilocode-main`（SolidJS webview 架构，与本项目 Qt 原生渲染形态不同，但分层思想可直接移植）：

| 机制 | kilocode 实现 | 本项目可移植点 |
|:---|:---|:---|
| **工具名注册表分派** | `参考代码/kilocode-main/packages/kilo-ui/src/components/message-part.tsx` 的 `ToolRegistry.register({name, render})`，按工具名查注册表，查不到用 `McpTool` 通用渲染器兜底；宿主可同名覆盖 | `make_tool_card` 增加"工具名 → 卡片类"二级分派表，未命中回退 McpCard |
| **MCP content 按 type 分发** | 服务端 `参考代码/kilocode-main/packages/opencode/src/session/tools.ts` 将 content 数组拆为 `output`（text 拼接）+ `attachments`（image/blob 转 data-URI）两个通道 | 协议层 `_extract_raw_output` 拆分 text 与 image，image 走独立载荷字段下传 |
| **出参 JSON 探测解析** | `McpTool.formattedOutput`：`try JSON.parse(output)` 成功则 pretty-print，失败原样输出 | 在协议层对出参做同策略的 try-parse，渲染层兜底再做一次 |
| **图片渲染** | `read` 渲染器从 attachments 过滤 `mime.startsWith("image/")`，内嵌 `<img>` 展示 | 本项目已有先例：`gui/panels/chat/transcript.py` 用户气泡用 `BodyHtml` + `<img src="file://...">`，直接复用该模式 |
| **通用卡骨架** | `BasicTool`：trigger 行（图标+标题+副标题+关键参数 chips）+ Collapsible body（入参区/出参区带分节标签） | 本项目 `ToolCard` 骨架已具备，保留；在 body 内做分节升级 |
| **回执过滤** | ⚠️ kilocode **无集中式系统文本过滤器**，采用多点分散策略（隐藏工具清单、synthetic part 过滤、已知错误提示降级） | 本项目需自行新增一层，挂点在协议层出参管线 |
| **输出截断** | 服务端截断（2000 行 / 50KB），截断后附提示并下传 `truncated`/`outputPath` 元数据 | 保留现有 `_OUTPUT_LINE_MAX` 行数截断，但合法 JSON 单行不按字符截断 |

## 4. 修复方案

按"协议层 → 路由层 → 渲染层"自底向上推进，分五个任务。任务间依赖：T1/T2 可并行，T3 依赖 T1，T4 依赖 T1+T2，T5 依赖 T1+T2。

### T1：协议层入参回填（修 S1 / R1 R2）

**改动点 1 — `_map_tool_call_update` 增补 rawInput 提取**（`llm/providers/acp.py`）：

```
# llm/providers/acp.py

def _map_tool_call_update(update) -> Chunk | None:
    ...
    raw_input = <从 update 取 rawInput>
    if raw_input and not state.input_detail_seen(tool_call_id):
        detail = _format_input_detail(update)   # 复用首帧同一函数
        if detail:
            payload["input_detail"] = detail
            state.mark_input_detail_seen(tool_call_id)
```

- 需要一个按 `tool_call_id` 的"入参已提取"簿记（避免后续帧重复回填）。复用/扩展 `ToolCallInfo` 既有状态即可，不新增全局表。
- 簿记生命周期与工具调用一致：会话结束或 `tool_call_id` 完成态到达后可惰性清理。

**改动点 2 — `_INPUT_DETAIL_KEYS` 增补 "other" kind**（`llm/providers/acp.py`）：

| kind | 键白名单（在现有基础上新增） |
|:---|:---|
| `other` | `path`、`filePath`、`url`、`query`、`command`、`prompt`、`description`、`questions`、`todos`、`name` |

- 命中规则沿用现有"按序取第一个非空键"语义；未命中且 rawInput 非空时保留现有 JSON pretty 兜底。
- 长值（如 `prompt`、`questions`）在入参区做摘要化：超过约 200 字符截断加"…"，完整值留给出参/展开区（对齐 kilocode `McpTool.inputArgs` 只取 1 个参数的克制策略）。

**改动点 3 — 载荷契约**（`llm/base.py`）：`ToolUpdatePayload` 确认/补充 `input_detail: str | None` 可选字段，docstring 注明"update 帧迟到入参回填"。

### T2：协议层出参与 content 分发（修 S2 S3 S4 / R3 R4 R5）

**改动点 1 — `_extract_raw_output` 重构为双通道产出**（`llm/providers/acp.py`）：

返回由"纯文本字符串"改为 `(text, images)` 二元组（或等价 dict），由调用方分别装入载荷：

| 输出通道 | 内容 | 去向 |
|:---|:---|:---|
| `output` | text 块拼接 + 字符串出参 JSON try-parse pretty 化 | `ToolUpdatePayload.output`（既有字段） |
| `images` | `image`/`image_url` 块的 data-URI 或 `file://` 路径列表 | `ToolUpdatePayload.images`（新增字段） |

**改动点 2 — content 类型识别矩阵**（覆盖 ACP 与 MCP 两种包裹形态）：

| 输入形态 | 判定 | 处理 |
|:---|:---|:---|
| `item.content.type == "text"` | 现有逻辑 | 拼入 `output` |
| `item.content.type == "image"`（ACP 原生，`data` + `mimeType`） | 新增 | 组装 `data:{mime};base64,{data}` 入 `images` |
| `item.content.type == "image_url"`（OpenAI 形态，`image_url.url`） | 新增 | `url` 为 `data:` 或 `file:` 开头直接入 `images`；`http(s)` 链接转为文本行拼入 `output`（不联网拉取） |
| `item.content.type == "resource"` | 新增 | `resource.text` 拼入 `output`；`resource.blob` 按 mime 判断图片则入 `images`，否则丢弃并留一行 `[resource: <uri>]` 占位文本 |
| 出参为纯字符串且 `json.loads` 成功 | 新增 | `json.dumps(obj, indent=2, ensure_ascii=False)` pretty 化 |
| 出参为纯字符串且解析失败 | 现有逻辑 | 原样保留 |

特别地，ReadMediaFile 出参形如 `[{"type":"text","text":"<image path=...>"},{"type":"image_url","imageUrl":{"url":"data:image/png;base64,..."}}]`，是**序列化为字符串的 content 数组**——try-parse 成功后需对解析结果**再走一遍上表分发**，text 项中 `<image path="...">` 标签里的本地路径也应提取为 `file://` 图片。

**改动点 3 — 截断策略修正**：探测到整段为合法 JSON（try-parse 成功）时不做 `_OUTPUT_LINE_MAX=300` 单行字符截断；pretty 化后按行数截断（保持现有 300 行上限语义）。

**改动点 4 — 系统回执过滤 `_filter_tool_receipt`**（`llm/providers/acp.py` 新增）：

```
# llm/providers/acp.py

_RECEIPT_PATTERNS = [
    r"(?ms)^Todo list updated\.\s*$",
    r"(?ms)^Ensure that you continue to use the todo list.*$",
    # 后续确证的模式在此追加，集中维护
]

def _filter_tool_receipt(text: str) -> str:
    """剔除工具出参中夹带的系统指令性回执文本。白名单模式、保守起步。"""
```

- 过滤时机：text 拼接完成后、JSON try-parse 前（对字符串形态与解析后 text 项各做一次）。
- 原则：只过滤已确证的系统提示文本，宁漏勿错（见 §6 风险表）。

**改动点 5 — 载荷契约**（`llm/base.py`）：`ToolUpdatePayload` 新增 `images: list[str] | None` 可选字段，docstring 注明元素为 data-URI 或 `file://` 路径。

### T3：路由层放行（修 S1 / R6）

- `gui/panels/chat/panel.py` 的 `_allow_progress_frame` 放行条件增补：载荷带 `input_detail` 或 `images` 的 in_progress 帧不再丢弃。

```
# gui/panels/chat/panel.py

def _allow_progress_frame(payload) -> bool:
    if payload.get("diff_hunks") or payload.get("summary"):
        return True
    if payload.get("input_detail") or payload.get("images"):   # 新增
        return True
    return False
```

### T4：渲染层 McpCard 升级（修 S1 S2 S3 / R7 R8）

**改动点 1 — 入参回填钩子**（`gui/panels/chat/cards.py`）：

- `ToolCard.apply_update` 增加分支：收到带 `input_detail` 的 update 时调用 `self._set_input_detail(...)`。
- `McpCard` 实现 `_set_input_detail`：当前入参区文本为"（无）"时直接替换；已有内容时不覆盖（首帧优先）。
- 更新走既有 `apply_update` 通道（已在 GUI 线程），无线程安全问题。

**改动点 2 — 出参区载体升级**：

- `McpCard` 出参区由 `BodyText`（QPlainTextEdit）换成 `BodyHtml`（QTextBrowser，现有组件，用户气泡与 DiffCard 已在用）。
- 组装 HTML 的规则：

| 内容 | HTML 形态 |
|:---|:---|
| text 出参 | `html.escape` 后包 `<pre>`（保留等宽纯文本观感与换行） |
| `images` 中 data-URI | `<img src="data:..." width="<限宽>">` |
| `images` 中 `file://` | `<img src="file://..." width="<限宽>">`（同 `gui/panels/chat/transcript.py` 用户气泡模式） |

- 图片限宽：按卡片可用宽度取固定上限（建议 480px 起调），防止 base64 大图撑破布局；QTextBrowser 不支持 `max-width` 时用 `width` 属性硬限。
- 出参 JSON pretty 化若在协议层漏网（如旧会话历史重放），渲染层 `set` 前再做一次 try-parse 兜底。

### T5：按工具名二级分派 + 专用卡（修 S5 / R9）

**改动点 1 — 工具名分派表**（`gui/panels/chat/cards.py`）：

**改动点 2 — 专用卡清单**：

| 工具名 | 卡片 | 渲染要点 |
|:---|:---|:---|
| ReadMediaFile | 复用升级后的 McpCard | 入参显示 path；出参图片内嵌 `<img>`（T4 已解决） |
| AskUserQuestion | 新建 `QuestionCard`（继承 ToolCard） | body 为问答对列表：每个问题一行粗体 + 所选答案普通行；pending 时显示"等待用户回答…"；出参 `{"answers":{...}}` 解析后按问答对展示，不显示裸 JSON |

- 工具名匹配注意大小写与命名空间差异（如 `mcp__xxx__AskUserQuestion` 形态）：匹配前做归一化（取末段、去 `mcp__` 前缀）。

## 5. 可视化验证闭环（mock + 截图 + 查看确认）

**核心要求**：每个任务完成后，不依赖真实后端，用 mock 数据驱动卡片渲染，`QWidget.grab()` 截图落盘，再用读图工具查看截图确认效果，形成"修改 → 测试 → 查看 → 确认"闭环。

### 5.1 技术依据（项目内已有先例）

| 设施 | 位置 | 复用方式 |
|:---|:---|:---|
| `window.grab().save(path)` 截图 | `main.py` 的 `setup_screenshot` | 同样的 grab 调用用于卡片级截图 |
| `--auto-screenshot` / `--screenshot-on-start` CLI | `main.py` 的 `parse_args` | 真机联调阶段整窗截图 |
| `QT_QPA_PLATFORM=offscreen` 无头渲染 | `scripts/render_logo.py` | 截图脚本统一 offscreen，无显示环境亦可跑 |
| 截图落盘目录约定 | `main.py` 的 `SCREENSHOT_DIR`（开发态 `PROJECT_ROOT/.tmp`） | 本项目遵守 AGENTS.md"临时文件必须存放在项目根目录内"，统一用 `./.temp/card_shots/`，禁止系统临时目录 |
| Python 解释器 | 项目 `.venv` | 强制使用，禁止系统全局 Python |

### 5.2 mock 截图脚本（新增 `scripts/shot_tool_cards.py`）

职责：构造一组覆盖全部症状场景的 mock 载荷 → 走真实建卡链路（`make_tool_card` + `apply_update`）→ 逐卡 `grab()` 存 PNG → 打印产物路径清单。

```
# scripts/shot_tool_cards.py

os.environ.setdefault("QT_QPA_PLATFORM", "offscreen")

SCENARIOS = [
    # (场景名, 建卡 payload, [update payload 序列])
    ("readmedia_kimi_首帧空壳",  {...tool_call 首帧无 rawInput...},
                                 [...in_progress 帧带 rawInput.path..., ...completed 帧带 text+image_url 出参...]),
    ("askuserquestion_问答对",   {...questions 入参...}, [...{"answers":{...}} 出参...]),
    ("agent_子代理",            {...description+prompt...}, [...结果正文...]),
    ("todolist_回执过滤",        {...todos...}, [...带 Ensure that you continue... 的出参...]),
    ("mcp_裸JSON出参",          {...}, [...minified JSON 字符串出参...]),
    ("mcp_长JSON不截断",         {...}, [...超 300 字符单行 JSON...]),
]

for name, call_payload, updates in SCENARIOS:
    card = make_tool_card(call_payload)
    for u in updates:
        card.apply_update(u)
    card.adjustSize(); card.resize(card.sizeHint())
    card.grab().save(f".temp/card_shots/{seq}_{name}.png")
```

要点：

- **mock 必须走真实链路**：建卡用 `make_tool_card` 工厂（验证 T5 分派），更新用 `apply_update`（验证 T1 回填、T4 图片渲染），禁止直接 new 卡片类绕过分派。
- **kimi 首帧空壳场景必测**：模拟"首帧无 rawInput → in_progress 帧补齐"的时序，验证入参回填。
- 图片 mock：生成一张小尺寸纯色 PNG 转 base64 内嵌（脚本内用 QPixmap 现场生成，不依赖外部文件）。
- 脚本同时输出一份 `manifest.md`（场景名 → PNG 路径 → 预期看点），便于逐张核对。

### 5.3 闭环流程（每个任务的 DoD）

```
修改代码
  → .venv/bin/python scripts/shot_tool_cards.py        # mock 渲染 + grab 截图
  → 用读图工具逐张查看 .temp/card_shots/*.png           # 视觉确认
  → 对照 manifest.md 的预期看点逐项打勾
```
