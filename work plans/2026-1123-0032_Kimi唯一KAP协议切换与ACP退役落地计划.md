## 1. 背景与目标

Kimi KAP 链路已作为 `kimi-kap` 增量接入并完成真实验收：普通轮、工具审批、后台通知轮交错追问、长任务、停止、服务重启后的会话恢复均通过，且绕开了 Kimi ACP 的通知轮提前收尾缺陷。当前实现仍是双协议并存：`DEFAULT_BACKEND = "kimi-acp"`，Kimi 下同时注册 `Kimi ACP` 与 `Kimi KAP`，KAP 仍标注为实验链路。

Kimi 官方正式维护的 Desktop/Web UI 链路使用 KAP；DSH 的对外协议则是 ACP。本项目因此按厂商选择协议，不做全库一刀切：Kimi 只保留 KAP，DSH、Local 继续使用现有 ACP。

目标：

1. Kimi 厂商唯一接口为 `kimi-kap`，出厂默认后台改为 `kimi-kap`，不再提供 Kimi ACP 菜单、工厂或运行时实现。
2. 老用户的 `kimi-acp` 设置、模型记忆和强度记忆安全迁移到 `kimi-kap`；已经使用 KAP 的用户选择不被旧值覆盖。
3. 删除 Kimi ACP 专属代码与对应测试，保留 KAP 仍复用的 `KimiUpdateMapper`、模型载荷、卡片和 presenter，避免误删共享设施。
4. 公共 ACP 传输层及 DSH、Local 行为零变化；不增加“KAP 不可用就回退 ACP”的隐式通道。
5. 文档、架构守卫、能力快照与真实 GUI 验收统一反映“Kimi = KAP”。

非目标：

- 不把 KAP 抽象成跨厂商公共协议，不把 KAP 私有字段移入 `providers/acp/`。
- 不修改 DSH、Local 的协议、启动参数、会话恢复或默认选择。
- 不建立 ACP 与 KAP 之间的服务端会话续接；旧 ACP 会话存档只保证文字回放。
- 不保留隐藏的 Kimi ACP 配置开关、兼容注册项或自动回退；需要回退时通过 Git 历史恢复完整版本。

## 3. 现状锚点

- `src/ide/llm/providers/kimi/spec.py` 当前同时声明 `SPEC`（`kimi-acp`）和 `KAP_SPEC`（`kimi-kap`），两者共享以 `kimi-acp` 为键的目录缓存。
- `src/ide/llm/registry.py` 当前注册序为 `kimi-acp`、`kimi-kap`、`dsh-acp`、`local-acp`，默认仍是 `kimi-acp`。
- `src/ide/gui/settings.py` 的 `DEFAULT_SETTINGS` 经 `DEFAULT_BACKEND` 取得初值；`load_settings()` 已具备旧权限键、旧全局模型键的读取迁移范式，但没有后台 ID 迁移。
- `model_versions` 与 `model_efforts` 都按接口实现名记忆。仅改默认值而不迁移，会丢失老用户已选模型/强度；若旧值直接覆盖已有 `kimi-kap` 条目，又会破坏已试用了 KAP 的用户选择。
- `src/ide/gui/panels/chat/model_bar.py` 已在接口总数为 1 时隐藏接口按钮，无需增加 Kimi 专属 UI 分支。
- `src/ide/llm/providers/kimi/kap/events.py` 复用 `models.py` 与 `updates.py`；`kap/provider.py` 只从公共 ACP 包借用中性 `PermissionRequest`、`TurnCancelled`，不借用 `AcpConnection`。
- `src/ide/llm/providers/kimi/provider.py` 是 Kimi ACP 运行时；`usage_poll.py` 只读 ACP 私有 wire；`permissions.py` 只解释 ACP `session/request_permission`。KAP 的审批/提问映射已经由 `kap/provider.py` 自行完成。
- `config/sessions/` 的 `SessionRecord` 保存接口实现名。旧记录中的 `kimi-acp` 在注销后由现有 `ModelBar` 失效回退到首个可用接口；该路径只回放历史文字，不携带 ACP session id，因此下一轮会建立新的 KAP 会话。
- `2026-1122-2308_KimiKapServer链路增量接入落地计划.md` 已记录 KAP 全量门禁 `373 passed` 与真实链路验收；本计划不再验证“KAP 是否可用”，而验证“成为唯一入口后没有旧链路残留与迁移回归”。

## 4. 设计决策

1. **唯一协议等于删除运行时，不只是隐藏菜单**：Kimi ACP 的注册项、工厂导出和专属实现一并退役，避免继续维护无人可用的代码。
2. **保留稳定后台 ID**：唯一接口仍叫 `kimi-kap`，不改名为 `kimi`；协议身份清晰，也避免第二轮无意义的配置迁移。
3. **界面标签保留 `Kimi KAP`**：便于诊断和文档对齐；`dev_note` 不再把它描述为本项目的实验性备选链路。上游 REST/WS schema 仍可能变化，该维护风险保留在维护手册，不等同于继续把 KAP 当备用后端。
4. **只迁移精确旧 ID**：`load_settings()` 仅识别 `model_backend == "kimi-acp"`；其他未知或手改后台值仍走现有失效回退，不擅自改成 Kimi。
5. **新值优先，旧值兜底**：两份记忆表均以已有 `kimi-kap` 条目优先；只有目标条目缺失时才接收 `kimi-acp` 旧值。迁移在内存返回值中移除旧键，读取本身不写盘，后续正常设置写回时旧键自然消失。
6. **旧全局模型键也参与迁移**：先完成现有 legacy `model_version` seed，再执行后台 ID 归一，确保更老配置不会绕过本次迁移。
7. **会话不跨协议伪装续接**：旧 ACP 存档可以继续显示历史；下一次发送是全新的 KAP 会话。不得把 ACP session id 填入 KAP，也不得宣称恢复原 ACP 上下文。
8. **失败显式，无自动回退**：CLI 缺失或低于 KAP 门槛时，Kimi 入口按现有机制显示不可用；不得启动 `kimi acp`，也不得静默切换厂商。
9. **共享设施按实际依赖保留**：`updates.py`、`models.py`、Kimi 卡片和 presenter 不属于 ACP 专属，不能随 `provider.py` 一并删除。
10. **公共 ACP 零改动**：KAP 继续只借用中性类型；DSH、Local 的连接、审批、terminal 分发和诊断路径保持原样。

## 6. 风险与注意点

- ⚠️ **可用性门槛提高**：Kimi 不再以 ACP 作为低版本 CLI 的退路；CLI < 2.7.0 时 Kimi 不可用是本计划的明确结果，不是回归。
- ⚠️ **旧会话上下文不可跨协议恢复**：文字存档可回放不等于 agent 上下文续接；验收和文档必须明确，不得伪造 session 映射。
- ⚠️ **共享映射误删风险**：`updates.py` 与 `models.py` 虽曾服务 ACP，现在仍是 KAP 事件适配核心；删除前以实际 import 为准，不能按文件名猜测归属。
- ⚠️ **测试误删风险**：部分名为 `kimi_min`、`kimi_turn` 的文件混有通用 UI 行为，必须迁移仍有效用例，不能为了测试变绿整批删除覆盖。
- ⚠️ **上游契约仍会演进**：本项目“转正”不改变上游 REST/WS 的兼容性事实；CLI 升级后继续核对 `openapi.json`、`asyncapi.json`、`kap.md`，未知事件降级而非阻断聊天。

### 8.3 经验沉淀

1. **协议退役先画共享依赖图**：Kimi 的 `updates.py` 和 `models.py` 虽由 ACP 链路定型，但已是 KAP 卡片适配核心；只能删除 `provider.py`、`usage_poll.py`、`permissions.py` 三个确认无 KAP 依赖的模块。
2. **配置迁移要放在旧 seed 之后**：legacy 全局 `model_version` 先按旧后台 ID 入表，再统一归一 KAP，才能覆盖更老配置；记忆表用 `setdefault` 保证已经试用 KAP 的新选择不被旧值覆盖。
3. **读取迁移与文件迁移应分离**：`load_settings()` 只改内存返回结构，后续正常写盘自然清除旧键；这样启动验证不会意外修改用户配置。
4. **存档恢复不等于协议续聊**：旧记录中接口 ID 的 UI 回退只决定新 provider，历史回放文本不会进入 agent 上下文；验收必须同时断言“文字可见”和“provider 历史为空”。
5. **单接口隐藏不需要厂商特判**：`ModelBar` 按接口总数自动显隐，注册表收口即完成底行 UI；设置中心是信息展示面，不应机械套用底行隐藏规则。
6. **测试不能按文件名整批删除**：`kimi_min_usage` 混有通用 GUI tick，`kimi_turn_ui` 混有通用忙碌/待发逻辑；先迁移有效覆盖，再删除 ACP 私有实现测试，避免用覆盖率换绿灯。
