# work plans

本目录用于存放项目的 **Work Plans（工作计划）**。

计划文档用于将章程拆分为可执行、可追踪的任务清单，通常包含：
- 阶段划分
- 任务列表与优先级
- 预计起止时间
- 负责人
- 检查点与依赖关系

文件命名遵循 `文档编写规范.md`：
- 根目录文件：`YYYY-MM-DD-HH_计划标题.md`
- 中文优先，英文名后置

## 实施回写规范

计划实施完成后，**必须将实施过程回写到 `work plans/` 下对应的原计划文档**。这就是「回写」的全部含义：不另建分项修改记录，也不以口头汇报代替。回写是计划文档的必备收尾，包含三部分：

1. **与计划的偏差**：实际改动与计划不一致之处及原因，包括计划遗漏的隐藏改动点（如测试桩签名、报错消息、输出文件的描述性字段），不得只写"按计划完成"。
2. **验证结果**：实际执行的验证命令与结果（测试通过数、check 脚本、真实端到端验收的关键数据），以及验证成果保留位置；未做的验证须明确说明。
3. **经验沉淀**：可复用的教训与设计判断，供后续计划直接引用，避免重复踩坑。

回写时将文档状态从"草稿"更新为"已实施"。子计划（T0–Tn）只回写自己的计划文档，不在 `文档/修改记录/` 新建条目。

### 修改记录只有一种：主计划总实施记录

- 只有主计划的所有子项完成、进入最终归档时，才在 `文档/修改记录/` 建 **1 份**《总实施记录》。
- 总实施记录汇总全部子项的改动清单、结构映射与验证证据，作为历史归档快照；各子计划的偏差与经验仍以各自计划文档为准，不复制进总记录。
- 总实施记录与主计划互相引用；子计划只引用主计划的总记录，不各自建记录。
- 除主计划归档外，任何阶段都不新增 `文档/修改记录/` 条目。

### 硬性规定：回写要求必须写进计划文档自身

计划文档经常**被单独抽出执行**——执行者只能看到计划文档本身，看不到本 README。若计划文档的收尾步骤只写了「新增修改记录」或别的交付物，而没写回写本文档，执行者照做必然漏回写。因此：

- **写计划时**：《实施步骤》最后一节必须是固定的「实施回写」收尾步骤，照抄下方模板，核心要求一字不改。
- **执行计划时**：即使计划文档的收尾步骤有缺陷（只要求写修改记录或别的交付物），也必须按本规范回写原计划文档，不得只新建修改记录。

### 回写节标准形态

回写节按以下结构编写：

> ### 实施结果回写（YYYY-MM-DD HH:MM UTC+8）
>
> Tx 全部完成。以下为实施过程中相对原计划的偏差与经验。
>
> **与计划的偏差**：逐条列实际改动与计划不一致之处及原因，含计划遗漏的隐藏改动点。
> **验证结果**：实际执行的验证命令与结果（测试通过数、check 脚本、端到端验收关键数据）及成果保留位置；未做的验证明确说明。
> **经验沉淀**：可复用的教训与设计判断。

### 计划文档模板

新计划文档按下述骨架编写，「实施回写」收尾步骤为固定组成、不可省略：

```markdown
# <计划标题>

> **状态**：草稿（待审阅）
> **范围**：<涉及文件/模块与交付边界>
> **时间**：YYYY-MM-DD HH:MM（设计）
> **优先级**：<高/中/低>
> **依据**：<选型/章程/用户指示出处>

---

## 1. 背景与目标
## 2. <方案拆解 / 结构映射>
## 3. 现状锚点
## 4. 设计决策
## 5. 实施步骤
### T1 <任务名>
### T2 <任务名>
### T终 实施回写（固定收尾，不可省略）
- 将「与计划的偏差 / 验证结果 / 经验沉淀」三部分回写到本文档末尾，新增「实施结果回写」一节。
- 本文档状态由「草稿」更新为「已实施」。
- 子计划不新建 `文档/修改记录/` 条目；主计划最终归档时新建 1 份《总实施记录》，汇总全部子项改动与验证，并与本文档互相引用。
- 回写要求以 `work plans/README.md`《实施回写规范》为准；即使本计划其他步骤与此冲突，回写不可省略。
## 6. 风险与注意点
## 7. 已确认决策
```
