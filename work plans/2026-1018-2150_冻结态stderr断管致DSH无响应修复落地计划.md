# 冻结态 stderr 断管致 DSH 无响应修复落地计划

> **状态**：已实施（打包验证由用户自行执行）
> **范围**：`main.py`、`src/llm/providers/`（dsh/local/reasonix/opencode/dream/kilocode 六家 ACP provider）、`src/gui/panels/chat/worker.py`、`src/gui/panels/terminal/screen.py`
> **时间**：2026-10-18 21:50（设计，UTC+8）/ 2026-10-18 21:55（实施）
> **优先级**：高

## 事件

用户反馈：最新打包冻结态（AppImage）中 DeepSeek Harness 发送消息后永久卡在「响应中…」，停止按钮无效，界面零反馈。开发态同机同凭据对话正常。

## 诊断结论（已核实）

1. **远端健康**：`scripts/spike_dsh_acp.py` 全链路实测通过（握手/会话/配置切换/对话/取消），证据 `文档/帧存档/dsh_spike_20261018_212837.json`。
2. **冻结态日志位置**：AppImage 实例写 XDG 配置目录 `~/.config/zen-studio/logs/zen-studio.log`（非项目内 `config/logs/`）。
3. **根因**（冻结态日志四次复现同一 traceback）：冻结态从桌面启动时 **stderr 是断管**；`_log_agent_info` 里 `print(..., file=sys.stderr)` 在 initialize 握手**成功之后**抛 `BrokenPipeError`，异常在 `session/new` 之前炸出——dsh 子进程建了半个会话即闲置（与「dsh 空转、零 TCP、`~/.dsh` 无活动」的现场完全吻合）。
4. **界面卡死零反馈的二阶原因**：worker 的 `except` 里 `traceback.print_exc()` 再次打 stderr 再抛 BrokenPipe，把紧随其后的 `finished_with_error.emit(...)` 跳过——错误卡片永不上屏、busy 态永不收尾；`cancel()` 因 session 未建成而空转，停止按钮形同虚设。
5. 开发态正常仅因终端里 stderr 有效；kimi 后台在冻结态正常，因其无 stderr 打印。

## 修复内容

统一原则：**运行期诊断输出一律走 logging**（logging handler 的 `handleError` 兜底保证即使 stderr 断管也不会向业务代码抛异常），禁止直打 stderr/stdout。

- 六家 ACP provider 的 `_log_agent_info`：`print(file=sys.stderr)` → `logger.info`，同步移除已无人使用的 `import sys`，docstring 注明断管缘由。
- `src/gui/panels/chat/worker.py`：`traceback.print_exc()` → `logger.exception`（关键修复——保证异常信号一定能 emit 到界面，busy 态不再死锁）。
- `src/gui/panels/terminal/screen.py`：pyte 解析兜底的 stderr print → `logger.warning`（同类隐患，顺手收掉）。
- `main.py`：Logo 缺失与工作区目录无效两处 print → `logging.getLogger("main").warning`（后者走 stderr，同属断管崩溃面）；`--screenshot` 调试链的 stdout 路径打印保留（截图脚本按 stdout 解析路径）。
