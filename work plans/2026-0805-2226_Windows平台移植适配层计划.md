# Windows 平台移植：单 Protocol + 独立适配包计划

## 1. 背景

用户决策链（2026-08-05 会话原话收敛）：

> 某些地方不能用在 Linux 上、或者兼容不好，我们直接抽象出来额外写一份适配 Windows 的。毕竟前端都是通用的，这样就不会因为为了适配 Windows 而把我们的代码搞乱，依然能保持纯净。

> 能不能更加抽象，将 Windows 的代码单独放到一个包里？

最终拍板架构：**一个 Protocol + 一个惰性工厂 + 一个 `platform_win/` 独立包**。全代码库仅一处平台判断（工厂内），Windows 实现整体隔离为一个可装卸的目录；Linux 实现作为默认后端原样保留，主库零污染。

### 1.1 抽象黄金分割点（已确认的设计边界）

| 差异类型 | 处置 | 例子 |
|---|---|---|
| **行为差异** | 进平台包 | 怎么起 PTY、怎么锁文件、配置目录放哪、怎么重启自己 |
| **数据差异** | 留原地，追加候选 | provider 的 CLI 安装路径表、`.exe` 后缀 |
| **打包链路** | 天然平行，不抽象 | AppImage 脚本 vs Windows 安装包 |

### 1.2 现成范式

`core/external_apps.py` 已验证该路线：平台判断收敛于注入点（`platform: str = sys.platform` 参数），业务代码不感知平台，测试以注入模拟分支。本计划将此范式从单点推广为全库唯一的平台缝合层。

### 2.2 规模事实

- 全项目约 95 个 Python 文件、1.9 万行；GUI 层全走 PySide6（跨平台），聊天/资源管理器/Git 图谱/查看器等面板**零平台假设**。

## 3. 设计

### 3.1 目标结构

```
core/
├── platform_api.py       ← 唯一缝合点：Protocol 定义 + 惰性工厂
├── platform_posix.py     ← 默认后端：现有实现的薄封装，语义一行不改
platform_win/             ← Windows 独立适配包（Linux 上从不被 import）
├── __init__.py           ← 组装：导出 WindowsBackend
├── pty.py                ← pywinpty（ConPTY）PTY 后端
├── filelock.py           ← msvcrt.locking 文件锁
├── config_dir.py         ← %APPDATA% 配置目录
├── relaunch.py           ← exe 重启
└── bin_probe.py          ← CLI 候选路径 Windows 扩展表（供 provider 查询）
building/
├── build_windows.ps1     ← 新增：PyInstaller Windows 构建入口
└── installer/            ← 新增：Inno Setup 脚本（可选，后置）
```

### 3.2 D1：缝合点——`core/platform_api.py`

```python
# core/platform_api.py
class PtyHandle(Protocol):
    """PTY 字节管道句柄：spawn 产物，不懂终端语义（pyte 的事）。"""
    def read(self) -> bytes: ...
    def write(self, data: bytes) -> None: ...
    def resize(self, rows: int, cols: int) -> None: ...
    def wait(self) -> int | None: ...
    def terminate(self) -> None: ...

class PlatformBackend(Protocol):
    def spawn_pty(self, argv: list[str], cwd: str, rows: int, cols: int) -> PtyHandle: ...
    def default_shell_argv(self) -> list[str]: ...
    def flock_exclusive(self, fd: int) -> None: ...
    def funlock(self, fd: int) -> None: ...
    def user_config_dir(self) -> Path: ...
    def relaunch(self) -> None: ...

_backend: PlatformBackend | None = None

def backend() -> PlatformBackend:
    """惰性选择平台后端——全代码库唯一一处 sys.platform 判断。"""
    global _backend
    if _backend is None:
        if sys.platform == "win32":
            from platform_win import WindowsBackend   # Linux 永不执行此行
            _backend = WindowsBackend()
        else:
            from core.platform_posix import PosixBackend
            _backend = PosixBackend()
    return _backend
```

设计要点：

- **惰性 import 是打包分流的关键**：PyInstaller 按 import 链收编，`sys.platform` 分支内的 import 在对侧平台上不被静态跟随（辅以 spec 级 `excludes` 兜底声明），Linux AppImage 不会打进 pywinpty，Windows 包不会打进 ptyprocess。
- 工厂缓存单例；测试可通过注入重置 `_backend`（延续 `external_apps.py` 的注入测试风格）。

### 3.3 D2：PosixBackend——现状薄封装，不是重写

`core/platform_posix.py` 的内容 = 把 `session.py` 的 PtyProcess 装配、`settings.py` 的 flock 调用、`paths.py` 的 XDG 解析、`main_window.py` 的 AppImage 重启**原样搬入**，接口对齐 Protocol。Linux 行为逐字节不变，回归风险归零。

### 3.4 D3：调用点改造清单

| 调用点 | 改造 |
|---|---|
| `gui/panels/terminal/session.py` | `PtyProcess.spawn(...)` → `backend().spawn_pty(...)`；shell 解析 → `backend().default_shell_argv()`；读写/resize/wait 经 PtyHandle |
| `gui/settings.py` | 两处 `fcntl.flock` → `backend().flock_exclusive(fd)` / `funlock(fd)`；删除 `import fcntl` |
| `core/paths.py` | `USER_CONFIG_DIR` 解析 → `backend().user_config_dir()`（XDG 规约整体迁入 PosixBackend） |
| `gui/main_window.py` | FUSE/AppImage 重启段 → `backend().relaunch()` |

改造后以上文件**不出现任何 `sys.platform` 字样**。

### 3.5 D4：Windows 后端各模块要点

| 模块 | 实现路线 | 备注 |
|---|---|---|
| `platform_win/pty.py` | `pywinpty.PtyProcess`（ConPTY） | API 与 ptyprocess 高度对称（spawn/read/write/setwinsize）；输出编码注意 UTF-8 强制 |
| `platform_win/filelock.py` | `msvcrt.locking(fd, msvcrt.LK_LOCK, 1)` | 标准库自带，零新依赖 |
| `platform_win/config_dir.py` | `%APPDATA%/zen-studio/`，缺省回退 `~/AppData/Roaming/zen-studio/` | 与 XDG 分支语义对齐：相对路径视为无效 |
| `platform_win/relaunch.py` | `os.execv(sys.executable, ...)` 或 `subprocess.Popen + sys.exit` | Windows 无 FUSE 挂载点问题，逻辑大幅简化 |
| `platform_win/bin_probe.py` | CLI 候选表：PATH → `%LOCALAPPDATA%/Programs/...` → npm 全局 `%APPDATA%/npm` | 供 provider `_find_bin()` 查询，见 D5 |

### 3.6 D5：数据级差异留原地（防过度抽象）

provider 的 `_find_bin()` 候选列表追加 Windows 条目，**不抽进平台包**——各 agent CLI 安装位置是 provider 自己的领域知识，强抽会让 provider 与平台包互相纠缠。`platform_win/bin_probe.py` 仅提供「通用目录常量 + `.exe` 后缀工具函数」，选择权留在 provider：

```python
# llm/providers/kimi_common.py（改造示意：追加，不改主链）
candidates = [which("kimi"), ...]  # 现有三级链原样
candidates += backend().extra_bin_candidates("kimi")  # 非 Windows 返回 []
```

PosixBackend 的 `extra_bin_candidates` 返回空列表，Linux 路径零行为变化。

### 3.7 D6：依赖与打包分流

`pyproject.toml`：

```toml
# pyproject.toml（dependencies 节选）
"ptyprocess>=0.7.0; sys_platform != 'win32'",
"pywinpty>=2.0; sys_platform == 'win32'",
```

- 环境标记（PEP 508）使 uv/pip 按平台解析，Linux 环境连装都不装 pywinpty。
- `building/zen-studio.spec` 增设 per-platform `excludes`；新增 `build_windows.ps1`（PyInstaller 调用 + 产物校验），与 AppImage 链平行互不引用。
- Inno Setup 安装包脚本列为可选后置项（首版绿色 zip 即可）。

## 6. 风险

| 风险 | 等级 | 缓解 |
|---|---|---|
| ConPTY 渲染/转义行为与 xterm 差异（pyte 解析边界） | ⚠️ 中 | PtyHandle 接口已隔离字节管道；差异集中在 T6 实测调优，不回流主库 |
| Agent CLI 在 Windows 不可用或安装路径混乱 | ⚠️ 中 | D5 候选表机制 + T6 可用性矩阵；不可用的 provider 按现有「二进制缺失」降级路径处理，无需新机制 |
| PyInstaller 误收对侧平台依赖 | 🟢 低 | 惰性 import + spec excludes 双保险；构建脚本加产物审计步骤（检查包内无 pywinpty/ptyprocess 错配） |
| 抽象层过度设计诱惑 | 🟢 低 | §1.1 黄金分割点已拍板：数据差异留原地，禁止为「统一」而抽 |
