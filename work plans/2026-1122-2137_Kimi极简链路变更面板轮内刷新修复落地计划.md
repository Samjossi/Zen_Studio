## 1. 背景与目标

### 1.1 问题

历史问题“AI 在长任务中连续修改文件，但右栏下变更面板直到整轮结束才一次性显示变更”曾于 2026-10-22 修复。当时的第六刷新事件源为：改盘类工具终态帧触发 `files_maybe_changed`，经 `ChatTabs` 转发到 `GitStatusController`，再由既有 300ms 去抖执行 Git 刷新。

现行代码中的 GUI 信号与接线仍在，但 Kimi 极简链路没有向工具终态载荷传递刷新判定所需的 `tool_kind`，导致该事件源对 Kimi 实际失效，只剩轮次结束时的 `turn_finished` 兜底。

### 1.2 已确认的直接断点

1. `src/ide/llm/providers/kimi/updates.py` 的 `_map_tool_call()` 会把首帧显式 `kind` 写入 `payload["tool_kind"]`。
2. 同文件 `_map_tool_call_update()` 虽读取更新帧的 `kind`，却没有写入 `ToolUpdatePayload`；即使终帧明确携带 `kind="edit"`，映射后的载荷仍没有 `tool_kind`。
3. `src/ide/llm/providers/kimi/models.py` 的 `ToolUpdatePayload` 也未声明该字段。
4. `src/ide/gui/panels/chat/vendors/kimi/presenter.py` 只透传标题、命令等路由信息，不补工具类型；其 `is_fs_mutation_terminal()` 要求终态载荷同时具有 `status=completed/failed` 与 `tool_kind=edit/execute`。
5. 因此 `src/ide/gui/panels/chat/panel.py` 中既有的 `files_maybe_changed.emit()` 无法由当前 Kimi 工具终帧触发。

设计前已用项目 `.venv` 直接调用真实 `KimiUpdateMapper`：同一 `edit` 调用的首帧载荷含 `tool_kind="edit"`，`completed` 终帧载荷只有 `tool_call_id` 与 `status`。这与用户所见“轮中不刷、轮末集中出现”形成完整因果链。

### 1.3 目标与成功判定

1. Kimi 的 `edit/execute` 工具到达 `completed/failed` 时，轮次进行中即可触发现有 Git 刷新；正常仓库负载下，变更随各次工具完成逐条出现，不等整轮结束。
2. 更新帧显式携带 `kind` 时准确保留；更新帧省略 `kind` 时，从同一 session、同一完整 `toolCallId` 的首帧继承可信类型。
3. `read/search/fetch/think/other` 与 `in_progress/pending` 不触发该实时源；缺少可信类型时保持静默，不按工具标题猜测。
4. 官方 ACP 若输出带子调用 ID 的嵌套工具帧，沿用同一映射和信号路径；不恢复私有 wire 子代理旁路。
5. 现有 300ms 去抖、轮末兜底、文件树着色、查看器徽标、变更面板与状态栏统计的统一扇出不变。
6. 自动化、离屏信号链和真实 Kimi 多文件长任务验收通过，DSH/Local 与 Kimi 极简轮次契约无回归。

### 1.4 明确不做

- 不修改 `src/ide/gui/panels/chat/panel.py`、`src/ide/gui/panels/chat/tabs.py`、`src/ide/gui/main_window.py` 或 `src/ide/gui/controllers.py` 的生产逻辑。
- 不新增递归文件系统监视器，不新增第二套 Git 刷新定时器，不缩短或取消既有 300ms 去抖。
- 不恢复 `turn_state.py`、drain、同步提示、待发闸门、`session/close` 停止分流或私有终态判断。
- 不读取 wire 来判断工具是否落盘，不恢复子代理 wire 合成帧。
- 不按 `ReadMediaFile`、`TodoList` 等工具名反推改盘类型，不改变 Kimi“显式 kind 可信”的现行约定。
- 不修改 DSH/Local 的映射器、presenter 或协议语义。
- 不处理本工作区同时进行的 Kimi 用量恢复等无关改动，不提交、不推送。

## 3. 设计决策

### D1 在 Kimi 映射器修复载荷，不在 GUI 加厂商特例

工具类型属于 ACP 帧投影的一部分，应在 `KimiUpdateMapper` 内形成自洽载荷。GUI 已定义清晰且厂商中立的消费条件，继续保留现有 `ChatPanel → ChatTabs → MainWindow → GitStatusController` 链路，可避免在公共面板读取 Kimi 原始字段或复制一套类型账本。

### D2 显式类型优先，首帧账本只补缺失字段

拟在 `KimiUpdateMapper` 内增加以 `(session_id, tool_call_id)` 为键的私有工具类型账本：

- 首帧到达时记录该调用的显式 `kind`，包括 `other`，不得只登记改盘类型。
- 更新帧携带非空字符串 `kind` 时直接使用，并同步账本；不得让首帧旧值覆盖更新帧的新显式值。
- 更新帧省略 `kind` 时才读取账本；命中后写入 `payload["tool_kind"]`。
- 首帧与更新帧都没有可信类型时不填默认值、不按标题猜测，现有判定自然不刷新。
- 嵌套调用使用完整层级 `toolCallId` 作为键的一部分，父 ID 只负责现有卡片路由，不参与账本匹配。
- `reset()` 清空账本；`completed/failed` 载荷完成赋值后清理该调用条目，防止长期会话累积和同 ID 复用串值。清理不得影响本次终态判定。
- 账本会话键不可省略，避免同一 provider 恢复会话或不同会话出现相同工具 ID 时串值。

该账本只保存协议已明确提供的类型，不引入工具名启发式，也不判断轮次是否结束，不属于极简重写所删除的防御层。

### D3 终态语义和刷新成本保持历史定稿

- `completed` 与 `failed` 都提示“可能改盘”，因为失败的多步编辑仍可能部分落盘。
- `in_progress` 不刷新，避免写盘尚未完成时读取旧 Git 状态。
- `execute` 继续覆盖命令行重定向、代码生成器等改盘形式；其代价是一次经去抖合并的 Git 查询。
- 连续工具终帧仍复用同一个 300ms `QTimer`，不得为追求逐文件上屏而绕过去抖直接调用 `refresh()`。

### D4 以真实长任务验收，不用单测代替用户场景

自动化负责证明字段与信号链恢复，真机负责证明 Git 数据最终进入右栏变更面板。只有整轮结束才出现的旧现象消失，且多个文件在轮中依次出现，才算本计划闭环。

## 5. 风险与注意点

| 风险 | 影响 | 控制 |
