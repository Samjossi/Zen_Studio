# 用量徽章轮次内实时刷新计划

> 现状徽章只在「一轮 prompt 收尾」时刷新一次。一轮之内（agent 可能跑几十次工具调用、持续数分钟）用量持续攀升，用户完全无感。本计划让徽章在轮次内随子步骤增量刷新，覆盖当前默认后端 kimi-acp；kilocode/opencode 受 agent 推送时机约束，维持现状并文档说明。

## 1. 问题确认（实证结论）

**代码里确实存在该问题，且是设计使然，四个后端无一幸免。**

徽章刷新链路本身无延迟——`panel.py:633-637` 收到 `Chunk("usage")` 立即刷新 `_refresh_usage_label()`。瓶颈在**用量数据的产生时机**：

| 后端 | 用量数据来源 | 到达时机 | 轮次内刷新 |
|:---|:---|:---|:---|
| kimi-acp（当前默认，`config/settings.json` `model_backend`） | kimi ACP **不推** `usage_update`（1412 T5 实测），IDE 轮次收尾改读 `~/.kimi-code` 会话落盘 `wire.jsonl` 末条 `usage.record`（`kimi_acp.py:246-288`） | **收到 prompt response 后**，短轮询 ≤3s 等异步写盘 | ❌ 全程零刷新 |
| kilocode-acp / opencode-acp | ACP `usage_update` 推送（`acp.py:385-387`） | **每轮一条**（`panel.py:131` 注释口径），轮次边界到达 | ❌ 轮次内不推 |
| reasonix-acp | 同上 ACP 推送 | 同上 | ❌ 同上 |

用户场景还原：一轮任务内 agent 循环调用工具几十次，上下文从 20% 爬到 76%，徽章在整个过程中停留在上一轮的 20%，任务结束瞬间跳到 76%。

### 1.1 kilocode 源码级实证（2026-08-02 01:32 补，调研 `参考代码/kilocode-main`）

「每轮一条、轮末才推」在 kilocode 源码中得到确证，且**协议层面 client 无任何手段要求更频繁推送**：

| 结论 | 证据（kilocode-main 内路径） |
|:---|:---|
| `usage_update` 唯一触发点是轮末 | `packages/opencode/src/acp/service.ts:494-527`：`sdk.session.prompt()` **HTTP 阻塞至整个 agent loop 跑完**，返回后才执行行 525 `sendUsageUpdate`；slash/summarize 路径同理（行 547、567） |
| 轮次内事件流不含用量 | `acp/event.ts` 订阅 SSE 只转三类事件：`message.part.delta`→文本/思维链 chunk、`message.part.updated`→tool_call、`permission.asked`——**无 token/usage 类推送** |
| 轮末推送的数据来源 | `sendUsageUpdate` 用 HTTP SDK `sdk.session.messages()` 拉全部消息，取**末条 assistant 消息** tokens（`service.ts:618-644`），`used = input + cache.read`（input 已扣缓存）、`size` = models.dev context limit、`cost` = 会话累计 |
| 用量非本地估算 | 每个 LLM step 的 `finish-step` 事件携带 provider API 原始 usage（`src/session/processor.ts:869-873`），经 `session.ts:404-488` 归一化写入 assistant 消息 |
| ACP 协议无频率约束、无请求用量手段 | `@agentclientprotocol/sdk@0.21.0` 中 `UsageUpdate` 标注 UNSTABLE/experimental；`session/update` 是纯通知，发送时机完全由 agent 自定；initialize 的 client capability 无用量相关开关（`service.ts:91-138`） |
| **轮次内数据其实已存在** | 每个 step 的 `step-finish` part 都带 `tokens`/`cost`（`processor.ts:926-940`），只是 `acp/event.ts` 没订阅转换。若给 kilocode 打补丁在 event.ts 订阅对应事件转 `usage_update`，推送型后端也能轮次内刷新（见 §4 D4 补记） |

## 2. 目标行为

| 场景 | 现状 | 目标 |
|:---|:---|:---|
| kimi-acp 长任务进行中 | 徽章停留上一轮数值 | 轮次内随子步骤增量刷新（秒级间隔） |
| kimi-acp 任务收尾 | 收尾读 wire.jsonl 刷新一次 | 保持（作为兜底真值，不被轮次内估值覆盖语义破坏） |
| kilocode / opencode / reasonix | 轮次边界一条 | 维持现状（推送时机由 agent 决定，IDE 侧无法强求，见 D4） |
| 停止 / 报错 / 切后端 | 徽章行为各异 | 计时器随轮次状态机启停，不残留空转 |

## 4. 设计要点

### D1 轮询放 GUI 侧 QTimer，不动协议层与 worker

worker 线程阻塞在 `conn.next_update()`（`acp.py`），无法在其循环内插桩轮询；给 `next_update` 加超时属协议层侵入，复杂且影响四后端。GUI 侧 `QTimer` 直调 `provider.poll_usage()` 只读文件、与 ACP 连接零交互，无线程安全问题（`_session_id` 只读；读文件失败静默返回 `None`）。读取须控制成本：wire.jsonl 随会话增长，轮询只读文件尾部（seek 尾端回溯取末若干行），禁止全文件 `read_text`。

### D2 轮次内轮询与收尾基线语义分离

收尾 `_poll_wire_usage` 卡「条数 > 轮初基线」是为防误读上一轮记录；轮次内轮询语义相反——**就要最新一条**，无论属于本轮哪个子步骤。两者并存：轮次内轮询给实时感，收尾基线轮询给最终真值（覆盖轮次内可能漏掉的最后一跳）。`poll_usage` 不复用 `_poll_wire_usage`，独立薄封装 `_read_wire_usage`。

### D3 数据可行性前置验证（T0 spike，开工第一步）

未知点：kimi-code 在**一轮之内**的每次内部 API 调用后是否增量向 wire.jsonl 写 `usage.record`（`usageScope == "turn"`）。1454 计划仅实证了「prompt response 后 1~3s 写盘」。验证方法：起一个真实长任务（多轮工具调用），任务进行中 `tail -f` wire.jsonl 观察记录写入节奏。

- 若轮次内每次子响应都写 → 本计划成立，按 §3.2 实施。
- 若只在轮次末才写 → kimi 轮次内刷新**无数据源**，本计划降级为「仅文档说明限制」，不得臆造估算值（D4 红线延伸）。

### D4 推送型后端不造假（IDE 侧）

kilocode/opencode/reasonix 的 `usage_update` 由 agent 决定推送时机（kilocode 源码实证见 §1.1：轮末唯一触发，协议无频率协商手段），IDE 侧无中间数据可挖。不插值、不估算、不按 token 流长度臆造百分比——维持轮次边界刷新，在本计划实施记录与 `llm/README.md` 注明该限制。

**D4 补记（上游补丁路径，本计划外可选）**：kilocode 轮次内每个 LLM step 的 `step-finish` part 已携带 `tokens`/`cost`（kilocode-main `processor.ts:926-940`），数据并不缺，缺的只是 `acp/event.ts` 没把它转成 `usage_update`。若后续给 kilocode 打补丁（event.ts 订阅 step-finish 类事件 → `connection.sessionUpdate("usage_update")`，复用 `usage.ts` 的定型逻辑），推送型后端即可获得轮次内刷新能力，IDE 侧 `Chunk("usage")` 通用管道零改动即可消费。opencode 上游同源同理。此路径属 agent 侧改造，不在本计划范围，仅记录可行性。

### D5 计时器生命周期挂接轮次状态机

启动点 `_on_send`（`panel.py:597`），停止点 `_on_finished`（688）/ `_on_stopped`（706）/ 后端切换（210 附近清零处）。间隔 2s（对齐实测 usage.record 1~3s 写盘节奏，再密无意义）。多标签各自独立计时器，随 tab 销毁。

## 6. 验证标准

- kimi-acp 跑一个含 ≥5 次工具调用的任务，徽章在任务进行中至少刷新 2 次，数值单调爬升（允许 cache 命中导致的持平）。
- 收尾后徽章终值与轮次内最后一次刷新值一致或略高（收尾真值兜底），不出现回落跳变。
- 停止任务、任务报错、切换后端后计时器停止，无后台空转（日志/断点确认）。
- kilocode 后端行为与实施前逐行等价。

## 7. 红线

- 不臆造用量数值：无数据 → 徽章保持现状或隐藏，绝不显示估算百分比。
- 不改 `acp.py` 协议层、不改 `worker.py` 线程模型。
- 轮询只读文件尾部，禁止每 2s 全量读取可能达 MB 级的 wire.jsonl。
- 非 kimi 后端零行为变化（`poll_usage` 默认 `None`，计时器 tick 空转成本可忽略，或按 provider 类型条件启停——实施时取更简单者）。
