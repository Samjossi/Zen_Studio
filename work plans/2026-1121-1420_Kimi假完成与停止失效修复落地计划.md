## 1. 背景与目标

### 1.1 事故一句话

Kimi CLI 在轮次仍在执行时提前向 ACP 返回 `end_turn`；客户端把这条回执当作“本轮真正结束”，于是界面假完成、排队文本自动注入忙态 agent、完成音反复播放；假完成又清空了 `_turn_id`，`session/cancel` 变成 no-op，而客户端从未实现官方 `session/close`，隐藏通知轮再也停不下来。

### 1.2 为什么现在必须修

- 11-20 09:26 已诊断出同一问题，随后落地的 `kimi_turn_consistency.py`（276 行）、`_drain_turn_consistency`、`mark_stalled`、turn_sync 提示与 Kimi 看门狗，在 11-20 22:42 的 `85cf8aa` 中被整体移除，前提是“官方单轮次契约可信”。
- 11-21 13:41 与 13:53 两次复验证明该前提不成立：2.7.2 仍提前 `end_turn`，且新增“用户 turn 仍在执行、没有第二个 prompt 也提前回 `end_turn`”的表现。
- 当前代码没有任何防线：Kimi 的 `stall_watchdog=False`、没有 `session/close`、`purge_updates()` 缺失、完成播报只看 response。用户侧表现为“按钮变灰、一按就完成音、AI 不再回答、会话像断了”。
- 13:53 事故的孤儿轮次在界面“完成”后又跑了 11 分 51 秒、66,416 输出 token，并自行写了一份事故报告——这不是提示音误报，是执行生命周期完全脱钩。

### 1.3 本期目标

1. **假完成归零**：ACP `end_turn` 到达但 Kimi 真实轮次未结束时，界面不进入完成态、不播完成音、不写成功历史。
2. **自动待发归零**：通知轮/孤儿轮活跃期间，排队文本不得自动进入 `session/prompt`；文本驻留输入框，可编辑、可取消。
3. **停止真正生效**：假完成或通知轮活跃时，停止按钮能通过 `session/close` 终止 agent 内部轮次并回收后台子进程；切后端/关标签同样走关闭路径。
4. **状态可见**：同步/排空期间保持 busy、停止可用，输入区明确显示“Kimi 后台轮次同步中”，不再出现“看起来完成、实际还在跑”。
5. **不回归**：正常 Kimi 对话、手动停止、断管恢复、DSH/Local 行为、用法与用量展示不变；`85cf8aa` 的“不自动杀 Kimi”决策不被顺手回滚。
6. **可验证**：用 13:53 事故夹具与冻结态 AppImage 的 Prompt A/B 复验，给出 0/0/0 的硬指标（假完成、自动注入、孤儿轮增长）。

### 1.4 非目标

- 不修改 Kimi CLI 安装、配置或任何项目外文件；不把上游 issue 当作本期交付。
- 不恢复 10 分钟自动中断（`2026-1120-2134` 明确取消，改为用户手动停止），只把“停止”做成真的可用。
- 不把私有 wire 解析扩散到 DSH/Local 或公共 ACP 层。
- 不自动重放原 prompt、不自动 `session/resume`、不静默 `session/new`。
- 不用固定 sleep 或“等几秒没新帧就算完成”代替状态判定。
- 不借机重构与本次无关的卡片、主题或终端逻辑。

## 4. 设计决策

### D1 官方契约为唯一主链路，终态确认只做“风险轮次”

正常 Kimi 对话仍以 `session/prompt` 响应为主信号，不引入第二个常驻状态机、不改公共 ACP 路由。只有出现风险证据时才进入核对：`trigger=notify` 的轮次、用户轮未落盘/未完成、最后一步为 `tool_use`、存在未终止的后台任务。无风险轮次保持现有路径，避免把私有 wire 变成所有后台的前置条件。

### D2 恢复轻量 wire 元数据跟踪器（Kimi 包内）

新建 `src/ide/llm/providers/kimi/turn_state.py`，从 `85cf8aa^` 的 `KimiTurnTracker` 裁剪而来，只解析元数据：

- 字节游标 + 残行缓冲，支持增量读取；轮次开始时由 `chat()` 记录 `wire.jsonl` 当前 size 作为起点；
- `turn.prompt` 的 `promptId/turnId/origin.kind/trigger`、`prompt.steered`、`step.end.finishReason`、`turn.ended`、`prompt.completed`、`task.started/task.terminated`；
- 不保存 prompt 正文、工具参数、工具输出、diff；
- 文件缺失、半行、截断、未知记录、JSON 损坏一律不抛异常，落到 `missing/broken` 标记。

边界：模块只被 `kimi/provider.py` 引用，公共 `acp/` 层不感知；DSH/Local 不引入。

### D3 四态判定，禁止一个布尔值打天下

| 状态 | 判定 | 界面与动作 |
|:---|:---|:---|
| `normal` | 用户轮完整 `completed`、最后一步 `end_turn`、无活跃通知轮、无未终止后台任务 | 走现有成功路径，只收尾一次 |
| `draining` | response 已到，但通知轮/后台任务/用户轮仍未落定 | 保持 busy，继续消费 update，显示“同步中”，不播完成音、不发待发；停止可用 |
| `desynchronized` | 用户 prompt 缺失且超时、用户轮未完成却已响应、最后一步 `tool_use`、终态不是 `completed` | 等 agent 安全空闲后走失配收尾（非成功），保留卡片、回滚可重发历史、保留草稿，禁止重放 |
| `unknown` | 已进入风险核对但 wire 不可读/损坏/信息不足 | 风险轮次 fail closed：保持 busy，显示“无法确认终态，请核对后停止”，不播成功；无风险轮次不进入此态 |

判定复用 `85cf8aa^` 的 `snapshot()` 语义，但把“用户 prompt 缺失”的等待改为有界确认窗口（模块常量 `PROMPT_GRACE_MS=1500`，v1 不暴露用户设置），不再依赖固定长 sleep。

### D4 draining 期间可见、可控，不制造第二个隐藏后台

- 保持当前 worker 与 `_busy=True`，不新建 provider、不新建标签、不自动 `resume`；
- 继续消费 `session/update`，编辑卡片、工具结果、todo 照常上屏；
- 输入区显示“Kimi 后台轮次同步中…（完成与自动待发已暂停）/ ■ 停止”；
- 停止按钮始终可用，走 D7；
- 连续通知由同一个 drain 循环吸收，不为每个通知新建 worker。

### D5 失配 fail-closed，恢复但不重放

- 失配走非成功收尾：保留已显示正文与工具卡，回滚可重发的用户消息，取消待发，草稿保留在输入框；
- 不播完成音、不写成功历史、不发桌面通知；
- 标记 `recovery_pending`（复用现有能力位，但日志/文案区分“连接失效”与“轮次失配”两种原因），只有用户下一次**手动**发送才重建连接并 `session/resume`；
- 原 prompt/追问自动重放次数必须为 0；
- 恢复失败继续 fail-closed，不静默新建空会话。

### D6 provider + GUI 双层闸门

- provider：`begin_turn()` 前检查 `purge_updates()`，并在 drain 未落定时**立即拒绝**新的 `session/prompt`，抛可识别的 `TurnBusy` 异常（不阻塞、不自动重试）；GUI 捕获后保持草稿与排队态，等真实落定再允许发送；
- GUI：`_fire_pending_send()` 只在 `real_completion=True` 时执行；draining/失配/停止路径一律不补发；
- 两层共享同一个状态来源（provider 的 `turn_busy`/快照），GUI 不另建互相矛盾的布尔标志。

### D7 实现 `session/close`，让停止与关闭真正生效

- `initialize` 记录 `sessionCapabilities.close`；
- 新增 `AcpConnection.close_session(session_id)`，走同步 `request()`，超时短（如 2 秒），失败只记日志不杀连接；
- `KimiProvider.cancel()`：
  - 有活跃 `_turn_id` 且无通知风险 → `session/cancel`（轮次级，保留连接）；
  - 面板仍 busy 且快照为 `draining/desynchronized`（含 `_turn_id is None` 的假完成后场景）→ 直接 `session/close`（会话级，停内部轮与后台子进程）；
  - 空闲/无活跃轮次时按停止不产生动作（按钮此时本应禁用）；
- 标签关闭、切后端、应用退出：先 `session/close`，再 `terminate()` 兜底；
- `session/close` 成功后：清空 provider 的活跃会话态，但**保留 `sessionId`**；用户下一次手动发送只尝试一次 `session/resume`，失败则 fail-closed 并提示，不静默 `session/new`；
- CLI 未声明 `close` 能力时：回落 `session/cancel` + 明确日志与界面提示，不假装已停止。

### D8 完成播报只认真完成

`turn_completed.emit(True)` 与声音/桌面通知只在 `normal` 且 `real_completion=True` 的分支发出；`draining` 不发声，`desynchronized` 走失败提示，`unknown` 不发声。

### D9 清理、诊断与 2.7.2 容错

- `chat()` 开轮前 `conn.purge_updates()`；
- 轮末结构化日志（不记正文）：ACP request/response id、`stopReason`、sessionId、generation、wire 状态、用户 `promptId/turnId`、最后 `finishReason`、活跃通知 id、`taskId`、判定结果与原因；
- 2.7.2 容错：核心判定用 `turn.ended` + `prompt.completed` + 活跃通知/任务；`step.end/finishReason` 只作增强证据——出现 `tool_use` 直接判 `desynchronized`，缺失时不单独判 `unknown`，也不据此误判 `normal`。

### D10 尊重“不自动杀 Kimi”的既定决策

`stall_watchdog=False` 保持不变，不恢复 10 分钟自动中断。替代方案：

- 长任务可见：状态行/占位符显示已运行时长（如“Kimi 后台轮次同步中，已 6 分 12 秒”），不弹模态；
- 停止可用：D7 保证用户随时能真正停；
- 可选设置项“长任务提示阈值”（默认 5 分钟，0=关）只影响文案，不触发中断。

### D11 既有测试口径调整

`85cf8aa` 新增的测试里有若干条锁定了本次要修的前提，必须显式改写并在计划回写中说明理由：

| 测试 | 旧断言 | 新口径 |
|:---|:---|:---|
| `test_i3_wire_cannot_override_end_turn` | wire 不可推翻 `end_turn` | 拆成 5 条矩阵：正常成功、notify 活跃 drain、用户轮未完成 desync、wire 缺失 fail-open、wire 损坏 + 风险 unknown |
| `test_i6_next_prompt_after_stop_has_no_old_drain` | 停止后下一轮无 drain | 保留“无旧 drain”语义，但允许风险轮次的 drain；新增 purge 断言 |
| `test_i7_i8_kimi_never_runs_stall_watchdog` | Kimi 不跑看门狗 | **保持不变**（D10），另加“长任务只显示、不自动停”的测试 |

### D12 降级与兼容

- 所有新逻辑只对 `kimi-acp` 生效，DSH/Local 走原路径。

## 9. 实施结果回写（2026-11-21 14:55 UTC+8）

T0–T6 全部完成，T7 开发态真实链路验证通过。以下为实施过程中相对原计划的偏差与经验。

### 与计划的偏差

1. **`TurnDesynchronized` 消息前缀中性化**：异常消息由"Kimi 轮次状态失配"改为"轮次未确认完成"（GUI 按前缀分流 `[未完成]`/`[请求失败]` 与恢复提示）。原因：`tests/test_provider_boundaries.py` 守卫禁止 GUI 通用层字符串常量出现厂商显示名，GUI 无法匹配带"Kimi"的前缀；口径沿用项目既有的 `error.startswith("原会话恢复失败")` 匹配模式。
2. **`_turn_pending` 语义扩展**：计划仅要求失配时置位；实施为"draining/unknown 期间置位、normal 清零"的状态机。原因：D7 停止分流依赖该标志区分"假完成/通知轮活跃"（cancel_turn 返回 False 且 turn_pending=True 才回落 `session/close`）；仅在 desync 置位会导致 drain 中被停止时漏发 close。
3. **`close_session()` 成功后置 `_needs_recovery=True`**：计划只说"清空活跃会话态、保留 sessionId"；实测发现不置恢复态则下一次发送直接复用旧连接发 prompt（agent 侧会话已关闭），不会走 `session/resume`。
4. **GUI 停止/关闭路径零改动**：计划的"GUI `request_stop()` 在 draining/desync 下走 close_session、标签销毁/切后端统一先 close"全部收敛进 `provider.cancel()` 与 `provider.close()` 内部，GUI 现有调用点自动获得新语义。比计划在 GUI 层改调用更内聚，DSH/Local 不受影响。
5. **长任务提示阈值为模块常量 60 秒**（`ChatPanel._LONG_TASK_HINT_S`）：计划 7.2 建议默认 5 分钟设置项。设置项需动 `AppSettings`/`DEFAULT_SETTINGS`/设置对话框 UI，本期降级为常量（0=关），暴露设置项留待后续。
6. **`TurnConsistencySnapshot` 增加 `user_ended_at_ms`**：wire `turn.ended` 记录自带的毫秒时间戳透传，A10"仅凭日志重建 response/turn.ended/判定时序"需要它（计划字段清单未列）。
7. **`_confirm_turn_end` 返回 `(snapshot, last_push)` 元组**：drain 期间消费到的末次 usage push 回传轮末用量收尾，避免 drain 帧丢失用量（计划未明示返回形态）。
8. **既有测试断言修正（D11 精神）**：`test_i13` 原桩 `_fire_pending_send` 恒返回 True，掩盖了"接续轮补发成功时不播完成音（留给接续轮收尾）"的真实语义；新 harness 复用真实方法体后断言改为"补发成功 → 不 emit turn_completed；无待发 → emit(True)"。`test_i14` 中断形态从 RuntimeError 放宽为 `(RuntimeError, TurnAborted)`——`close()` 先 `close_session()`（内含 `abort_turn`），本地中断先于死讯。
9. **D6 GUI 闸门用鸭子读取**：`getattr(provider, "turn_pending", False)`，DSH/Local 无此属性时默认 False（同 `capabilities_of` 的中性读取模式）。

### 经验沉淀

1. **GUI 通用层厂商名红线**：任何要在 GUI 匹配/显示的厂商文案，源头就用中性前缀（异常消息、status 文案经 `BACKEND_LABELS` 组装），否则边界守卫全量测试阶段才爆，返工成本高。
2. **fail-open 的准确门槛**：tracker"从未读到任何字节 + 无任何证据"才 fail-open；"wire 存在但为空 + response 已收"是 prompt 未落盘路径，必须走 draining→desync（若把它也 fail-open，"上游吞消息"将永远被判成功）。文件不存在与文件为空是两种语义，测试时序要分开构造。
3. **`start_at_end` 测试陷阱**：tracker 构造即跳文件尾，预写全量事件的测试会假阴性（读不到 → user None → 错误判 desync）。正确姿势：空文件构造 + 回调分拍写入（模拟真实落盘时序），或"取出 response 前预写"（模拟 wire 早于 end_turn 落盘的真实时序）。
4. **`session/close` 后必须置恢复态**：close 只是协议层的会话终止通知，provider 状态机要主动把"下一次发送"导航到 resume；否则旧连接直接发 prompt 到已关闭会话，行为取决于上游容错（实测 Kimi 直接报错）。
5. **接续轮完成音语义**：补发接续成功时 `turn_completed` 不 emit（busy 不间断，完成音留给接续轮收尾）——简化测试桩曾把这条语义掩盖成"恒 emit"，测试桩应尽量复用真实方法体。
6. **上游 2.7.2 实测确认**：Prompt A 类场景（后台任务 + `tool_use` 收尾 + 通知 steering）稳定触发提前 `end_turn`；`finishReason=tool_use` 判 desync 与 13:53 事故报告的两份独立结论一致，四态判定对该序列的覆盖是完备的。
