# 启动模式设置与最后关闭项目恢复计划

> **状态**：已实施（2026-09-05）
> **范围**：`main.py`、`gui/settings.py`、`gui/settings_dialog.py`、`gui/recent_projects.py`、`gui/main_window.py`
> **时间**：2026-09-05 20:25（UTC+8）（设计）/ 2026-09-05 20:37（实施）
> **优先级**：中

---

## 0. 背景与目标

### 0.1 问题现象

用户同时打开项目 A 与项目 B 两个窗口，先关 B 再关 A，下次无参启动程序时恢复打开的却是 **B**，而非用户最后离开的 A。

### 0.2 根因（已查明）

- 记录时机在**窗口启动**：`gui/main_window.py` 的 `_init_recent_projects()` 在建窗时调用 `RecentProjectsStore.add()`，语义为「去重 + 置顶」——最后**打开**的项目居列表首位。
- **关闭窗口不写任何记录**：`closeEvent` 只保存窗口几何/会话快照，不触碰最近项目列表。关 B 再关 A，列表仍是 `[B, A]` 纹丝不动。
- 无参启动恢复**列表首项**：`main.py` 的 `_default_workspace()` 取 `config/recent_projects.json` 首项（过滤消失目录与解包目录后）作为默认工作区。

即：程序记住的是「最后**打开**的项目」，而非「最后**关闭**的项目」。现有行为与 VS Code 最近列表语义一致，本身不算 bug，但与用户「恢复最后工作现场」的预期不符。

### 0.3 目标

1. **恢复语义改为「最后关闭」**：无参启动时恢复用户最后关闭的窗口所绑定的项目。
2. **启动模式入设置中心**：新增偏好项「启动时」，二态——
   - **恢复上次项目**（默认）：无参启动恢复最后关闭的项目；
   - **空白窗口**：无参启动不加载任何项目（与 `--blank` / 新建窗口同形态）。
3. 两种模式用户可随时在设置中心切换，即时持久化，下次启动生效。

---

## 1. 关键决策

### D1 「最后关闭」独立成键，不扰动最近列表顺序（核心）

不复用「关窗时再 `add()` 置顶」方案。反例：「打开文件夹」换根关旧窗路径（`gui/main_window.py` `_close_after_spawn()`）——新窗启动 `add(新根)` 置顶后，2 秒探活成功旧窗 `close()` 若再 `add(旧根)` 置顶，列表首项就错回旧根，下次无参启动会打开用户早已离开的旧项目。要排除这类程序主动关窗需引入关闭来源标志位，且菜单「最近打开的项目」列表顺序会随关闭动作跳动，语义浑浊。

改为在 `config/recent_projects.json` 增设第二键 `last_closed_root`：

- `recent_projects` 列表维持「最近**打开**」语义不变（菜单消费侧零改动）；
- `last_closed_root` 仅由 `closeEvent` 写入（后关者胜，天然即「最后关闭」），仅由启动恢复路径读取。

### D2 写入收口在 `closeEvent`，全关窗路径天然覆盖

所有关窗路径（标题栏关闭按钮、菜单退出、换根关旧窗的 `self.close()`、系统关机）均汇聚 `QWidget.close()` → `closeEvent`，无需多点埋点。`closeEvent` 中 `_save_layout_state()` 之后追加：工作区根非 `None` 时 `set_last_closed(root)`。空白窗口（根为 `None`）不写——空窗没有可恢复的现场。

「换根关旧窗」场景在 D1 方案下天然正确：新窗启动不写 `last_closed_root`；旧窗探活关闭写入旧根；用户随后关闭新窗写入新根——终值为新根，正是用户最后的现场。

### D3 设置项选址与默认值

- 键名 `startup_mode`，值域 `restore`（恢复上次项目）/ `blank`（空白窗口），存 `config/settings.json`，走 `gui/settings.py` 既有「KEY_* 常量 + AppSettings 键 + DEFAULT_SETTINGS + load_settings 值域防御」标准流程。
- **默认 `restore`**：与现状行为族一致（恢复语义从「最后打开」修正为「最后关闭」），老用户升级无感；`blank` 为显式选择。
- `startup_mode` 是**偏好**而非历史数据，放 settings.json 正确；`last_closed_root` 是历史数据，放 recent_projects.json（沿用该文件选址论证：不随「恢复默认设置」被清）。
- 生效时机：启动决策在进程入口一次性做出，无法热切换——设置即时持久化、**下次启动生效**，页副标题文案写明。

### D4 显式参数优先于设置（维持既有优先级）

`main.py` 启动分流优先级不变：命令行 `folder` > `--blank` > 设置项。菜单「新建窗口」spawn `--blank` 不受影响；双击图标/无参启动才读 `startup_mode`。

### D5 「清除列表」连带清 `last_closed_root`

文件菜单「最近打开的项目 ▸ 清除列表」的语义是清空历史，`last_closed_root` 同属历史——`RecentProjectsStore.clear()` 整表重写时一并清除（否则清完历史下次启动仍恢复旧项目，与 `2026-0903-0305_清空最近项目后启动回退空白窗口修复计划.md` 的目标行为冲突）。

### D6 恢复落点的有效性回退链

`restore` 模式无参启动的解析顺序：

1. `last_closed_root` 存在、目录仍在、非解包目录 → 恢复之；
2. 否则回退遍历 `recent_projects` 列表首项有效者（兼容旧版无 `last_closed_root` 键的存量文件，以及最后关闭记录失效的场景）；
3. 全无效 → 返回 `None` → 空白窗口（`2026-0903-0305` 计划既有分支，零新代码）。

`_is_unpack_dir()` 防护对 `last_closed_root` 同样适用。

## 3. 验证方案

1. **函数级验证（项目 `.venv`，临时脚本落 `./.tmp/` 验完即删）**：
   - `set_last_closed(A)` 后 `get_last_closed()` 返回 A，且 `recent_projects` 列表键不受影响；
   - `clear()` 后 `get_last_closed()` 为 `None`、`list()` 为空；
   - `load_settings()` 对缺失/非法 `startup_mode` 回退 `restore`；
   - `_default_workspace()`（或更名后函数）：`blank` 模式返回 `None`；`restore` 模式 `last_closed_root` 有效时返回之、失效时回退列表首项、全无效返回 `None`。
2. **核心场景端到端（开发态 `uv run main.py`）**：
   - 开 A、开 B → 先关 B 再关 A → 无参启动 → **恢复 A**（本计划修复目标）；
   - 开 A、开 B → 先关 A 再关 B → 无参启动 → 恢复 B；
   - 设置切「空白窗口」→ 无参启动 → 空白窗口（欢迎占位、面板置灰）；
   - 设置切回「恢复上次项目」→ 无参启动 → 恢复最后关闭项目。
3. **回归场景**：
   - 「打开文件夹」换根关旧窗：A 窗换根到 C 后关闭 C 窗 → 无参启动恢复 **C**（D1/D2 防护点）；
   - `--blank` 与显式 `folder` 参数优先于设置（D4）；
   - 菜单「新建窗口」、清除列表后启动回退空白（D5 与 `2026-0903-0305` 计划回归）；
   - 恢复目标根已被活窗口占用 → 唤活已有窗口、退出码 3（一窗一根既有路径）。
4. **打包态端到端**：用户自行构建 AppImage（`building/build_appimage.sh`）复测场景 2。

## 4. 风险与影响面

- ⚠️ 行为变化：无参启动恢复目标从「最后打开」变为「最后关闭」——本计划目标行为；单项目用户（绝大多数场景）两者等价，无感。
- ⚠️ 边缘场景：「换根关旧窗」后新窗**崩溃**（非 `closeEvent` 的正常退出）时，`last_closed_root` 停留在旧根，下次启动恢复旧根而非新根。窗口崩溃非常态，且旧根仍是用户项目、列表首项为新根可一键回访，接受此残差。
- 多窗并发写 `last_closed_root` 为后关者胜——正是所需语义，无需加锁（沿用该文件「列表非关键数据，收敛即正确」的并发姿态）。
- 「恢复默认设置」将 `startup_mode` 重置为 `restore`（默认），`last_closed_root` 存 recent_projects.json 不受影响（D3）。
- 空白窗口关闭不写 `last_closed_root`：全空窗会话不会冲刷掉上次项目现场，再次无参启动（restore 模式）仍可恢复——符合直觉。
