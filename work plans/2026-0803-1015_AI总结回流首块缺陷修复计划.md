# AI 最终总结回流首块缺陷修复计划

## 1. 背景

用户实机观察发现：AI 回复若呈「开场白 → 若干工具调用（Read/Edit/Thinking
等卡片）→ 最终总结」结构，**最终总结不出现在对话末尾，而是跑到最前面**——
与开场白挤进同一个顶部正文块，观感上如同总结"覆盖/顶替"了第一段回复。
截图实证：开场白位置同时出现了总结内容，其后才是 Thinking/Read/Edit 卡序列。

本缺陷属于 0645 融合计划新轨（cards 轨道，`ChatTranscriptView`，块级
QWidget 追加式）特有；旧轨（classic，`gui/panels/chat/output.py`，
QTextBrowser 单文档）所有文本一律 `movePosition(End)` 插到文档末尾，
天然按到达顺序排列，无此问题。

## 2. 根因（已定位，代码走读）

新轨整轮对话**只建一个正文流式块**，且跨工具事件不作废：

1. 每轮发送时路由层调一次 `begin_stream("AI")`，创建正文块 A 追加到
   布局末尾；开场白 chunks 全部写入块 A。
2. 第一个工具事件到达，`append_tool_call` 先调 `_flush_stream()`——
   该方法**只把缓冲文本冲刷落块，不把 `_stream_block` 置 None**——
   然后工具卡追加到布局末尾（位于块 A 之后）。
3. 更多工具卡陆续追加在块 A 之后。
4. 最终总结 chunks 到达，`append_stream_chunk` 发现 `_stream_block`
   仍指向块 A（非 None），**总结文本被追加进块 A**——而块 A 在布局中
   位于所有工具卡之前，于是总结出现在对话顶部。

即：**任何「文本 → 非文本块 → 文本」交错，后段文本都会回流到首个
文本块**。受影响路径不止工具卡：`append_tool_update`、
`upsert_todo_block`、`append_reasoning_chunk` 均调 `_flush_stream()`
但保留 `_stream_block`。

旁证（簿记纪律不对称）：思维链卡 `end_reasoning` 用后把
`_thinking_card` 置 None；`reset_activity_anchors` 轮次收尾清空全部
簿记；唯独 `_stream_block` 在 `_flush_stream` 后不作废，形成遗漏。

已排除的嫌疑项：全 chat 目录无 `insert(0` 倒序插入（`_add_block`
用 `insertWidget(count-1)` 追加，正确）；正文块无 id 复用更新逻辑；
无排序/时间戳逻辑；无 UI 重建路径。

## 3. 修复方案（待拍板）

### 3.1 技术方案

`_flush_stream()` 在冲刷后将 `self._stream_block` 置 `None`——语义由
"冲刷缓冲"升级为"**封存当前正文块**"：

```python
# gui/panels/chat/transcript.py
def _flush_stream(self) -> None:
    """各非正文上屏方法的次序守卫：冲刷即封存（用后作废，同思维链卡纪律）。"""
    if self._stream_block is not None:
        self._stream_block.flush_stream()
        self._stream_block = None
```

效果链：工具卡上屏 → 块 A 封存作废 → 最终总结首帧到达时
`append_stream_chunk` 走防御分支 `begin_stream("")` 新建块 B，
`_add_block` 追加到**布局末尾**（所有工具卡之后）→ 顺序恢复为
「开场白 → 工具卡 → 总结」。

单点修改，四条受影响路径（tool_call / tool_update / todo / reasoning）
一并修复；`begin_stream` 与 `end_stream` 内部也调 `_flush_stream`，
置 None 对二者无害（`begin_stream` 随后立即赋新块，`end_stream`
本就再置一次 None，幂等）。

### 3.3 候选替代（弃）

- **工具卡插到当前正文块之前**：改动 `_add_block` 插入位——破坏
  "块只追加"的简单不变式，todo/思维链卡亦需跟随特判，复杂度高，不取。
- **文本帧到达时才建新块、工具帧到达时不冲刷**：等价于 D1-A 的效果
  但把作废时机分散到帧类型判断里，不如单点封存直白，不取。
