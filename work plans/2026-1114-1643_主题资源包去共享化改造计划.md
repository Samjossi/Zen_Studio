> **范围**：`src/ide/gui/theme.py` 六资源包架构改造、四主题资源包内联化、`tests/test_theme.py` 注册表回归重写

## 1. 背景与需求

当前四个主题共享六个模块级资源包常量（syntax/terminal/chrome/git_status/chat/git_graph），其中的蓝色（git 已修改态天蓝 `#1e88e5`、终端 blue、语法关键字蓝 `#0000af`、聊天时间线蓝、diff hunk 蓝带等）对所有非蓝主题都是违和色——暖米主题里 git 修改态显示天蓝、薄荷主题里终端 blue 槽是蓝即为例证。用户拍板：拆掉共享包，每款主题自带六包，共享包里的蓝全部按各主题色相归位替换，**全系统不再有任何「共享包里的蓝」**。

本计划只做架构改造与蓝色归位，不新增主题。

## 2. 现状机制与改造理由

主题体系为「唯一 QSS 模板 + 令牌渲染」（`assets/themes/README.md`）：`assets/themes/base.qss` 以 `$token` 占位，`src/ide/gui/theme.py` 的 `THEME_PALETTES[主题名]` 渲染替换；设置中心外观页下拉由 `list_available_themes()` 动态枚举；持久化 `is_valid` 兜底未知主题名回退默认主题。

资源包现状：`SYNTAX_PACK`（:139）、`TERMINAL_PACK`（:159）、`CHROME_PACK`（:170）、`GIT_STATUS_PACK`（:178）、`GIT_GRAPH_PACK`（:188）、`CHAT_PACK`（:221）六个模块级常量，四主题同对象共享（`tests/test_theme.py` :27-34 有 `_SHARED_PACKS`、`palette[key] is pack` 同一性断言，:71-78）。模块级 `WARNING_COLOR`（:199）是 UI 警示色单一来源，不在六包内，不动。`title_bar` 包已是每主题自带，不动。

**为什么反转既有的「资源包单套化」决策**（theme.py 头部 :9-12 注释，2026-07-20 模板化同期产物，当时背景是深色主题移除后只剩亮色系、色相趋同，共享单套最省维护）：如今主题家族已分化为蓝（cloud/sky）/橙（wheat）/绿（mint）多个色相阵营，继续共享一套含蓝的包，等于强迫非蓝主题接受异色。去共享化后每主题色系统一自闭，后续任何主题调色不再牵一发动全身。

**消费方零改动**：`get_theme_palette` / `git_status_color` / `git_graph_color` 等 API 签名与返回结构不变（返回值从「共享对象」变为「每主题自有对象」，消费方全部按键取值，不受影响）。实施时以 grep 六包常量名 + 三个查询函数做全量清单复查。

## 3. 目标

1. 六个共享包常量删除，四主题各自内联六包副本；所有原共享蓝键按 §5 表归位，系统内不再出现旧共享蓝值。
2. 消费方代码除 §2 表三处外零 diff，`bash scripts/check.sh` 全量门禁通过。
3. offscreen 截图走查通过（重点：git 修改态、终端 blue 槽、语法关键字、聊天时间线在各主题下不再违和）。

## 4. 非目标与硬边界

- 🔴 不改 `assets/themes/base.qss` 模板，不新增 qss 文件（模板化纪律不破）。
- 🔴 不改任何主题已有 qss 令牌值；去共享化只动六个资源包。
- 🔴 非蓝色键值逐值保留（实施后以测试断言守护）；唯一例外见 §8 决策点 D4。
- 🔴 不改主题查询 API、不引入新依赖、不新增主题。
- 🔴 默认主题 cloud 不变；既有四主题菜单顺序不变。

### 5.2 替换规则

- **蓝系主题**（cloud `#0765d4` / sky `#0284c7`）：保留蓝，但归位到自家 accent 同族——不再是全系统共用同一个蓝。
- **非蓝主题**（wheat 橙 / mint 绿）：蓝键替换为各自 accent 同族深色档。
- **硬约束：替换后不得与同包既有非蓝色撞色**（终端 ANSI 16 色相可分辨、git 五态可分辨、聊天时间线三档可分辨）。🟡 标记格为实施渲染走查重点，必要时在 ±同族内微调。
- **表外三键**：syntax 的 Name.Class / Generic.Heading / Generic.Subheading 原 `#2050a0` 亦属共享蓝，取本主题 Keyword 同族较浅档维持原层次关系（浅于 Keyword、深于注释灰），具体值实施时渲染走查定稿后锁进测试表。
- git_graph.remote（青）与 chat.timeline_tool_fg（青）按 D1 保留不动。

## 8. 决策点（请审阅时拍板）

- **D1 青色系算不算「带蓝」**：`#168396`、`#00a7b5` 等 cyan/teal。🟡 建议：不算，全系统保留（终端 ANSI 可分辨性依赖；青非蓝）。
- **D2 wheat 终端 blue 槽与 brown 槽近族**：🟡 建议：初值按 §5.3，走查撞色时**唯一例外**——允许微调 brown 槽明度（非蓝键的唯一改动口子，须在本计划实施记录中写明）。
- **D3 mint 的绿区**：🟡 建议：modified 按 §5.3 取深绿档 `#0f6e3f`（VS Code 式深绿修改态），untracked 保持中绿，靠明度区分。⚠️ 姊妹项目实践证明此路线最终被语义族回改（见 D6），若认同语义族口径请直接跳 D6 终值。
- **D4 表外三键（Name.Class / Generic.Heading / Generic.Subheading）**：🟡 建议：取本主题 Keyword 同族较浅档，渲染走查定稿后锁进测试表。
- **D5 单套化历史文档**：本次为反转决策，`文档/修改记录/` 需新增一条记录写明 why（单套化当时前提是亮色系色相趋同，现已分化为蓝/橙/绿阵营）。
- **D6（新增，本项目适配）`git_status.modified` 一次到位**：🟡 建议**直接采用姊妹项目终值**——cloud `#0765d4`（不变）、sky `#0369a1`（对比度 4.10→4.5+，族内加深）、wheat `#406da0`（低饱和蓝）、mint `#0765d4`（修与 untracked 绿撞色）。理由：姊妹项目已替我们走完「accent 归位 → 走查不满 → 语义族回改」整个循环，终值经用户二轮终裁。若坚持按 §5.3 初值执行，后续须再立语义族计划回改（即移植版 1311 计划）。
