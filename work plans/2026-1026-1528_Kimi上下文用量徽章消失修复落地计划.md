# Kimi 上下文用量徽章消失修复落地计划

> **状态**：已实施（修改记录：`文档/修改记录/2026-1026-1642_Kimi上下文用量徽章消失修复修改记录.md`）
> **范围**：AI 聊天面板状态行右侧上下文用量徽章；`kimi-acp` 的轮末用量采集、wire 兜底与模型上下文上限解析；相关测试和维护文档
> **时间**：2026-10-26 15:28（设计与调研，UTC+8）/ 2026-10-26 16:42（实施）
> **优先级**：高

## 1. 需求与现象

用户截图所示位置是 AI 聊天面板的**状态行**：输入区顶部横条，左侧为活动时间线色块条，右侧为上下文用量徽章，即既有「左条右徽」布局。

当前故障：

- Kimi CLI 后端的右侧上下文用量徽章不显示；
- 其他后端可正常显示；
- 前一天仍正常，用户关注到 Kimi 官方近期重置会员用量、调整计量及子代理行为，希望确认是否由官方流量计量协议变化引起；
- 本文只形成修复计划供审阅，本阶段不修改功能代码。

## 2. 结论摘要

**高置信根因在 Zen Studio 的 Kimi 用量采集链路，不在徽章布局，也没有证据表明是会员额度重置直接把徽章归零。**

具体是以下故障链：

1. Kimi 官方 ACP 已在每轮结束后提供 `usage_update`，其中 `used` 是当前上下文 token 数，`size` 是当前模型的实际上下文窗口；但该通知在 `session/prompt` 响应之后异步发出。
2. Zen 在收到 prompt 响应后立即结束本轮消费，随后下一轮还会清掉迟到通知，因此官方这份更直接、语义更正确的数据没有被利用。
3. Zen 唯一实际依赖的是私有 `wire.jsonl` 兜底，并错误地把 `llm.request.maxTokens` 当成上下文窗口。上游当前实现证明它来自 `maxCompletionTokens`，即输出预算；没有显式输出预算时还可以缺省。
4. 既有轮末等待逻辑还会把非 turn 请求计入必须配对的请求数，并在 3 秒超时后无条件返回 `None`，即使此前已经读到有效用量也一并丢弃。
5. 任一环节失效后，`_usage` 无法生成，GUI 按既有「无数据则空文本」规则显示为空白；其他后端不走这条 Kimi 私有 wire 链路，所以不受影响。

截至本次检索，Kimi 官方公告的「重置」是**会员月度额度补偿与用量重置**，不是把会话上下文占用清零。2.3.0 到 2.3.2 的相关上游源码也没有 `usage.record`、`llm.request`、token 计数或 ACP 用量推送协议差异。不能排除服务端存在未公告的计量或时序调整，但它不是解释或修复本故障所需的前提。

## 4. 本地代码证据与根因拆解

### 4.1 GUI 只是按无数据规则隐藏，不是布局故障

`src/gui/panels/chat/panel.py` 中：

- `_usage_label` 恒宽占位，布局始终存在；
- `_refresh_usage_label()` 在 `_usage is None` 时设置空文本；
- 只有收到有效 `Chunk(kind="usage", usage=...)` 或轮询得到有效 `UsageStats` 才显示百分比；
- `src/llm/providers/acp.py` 的 `map_usage_update()` 本身已能解析标准 ACP 用量帧。

因此不需要调整 QSS、状态行高度、控件宽度或活动时间线。

### 4.2 确定的语义错误：maxTokens 不是上下文窗口

`src/llm/providers/kimi_acp.py` 当前把末条 `llm.request.maxTokens` 作为 `UsageStats.size`，缺失就返回 `None`。

但上游当前实现为：

- `llmRequesterService` 用 `effectiveMaxCompletionTokens(request.params)` 生成该字段；
- `effectiveMaxCompletionTokens` 读取的是 `params.maxCompletionTokens`；
- `resolveCompletionBudget()` 在没有显式输出预算时返回 `undefined`；
- ACP 的上下文窗口另从模型目录 `max_context_size` 获取。

来源：

- [上游 llmRequesterService](https://github.com/MoonshotAI/kimi-code/blob/b8dd3a134060c6e80ba4a1659335cd63b68483f2/packages/agent-core-v2/src/agent/llmRequester/llmRequesterService.ts)
- [上游 completion-budget](https://github.com/MoonshotAI/kimi-code/blob/b8dd3a134060c6e80ba4a1659335cd63b68483f2/packages/agent-core-v2/src/llm-adapter/model/completion-budget.ts)
- [上游模型请求接口](https://github.com/MoonshotAI/kimi-code/blob/b8dd3a134060c6e80ba4a1659335cd63b68483f2/packages/agent-core-v2/src/llm-adapter/model/model-requester.ts)

这证明 Zen 早期「`maxTokens` 恒为上下文上限」的假设目前已不成立。即使某次记录中数值恰好等于窗口，也不能再把它当稳定协议使用。

### 4.3 确定的轮末时序缺口：官方通知被留在响应之后

`src/llm/providers/kimi_acp.py` 当前 response 分支只轮询 wire，随后立即 `return`。

`src/llm/providers/acp.py` 当前行为为：

- prompt 响应和 `session/update` 通知进入同一 `_updates` 队列；
- `purge_updates()` 在下一轮开头清空上一轮迟到通知。

上游却明确在 prompt 响应完成后异步发 `usage_update`。因此 Zen 已有解析器但收不到有效消费机会，这是确定存在的代码时序缺口。

### 4.4 确定的项目回归：超时丢弃已读到的有效用量

`2026-1023-1632_上下文用量徽章悬停输出速度落地计划.md` 和对应修改记录都要求：等待末条记录超时后，按已落盘子集计算，保持原用量徽章不退化。

当前 `_poll_wire_usage()` 却在截止时间到达时直接返回 `None`，没有返回本轮已经读到的新用量。这不符合原计划，也会把「只是末条晚到」放大成「徽章完全空白」。

### 4.5 确定的计数与配对盲区：非 turn 请求被混入

当前代码把所有 `llm.request` 都计入 `request_count`，要求新增的 turn 级 `usage.record` 数量必须达到该数才收尾。

上游请求来源却区分 `turn` 与 `operation`，只有 turn 来源产生 `turnStep`；压缩等请求也可写 `llm.request`，其用量 scope 不必是 `turn`。此外，速度解析会让任意 `llm.request` 覆盖待配对时间，非 turn 请求插在中间时会配错对象。

本次用合成 wire 做了无等待复现：

- `_read_wire_turn_stats()` 能读出 `UsageStats(used=120, size=262144)`；
- 文件额外存在一条无对应 turn 用量的请求时，`_poll_wire_usage()` 返回 `None`；
- 排除该额外请求对应的基线后，同一函数返回有效 `UsageStats`。

这证明「已有有效数据仍被轮末逻辑丢弃」可独立复现，无需假设官方变更。

### 4.6 现有测试为何没有报警

本次先运行既有相关测试：

- `tests/test_turn_speed.py`
- `tests/test_kimi_catalog.py`
- `tests/test_usage_badge_timing.py`

结果为 **33 passed**。但现有用例只覆盖旧 wire 字段、速度纯函数和 tooltip 文案，没有覆盖：

- response 后才到的 ACP `usage_update`；
- `maxTokens` 缺失或语义变化；
- 非 turn 请求参与计数；
- 超时但已有部分有效用量；
- ACP 与 wire 的优先级和去重。

## 5. 根因表述的证据边界

已证实：

- Zen 错用 `maxTokens` 的语义；
- Zen 漏收 response 后的官方 ACP 用量通知；
- Zen 超时会丢弃已取得的部分用量；
- Zen 的计数和速度配对未隔离非 turn 请求；
- 以上任一问题都能使 Kimi 徽章缺失或失真，而其他后端不受影响。

未声称已证实：

- 未读取用户真实会话正文、凭证或完整私有 wire，故不把某一个触发分支断言为此次唯一现场原因；
- 未发现 Kimi 在 2.3.0 到 2.3.2 之间更换相关公开协议，故不写成「官方已更换计量协议」；
- 不把服务端是否还有未公告调整当作确定事实。

实施时如需进一步确认当天触发分支，只使用用户提供的脱敏字段样本，或由用户在项目 `.temp/` 中提供只含记录类型、字段名、数值和时间戳的摘要。不得复制凭证、消息正文、工具参数、系统提示或完整会话到项目。

## 6. 修复目标与非目标

### 6.1 目标

- 恢复 Kimi 后端右侧上下文用量徽章；
- 百分比优先与 Kimi 官方 ACP 对外报告的上下文值一致；
- 保留轮内 wire 轮询带来的实时刷新能力；
- 保留 tooltip 中的会话计时、实时输出速度和上轮输出速度；
- 修复非 turn 请求计数、速度错配和超时丢弃部分用量；
- 不再把 `llm.request.maxTokens` 当上下文窗口；
- 无双源数据时继续保持诚实空态，不伪造 0% 或字符估算值。

### 6.2 非目标

- 不修改会员额度、`/usage`、计费或重置逻辑；
- 不修改 Kimi 用户配置，不降级或锁定 CLI 版本；
- 不修改上游 Kimi 仓库；
- 不调整状态行布局、活动时间线、颜色或控件宽度；
- 不改变其他后端的用量采集路径；
- 不新增静态模型上下文上限表，不把输出预算当窗口；
- 不通过单纯延长超时掩盖问题；
- 不全局删除 `purge_updates()`，避免串轮和旧通知污染。

## 7. 默认行为决策

### D1：ACP 为轮末主数据源，wire 为实时与兜底数据源

轮末优先级：

1. 有效 ACP `usage_update`：`source="push"`；
2. ACP 未到达或无效时，使用本轮新增 wire 用量：`source="transcript"`；
3. 两者均无有效数据：不生成用量帧，徽章维持既有空态或最后有效值，不清零、不估算。

选择 ACP 后，百分比可能相对旧 wire 公式变化。这是从「输入计费字段推导」改为「agent 报告的实际上下文占用」的语义纠偏，验收应对齐 ACP 与 Kimi 自身显示，不要求与旧公式数值相同。

### D2：轮末共用一个最长 3 秒窗口

- 保留现有 `_WIRE_USAGE_WAIT_S = 3.0` 的总体等待上限；
- ACP 通知接收、wire 完整性等待和 sidecar 尾部排干在同一收尾阶段交替进行；
- 不先等 3 秒 wire、再等 3 秒 ACP，避免把最坏等待翻倍；
- ACP 与所需 wire 数据都齐备可提前结束；
- ACP 已到但 wire 不完整时，可继续等待输出速度所需记录至共同截止点；超时按已落盘子集算速度；
- 如果没有 wire 会话目录，收到有效 ACP 后即可提前结束，不空等。

### D3：上下文上限来自模型目录，不来自 maxTokens

在 `src/llm/providers/kimi_common.py` 新增目录派生：

- 从 `kimi provider list --json` 的每个模型条目读取 `maxContextSize`；
- 与现有档位、显示名解析一致，先合并 `overrides`；
- 仅接受正整数；缺失、类型错误、非正数均不生成映射；
- 不写模型静态兜底表。

`KimiAcpLLM` 在工作线程的会话准备阶段按需加载并缓存「别名 → 上下文上限」映射：

- 不在 GUI 的 2 秒轮询中调用 CLI 子进程；
- 缓存赋值后只读，GUI 轮询与 worker 并发时保持现有原子赋值方式；
- 目录读取失败不阻断聊天，也不影响 ACP 主数据源；
- wire 记录中的 `modelAlias` 用于查上限，缺失时才用 provider 当前 `_model`；两者都无法确定时诚实返回无数据。

### D4：turn 请求只认带 turnStep 的记录

- 基线、轮末新增请求计数、速度配对均只使用带非空 `turnStep` 的 `llm.request`；
- 无 `turnStep` 的 operation、压缩或其他请求不得占用 turn 用量配额，也不得覆盖速度配对时间；
- 旧记录缺少必要字段时跳过对应条目，不用位置猜测其来源。

### D5：超时返回本轮已落盘的部分有效数据

- 若截止时本轮已有新增有效 wire 用量，返回最新一条，不得返回 `None` 把它抹掉；
- 只有本轮没有新增有效用量时才返回 `None`；
- 输出速度同样按有效配对子集计算；没有有效配对则仅省略速度行，不连累用量徽章。

### D6：推送语义如实标注，不冒充实测真值

- ACP 帧继续使用现有 `source="push"`，tooltip 显示「agent 实时推送」；
- 不把 ACP 的 `used` 写成「会员额度」或「纯 API 实测值」；
- 不因为官方默认策略含估算就给 ACP 数值自行加 `~`：该值是 agent 正式对外报告的上下文结果，且通知没有携带可用于 Zen 二次拆解的估算比例；
- wire 兜底继续使用 `source="transcript"`，估算来源的既有 `~` 规则不变。

### D7：wire 的 used 对齐上游实测上下文四项总和

wire `usage.record` 的 `used` 固定为：

`inputOther + inputCacheRead + inputCacheCreation + output`

依据是上游 `tokenUsageTotal()` 的同项求和，不再使用旧的 `inputOther + inputCacheRead` 两项公式。四项必须都是非负整数，任一缺失或类型错误则该条记录不参与定型，不能用 0 猜测补缺。

该值代表 API 实测上下文；ACP 默认还可能叠加未实测尾部估算，因此 wire 兜底允许与 ACP 略有差异，轮末通过 D1 的固定优先级避免两源反复覆盖。

## 8. 实施步骤

### 步骤 1：先补故障回归测试

新增 `tests/test_kimi_usage.py`，使用合成 ACP 帧和 `.temp/` 规则兼容的 pytest 临时目录，不访问真实会话。至少覆盖：

1. prompt response 之后才到 `usage_update`，最终仍产出 `Chunk(kind="usage")`；
2. ACP 的 `used/size` 原样进入 `UsageStats`，`source="push"`；
3. ACP 与 wire 同时有效时选择 ACP，且只更新一次最终用量，不发生 push 被 transcript 覆盖；
4. ACP 缺失时回退本轮 wire；两者都缺失时不伪造数据；
5. wire 中 `maxTokens` 缺失或与窗口不同，仍按目录 `maxContextSize` 计算；
6. 无 `turnStep` 请求不参与请求计数，也不破坏速度配对；
7. 截止时只有部分新用量，返回部分有效数据而非 `None`；
8. 完全无新增用量时仍返回 `None`；
9. 迟到的其他 session/update 不被静默丢弃，sidecar 尾部仍按原路径排干；

## 9. 风险与回滚

### 风险

- ACP `used` 采用官方 token_counting 策略，数值可能包含估算尾部；这是官方口径，不得与会员计费或旧 wire 输入公式混为一谈。
- ACP 与 wire 同时到达时若缺少统一优先级，可能出现百分比来回跳动；实现必须按 D1 单点选择最终值。
- 等待 ACP 时仍要处理 sidecar 和其他迟到帧，否则可能修复徽章却丢失工具卡尾部。
- 模型目录加载失败只能影响 wire 兜底，不得拖垮聊天或 ACP 主路径。
- wire 四项总和是 API 实测上下文，ACP 默认还可能包含估算尾部；两者存在合理差异时以 ACP 轮末值为准，不在 GUI 来回去重覆盖。

### 回滚

- 不涉及配置迁移、数据库、用户凭证或上游文件，回滚只需还原本项目代码、测试与文档；
- 若 ACP 双源收尾出现异常，可先恢复 wire 单源收尾，但必须保留 D3、D4、D5，不得回退到错误的 `maxTokens` 窗口假设和超时丢弃行为；
- 不建议通过降级 Kimi CLI 作为修复或长期回滚。
