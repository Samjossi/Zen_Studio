## 1. 背景与目标

### 1.1 一句话

把 Kimi ACP 连接链路退到「还没有任何客户端补偿」的 `c3b5910`，用 2.5.0 重跑原始长任务场景，看**症状是否仍然出现**；并用带外的 ACP 帧代理区分「上游没回包」和「我们自己卡住」。

### 1.2 已确认的三条事实

1. 2.5.0 退版后的「问题依然在」**不是**上游证据：4 条 `轮次响应`、0 条 `终态确认`，四轮全部卡在 `TurnStateTracker` 的 `trigger` 字段失配上（详见审计报告 §3）。
2. 同一份真实 wire，仅放宽 `trigger` 就返回 `normal`；2.7.2 原版也返回 `normal`。2.5.0 的其它终态证据是完整的。
3. 现有 `unknown` 分支没有任何出口，任何一次私有 wire 漂移都会把「可诊断失败」变成「静默挂死」。

### 1.3 本期目标

1. **拿到干净基线**：`c3b5910` 的全裸行为在 2.5.0 上可运行、可观测、可复现。
2. **回答一个问题**：原始「长任务后会话无响应」在全裸版本上是否复现。
3. **区分责任**：若复现，用带外帧证据判定是「上游没有回 `session/prompt` response」还是「客户端另有阻塞点」。
4. **不污染**：实验不触碰当前工作树、真实配置、真实会话数据与 CLI 安装。

### 1.4 非目标

- 不修复任何缺陷（本计划只取证；修复另案）。
- 不评价 B0 的 UX（停止失效是全裸版本的**已知必然**，不是新发现）。
- 不把 2.5.0 宣称为安全版本，也不宣称上游缺陷已消失。
- 不借机重构、不改 DSH/Local、不动卡片/主题/终端。
- 不在实验期间升级或降级 CLI。

## 2. 「问题」必须先定义

### 2.1 为什么要先定义

「问题还在」在 2.5.0 这次已经被证明可以被客户端自己制造。若不先定义可观察签名，实验会重复同一个错误：把新症状当成旧症状。

### 2.2 症状码

| 码 | 名称 | 客观签名（满足任一） |
|:---|:---|:---|
| S1 | 无响应 | 发送后 10 分钟仍 busy，且代理日志中**没有**该 requestId 的 `session/prompt` response |
| S2 | 假完成 | 代理已见 `session/prompt` response（`end_turn`），但之后仍有 `tool.call` 帧或测试工作区文件继续增长 |
| S3 | 停止失效 | 按停止后 60 秒内无收尾（无 `cancelled`、无 busy 解除、无进程退出） |
| S4 | 会话报废 | 只能新建会话才能继续对话（原会话 resume/继续发送均失败） |
| S5 | 重复执行 | 同一 prompt 对应的写操作在测试工作区发生两次 |

### 2.3 三态判定

| 判定 | 条件 |
|:---|:---|
| 复现 | 同一场景 ≥2 次出现同一 S 码，且有代理/文件证据 |
| 未复现 | 同一场景 ≥3 次均无任何 S 码，且代理显示正常 response |
| 不确定 | 证据缺失（丢帧、版本不明、场景被中断）→ 不计入分子也不计入分母，重跑 |

## 3. 基线与变量

### 3.1 四个候选基线

| 基线 | 提交 | 含什么 | 不含什么 |
|:---|:---|:---|:---|
| **B0 全裸（本期采用）** | `c3b5910` | 官方 ACP 单轮次、原始 `next_update(timeout=None)` | abort、看门狗、断管恢复、stopReason 分类、终态确认、`session/close`、待发闸门 |
| B1 原生简化 | `85cf8aa` | B0 + abort + 断管恢复 + stopReason | 终态确认、`session/close` 停止分流、待发闸门 |
| B2 再加固前 | `3c406cb^` | 同 B1 | 同 B1 |
| B3 当前 | HEAD | 全部 | — |

### 3.2 为什么 B0 是「极限」也是风险最大的

- B0 的停止**在设计上就依赖 agent 回包**：`cancel()` 只发 `session/cancel`，没有本地 abort。agent 沉默时停止按钮必然无效。
- B0 没有看门狗：挂起时界面不会自动中断，也不会提示。
- B0 没有断管恢复：连接 EOF 后原会话上下文无法接回。
- B0 的 Kimi 开轮前不调用 `purge_updates()`（连接层已有该方法，只是 Kimi 没用）：上一轮的迟到帧可能串进下一轮。

**因此：实验中出现 S3（停止失效）是预期结果，不能当作「问题复现」的证据，也不能当作新缺陷上报。** 它只用于确认「全裸状态确实回到了 11-18 之前」。

## 4. 落地方式（D1 决策）

### 4.1 方式 A：独立 worktree（推荐）

```bash
git worktree add --detach .temp/b0-naked c3b5910
cd .temp/b0-naked
../../.venv/bin/python main.py --blank
```

- 与当前 `main` 工作树物理隔离，零污染；
- 依赖与当前一致（`pyside6/pyte/ptyprocess/pygments`，`requires-python >=3.12`），可直接复用 `.venv`；
- 开发态配置与日志落在 `.temp/b0-naked/config/`，不碰 `~/.config/zen-studio`；
- 结束用 `git worktree remove .temp/b0-naked`（先确认无进程占用）。

**机制已实测（2026-11-22 11:44）**：用一次性目录 `.temp/.__wt_probe` 执行同一命令，`ADD_OK`；确认 B0 树内 `main.py` 与 `src/ide/llm/providers/kimi_acp.py` 均存在；随后 `git worktree remove --force` 删除，`git worktree list` 无残留。即路径与命令可直接采用。

### 4.2 方式 B：当前树内做「行为级剥离」

保留现有 `kimi/`、`acp/` 模块结构，只把终态确认、`session/close` 分流、待发闸门、abort、看门狗逐项摘除。

- 优点：可以与当前 UI 同源比较，混杂变量少；
- 缺点：需要写一批「反向补丁」，剥错一处就污染结论；且会动当前工作树。

### 4.3 对比

| 维度 | A：worktree | B：当前树剥离 |
|:---|:---|:---|
| 忠实度 | 高（就是那个提交） | 中（取决于剥离是否彻底） |
| 对当前树风险 | 零 | 有（误改/漏改） |
| 混杂变量 | 多（62 提交） | 少 |
| 回滚成本 | 删除目录 | 需要反向补丁 |
| 适用 | 先回答「上游还在不在」 | 后续定位具体防线 |

### 4.4 建议

**先 A 后 B。** A 用来回答「全裸会不会挂」；只有在 A 复现、且需要知道「是哪一层防线在起作用」时，才做 B 的分层对照。

## 5. 可观测性（本计划的核心，不可省）

### 5.1 为什么 B0 必须外挂观测

B0 没有任何自诊断：没有 `generation`、没有 `failure_reason`、没有 `终态确认` 日志。挂起时 UI 只是一个永远转的 busy，**无法区分「agent 在想」和「agent 已经丢了事件」**。若只看界面，实验会退化成「凭感觉」。

### 5.2 三种证据源

| 源 | 作用 | 边界 |
|:---|:---|:---|
| ACP 帧代理（带外） | 判定 `session/prompt` response 是否到达、何时到达、之后还有没有帧 | 只记元数据，不记正文 |
| `wire.jsonl` 元数据 | 判定 agent 内部轮次是否真的结束（`turn.ended`/`prompt.completed`/`step.end`） | 只读 `type/reason/turnId/promptId` |
| 测试工作区文件 | 判定工具副作用是否在「完成」后继续发生（S2/S5） | 只记录文件名、mtime、大小、哈希 |

### 5.3 帧代理的接入方式

B0 的 `_find_bin()` 顺序是 `PATH` → `$KIMI_CODE_HOME/bin` → `~/.kimi-code/bin`，因此用 PATH 前置即可，**不需要改 B0 代码**：

```
.temp/b0-run/bin/kimi          # shim（可执行）
```

- 参数为 `acp` → 启动代理，代理再拉起真实 `~/.kimi-code/bin/kimi acp`；
- 其它子命令（如 `provider list --json`）→ 直接 `exec` 真实二进制，不介入；
- 代理只做逐行转发，**不得**改写、排序、缓存或延迟帧；每行写完立即 flush；
- 子进程 stderr 原样透传到代理 stderr（B0 会排空它做诊断），不合并进 stdout；
- 子进程退出时记录退出码与信号。

### 5.4 帧日志字段（只记这些）

| 字段 | 说明 |
|:---|:---|
| `ts` | 单调时钟 + 墙钟 |
| `dir` | `c2s` / `s2c` |
| `method` / `id` | JSON-RPC 方法与请求号 |
| `type` | `session/update` 的 `update.sessionUpdate` 类型 |
| `stopReason` | 仅 response 帧 |
| `bytes` | 原始行字节数（用于发现截断/丢帧） |

**禁止记录**：prompt 文本、工具参数、工具输出、文件内容、任何凭证。

### 5.5 有效性前置检查（A0）

在跑任何长任务前，先跑一个短轮（例如「只回复 OK」）：

- 必须在 30 秒内完成；
- 代理必须看到 `initialize`、`session/new`、`session/prompt` request 与 response；
- 双向行数必须与 shim 计数一致（零丢帧）。

A0 不通过 → 环境无效，停止，不进入后续场景。

## 6. 场景矩阵

| 编号 | 场景 | 固定动作 | 主要观察 |
|:---|:---|:---|:---|
| A0 | 短轮基线 | 发一条要求只回复固定短句的消息 | 环境有效性、代理零丢帧 |
| A | 普通多轮 | 连续 3 轮问答，无工具 | 会话连续性、response 时序 |
| B | 前台长任务 | 两次前台 Bash `sleep 240`，再写标记文件并回复 | S1/S2、response 是否在任务结束后才到 |
| C | 后台任务完成 + 追问 | 启动后台任务 → 等其自然完成 → 立即追问 | 通知轮是否可见、追问是否被吞 |
| D | 后台任务停止 + 追问 | 启动后台任务 → 停止它 → 立即追问 | 停止通知轮、追问执行次数 |
| E | 手动停止 | 前台 Bash `sleep 60` → 中途按停止 | S3（预期失效，用于确认 B0 状态） |
| F | 断管 | 杀掉 agent 子进程 → 再发一条 | S4（B0 无 resume，预期会话报废） |

每个场景：新会话、固定提示词、记录 `sessionId`、跑完清理测试工作区与残留进程。

### 6.1 场景判定表

| B0 现象 | 帧代理证据 | 判定 |
|:---|:---|:---|
| A0 短轮完成 | 有 response | 环境有效，继续 |
| A0 短轮挂起 | 有 response | B0 自身另有阻塞点 → **停**，先查环境/代理 |
| B 挂起 | **无** `session/prompt` response | 上游未回包 → 原始根因链成立（S1） |
| B 挂起 | response 已到，之后仍有 `tool.call` / 文件增长 | 上游提前回包后继续执行（S2） |
| B 完成 | 有 response，wire 已 `completed` | 本轮未触发；加轮次或换场景 |
| E 停止无效 | 无 cancel 回执 / 无进程退出 | B0 设计必然（S3），只记录，不算复现 |
| F 会话报废 | EOF 后无 resume attempt | B0 设计必然（S4），只记录，不算复现 |

> 关键：**S3/S4 在 B0 上是「按设计如此」**，只有 S1/S2/S5 才是本实验要回答的问题。

### 13.4 Q1–Q3

### 13.5 与既有报告的互证 / 修正

- 复现并确认既有审计 §3.1：2.5.0 的 `turn.prompt` 无 `trigger` 字段（实测 3 条均无）。
