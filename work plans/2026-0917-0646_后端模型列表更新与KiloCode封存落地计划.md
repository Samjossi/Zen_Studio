## 1. 问题现象

用户提出两件事：

1. 各 CLI 后端上游模型有版本更新（Kimi 侧新增模型；DeepSeek 发布 V4.1 Flash），需更新模型列表——本次只覆盖 **Kimi / Reasonix / OpenCode** 三家。
2. **Kilo Code 后端封存**：不再官方维护。用户切换到该后端时，界面需明确告知「已转为个人维护项目；如需使用，请自行修改代码并重新编译」。

## 2. 现状诊断

### 2.1 模型列表全部是动态枚举，代码库内无静态模型表

四家后端的模型枚举均为运行时动态拉取（装配单点 `llm/registry.py` REGISTRY，:206-314）：

| 后端 | 枚举来源 | 实现 |
|:---|:---|:---|
| kimi-acp | `kimi provider list --json`（模型与强度档位同源同载荷） | `llm/providers/kimi_common.py:45` |
| reasonix-acp | 解析 `~/.reasonix/config.toml` 的 `[[providers]]` 段（无 CLI 枚举命令） | `llm/providers/reasonix_acp.py:137` |
| opencode-acp | `opencode models` 纯文本行，剔除 `opencode/` 前缀 Zen 模型 | `llm/providers/opencode_acp.py:98` |
| kilocode-acp | `kilo models` 纯文本行 | `llm/providers/kilocode_acp.py:107` |

**2026-09-17 实测基线**（`.venv/bin/python` 直调 REGISTRY 各 `list_models`）：

- **kimi**：`kimi-code/k3`、`kimi-code/k3-256k`、`kimi-code/kimi-for-coding`、`kimi-code/kimi-for-coding-highspeed`（后两者中的 `kimi-for-coding-highspeed` 相对注册表注释样本为新增）。强度目录实测：仅 k3 / k3-256k 有档位（low/high/max，默认 high），`kimi-for-coding*` 无强度轴——服务端目录下发，代码自动呈现，无需改动。
- **reasonix**：`deepseek-pro/deepseek-v4-pro`、`deepseek-flash/deepseek-v4-flash`（与注册表注释一致）。注意：DeepSeek 已于 2026-09-10 发布 **V4.1 Flash**（官方通告：V4 Pro 请求过渡期全部路由至 V4.1 Flash；另旧名 `deepseek-chat`/`deepseek-reasoner` 已于 2026-07-24 停用）。reasonix 无 CLI 枚举，**新模型需写入 `~/.reasonix/config.toml` 才会出现**——该文件在项目目录外，见 T6（用户配合项）。
- **opencode**：8 项——`deepseek/deepseek-chat`、`deepseek/deepseek-reasoner`、`deepseek/deepseek-v4-flash`、`deepseek/deepseek-v4-pro`、`kimi-for-coding/k3`、`kimi-for-coding/k3-256k`、`kimi-for-coding/kimi-for-coding`、`kimi-for-coding/kimi-for-coding-highspeed`。其中两个旧 DeepSeek 别名上游已停用，是否仍可调通待 T7 实测；枚举的黑名单前缀设计（`GATEWAY_MODEL_PREFIX`）会自动呈现用户新认证的 provider，无需维护名单。

**结论**：「更新模型列表」在代码层**不需要动枚举逻辑**（动态已覆盖）；真正要做的是：

- 同步各文件注释/docstring 中的实测样本登记（已漂移）；
- 验证新模型在 UI 的呈现链路（强度档位菜单、上下文徽章、图片支持声明）；
- reasonix 侧新模型落用户配置文件（项目外，用户操作）。

### 2.2 Kilo Code 封存面

**核心改动点**：`llm/registry.py:271-289` 的 `BackendSpec(name="kilocode-acp", ...)` 注册项。

**可直接复用的现成机制**：`BackendSpec.dev_note`（`llm/registry.py:84-88`）——非空时切换到该接口、以及恢复后首次发送，对话流各追加一条「系统」消息。消费点 `gui/panels/chat/panel.py:380-390`（`_show_dev_note`）+ `:862-865`（发送前兜底）。目前仅 dream 在用（`llm/registry.py:306-311`）。但 dev_note **只提示、不阻止使用**，不满足「要用就得自己改代码并编译」。

**其他引用点**：

- `gui/panels/chat/panel.py:674`：图片不支持时的提示文案「切换至 Kimi / Kilo Code 后端可使用图片缩略图附件」——封存后需去掉 Kilo Code。
- 实测：kilocode `available=True` 但模型枚举已返回空列表（kilo CLI 输出疑似已漂移），封存恰逢其时。
- 纯文档/致谢类引用不动：`README.md`、`NOTICE`、`gui/main_window.py:890`（关于对话框致谢）、`llm/README.md`、`scripts/probe_subagent_frames.py`（探针配置）、各审计报告——属历史留痕。
- `config/settings.json` 的 `model_versions` 残留 `kilocode-acp` 条目：**不动**（用户记忆数据，封存只是停用不抹除；发送拦截后该条目无实际效果）。

## 3. 方案

**D1：模型枚举代码零改动。** 三家后端均为动态枚举，新模型自动出现；只同步注释/文档登记与验证链路。

**D2：kilocode 封存 = 菜单可见可切换 + 切换即提示 + 发送拦截。** 用户明确要求「切换到那里的时候告知」，故不采用 `available=False`（那会让菜单标「（未检测到）」并禁用，用户根本切不过去、看不到提示）。具体：

- `BackendSpec` 新增字段 `archived: bool = False`（`llm/registry.py:84-88` 附近，与 dev_note 并列）。
- kilocode 注册项：`archived=True`；`vendor_label` 改为 `Kilo Code（已封存）`（菜单分组标题直接可见）；`dev_note` 写封存文案，大意：「Kilo Code 后端已封存，转为个人维护状态，不再随项目更新。如需使用，请自行修改 `llm/registry.py` 中 kilocode-acp 注册项（撤除封存标记）并重新编译。」
- 发送拦截：`gui/panels/chat/panel.py` 发送路径（仿 `:844-846` 既有「后端不可用」系统消息范式）：当前后端 `spec.archived` 为真时追加 dev_note 系统消息并中止发送。ModelBar 与设置中心两个入口最终都收敛到同一发送路径，一处拦截全覆盖。
- 重新启用方式即「手动修改代码并编译」：撤掉注册项的 `archived=True`（及视情况 dev_note），重新构建。

**D3：opencode 旧 DeepSeek 别名不处理代码。** `deepseek-chat`/`deepseek-reasoner` 是否仍可调通由 T7 实测确认；若失效仅在手册备注，不改过滤逻辑（黑名单前缀是既定设计 D6，新 provider 自动出现）。

**改动清单**：

1. `llm/registry.py`：`BackendSpec` 加 `archived` 字段；kilocode 注册项封存化（`archived`、`vendor_label`、`dev_note`）；kimi/reasonix 注册项注释中的实测样本更新为 §2.1 基线。
2. `gui/panels/chat/panel.py`：发送路径加 archived 拦截；`:674` 图片提示文案去掉「Kilo Code」。
3. `llm/providers/kimi_common.py` / `llm/providers/opencode_acp.py`：docstring 中实测样本登记同步（kimi 目录 4 项、opencode 8 项清单）。
4. `维护手册/后端CLI工具维护说明手册.md`：§3 Kilo Code 节首加封存标注；§4 Reasonix 补 DeepSeek V4.1 Flash 备注（新模型需写入 config.toml）；更新头部「最后更新」行。
5. `tests/` 新增封存行为测试（见 T5）。
6. **不动**：枚举/缓存/回退链逻辑、`config/settings.json`、README/NOTICE/致谢、探针脚本、dream 后端。

## 5. 影响面评估

- ✅ kimi/reasonix/opencode 枚举与缓存逻辑零改动，新模型呈现依赖既有动态链路。
- ✅ 持久化恢复安全：若 `model_backend` 恰为 `kilocode-acp`，启动恢复仍会切到它——dev_note 在恢复后首次发送前兜底提示 + 发送拦截，用户不会被静默卡住。
- ✅ ModelBar / 设置中心菜单无需改动：`vendor_label` 一改两处同时生效（`model_bar.py:164-173`、`settings_dialog.py:344-347` 均读同一字段）。
- ✅ 强度档位轴不受影响：kilocode 的 `list_efforts` 保留原样，封存不删代码。
- ⚠️ `BackendSpec` 加字段是注册表公共结构变更，构造点仅 REGISTRY 一处，带默认值不影响其他四家。
- ⚠️ T6 涉及项目目录外文件（`~/.reasonix/config.toml`）——用户已于 2026-09-17 明确授权代为操作；改动前备份原文件，改动仅追加模型条目，不动既有配置。
- ⚠️ opencode 旧 DeepSeek 别名若实测已失效，用户从菜单选中会收到上游报错——属上游模型退役的如实呈现，不在本次拦截范围。
