## 1. 背景与症状

客户报告 `2026-0811-0841_集成终端环境变量污染问题报告_ZenStudio.md`：在 Zen Studio（AppImage 版）**集成终端**内运行自带 Qt 6.10 的 PySide6 项目，启动即崩溃：

```
ImportError: .../PySide6/Qt/lib/libQt6Core.so.6: version `Qt_6.11' not found
(required by /tmp/.mount_zen_stekLeAF/usr/bin/_internal/libQt6DBus.so.6)
```

终端内实测：

```bash
$ echo $LD_LIBRARY_PATH
/tmp/.mount_zen_stekLeAF/usr/bin/_internal:/tmp/.mount_zen_stLFnhJj/usr/bin/_internal:/tmp/.mount_zen_stgmaiKL/usr/bin/_internal:/tmp/.mount_zen_stlOibGN/usr/bin/_internal
```

对照实验：`env -u LD_LIBRARY_PATH` 清除后运行完全正常。

---

## 2. 根因分析

### 2.1 机制链

1. AppImage 运行时挂载 squashfs 到 `/tmp/.mount_zen_st*`，执行 AppRun（`building/build_appimage.sh` 生成的 AppRun **本身不设** `LD_LIBRARY_PATH`，仅 exec 主程序）；
2. 污染源是 **PyInstaller bootloader**：onedir 形态启动时为让主程序找到 `_internal/` 内的私有库，向进程环境**前插** `_internal` 路径到 `LD_LIBRARY_PATH`——这对 IDE 自身运行是必要的，代码侧无法也不应干预；
3. 🔴 问题在派生侧：Zen Studio 派生**面向用户的子进程**时直接原样继承 `os.environ`，IDE 私有库路径随之泄漏进用户工作环境；`LD_LIBRARY_PATH` 优先级高于应用自带库路径，动态链接器抢到 IDE 打包的 Qt 6.11，与用户应用自带 Qt 6.10 冲突，加载失败；
4. **跨窗累积**：`gui/main_window.py` `_spawn_window` 原样继承环境再起 AppImage，新窗 bootloader 再前插**自己**的挂载点——报告实测值中 4 个 `.mount_` 条目即多次新开窗口层层叠加的结果。

### 2.2 影响面定界

凡「自带同类动态库但版本与 IDE 不同」的用户程序均中招（Qt、OpenSSL、ICU 等），纯命令行工具不受影响——隐蔽性强。

代码走查确认的面向用户子进程派生点（污染出口）：集成终端 shell（`gui/panels/terminal/session.py`）、ACP agent 长驻进程与模型枚举（`llm/providers/`）、Typora 调起（`core/external_apps.py`）、新开窗口（`gui/main_window.py` `_spawn_window`）。git 子进程不受影响，不在修复面。

## 3. 修复方案

### 决策点 D1：净化策略——整变量剔除还是按条目过滤

| 方案 | 内容 | 裁定 |
|:---|:---|:---|
| A | **按条目过滤**：从 `LD_LIBRARY_PATH` 中仅剔除 IDE 私有库条目（AppImage 挂载点特征路径 + 当前解包根），用户原有其他条目原样保留；过滤后为空则整个变量删除 | ✅ 采用：用户自设条目（CUDA、MATLAB 等）不受误伤 |
| B | 整个移除 `LD_LIBRARY_PATH`（报告建议 1） | ❌ 不采用：会误删用户合法自设条目 |

过滤判据（满足任一即剔除该条目）：

- 条目等于或位于当前解包根（`core/paths.py` 的 `PROJECT_ROOT`，frozen 态即 `sys._MEIPASS`）之下——覆盖 bootloader 前插的本窗 `_internal`；
- 条目含 `/.mount_`（AppImage FUSE 挂载点签名）——覆盖 `_spawn_window` 继承来的**其他窗口**历史挂载点（其路径与本窗解包根不同，仅靠上一条判据漏网）。

开发态（非 frozen）`PROJECT_ROOT` 为项目目录，正常不会出现在 `LD_LIBRARY_PATH` 中；判据天然幂等，开发态行为零变化，无需 `IS_FROZEN` 分支。

### 决策点 D2：净化落点——按派生点接入还是启动时一次性净化

| 方案 | 内容 | 裁定 |
|:---|:---|:---|
| A | 五个派生点各接 `user_process_env()` 取净化环境 | ❌ 不采用：改动面大，未来新增派生点忘接即漏 |
| B | **启动时一次性净化 `os.environ` 本身**：`main.py` 启动早期调用，此后一切派生点零改动自然继承干净环境 | ✅ 采用（用户裁定）：单点收口、防漏；glibc 动态链接器仅进程启动时读一次 `LD_LIBRARY_PATH` 并缓存，运行期改写不影响 IDE 自身 dlopen（Qt 插件懒加载不受波及）；跨窗挂载点累积亦自动根治 |

D2-B 的关键认知：「新窗原样重拉」本身不能解决问题——每个实例的 bootloader 会**自行再次前插**自己的 `_internal`（继承环境再干净也没用，一条污染即足以复现崩溃），所以净化必须发生在进程环境层面，D2-B 正是对该出口的收口。

### T1：新增子进程环境净化模块 `core/child_env.py`（已完成）

- `sanitize_environ(env=None)`：原地净化（缺省 `os.environ`），按 D1 双判据过滤 `LD_LIBRARY_PATH`，过滤后为空则整键删除（空串等价于注入「当前目录」进链接器搜索路径，必须避免），其余变量透传；
- `_is_private_lib_dir(entry)`：双判据判定，单独抽出便于探针单测；
- 依赖 `core/paths.py` 的 `PROJECT_ROOT`（frozen 判据全库唯一定点，禁止自行探测 `sys._MEIPASS`）；
- 已登记 `core/README.md` 模块表。

### T2：`main.py` 启动时一次性净化接入（已完成）

## 4. 风险与取舍

- ⚠️ 启动净化改写的是全局 `os.environ`：若未来出现「需要 IDE 私有库的内部子进程」会静默踩空（目前不存在这类进程；真有此需求时显式构造 env 即可）；
- ⚠️ 净化只处理 `LD_LIBRARY_PATH` 一个变量：`LD_PRELOAD`、`QT_PLUGIN_PATH` 等本次实测无污染（bootloader 不设），不做 speculative 扩展；后续若发现新污染变量，往 `core/child_env.py` 加判据即可；
- 取舍：git 子进程不受影响本就无需处理；报告建议的 AppRun 保存原值方案（`LD_LIBRARY_PATH_SAVE`）不采用——污染来自 PyInstaller bootloader 而非 AppRun，改 AppRun 拦不住；
- 开发态行为零变化（判据幂等），打包态真机验证为收口必经环节。
