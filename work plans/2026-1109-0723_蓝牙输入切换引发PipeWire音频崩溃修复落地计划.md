## 1. 背景与问题定义

用户在使用蓝牙音响作为输入设备时，通过音响或系统切换控件改到声卡输入，Zen Studio 会整个退出。实测呈现明显的单次特征：开机后第一次发生该切换时容易退出；此前已经成功切换过一次时，后续操作通常不再复现。

2026-11-09 07:18:11，用户再次触发问题。本次保留了系统日志与用户会话日志，已经能够把“IDE 退出”定位到原生音频线程段错误，不再只是现象猜测。

这不是普通功能失效，而是会中断用户工作、存在未保存数据丢失风险的进程级崩溃。修复目标不是勉强让提示音继续播放，而是首先保证：**无论系统音频设备如何切换，提示音后端发生何种原生故障，都不得带走 Zen Studio 主进程。**

原始排查交接见 `2026-1108-0540_蓝牙功能测试命令交接.md`。该文档当时明确记录“根因尚未确定”；本计划新增的是 2026-11-09 事故日志所提供的后续证据，不改写历史文档当时的结论。

### 2.4 证据能排除的方向

- **不是 Python 层主动调用退出**：原生线程 `SIGSEGV` 会直接结束进程，现有 `try/except`、`sys.excepthook` 与日志桥无法接住。
- **不是正常窗口关闭或双开占用退出**：事故 PID 没有正常退出码及收尾记录。
- **不是桌面整体重启带走全部应用**：同一秒内其他桌面应用仍在持续写日志；现有证据只支持 Zen Studio 自身原生崩溃。
- **不是 `bluetoothctl` 命令直接关闭 IDE**：本次场景是用户切换输入设备，日志证据链落在 Qt 音频上下文与 PipeWire，而非自动重连命令。
- **不是单纯找不到音频文件**：事故前同一提示音链路已经成功播放，崩溃点位于系统原生音频协议模块。

## 3. 原因分析

### 3.1 IDE 侧触发链

`src/gui/sound_player.py` 当前以 `QSoundEffect` 为提示音主路径：

1. 第一次播放时创建模块级 `_effect` 单例。
2. 单例为防垃圾回收中断播放而长期存活，即使声音播完也不会主动销毁。
3. 因此，Qt/PipeWire 的音频上下文与相关连接会留在 IDE 进程内。
4. 用户从蓝牙输入切换到声卡输入时，蓝牙免提语音通道、输入源、输出端及 WirePlumber 链接可能一起拆除和重建。
5. 驻留的 `QAudioContext` 在处理这次变化时进入 PipeWire 原生协议模块并发生段错误，IDE 主进程随之结束。

事故前已经出现提示音播放记录，与上述“第一次播放后单例常驻”的代码路径吻合。

### 3.2 为什么切换“输入”会影响提示音“输出”

这次操作不能被简化为一个互不影响的麦克风下拉框变化。蓝牙音响在免提模式下通常同时涉及输入、输出、SCO/HFP 通道与控制连接。日志明确显示默认 source 和 default sink 同时不可用，BlueZ 的 Hands-Free Voice gateway 与 WirePlumber 链接也在同一秒失效。

因此，即使用户主观操作是“从蓝牙输入切到声卡输入”，系统实际执行的是一组音频配置档案与设备图变化；正在驻留的输出音频上下文同样会收到冲击。

### 3.3 单次触发规律的解释边界

现有现象与以下竞态模型一致：开机后的首次配置档案切换需要拆除并重建蓝牙免提音频节点，驻留的 Qt 音频上下文正好处理失效连接；完成一次重建后，后续切换所面对的节点与连接状态已经不同，因此不一定再次踩中同一时序窗口。

但必须区分：

- ✅ **已确认**：本次崩溃线程、原生库、发生时间、设备拆除事件及所属应用作用域。
- ✅ **已确认**：当前提示音代码会在 IDE 内长期持有 `QSoundEffect`。
- 🟡 **合理推断**：设备图拆除/重建与 Qt/PipeWire 回调之间存在时序竞态。
- 🟡 **尚未确认**：PipeWire 内部具体哪个对象生命周期错误导致地址 `0x1c` 的访问，以及为何每次开机只出现一次。
- ❌ **不得承诺**：“它以后只会在开机第一次发生”或“第二次绝对安全”。单次表现是复现线索，不是安全保证。

如后续需要向上游报告具体空指针或生命周期缺陷，应另取核心转储与完整原生栈；本计划不等待上游定根因，先通过进程隔离消除 IDE 被连带退出的风险。

## 4. 修复目标与边界

### 4.1 必须达到

1. 提示音链路不再在 Zen Studio 主进程中创建或持有 `QSoundEffect`。
2. 蓝牙输入与声卡输入切换时，IDE 主进程不得因提示音音频后端故障退出。
3. 外部播放器自身即使异常退出，也只能影响对应子进程，不得影响 IDE。
4. 保留现有事件映射、设置开关、试听行为、同事件 0.5 秒防抖、跨事件不压制与多窗口独立播放语义。
5. 开发态与实际事故形态 AppImage 都必须验证；只跑 offscreen 测试不能宣告修复完成。
6. 所有自动测试继续禁止真实出声，临时文件只放 `.temp/`。

### 4.2 明确不做

- 不修改蓝牙服务、不重启 PipeWire/WirePlumber、不执行 `bluetoothctl power off`，不以系统级破坏操作作为修复手段。
- 不通过默认关闭提示音来伪装修复。
- 不新增 Python 包或系统依赖，不要求用户额外安装某个指定播放器才能保住 IDE。
- 不在本计划中重写 `src/gui/panels/viewer/media_viewer.py` 的内嵌音视频播放器。
- 不声称已经修复 PipeWire 上游缺陷，也不声称覆盖尚未发生事故的所有 Qt Multimedia 使用场景。

### 4.3 媒体查看器风险边界

媒体查看器在用户真正打开音视频时才懒创建 `QMediaPlayer + QAudioOutput`，理论上同样可能在主进程中形成 Qt 音频上下文；本次事故日志只证明了提示音路径，并未证明媒体查看器参与事故。

本计划通过移除提示音 `QSoundEffect` 关闭已确认的触发源，但保留以下诚实边界：**若用户已初始化媒体查看器，主进程中仍可能存在另一条 Qt 音频路径。**真机验收必须分别覆盖“未打开媒体查看器”和“已打开媒体查看器”两种状态；若后者仍能复现，应保留日志并另行立项做媒体播放进程隔离，不得把它隐瞒为同一修复已完成。

## 5. 方案选型

### 5.1 采用方案：外部播放器子进程作为提示音唯一主路径

当前 `src/gui/sound_player.py` 已有 `aplay/paplay/play` 系统播放器兜底，且 `src/gui/panels/viewer/media_viewer.py` 也复用该出口。本次不再把它放在 `QSoundEffect` 失败之后，而是直接作为提示音唯一播放路径：

- 每次播放启动一个短生命周期子进程。
- 主进程只负责选择文件、执行既有防抖、探测播放器与发起 `subprocess.Popen`。
- 音频解码、PipeWire/PulseAudio/ALSA 连接及原生设备变化全部移出 IDE 主进程。
- 子进程崩溃、被信号终止或返回非零时，最坏结果是本次没有提示音，不是 IDE 退出。

这是基于现有代码的最小结构变化，同时从进程边界上解决原生段错误不可被 Python 捕获的问题。

### 5.2 不采用的方案

| 方案 | 不采用原因 |
|---|---|
| 给 `QSoundEffect` 外层增加更多 `try/except` | 无法捕获原生线程 `SIGSEGV`，对本次崩溃无效 |
| 每次播放重新创建 `QSoundEffect` | 音频上下文仍在 IDE 主进程内，设备切换时仍可能崩溃 |
| 在设备切换前停止或销毁 `QSoundEffect` | 主程序没有可靠的“系统即将切换输入”前置通知；设备拆除回调期间已经进入危险原生路径 |
| 仅升级 Qt、PipeWire 或 WirePlumber | 尚无已验证的修复版本；系统库与 AppImage 打包库来源不同，不能把用户环境升级当作唯一防线 |
| 永久改用 PulseAudio/ALSA 后端环境变量 | 未经过针对性验证，且仍是在主进程中运行原生音频代码，隔离保证弱于子进程方案 |
| 默认关闭所有提示音 | 牺牲正常功能规避崩溃，不符合需求 |
| 本计划顺带重写媒体查看器 | 事故未证明该路径参与，扩大改动会增加回归面；先保留边界并单独验收 |

### 5.3 方案代价与接受理由

- 外部播放器启动成本高于进程内 `QSoundEffect`，但提示音是低频、短时事件，现有异步 `Popen` 不阻塞 GUI，代价可接受。
- 极简系统可能没有任何一个播放器。此时保持“记录警告、静默跳过本次声音”的降级，不影响 IDE；宁可少响一次，也不能冒主进程崩溃风险。
- 外部播放器本身的设备兼容性与音量混音策略由系统工具决定。本修复优先保进程存活，不顺带调整播放器优先级、音量规格或解码能力，避免无关行为变化。

## 6. 实施步骤

### 6.1 移除提示音的 Qt 音频驻留路径

修改 `src/gui/sound_player.py`：

1. 删除 `QSoundEffect` 与 `QUrl` 导入；`QTimer` 仅可保留给外部播放器子进程的异步回收使用，不得再用于 Qt 音频状态复查。
2. 删除 `_effect`、`_replay_armed`、`_STATUS_CHECK_MS` 等 Qt 音频状态。
3. 删除 `_arm_replay_when_ready` 与 `_fallback_if_failed`；外部播放器没有 Qt 的 `Loading/Ready/Error` 状态机，不再保留无效补偿逻辑。
4. 将 `_play(path)` 收敛为外部播放器入口，直接调用 `play_system(path)`。
5. 保持公开接口不变：`play_event_sound`、`play_completion_sound`、`play_preview`、`play_system` 的名称与调用方语义不变。
6. 保持 `_last_play_at`、`_DEBOUNCE_S`、事件到设置键映射、文件存在性检查不变，避免把崩溃修复与提醒策略调整耦合。
7. 保留 `_PID` 与播放日志，确保多窗口共用日志时仍能区分来源。

完成后，`src/gui/sound_player.py` 不得再导入或构造 `QSoundEffect`，也不得保留一个看似未使用、实际仍会初始化 Qt Multimedia 的模块级对象。

### 6.2 加固外部播放器子进程边界

继续修改 `src/gui/sound_player.py`，但仅限既有 `play_system` 职责：

1. 沿用 `aplay/paplay/play` 探测顺序与参数形态，第一轮修复不改变用户现有兜底偏好。
2. 继续使用参数数组和 `shell=False` 默认语义；音频路径作为独立参数传递，禁止拼接 shell 命令。
3. 保持 `stdout`、`stderr` 重定向到 `subprocess.DEVNULL`，避免后台播放器输出污染 IDE 日志或终端。
4. 启动前收割 `_procs` 中已经结束的子进程，并用 GUI 线程的 `QTimer` 延时复查仍在运行的播放器；进程结束后及时移出列表，不能只等下一次播放才回收，否则最后一次播放可能长期留下僵尸进程。
5. 对 `shutil.which` 已返回路径但 `Popen` 仍抛出 `OSError` 的情况补防御：记录包含 PID、播放器与文件名的警告，并尝试下一个可用播放器；全部失败时返回 `False`。
6. 收割子进程时如发现非零退出或负信号返回码，记录诊断日志；日志只用于后续定位，不向主流程抛异常。
7. `play_system` 的返回值继续表示“是否成功发起子进程”，不把异步播放尚未结束误报为已经播放成功。
8. 不增加后台轮询线程，不调用会等待播放器退出的阻塞式 `wait()`；定时回收只在 GUI 事件循环中执行非阻塞 `poll()`，没有存活子进程时不得留下永久轮询。

### 6.3 更新测试与测试纪律文档

修改 `tests/test_notification.py`：

1. 删除只对 `QSoundEffect` 有意义的导入、`_FakeEffect`、`_FakeSignal` 与 Loading 补播测试。
2. 将真实 wav 全链路用例改为打桩 `subprocess.Popen`：断言选择了真实存在的 `done.wav`、命令参数正确、父进程侧不抛异常，但绝不真正启动播放器。
3. 保留同事件防抖、窗口过期、跨事件、试听豁免、事件文件映射、未知事件与缺文件等现有用例，确保提醒语义零回归。
4. 新增播放器探测用例：首个命令存在时只启动对应命令；全部缺失时返回 `False` 且不调用 `Popen`。
5. 新增 `OSError` 降级用例：第一个播放器启动失败后尝试下一个；全部启动失败时返回 `False`，异常不越过 `play_system`。
6. 新增子进程回收用例：已结束对象会从 `_procs` 移除；模拟非零或信号返回码只记日志，不导致播放调用抛异常。
7. 新增架构守卫：提示音模块不再暴露 `QSoundEffect`、`_effect` 或 `_replay_armed`，防止以后无意把主进程原生音频路径加回来。
8. 测试中的进程桩需覆盖 `poll()` 与返回码，不依赖真实声卡、PipeWire 状态或外部命令是否存在。

修改 `tests/README.md`：

- 把“`QSoundEffect` 换假后端”的现行方式更新为“`subprocess.Popen` 必须打桩”。
- 保留历史事故说明，但明确它描述的是旧实现，不再指导新代码继续创建 Qt 音频假后端。
- 继续强调 offscreen 不会关闭音频，任何测试都不能真实出声。

`tests/test_media_viewer.py` 中对 `play_system` 的公共出口打桩应保持有效；若因加固后的返回码或日志语义需要调整，只改测试桩，不改变媒体查看器产品行为。

## 7. 验证方案

### 7.1 自动化验收

必须同时满足：

- 全量测试通过，且运行期间没有真实提示音外放。
- 提示音测试证明只发起外部播放器子进程，不创建 Qt 音频对象。
- 防抖、试听、事件映射、设置开关与多窗口进程模型相关旧测试无回归。
- 模拟播放器不存在、启动失败、非零退出、被信号结束时，主调用链均不抛异常。
- AppImage 构建成功，产物内提示音资源完整。

### 7.2 真机安全前置

真机切换测试具有真实崩溃历史，执行前必须：

1. 保存全部工作，关闭浏览器及其他重要应用；被测 Zen Studio 使用不含未保存工作的测试窗口。
2. 优先在独立测试机或独立测试会话验收。
3. 保持主机蓝牙适配器开启，只操作用户原本使用的输入切换控件；不得关闭蓝牙服务或桌面进程。
4. 记录每步时间、使用的是开发态还是新 AppImage、原输入与目标输入、是否播放过提示音、是否打开过媒体查看器。
5. 若再次出现退出，立即停止重复复现，先采集事故前两分钟起的 `journalctl -b` 与 `journalctl --user -b`，日志副本保存到 `.temp/`。

### 7.3 核心真机用例

| 编号 | 场景 | 步骤要点 | 通过标准 |
|---|---|---|---|
| A | 开机后首次切换，严格复刻事故 | 冷启动登录后，在尚未做过任何输入切换的状态下启动新 AppImage；蓝牙输入有效；通过设置中心试听一次；保持 IDE 空闲后切到声卡输入 | IDE 不退出、不闪退，窗口与会话仍可操作；无新的 `QAudioContext` 段错误 |
| B | 播放结束后驻留 | 播放提示音后等待超过声音长度，再执行蓝牙输入与声卡输入互切 | 多次操作 IDE 均存活；旧实现单例常驻场景已不存在 |
| C | 播放过程中切换 | 连续触发试听，在短提示音可能仍未结束时切换输入 | IDE 均存活；最多允许本次声音中断，不允许主进程退出 |
| D | 第二次及往返切换 | 完成一次成功切换后，再往返切换数次 | 不因“第二次通常安全”而放松标准；每次都应存活 |
| E | 提示音功能回归 | 分别触发完成、失败、提问与手动试听；检查同事件快速重复与跨事件连续提醒 | 有播放器时提示音可听；防抖与试听语义符合原计划 |
| F | 无播放器降级 | 在隔离测试环境模拟三个播放器均不可用，或在单元测试中覆盖 | IDE 正常运行，记录警告，无未捕获异常 |
| G | 子进程故障隔离 | 用隔离假播放器模拟非零退出或信号终止，不使用真实系统蓝牙服务 | IDE 存活，故障仅归属于子进程，日志可诊断 |
| H | 媒体查看器边界 | 分别在从未打开媒体查看器与已经初始化媒体查看器两种状态下执行输入切换 | 前者必须全部通过；后者若崩溃则记录为另一路径未覆盖，不得把 A–G 的通过夸大为全场景修复 |

### 7.4 进程与日志核验

- 对只使用过提示音、从未初始化媒体查看器的被测进程，不应再出现由提示音创建的常驻 `QAudioContext` 线程。
- 外部播放器应表现为独立 PID 的短命子进程，不得成为新的常驻后台服务。
- 切换后检查 `zen-studio.log`：不应出现原事故 PID 的异常消失；正常操作期间也不应有未捕获异常。
- 检查系统日志：不得新增归属于 Zen Studio 提示音链路的 `QAudioContext ... segfault`。
- 若外部播放器自身出现非零或信号退出，应能区分其子进程 PID 与 IDE PID；IDE 仍存活才算隔离有效。

### 7.5 完成判定

只有以下条件全部满足，才能把修复标记为完成：

1. 自动化测试与本地门禁全绿。
2. 新 AppImage 的核心真机用例 A–G 全部通过。
3. 用例 H 已执行并如实记录结果；若暴露媒体查看器独立崩溃，必须单列开放项，不能隐瞒。
4. 原始事故链所涉及的提示音 `QSoundEffect` 已从代码和运行时移除。
5. 实施后修改记录明确区分“自动化已通过”“真机已通过”“上游根因仍未定”三种状态。
