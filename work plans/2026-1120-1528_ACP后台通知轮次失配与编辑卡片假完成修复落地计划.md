### 2.4 同一模式的第二次触发

15:18:13，GUI 探针因 offscreen `QToolButton.showMenu()` 悬挂而被 `TaskStop`。其后再次出现：

`prompt.steered` → 当前步骤 `finishReason=tool_use` → 当前通知轮次 `turn.ended reason=completed` → 新的 `origin=task` 通知轮次。

同一模式在一次会话中连续出现两次，已经将上午审计中的“高置信诱因假设”升级为有直接时序证据的故障链。

### 2.5 根因分层

1. **直接上游异常**：ACP 响应宣称 `end_turn`，但对应用户轮次缺失、未执行，或最后模型步骤仍为 `tool_use`。
2. **通知调度缺陷**：后台任务通知被拆成内部轮次，并与 ACP 请求完成、后续用户 prompt 排队发生状态错位。
3. **IDE 信任边界缺失**：`src/ide/llm/providers/kimi_acp.py` 收到 response 后只做 `stopReason` 分类和用量收尾；`end_turn` 直接正常返回，没有核对通知轮次和用户 prompt 执行状态。
4. **危险接续**：界面解除 busy 后允许待发或用户新消息进入仍处于内部通知轮次的 agent，进一步触发丢执行与假完成。
5. **独立验证工具缺陷**：offscreen 模态菜单悬挂产生长时间任务和 `TaskStop` 通知，增加了竞态触发机会。

## 4. 设计决策

### D1 ACP response 仍是主信号，但不再无条件下等同任务成功

正常无通知轮次保持现有协议行为。只有出现后台通知、内部轮次、用户 prompt 缺失或 `tool_use` 终界等风险证据时，才进入一致性核对；不因普通对话额外等待私有 wire，也不把 wire 变成所有后台的通用协议。

这是对 0946 期“不能只靠 stopReason”的直接补洞：上游返回 `end_turn` 时，IDE 仍需能识别明确矛盾，但不能凭正文、工具数量或固定延迟猜测完成。

### D2 新增 Kimi 主 wire 的轻量轮次元数据跟踪器

跟踪器只解析必要字段，不记录或输出 prompt 正文、工具参数与工具输出：

- 字节游标与残行缓冲；
- 用户 `promptId`、`turnId`、`origin.kind`、`trigger`；
- `prompt.steered` 的 active prompt 与通知 ID；
- 各轮 `step.end.finishReason`；
- `turn.ended`、`prompt.completed`；
- 当前活跃的内部通知轮次及起止顺序。

优先复用现有增量 JSONL 的残行纪律，但不强制重构用量和子代理模块。文件截断、半行、短暂不存在和格式漂移不得使 reader 崩溃或重复计数。

### D3 明确四种轮末状态，禁止混为一个布尔值

| 状态 | 判定 | 界面与后续动作 |
|:---|:---|:---|
| `normal` | 无内部通知风险，或用户 prompt 已完整执行且最后步骤为 `end_turn`，agent 已空闲 | 走现有成功路径，只收尾一次 |
| `draining` | ACP response 已到，但内部通知轮次仍活跃，暂未发现用户轮次矛盾 | 保持同步中，不播报成功、不发待发；继续显示工具帧并排干通知，落定后再判 |
| `desynchronized` | 用户 prompt 未出现/未完成、在 `tool_use` 后提前完成，或 response 与活动通知轮次明显错位 | 等活跃 agent 安全落定后走非成功失配收尾，保留下一轮恢复 |
| `unknown` | 已进入风险核对，但 wire 不可用、损坏或信息不足，无法证明一致 | 风险轮次 fail closed，不得为兼容而播报成功；正常无风险轮次不受此限制 |

不新增全局长驻状态机。状态只在 Kimi 当前轮次及必要的通知排空期间存在，安全收尾后收敛到现有正常或恢复待处理状态。

### D4 活跃通知期间保持可见、可控，不制造第二个隐藏后台

进入 `draining` 或发现 `desynchronized` 且 agent 仍活跃时：

- worker 保持本轮受控生命周期，GUI 显示“正在同步 Kimi 后台通知轮次；完成与待发已暂停”；
- 继续消费 ACP update 与必要 wire 元数据，让编辑卡片和工具结果可见；
- 停止按钮与本地 abort 保持可用；看门狗沿用现有设置，不另设短超时强杀任务；
- 不调用 `session/resume`，不启动第二个 provider，不新建标签，不自动补发任何 prompt；
- 连续通知可被同一排空循环跟踪，不能每来一个通知就创建新 worker。

若连接在此期间死亡，立即转既有断管失败与恢复路径。

### D5 失配落定后 fail closed，恢复原会话但不重放副作用

活跃内部轮次安全结束后：

- 若原用户轮次完整且一致，才允许一次正常成功收尾；否则抛出明确的 `TurnDesynchronized` 或等价专用异常。
- 失配走非成功路径：保留已显示正文和工具卡片、回滚可重发的用户历史、取消待发、保留输入草稿，不播放任务完成通知。
- 界面提示原请求未被确认完成、工具副作用需核对、下一次手动发送将恢复原会话。
- 标记 Kimi 下轮恢复；只有用户新的手动发送才执行重建与 `session/resume`，原中断 prompt 和追问均不得自动重放。
- 恢复失败继续 fail closed，不静默 `session/new`。

### D6 阻止通知轮次期间的新 prompt 与自动待发

response 后即使原轮次看似有效，只要跟踪器仍看到内部通知活跃，就不得让面板自动待发立刻进入 `session/prompt`。若用户在同步期间输入，沿用单条待发驻留输入框；同步结果为失配时取消自动发送并保留草稿。

provider 在下一轮 `begin_turn()` 前再次检查是否仍需 drain，不能仅依赖 GUI 防重入。GUI 与 provider 两层都应有守卫，但状态来源保持唯一，避免各自维护互相矛盾的布尔标志。

### D7 保留停止、用量与通知优先级

- 用户停止优先于 agent `cancelled`、失配与看门狗文案。
- `cancelled`、`max_tokens`、`max_turn_requests`、`refusal` 的现有分类不变。
- 一致性核对与现有轮末用量窗口协同，不用固定 sleep 替代状态判断；通知排空期间的 usage 只更新徽章和消耗一次。
- 失配、恢复失败和正常完成不得重复发出完成声音或桌面通知。
- DSH、Local 的正常完成、失败、停止与用量路径不变。

### D8 上游修复必须覆盖两个契约缺口

以脱敏最小复现向 Kimi CLI 上游提交两项明确要求：

1. 原用户轮次仍有 `tool_use` 后续工作时，后台通知 steering 不得使对应 ACP prompt 提前以 `end_turn` 完成。
2. 内部通知轮次期间收到用户 prompt 时，必须二选一：可靠排队并最终形成恰好一个用户 `turn.prompt` 后再响应；或立即返回明确错误。禁止只更新 `lastPrompt`、未执行却返回 `end_turn`。

上游修复与 IDE 防护并行，不把“已提交 issue”当作 IDE 可以停止防护的理由。默认只制作 `.temp/` 内复现和脱敏材料；修改本机 CLI 安装、配置或任何项目外文件必须另行取得用户明确同意。

### D9 GUI offscreen 探针移除模态阻断

- offscreen 验证禁止 `QMenu.exec()`、`QToolButton.showMenu()` 等依赖模态事件循环的路径。
- 菜单截图采用非模态、可证明不阻塞的布局与 `grab()`；若隐藏控件抓取不可靠，使用普通 `show()` 加明确关闭，不进入模态循环。
- 探针由有界 subprocess 超时保护，并在 `finally` 关闭控件和回收进程；不再把 `TaskStop` 当作普通测试清理手段。
- 普通 GUI 验收与“后台通知竞态复现”分开执行，避免无关通知污染对照组。
- 除非真实生产路径也出现同样问题，本项只改探针、测试和视觉验证指南，不借事故重构生产菜单。

### D10 日志只记录元数据，足以重建时序

补充 response 请求 ID、session ID、连接代次、用户 promptId/turnId、通知 ID、origin/trigger、最后 finishReason、一致性判定、drain 起止、失配原因、空闲确认和恢复结果。禁止记录 prompt 正文、完整工具参数、工具输出、diff、凭证和完整 wire 原文。

## 5. 明确否决的做法

- 不只把 `end_turn` 也改成失败：这会破坏所有正常对话，且没有解决通知调度。
- 不在 response 后固定等待几秒就宣布成功：通知延迟和内部轮次时长不可预测。
- 不发现失配就立即 kill 或 `resume`：旧 agent 可能仍写文件，会造成双客户端和重复副作用。
- 不自动重放原 prompt 或用户追问：Edit、Bash、提交等操作不可假设幂等。
- 不仅靠隐藏工具卡片或关闭提示音掩盖状态分裂。
- 不把私有 wire 解析扩散到 DSH、Local 或公共 ACP 层。
- 不通过禁用所有后台 Bash 来回避问题；后台任务本身是正常能力，必须修其通知边界。
- 不用 570 项或更多假后端测试替代真实 Kimi 与 AppImage 验收。

**检查点**：本次事故夹具在旧代码走成功，在新代码绝不走成功，且后台活动不脱离面板控制。

## 7. 验收条件

### 7.1 安全与功能

- 原用户 prompt 未执行或在 `tool_use` 后提前结束时，成功通知、成功历史和自动待发均为 **0**。
- 通知轮次活跃时，新 ACP 用户 prompt 发送次数为 **0**；工具活动仍可见，停止仍可用。
- 失配时活跃 agent 被盲目 kill/resume 次数为 **0**；空闲后原 prompt 自动重放次数为 **0**。
- 用户新手动指令恢复后只发送一次，session ID 不变，已发生写操作不重复。
- 正常对话不被私有 wire 缺失拖入失败；只有已出现通知/失配风险的轮次才 fail closed。
- offscreen GUI 探针无模态悬挂，失败有明确超时与清理，不依赖 TaskStop。

### 7.2 诊断与隐私

- 每次失配可由请求 ID、promptId/turnId、通知 ID、finishReason 和 drain/recovery 结果重建时序。
- 日志不记录正文、完整工具参数/输出、diff、凭证或无界 wire。
- 上游报告仅含脱敏元数据和最小临时复现。

### 7.3 工程与交付

- 新增故障矩阵、相关旧回归、隐私扫描、ruff 和全量 pytest 全绿。
- 真实 Kimi 原始场景通过，且最终 AppImage 同步通过；未完成项必须明示。
- 断管恢复、停止原因、分页器、用量徽章和 Token 消耗无回归。
- 所有测试数据、截图和临时仓库只放 `.temp/`，不修改项目外 CLI 或用户配置。

## 8. 风险与注意点

- **私有格式风险**：wire 不是公共 ACP 契约，因此只做 Kimi 风险轮次的矛盾检测；解析失败不得影响正常无风险轮次。
- **长通知轮次风险**：drain 可能持续数分钟，必须沿用看门狗和用户停止，不能用短超时强杀以换取表面稳定。
- **副作用风险**：失配后最重要不是立即恢复连接，而是先确认旧 agent 不再写文件。
- **误判风险**：合法后台通知可以晚于正常用户轮次，需区分有效完成后的 drain 与 `tool_use`/prompt 缺失的失配，不能一律报错。
- **用量风险**：延长消费窗口可能遇见重复 usage 和消耗记录，必须沿用基线与幂等键。
- **UI 风险**：同步中继续接收迟到帧，不能误开新 assistant 历史或重复渲染旧工具卡。
- **范围风险**：不借本期重做所有 provider、会话持久化、新标签重挂接或通用 Worker 信号；这些可另立计划。
- **外部修改风险**：上游报告和 `.temp/` 探针属于本计划；修改已安装 CLI、用户配置或项目外源码需另行明确授权。
- **真实性风险**：上游不可用或 AppImage 未验收时，只能写“代码已实施、真实场景待验证”，不得宣称完整修复。
